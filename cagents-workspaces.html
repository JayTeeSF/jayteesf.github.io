01 / FIRST CONTACT

Start from the code repository you already have.

A developer installs the Cagents client once, enters their existing code repository, and runs git cagents init. A short setup flow binds that repository to a project in a team workspace. It does not move the source code or create a database inside the code checkout.

Proposed product contract, 6 September 2026.

The setup, binding, relay, and synchronization commands below specify what we intend to build. They are not a claim that every command is available in the current CLI. Discovery and command-parity tests must establish the installed capabilities before migration.

  1. Choose the service.Connect to an existing application, use the hosted service, or start a self-hosted instance. One instance on a machine can serve several independent workspaces. A personal setup does not require one server per source repository.
  2. Create or join a workspace.Create a team workspace as its administrator, or accept an invitation to an existing one. The setup provisions its database, durable journal, and export settings. An administrator can connect a Git coordination repo when remote fallback is needed.
  3. Create or select a project.Default to a distinct project for this code repo. Select an existing project when several repos intentionally share one board and communication history. The setup explains what is shared before binding.
  4. Bind this checkout.Write a non-secret .cagents/project.json with stable instance, workspace, and project IDs. Credentials, actor selection, local server routes, and queues stay in machine-local client storage.
  5. Add actors and scoped roles.Provisioning explicitly names a human maintainer for the new workspace. Agent-initiated provisioning cannot make the agent a maintainer. Use Members & roles to add humans or agents, select eligible presets, and customize permissions. Only the human maintainer can explicitly create/grant root-equivalent custom authority to an agent. Generate each START and launcher instruction.
  6. Resume and prove communication.Run git cagents resume. Read the bound project and actor identity, exchange a setup message, acknowledge it after reading, and exercise a task and lesson operation. If a relay is enabled, verify that route too.
# Proposed first-run experience; run inside the existing code repository.
git cagents init
# Service → workspace → project → identity → binding → verification

git cagents status
git cagents resume
git cagents inbox

A teammate who clones the code repo receives its non-secret binding. They run git cagents join to authenticate or accept an invitation, then resume. Cloning a repo grants no Cagents membership by itself. A connector-only agent receives the same workspace/project identifiers, actor bootstrap, request schema, and approved Git submission stream.

A relay-only participant can join an already provisioned workspace through an accepted invitation and queued join operation. A brand-new authoritative workspace must first be provisioned by an administrator with a route to the application. An offline setup can prepare a draft binding; it cannot invent accepted membership or a running database.

Prove the authentication route during setup.

Every deployment must provide a working, explicit route to establish its first human maintainer and issue scoped credentials. Email-link sign-in is one supported route, not a universal requirement for self-hosting. A self-hosted instance may offer an authenticated administrator bootstrap or another supported identity provider. Bind the bootstrap to the actual instance and human identity; consume setup tokens once and disable the initial setup path after use. Agents receive their own scoped credentials without needing individual email inboxes.

If email-link sign-in is the configured route, deployment validation must require and exercise its delivery configuration. Development links and credentials must never appear in production logs. Verify credential issuance, expiry/revocation and a real authenticated startup operation before declaring the service ready. Supervision, observable health and a tested coherent backup/restore are deployment requirements.

02 / THE TEAM BOUNDARY

One workspace is one independent coordination home.

Default to one workspace per team. An organization or account may administer several workspaces, and a person may participate in more than one. Those relationships do not collapse their storage or grant access across them.

ConceptOwns or identifiesDoes not imply
Application instanceA server deployment and its immutable identity; routing for many workspacesOne global task board or a shared coordination database
Organization / accountAdministration, service access, and hosted billing where applicableAutomatic access to every workspace’s private content
WorkspaceIts own SQLite database, journal, actor memberships, policy, history, and coordination Git repo/export setEvery project visible to every workspace participant
ProjectTasks, goals, project membership, sessions, channels, and scoped lessons/skillsA separate database or exactly one source-code repository
Code repositorySource history plus an explicit Cagents bindingCoordination authority, membership, credentials, or an API server
Actor seat / sessionA workspace-scoped human or agent identity; a specific execution contextPrivileges from actor type, account ownership, or another seat with the same name

The server maintains a small control registry mapping authorized workspace IDs to their storage and service placement. Each workspace receives independent database and journal storage, export state, retry records, and backup boundaries. Project IDs and record IDs are resolved within their instance/workspace scope; display names are never authority.

The hosted entitlement check belongs in the hosted service boundary. Self-hosted operation uses the same coordination semantics without requiring a paid hosted subscription. Neither Git fallback nor a different UI changes authorization.

03 / ROLE-BASED AUTHORITY

Humans and agents are actors. Roles grant authority.

One reserved role: Maintainer is human-only.

All other presets and custom roles use the shared human/agent permission model. Being human does not automatically grant authority. An agent may receive a custom role with an equivalent set of operational capabilities, but that role must be explicitly created and granted by a human maintainer. The agent never becomes a Maintainer.

A human maintainer has full authority within its assigned scope. A project maintainer controls that project, including membership, roles, custom permissions, instructions, delegation, and records. Several humans may concurrently maintain the same project. A human can maintain Project A, contribute to Project B, and have no access to Project C. An agent can have explicitly granted custom full operational access in A and limited access in B. Workspace or instance authority requires an explicit wider assignment; a project role never implies control of other teams.

Every assignment records a stable actor ID, versioned role/preset ID, workspace, explicit project scope or project set, granting actor, and optional expiry or delegation limits. Channel/record audiences and membership remain relevant boundaries inside the authorized scope. Credentials, sessions, and START text describe or authenticate an actor; they do not replace authoritative assignments.

Proposed presetTypical allowed actions, within assigned projectsNot included by default
ViewerRead permitted conversations, tasks, lessons, history, and search resultsPosting, task changes, role administration
ContributorParticipate in permitted conversations; create work records and update assigned tasks; contribute lessons/evidenceGranting privileges, administering membership, directing unrelated work
ReviewerRead assigned work; record reviews, evidence, and permitted acceptance/integration decisionsRole administration or automatic source-repository merge rights
CoordinatorOrganize and assign work, direct participants, and delegate tasks within granted project capabilitiesSelf-promotion, arbitrary privilege grants, control of other projects
Maintainer — humans onlyAll authority within the explicitly assigned project, workspace, or instance scope; explicit creation and granting of equivalent custom authorityAssignment to an agent; authority beyond that scope
Custom role / actor customizationAn explicit capability set and scope, up to root-like operational authority when explicitly created and granted by a human maintainerThe Maintainer role/title, an inferred grant, or self-approved root authority

Presets are starting points. Store role definitions and assignment customizations explicitly and version them. For non-maintainer assignments, combine scoped grants and apply explicit scoped restrictions; absent authority means deny. Effective-access inspection must explain every contributing grant or restriction. Maintainer is explicitly full authority in its scope: use a lower/custom role or change its assignment to reduce it, rather than hiding contradictory restrictions beneath a “maintainer” badge.

Root-like power must be explicit, not prohibited. The custom-role editor must support selecting the equivalent operational capability set for an agent. Record the approving human maintainer, exact target actor, capabilities, project/workspace scope, role version, and grant transaction. Ordinary actions within that grant need no renewed human approval unless its conditions require it. Creating, granting to another actor, or broadening root-equivalent authority still requires the human maintainer’s explicit authorization; the agent cannot approve that reserved act for itself or another agent. A recorded exact human authorization can be delivered through an agent or Git relay without asking the human to approve it again.

Enforce these rules in the server for direct APIs, role cloning/template edits, combined grants, imports, Git submissions, and AI-assisted actions. Detect effective root-equivalent authority even when assembled from several roles or customizations; do not rely on the role’s display name. Preserve identity type in the authoritative identity registry. A custom root-like role never counts as a human maintainer for ownership, transfer, or last-maintainer checks.

Only an actor authorized to administer the target scope can assign or modify its roles. Limited role managers may grant only capabilities they are explicitly allowed to delegate. Role changes, revocations, and expirations govern future authorization checks, including queued operations, AI tools, event subscriptions, and exports. Preserve historical evidence of authority at the time an action occurred. Cagents permissions do not silently grant access to a separate Git hosting account or source repository.

04 / SECURITY DEFAULT

Grant only the authority needed for the assigned work.

Least authority is the default throughout Cagents. This follows the principle of least privilege: permissions should be limited to what an actor needs for its function. The rules below are the project’s design contract, including its explicit human-maintainer exception.

BoundaryDefaultExplicit expansion
New actor / invitationNo project data or operation access until an authorized grant appliesSelect the minimum useful preset or custom capability set for the assigned work
ScopeThe required task, records, channel, or named project onlyAdditional projects or workspace scope must be selected and justified by the work
DurationPrefer task/session-bound or short-lived grants where practicalPersistent authority is an explicit choice; record expiry or persistence and a review/revocation path
DelegationNo onward grant of capabilities by defaultAllow a specified subset, scope, and duration; a child grant cannot exceed its parent
Credentials and toolsActor- and scope-bound credentials; minimal tool allowlists and data accessNo shared maintainer credential or ambient machine-wide authority
Root-like custom authorityNever automatically selected or inferred for an agentA human maintainer explicitly creates/grants the exact operational capability set, target, scope, and duration

Show the effective combined authority before changes, including overlapping roles and customizations. Review capability sets rather than trusting role names. Custom roles pin an explicit capability catalogue/version; adding new server capabilities must not silently broaden an existing grant through an open-ended wildcard or template update. A human maintainer’s built-in full authority stays distinct from versioned custom grants.

Revocation and expiry apply to future requests and active subscriptions, including queued Git requests and AI tools. Invalidate affected authorization caches and close or narrow event streams as required. Preserve audit history and visible pending/denied results. Credentials used by the relay, exporter, search, and optional AI service receive only the service capabilities they require.

Least authority does not require repeated permission requests for already authorized work. A valid scoped instruction or delegation survives forwarding; routine operations within its grant continue. Elevation and changed scope are explicit changes. Full custom operational authority remains possible when the human maintainer deliberately chooses it, while routine onboarding and ordinary execution use narrower grants.

Assignments include their required communication permissions explicitly. When an authorized maintainer or delegated grantor assigns an orchestrator, worker or reviewer, the assignment records the named peers/channels, allowed directions, scope and duration needed for questions, replies and evidence. Provision those limited grants with the assignment or report exactly what is missing. Do not send every authorized reply back through the maintainer, and do not infer a general messaging mesh from task ownership. Communication access stays separate from command authority and does not automatically include onward delegation.

05 / MEMBERS & ROLES

A maintainer can set up a project’s participants in one screen.

Provide a server-backed Project → Members & roles screen early in the web UI. Use one list for humans and agents, with an authoritative type label. Show project scope, preset/custom role, effective permissions, assignment source, invitation/credential status, and expiry where applicable. Use a shared capability matrix, with Maintainer eligibility restricted to humans.

The editor starts with no grants, not a broad role preselected. Help the maintainer choose the minimum preset and narrow its task/project scope. Show delegation and duration as explicit settings. Make any root-like custom grant a clearly identified exceptional action with its purpose and exact scope in the recorded approval; ordinary custom-role editing should not steer users toward full authority.

  1. Add or select actors.Invite a human, register an agent seat, or select existing actors. Support bulk selection and one or more explicit projects that the acting maintainer administers.
  2. Choose an eligible preset.Offer viewer, contributor, reviewer, coordinator, and saved custom roles to both types. Offer Maintainer only for human targets; explain the restriction for agents and mixed selections. Enforce it again on the server.
  3. Customize authority.Show grouped capabilities and scope. A human maintainer can explicitly construct and grant an agent the full operational capability set through the custom-role editor. Label it as custom authority with its granting maintainer; never relabel the agent as Maintainer.
  4. Review and apply.Show the effective-access diff, target actor, scope, and role revision. Record the human maintainer’s explicit authorization for full/root-equivalent custom grants. Submit through the versioned role API and display conflicts, pending results, and receipts.

Maintain a searchable role-change history. Provide a way to inspect “why can this actor do this?” and “who can perform this action?” Detect accidental removal of the last maintainer and supply an explicit ownership-transfer/recovery flow. Changing a role template previews all affected assignments before applying it. Existing customizations do not silently disappear.

The server owns role presets, customizations, effective-permission evaluation, and enforcement. The web UI and CLI share those APIs. Agent-based administration remains supported within explicitly granted custom capabilities, subject to the reserved human-maintainer acts above. Multiple human maintainers may administer overlapping projects without silent last-write-wins changes. Last-maintainer checks count humans holding Maintainer, not agents with equivalent custom capabilities.

06 / SEPARATE OR TOGETHER

Choose how much coordination to share.

Independent teams

Separate workspaces. Separate databases, journals, coordination repos, credentials, and histories. This is the default for unrelated teams or personal versus employer work.

Related projects

One workspace, separate projects. Keep boards and memberships distinct. Share selected channels, lessons, or skills through explicit audience and access rules.

One product, several repos

Bind several source repos to the same workspace and project. They share one board, communication history, and project membership while retaining separate code histories.

PreferenceBinding choiceResult
Keep everything separateDifferent workspace IDsIndependent storage, history, credentials, and exports
Separate work, selected shared conversationsSame workspace; different project IDsSeparate boards; explicit channel membership and scoped sharing
Work together as one projectSame workspace and project IDs for multiple code reposOne project graph and history, multiple source repositories
See all my work in one placeA dashboard with several explicit workspace/project subscriptionsAuthorized aggregation; source labels remain visible; no data merge

A project may expose a shared channel to selected actors without granting them tasks, sessions, other channels, or full project membership. Workspace-wide lessons or skills are explicitly published at that scope; project-private knowledge does not silently become global. Cross-workspace sharing requires an explicit export/import or a separately authorized collaboration workspace. Automatic federation is outside the first cutover.

Changing a binding is not a data migration. Rebinding a checkout only changes where future operations go. Combining or splitting existing project histories requires a separate administrative migration with an inventory, reference mapping, and provenance. Pending requests retain their original destination and must never be redirected by a rebind.

07 / SAME MACHINE, DIFFERENT WORK

The directory selects the project. The session pins it.

Store the shareable binding in the code repository; keep connection and identity secrets outside it. For a public source repo, the team can choose a local-only binding if even workspace metadata should remain private. A binding is routing information, not permission to access the referenced workspace.

The local profile maps these IDs to approved API and Git routes, credential references, and actor seats. A local machine may use loopback while a remote seat uses the relay; the tracked IDs are identical. Installation provides a real git-cagents executable or equivalent alias to the Cagents client. Merely cloning a repo does not install executable Git extensions.

  1. Resolve an explicit destination argument, a worktree-local override, or the binding inside the current code repository. In a monorepo, the nearest explicit subproject binding can select a subproject; otherwise use the repository-root binding. Do not search outside the current Git repository for a fallback binding.
  2. Validate the full instance/workspace/project tuple and approved connection profile. Conflicting explicit, environment, and repository selectors produce a clear error. A leftover CAGENTS_PROJECT must never silently override the current repository.
  3. Pin the tuple, actor, binding revision, and session ID at resume. A bound agent cannot silently switch projects because a subprocess changes directory. An intentional rebind or actor switch starts or explicitly rebinds the session.
  4. Namespace caches, request queues, credentials, cursors, and receipts by instance, workspace, seat, and producer/session as applicable. Use one working directory and request stream per producer, including simultaneous sessions of the same actor.
No machine-wide “last project” authority.

A project selector in one terminal cannot redirect another terminal. Missing or ambiguous context requires explicit binding. Administrative cross-project commands name their destination; ordinary commands inherit the verified session.

Different projects may be bound to different instances, or to different workspaces on the same instance. Git worktrees normally inherit the tracked binding; an explicit local worktree override may select another approved project. A newly cloned untrusted binding never causes the client to send credentials to an unapproved endpoint.

08 / EVERY RESTART

Keep START.md. Make its workflow transport-independent.

The launcher tells each participant to read CAGENTS.md, its own workspace-scoped agents/<actor>/START.md or humans/<actor>/START.md, then the selected project’s instructions before resuming. A shared actor bootstrap describes the seat; project identity, prompt and any actor-specific project overlay describe its work in that scope. The API and published Git tree render the same versioned records.

Every agent and human START must be read and rewritten for the new system, preserve role and constraints, resolve its required skills and lessons, and remain strictly below 8,000 UTF-8 bytes. Original blobs remain unchanged in migration history. Generated bootstrap includes the tested command names and minimum compatible client version; credentials stay outside Markdown.

LayerCanonical location and scopeWho may publish
Shared protocol and actor baseCAGENTS.md; agents/<actor>/START.md or humans/<actor>/START.md, within one workspaceAn actor explicitly authorized to publish that workspace record or that actor’s base instructions
Project instructionsprojects/<project>/PROJECT.md, PROMPT.md, and optional projects/<project>/agents/<actor>/START.md or the corresponding humans/ pathAn actor with instruction-publication capability for that project and target
Resolved startup bundleManifest bound to workspace, project, actor, instruction generation and exact source revisions at one snapshotServer-generated read model; the API and exporter resolve the same layers

Publication is capability-based. Humans and agents may draft or publish only within their explicit instruction-publication authority. Being human grants no automatic publishing privilege; being an agent does not prohibit authorized publication. The target being the publisher’s own START neither authorizes nor categorically forbids the edit. Preserve the original approval, current capability checks, revision preconditions and audit receipt. START text cannot grant permissions, rewrite the server’s role checks, or create root-like authority.

A project-only publisher cannot alter the actor base or another project’s layer. Do not flatten distinct project documents onto one global export path. Required layer conflicts or missing required records are surfaced explicitly; broader-scope constraints and role permissions cannot be weakened by a project overlay. Optional absent overlays are harmless. Every base and overlay START must pass UTF8_bytes < 8000: 7,999 bytes may pass; 8,000 and 8,001 must fail. The assembled bundle has a separately declared total context budget and is never silently truncated.

  1. Verify the bound instance, workspace, project, actor, effective role assignments, client capabilities, and instruction/migration generation. Show the authority’s scope; never infer it from human/agent type.
  2. Reconcile outstanding operation IDs, receipts, and locally retained drafts without blocking startup on unrelated actors’ dirty checkouts.
  3. Load a consistent, bounded context: shared rules, START, relevant skills/lessons, board, active tasks, unread messages, and restart context. Mark snapshot cursor and freshness.
  4. Record the session and its synchronization state through the strongest configured route. In relay mode, retrieve the result and referenced startup snapshot.
  5. Proceed under the scoped authority of received instructions, role grants, and valid delegations. Record “authorized; synchronization pending” when appropriate. Explicit pauses, conditional restart requirements, and exclusive-resource claims retain their own conditions.

Loading an inbox never acknowledges its contents. Fetching a START alone does not prove that current restart conditions were met. A disconnected participant can continue work within known authority, but cannot claim unseen updates or a newly requested exclusive resource as confirmed.

09 / ONE COMMAND FAMILY

Use git cagents from either code or coordination workspaces.

git cagents … and cagents … use the same command implementation. In a code repository, the binding resolves the coordination project; coordination operations never stage or commit source files. An editable coordination checkout is a distinct, client-managed view bound to that same project.

10 / PREPARE ONCE

Commands and file edits converge on semantic operations.

A domain command directly constructs a validated request. For participants who prefer files, provide a private editable coordination checkout with familiar paths. Staged edits become a request bundle with their base record revisions; arbitrary exported-file diffs never become unchecked database writes.

# In the private COORDINATION checkout, not the source-code checkout:
git cagents pull
# Edit a lesson or other supported coordination record.
git add -- path/to/record.md
git cagents push
git cagents status

The client captures the exact staged content and constructs an immutable operation ID before transport. The envelope identifies protocol version, instance/workspace/project, producer/session, operation, payload hash, expected revisions, causal dependencies, and instruction/delegation references where relevant. The server binds the authenticated submitting identity; it does not trust a free-form actor field.

A task claim, acknowledgement, recipient change, or coordinated multi-record update must use the corresponding semantic action. If an edit has no unambiguous mapping, explain the unsupported change and the operation required. Atomic groups are accepted or rejected as a group; a rejected prerequisite blocks its explicit dependents, not unrelated work.

11 / SCOPED DIRECTION

Role-based authority survives an authorized relay.

Maintainer instruction → orchestrator → worker.

The instruction authorizes work within its scope. A server receipt confirms recording. A transport delay must not demote a received instruction into a new permission request.

Preserve the original source and wording, originator, authenticated submitter, authorized delegation chain, work scope, conditions, and amendments. Relaying does not change the originator or automatically expand the scope. An orchestrator authorized to organize work can issue subtasks within that delegation; an agent’s interpretation remains separately attributed.

The originator’s authority comes from its role and scope. Only humans hold Maintainer. An agent with explicitly granted custom authority can issue or relay directions within those capabilities without claiming the Maintainer role. Preserve the originating human instruction or custom-role/delegation evidence. Neither ordinary human messages nor an agent’s role label automatically become maintainer instructions.

Use source evidence from an authenticated maintainer interaction or verifiable instruction record. A branch name, Git author string, or untrusted quotation alone cannot establish maintainer authority. Provisioned connector seats must have an approved identity/delegation mechanism: actor-scoped signed requests or a trusted connector binding with explicitly limited seat authority. Shared GitHub credentials alone cannot prove which agent authored an instruction.

Keep authorized, submitted, accepted into storage, delivered, acknowledged, and completed distinct. A worker can be authorized while its task event awaits synchronization. A self-requested exclusive claim is not acquired merely by queueing it.

Amendments and cancellations explicitly reference the instructions they supersede and propagate through relays. During complete disconnection, an agent cannot know an unseen cancellation; freshness must be visible. Continue only within the received authority and its conditions, preserve local records, and apply new directions on reconnection. This does not override an explicit maintainer pause or migration gate.

12 / FAST WHEN CONNECTED, DURABLE WHEN REMOTE

API first. Git fallback. One application state.

Connector-only environmentSame envelope through GitHub connector operations; no CLI execution requiredSame authorized publication and receipt records

Fallback is for connectivity and configured service unavailability. An explicit authentication denial, authorization denial, or revision conflict is reported as such. The Git relay calls the same API and cannot bypass those decisions. If the API timed out after committing, resubmission through Git returns the original outcome using the same scoped idempotency key.

Default to separate publication and submission repositories. The publication repository is an exporter-written readable view of accepted state, history and authorized receipts. The submission repository carries immutable request envelopes in isolated producer streams. A relay near the application consumes approved streams and submits them through the normal API. Exporter and relay have separate least-authority service credentials; neither executes repository-provided scripts or treats published exports as new requests.

A shared remote repository is an optional deployment choice only when its readers are authorized to every included submission and export, its refs have the required writer protections, and its clients use isolated checkouts and streams. Sharing a remote does not inherently mean sharing a mutable checkout. Branches do not create confidentiality boundaries; differing audiences require separate authorized repositories/projections. Split submission repositories further by audience where request payloads are private.

One synchronizer owns each mutable checkout; each producer/session owns its draft directory and submission stream. No competing watchers run fetch/pull against that checkout, and no network wait holds a global coordination lock. Private checkouts remain replicas or draft staging, never separate coordination authorities.

Order explicit dependent operations; preserve causal references rather than guessing from wall clocks. Restart the relay from durable checkpoints, isolate malformed requests, apply fair per-workspace scheduling, and resume unrelated streams after failures. A queued Git submission is durably transported, but its domain result remains pending until the server processes it.

Synchronization health is a product contract.

Every watcher, CLI status and live UI reports the last successful synchronization, heartbeat deadline, last applied cursor, audience-authorized server progress and publication age where relevant. Show connected and caught up, connected but behind, disconnected/stale, or not yet synchronized. A running process is not evidence of successful delivery. Silence beyond the negotiated deadline becomes an explicit stale state even when the connection remains open.

Send heartbeats when there are no domain events. A healthy heartbeat with an unchanged authorized head means the stream is quiet; an advancing authorized head with a stuck applied cursor means delivery or processing is behind. Cursors and health metadata must not expose hidden projects, events or counts; use opaque tokens or audience-scoped progress. Reconnect with backoff and gap recovery. Git-only users can observe their fetch success and export age, but cannot claim current server health from an old snapshot. Verify silent stalls separately from dropped connections.

13 / NO LOST DRAFTS

Cleanup follows the exact captured operation.

StateWhat the client retains or retires
Draft / queuedRetain staged content, immutable request, original destination, and retry identity
Outcome unknownQuery or retry the same ID; never manufacture a new mutation to resolve uncertainty
Rejected / conflictingPreserve the proposed edit and reason; resolution creates a new operation referencing the old one
AcceptedRecord the receipt and retire that retry entry; maintain a visible accepted result if publication lags
Reflected in the viewRemove only the corresponding managed overlay once the snapshot includes the accepted transaction

Compare the captured content with the current local file before retiring it. If the participant edited the file again, retain those newer changes. Pull and sync must preserve unstaged edits, unresolved conflicts, and unrelated files. Never use a broad hard reset or clean as a synchronization strategy.

Server deduplication retention must cover the supported retry/replay horizon; a compacted journal cannot make an old operation look new. Persist receipt identity or a replay fence across compaction and backup/restore. An old restored snapshot must not silently reuse a generation that could replay previously accepted effects.

14 / SERVER STORAGE

Scale through independent workspace writers.

The intended application stack combines hey_record, hey_durable_log, and hey_sqlite3. Each workspace has its own database and journal namespace. Domain services validate authorization and revisions, order a logical transaction, durably commit it, and materialize current state and retained history.

A receipt means the mutation crossed the configured durability boundary. If the current-state materializer is behind, the service must wait for the required cursor or otherwise provide an equivalent consistent read. It must not acknowledge an in-memory queue as crash-safe completion. Git export stays asynchronous and never extends the normal API commit path.

  • Independent queues: serialize writes where a workspace needs it; avoid a machine-wide coordination lock. Bound buffers and fair scheduling prevent one slow team from monopolizing service.
  • Server-owned connections: select databases by authorized registry IDs; clients never open or share a network-mounted SQLite file.
  • Many workspaces: bound open database connections, schedule exports independently, and allow workspace placement across server workers/hosts as capacity requires. No scale number is claimed without workload measurements.
  • Recovery: back up journal, database checkpoint/cursor, receipt identity, instruction history, and required source artifacts coherently. Restore is an explicit workspace operation with generation control.
  • History: retain original Git DAGs, object provenance, events, and ordered changes needed for past-point reconstruction. Materialized current state alone is insufficient.
15 / ISOLATION IS ENFORCED EVERYWHERE

Every read, write, and export has a destination and an audience.

Use instance/workspace scope in operation IDs, actor bindings, database routing, cache keys, subscription topics, journal paths, export cursors, and retry queues. Apply project, channel, and DM audience rules to every query and export. A valid credential for one workspace cannot choose another workspace merely by changing a request field.

A workspace’s full coordination Git repo is appropriate only for readers authorized to all exported contents, including history. Git branches are not confidentiality boundaries. If project or channel audiences differ, publish separate authorized repositories/projections or provide API-only access for private content. Repository access controls must match each projection’s audience.

Removing access cannot erase copies or Git history already downloaded. This is an explicit consequence of exporting data, so publication must be scoped before disclosure. The application can enforce future access and stop future delivery; it must not imply retroactive removal from a reader’s machine.

Shared administrative infrastructure does not make per-team SQLite files an absolute process-security boundary. Stronger deployments can use separate service processes/hosts and storage credentials per workspace. The baseline contract requires enforced tenant routing and authorization plus independent storage; operational hardening follows the deployment’s needs.

16 / KEEP THE READABLE TREE

The repo remains a legible, historical view.

One canonical record/path model serves the API tree, Slack-like UI links, export, and historical reconstruction. Preserve readable names alongside stable IDs, familiar project/actor/task/message directories, record provenance, attachments, and valid links.

The exporter publishes consistent snapshots with workspace identity, migration generation, ordered cursor, and timestamp. Batch commits for reasonable eventual freshness; measure lag rather than promising instantaneous Git synchronization. API users keep working while a Git provider is slow. Remote users see publication age and pending results.

Full-fidelity administrative export can preserve all authorized workspace data and both imported Git histories. Audience-restricted projections preserve only what that audience may receive and must not masquerade as a complete administrative backup. The default readable branch is written by the exporter alone; private editable working copies are drafts submitted through the client.

18 / CLIENT PARITY

One contract for humans, agents, and every interface.

Web, iOS, Android, macOS, CLI, and connector adapters share operation schemas, role evaluation, actor scope, validation, idempotency, revision conflicts, receipts, and record paths. Shell clients use the Git extension; connector-only agents create the equivalent envelope without hand-writing mailbox refs or task transitions. Every interface enforces human-only Maintainer eligibility and explicit human-maintainer authorization for root-equivalent custom grants, while using the shared capability model for ordinary operations.

The common instruction set describes behavior once. Each participant START adds role-specific constraints. Connection profiles and adapter help explain mechanics. Provisioning must prove the identity and operation capabilities of each seat before the restart test; a successful Git push alone is insufficient evidence of a correctly bound actor.

UIs display the active workspace/project next to actions and preserve those labels in aggregated views. They show freshness, pending versus accepted records, unread versus acknowledged delivery, and conflicts. They never require users to understand journal internals to send a message.

19 / SERVER FIRST

Give the CLI and migration work solid APIs before expanding clients.

The cagents-application orchestrator owns the application server and all UIs. Its first delivery priority is a versioned, documented, executable API contract that the generic_cagents client and migration tools can depend on. Reconcile existing routes and implementations before adding replacements. The application must be usable without a rich UI or AI provider.

Publish examples and conformance fixtures for successful calls and failures: malformed/unsupported requests; missing or invalid credentials; unauthorized actor/project/channel; revoked roles or delegations; stale revisions; reused operation ID with different payload; rate limits; service unavailability; and lost responses after commit. Revalidate current permissions at the action boundary and invalidate affected access/search/subscription caches when roles change. Preserve the historical record of who was authorized at the time. API and Git paths must converge on the same outcome. Give the CLI orchestrator exact implementation pins and runnable fixtures as each command family becomes usable.

20 / THE WEB WORKSPACE

Conversation, administration, and exploration belong in the first UI.

Search across authorized projects and mailboxes.

Provide an explicit cross-project search mode through the ordinary search API. A maintainer can search all coordination records within the scope they maintain; a reviewer can receive a narrower, explicit grant to read and search the selected projects, channels or records. “Operator” describes this query mode, not a privileged identity type or an automatic bypass. Having the endpoint available does not confer access to all workspaces.

Apply current effective permissions before returning results, snippets, historical records, facets, counts or suggested filters. Retain source labels and report the selected scope, permitted coverage and indexing freshness so a partial search cannot masquerade as a complete search of the workspace. Tree/blob reads, exported projections, activity views and AI retrieval enforce those same grants. A broader search grant does not grant write, role-administration or forwarding authority.

After the server contracts, prioritize the web UI. It should combine a Slack-style workspace with setup and administration, rather than treating chat as the entire product. Each screen consumes the server’s current capabilities and enforces its decisions through the ordinary APIs.

Set up and manage

Create/join workspaces and projects; add humans/agents; assign preset or custom roles; inspect effective access, invitations, actor sessions, and role history.

Communicate and work

Channels, DMs, threaded replies, inbox/read state, task links, instructions/delegations, progress, lessons, and receipts. Display pending and rejected actions accurately.

Search and browse

Search messages and records; browse the familiar project/actor/task tree and historical views; filter by scope, actor, time, machine, and repository without leaking unauthorized metadata.

After the web foundation, deliver native clients in this order: iOS → Android → macOS. Reuse server schemas, permissions, receipt semantics, and query/event APIs. Their platform-specific authentication and presentation do not change an actor’s authority. Later visualizations and AI must not delay the server, basic web role management, or migration readiness.

21 / LIVE COORDINATION VIEW

Watch authorized information flow between actors and machines.

Add an optional read-only, near-realtime activity view. Represent actors, machines, project/source repositories, API/relay routes, and communication connections. Use clear event states for submitted, accepted, delivered, acknowledged, and completed work; presence or a moving line is not proof of delivery.

Let viewers filter by workspace, project, channel, participant, repository, machine, event kind, and time. Selecting a node shows its authorized activity; selecting a connection opens the underlying permitted messages/events and their timestamps, task links, provenance, and receipts. Offer pause/resume and a bounded historical window, plus a list/table equivalent for precise inspection and accessibility.

The server provides audience-filtered event records with stable IDs and a resumable cursor. Reconnection deduplicates events, detects gaps, and recovers through a snapshot/backfill. Batch or sample high-frequency operational activity with an explicit indicator; do not claim unsampled completeness. Stale connections and relay/export lag remain visible. Cross-workspace views require explicit authorized selection and retain source labels. Even counts, actor names, and connection existence can be private.

Record source machine, session, and repository provenance only when available and permitted; distinguish registered/verified metadata from actor-reported labels and show unknown values honestly. Keep visualization fan-out off the durable mutation path. Inspecting a message here does not automatically acknowledge it, and the flow view itself performs no coordination mutations.

22 / OPTIONAL SERVER-MEDIATED AI

Ask questions, propose improvements, and save repeatable actions.

A workspace maintainer may enable an optional AI provider through the server, choose a local or hosted model, and configure allowed scopes, data-sharing policy, tools, and usage limits. Keep provider credentials on the server. Normal communication, permissions, search, task work, and migration continue to work with AI disabled or unavailable.

AssistanceBehavior
Query informationRetrieve only records the caller may access; answer with links to those sources and indicate missing or stale context
Review permissionsIdentify redundant grants, unexpectedly broad scopes, expired delegations, and possible gaps; explain the evidence and propose an exact before/after change
Detect issuesSurface stuck tasks, unanswered requests, conflicting assignments, communication bottlenecks, or relay failures with supporting records; distinguish inference from a confirmed fact
Create action buttonsPropose named parameterized server-action templates for useful repeated work, with visible scope, required permissions, defaults, and expected effects

The AI operates within the caller’s effective permissions and an explicit, limited assistant delegation/tool allowlist. Reading a maintainer’s message does not grant the model that maintainer’s role. Retrieved messages and documents remain input data, not privileged tool instructions. Filter context before sending it to a provider and isolate model sessions, caches, and retrieval indexes by workspace/audience.

Retrieve only the records and fields relevant to the query, rather than sending every record the caller could potentially read. Tool and retrieval scopes should be narrower than the caller’s full permissions when the task allows it. Access to a saved action button does not grant any of the underlying capabilities.

Default to read-only queries and proposals. Ordinary mutations may be approved by an authorized human or agent, or an explicit pre-authorized automation policy. The reserved cases remain human-only: an agent cannot hold Maintainer, and AI/agents cannot create, approve, or broaden root-equivalent custom authority without the human maintainer’s explicit authorization of the exact grant. Recheck current permissions and revisions at execution, use the ordinary API, and retain the proposal, authorization, operation identity, and receipt. AI failure cannot partially apply a proposed cleanup.

A saved button contains a named server action or validated action group and parameters, not arbitrary generated code, credentials, or a privileged API bypass. Its owner controls who may see/use it. Every deliberate click creates a new operation identity; retries reuse that identity. Preview sensitive effects, resolve parameters, and validate the caller’s current authority each time. Sharing a button never shares its creator’s credentials or grants.

Implementation responsibility and order

Cagents orchestrator — generic_cagents and existing cagents migration: own the modular CLI/Git extension, setup and binding, role-aware startup, domain/access command clients, immutable submission envelopes, retries/drafts/cleanup, connector-only adapter, and transport conformance. Own complete extraction/inventory/reconciliation of the existing cagents Git histories, semantic mapping, START rewrites, migration inputs, and export/reimport fixtures. Integrate against the application server’s actual APIs; do not build a second permission or storage authority.

Cagents-application orchestrator — server and every UI: first deliver the robust versioned APIs, role policy, workspace isolation, durable transaction/recovery path, operation receipts, administrative import/export, query/events, and supervised relay service. Then deliver web setup/Members & roles, Slack-style communication, search/tree/history, followed by the activity view and optional AI assistance. Native order is iOS, Android, then macOS. Keep the migration-critical server and basic web work ahead of optional visualizations and AI.

Shared seam: application owns server-side envelope validation, authorization, receipt semantics, relay consumption, administrative import, deterministic export and the deployed service; generic_cagents owns client envelope production, submission streams, adapters, local recovery, source extraction/mapping and history fixtures. These responsibilities are authorized; no additional ratification is needed. Agree executable failure fixtures and publish exact matching implementation pins. Reuse existing tasks and avoid parallel replacement implementations.

Legacy role mappings: inventory each legacy agent-Maintainer assignment and present the exact proposed target actor, custom capabilities, scope, duration and human approval needed. Preserve its original history. Only that unresolved privilege mapping awaits approval; extraction, fixtures and already authorized START conversion continue. No silent elevation, deletion or relabeling is permitted.

Named review: the existing chatgpt participant is the Cagents overseer and independent reviewer for generic_cagents, migration and combined cutover evidence. Preserve that identity and history; do not create a duplicate seat to match a role name. The application’s existing cagents-application-overseer retains its independent review/integration responsibilities. Reviewer authority is scoped review and coordination, not Maintainer or root-like authority. Keep the explicit communication grants needed for each review lane.

Authorized START correction: the CLI/migration orchestrator may rewrite and publish the migration’s reviewed instruction conversion within its assigned scope, preserving provenance and independent review. After cutover, the accepted server journal is authoritative; a mutation is durable when it crosses its configured journal durability boundary; Git is an asynchronous readable projection and optional request transport. Apply that already approved wording without asking the maintainer to authorize the same conversion again. Do not activate the new startup generation before cutover.

During migration: isolate mutable checkouts immediately and give each exactly one synchronization owner. Use bounded network waits and observable failures; avoid a herd of watchers pulling against one checkout. Preserve all unpushed work while moving seats, and verify that they still share cagents/main as the live coordination authority. Private replicas and worktrees do not create new boards. Existing mirror, path-guard and CI fixes should be verified at their actual pins, not reimplemented.

Cutover sequence

Prepare and rehearse before switching live agents. At the agreed freeze, capture the final legacy data and pending work, import and reconcile it, publish the new instruction generation and bootstrap, protect the published branch, and run the acceptance scenarios. Tell the maintainer when remote and local participation both work so remaining agents can be stopped or restarted against the new interface. Correct live entry points; preserve old instructions only as clearly historical records.
