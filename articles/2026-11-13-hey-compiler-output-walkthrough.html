What the captured Hey compiler output says

Imports and exports: partly works General compiler: partly works

An import can parse, appear to resolve, and still fail when HIR reads the imported declaration. This walkthrough follows captured output so you can see what passed, where it stopped, and which fixes have to come first.

Capture labels. The original phase walk and opening import/export audit are frozen build2 evidence. The later HIR/SSA follow-up has its own binary hashes and records. Source paths and line numbers are capture-time pointers. Read each section’s evidence label before comparing phases.

Start with imports: syntax works, the full system doesn't

This frozen build2 import audit is separate from the post-cutover HIR/SSA follow-up below. It is not a pipeline7 import recheck. A 13-case, two-file audit parsed every example with canonical parser SHA-256 9a913f4f005cbec811a51195f827d273e2833c900c3551d3d23461e53345015e. All 13 source-resolution cases and every resolution-pass HIR case were rerun with pipeline-inference-2, SHA-256 9c1f81a8377dba99ada9d9900465f98f972f89ea532d9cbb4df153d6cc46d039.

The compact import receipt records all 13 phase outcomes. “The parser accepts imports” is not “imports work.” Allowed namespace and explicit forms don't enter HIR. Wildcard status doesn't identify the selected function. Visibility checks work for these negative examples, while re-export and selector-renaming behavior remain missing in this capture.

Fix the boundary in dependency order

  1. Build the numeric module surface: local exports, explicit and wildcard imports, facade re-exports, privacy and selector-rename policy.
  2. Attach namespace spellings to provider identities: aliases and plain namespaces must name the same verified unit.
  3. Project imported declarations into HIR: preserve declaration identity and provider bodies.
  4. Carry cross-unit targets through MIR and LLVM: agree on call ABI, then link and execute legal two-file cases while retaining privacy failures.

Status: proposed order from measured failures. Newer working-tree edits are not proved by this frozen binary.

Physical lowering remains the next boundary

The emitted MIR values still say representation=unplanned; their owner and borrow-region fields are empty. The current values establish semantic SSA identities and control-flow edges. They do not describe machine representations, ownership, or an LLVM-ready calling convention. The pipeline7 run tried emit-llvm and received exit 70, no output file, and the diagnostic “LLVM emission is unavailable: physical representation and ownership planning are not implemented.” See the exact captured refusal receipt.

The next compiler step is to plan physical representations and ownership for these SSA values, then teach the LLVM path to consume that planned MIR and capture its output. The earlier LLVM listings on this page belong only to build2 and are not evidence for this later HIR/MIR pair.

Four stages, four jobs

AST means abstract syntax tree. HIR is the high-level intermediate representation with structure and semantic facts. MIR is the mid-level intermediate representation with values, storage and calls. LLVM is the compiler toolkit's intermediate language.

  1. Sourceresolve-source
    admitted AST
  2. ASTemit-hir
    semantic HIR
  3. HIRlower-mir
    execution MIR
  4. MIRemit-llvm
    LLVM text
  5. LLVMlink and native run are separate

An error ends the path. No later output exists unless its command ran.

Why the local stays Int in HIR: the hi_body helper in HeyHirInference.hey records which definition reaches each read in statement order. analyze builds dependencies and reverse users, then queues only nodes whose inputs changed. hi_transfer applies the type rule. HeyHirStatements.lower_function calls this pass. That is the new inference technique behind the captured local facts; MIR representation and ownership remain separate decisions.
