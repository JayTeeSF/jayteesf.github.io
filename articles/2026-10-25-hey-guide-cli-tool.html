Build a real command-line tool in Hey

You'll write wordfreq, a small tool that finds the most common words in a folder of text files. Along the way you'll read flags, walk files, count with a map, run another program, report errors with the right exit code, test it, and turn it into one native binary you can copy anywhere.

The short version

  • hey wordfreq.hey runs your tool like a script. The first run compiles it to native code and caches it; later runs start the cached binary in 8.3 ms.
  • hey build wordfreq.hey -o build/wordfreq makes one 270 KB executable that needs only the system C library. It starts in 2.1 ms.
  • stdlib:Cli gives you flags, typed values and a help screen; Files, Process and Text do the rest.
  • Honest gaps, all measured below: Hey has no statement that sets an exit status (fail always exits 70; tools hand their output to /bin/sh). Flag values need --top=5, not --top 5. And counting real text is slow today: 2.65 s against Ruby's 66 ms, because of a compiler defect that copies a map on every update.

You are here Guide 1 installed Hey and ran hello. Guide 2 added packages. This guide builds a tool. Guide 4 builds a web server, guide 5 builds apps, guide 6 ships them.

1. The tool, in one picture

Every command-line tool is the same shape: arguments come in, some files get read, something gets computed, text comes out. wordfreq is that shape with nothing extra.

Hey in five words. let makes a name, set gives it a new value, says prints a line, program ... end is where the run starts, and [...out, x] is a new list with x added on the end. Values never change in place; you make a new one and set the name to it.

The project is three files:

wordfreq/
  wordfreq.hey      the program: flags, files, output
  lib/count.hey     the pure part: text in, counts out
  count_spec.hey    tests for lib/count.hey

Here's what it does when you're done. Run it on a folder with two short text files:

$ hey wordfreq.hey --top=5 sample
2 files, 12 different words
     4  the
     3  dog
     2  a
     2  fox
     2  is

2. Read flags with Cli Works today

You describe your options once, as data. Cli turns that description into a help screen and into checked, typed values. Nothing to subclass, no annotations.

fn schema()
  return Cli.schema('wordfreq [FOLDER]', 'Count the most common words in text files.', [
    Cli.option('top', 'int', 10, 'how many words to show'),
    Cli.option('ext', 'string', '.txt', 'which file ending to read'),
    Cli.option('git', 'bool', false, 'only read files git tracks'),
    Cli.option('help', 'bool', false, 'show this help')
  ])
end

Then the top of program reads the real arguments and checks them:

  let parsed = Cli.current()                    # reads argv and splits flags from the rest
  let checked = Cli.validate(parsed, schema())  # a Result: ok, or which flag was wrong
  ...
  let folder = Cli.parsed_positionals(parsed).first('.')   # first item, or '.' if there is none
  let top = Cli.typed_flag(checked, 'top', 10)  # already an Int, not text

.first('.') works because the file has import 'stdlib:Collections' exposing: [first] forms: [:dotted]: that import lets you call first(list, fallback) as list.first(fallback). (Imports are covered in Modules, imports and exports.)

The help screen comes for free:

$ hey wordfreq.hey --help
Usage: wordfreq [FOLDER] [options]
Count the most common words in text files.
Options:
  --top <int>  how many words to show default=10
  --ext <string>  which file ending to read default=.txt
  --git  only read files git tracks default=false
  --help  show this help default=false

A bool option is switched on by its name alone (--git) or given =true/false/yes/no/on/off/1/0; --no-git switches it off. Anything that doesn't start with a dash is a positional argument (here, the folder).

Write values with =: --top=5, not --top 5. Partly works Cli.parse reads flags before it sees your schema, so it can't tell that --top takes a value. It treats --top as a switch and 5 as the folder, and then validation says the flag isn't an Int:

$ hey wordfreq.hey --top 5 sample; echo "exit status: $?"
--top expects int
Usage: wordfreq [FOLDER] [options]
…  (the rest of the help screen)
exit status: 64

The older list helpers (Cli.flag(args, 'top', 10)) do accept --top 5, so the two halves of Cli disagree. No task covers this yet; it is recorded as a known issue.

The full Cli, Files, Process and Env function lists live in the standard library reference. There's also a small hey_cli package (0.1.0) with command and exit-result records; this guide sticks to the standard library because that's all wordfreq needs.

3. Walk files and count with a map Works today

Files.files(folder, '.txt') returns every file under the folder that ends in .txt, sorted, searching subfolders too. Files.read_text(path) reads one file into a String.

The counting lives in its own module so the tests can call it without touching the disk:

# The pure part of wordfreq: text in, counts out. No files, no flags.
import 'stdlib:Text'
import 'stdlib:Collections'

module WordCount
  # Lower-case a word and peel punctuation off both ends.
  fn clean(word)
    let w = Text.lower(word)
    let marks = ".,;:!?\"'()[]{}<>*_-#`"
    while len(w) > 0 and Text.contains?(marks, slice(w, 0, 1))
      set w = slice(w, 1, len(w) - 1)
    end
    while len(w) > 0 and Text.contains?(marks, slice(w, len(w) - 1, 1))
      set w = slice(w, 0, len(w) - 1)
    end
    return w
  end

  # Add every word in `text` to the `counts` map and return the new map.
  fn add(counts, text)
    let out = counts
    for raw in Text.words(text)
      let w = WordCount.clean(raw)
      if len(w) > 0
        if has?(out, w)
          set out = put(out, w, out[w] + 1)
        else
          set out = put(out, w, 1)
        end
      end
    end
    return out
  end

  fn by_count_then_word(left, right)
    return Collections.compare_chain([
      Collections.compare_desc(left[1], right[1]),
      Collections.compare(left[0], right[0])
    ])
  end

  # The `n` most common words as [word, count] pairs, ties broken A to Z.
  fn top(counts, n)
    let pairs = Collections.sort(entries(counts), WordCount.by_count_then_word)
    return Collections.take(pairs, n)
  end
end

What would you predict? Hey values never change. put(out, w, 1) returns a new map with one more entry. So does counting a 10,000-word file copy the map 10,000 times?

Answer (and an honest surprise)

It shouldn't. The compiler's middle stage (MIR, the step that decides when values are created and freed) tracks who still holds each value. In set out = put(out, ...) the old out is never used again and nobody else holds that map, so put may change it in place. You write code that reads as if nothing changes; the machine does the cheap thing. The full story is in Values, memory and Strings.

But today, in this exact shape, it does copy. We measured the same counting loop two ways on one 245 KB file (32,761 words):

Where the map startsTime
let out = {} inside the function that fills it37 ms
let out = counts, where counts is a parameter (as in WordCount.add)3.93 s

When the map arrives as a parameter, every put copies the whole map. That's a compiler defect, not a rule of the language. It is recorded as a known issue with a two-file reproduction, for repair in MIR's ownership plan. The guide keeps the natural code; see how fast it is on real text for what it costs today.

Back in wordfreq.hey, the main loop is four lines:

  let counts = {}
  for path in paths
    set counts = WordCount.add(counts, Files.read_text(path))
  end

4. Run another program Works today

With --git, wordfreq asks git which files it tracks instead of walking the folder. Process.run_argv takes the command as a list of words. There's no shell in between, so spaces and quotes in file names arrive exactly as written.

fn files_from_git(folder, ext)
  let run = Process.run_argv(['git', '-C', folder, 'ls-files', '*' + ext])
  if !run.ok
    return []
  end
  let out = []
  for name in Text.lines(run.stdout)
    if name != ''
      set out = [...out, Files.join(folder, name)]
    end
  end
  return out
end

The answer is a record: ok, stdout, stderr and the child's status. Here the sample folder is a git repository that tracks only a.txt:

$ hey wordfreq.hey --git --top=3 sample
1 files, 9 different words
     3  the
     2  dog
     1  brown

If a child might hang, use Process.run_argv_timeout(args, 30_000): it kills the whole process group after 30 seconds. For a long-running child you talk to, Process.spawn gives you its stdin and stdout handles.

5. Errors and exit codes

Hey separates two kinds of failure, and the difference matters for a tool.

Expected failures are values. A missing folder or a bad flag is something a user will do. Return a Result (Result.ok(v) or Result.error_with(code, message)), check .ok, and print something helpful. Cli.validate already does this for flags.

Bugs stop the program. fail 'message', or any runtime error, stops the whole process at once. Hey calls the thing a failure stops the unit of work: in a server it's one request, in a tool it's the whole process. It prints the message and exits with status 70. There's no try/catch; that's a ruled design choice (fail fast, Erlang style).

$ cat fail_demo.hey
program
  says 'checking...'
  fail 'the config file is missing'
end
$ hey fail_demo.hey; echo "exit status: $?"
checking...
hey error: the config file is missing
exit status: 70

The gap: choosing your own exit code Partly works

Shell scripts and CI care about exit codes: 0 for success, 1 for "found a problem", 64 (or 2 in many tools) for "you typed it wrong". Hey has no statement that sets the process exit status today. A program that ends normally exits 0; fail exits 70. No release, ruling or task covers adding one yet; the gap is recorded as a known issue.

Cli can already work out the right number for you: Cli.exit_status(checked) gives 0 for success and 64 (the usual "bad usage" code) for a missing or malformed flag, and Cli.ok_exit / Cli.error_exit build exit records. Nothing applies that number to the process, though.

The working pattern, used by the published hey_secret_lint package, is to build the whole output as one String and hand it to /bin/sh, which prints it and exits with the code you pick. Process.exec_env_argv replaces the Hey process, so nothing printed earlier can be lost:

# Hey has no statement that sets an exit status yet, so hand the text
# to /bin/sh, which prints it and exits with the status we choose.
fn finish(text, status)
  Process.exec_env_argv({}, ['/bin/sh', '-c', 'printf "%s" "$1"; exit "$2"', 'wordfreq', text, status.to_s])
end

wordfreq passes Cli.exit_status(checked) to finish for a bad flag, and 1 for a missing folder:

$ hey wordfreq.hey --top=many sample; echo "exit status: $?"
--top expects int
Usage: wordfreq [FOLDER] [options]
…  (the rest of the help screen)
exit status: 64

$ hey wordfreq.hey no-such-folder; echo "exit status: $?"
wordfreq: no such folder: no-such-folder
exit status: 1

It works, but it costs a /bin/sh start and doesn't exist on hosts without a POSIX shell. Treat it as a stopgap.

6. Test it

Hey has two kinds of test, and a tool usually wants both.

KindWhat it checksHow you run itStatus
spec blockThe whole program's stdout, stderr or exit status (a golden test)heyc file.hey --testWorks today
stdlib:MinispecIndividual values: to_equal, to_include, to_be_error, and morecall it from a program; pair with a spec blockWorks today (reference: Standard library)

A spec block runs the program with no arguments, so put the tests next to the pure module, not next to the tool:

spec 'WordCount cleans, counts and ranks words'
  expect stdout "WordCount: 5 passed, 0 failed\n"
end

import 'stdlib:Minispec'
import './lib/count.hey'

program
  let s = Minispec.suite('WordCount')
  set s = Minispec.to_equal(s, 'strips punctuation', WordCount.clean('"Hello!"'), 'hello')
  set s = Minispec.to_equal(s, 'keeps inner apostrophes', WordCount.clean("don't"), "don't")
  let counts = WordCount.add({}, 'the cat and the hat. The end')
  set s = Minispec.to_equal(s, 'counts case-blind', counts['the'], 3)
  set s = Minispec.to_equal(s, 'top word first', WordCount.top(counts, 1), [['the', 3]])
  set s = Minispec.to_equal(s, 'ties go A to Z', WordCount.top(counts, 3), [['the', 3], ['and', 1], ['cat', 1]])
  Minispec.report(s)
end

You can run the file as an ordinary program to see the report:

$ hey count_spec.hey
WordCount: 5 passed, 0 failed

Today, heyc --test only finds the standard library when you run it from inside the Hey checkout. Partly works From your own project folder, any spec file that imports a stdlib: module fails before it starts (setting HEY_ROOT doesn't help):

$ heyc count_spec.hey --test
FAIL: WordCount cleans, counts and ranks words
expected stdout: WordCount: 5 passed, 0 failed

actual stdout:   
FAIL: WordCount cleans, counts and ranks words
unexpected stderr: heyc: file not found: stdlib/Minispec.hey

FAIL: WordCount cleans, counts and ranks words
expected exit: 0
actual exit:   1
exit status: 1

Until that's fixed, run it from the Hey checkout and pass the full path:

$ cd "$HEY_HOME" && heyc ~/code/wordfreq/count_spec.hey --test
PASS: WordCount cleans, counts and ranks words
exit status: 0

($HEY_HOME here means wherever your Hey toolchain lives. A spec with no stdlib: import passes from anywhere.) No task covers this yet; it is recorded as a known issue.

A Minispec suite is a plain value: each assertion returns a new suite with one more result in it. Minispec.report prints the totals, and the spec block checks that line. For a CI job without the golden harness, Minispec.finish(s) prints the report and exits 70 if anything failed.

The whole of wordfreq.hey, in one piece 
# wordfreq: the most common words in the text files under a folder.
import 'stdlib:Cli'
import 'stdlib:Files'
import 'stdlib:Process'
import 'stdlib:Text'
import 'stdlib:Collections' exposing: [first] forms: [:dotted]
import './lib/count.hey'

fn schema()
  return Cli.schema('wordfreq [FOLDER]', 'Count the most common words in text files.', [
    Cli.option('top', 'int', 10, 'how many words to show'),
    Cli.option('ext', 'string', '.txt', 'which file ending to read'),
    Cli.option('git', 'bool', false, 'only read files git tracks'),
    Cli.option('help', 'bool', false, 'show this help')
  ])
end

# Hey has no statement that sets an exit status yet, so hand the text
# to /bin/sh, which prints it and exits with the status we choose.
fn finish(text, status)
  Process.exec_env_argv({}, ['/bin/sh', '-c', 'printf "%s" "$1"; exit "$2"', 'wordfreq', text, status.to_s])
end

fn files_from_git(folder, ext)
  let run = Process.run_argv(['git', '-C', folder, 'ls-files', '*' + ext])
  if !run.ok
    return []
  end
  let out = []
  for name in Text.lines(run.stdout)
    if name != ''
      set out = [...out, Files.join(folder, name)]
    end
  end
  return out
end

program
  let parsed = Cli.current()
  let checked = Cli.validate(parsed, schema())
  if !checked.ok
    finish(checked.error + "\n" + Cli.help(schema()) + "\n", Cli.exit_status(checked))
  end
  if Cli.typed_flag(checked, 'help', false)
    finish(Cli.help(schema()) + "\n", 0)
  end

  let folder = Cli.parsed_positionals(parsed).first('.')
  if !Files.directory?(folder)
    finish('wordfreq: no such folder: ' + folder + "\n", 1)
  end

  let ext = Cli.typed_flag(checked, 'ext', '.txt')
  let paths = []
  if Cli.typed_flag(checked, 'git', false)
    set paths = files_from_git(folder, ext)
  else
    set paths = Files.files(folder, ext)
  end

  let counts = {}
  for path in paths
    set counts = WordCount.add(counts, Files.read_text(path))
  end

  says "#{paths.length} files, #{entries(counts).length} different words"
  for pair in WordCount.top(counts, Cli.typed_flag(checked, 'top', 10))
    says "#{Text.pad_left(pair[1].to_s, 6, ' ')}  #{pair[0]}"
  end
end

7. Script or binary? Measure it

You've been running hey wordfreq.hey. That's the script path: Hey compiles the program to native code the first time and keeps the result in a cache keyed by the source and everything it imports. Change any imported file and the next run recompiles. Nothing goes stale.

You can also make the file itself executable:

$ head -1 wf
#!/usr/bin/env hey
$ chmod +x wf
$ ./wf --top=3 sample

     2  a

How fast is it on real text? Partly works

Hey's goal is C and Rust speed for every program. Startup is already there. The counting is not, today, because of the copying defect from section 3. We ran the built binary and a plain Ruby script doing the same job on one 245 KB file of Hey's own docs (32,761 words, 5,188 different ones), 5 runs each:

ProgramMean time
build/wordfreq (Hey, native)2.65 s
wordfreq.rb (Ruby 4.0.6 with YJIT)66 ms
Same work in Hey (same cleaning and ranking), but the map is created inside the counting function68 ms

The last row does exactly the same work as wordfreq; the only change is where the map starts. It runs level with Ruby, so the whole gap is the copying. That is the number wordfreq should reach once the compiler stops copying a map that arrives as a parameter; it's still short of the C-speed goal. Performance work for the 606a release and after is tracked in Performance; we'll re-measure this table when the fix lands.

8. Ship it as a package command Works today

A package can declare commands in its hey-package.json. Anyone who depends on the package gets the command, verified against the lock file's hashes every time it runs. This is how hey_secret_lint ships secret-lint:

  "commands": {
    "secret-lint": "bin/secret-lint.hey"
  }

From a project that depends on it:

$ cat hey-package.json
{
  "name": "lintdemo",
  "version": "0.1.0",
  "registry": "https://www.jayteesf.com/packages/registry-v1.json",
  "dependencies": {
    "hey_secret_lint": "^0.1.0"
  }
}
$ hey package ensure --project . --update-lock
ensured hey_packager@0.1.13 from hey_secret_lint
ensured hey_secret_lint@0.1.2 from project
updated ./hey.lock.json packages=2 edges=1
$ hey package commands --project .
secret-lint hey_secret_lint@0.1.2 bin/secret-lint.hey
$ cat app.hey
module Login
  fn allowed?(row, attempt)
    return row.key_hash == attempt
  end
end
$ hey secret-lint .; echo "exit status: $?"

A package can't shadow a built-in command, and two packages can't claim the same name. Publishing your own package is guide 2.
