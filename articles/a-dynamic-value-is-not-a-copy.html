Hey language · runtime design note · 7 August 2026

A Dynamic Value Is Not a Copy

Hey can keep Ruby-like dynamic values without returning to the allocation-and-copy behavior that made immutable code painfully slow. The key is to separate a type question from a storage strategy.

Explored, not yet fully shipped

TL;DR

  • Verdict: keep dynamic values, reject box-and-copy execution. A runtime type tag may be necessary; copying the payload is not.
  • When the compiler knows the type, integers and booleans stay native, while strings and collections keep references to immutable backing storage.
  • At a genuinely dynamic boundary, use a small tagged handle, inspect its tag, and borrow the existing payload.
  • Weakness: Hey still has legacy paths where “boxed” can mean allocation, cloning, or stringification. This policy is the destination, not a claim that every path already follows it.
  • Falsifiability: increase a dynamic read, comparison, or same-process actor-send loop from thousands to hundreds of thousands of iterations; payload-copy bytes must remain zero and allocator counts must not grow with the loop.

The word “boxed” is doing too many jobs

When a compiler says a value is “boxed,” that may mean only that its type is not statically known. But the same word is often used for a much more expensive implementation: allocate a wrapper, copy the payload into it, pass the wrapper, then extract or copy the payload again.

Those are different decisions. Hey still needs runtime type information in places such as heterogeneous values, generic APIs, the REPL, actor messages, and JSON-shaped data. It does not follow that those values must be copied.

The useful distinction: “dynamic” answers when do we know the type? “Box-and-copy” answers how do we store and move the value? The first can be necessary while the second remains a bug.

Three representations, one language

Known integer or booleanNative machine valueNone

The compiler should erase the dynamic machinery whenever it proves the type. Where it cannot, the runtime should inspect the tag and use the same backing storage. That keeps Ruby-like ergonomics without charging every operation the cost of a heap allocation.

What dynamic find should do

A recent compiler bug made the distinction concrete. A generic operand reached a string helper, which converted the value to text before checking whether it was actually a string. An integer such as 123 silently became "123". The operation succeeded, but the language semantics were wrong.

known String + known String
  → direct string search

known Bytes + known Bytes
  → direct byte search

dynamic Value + dynamic Value
  → inspect both tags
  → String/String: borrow both string payloads
  → Bytes/Bytes: borrow both byte payloads
  → anything else: Hey type error

The important line is the one that is absent: there is no generic “convert to string” step. A runtime helper may cost a tag comparison. It must not turn type checking into coercion, and it must not duplicate the data merely to inspect it.

Where quadratic copying comes from

Immutability becomes expensive only when an implementation rebuilds everything. If an accumulator of length 1 is copied to make length 2, then copied again to make length 3, the total work after n updates is roughly 1 + 2 + … + n. That is the quadratic trap.

The escape is not visible mutation in user code. It is better representation: structural sharing for persistent collections, transient builders before publication, and in-place reuse when ownership proves the old value has no surviving aliases.

For same-process actors, immutable messages should be transferred or shared. Deep copying belongs at explicit process and network boundaries—not between two actors living in the same runtime.

The performance contract

This design is only useful if it is measurable. The runtime should expose counters such as payload_copy_bytes, actor_send_payload_copy_bytes, borrow_promotions, and container_full_rebuilds. Then the gates become blunt and hard to game:

  • A dynamic scalar comparison copies zero payload bytes.
  • A read from a dynamic string or collection borrows existing storage.
  • A same-process actor send copies zero immutable payload bytes.
  • Repeated spread or indexed update grows approximately linearly when prior versions are dead.
  • Retained historical versions share unchanged branches rather than rebuilding the whole collection.

What is not yet true

This is the policy Hey is converging on, not a victory lap. The compiler still uses the name boxed for several paths that do not all have the same cost or semantics. Some helpers still allocate, clone, or stringify where a tag check and borrow should be enough. Renaming the representation to Value or tagged_value would make the intended contract harder to misunderstand, but the name change is less important than the counters.

The verdict: Hey should preserve dynamic values and remove box-and-copy behavior. The target cost of uncertainty is one tag check. The target cost of immutability is sharing—not duplication.

Terms used here

Tagged value
A small runtime representation carrying a type tag plus an immediate scalar or a reference to existing payload storage.
Borrow
A temporary, non-owning view of a value that does not copy or outlive its valid scope.
Structural sharing
Building a new immutable collection by reusing unchanged branches and replacing only the changed path.
Copy-on-write
Sharing storage until a write occurs, then detaching only when the storage is not uniquely owned.
