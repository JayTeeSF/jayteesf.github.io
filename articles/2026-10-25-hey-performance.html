Hey performance: Rust speeds, honestly

The goal is C speed on every benchmark and every real app. Today Hey matches C on two workloads, is 1.3 to 2.6 times C on ten others, and is about 56 times C on the 1BRC data-processing benchmark. This page shows those numbers, how they're measured, and the decided work that has to close the gap.

1. The bar: as fast as C, for every program Decided, coming

On the Maintainer set the bar: Hey has to be on par with C, or faster, on all the benchmarks, and above all fast for the programs people build with it: hey_web servers, phone apps and TV apps. Benchmarks only stand in for those. (It replaced an interim "1BRC within 10–15 times C" target that was set while the compiler was cheating; see section 3.) "Rust speeds" in the title is the same idea: Rust and C land in the same place on these programs.

Every number below is a ratio: Hey divided by C for the same program, same input, same machine. 1.0 means a tie. 2.0 means Hey does twice the work.

Mostly into work around the work. A profile of the plain 1BRC program found about 45% of the time in three stdlib calls, and most of that wasn't their real job: Files.read_line built and freed a Result record and a line record for every line; Text.split allocated an array and copied both fields into new strings; then all of it was released a moment later. The lesson recorded that day: profile a stdlib call's overhead apart from its work. Works today (a lesson in force) The integer loop has none of that, which is why it ties C, and why "Hey is just slow at this" isn't an answer anyone gets to give.

The two numbers that look worst, explained

1BRC changed programs. Older releases scored a quarter of today's instructions on 1BRC, but they compiled a different, hand-tuned program (about 170 MB of memory, and before that a hand-tuned memory-mapping library). Today's is plain Hey that streams the file in 5.8 MB.1 That comparison is between programs, not compilers.
With copy-on-write off, W9 takes 1,309.5G. That's 713 times the default. HEY_RC_COW=0 switches off the runtime's "is anyone else holding this?" test, so only the compiler's own proof that a value is unshared can update it in place. The gap says the compiler can't prove that yet for W9, W10 and 1BRC (which times out at 300 s). Closing it is in section 5.

Self-compile: the compiler compiling itself Works today (measured)

The biggest real program written in Hey is its own compiler. On a Mac M3 Pro, a whole self-compile takes about 15,800 billion instructions and peaks near 8.8 GB of memory, in the LLVM emit stage; the previous release took 6.3% more instructions and 10% more memory. On Linux a full build takes about 100 minutes with a 1.5 GB peak.

3. How we measure, and how we refuse to cheat Works today (rules in force)

A fast number is easy to get by teaching the compiler one benchmark. Hey's rules are written to make that impossible, and they came from getting it wrong.

Idiomatic programs. Benchmarks are written the way anyone would write Hey. A benchmark's source is never bent around a compiler defect; the defect is fixed instead.2
Instructions and peak memory. Counted by the processor and the OS for every process, including the C compiler's children. Wall time counts only on a quiet machine (load below 1.5).
Doubling curves. Run at N, 2N, 4N, 8N. Linear work doubles; a 4× step means something is quadratic, even if one size looked fine.
A scoreboard against the last release. Every change is compared with the previous release for correctness, time and memory. A landing needs every gate, the self-compile peak, and build times compared with the previous release.

Falsification hooks: the switches that must break things Works today

Hey's runtime keeps one test for "can I update this in place?": is the reference count exactly 1? Two environment variables sabotage that single test on purpose. HEY_VIOLATE_COW_UNIQUENESS=1 says "yes, unique" every time, so shared values get overwritten and the ownership specs must fail. HEY_RC_COW_FORCE_SHARED=1 says "no, shared" every time, so everything copies: output must stay the same and the copy counters must move. If a gate still passes with a hook on, the gate isn't testing anything.3

alias.hey

fn bump(m)
  return m.put('x', 2)
end

program
  let a = {x: 1}
  let b = bump(a)
  says a
  says b
end

Run it

$ hey build alias.hey -o alias
...
$ ./alias
{"x":1}
{"x":2}
$ HEY_VIOLATE_COW_UNIQUENESS=1 ./alias
hey: HEY_VIOLATE_COW_UNIQUENESS is ON -- the copy-on-write uniqueness test is DISABLED and every mutation writes through. This is stage (b)'s falsification mode; results are not product behaviour.
{"x":2}
{"x":2}
$ HEY_RC_COW_FORCE_SHARED=1 ./alias
{"x":1}
{"x":2}

With the uniqueness test sabotaged, a changed underneath the caller: exactly the bug the specs must catch. Forcing copies keeps the output right and costs work. On the counting program from Values, memory and Strings (n = 100,000), the default took 176,158,284 instructions; HEY_RC_COW_FORCE_SHARED=1 took 46,938,780,478 and HEY_RC_COW=0 46,938,612,348, both printing the same 100. That 266× is the copy-on-write gap from section 2 on a program you can run.

Three stories that made the rules

  1. The region that fit one tree. One release freed records in bulk through a "region", but its rule admitted only records of integers built by recursive calls, which matched exactly one benchmark: binary trees . It was deleted, and W11's cost per operation went from 426.8 to 850.8 instructions. The general version is designed in Values, memory and Strings.
  2. The 1BRC library. Until the 1BRC examples imported a memory-mapping library "shaped around compiler limits". Replacing it with plain Hey made the scorecard look 6.2× worse, while the same plain program actually took 25% fewer instructions on the newer compiler. The library had been measuring its author, not the compiler.
  3. The planner that read spellings. A region planner decided which calls keep their arguments by looking up operation names like len and split in a list. Rename a function and the answer changes. It was reverted. Facts come from the compiler's resolved identities, never from names.
Spot the cheat. Two ways to make the counting loop below faster. One is honest. Which? 
let counts = {}
for word in words
  if counts.has?(word)
    set counts = counts.put(word, counts[word] + 1)
  else
    set counts = counts.put(word, 1)
  end
end

Inside a program block with let words = ['a', 'b', 'a', 'c', 'a'] and says counts, hey cheat.hey prints {"a":3,"b":1,"c":1}.

A. The emitter sees a variable named counts updated with put inside a for loop, and emits a mutable hash table for it.
B. MIR proves counts has one owner and isn't read again after the put, marks that put ; own … ; reuse … in MIR, and the runtime updates the map in place.5
Show the answer

A is the cheat. It's keyed on a name and a shape, and it's decided in the emitter, which must only obey MIR's plan. Rename the variable, or move the loop into a helper, and the speed disappears. B is honest: "one owner" and "not used again" are facts any program can have, and B is what MIR does today for this loop; the runtime then checks that the count really is 1 before writing in place (see Values, memory and Strings).

4. Why compiles are slow, and the 60% plan

A whole self-compile is about 16 minutes. The goal, set, is about 60% faster: 16 minutes down to about 6.5, counting every stage and the C compiler. Decided, coming (the goal)

The bottleneck ledger names the causes, each measured:

  • Every stage grows faster than the program. Doubling the input program multiplied each stage's work by 2.5 to 3.4 times. Linear would be 2.
  • Re-reading text. HIR rediscovered operator precedence by scanning expression text (about 19% of HIR emission); stages pass text to each other and re-parse it several times.
  • Copying values. Maps and arrays updated by copy (a resolver helper copied its whole array on every put); growing strings built with + (about 14% of HIR emission was moving memory).
  • Re-checking. MIR's read-and-verify re-derived ownership at every boundary, about 950 billion instructions per self-compile. It stays on in gates; release builds skip the self-check (ruling).

These are the same costs ordinary programs pay. The compiler is a Hey program using the same runtime, so a fix to map copies speeds up compiles and apps at once.

What the compiler overhaul does about it Decided, coming

  • No double parse. Each file is parsed once, into the syntax tree that every stage reads.
  • No quadratic copying in type narrowing: a worklist instead of copied rounds.
  • Smaller IR between stages.
  • Parallel and incremental module builds. Reuse a module that hasn't changed, with sound invalidation and bounded memory.

What comes after that

  • The 16-byte String (Values, memory and Strings): the baseline found Hey's split 25.5× C, building strings 4.4× C and slicing 283× Rust (Rust borrows). The 16-byte String targets those directly.
  • Native ABI v2 (Native code and C): a native call cost about 5,374 instructions when measured; the static design is estimated at 40 to 90 (an estimate, not a measurement), and the release goal is at most 200, measured.

Specialization: one fast copy per type Decided, coming

Hey has no type annotations, so a function like fn add(a, b) has to accept anything, and every value travels in a box with a type tag. Specialization compiles a separate native copy for each set of concrete types a call site actually uses: add called with two Ints gets a copy that adds two machine integers. The mechanism (instance key, cache, cap, depth limit) is in the compiler article. Its effect on these numbers hasn't been measured yet. Today a cast such as n.to_i gives the same unboxed path, and every program can use it.

6. Mechanisms already working

Self tail calls don't grow the stack Works today

A function whose last act is calling itself with Int arguments reuses its own stack frame: MIR marks the call tail.self, and LLVM emits a musttail call. Without that, a ten-million-deep recursion would need hundreds of megabytes of stack.

tail.hey

fn sum_down(remaining, total)
  if remaining == 0
    return total
  end
  return sum_down(remaining - 1, total + remaining)
end

program
  says sum_down(10000000, 0)
end

Run it

$ hey tail.hey
50000005000000

See the plan in MIR, then the LLVM call

$ hey phase mir tail.hey -o tail.mir
...
$ hey phase llvm tail.mir -o tail.ll
...
$ grep tail.self tail.mir; grep -c musttail tail.ll
  tail.self i64 call @t0.0 sum_down(remaining - 1, total + remaining)
1

Ten million calls deep, and it returns the right sum.

Run on a Mac M3 Pro.

The limits: only direct self-recursion where the function and every parameter are plain 64-bit integers. Mutual recursion, Strings, boxed values, actors and closures stay ordinary calls for now.
