A web server in Hey

You'll start with a three-line route, test it without opening a socket, then grow it into a small hey_web app with controllers, views, a SQLite database and background Jobs. Then you'll break a handler on purpose, build the server into one native binary, and measure the two ways Hey can carry connections.

The short version

  • A route is a function. Web.get('/hello/:name', hello) pairs a path with an ordinary Hey function that takes a request and returns a response.
  • The same route table runs with or without a socket. Web.dispatch answers a request value in a test; Web.serve answers real HTTP.
  • hey_web 0.3.9 adds the Rails-shaped parts: config file, controllers, EHY views with layouts, Jobs helpers, a request log, auth helpers and a curl-like client.
  • A failing handler costs one request. That request gets a 500; the next one is served normally.
  • The default transport is a thread per connection. A second lane, the readiness poller, is opt-in: you import it and call one different function. Pick it when you hold many mostly idle connections.

1. Your first route Works today

A route is a pair: an HTTP method and path, and the function that answers it. A handler is that function. It gets one argument, the request, and returns a response. No classes, no decorators.

hello_web.hey

import 'stdlib:Web'

fn hello(request)
  return Web.text('Hello, ' + request.params.name + "\n")
end

fn health(request)
  return Web.json({ok: true})
end

program
  let routes = Web.routes([
    Web.get('/hello/:name', hello),
    Web.get('/health', health)
  ])
  says 'listening on http://127.0.0.1:8080'
  let served = Web.serve(routes, {host: '127.0.0.1', port: 8080, workers: 4})
end

:name in the path is a path parameter: whatever sits in that spot of the URL shows up as request.params.name. Run it with hey hello_web.hey (it compiles to native code and caches it, like go run), then from a second terminal:

$ curl -i localhost:8080/hello/Ada
HTTP/1.1 200 OK
content-type: text/plain
content-length: 11
connection: keep-alive

Hello, Ada

$ curl localhost:8080/health
{"ok":true}

$ curl -i localhost:8080/nope
HTTP/1.1 404 Not Found
content-type: application/json
content-length: 21
connection: keep-alive

{"error":"not_found"}

The server also prints one line to stderr when it starts. It's worth reading once, because it tells you the limits the runtime picked for this machine:

hey: web connection pool armed -- max_connections=2304 (derived, binding anchor=memory_limit; fd anchor=1/2 of RLIMIT_NOFILE=1048576 less 20 reserved; stack anchors=1/4 of RLIMIT_AS and 1/8 of governing memory=18432MB, at 1024KB per thread) workers=4 reserved_address_space=2304MB idle_retire=10000ms over-bound policy=503+close

In plain words: four worker threads to start, room for at most 2,304 open connections (worked out from this Mac's memory), and a connection past that limit gets a 503 and is closed. Keep that 2,304 in mind; it comes back in section 10.

The response helpers in stdlib:Web: Web.text, Web.html, Web.json, Web.created (201), Web.accepted (202), Web.bad_request, Web.unauthorized, Web.forbidden, Web.not_found, Web.method_not_allowed, Web.conflict, Web.payload_too_large, Web.unprocessable, Web.server_error, Web.redirect(location) and the general Web.response(status, headers, body). Routes: Web.get, Web.post, Web.put, Web.patch, Web.delete. Reading the request: Web.param, Web.query_param(request, name, fallback), Web.header, Web.body, Web.json_body. Static files: Web.file(root, path) and Web.file_from(request, root), which pick the content type from the extension. CORS: Web.cors(policy) (see the note on the middleware helpers).

2. Test routes without a socket Works today

Here's the part Rails and Express people tend to like. The route table is a plain value, so you can hand it a request value and get a response value back. No port, no HTTP client, no waiting for a server to come up. Web.dispatch is the function that does the matching, and Web.serve uses the same function for real requests.

hello_dispatch.hey

spec 'routes answer without a socket'
  expect stdout "200\nHello, Ada\n\n404\n"
end

import 'stdlib:Web'

fn hello(request)
  return Web.text('Hello, ' + request.params.name + "\n")
end

program
  let routes = Web.routes([Web.get('/hello/:name', hello)])
  let found = Web.dispatch(routes, {method: 'GET', path: '/hello/Ada', headers: {}, body: ''})
  says found.status
  says found.body
  let missing = Web.dispatch(routes, {method: 'GET', path: '/nope', headers: {}, body: ''})
  says missing.status
end

The spec block at the top says what the program must print. heyc FILE --test runs the program and compares:

$ hey hello_dispatch.hey
200
Hello, Ada

404

$ HEY_STDLIB_PATH=~/hey/stdlib heyc hello_dispatch.hey --test
PASS: routes answer without a socket

Snag we hit: outside the Hey source folder, heyc FILE --test answered heyc: file not found: stdlib/Web.hey until we set HEY_STDLIB_PATH to the toolchain's stdlib folder, as shown. hey FILE needed nothing extra. (Recorded as a gap on the documentation task #{DOC}; First steps covers specs.)

3. What happens to one request

Two things to take from the picture. First, everything except your handler is the runtime's C code: reading bytes, parsing the HTTP head, writing the reply. Second, the default lane gives each open connection its own thread for as long as the client keeps it open. (Browsers and HTTP clients keep a connection open after a request so the next one skips the TCP handshake; that's keep-alive.) That's simple and fast while connections are busy, and it's the reason a second lane exists (section 10).

4. Grow it into a hey_web app Works today

hey_web is a package (version 0.3.9) that sits on top of stdlib:Web. It doesn't parse HTTP or open sockets itself. It adds the shape a Rails developer expects:

ERB views and layoutsEHY templates through HeyWebView
Active JobHey Jobs + HeyWebJobs
Active Recordhey_record over hey_sqlite3, hey_postgres, hey_mysql

    return [
      Web.get('/', CardsController.index),
      Web.get('/cards', CardsController.list),
      Web.post('/cards', CardsController.create),
      Web.get('/search', CardsController.search),
      Web.post('/signup', CardsController.signup),
      Web.get('/boom', CardsController.boom),
      Web.get('/health', CardsController.health)

app/controllers/cards_controller.hey

import 'stdlib:Web'
import 'stdlib:Text'
import 'pkg:hey_web@0.3.9/views'
import 'pkg:hey_web@0.3.9/jobs'
import '../models/card_store.hey'
import '../jobs/welcome_job.hey'

# <%= %> prints text as it is. Escape anything a user typed before it reaches a view.
fn h(text)
  let out = Text.replace_all('' + text, '&', '&amp;')
  set out = Text.replace_all(out, '<', '&lt;')
  set out = Text.replace_all(out, '>', '&gt;')
  return Text.replace_all(out, '"', '&quot;')
end

module CardsController
  fn index(request)
    let shown = []
    for card in CardStore.all()
      set shown = [...shown, {front: h(card.front), back: h(card.back)}]
    end
    return HeyWebView.response('app/views/cards/index.ehy', {title: 'Cards', cards: shown}, 'app/views/layouts/application.ehy')
  end

  fn list(request)
    return Web.json({cards: CardStore.all()})
  end

  fn create(request)
    let body = Web.json_body(request)
    let added = CardStore.add(body.front, body.back)
    if added.ok == false
      return Web.bad_request({error: added.error})
    end
    return Web.created({front: body.front, back: body.back})
  end

  fn search(request)
    return Web.json({q: Web.query_param(request, 'q', '(none)')})
  end

  fn signup(request)
    let body = Web.json_body(request)
    return HeyWebJobs.accepted(WelcomeJob.pool(), {email: body.email})
  end

  fn boom(request)
    fail 'this handler always fails'
  end

  fn health(request)
    return Web.json({ok: true})
  end
end

server.hey

import 'stdlib:Cli'
import 'pkg:hey_web@0.3.9/main'
import 'pkg:hey_web@0.3.9/config'
import 'pkg:hey_web@0.3.9/server'
import 'config/routes.hey'
import 'app/models/card_store.hey'

program
  let ready = CardStore.setup()
  let config = HeyWebServer.options(Cli.args(), HeyWebConfig.load_or_default('config/hey_web.json'))
  let app = HeyWeb.application('cards', Routes.all(), config)
  says HeyWebServer.banner(app)
  let running = HeyWeb.serve(app)
end

HeyWebServer.options reads the JSON and then lets flags override it, so --port 3001, --workers 8, --host, --request-timeout-ms and --max-body-bytes all work. workers: 0 means one per CPU core.

Predict it. server.hey imports pkg:hey_web@0.3.9/main, and main.hey itself imports config.hey. So why does server.hey also import .../config?

Answer

Imports in Hey are lexical: a file may call a module only if that file imports it. Importing main doesn't pass HeyWebConfig through to you. Leave the import out and the compiler stops with:

hey error: hey_resolve_program: missing direct module import: routes_spec.hey:10:55: HeyWebConfig.defaults requires a direct import in this source unit

That's on purpose: you can read any file and see every module it can touch. Modules, imports, exports has the rules.

5. Views: EHY templates and layouts Partly works

EHY is Hey's version of ERB. <%= expr %> prints a value, <% code %> runs a statement (loops, ifs), <%# ... %> is a comment, and -%> also eats the newline after the tag. {{ name }} is Mustache, not EHY.

app/views/layouts/application.ehy

<!doctype html>
<html><head><title><%= title %></title></head>
<body>
<%= content %>
</body></html>

app/views/cards/index.ehy

<h1><%= title %></h1>
<ul>
<% for card in cards %>
  <li><%= card.front %> &rarr; <%= card.back %></li>
<% end %>
</ul>

The controller calls HeyWebView.response(view, bindings, layout). The view renders first; its output becomes content in the layout. Pass '' as the layout for none.

Escaping is your job

<%= %> prints text exactly as it is. It does not turn < into &lt;, and the standard library has no public HTML-escape function today. That's why the controller above runs every user-typed field through its own small h() before handing it to the view. Without it, the card whose front is <b>x</b> would be bold, and a card holding a <script> would run in your visitors' browsers.

What happened when we ran it

The first request to / failed:

The escaped card shows up as text, as it should. But look at the timings: about 130 ms for the EHY page against under 1 ms for the same rows as JSON, because each request runs two small programs (view, then layout). Each render also leaves a build/ehy_render_*.hey file behind that nothing deletes.

What to use instead, today. The hey_web apps that serve real users don't render EHY per request. elders_prayer_app reads HTML templates with Files.read_text and fills {{TOKEN}} placeholders with Text.replace_all; hey_web's bin/pages-embed renders .html.ehy files once, at build time, into a generated Hey module, so serving a page is returning a string. Request-time EHY is fine for an admin page; don't put it on a hot path. A request-time EHY that compiles each template once and doesn't need the source tree is not built and has no task yet.

6. A database Works today (as packages)

Hey has no database built in. Drivers are packages, published in the same registry as hey_web:

PackageLatestWhat it is
hey_sqlite30.5.2SQLite through a small C library: prepared statements, typed rows, rows as JSON built by SQLite itself
hey_postgres0.1.0PostgreSQL
hey_mysql0.4.2MySQL / MariaDB, settings from env with a prefix (from_env_prefix)
hey_duckdb0.1.0DuckDB, for analytics queries
hey_record0.5.2models on top of a driver (the Active Record role)

hey_sqlite3 is a native package: part of it is C that has to be compiled for your machine once. That's one command, and its output is a library file you point the app at:

$ HEY_ROOT=~/hey \
    .hey/packages/hey_sqlite3/0.5.2/bin/build-native --out "$PWD/.hey/native/hey_sqlite3"
native_target=darwin-arm64
native_library=.../cards/.hey/native/hey_sqlite3/libhey_sqlite3.dylib

$ export HEY_SQLITE3_LIBRARY="$PWD/.hey/native/hey_sqlite3/libhey_sqlite3.dylib"

(Give --out an absolute path. With a relative one, the build wrote its generated C into one place and then looked for it in another: clang: error: no such file or directory.)

app/models/card_store.hey

import 'stdlib:Env'
import 'pkg:hey_sqlite3@0.5.2/adapter'

# One place that opens the database. A connection is not shared
# between threads, so each call opens its own and closes it.
module CardStore
  fn path()
    return Env.default('CARDS_DB', 'db/cards.sqlite3')
  end

  fn open()
    let connected = Sqlite3.connect(CardStore.path(), {library_path: Env.default('HEY_SQLITE3_LIBRARY', '')})
    if connected.ok == false
      fail connected.code + ': ' + connected.error
    end
    return connected.value
  end

  fn setup()
    let db = CardStore.open()
    let made = Sqlite3.execute(db, 'CREATE TABLE IF NOT EXISTS cards (id INTEGER PRIMARY KEY, front TEXT NOT NULL, back TEXT NOT NULL)')
    let closed = Sqlite3.close(db)
    return made.ok
  end

  fn add(front, back)
    let db = CardStore.open()
    let added = Sqlite3.execute_params(db, 'INSERT INTO cards (front, back) VALUES (?, ?)', [front, back])
    let closed = Sqlite3.close(db)
    return added
  end

  fn all()
    let db = CardStore.open()
    let found = Sqlite3.query(db, 'SELECT id, front, back FROM cards ORDER BY id')
    let closed = Sqlite3.close(db)
    return found.value.rows
  end
end

Typed rows means each column comes back as the Hey value its SQLite type maps to: the INTEGER id arrives as a number ("id":1 below, no quotes), TEXT as a string, NULL as nil, a BLOB as bytes. You don't parse strings back into numbers.

The ? placeholders are filled by SQLite from the list you pass, so a value never becomes part of the SQL text. That's what keeps the <b>x</b> card from being anything but data:

$ curl -i -X POST localhost:3000/cards -d '{"front":"hola","back":"hello"}'
HTTP/1.1 201 Created
content-type: application/json
content-length: 31
connection: keep-alive

{"front":"hola","back":"hello"}

$ curl -X POST localhost:3000/cards -d '{"front":"<b>x</b>","back":"tags & such"}'
{"front":"<b>x</b>","back":"tags & such"}

$ curl localhost:3000/cards
{"cards":[{"id":1,"front":"hola","back":"hello"},{"id":2,"front":"<b>x</b>","back":"tags & such"}]}

$ curl 'localhost:3000/search?q=cats'
{"q":"cats"}

Rules for database calls in a server

  • One connection per thread. A connection is mutable state outside Hey; don't share one between workers. This sample opens one per call to stay short. A busier app keeps one per worker so SQLite's statement cache stays warm.
  • Database calls block. On the default lane that's acceptable: it ties up one worker for that request. On the poller lane (section 10) it stalls every connection on the loop, so move slow queries into a Job there.
  • Migrations are yours. Neither hey_web nor the drivers ship a migration tool. elders_prayer_app's bin/db-migrate is a worked example: db/schema.sql creates tables with CREATE TABLE IF NOT EXISTS, and the script checks each expected column with pragma_table_info, adding the missing ones, with a --check mode for deploys.
  • JSON straight from SQLite. Sqlite3.query_rows_json(db, sql, params) returns the rows already encoded as JSON text, so a JSON endpoint doesn't build Hey values just to turn them back into text.

Decided, coming Today each call into the C library goes through a general-purpose bridge that looks the function up by name and packs the arguments into an array at run time. On the Maintainer ruled for statically bound native calls (decision L-IMP-30 in the decision ledger): the compiler reads the package's hey.native.json at build time and emits a direct, typed call to the generated C wrapper. That's part of the native ABI v2 train (ABI: the agreed shape of calls between Hey code and C code), built in the resolver, MIR and LLVM stages. It's in progress; the measured cost per call today and after, and the schedule, are in Native code and C and the roadmap.

7. Background work with Jobs Works today

A Job is a named pool of worker threads with a bounded queue. You hand it a message, you get a receipt back right away, and a worker runs the function later. Retries, dead letters and how to choose between Jobs, workers and actors are in Workers, Jobs and streams; here's the web part.

app/jobs/welcome_job.hey

import 'stdlib:Jobs'

# A worker is a plain function that runs on the Job's own threads.
worker SendWelcome(message)
  return 'welcome sent to ' + message.email
end

module WelcomeJob
  # Jobs.define names the pool. Defining the same name again hands back
  # the pool that already exists, so a handler can call this every time.
  fn pool()
    return Jobs.define('CardsWelcomes', SendWelcome, count: 2, capacity: 64, result_capacity: 64)
  end
end

The controller's signup calls HeyWebJobs.accepted(WelcomeJob.pool(), {email: body.email}). That enqueues the work and answers 202 Accepted with the receipt, so the client can ask about it later (HeyWebJobs.await(job, receipt, timeout_ms) waits for the result). If the queue is full the client gets a 500 with job_queue_full instead of the request hanging.

$ curl -i -X POST localhost:3000/signup -d '{"email":"ada@example.com"}'
HTTP/1.1 202 Accepted
content-type: application/json
content-length: 51
connection: keep-alive

{"accepted":true,"job":"CardsWelcomes","receipt":1}

Why not the shorter job Welcomes ... end form? We tried it first. That declaration only works in the file that holds program; put it in app/jobs/ and import it, and the compiler says:

heyc: job declarations are application-entry declarations and cannot be imported: job Welcomes

A handler also can't see values the program made at startup (handlers are looked up by name and capture nothing). So the pattern real apps use, and this sample uses, is a function that calls Jobs.define with a fixed name. recall_coach_app's workers do the same.

8. When a handler fails Works today

Hey fails fast: there's no try/rescue. A runtime error or a fail stops the unit of work it happened in, and for a server that unit is one request. The /boom handler above always fails. Here's the server answering it, then answering the next request as if nothing happened:

$ curl -i localhost:3000/boom
HTTP/1.1 500 Internal Server Error
content-type: application/json
content-length: 24
connection: keep-alive

{"error":"server_error"}

$ curl -i localhost:3000/health
HTTP/1.1 200 OK
content-type: application/json
content-length: 11
connection: keep-alive

{"ok":true}

server log (default lane):
hey error: this handler always fails

server log (poller lane, same request):
hey error: this handler always fails
hey: web handler on GET /boom stopped by a runtime error; answering 500

That held on the native binary, on hey server.hey, and on both transport lanes. The runtime also releases the values that the abandoned function calls had registered, so a failing route doesn't pile up memory (one known hole: a value the compiler kept only in a CPU register, never registered, can still leak; closing it is compiler work in progress). What this does not cover: a handler stuck in an endless loop without an error is not stopped (that needs safe points, places the compiler inserts where a running loop can be told to stop; decided separately, not built), and a call blocked inside C can't be interrupted. The full rules, with actors and Jobs, are in Actors and failure.

One difference we saw: on the default lane the log names only the error, while the poller lane also names the route (GET /boom). Put the route in your own fail message until both lanes log it (recorded on #{DOC}).

10. Going fast: the two transport lanes

Same routes, same handlers, same request values. Only the part that moves bytes between sockets and your handler changes.

Default: Web.serve Works today

What HeyWeb.serve(app) calls. A thread per open connection. Fastest when you have a modest number of connections that are actually sending requests: API servers behind a load balancer with a small pool, internal services, benchmarks.

Opt-in: HeyWebPoller Works today opt-in

One readiness loop (also called an event loop): a single thread asks the OS "which of these thousands of sockets have data?" (kqueue on macOS, epoll on Linux), then serves just those, in a batch. Choose it when you hold many connections that are mostly idle: browsers, mobile clients, long-lived API clients.

How to turn the poller lane on

Three steps. hey_web already depends on hey_poller 0.2.3, so hey package ensure installed it. Then: (1) import pkg:hey_web@0.3.9/poller, (2) call HeyWebPoller.serve_application(app) instead of HeyWeb.serve(app), (3) build the one native library your OS needs, once.

server_poller.hey: the only change is the import and the last line

import 'stdlib:Cli'
import 'pkg:hey_web@0.3.9/main'
import 'pkg:hey_web@0.3.9/config'
import 'pkg:hey_web@0.3.9/server'
import 'pkg:hey_web@0.3.9/poller'
import 'config/routes.hey'
import 'app/models/card_store.hey'

program
  let ready = CardStore.setup()
  let config = HeyWebServer.options(Cli.args(), HeyWebConfig.load_or_default('config/hey_web.json'))
  let app = HeyWeb.application('cards', Routes.all(), {...config, workers: 1})
  says 'cards on the readiness lane (one kqueue/epoll loop)'
  let served = HeyWebPoller.serve_application(app)
end

  • workers here means number of loops. They share the port with SO_REUSEPORT (a socket option that lets several listeners bind one port); Linux spreads connections across them, macOS doesn't, so use one loop on a Mac.
  • Run from the project root, or set HEY_KQUEUE_LIBRARY (macOS) / HEY_EPOLL_LIBRARY (Linux) to the library's path.
  • Handlers run on the loop's thread. A slow query or an outbound HTTP call stalls every connection on that loop. Keep handlers quick and push slow work into Jobs.
  • Not supported on this lane: chunked request bodies (answered 411) and request heads over 64 KiB (431). Bodies over max_body_bytes get 413.
  • On Linux you can ask for io_uring (Linux's newer interface that queues I/O requests in memory shared with the kernel) instead of epoll with HEY_POLLER_BACKEND=io_uring; if the kernel or Docker's seccomp profile (Docker's default list of blocked system calls) blocks it, it falls back to epoll and says why on stderr.

"Successful per second" is 200 responses divided by the run's length. oha's own "Requests/sec" also counts the 503s, so it reads higher for Web.serve at 4,000. "Timed out" are requests oha gave up on after its 20-second default wait or that were still open when the 10 seconds ended. Threads were counted with ps -M and memory with ps -o rss, six seconds into each run, on the listening process.

How to read it. With 64 busy connections the default lane does about 1.8 times the work, because it spreads over several cores and the single loop uses one. With 4,000 connections the two are close in throughput, but the default lane hit the 2,304-connection limit from section 1 and turned away 20,000 to 28,000 requests while holding 2,311 threads and 78 to 98 MB. The single poller loop refused nothing, used one thread and 6.6 MB, and had half the p99. That's the trade: raw throughput on few connections versus many connections at a flat, small cost.

Correction, made before publishing. Our first pass at this table read the thread and memory counts from the wrong process: lsof -ti tcp:3000 also lists the load generator's sockets, and we picked up oha's process. The table above uses lsof -ti tcp:3000 -sTCP:LISTEN, which returns only the server. If you measure this yourself, use the listening process.

Sidebar: io_uring versus epoll, and the $12-server challenge Proposed

hey_fast_web is a separate research app: a five-endpoint feed API over SQLite, one event loop per core, written to try a public "max out a $12 server" challenge. In an arm64 Linux container limited to 1 CPU it held 64,000 users for five minutes at 6,795 req/s with p99 22 ms, 0 failed requests and 52 MB of memory. The Rust io_uring entry it was compared with did the same work at about half the CPU. Its io_uring loop and its epoll loop measured within noise of each other on that VM; whether io_uring should become Linux's default is still open. None of this was run on the challenge's actual x86 box. Details: hey_fast_web/RESULTS.md.

Old numbers you may run into. hey_web's docs/PERFORMANCE.md (and a line in its README) say calls from your app into package code go through an interpreter at about 7 ms each, and that Web.serve is fastest with workers: 1. Both describe Hey 0.99.390a-era builds and are no longer true: the handlers on this page are native code, and /cards answered in under a millisecond including a SQLite query. Don't plan around those figures.

Against the bar. Hey's goal is C-level speed on every workload. This page has no C server measured on the same machine with the same load, so it makes no ratio claim. The like-for-like web numbers, and the plan for closing gaps, are in Performance.

13. Deploying it

The binary from section 9, the two native libraries, your config/, db/ and templates are the whole app. elders_prayer_app is the worked example: its bin/server builds with heyc build when sources change, refuses to start if the port is already taken (a bind conflict otherwise exits quietly with status 0), and runs the binary with line-buffered output so access-log lines show up immediately; bin/deploy ships it with Kamal behind a TLS proxy. The step-by-step, with image sizes and Linux linkage, is Build and deploy.
