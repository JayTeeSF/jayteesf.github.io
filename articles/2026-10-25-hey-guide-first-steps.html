First steps with Hey

In about fifteen minutes you'll have Hey installed, a program running as native code, a binary you can copy to another machine, a test that lives next to the code it checks, and an actor keeping count. You won't write a single type annotation.

Who this is for: you write Ruby, Go or Python and have never seen Hey. You know a terminal.

What the badges mean: Works today you can do it now. Partly works it works with a stated hole. Decided, coming ruled, not built yet. Proposed designed or asked for, no ruling yet.

Every command on this page is run by Hey's documentation test, and its output must match what you see here. Where output is long, a line with ... stands for the lines left out.

1. Install Hey

Works today on macOS (Apple Silicon) and Linux x64.

Hey installs from a checkout of its source. The installer finds your package manager, can install the C, LLVM and OpenSSL build tools it needs (only if you allow it), builds Hey, and links four commands into ~/.local/bin: hey, heyc, hey-repl and hey-install.

Preview what it will do (changes nothing), then install

$ ./install.sh --dry-run
Hey installer
...
== Build Hey ==
== Install commands ==
...
Hey installation complete.
Activate now with: . '~/.config/hey/env.sh'
Then verify with: hey --version
$ ./install.sh

Add --yes to let it install missing build tools, or --system to link into /usr/local/bin. Then open a new shell, or run the . ~/.config/hey/env.sh line it prints.

Be ready for a long first build. The installer compiles the whole compiler, which takes a while on a laptop. There's no Homebrew formula and no Windows compiler yet; the platform list has the details.

Check it worked:

$ hey --version
0.99.607a
$ hey help
Hey command line

Everyday use
...hey FILE.hey [args...]...Compile/cache and run a Hey program
...hey repl...Start the interactive REPL
...hey build FILE.hey -o APP...Build a native application
...heyc FILE.hey --test...Run embedded specs in one source file
...

hey help all lists every command, and the commands reference explains each one.

2. Hello, world

Make a file called hello.hey:

program
  says 'Hello, world'
end

program ... end is where execution starts. says prints a value and a newline. Run it:

$ hey hello.hey
Hello, world

That's a native program. Hey didn't interpret your file; it compiled it to machine code and ran that.1 Works today

3. What just happened: the native cache

Predict: the first run compiled your file. What happens on the second run of the same unchanged file?

$ time hey hello.hey
Hello, world

real	...
user	...
sys	...

Run it twice and compare the real line. The first run takes seconds, because it compiles. The second takes a few hundredths of a second.

The second run never started the compiler. A tiny native launcher checked that your file, everything it imports, and the compiler itself were unchanged, then jumped straight into the cached program.2 The cached program is native code built by LLVM, the same compiler back end Rust and Swift use.

Change one character in hello.hey, or in any file it imports, and the next run compiles again. The cache key covers the whole import graph, so you never run stale code.

The cache lives in your user cache folder (on a Mac, ~/Library/Caches/Hey; on Linux, ~/.cache/hey). hey cache path shows it; hey cache gc cleans it. Guide 6 has the details.

4. Build a binary you can ship

Works today

$ hey build hello.hey -o build/hello
built .../build/hello
$ ./build/hello
Hello, world

build/hello is an ordinary executable. Copy it to another Mac of the same kind and it runs there; Hey isn't needed on that machine.

When to use which:

Use hey file.hey whenUse hey build file.hey -o app when
you're editing and running, or it's a personal script (start it with #!/usr/bin/env hey and chmod +x)you'll copy it somewhere: a server, a container, a release, another person's machine
you want edits picked up automaticallya build must fail before deploy, not on first run
a quick cache check on each start is fineyou're benchmarking, signing, or putting it in an app bundle

The binary's size, what it links, and how to ship it are in Guide 6.

5. Values and functions

Hey values never change. You make new ones from old ones. Save this as tour_01_values.hey (it's also in the Hey examples folder):

program
  let user = {name: 'Ada', visits: 1}
  let next = {...user, visits: user.visits + 1}
  let names = ['Ada', 'Grace']
  let expanded = [...names, 'Katherine']

  says next.name + ' has ' + next.visits + ' visits'
  says expanded.to_json
  says user.name + ' still has ' + user.visits + ' visit'
end

Predict the third line before you look. next was made from user with visits bumped. How many visits does user have now?

$ hey tour_01_values.hey
Ada has 2 visits
["Ada","Grace","Katherine"]
Ada still has 1 visit

Still 1. {...user, visits: ...} copies user's fields into a new object and overrides one. let names a value; nothing can change what it names. (Why this is still fast, even in a loop, is the subject of values, memory and Strings.)

Functions are values too. Save this as tour_02_functions.hey:

fn greet(name)
  return "Hello, #{name}!"
end

fn add(a, b)
  return a + b
end

program
  let formatter = greet
  let operations = [add]
  says formatter('Ada')
  let operation = operations[0]
  says operation(40, 2)
end
$ hey tour_02_functions.hey
Hello, Ada!
42

No types written anywhere. The compiler works them out from how values are used. "#{name}" inside double quotes is string interpolation, like Ruby. The language reference covers all of it.

6. A test in the same file

Works today

A spec block says what the program should print. It sits in the same file as the code.

Here's one with a bug in it. The spec wants an exclamation mark; the function forgot it. Save it as greet.hey:

spec 'greets by name'
  expect stdout "Hello, Ada!\n"
end

fn greet(name)
  return "Hello, #{name}"
end

program
  says greet('Ada')
end
$ heyc greet.hey --test
FAIL: greets by name
expected stdout: Hello, Ada!

actual stdout:   Hello, Ada

$ echo $?
1

Fix the return line to "Hello, #{name}!" and run it again:

$ heyc greet.hey --test
PASS: greets by name

The exit code is 0 on pass and 1 on fail, so heyc file.hey --test drops straight into CI. Every file in the Hey examples folder carries its own spec.

7. Check without running

Works today

heyc FILE --check parses the file and resolves every name, then stops. It's the fast "did I break anything" button. Here's a file that calls a function nobody defined, oops.hey:

program
  says greet('Ada')
end
$ heyc oops.hey --check
heyc: unknown function: greet [source=oops.hey]
$ heyc hello.hey --check        # no output, exit status 0: all good

When you want to know what a library function takes and returns, ask hey doc:

$ hey doc Web.serve

8. The REPL

Works today

hey repl is for trying things. It uses the same parser and name rules as compiled programs; definitions persist for the session, and multi-line blocks continue until they're complete.

$ hey repl
Hey now. Hey REPL v... Type help or quit.
hey> let x = 40 + 2
hey> says x
42
hey> fn greet(name)
...>   return 'Hello, ' + name
...> end
defined fn greet/1
hey> says greet('Ada')
Hello, Ada

The REPL evaluates what you type instead of compiling it to native code, so don't time anything in it. Imports work there just as in a file, for example import 'stdlib:Text' exposing: [trim].

9. Your first actor

When some state has to live and change over time (a counter, a connection, a game room), Hey gives it an owner: an actor. An actor is a small independent worker with a private mailbox. Other code can't touch its state; it can only send it messages, and the actor handles them one at a time.

spec 'tour actors own state'
  expect stdout "visits=1\nvisits=2\n"
end

actor Counter(label)
  state count = 0
  receive message

  if message == 'increment'
    set count = count + 1
    says label + '=' + count
  elsif message == 'stop'
    exit
  end
end

program
  let counter = spawn Counter('visits')
  send counter, 'increment'
  send counter, 'increment'
  send counter, 'stop'
  join counter
end
$ hey tour_03_actors.hey
visits=1
visits=2
$ heyc tour_03_actors.hey --test
PASS: tour actors own state

Read it top to bottom:

  • state count = 0 is the actor's private memory. set count = ... replaces it for the next message. Nothing outside the actor can change it.
  • receive message names the message being handled; the code after it runs once per message.
  • spawn starts the actor, send drops a message in its mailbox and returns at once, exit ends the actor, join waits for it to finish.

Actors run on a pool of threads across your CPU cores, and a failure inside one stops that actor, not your program. All of that is in actors and failure.
