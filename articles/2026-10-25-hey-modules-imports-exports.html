Modules, imports and exports

A module decides what it offers. An import decides what a file uses, and how it may be spelled. Both choices are made at compile time, in plain sight, and only for the one file that wrote them.

In one paragraphYou write exposes name forms: [...] at the end of a module to publish a function. Write import './file.hey' to use it as Module.name(...), or add exposing: [name] to call it bare, or forms: [:dotted] to call it as value.name(...). A dotted call is just a function call with the value moved to the front; there are no classes and no method lookup at run time.

Three words used throughout. A receiver is the value before the dot in value.f(…). A file's lexical scope is the set of names that file can use, decided by what it declares and imports. A facade is a module that exists only to re-offer a chosen set of names from other modules.

1. A module publishes; an import activates

This module is used by most examples below. module Name … end groups functions; module names are CamelCase. Works today Notice BankAccount.valid_amount?: today a function names its own module to call a sibling.

bank_account.hey
module BankAccount
  fn open(owner, balance)
    return {owner: owner, balance: balance}
  end

  fn deposit(account, amount)
    if !BankAccount.valid_amount?(amount)
      fail 'negative deposit'
    end
    return {...account, balance: account.balance + amount}
  end

  fn withdraw(account, amount)
    return {...account, balance: account.balance - amount}
  end

  fn balance(account)
    return account.balance
  end

  private fn valid_amount?(amount)
    return amount >= 0
  end
end

Inside a module, a sibling is called by its bare name, and it answers before any built-in of the same name.5 Decided, coming

sibling_call.hey
module Prices
  fn with_tax(amount)
    return amount + tax(amount)
  end

  fn tax(amount)
    return amount / 10
  end
end

program
  says Prices.with_tax(100)
end
$ hey sibling_call.hey
110

Reopening a module across files Decided, coming

Like Ruby, a Hey module can be opened in more than one file. Every file that says module Shapes adds its functions to the same module:

shapes_area.hey
module Shapes
  fn area(w, h)
    return w * h
  end
end
shapes_perimeter.hey
module Shapes
  fn perimeter(w, h)
    return 2 * (w + h)
  end
end
main.hey
import './shapes_area.hey'
import './shapes_perimeter.hey'

program
  says Shapes.area(3, 4)        # 12
  says Shapes.perimeter(3, 4)   # 14
end

The rules:

  • Members combine. The module is every function from every file that opens it. The order the files are imported in doesn't matter.
  • One name, one definition. Defining the same function twice in one module is a compile error that names both files. Ruby only warns about this (with -w); Hey checks the whole program before it runs, so it can always tell you.
  • private covers the whole module. A private function in one file can be called from the module's other files, and from nowhere else.
  • Built-in namespaces are different. Reopening a built-in module such as Path is allowed but gives a warning, because it hides the built-in.
No runtime cost. Ruby reopens a module while the program runs, so it has to update its method tables and throw away cached lookups. Hey resolves every name before the program runs, so a function compiles to the same native code whichever file it's written in. The build cache keeps each file's part separately, so editing one file rebuilds only the code that uses what changed.

Sub-modules: Outer/Inner

The other way to split a big module is into named sections. module Shapes/Area is a sub-module of Shapes, and its members are called with the slash in the name: Shapes/Area.rect(3, 4). That's the one spelling: a / b with spaces is still division, and the dotted chain Shapes.Area.rect is refused with a message suggesting Shapes/Area.rect.6 Decided, coming

shapes_sub.hey
module Shapes/Area
  fn rect(w, h)
    return w * h
  end
end

program
  says Shapes/Area.rect(3, 4)
end
$ hey shapes_sub.hey
12

2. exposes and its forms

The exposes lines at the end of a module are its whole public surface; anything not listed stays inside. Each line names the forms a caller may use: :qualified (BankAccount.deposit(a, 1)), :unqualified (deposit(a, 1) after exposing:) and :dotted (a.deposit(1)). A facade module may write exposes *. Decided, coming Until a build accepts the line, a module with no exposes offers every function.

bank_exposes.hey
module BankAccount
  fn open(owner, balance)
    return {owner: owner, balance: balance}
  end

  exposes open forms: [:qualified, :unqualified]
end

program
  says BankAccount.open('Ada', 100).owner
end
$ hey bank_exposes.hey
Ada

3. Every import form

You writeThe file gets
import 'stdlib:Text'a standard library module, qualified: Text.upper(s)
import './x.hey', import '../x.hey'a file relative to this one, qualified
import 'pkg:name@1.0.0/main'a locked, hash-checked package module (Packages guide)

The lists after exposing:, forms: and conceals: are written in the source, so the compiler knows every name before the program runs. There's no runtime import: a value computed while the program runs can never create a name. There's no Module.load either.7 Works today

4. Receiver calls are static

x.f(a) is f(x, a), chosen by the compiler from this file's imports. x.name with no parentheses reads a field. The dotted_import.hey run above shows a two-segment chain. Works today

A field holding a function ({run: shout}) is called with only the arguments you wrote. When a dotted call could mean either a callable field or an imported receiver function, the nearest and latest binding wins, and the compiler warns, naming both places.8 To be explicit: value['name'](arg) for the field, Module.name(value, arg) for the function. Decided, coming

field_vs_receiver.hey
fn shout(amount)
  return 'field called with ' + amount.to_s
end

program
  let account = {owner: 'Ada', run: shout}
  says account.run(25)
end
$ hey field_vs_receiver.hey
field called with 25

5. Collection method sugar

names.uniq() isn't a method on arrays. It's uniq(names), made available as a dotted form by importing it that way. Each file chooses its own vocabulary; Hey never patches a global method table. A few small helpers such as .to_json and .len work with a dot without an import (shown here and in The language). Works today

collection_sugar.hey
import 'stdlib:Collections' exposing: [uniq, includes?, take] forms: [:dotted]

program
  let names = ['Ada', 'Ada', 'Lin', 'Grace']
  says names.uniq().to_json
  says names.includes?('Lin')
  says names.uniq().take(2).to_json
end
$ hey collection_sugar.hey
["Ada","Lin","Grace"]
true
["Ada","Lin"]

Standard library modules are different on purpose: every built-in lives in a namespace, and a qualified name such as Text.upper is always reachable without an import. An import is how a file asks for the bare or dotted forms.

  says Text.upper('no import line above')
end

7. Operator imports

A module may offer a function as the meaning of an overridable operator: exposes power_mod … infix: '**'. A file that imports it gets that meaning for **, in that file only. The parse never changes: 2 + 3 ** 2 still groups as 2 + (3 ** 2), because precedence belongs to the parser's table and imports can't touch it. Every arithmetic, comparison, boolean, bitwise and range operator is overridable; =, the set updates, await, spawn and the postfix forms are not. Decided, coming

mathx.hey
module MathX
  fn power_mod(base, exponent)
    return Math.pow(base, exponent) % 1000
  end

  exposes power_mod forms: [:qualified, :unqualified, :infix] infix: '**'
end
operator_import.hey
import './mathx.hey' exposing: [power_mod]

program
  # 2 + (3 ** 2), with ** meaning power_mod: 11
  says 2 + 3 ** 2
end
$ hey operator_import.hey
11

8. Facade modules instead of selector manifests

Want one import line that brings in a curated set? Write a facade: an ordinary module that imports what it wants and re-offers it with exposes *, so re-export is always explicit. Decided, coming

prelude.hey
module Prelude
  import 'stdlib:Text' exposing: [upper, trim]

  exposes *
end
facade_use.hey
import './prelude.hey' exposing: [upper, trim]

program
  says upper(trim('  ada  '))
end
$ hey facade_use.hey
ADA

9. pkg: imports

import 'pkg:name@version/module' loads a module from a package that hey package ensure has fetched, locked and hash-checked into the project. Adding and locking packages is in the Packages guide, where it's shown working. Works today In a folder with no locked package, the import fails:

pkg_import.hey
import 'pkg:hey_cli@0.1.0/main'

program
  says 'imported'
end
$ hey pkg_import.hey
hey error: could not open read file
exit status 70

stdlib: always means the toolchain's own standard library; there's no search path, so a project file called stdlib/Text.hey can't pass itself off as it.9 Decided, coming

A native package (one with C code inside) is imported like any other package, with pkg:; how it reaches C is in Native code and C. A separate native: scheme is Proposed, not ruled.

10. Built-ins live in namespaces

Every built-in function has a namespace (Path.basename, Json.encode, Text.upper), and the qualified name is what's reserved, so your own bare basename never collides with it. A small core set (print, len, Int and the like) is visible without a prefix. Strings use the method form, s.upper(). A warning appears only where the syntax tree shows your name changes which function a call reaches.10 Decided, coming The full list is in The standard library.

11. Seven additions from a look at other languages Decided, coming

Hey's module design was checked against what Python, JavaScript and TypeScript, Node, Rust, Swift, Go, Gleam, Zig, Elixir and others have changed recently.4 The verdict: keep the design (imports belong to one file, each file picks its receiver forms, re-export is always explicit through a facade, conflicts follow one lexical rule with warnings, packages are locked and hashed), and add the seven rules below. They are decided; the examples show what they do.

C1. A module body holds declarations, imports and constants only Decided, coming

Nothing runs just because a module was imported. A constant whose value is a literal is worked out at compile time. Any other constant is computed once, the first time something reads it, safely across threads; if computing it fails, the first reader fails fast. A call written at the top of a module is a compile error, and so is a constant that needs itself. Python and JavaScript are adding "lazy import" features to cope with slow, side-effecting module bodies; Hey never has the problem.

prices.hey
module Prices
  let TAX_RATE = 0.08                 # a literal: worked out at compile time
  let RATES = Text.split('a,b,c', ',') # computed once, on first use

  print_banner()                      # compile error: no calls at the top of a module

  fn with_tax(amount)
    return amount + amount * TAX_RATE
  end
end

C2. Functions may import each other in a cycle Decided, coming

The compiler resolves the whole program at once, so two files may import each other, as items in one Rust crate can. The only cycle that is an error is between constants (C1), because one of them would have to be computed first.

even.hey and odd.hey
# even.hey
import './odd.hey'
module Even
  fn even(n)
    if n == 0
      return true
    end
    return Odd.odd(n - 1)
  end
end

# odd.hey
import './even.hey'
module Odd
  fn odd(n)
    if n == 0
      return false
    end
    return Even.even(n - 1)
  end
end

C3. within: :package: public to your package, not to the world Decided, coming

Today a name is either private to its module or public to everyone. Swift added package access, Rust has pub(crate) and Go has internal/ directories for the same reason: a helper your other modules need shouldn't become part of your public API. Hey adds one clause to the exposes line. The package manifest also gets an exposes list naming the modules outsiders may import with pkg:; importing any other module of the package from outside is refused with a message naming the manifest. The facts come from the syntax tree and the manifest, never from directory names.

csv.hey
module Csv
  fn parse_row(line)
    return Text.split(line, ',')
  end

  exposes parse_row forms: [:qualified] within: :package
end

C4. ::Shapes starts from the root Decided, coming

With nested modules, the nearest name wins. That can hide the module you meant, with no way left to name it; Swift recently added module selectors for this. Hey borrows Ruby's answer for constants: a leading :: starts the path at the root. The nearest-path warning suggests it as the fix.

root_path.hey
module Report
  module Shapes                  # a nearer Shapes hides the top-level one
    fn area(w, h)
      return 0
    end
  end

  fn total()
    return ::Shapes.area(3, 4)   # the top-level Shapes, whatever is nearer
  end
end

C5. Explicit names beat exposing: *, and an ambiguous star import is an error Decided, coming

With a star import, a dependency that adds a new name could silently change what a bare call in your file means, decided by which import line comes later. So, following Rust's rule for glob imports: a local definition or a name listed in exposing: always beats a star import, whatever the order. If two star imports both supply a name your file actually uses, that is a compile error asking you to pick one by name. A clash on a name you never use stays silent. This narrows the general "later binding wins, with a warning" rule for star imports only.

stars.hey
import './bank.hey' exposing: *      # exposes open, balance
import './files.hey' exposing: *     # exposes open, read
import './bank.hey' exposing: [balance]

program
  says balance(acct)   # fine: named in exposing:, beats any star
  says open('Ada')     # compile error: both star imports supply open; name the one you mean
end

C6. Unused-import warnings, and hey fix rename Decided, coming

Because importing a module never runs anything (C1), an import or an exposing: entry that nothing uses is always safe to delete, and the compiler warns about it. A rename tool works from resolved identities: it rewrites only the call sites that resolve to that function, never other things that happen to share its spelling. A module can keep the old name working for a while with a deprecation message.

rename
$ hey fix rename Files.read Files.read_text

module Files
  exposes read_text forms: [:qualified]
  exposes read as read_text deprecated: 'use read_text'
end

C7. Publishing a package requires exposes Decided, coming

A module with no exposes line is entirely public. That's convenient for scripts and apps, which stay unchanged. But a published package's surface should be deliberate, so hey package publish refuses any module the manifest exposes that has no exposes line. (The JSR registry for JavaScript is strict about published APIs in the same way.)

publish
$ hey package publish
refused: module Csv is exposed by the manifest but has no exposes line

Looked at and turned down

  • Lazy imports (Python's lazy import, JavaScript's import defer). They delay running a module that is already loaded; Hey links one program with no module loading at run time, and C1's lazy constants give the only useful part.
  • Runtime loader hooks and import maps. A hook that changes what an import means while the program runs would break resolving every name before it runs.
  • Separate type or interface files (like TypeScript's .d.ts). Hey has no type annotations in user code; the build cache can fingerprint each module's surface instead.
