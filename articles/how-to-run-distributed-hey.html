Distributed Hey · practical guide

Imagine if adding a machine felt like adding another worker.

Your web process accepts a burst of work. Hey actors spread that work across cores, containers, and other machines. One machine disappears; the rest keep going. A replacement joins. Your application still mostly talks in actors, immutable values, and jobs.

What the dream should feel like

Application code should stay boring.

import 'stdlib:Jobs'

fn resize(job)
  return Images.resize(job.image, job.width)
end

program
  let workers = Jobs.cluster('image-workers')
  let results = Jobs.map(workers, uploads, resize)
  save(results)
end

The runtime should do the distributed work.

node-acoordinator · 12 actors

node-c28 jobs running

That exact Jobs API is the destination, not today's API.

The transport underneath it is real today. The remaining work is making distribution feel native to Hey actors and Jobs rather than making application code manually manage peers and connections.

Quick start · one machine

See a real remote call in about a minute

Build the local compiler once

./bin/subcmds/hey-build --native

Start two Hey processes and make a remote call

examples/distributed/run_demo.sh \
  examples/distributed/01_ping_pong.hey \
  9101 tcp

Look for the proof

[A] A handshake ok with peer=B ...
[A] A got reply=pong echo.ping=hello from A from=node-B
[B] B handshake ok with peer=A app=pingpong

What just happened?

The script launched node B in the background and node A in the foreground. A created a RemotePid, sent a request through Remote.call, and B returned an immutable structured reply.

The tcp argument is deliberately the easiest development mode: no certificate setup, same transport protocol above the stream layer.

Same machine · secure path

Now run the same demo over TLS

You do not need to manufacture certificates just to see it work. The repository already contains test-only TLS material.

copy / paste from the repository root
export HEY_DIST_CERT="$PWD/test/fixtures/tls/server-cert.pem"
export HEY_DIST_KEY="$PWD/test/fixtures/tls/server-key.pem"
export HEY_DIST_CA="$PWD/test/fixtures/tls/ca-cert.pem"
export HEY_DIST_SNI=localhost

examples/distributed/run_demo.sh \
  examples/distributed/01_ping_pong.hey \
  9102 tls

Those certificates are for the demo.

They make the article reproducible. Do not copy the repository's private fixture key into a real service. Production deployment should issue a server certificate for the service name you actually use.

Optional · Docker

Two nodes, one laptop, isolated Linux containers

The simplest article path is two processes. If you want a closer simulation of two machines, build the existing Linux dev image and put two containers on one Docker network.

build + network
docker build \
  -f docker/linux/alpine/Dockerfile \
  --target dev \
  -t hey-dev:local .

docker network create hey-dist

Terminal 1 — node B

docker run --rm --name hey-b \
  --network hey-dist \
  -e HEY_DIST_BIND=0.0.0.0 \
  hey-dev:local sh -lc '
    HEY_ROOT=/opt/hey \
    HEY_STDLIB_PATH=/opt/hey/stdlib \
    heyc /opt/hey/examples/distributed/01_ping_pong.hey \
      --run -- server 9101 tcp
  '

Terminal 2 — node A

docker run --rm --name hey-a \
  --network hey-dist \
  -e HEY_DIST_PEER=hey-b \
  hey-dev:local sh -lc '
    HEY_ROOT=/opt/hey \
    HEY_STDLIB_PATH=/opt/hey/stdlib \
    heyc /opt/hey/examples/distributed/01_ping_pong.hey \
      --run -- client 9101 tcp
  '

Two real machines

Move node B to another computer

Assume node B is reachable at 192.168.1.20. Both machines have the same Hey checkout and have run ./bin/subcmds/hey-build --native.

Machine B — server

export HEY_DIST_BIND=192.168.1.20
export HEY_DIST_ACCEPT_MS=15000
export HEY_DIST_CERT="$PWD/test/fixtures/tls/server-cert.pem"
export HEY_DIST_KEY="$PWD/test/fixtures/tls/server-key.pem"

./build/heyc \
  examples/distributed/01_ping_pong.hey \
  --run -- server 9101 tls

Machine A — client

export HEY_DIST_PEER=192.168.1.20
export HEY_DIST_CA="$PWD/test/fixtures/tls/ca-cert.pem"
export HEY_DIST_SNI=localhost

./build/heyc \
  examples/distributed/01_ping_pong.hey \
  --run -- client 9101 tls

Why connect to an IP but verify “localhost”?

The repository's fixture certificate is issued for localhost. The socket connects to B's LAN IP, while TLS verifies the certificate name supplied through HEY_DIST_SNI. That trick is convenient for a test fixture; a real deployment should issue a certificate for its real DNS/service name.

What still feels manual?

Today's friction, and the feature that removes each piece

This is the section the old article blurred. The left side is what feels awkward today. The right side is the specific product work that makes it disappear.

today

You create peers and connections yourself.

Application code knows hostnames, ports, handshakes, and DistTransport.

fix

Node service + connection-owning actors. A supervised node runtime owns listeners, peer connections, reconnects, and backoff.

today

You explicitly construct remote actor addresses.

You use Remote.pid(node, name) and keep track of where the actor lives.

fix

Registry + discovery. Ask for 'resize-worker'; get a local or remote actor reference.

today

Jobs do not automatically spread across nodes.

The transport can move messages, but the Jobs layer does not yet schedule work onto a distributed worker pool.

fix

DistributedJobs. Put ordinary immutable jobs on local or remote workers with the same failure policy.

today

The compiler path is not complete for every Dist*/Codec call shape.

The demos still use --run while the one-true compiler closes the remaining boxed/callable cross-unit cases.

fix

P2 compiler closure. Default build must compile the distributed examples through Hey → HIR → MIR → HeyLlvm → LLVM with zero fallback.

today

Cluster membership is manual.

A node can talk to a known peer; the runtime does not yet maintain a live view of “the cluster.”

fix

Seeds → discovery → membership. Start simple with configured seeds/DNS; add gossip only if the system actually needs it.

today

You cannot see the whole cluster at a glance.

Transport counters exist, but cluster-wide health, actors, queues, jobs, latency, and restarts are not yet a coherent product surface.

fix

Cluster observation. A first-class dashboard/API over node health, actors, mailboxes, jobs, traffic, backpressure, monitors, and supervision.

Truth in advertising

The next thing to fix is not another networking feature

The distributed examples still use the interpreter today.

That is not the desired end state. The compiler can compile itself through the Hey-owned LLVM path with zero fallback, but the broader language corpus still contains cross-unit boxed-result and callable-value shapes that the emitter does not lower everywhere. Those same shapes are what keep the Dist*/Codec examples on --run.

The correct next milestone is compiler completeness: the distributed examples should build as ordinary native programs with the default compiler path, with no fallback, before more distribution polish gets priority.

Why this is worth finishing

Hey starts from unusually good distributed assumptions

Immutable values

Messages already cross an ownership boundary. A machine boundary is conceptually another copy/serialization boundary, not a shared-memory illusion.

Actors

Concurrency is already message-oriented. Distribution extends that model instead of replacing it with RPC-shaped application architecture.

Native programs

No mandatory distributed VM is required. Each node can remain a normal compiled process with a small networking/runtime layer beside the actor system.

The goal is not to prove that two computers can exchange pong. That part works. The goal is to make adding a computer feel like giving the same Hey program more places where actors and jobs can run—and to make the cluster observable enough that you trust it when something goes wrong.
