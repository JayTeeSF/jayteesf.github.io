What the emitter is, and what it is not

The compiler pipeline is Hey → HIR → MIR → {native-C emitter, Hey emitter}. Two back ends consume the same MIR. HeyLlvm.hey is one of them: it lowers MIR to textual LLVM IR. The native-C emitter (heyc.c) is the reference oracle, and every arm added to the Hey emitter is compared byte-for-byte against what native emits for the same MIR.

So when a rung “teaches the emitter Collections.reverse,” the whole of that knowledge is a lowering rule:

MIR:   Collections.reverse(prefixes.prefixes)
emit:  %t = call ptr @hey_llvm_collections_reverse_value(ptr %field)

The function hey_llvm_collections_reverse_value is implemented in the C runtime; the emitter only carries its declare. No list-reversal logic moves into HeyLlvm.hey. The same is true for reduce, enumerate, filter, take, drop, and every map-value, call-argument, and comparison shape closed this week.

Direct answer to “will the core need to be rewritten if HeyLlvm.hey changes?” No. Semantics live in the parser, HIR, MIR, and the runtime — not in the emitter. Changing the emitter changes code generation for one back end. The parser, the type/inference passes, and the runtime are untouched, and the native oracle keeps the Hey emitter honest by construction.

The special-case worry is correct — and it has a named fix

The instinct that if starts_with 'Collections.enumerate(', one arm per facade, is special-case accumulation is right. It couples the emitter to each facade by name. Two facts hold at once:

Why it is this shape nowDeliberate and temporary.
Mirror disciplineThe Hey emitter is proven equal to native heyc.c per operation. Native dispatches per operation, so the mirror must too, or the byte-identity check cannot see the two agree.
The oracle is the only guardUntil a semantic/property gate replaces it, the native differential is the one thing keeping the emitter from silently diverging. It cannot be removed mid-campaign.
The clean-up, deferred on purposeA later milestone, tracked so it is not lost.
Uniform lowering tableReplace the N bespoke facade arms with one signature/metadata-driven facade-to-runtime dispatch. One place to add a facade, not a hand-written arm.
Sequenced after retirementLand the gate on the mirror, retire heyc.c, then refactor. Refactoring the mirror and proving it still matches native cannot be done simultaneously.

This is why the campaign does not refactor now. Doing both at once forfeits the differential oracle at exactly the moment it is doing its job.

The clean-up started: a segment-scanner became a recursive fold

Rung 56 — a heterogeneous string concatenation like "form " + kind(node) + " " + span_text(span(node)), mixing string literals, a module call, and a nested user call — did not yield to another special-case arm, and that was the signal. The existing boxed_concat_value lowered concatenation by scanning the source text for top-level + while tracking only quotes, not ()/[]/{} depth. Any operand carrying its own delimiters — a call, a nested call — was misclassified. The project's own research corpus had already named this class of defect: eight named plus five anonymous scanners, only one of which implements precedence.

The fix is the structure every mature compiler uses and the structure the reference C emitter already used: an AST-recursive left-fold. Split at the last top-level + with a depth-aware scan, recurse both sides, fold with add_value, and release each fresh operand immediately after the fold that consumes it — one uniform freshness predicate, not eight hand-set flags. Nesting depth comes for free from the recursion; the + inside f(a + b) is a child of a different node and can never be mistaken for a sibling. The result is byte-identical to native across every operand kind and leaves all 91 LLVM and 24 HIR/MIR goldens green.

This is the deferred refactor, arriving early and in the small. The uniform lowering-table clean-up this note describes is exactly “replace scattered hand-written scanners and arms with one structural rule.” The concat fold is that move applied to one operator, under the discipline that keeps it honest: it was landed only because it stayed byte-identical to the native oracle and passed the golden suites and a negative control (an object literal {a: x + y} and a call f(a + b) must not fold at the top level). The refactor is no longer only a plan; its first step is proven.

Method note: this one was solved with help. A read-only research agent mapped the corpus and how CPython, Ruby, V8, Rust, and Go lower a heterogeneous a + b + c — establishing that a recursive fold beats a segment-scan for nested operands and that intermediates are freed after each fold, not at statement end. A second agent, carrying the campaign’s full context, instrumented the failing loop, confirmed the exact arm that bailed, implemented the fold, and gated it. The recommendation and the implementation met in the middle, and the byte-identity oracle refereed the result.

Method notes carried forward

  • One flag, not a dangling else. To gate a large existing conditional chain, a boolean flag with if !handled is safe; wrapping the chain in an else can re-bind a trailing else deep in the chain to the outer if and run both branches. Rung 26 cost hours to this before the flag form fixed it.
  • Cache discipline. The pipeline sidecar is hash-keyed and self-invalidates on a valid source edit. When an edit appears not to take effect, the first check is whether the source parses; a syntactically broken intermediate makes the runner fall back to the last good cached emitter. Use hey cache clear or hey cache gc rather than deleting build directories by hand.
  • Shared-path changes are golden-gated. Any change to a value classifier, comparison path, or array-element path is followed by the full 91 LLVM and 24 HIR/MIR golden runs before the next rung.
