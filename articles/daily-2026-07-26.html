Daily: The Day Hey Beat Go — and Found the Leak

One overnight session, five releases, and a matched-comparison win over Go on two operating systems — plus the honest, unglamorous second half: a memory leak that's fixed in one place and still sitting, found but not fixed, in another.

TL;DR

  • Verdict: ship it, but say the whole truth. Hey is faster than Go on the matched throughput comparison, certified on macOS and Linux the same day. Five releases landed and deployed overnight. A nasty memory-retention bug was root-caused and fixed in the language's own loop compilation — but a second copy of that same bug, living in the code that builds web responses, is found and precisely isolated, not yet fixed. Both halves of that sentence matter; neither gets left out.
  • The headline number: Hey cleared its within-3%-of-Go goal and then beat it — certified faster on both platforms measured, the same day, not just "close."
  • The disclosed weakness: the web server's own copy of the retention bug was measured still present after the loop-level fix shipped, in different code than the part that's fixed. It's not vague — it's named, located, and queued.
  • Infrastructure honesty: the project caught and fixed its own test/verification tooling lying to it four separate times tonight, on top of the five feature releases.
  • Falsifiability: the throughput claim's receipts are in "Faster Than Go? Certified on Linux and Darwin"; the release list and every number below are drawn from this session's own dated records, cited inline.

1. The headline: Hey beat Go, certified on both machines

The short version: Hey's long-standing goal was to get its web throughput within 3% of Go's, measured per CPU core under matched conditions. That goal wasn't just met tonight — it was beaten, and beaten on two separate operating systems the same day: certified faster on both the Linux box and the macOS box that host this project's benchmarking. See "Faster Than Go? Certified on Linux and Darwin" for the full measurement writeup and its own disclosed caveats; this report isn't re-deriving that number, just recording that it landed the same day as everything below.

Term: G1

G1 is the project's standing "fast" goal: within 3% of Go's throughput, per core, under matched conditions — a ratio the team re-checks every time Go's own number moves, not a number it can just claim once and walk away from. Full entry →

2. Five releases, back to back

Five versions landed and deployed in this session, 439a through 443a, each going through the project's full chain of gates before merging:

  • 439a — a memory-safety tripwire suite: a new guard that watches value handling across nine operation families, designed to fail loudly the moment a future change breaks an invariant it's protecting.
  • 440a — two compiler-coverage batches landed together, closing dozens of "the old and new compiler don't yet agree on this shape" gaps toward the R-ladder.
  • 441a — a syntax-checker fix: a self-hosting smoke test that had been structurally unable to pass on any base was repaired and folded permanently into the chain.
  • 442a — web-server crash and truncation fixes: a server-killing signal-handling bug and a related short-read/short-write edge case, both now pinned by regression tests.
  • 443a — the loop-release fix: the root-cause repair for half of tonight's big story, below.

Every one of the five went through byte-identity verification and goldens before it was allowed to land.

3. The detective story: chasing K8

Term: K8, the retention bug

K8 is this project's name for a memory-retention bug: compiled Hey code was creating values inside loops and never freeing them, so a running server's memory grew, request after request, until something gave out. Full entry →

Servers running compiled Hey code were leaking roughly 1.4 KB per request on their busiest route — small enough per request to be easy to miss, large enough that a sustained-traffic server would eventually exhaust its memory and shut itself down. That's the kind of bug that's brutal to chase precisely because nothing crashes right away; the evidence is a slope, not a stack trace.

Two independent investigations converged on it from different directions, which is exactly why the diagnosis holds up. One session isolated the mechanism class by running the same loop through Hey's interpreter and through its compiled path side by side: the interpreter released memory correctly and the compiled version didn't, which pointed straight at loop compilation itself rather than at anything the loop's contents were doing. The other session found the exact site the hard way, with an OS-level heap census and a backtrace, the kind of forensic pass that only works because "trust the runtime's own counters" had already been ruled out earlier tonight as its own kind of mistake. Both paths landed on the same bug.

4. The honest status: half fixed, half found

Status, plainly stated

The language-loop half of K8 is fixed, and fixture-verified, in release 443a. The web server's own copy of the same class of bug is not fixed — it lives in different code (the helpers that construct response values, not the loop-compilation path 443a repaired), and a pre-registered, five-part gate battery measured it still present after 443a shipped — on both platforms, isolated down to a single response-building call with everything else stripped away. Its fix is already in flight. That is the whole status; neither half is optional to report.

It would be easy to read "the leak is fixed" off the headline alone and stop there. It would be wrong. The loop-release fix in 443a closes the mechanism that was leaking inside ordinary Hey code — a real, verified fix, not a partial one, for the piece it covers. But the server's response-construction path has its own independent copy of the same class of defect, and that copy was still there, measured, after the fix landed. Calling the whole bug dead tonight would be the kind of overclaim this project's own house rules exist to catch.

5. Infrastructure honesty: the project audited itself

Alongside the five feature releases, the project caught and fixed its own test and verification tooling misbehaving four separate times tonight:

  • A Mac-only test that had never actually run on macOS at all — it silently crashed before producing a result, and nobody had noticed.
  • A benchmark timer that was charging time it shouldn't have been counting, skewing a threshold it was supposed to measure cleanly.
  • A release-checklist step that had been silently skipped for roughly 58 versions — the tool responsible for keeping it current had a gap that let the step drift unnoticed release after release.
  • A test assertion that was counting the wrong thing, so it could report success without actually checking what it claimed to check.

On top of fixing all four, the project consolidated its release-verification steps into one canonical verification script that now travels with the code itself, rather than living as separately-remembered steps a person has to recall in the right order. A project that finds and fixes its own test infrastructure lying to it, in public, four times in one night, is doing exactly what its own gate discipline is supposed to produce.

6. Two articles, through the full pipeline

Two articles were carried through the project's research → fact-check → publish pipeline tonight. The fact-check step wasn't a formality: it caught a draft that had put quotation marks around words nobody had actually said, attributing a paraphrase as if it were a direct quote. The process caught it before publication, not after — which is the entire point of running a fact-check step instead of trusting a draft on the strength of how confident it reads.

7. What's next, and what got rejected

Next up:

  • The mux event-core prototype is landing, but opt-in and off by default until more of it is proven under sustained load.
  • Remaining compiler-coverage gaps in the R-ladder continue closing batch by batch.
  • The next stage of the refcount program (I5) is queued — the project's biggest remaining lever on its throughput goal.

Term: the mux

The mux is an event-loop-style redesign of the web server's connection handling: a small pool of threads services many open connections, instead of giving each connection its own thread. Measured on both operating systems it wins at the same load using 6 threads instead of 70, with no memory penalty. Full entry →

Explicitly rejected tonight, and why:

  • Mid-message actor pausing — letting an actor suspend partway through handling a message. Run-to-completion message handling stays the design; nothing gets to interrupt a handler mid-body.
  • Startup snapshots — pre-baking a warm startup image. Rejected because startup was measured essentially free on both platforms already, which leaves the sub-5 ms CLI target reachable without that complexity.
  • io_uring and other per-platform server designs — a single event-loop mechanism is the target shape everywhere, not a different mechanism hand-picked per operating system.
  • Deleting the old C compiler yet — the R-ladder isn't finished; the old compiler stays until its replacement has earned that step rung by rung.
  • Trusting any single measurement instrument — the K8 investigation above is itself the argument: it took two independent instruments, not agreement with itself, to trust the diagnosis.
