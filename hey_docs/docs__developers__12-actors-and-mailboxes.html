Actors and mailboxes#

Actors own identity and private mutable state. Each actor processes one mailbox message at a time, so application code does not coordinate shared mutable objects or locks.

Define state and handle messages#

actor Counter(reply_to)
  state count = 0

  receive message
    set count += message.amount
    send reply_to, count
  end
end

Actor parameters are immutable inputs. state persists between mailbox turns. set may update only state owned by the active actor, monitor, or supervisor.

Spawn, send, join, and stop#

actor Printer
  receive value
    says value
  end
end

program
  let printer = spawn Printer
  send printer, 'hello'
  join printer
end

Messages own the values transported through the mailbox. No raw pointer, borrowed compiler value, or shared mutable application object crosses the boundary.

Multiple messages#

actor Accumulator(reply_to)
  state total = 0

  forever
    receive message
    if message.kind == 'add'
      set total += message.value
    else
      if message.kind == 'read'
        send reply_to, total
      else
        if message.kind == 'stop'
          exit
        end
      end
    end
  end
end

Mailbox order is FIFO for messages delivered to one actor. Cross-actor completion order is intentionally not a global ordering guarantee.

Immutable helpers#

Keep pure calculations in ordinary functions and use actor state only for identity-bearing coordination:

fn next_balance(balance, amount)
  return balance + amount
end

actor Account(reply_to)
  state balance = 0

  receive amount
    set balance = next_balance(balance, amount)
    send reply_to, balance
  end
end

The same helper can be called by ordinary code, actors, workers, and Jobs.

Supervision and failure#

Links, monitors, and supervisors make failure relationships explicit. A supervisor owns restart policy; it does not expose another actor's state. Runtime errors remain bounded to the actor turn and its configured supervision relationship.

When to use an actor#

Use an actor when the concept needs persistent identity or serialized mutable state. Use a function for pure transformation, a worker for replicated stateless work, and Jobs when callers need receipts, retries, cancellation, durability, or metrics.
