Hey language · design note · 22 August 2026

No type annotations in your code, every type in the compiler

Hey source stops writing type annotations and starts casting — x.to_i, x.to_s, x.to_f — and the compiler reads the exact same type off the cast. The type-bearing casts stay in the code; only the notation — the written -> type arrow — leaves it. Nothing about the type system got weaker. The boolean cast !! is the decided spelling for this too, but it is not built on trunk yet.

Status
This note describes a decided design direction, not a feature fully in the shipping toolchain. The three conversion casts (.to_i, .to_s, .to_f) are built; the boolean cast !! is decided but NOT built on trunk — grep heyc.c for "!!" returns 0. Where the two sources differ (the language reference presents !! as settled contract; the construct census records it unbuilt), this page discloses the gap rather than papering over it.

TL;DR

  • Hey is fully typed, and user source writes no -> type annotation. There is no -> bool or -> i64 in user code — a cast conveys the type, the compiler reads the exact same type off it, and it still recognizes and enforces every type. The notation moved; the type system did not weaken.
  • Three built casts, three result types: x.to_i is Int, x.to_s is Str, x.to_f is Float. The fourth cast is the boolean one, !!x → Bool; its build status is the disclosed weakness below.
  • The compiler reads the type off the cast, and the compiler's intermediate representation (IR) carries it. fn g(x) return x.to_i end infers -> Int with no annotation; the IR goldens still print -> i64.
  • The old ?-name→bool rule is superseded. A function's boolean-ness is meant to come from a cast in its body, not from a ? on its name.
  • Disclosed weakness: the boolean cast !! is decided direction, not built on trunk — grep heyc.c for "!!" returns 0, so a reader who types !!x today gets nothing. The sources record it as decided-but-not-built; they give no !!-specific scheduling note, only the general rule that language features wait behind compiler completion.
  • Reproduce it: compile fn g(x) return x.to_i end and inspect the specs/ir/*.hir golden — it prints -> i64, the type you never wrote.

The one idea

Hey has a full, enforced type system. What this note changes is only how a type is indicated in the source a person writes: instead of a written annotation, a value is cast, and the compiler reads the exact same type off the cast. [13-language-reference §Casts convey type]

Read the language reference plainly:

Hey is fully typed and the compiler fully recognizes and enforces every type. What changes is only how a type is indicated in user-facing source: instead of a written -> type annotation (no -> bool/-> i64 in user code), a value is cast, and the compiler reads the exact same type off the cast. This is a notation change, never a weakening of the type system — the type is every bit as real as if it had been written out.

Reader takeaway: after this section you can state the whole thesis in one line — the annotation left the source, not the type from the compiler.

A cast is the annotation

A cast does two jobs at once. It converts the value, and by converting it, it tells the compiler the result's type. There is nothing else to declare. Four casts, one for each of the result types Int, Str, Float and Bool — three built on trunk today, and the fourth, the boolean cast, decided but not yet built. [13-language-reference, cast table; language-full-shape §3 casts table]

That third column carries two facts worth holding onto. First, on representation: with x.to_i the compiler, not the programmer, decides whether the value lives as a raw i64 or a boxed integer — representation choices stay inside the compiler and out of user-facing code, which is the whole point of moving the notation. Second, on lane coverage: only .to_f is verified present in every compilation lane, while .to_i and .to_s/.to_string are cited in the native lane on trunk. Reader takeaway: you can now read a Hey function's return type off its final cast — no arrow to hunt for — and know the compiler read it the same way.

Inference, worked

Because the cast carries the type, a function's return type falls out of its body with nothing written down. Here is the case that actually compiles on trunk today:

fn g(x) return x.to_i end     # infers -> Int, no annotation — BUILT

x.to_i makes g return Int, inferred exactly as if the type had been written, because the cast is where the type was written. The language reference pairs this with a boolean example — fn f(x) return !!x end is meant to infer -> Bool the same way:

fn f(x) return !!x end       # decided: infers -> Bool — the not-yet-built case

So the demonstrator to reach for is g. It shows the whole mechanism working end to end; f shows where the mechanism is heading once the boolean cast is wired. [13-language-reference §Casts convey type; language-full-shape §3 casts table]

Reader takeaway: you can predict a function's inferred return type by reading its body's final cast — and you can tell which examples run today (g) from which document the destination (f).

The source drops the annotation; the IR keeps the type

The key thing to hold onto: dropping the annotation from source does not drop the type from the compiler. The type is fully real, so the compiler's own intermediate representation still carries it. The goldens in specs/ir/*.hir — the high-level IR (HIR) and mid-level IR (MIR) stages — print -> bool, -> i64, -> str, -> boxed, and so on. That is the rule working, not a violation of it — the type was read off the code, never written by hand. [13-language-reference §Casts convey type]

Note that the IR carries more inferred types than the four casts produce: a nil/object return prints -> boxed, which no cast spells. That is the inference reading the code, not a cast the programmer wrote.

One consequence for anyone who works on the compiler: when inference sharpens, the IR goldens legitimately shift. A result that once printed -> i64 may now print -> bool; a nil/object return may now print -> boxed. That is the type being read more precisely — regenerate the goldens to match. Do not mistake the sharper type for unrelated drift, and never strip -> type out of the IR: user source omits the annotation, but the compiler still knows the type. [13-language-reference §Casts convey type]

What this supersedes: the ?-name→bool rule

Hey used to infer boolean-ness from a function's name: a trailing ? made the return type bool. In the native emitter that rule is a single line — if (len>0 && name[len-1]=='?') return "bool";, at runtime/heyc.c:5797 on trunk. [language-full-shape §3, Operators]

The cast model supersedes that name-based inference. Boolean-ness is meant to come from the cast in the body — !!x — not from a punctuation mark on the name. The design canon records the old rule as an oddity that the decided cast model (!!/.to_i/.to_s/.to_f) makes a latent defect to remove, not a feature to keep. Note the timing tension: the replacement it points to, !!, is not built yet — so the old line is superseded in the design, and still the only boolean-return inference actually running on trunk. [language-full-shape §3 + §Divergences]

Why this is not a weakening

It would be easy to misread "no annotations in source" as "looser typing." It is the opposite kind of change. The type system's job — recognize and enforce every type — is unchanged; the enforcement still happens, and the IR still carries the type end to end. All that moved is the notation: from a written arrow to a cast the programmer was already reaching for. [13-language-reference §Casts convey type]

This also keeps a standing tension out of user code. Hey's doctrine is that user code does not use type annotations, yet the parser still accepts a handful of parameter type annotations (i64 f64 bool str boxed nil) — in direct tension with that doctrine. The decided direction moves types to casts, not to -> type, resolving the tension in favor of the doctrine. [language-full-shape §5, parameter type annotation]

Why is the boolean cast still unbuilt while its design is settled? The sources give no !!-specific scheduling note — but they do give a general reason. The maintainer's rulings set an explicit doctrine that language work is deferred behind compiler completion (R1, R2, R4), and the strictness-levels ruling (D48-a) applies exactly that pattern to a new compiler capability. So !! falls under a sourced reason-class — language features wait for the compiler — even though no note names !! itself. Read the specific timing as undocumented, not as unexplained. [language-full-shape §3 casts table (decided, not built); maintainer-rulings R1/R2/R4 + D48-a — language work deferred behind compiler completion]
