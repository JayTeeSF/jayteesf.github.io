The Billion-Row Bet

We're betting that a language built on immutable values — Hey, where every value is copy-on-handoff and nothing gets mutated out from under you — can run one of the world's most famous speed contests fast. And we're publishing the target before we have the result.

Status: bet placed, baseline measured — nothing built or shipped yet

The fast 1brc.hey program this article bets on does not exist yet. What's real, dated 2026-07-27: the 15 GB, one-billion-row file, timed on this machine, and a first, honest reading of how far there is to go.

1. The bet

TL;DR

  • We're betting that Hey can run the One Billion Row Challenge (1BRC) fast, and we're publishing the target before we have the result. If the immutable way wins, a mutable type that snuck into the language by accident gets deleted.
  • Shoot for the sun, honestly: the dream is 1–2 seconds. Landing anywhere near 10 would still win the argument this bet exists to settle — that immutable-by-design can be fast.
  • Disclosed weakness, stated first: measured today, the honest starting line is months, not seconds — a lower-bound projection, and worse than it first looked. Two named causes, both already scheduled for removal (§4).
  • Falsifiable, on purpose: every number below is dated and traces back to the project log; the two pending rows in the chart are pending, not filled in with a guess.

Here's the wager, plainly. We aim to process one billion temperature readings — a 15 GB text file — in seconds, on the same machine, and the same language, that just beat Go's web-serving throughput, certified with 95% confidence. Same box, same design principle, a completely different kind of race: not requests per second, but rows per second, one billion of them, start to finish.

We're stating the target honestly, sun-shot and all. The dream is 1–2 seconds — in the neighborhood of the actual world record. That's a stretch goal, not a promise. Landing anywhere near 10 seconds would still win the argument this bet exists to settle: that a language which refuses to let you mutate a value out from under someone else can still run one of the fastest-known workloads in the world. There's a real stake attached, not just bragging rights: byte_buffer — the one mutable value type that slipped into an otherwise all-immutable language, by accident, during an earlier attempt at this exact benchmark — gets deleted from Hey if the immutable way wins.

2. What is 1BRC?

Term: the One Billion Row Challenge

The One Billion Row Challenge (1BRC, Gunnar Morling, January 2024) asks for exactly one thing: read one billion station;temperature text rows and print the minimum, mean, and maximum temperature per station, as fast as possible. The winning entries all leaned on the same handful of tricks — reading the file straight into memory instead of calling read(), scanning several bytes at a time instead of one, and skipping text allocation until the very last step.

3. Why we think we can make it

Three plain reasons, and none of them require inventing new speed.

We measured where the time actually goes, and the real work is already fast. Isolate just the scanning-and-comparing logic — the part of the program that actually reads a row and does 1BRC's real work — and it costs about 7 nanoseconds (ns, billionths of a second) per row on this machine. That's world-class pace, in the same neighborhood as the fastest published entries anywhere. Right now, that 7 ns is buried under memory bookkeeping worth roughly a thousand times that — allocating and copying memory the algorithm never actually needed. We don't need to invent speed. We need to stop paying for overhead that isn't earning its keep.

Most of the machine we need already exists. A fast 1BRC pipeline needs a handful of pieces — mapping the file into memory without copying it, scanning it without copying it, parsing numbers without allocating, and fanning the work out across workers who all share one view of the same data. Five of those six pieces already exist in Hey today, as immutable, zero-copy code. Only two gaps remain: a real sort where a slow hand-rolled one sits today, paired with a truly zero-copy row path (one fix), and a way to accumulate results without copying the whole running tally on every single row (a second, harder fix). Both are already scheduled — nothing here is speculative machinery we'd have to design from scratch.

We've done exactly this before, twice, in different directions. On speed: this project's own web server went from ~500 to over 120,000 requests per second by this exact method — measure the real cost, name it, delete it — documented start to finish in "From 500 to 100,000 Requests per Second." On ergonomics: an idiomatic, no-tricks Hey port of a real Ruby command-line tool now matches the speed of the hand-tuned version it retired, and a separate Ruby port's own memory story — a 481× reduction, bugs and all, printed in public — is the same discipline applied to a harder problem than a benchmark. And the meta-receipt: this team publishes its bets before the results and its corrections in public. This article is doing that right now.

Glossary

1BRC
The One Billion Row Challenge: read a billion station;temperature text rows and print the min/mean/max per station, as fast as possible.
byte_buffer
Hey's one mutable value type — an append-many-times output builder that writes to its own memory in place. Deleted if this bet's immutable approach wins.
zero-copy
Reading or sharing data by pointing at it, instead of duplicating it first.
The planned reference-counting upgrade
Values share until written, copy only when needed, instead of always copying. See the shared glossary. The in-place-aggregation fix in §3 is a small, scoped preview of this larger program.
