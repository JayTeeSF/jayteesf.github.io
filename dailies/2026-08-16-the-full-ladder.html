Four Walls, One Name

Everyone quoted the same ceiling: a Hey program stops working past about a thousand functions. That number was never one defect. It was four different walls wearing one name — and this week took down three of them.

TL;DR

  • The "1,145-function limit" was four separate problems sharing one symptom, and three are now fixed, at version 514a. A crash on wrapped programs, an entire class of depth crash, and a compile time that grew with the cube of the program are gone. The fourth — a thirty-second parse deadline at about 2,850 functions — still stands. All of this is landed: committed and through the battery. Nothing is deployed; this checkout has no remote.
  • The depth crashes were retired as a class, not patched one at a time. The interpreter now eliminates a function that calls itself as its last act — the thing the compiled route always did — so a program can no longer work built and crash run. A twenty-line reproduction that segfaulted at 450 functions now finishes, and so does one at 2,000, where even a release build used to die.
  • A compile time that grew with the cube of the program is now roughly linear. Lowering the middle representation re-scanned the whole accumulated output on every block end. At 500 functions that was 147 seconds; it is now 4.55 — a 32x cut — and the output is byte-for-byte identical, verified by diffing all of it.
  • The disclosed weakness: the fourth wall is a time limit, and I did not make parsing faster. I made the failure honest. The error used to name none of what a reader needed; it now names the knob and its default. Raising the compiler's own goals — actually parsing 2,850 functions inside the budget — is separate work that has not started.
  • The falsifiability test: switch the interpreter's tail-call elimination off and the same reproduction segfaults again at 450, 1,000 and 2,000. Switch a box-ownership isolation hook on and the race detector reports on five runs out of five; off, it is clean. Each fix carries a lever that brings the fault back on demand.
  • Six corrections below, at the same volume as the claims. The largest is not a bug: every depth number this project has ever published is a debug-build number, and that is worth a factor of three to four.

The number that was never a number

For weeks the shorthand was "Hey stops at about a thousand functions." It travelled as one fact and it hid four. Reading a bug report as a single defect is how the wrong one gets fixed, so the first real work was to pull them apart and measure each on its own.

The depth crashes: retired, not patched

The most satisfying of the three is the one where the temptation was to keep patching. A Hey program that recurses deeply would crash — but only when run directly, never when built. The compiled route turns a function whose last act is to call itself into a plain jump, so it uses no extra stack. The interpreter did not, so it piled up a stack frame per call and eventually fell over. The compiler's own front end runs interpreted, which is why the ceiling showed up as a limit on how large a program the compiler could chew on.

An earlier attempt had converted two of the offending loops by hand and moved the ceiling from 424 to about 440 — and then the next hand-written loop in the same family took over immediately. There were around thirty of them. Patching sites one at a time was measured not to work, and that measurement is why the fix went a level down instead: teach the interpreter to eliminate self tail calls, exactly as the compiler already does, and the whole class goes away at once. The roughly thirty rewrites are now optional cleanups, not defects.

The gate that watches this leans on correctness, not on the crash going away, because a wrong tail-call rule gives a wrong answer rather than a fall. It checks that return f(n) + 1 keeps its arithmetic, that a self-call with the wrong number of arguments still reaches its error, and that parameters are rebound each round. Both stored reference sets passed with nothing regenerated.

What is still open in the same class. Two functions that call each other get no such treatment — the compiled route is self-only too — and that overflows at a depth of 500. Measured, not implied. It is a smaller wall behind the one that just fell.

The cubic that hid in a helper

The third wall was pure time. Lowering the middle representation re-split the entire accumulated output on every block end and walked it with a loop that copied the whole list each pass, only to recompute how deeply nested it was. That is a cube: three nested passes over a growing thing. The depth is now carried along as an ordinary counter.

The give-away that it was cubic is in the doubling ratios: each time the program doubled, the old code took about four times as long — 3.86, then 4.20, climbing past four. The new code takes about 2.1 to 2.3 times as long, which is the shape of ordinary linear-ish work. The output is identical byte for byte on a corpus of nested modules, branches, loops and workers, checked by diffing the full thing, because a carried counter cannot quietly correct itself the way the re-scan could. One line in that fix is load-bearing: a clamp that stops a stray block-end from driving the counter negative. Drop it and later functions get silently swallowed into the previous one — a wrong answer, not a crash.

The wall still standing, and what I actually did to it

The fourth wall is the one a user hits first, and it is honest about being a clock. Build a program with more than about 2,850 top-level functions on default settings and the parse step gives up after thirty seconds. It is not a crash and not a stack limit; parsing that much source simply takes longer than the budget the compiler allows its own helper.

I did not make parsing faster. That is real work with its own evidence, and it has not started. What I fixed today is that the failure named none of what a reader needs. It used to read only stdlib delegation failed: HeyParser.parse_file (response deadline expired) — no mention of the file, the thirty-second default, or the setting that changes it. It now reads:

stdlib delegation failed: HeyParser.parse_file
  (response deadline expired after 200 ms;
   raise HEY_STDLIB_SIDECAR_TIMEOUT_MS, default 30000)

Naming the knob is cheap, separable, and immediately useful: a reader who hits the wall can raise the limit and finish the build while the deeper fix waits its turn. I proved the message by tripping the deadline deliberately — a short timeout on a few hundred functions reproduces the exact failure without waiting for the full-size program — and confirmed that on the normal thirty-second budget the same program sails past the parse step. The message only appears on a genuine deadline.

Underneath: the ownership ladder

The walls were the visible half of the week. The quieter half is a planned sequence for removing a fragile idea from the compiler: today, when a program hands a freshly wrapped value across a function boundary, the compiler tries to prove at build time that the value does not escape before it frees it. That proof has been written three times and shipped broken twice. The plan replaces it with a count on the wrapper, so the proof becomes unnecessary rather than more careful. Each rung lands with a lever that recreates the fault it fixes.

Corrections to my own work

Six, each with the mechanism rather than the corrected number. The first is not a bug and matters most, because it silently rescales almost every performance claim in this project.

1. Every depth number in this project is a debug-build number

The build the compiler produces for itself, and every gate that measures it, is compiled without optimisation. Releases are fully optimised. The difference is worth a factor of three to four in how deep a program can go before it runs out of stack: measured, a case that crashes at 450 unoptimised survives to about 2,000 optimised. Every depth figure quoted in this tree, including some on this very page, is the unoptimised one unless it says otherwise.

The mechanism: a measurement quoted without its build flavour is not a measurement. I once reported an unoptimised ceiling as the language's limit and had to withdraw it. The rule now: state the flavour or the number does not count.

2. A verification command that does not exist

The handoff a restarting session reads first named a binary-interface check four times, twice inside blocks headed "Verified." The command answers unknown option and always has. Those were receipts for something that never happened; the reason nobody noticed is that reading a pipeline's exit status reports the last stage, so the check appeared to pass when only a downstream head did. The receipts are struck and the header no longer cites it. (This correction stands from last week and was re-confirmed today.)

The mechanism: a plausible "ok" copied forward is indistinguishable from a real one. Re-run it, or delete the step.

3. Inherited leak figures that would not reproduce

The ownership design memo carried two per-call retention figures inherited from an earlier host. Re-measured here on one harness, they did not reproduce — one of them turned out to be a nested call's increment mistaken for a shape's slope. They are withdrawn rather than restated, and the rung's real before-and-after was measured fresh.

The mechanism: a number from another machine is a hypothesis, not a measurement. Re-derive it here or drop it.

4. A gate that could not see the wall it was supposed to watch

A scaling check counts clone calls over a compiled-in module. The wall is in an interpreted step it never touches. Greening that row would not move the wall and the wall falling would not green the row; an honest benchmark for the actual step is owed. Worse, one attempt to compare the ordinary build through an environment switch was vacuous — the ordinary build uses a compiled-in copy of the code under test, so the switch never reached it, and the arm was quietly testing the wrong binary.

The mechanism: census the thing the gate names, not the thing nearby. A gate pointed at the wrong translation unit reports health it cannot see.

5. A third unwatched check, red at head

A parallel-streams check has sat failing with a generated-code error and no ledger row watching it, so nothing noticed. Confirmed pre-existing by stashing this week's work and re-running: same failure. It is now registered as a known-red row, which is the honest state — a tracked defect rather than a surprise. Two golden checkers that were also unwatched were given rows the same way.

The mechanism: a check with no ledger row runs blind. The fix is not to green it in a hurry but to make it visible first.

6. "No output" is not "not fixed"

A crash discards whatever a program had buffered to print but not yet flushed. Reading an empty result as evidence that a fix had failed cost a revert of a correct patch earlier in the campaign. It is recorded here so the next reader does not pay it twice.

The mechanism: absence of output under a crash is absence of a flush, not absence of a fix. Confirm the exit signal before concluding.

What this page owes you

The hit is three of four walls down, and the best of the three retired a whole class rather than a single instance — because patching instances was measured not to work first. The miss belongs beside it: the wall a user actually hits is still standing, and all I did to it today was make it tell the truth about itself. Making it fast is next, and it has no shortcut. The honest read of the week is that the compiler got much harder to knock over and not yet much faster to feed.

Decisions needed from you

  1. What comes next — make the parse step fast enough that the fourth wall stops being reachable, or push the ownership ladder to its central hook so the per-request leak can close. I would take the parse step, because it is the one a real program hits on default settings, and the knob only postpones it.

Glossary

Reference for the shorthand used above. Terms marked new were coined or first used here since the previous daily.

Lane, or route
One of the ways a Hey program becomes a running program: the newer Hey-written code generator, the older C one, and the interpreter, which runs a program directly without building it.
Tail call new
A function call that is the very last thing a function does before returning. When a function's last act is to call itself, the machine does not need to keep the current frame around — it can reuse it, turning what looks like deep recursion into a plain loop.
Tail-call elimination new
The optimisation that spots a tail call and reuses the stack frame instead of adding a new one. The compiled route always did this; teaching the interpreter to do it is what retired the depth-crash class.
Stack, stack frame
The scratch space a program uses for the chain of functions currently calling one another. Each active call takes a frame; too many at once — deep recursion without tail-call elimination — exhausts the space and the program is killed.
Debug build versus release build new
The unoptimised build the compiler makes for itself and its tests, versus the optimised build shipped to users. They differ by roughly three to four times in how deep a program can recurse, which is why a depth number is meaningless without saying which build produced it.
Middle representation, lowering new
A halfway form a program passes through on its way from source to machine code. "Lowering" is the step that produces the next, more concrete form from it — the step whose cubic re-scan was the third wall.
Cubic, linear new
How work grows with size. Linear means double the program, double the time. Cubic means double the program, roughly eight times the time — the doubling ratio climbs past four, which is the fingerprint that was spotted here.
Parse, parse deadline new
Parsing is reading source text into a structure the compiler can work with. The deadline is a thirty-second limit the compiler puts on a helper doing that step; a large enough program exceeds it and the build fails. The limit is adjustable.
Knob new
A setting that changes behaviour without changing code — here, an environment variable that raises the parse deadline. "Naming the knob" means the error message now tells the reader the setting exists and its default.
Escape proof new
The compiler trying to prove, while building, that a freshly made value will not be needed elsewhere before it frees it. Proving this correctly is hard; it shipped broken twice. The ownership ladder replaces the proof with a count.
Reference count new
A small tally on a value of how many places currently hold it. When the tally reaches zero, the value can be freed. It makes the escape proof unnecessary: you free when nobody is holding, rather than proving in advance that nobody will.
Wrapper, or box new
A small container that lets code handle any kind of value uniformly. It has to be allocated and freed like anything else, which is where the ownership work lives. The reference count sits on the wrapper.
Falsification hook, or lever new
A switch built into a repaired program that restores the original fault on demand. It turns "the crash is gone" from an observation into a test: if flipping the switch does not bring the fault back, the fix was not what fixed it.
Gate, ledger, ratchet
A gate is an automated check with a recorded expected result; a known-failing check is a tracked defect, not a surprise. The ledger is the file listing every check and its expected result — a check with no ledger row runs unwatched. A ratchet records a debt count and permits it to fall, never to rise.
Golden, reference output
A stored copy of what a tool produced on an earlier day, kept so today's output can be compared against it character by character. There are 90 here, one per test program.
Byte-identical
Two routes producing exactly the same output, byte for byte — used here as a standard of proof that a speed fix changed nothing about what the program means.
Sidecar new
A helper process the compiler talks to for certain steps, including the parse step behind the fourth wall. The thirty-second deadline is how long the compiler waits for it to answer.
Mutual recursion new
Two functions that call each other in a cycle. The tail-call fix handles a function calling itself, not this case, so mutual recursion still overflows at a depth of 500 — the wall behind the wall.
Landed / Verified / Deployed
Verified: on a branch, with reproduced evidence. Landed: committed and through the check battery. Deployed: on the mainline and felt by users. Everything on this page is landed; nothing is deployed, because this checkout has no configured remote.
