Why Hey’s == Isn’t Constant-Time, and Why It’s Staying That Way

A password check written with == says “no” a little sooner when the first character is wrong than when only the last one is. That gap is what a timing attack measures. Hey’s designer asked why Hey’s == works that way, whether the compiler could just make it constant-time, and why anyone would want it not to be. These are the answers, with the numbers we measured, and the decision he made.

Status: decided; the check is built, the secret kind isn’t yet

== stays as it is. A secret value kind whose == is constant-time has been requested from the Hey team and doesn’t exist yet. A source check, hey_secret_lint, which flags == on values that look secret, was built the same day: run over eight apps, it found three real secret comparisons, and all three were fixed. Every timing below comes from one Apple M3 Pro laptop, and Linux wasn’t measured.

TL;DR

  • Why == isn’t constant-time: it stops at the first difference. On strings and bytes that’s O(k+1), where k is the length of the shared prefix: at 64 KiB, a first-byte mismatch costs 6 ns and a last-byte mismatch costs 1.33 µs. Arrays and JSON are different: Hey turns both sides into text first, so they’re linear in the size of both sides every time.
  • Could the compiler route == to the constant-time compare? Yes. Equality is one function in the runtime plus one inline path in the compiler. But every string comparison in every program would pay: a 64 KiB first-byte mismatch would go from 6 ns to about 20 µs on this machine. And it still wouldn’t make the program safe, because length, lookups by secret, and the code around the comparison all still leak.
  • Why keep a == that isn’t constant-time: most comparisons aren’t about secrets. A search through a list of n strings makes up to n−1 comparisons that come out unequal for every one that matches, and stopping early is what makes those cheap. Every language we checked keeps a fast default, and most ship a separate constant-time function. Three libraries go further and give one type a constant-time ==: Java’s SecretKeySpec, swift-crypto’s Digest and Haskell’s ScrubbedBytes. That’s the precedent for Hey’s secret kind.
  • Two corrections to the quick first answer. The question first got a fast reply from an AI assistant, before any of this was measured. It said constant_time_equal? is “O(n) always”, and it treated the slowdown as the cost of being constant-time. In fact Crypto.constant_time_equal? only compares bytes, answers false for two equal strings, and returns in about 19 ns whenever the lengths differ. And most of its 15× slowdown comes from Apple’s timingsafe_bcmp, which runs at byte-loop speed (about 3.2 GB/s); a word-at-a-time constant-time loop measured 2.8× a plain memcmp.

The problem: a check that answers faster the further off you are

Say a server checks an HTTP Basic credential. The obvious line is the first one below. It compares the strings left to right and returns at the first byte that doesn’t match. If an attacker can time the “no”, a slower “no” means more of their guess was right. 

# a sketch of the shape behind CVE-2015-7576, not code from My Queue
# before: how long "no" takes depends on how much of the guess was right
fn authorized?(supplied, expected)
  return supplied == ('Basic ' + expected)
end

# after: how long "no" takes depends only on the lengths
fn authorized?(supplied, expected)
  return Crypto.constant_time_equal?(bytes(supplied), bytes('Basic ' + expected))
end

The bytes(...) calls matter: leave them out and the function returns false even when the credential is right (see “It silently says false for two equal strings” below).

“Constant-time” is a slightly misleading name. A constant-time compare still takes longer for longer inputs. What it promises is that, for two inputs of the same length, the time doesn’t depend on what’s in them: equal, wrong at the first byte and wrong at the last byte all cost the same. The Perl advisory below states the risk plainly: a client who can time the replies “may recover a valid signature one byte at a time rather than searching the whole signature space.”

Question B: == stops at the first difference, so its time depends on the data

All of Hey’s equality goes through one C function, hey_value_equal_raw in runtime/hey_runtime.c. Its own comment calls it “the ONE equality rule list -- all lanes route through it”. It switches on the kind of value:

KindWhat == doesTime
Integers, numbers, booleans, nilone machine comparisonO(1)
Stringstrcmp, with no length check firstO(k+1), k = length of the shared prefix. Strings of different lengths that share a prefix still scan it.
Bytescompare lengths, then memcmpO(1) if the lengths differ, otherwise O(k+1)
Array or JSON objectserialise both sides to text, then strcmplinear in the size of both sides, every time, plus two allocations. No fast best case.

The quick first answer said == is “O(1) best / O(n) worst / O(k) for a k-byte common prefix.” That’s right for strings and bytes, with one wrinkle: for strings the best case is “the first byte differs,” and different lengths don’t help. Comparing a string of 65,535 as with one of 65,536 took 1.33 µs, the same as a full-length match. For arrays and JSON it’s wrong: they always pay for serialising both sides.

There’s a second path. When the compiler knows both operands are plain strings (say, parameters cast as String), the LLVM back end doesn’t call the runtime at all. It writes call i32 @strcmp(...) straight into the generated code, so any change to == has to cover that path too.

Across a row, the early exit shows: string == at 64 KiB costs 6 ns when byte 0 differs and 1.33 µs when the last byte does. Read down the constant_time_equal? rows and the contents stop mattering, but three other things show up.

Three things about Crypto.constant_time_equal?

It silently says false for two equal strings

The function returns false unless both arguments are bytes. We checked: called on two equal strings, it printed false. Python’s hmac.compare_digest raises a TypeError on types it doesn’t support and PHP’s hash_equals raises a type error; Hey gives a wrong answer without complaint. My Queue, the app where this question came up, already wraps both sides in bytes(...) in its credential check (server/auth.hey:425) for this reason.

It answers in about 19 ns when the lengths differ, so it leaks length

The “one byte shorter” row is flat at about 19 ns whatever the size. The function checks lengths first and returns at once. Go, .NET, PHP and Rack document the same behaviour. Go’s docs say the time “is a function of the length of the slices and is independent of the contents,” and when someone filed a bug about it, Go closed it with “It is literally impossible to make such a function constant time across all possible lengths.” Ruby’s OpenSSL.secure_compare is the exception we found: it hashes both sides with SHA-256 and compares the hashes, which are always 32 bytes, before it also checks the raw strings with ==.

The slowdown is Apple’s function, mostly

At 64 KiB, constant_time_equal? costs about 20 µs against 1.3 µs for an equal ==, roughly 15×. On Apple systems Hey hands the work to libSystem’s timingsafe_bcmp; elsewhere it uses OpenSSL’s CRYPTO_memcmp. A small C program (cc -O2, one call per iteration behind a compiler barrier) measured the pieces directly:

Called from C, timingsafe_bcmp takes 20.6 µs at 64 KiB; called from Hey, 20.4 µs. That’s about 3.2 GB/s, against about 50 GB/s for memcmp. So Hey adds nothing at that size, and the 15× is the speed of Apple’s function, which behaves like a byte-at-a-time loop. (We didn’t read Apple’s source; OpenBSD’s reference timingsafe_bcmp is a byte loop.) A portable loop that XORs eight bytes at a time and ORs the results ran equal and first-byte-mismatch inputs within 1% of each other, at 2.8× a full-length memcmp. At 64 B the story is different: constant_time_equal? costs 38–41 ns against 6–8 ns for ==, and about 15 ns of that is call overhead: wrapping each value for the runtime call (boxing) and copying it. The length-mismatch path compares nothing and still costs 19 ns.

How much does a sub-nanosecond leak matter? Hard to exploit, and fixed anyway

On this machine, one byte of strcmp or memcmp is worth well under a nanosecond: at 64 KiB, the 1.33 µs gap between “wrong at byte 0” and “wrong at the last byte” works out to about 0.02 ns per byte. The published floors for measuring time over a network are much coarser:

  • Crosby, Wallach and Riedi (2009): an attacker can measure “with 15-100µs accuracy across the Internet, and as good as 100ns over a local network.”
  • Brumley and Boneh (2003) extracted private keys “from an OpenSSL-based web server running on a machine in the local network.”
  • Van Goethem and colleagues (2020) used concurrent requests over HTTP/2 to “accurately detect timing differences as small as 100ns, similar to attacks launched on a local system.”

Our reading, and it’s an inference rather than a result: guessing a short token byte by byte through Hey’s == is hard, but nobody has shown it’s impossible. Attackers average many samples, and those floors aren’t hard limits. Big inputs leak more (1.33 µs at 64 KiB is well above 100 ns), though a 64 KiB secret is rare.

Question C: the compiler could route == to the constant-time compare, and here’s the bill

Mechanically, it’s a small change. Because hey_value_equal_raw is the one rule list, swapping the string and bytes arms to the constant-time compare covers almost every == in both of Hey’s back ends. The one bypass is the typed-string path that writes strcmp straight into the LLVM code; that would have to become a call too.

Every string comparison in every program pays

With Apple’s function, from the table above: a 64 KiB first-byte mismatch goes from 6 ns to about 20 µs, an equal 64 KiB compare goes from 1.3 µs to about 20 µs, and a 64 B compare goes from about 7 ns to about 39 ns. With the faster word-wise loop, the C measurement puts the 64 KiB cases near 3.6 µs instead. So “too slow” is partly an implementation question; a faster constant-time compare would shrink the bill. It wouldn’t make it go away, because the bill lands on map keys, de-duplication, index_of and every if that branches on a string. In those places we expect most comparisons to come out unequal: a search through n strings makes up to n−1 unequal comparisons for each match, and stopping at the first difference is what makes those cheap.

The compiler can quietly undo constant-time code it can see

While benchmarking the typed-string path we watched LLVM inline a small function, see that its strcmp had the same arguments on every loop iteration, and hoist it out of the loop. It called strcmp once and reported 0 ns per comparison. That’s legal: LLVM treats strcmp, memcmp and bcmp as known library functions and reasons about what they return. Neither timingsafe_bcmp nor CRYPTO_memcmp is on its list.

That matters because the obvious way to make the typed path constant-time would be to emit an XOR/OR loop directly in the generated code, and that’s the shape researchers have watched compilers turn back into an early exit. Simon, Chisnall and Anderson found Clang introducing a jump into supposedly constant-time selection code at -O2/-O3, and warn that “a compiler upgrade can suddenly and without warning open a timing channel in previously secure code.” Schneider and colleagues, looking at 44,604 targets, found compiler-introduced secret-dependent operations “within some of the most highly regarded hardened cryptographic libraries.” The libraries defend themselves: volatile in CPython and OpenSSL, a read_volatile “black box” in Rust’s subtle, and in .NET a NoInlining | NoOptimization attribute, with the comment “NoInlining because the NoOptimization would get lost if the method got inlined.”

So “the compiler could re-optimise it” is true with a condition. It’s a risk for a loop written in the generated code, or for runtime C that a whole-program build inlines. It isn’t a risk for today’s constant_time_equal?, which is an opaque call into a system library that the generated code can’t see inside. That’s the shape Go, .NET and Node use too.

And the program still wouldn’t be safe

Node’s documentation says it about its own function: using crypto.timingSafeEqual “does not guarantee that the surrounding code is timing-safe.” A constant-time == leaves all of these as they are:

  • the length of the secret, which every standard constant-time compare leaks;
  • looking a secret up rather than comparing it: WHERE token = ? in SQL, or a map lookup keyed by a token, which hashes and probes;
  • an early return on a length mismatch in the caller;
  • starts_with, < and cmp, which in Hey also use strcmp;
  • logging the value, or serialising it to JSON;
  • arrays and JSON objects, where position didn’t show in our timings but size does.

The OAuthLib advisory above is about both the length check and the first mismatch.

Question D: most comparisons aren’t about secrets, and stopping early makes them cheap

Because almost none of a program’s comparisons involve a secret, and for those the early exit is free speed. Checking whether a string is already in a list, whether two map keys match, or which branch of a command to run: we expect most of these to come out “different,” and the early exit makes that answer cheap. A constant-time == would make each of them read to the end.

The real case for the other side is the author who forgets. In four of the five CVEs above, an author used ordinary == or eq without thinking about timing at that line; the Rails and Rack authors knew they were handling credentials. A constant-time == would have protected them without their knowing. The cost is that it would also slow down everyone who wasn’t comparing a secret, and it would still leave the length and the surrounding code exposed.

We looked for a general-purpose language whose default == on strings is constant-time and didn’t find one. Absence isn’t proof; a language we didn’t check could do it. The last column shows the other route: Java, swift-crypto and Haskell’s memory package each mark one kind of value as secret and give that a constant-time ==, so code that compares two keys with ordinary == gets the safe compare without asking for it. Rust’s secrecy takes the stricter route and refuses == on a secret altogether. And the research language FaCT (PLDI 2019) builds the whole idea into a type system, compiling code on secret values into constant-time LLVM code.

The decision: keep ==, give secrets their own kind, and check the source

That’s the shape Hey’s designer chose. There are three parts, and only the first is true today.

  1. == stays as it is. Ordinary code keeps the early exit, and nothing on a hot path gets slower.
  2. A secret value kind whose == is constant-time, requested from the Hey team. Hey doesn’t show types in user code, which fits poorly with a type-level marker like Rust’s traits, but it does have value kinds, and hey_value_equal_raw already switches on kind. A secret arm there would call the constant-time compare and cost nothing for every other kind. Something like this, though the name and API aren’t settled: 
    # illustrative only: the secret kind doesn't exist yet
let key = Crypto.secret(bytes(row.key_hash))
if key == bytes(kh)          # constant-time, because one side is secret
    Our research brief (kept in a private repository) also suggests that printing, logging and JSON should redact or refuse a secret, and that < on one should be an error. Those are design questions for the Hey team, not decisions.
  3. hey_secret_lint, built: a source check that flags == and != where an operand’s name looks secret (token, secret, password, hash, signature, authorization and the like) or is a 'Basic …' / 'Bearer …' credential, and flags Crypto.constant_time_equal? called without bytes(...), since that always answers false. It reads names, not types, so a secret in a variable called value slips past it. Run over eight apps, it found three real comparisons: My Queue’s OAuth state value and its stored recovery-code hash, and a development enrollment secret in the VSS server. We rated the state one low risk, since an attacker would have to time the victim’s own request, but all three now go through the constant-time compare.

The two new pieces cover each other’s gaps. The secret kind protects an author who forgets the special function, but only for values someone remembered to mark. The lint looks for the values nobody marked, but it’s a heuristic, so it will miss some and flag some that don’t matter. Neither hides length unless the secret is padded or hashed first, and neither helps when a secret is looked up rather than compared.

Why this is sound, as opposed to just cautious: the constant-time cost lands only where a secret is compared, which is where it’s worth paying. It matches what every language we checked does with ==, and what three libraries do with secret types. It keeps the constant-time compare as an opaque call, which is the shape the compiler can’t undo. And it doesn’t pretend that a faster or slower == can make the code around it safe.

What we still don’t know

  • Whether the leak is exploitable remotely. Our per-byte difference is well under a nanosecond, and the best published remote floor is about 100 ns. Nobody has shown an attack at our scale, and nobody has shown one can’t work.
  • Linux. There Hey uses OpenSSL’s CRYPTO_memcmp, which has assembly versions for x86-64 and ARM64. We didn’t measure it, so the 15× may be Apple-only.
  • What constant_time_equal? should do with strings. The brief recommends comparing their UTF-8 bytes, and failing loudly on other kinds instead of returning false. That isn’t part of the decision above, and it’s still open.
  • The length policy. Leak it, as Go, .NET and PHP do, or hash both sides first, as Ruby’s secure_compare does.
  • What a secret kind allows. Can you take its length, concatenate it, hex it, print it? And can the typed-string strcmp path be proven never to receive one?
  • A guard against regressions. A constant-time test harness run as a gate, so a future toolchain change can’t quietly bring back an early exit. Nothing like it exists for Hey yet.
