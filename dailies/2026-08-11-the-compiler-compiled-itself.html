The Compiler Compiled Itself. Three Bugs Showed Up Anyway.

Hey's compiler can now build itself using only Hey-written code generation, with no automatic fallback to the older C path. That is a real milestone. It is also the day three separate defects surfaced that the existing checks had been passing straight over.

TL;DR

  • Hey's compiler now builds itself with zero automatic fallback. The build receipt reads selfhost_consumer=hey-llvm-text and selfhost_legacy_fallback_count=0. That check had been failing since August 7.
  • Both check suites pass on that commit. 107 quick checks and 8 slow checks, no unexpected failures and nothing waiting to be promoted: 115 checks selected, 90 green, 24 known-failing, 0 unexpected.
  • The lesson is about which checks earn their keep. A suite of 106 passing checks ran green over a live miscompile I had just written. The test that caught it was the one that deliberately fed the compiler something it should refuse.
  • This is not "one compiler in charge." An ordinary 104-line date program still needs the old path. Hey's script runner never finishes a common loop shape that the compiled version gets right. And two of the broadest correctness comparisons in the project fail on a clean tree while belonging to no suite.
  • Check it yourself. tools/restructure_gate_ratchet.sh --tier fast and --tier heavy reproduce the suite numbers; test/fixtures/compiler/llvm_bool_call_while_interp.hey reproduces the loop that never ends.

What "the compiler compiled itself" actually means

Hey's compiler is written in Hey. To turn a program into a binary it has to generate machine code, and until today it could not generate all of the machine code for its own source. Whenever it hit a shape it did not know how to translate, the build quietly handed that whole program to an older code generator written in C.

That fallback is why the current goal exists at all. When two different pieces of code can both answer "what does this program mean?", they can disagree, and a disagreement that nobody notices is a wrong answer that ships. Every one of the three most serious wrong answers this project has recorded came from the fallback answering, not from the new generator.

As of today the compiler's own source needs no fallback:

selfhost_frontend=hey
selfhost_consumer=hey-llvm-text
selfhost_legacy_fallback_count=0
selfhost_legacy_fallback_forced=false

Both check suites then passed on that commit — 107 quick checks and 8 slow ones, with no unexpected failures and no checks that had quietly started passing.

The shape that was blocking an ordinary program

Here is a real 104-line date program in the project that still could not take the new path. The offending line is not exotic:

fn leap_year?(year)
  return year % 4 == 0
end

if FourthSundays.leap_year?(year)
  return 29
end

Asking a yes/no question by calling a function was not supported in a condition. Comparisons were fine; calls were not. Any file containing one dropped to the old generator entirely.

The fix took one small function, because the capability already existed somewhere else in the compiler and simply was not wired to this position. The generated machine code is byte-for-byte identical to what the old generator produces for the same program — 1,368 bytes for the branching form, 788 for the loop form — which is the standard this project uses instead of "it seemed to work."

Then three problems surfaced that the checks had been missing

First, I wrote a bug. A second change I made looked harmless: teach one lookup to recognise function names written with a module prefix. It did recognise them — and then a guard one line below, which is supposed to reject functions returning text, stopped working because it could no longer determine what the function returned. The result asked "is this text true?" by treating the text's memory address as a number. Addresses are never zero, so the answer was always yes.

The full 106-check suite passed over that. The check that caught it was a small one written specifically to confirm the compiler still refuses something it ought to refuse. Without that check, "handles yes/no functions" and "handles all functions" look identical from the outside, and only one of them is true. The change was removed rather than shipped.

Worth sitting with. A green suite of 106 checks is not evidence that a change is correct. It is evidence that the change did not break anything anybody thought to test.

Second, Hey's script runner has a loop that never ends. This program prints 3 and exits when compiled, and hangs forever when run as a script:

fn is_even(n)
  return n % 2 == 0
end

program
  let c = 4
  while is_even(c)
    set c = c - 1
  end
  says c
end

Writing the condition as while c % 2 == 0 instead — same loop, same body — terminates correctly. So the problem is specific to calling a function in a loop condition. This is not new damage; it reproduces on a clean checkout with today's work removed. It matters more than an ordinary bug because the script runner is what we normally use as the tie-breaker when two compilers agree with each other and we want a third opinion.

Third, two of the broadest correctness comparisons in the project are failing and belong to no suite. One compares the two generators across roughly fifty example programs; the other compares ninety test programs. Both fail on a clean tree, for reasons that predate today. Because they are not registered anywhere, every suite can report green while they sit red — which is exactly what happened.

Where this leaves the roadmap

4 · Return to productsThe actual apps.not started

Step 2 is the honest sticking point. Today closed one shape and immediately revealed the next one behind it — the same date program now fails on a long arithmetic expression instead. That pattern is expected: each program reports only its first unsupported shape, so fixing one exposes another. It means the remaining work is a queue of unknown length, not a countdown.

The other half of step 2 has barely started. Removing the old generator turns out to be two different jobs, because the same code serves two purposes: it builds programs, and it is the reference answer several dozen checks compare against. The build role can retire. The reference role cannot — deleting it would remove the instrument used to prove the replacement is correct.

Not stable yet. A compiler that can build itself is a milestone, not a finish line. Ordinary programs still take the old path, one common loop shape does not terminate in the script runner, and the project's two broadest comparisons are red.

The encouraging part is not the milestone. It is that on a day when a compiler bug, a years-old loop defect, and two silently failing comparison suites were all sitting in the tree, the day ended with all three written down and one of them fixed. Speed is not what makes a compiler trustworthy. Being unable to hide is.
