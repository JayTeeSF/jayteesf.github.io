Distributed Hey: what runs across machines, and the cluster that is decided

Index Reference 3: Actors and failure Reference 4: Workers, Jobs, streams Reference 5: Distributed Reference 6: Standard library Every Hey decision

You have a laptop, a Linux box under the desk and a spare Mac mini. You'd like your Jobs to use all three without rewriting them. That is the goal the Maintainer ruled. This page is honest about the distance: the network pieces (nodes, encrypted links, remote actors, remote monitors) work; the cluster that finds machines and places work on them for you is decided but not built.

On one screen Works today: two or more compiled Hey programs connect over TCP or TLS, address each other's actors by remote pid, send and call with explicit outcomes, watch each other with remote monitors, and submit work to a named Job on a configured peer.1 Decided and coming: a written delivery contract for distributed work. Not built yet: discovery, placement, Jobs that spread themselves across machines, cluster supervision.

Badges: Works today compiled and run by the documentation test. Decided, coming ruled, not in a released build yet. Proposed designed, not ruled.

1. The goal, as ruled: add a machine, existing Jobs use it

Decided, coming An operator admits a machine to a trusted pool through a simple setup. Existing eligible Jobs then use its capacity without application changes: no socket names, no hand-built peer records, no retry or checksum loops in your code. Synchronization, checksums, delivery checks, retries and recovery are Hey's job. Being on the network grants nothing by itself: discovery and authorized admission are separate steps. Hey will not promise exactly-once external effects; work that cannot be safely repeated must say so, and Hey must report uncertainty instead of inventing success. One-line summary in the decision ledger.

3. Run the demos

Two words first. A frame is one length-prefixed message on the wire. TLS is the standard encryption and certificate check that HTTPS uses. Six multi-process demos ship with the toolchain in examples/distributed. Each program plays both roles: start node B as the server, then node A as the client, on the same port. The sessions below copy the demos into an empty folder, build one, start B in the background with its output going to b.log, give it a second to start listening, and run A. An incarnation id (inc-…) is new on every start, so yours will differ. Works today

Ping-pong: Remote.call

Run it (exact commands and output)

$ hey build 01_ping_pong.hey -o 01_ping_pong
...
$ ./01_ping_pong server 9301 tcp > b.log &
$ sleep 1
$ ./01_ping_pong client 9301 tcp
A up mode=tcp incarnation=inc-...
A handshake ok with peer=B incarnation=inc-...
A got reply=pong echo.ping=hello from A from=node-B
$ sleep 1
$ cat b.log
B up mode=tcp incarnation=inc-...
B listening on 127.0.0.1:9301
B handshake ok with peer=A app=pingpong
B stats frames_recv=3 frames_sent=2

A remote actor: Remote.send into a mailbox

Run it (exact commands and output)

$ hey build 02_remote_actor.hey -o 02_remote_actor
...
$ ./02_remote_actor server 9302 tcp > b.log &
$ sleep 1
$ ./02_remote_actor client 9302 tcp
A up incarnation=inc-...
A handshake ok
A sent (accepted for transport, at-most-once)
$ sleep 1
$ cat b.log
B up incarnation=inc-...
B listening on 127.0.0.1:9302
B handshake ok
B inbox received event=user_joined user=zoe tags=2
B done

"Accepted for transport" is all a send promises: the frame was written to the connection. B's log is how you know it arrived.

A remote monitor: node B goes away

Run it (exact commands and output)

$ hey build 03_remote_monitor.hey -o 03_remote_monitor
...
$ ./03_remote_monitor server 9303 tcp > b.log &
$ sleep 1
$ ./03_remote_monitor client 9303 tcp
A up incarnation=inc-...
A handshake ok with peer=B incarnation=inc-...
A monitoring remote pid actor=pong on node=B
A observed connection loss code=peer_closed
A watcher NODE_DOWN node=B reason=peer_closed
A watcher DOWN remote_pid.node=B actor=pong reason=peer_closed
A done
$ sleep 1
$ cat b.log
B up incarnation=inc-...
B listening on 127.0.0.1:9303
B handshake ok — now going away (simulated crash)

Node B drops the connection on purpose. A's watcher gets NODE_DOWN for the node and DOWN for the remote pid it was monitoring, both with reason peer_closed.

The other three

  • A restarted node is a new node (04_stale_incarnation.hey): run B twice on the same port. A remote pid for the previous incarnation is rejected, not routed, while a call to the current one is answered.3
  • Mandelbrot tiles (05_mandelbrot.hey) and word count (06_wordcount.hey): one coordinator hands work to four worker processes, one item at a time, so read them as correctness demos, not speed figures.
  • TLS is the default mode and the one to use between machines.4 Leave off the tcp argument; the server reads its certificate and key from HEY_DIST_CERT and HEY_DIST_KEY, and the client reads HEY_DIST_CA and HEY_DIST_SNI.

Across two real machines, set HEY_DIST_BIND on the server to its network address. How to run Distributed Hey walks through two machines and containers.

4. Honest delivery rules

Networks lose things. Hey's distributed modules never hide that behind a retry you did not ask for.

Predict it. Node A calls Remote.call on an actor on node B with a 2-second timeout, and gets a timeout. Did B do the work? Answer: unknown. The request may have been lost on the way, B may have done it and the reply was lost, or B may still be doing it. That is why Hey never retries a call for you: a retry could do the work twice.
RuleWhat it means for your codeStatus
Send is at most once. Success means "accepted for transport": framed and written to the connection.It does not mean the remote actor processed it. No silent retries, no deduplication inside Remote.send.Works today
A call is a send plus a matching reply, bounded by a timeout.A timeout can follow successful remote processing. Treat it as unknown, exactly like Actor.call locally.Works today
A missing Job reply is outcome_unknown.Never resubmit blindly; carry your own id.Works today
Peer loss is suspicion.A node cannot tell a network partition (the network between two healthy machines is cut) from a dead peer. A remote monitor's down notice does not cancel or retry your work by itself.Works today
No global ordering between different senders, connections or reconnects.Bytes on one connection stay in order; handler completion does not. Need business order? Use a partition key and one sequenced reducer.Decided, coming (as the written delivery contract)

5. Who owns what

6. Durability through hey_durable_log

Works today in the package hey_durable_log (not in the standard library). It appends records locally, replicates them to a quorum (a majority of the replicas), returns quorum_durable only after that majority confirms, fences a stale leader (a numbered term lets replicas refuse writes from a leader that has been replaced), and repairs divergent tails (the last few records a replica has that the majority never accepted). A missing majority returns an error; it never quietly downgrades to "saved locally". One catch: a quorum error may still leave a local append, so it is not proof that no record exists. What a durable log costs in memory and time is in the package's own documentation.

When Jobs run across machines, Hey will use the log's facts (who has authority, what is committed) rather than reimplement election or quorum arithmetic.

7. What the cluster adds

The goal in section 1 is ruled; the pieces that get there are designed but not yet ruled one by one, except the delivery contract, which is decided. In the order they build on each other:

PieceWhat it deliversStatus
The delivery contractWhat send, call, monitor, a Job receipt and each outcome promise across machines, written down and tested: recoverable job, attempt and result identities, lost acknowledgements, duplicates, reordering.5Decided, coming
A node serviceA supervised service that owns listeners, connections and peer state, reconnects within bounds, and offers authenticated services.Proposed
Registry, discovery and placementAdmitted machines found, authenticated and advertised with their capabilities and free capacity; work placed within those limits. Configured seeds first; gossip is optional.Proposed
ObservationOne record shape for node health, actors, mailbox and Job depth, latency, traffic, backpressure, dead letters and supervision history.Proposed
Jobs across machinesOrdinary Jobs, unchanged, running across nodes: accepted work recorded before the receipt, attempts numbered so a stale worker can't overwrite a result, recovery after a coordinator or worker is lost. There is no Jobs.cluster.Proposed
Supervision, draining and upgradesSupervision across nodes, draining a machine, in-flight work, protocol and package compatibility, rolling upgrades.Proposed

The recommended first slice is small: one durable Job partition, two workers, one handler that is safe to repeat, no automatic discovery, tested by crashing things on purpose before anything fancier.

8. Sync for devices

For phones and TVs that go offline, stdlib:Sync merges records field by field with clocks and revisions (a CRDT-style merge: two edits to different fields both survive). It is a standard-library module, documented in Reference 6: The standard library.
