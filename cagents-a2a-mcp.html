Cagents · interoperability · 1 September 2026

A2A lets agents talk to agents. MCP lets agents use tools. Cagents decides whether they should.

The agent ecosystem is settling on two complementary connections. Understanding the boundary between them makes the Cagents architecture much simpler—and gives Cagents a more valuable job than inventing yet another protocol.

You can understand the whole thing from one picture

An agent usually needs two kinds of outside help. Sometimes it needs a capability: read a file, query a database, open a ticket, call an API. Sometimes it needs another independent worker: ask a security-review agent to review a patch, hand a research problem to a specialist, or delegate a long-running job to another agent system.

MCP is a standard socket for tools and context

The Model Context Protocol gives LLM applications a standard way to connect to external data and capabilities. Its specification describes a host (the LLM application), clients inside that host, and MCP servers that expose capabilities over a JSON-RPC-based protocol.

MCP servers expose three especially useful primitives:

PrimitiveThink of it asExample
ResourceContext/data the application can readfile contents, schema, Git history, documentation
ToolAn action the model can ask to invokecreate issue, query API, write file, run approved operation
PromptA reusable interaction templatereview command, guided workflow, standard investigation prompt
Discovery is not authorization. An MCP server advertising a tool does not mean every agent should receive it. The MCP specification itself emphasizes user control, consent, authorization and the danger of arbitrary tool execution. Cagents should make the enterprise policy decision before a capability reaches the agent.

Primary references: MCP specification, server primitives, and authorization.

A2A treats the other agent as a capable black box

The Agent2Agent (A2A) Protocol solves a different problem. One agentic system can discover and collaborate with another without learning how that remote system is built. The remote system can use another model, another framework, another memory system, another company—or all of those.

The useful A2A objects are simple:

Agent Card
A discoverable JSON “business card”: endpoint, capabilities, skills, authentication requirements.
Message
A turn of communication between client and agent.
Task
A stateful unit of work that can be long-running and updated over time.
Artifact
The concrete output: report, structured data, file, image, result.

A2A supports ordinary request/response as well as streaming and asynchronous notification patterns, which is why it maps well to agents that may work for minutes or hours.

Primary reference: A2A core concepts.

The same job can use A2A and MCP at the same time

Imagine the Hey compiler team receives a report that a source change may have weakened a privilege boundary.

The protocols solve connectivity. Cagents makes the story durable: the Maintainer delegated a particular task, under a particular policy, to a particular agent; only specific source was allowed to cross the boundary; the remote reviewer returned an artifact; that artifact became evidence for a decision.

Cagents should be the authority graph, not protocol number three

The valuable question is not “can these systems connect?” It is “who is allowed to cause what, on whose behalf, with which data, under which policy—and can we prove it later?”

That suggests a clear division of labor:

LayerOwnsDoes not need to own
A2Aagent discovery, messages, long-running tasks, status, artifactsyour organization's project membership or delegation policy
MCPtool/resource/prompt discovery and invocation contractwhich Cagents project/actor should receive a capability
Cagentspersistent actor identity, project/channel membership, delegation, authority, approvals, data/source policy, receipts, durable work graphreimplementing every agent framework or every tool protocol

A delegation should be a durable object

id: delegation-7f2
issuer: human:maintainer
principal: agent:orchestrator
recipient: a2a:security-reviewer.example
project: hey
scope:
  task: ownership-repair
capabilities:
  - source.read: changed-files
  - artifact.write: review-report
may_redelegate: false
expires_at: 2026-09-01T23:00:00Z
policy_version: engineering-reviews@42

Then A2A is how that authorized delegation is executed. It is not itself the source of organizational authority.

An MCP capability should be filtered by policy

MCP server: production-db
project: payments
allowed actors: [incident-response]
allowed tools:
  - query_readonly
blocked tools:
  - execute_sql_write
human approval required:
  - export_rows

If the server advertises 40 tools and the actor is permitted to use three, the agent should see three.

What this could look like in Hey

These snippets show the intended shape of a future Cagents/A2A/MCP API. They are intentionally readable examples, not a claim that these exact packages/functions already exist.

Delegate first, then call the remote agent

program
  let delegation = cagents.delegate(
    project: 'hey',
    task: 'ownership-repair',
    to: 'a2a:security-reviewer',
    capabilities: ['source.read:changed-files'],
    may_redelegate: false
  )

  let review = a2a.send(
    delegation: delegation,
    message: 'Review the ownership patch for privilege-boundary errors.'
  )

  says review.task_id
end

The important part is not syntax. It is that a2a.send receives a scoped delegation instead of silently inheriting everything the caller can do.

Get permission before an MCP tool call

program
  let grant = cagents.capability(
    project: 'hey',
    server: 'github',
    tool: 'create_pull_request'
  )

  let result = mcp.call(
    grant: grant,
    tool: 'create_pull_request',
    arguments: {
      repo: 'JayTeeSF/hey',
      title: 'Fix ownership boundary'
    }
  )

  says result.status
end

Parallel reviewers still have one accountable task owner

worker ReviewRequest(request)
  return a2a.send(
    delegation: request.delegation,
    message: request.message
  )
end

program
  let reviewers = workers(ReviewRequest, count: 8, capacity: 128)

  for request in approved_reviews
    reviewers.enqueue(request)
  end

  reviewers.stop()
end

Hey can make execution parallel. Cagents should keep organizational accountability serializable: one task owner, multiple explicitly delegated runs.

Four security mistakes to avoid

1. Discovery ≠ trust
An Agent Card or MCP capability is a remote claim. Cagents policy determines local trust and authorization.
2. Authentication ≠ project authority
A valid OAuth token does not mean its holder may act for every Cagents project/task.
3. Delegation must not amplify privilege
A child gets the intersection of parent authority, delegation scope, target trust policy and current organizational policy—not the union.
4. Credentials are not context
Tokens and downstream secrets belong in identity/secret systems, not prompts, messages or Git exports.
This is the strategic opening for Cagents. Standard protocols make connectivity cheaper. That leaves Cagents free to concentrate on persistent identity, authority, source/data boundaries, approval, causal audit and durable organizational state—the things an enterprise actually has to govern.

The architecture decision

Use A2A. Let Cagents discover/register remote agents, authorize a delegation, send/observe A2A tasks, normalize their events, and ingest returned artifacts as evidence.

Use MCP. Let Cagents maintain an approved server/capability registry, filter tools/resources by actor/project policy, integrate proper OAuth/credentials, attach approval requirements, and record important calls as receipts.

Keep Cagents above both. The durable Cagents graph should answer why the interaction was permitted and what organizational state changed as a result.

A useful north star: Use MCP for agent → capability. Use A2A for agent → agent. Use Cagents for organization → authority.
