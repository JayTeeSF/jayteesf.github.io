01 / FIRST CONTACT

Start from the code repository you already have.

A developer installs the Cagents client once, enters their existing code repository, and runs git cagents init. A short setup flow binds that repository to a project in a team workspace. It does not move the source code or create a database inside the code checkout.

Proposed product contract, 6 September 2026.

The setup, binding, relay, and synchronization commands below specify what we intend to build. They are not a claim that every command is available in the current CLI. Discovery and command-parity tests must establish the installed capabilities before migration.

  1. Choose the service.Connect to an existing application, use the hosted service, or start a self-hosted instance. One instance on a machine can serve several independent workspaces. A personal setup does not require one server per source repository.
  2. Create or join a workspace.Create a team workspace as its administrator, or accept an invitation to an existing one. The setup provisions its database, durable journal, and export settings. An administrator can connect a Git coordination repo when remote fallback is needed.
  3. Create or select a project.Default to a distinct project for this code repo. Select an existing project when several repos intentionally share one board and communication history. The setup explains what is shared before binding.
  4. Bind this checkout.Write a non-secret .cagents/project.json with stable instance, workspace, and project IDs. Credentials, actor selection, local server routes, and queues stay in machine-local client storage.
  5. Introduce humans and agents.The creator gets an explicit human maintainer role. Add people and agent seats with project memberships and scoped credentials. Generate each START and a small launcher/harness instruction that reads it.
  6. Resume and prove communication.Run git cagents resume. Read the bound project and actor identity, exchange a setup message, acknowledge it after reading, and exercise a task and lesson operation. If a relay is enabled, verify that route too.
# Proposed first-run experience; run inside the existing code repository.
git cagents init
# Service → workspace → project → identity → binding → verification

git cagents status
git cagents resume
git cagents inbox

A teammate who clones the code repo receives its non-secret binding. They run git cagents join to authenticate or accept an invitation, then resume. Cloning a repo grants no Cagents membership by itself. A connector-only agent receives the same workspace/project identifiers, actor bootstrap, request schema, and approved Git submission stream.

A relay-only participant can join an already provisioned workspace through an accepted invitation and queued join operation. A brand-new authoritative workspace must first be provisioned by an administrator with a route to the application. An offline setup can prepare a draft binding; it cannot invent accepted membership or a running database.

02 / THE TEAM BOUNDARY

One workspace is one independent coordination home.

Default to one workspace per team. An organization or account may administer several workspaces, and a person may participate in more than one. Those relationships do not collapse their storage or grant access across them.

ConceptOwns or identifiesDoes not imply
Application instanceA server deployment and its immutable identity; routing for many workspacesOne global task board or a shared coordination database
Organization / accountAdministration, service access, and hosted billing where applicableAutomatic access to every workspace’s private content
WorkspaceIts own SQLite database, journal, actor memberships, policy, history, and coordination Git repo/export setEvery project visible to every workspace participant
ProjectTasks, goals, project membership, sessions, channels, and scoped lessons/skillsA separate database or exactly one source-code repository
Code repositorySource history plus an explicit Cagents bindingCoordination authority, membership, credentials, or an API server
Actor seat / sessionA workspace-scoped human or agent identity; a specific execution contextEvery privilege held by its human owner or another seat with the same name

The server maintains a small control registry mapping authorized workspace IDs to their storage and service placement. Each workspace receives independent database and journal storage, export state, retry records, and backup boundaries. Project IDs and record IDs are resolved within their instance/workspace scope; display names are never authority.

The hosted entitlement check belongs in the hosted service boundary. Self-hosted operation uses the same coordination semantics without requiring a paid hosted subscription. Neither Git fallback nor a different UI changes authorization.

03 / SEPARATE OR TOGETHER

Choose how much coordination to share.

Independent teams

Separate workspaces. Separate databases, journals, coordination repos, credentials, and histories. This is the default for unrelated teams or personal versus employer work.

Related projects

One workspace, separate projects. Keep boards and memberships distinct. Share selected channels, lessons, or skills through explicit audience and access rules.

One product, several repos

Bind several source repos to the same workspace and project. They share one board, communication history, and project membership while retaining separate code histories.

PreferenceBinding choiceResult
Keep everything separateDifferent workspace IDsIndependent storage, history, credentials, and exports
Separate work, selected shared conversationsSame workspace; different project IDsSeparate boards; explicit channel membership and scoped sharing
Work together as one projectSame workspace and project IDs for multiple code reposOne project graph and history, multiple source repositories
See all my work in one placeA dashboard with several explicit workspace/project subscriptionsAuthorized aggregation; source labels remain visible; no data merge

A project may expose a shared channel to selected actors without granting them tasks, sessions, other channels, or full project membership. Workspace-wide lessons or skills are explicitly published at that scope; project-private knowledge does not silently become global. Cross-workspace sharing requires an explicit export/import or a separately authorized collaboration workspace. Automatic federation is outside the first cutover.

Changing a binding is not a data migration. Rebinding a checkout only changes where future operations go. Combining or splitting existing project histories requires a separate administrative migration with an inventory, reference mapping, and provenance. Pending requests retain their original destination and must never be redirected by a rebind.

04 / SAME MACHINE, DIFFERENT WORK

The directory selects the project. The session pins it.

Store the shareable binding in the code repository; keep connection and identity secrets outside it. For a public source repo, the team can choose a local-only binding if even workspace metadata should remain private. A binding is routing information, not permission to access the referenced workspace.

// Proposed .cagents/project.json (JSON, shown without comments in the file)
{
  "schema": "cagents-binding-v1",
  "instance_id": "ins_product",
  "workspace_id": "wsp_product",
  "project_id": "prj_web"
}

The local profile maps these IDs to approved API and Git routes, credential references, and actor seats. A local machine may use loopback while a remote seat uses the relay; the tracked IDs are identical. Installation provides a real git-cagents executable or equivalent alias to the Cagents client. Merely cloning a repo does not install executable Git extensions.

  1. Resolve an explicit destination argument, a worktree-local override, or the binding inside the current code repository. In a monorepo, the nearest explicit subproject binding can select a subproject; otherwise use the repository-root binding. Do not search outside the current Git repository for a fallback binding.
  2. Validate the full instance/workspace/project tuple and approved connection profile. Conflicting explicit, environment, and repository selectors produce a clear error. A leftover CAGENTS_PROJECT must never silently override the current repository.
  3. Pin the tuple, actor, binding revision, and session ID at resume. A bound agent cannot silently switch projects because a subprocess changes directory. An intentional rebind or actor switch starts or explicitly rebinds the session.
  4. Namespace caches, request queues, credentials, cursors, and receipts by instance, workspace, seat, and producer/session as applicable. Use one working directory and request stream per producer, including simultaneous sessions of the same actor.
No machine-wide “last project” authority.

A project selector in one terminal cannot redirect another terminal. Missing or ambiguous context requires explicit binding. Administrative cross-project commands name their destination; ordinary commands inherit the verified session.

Different projects may be bound to different instances, or to different workspaces on the same instance. Git worktrees normally inherit the tracked binding; an explicit local worktree override may select another approved project. A newly cloned untrusted binding never causes the client to send credentials to an unapproved endpoint.

05 / EVERY RESTART

Keep START.md. Make its workflow transport-independent.

The launcher tells each participant to read CAGENTS.md, then exactly its own agents/<actor>/START.md or humans/<actor>/START.md, and resume the bound project. Common instructions and each START are authoritative application records rendered through the API and the published Git tree.

Every agent and human START must be read and rewritten for the new system, preserve role and constraints, resolve its required skills and lessons, and remain strictly below 8,000 UTF-8 bytes. Original blobs remain unchanged in migration history. Generated bootstrap includes the tested command names and minimum compatible client version; credentials stay outside Markdown.

  1. Verify the bound instance, workspace, project, actor, client capabilities, and instruction/migration generation.
  2. Reconcile outstanding operation IDs, receipts, and locally retained drafts without blocking startup on unrelated actors’ dirty checkouts.
  3. Load a consistent, bounded context: shared rules, START, relevant skills/lessons, board, active tasks, unread messages, and restart context. Mark snapshot cursor and freshness.
  4. Record the session and its synchronization state through the strongest configured route. In relay mode, retrieve the result and referenced startup snapshot.
  5. Proceed under the maintainer’s received instructions and valid delegations. Record “authorized; synchronization pending” when appropriate. Explicit pauses, conditional restart requirements, and exclusive-resource claims retain their own conditions.

Loading an inbox never acknowledges its contents. Fetching a START alone does not prove that current restart conditions were met. A disconnected participant can continue work within known authority, but cannot claim unseen updates or a newly requested exclusive resource as confirmed.

06 / ONE COMMAND FAMILY

Use git cagents from either code or coordination workspaces.

git cagents … and cagents … use the same command implementation. In a code repository, the binding resolves the coordination project; coordination operations never stage or commit source files. An editable coordination checkout is a distinct, client-managed view bound to that same project.

Proposed interfaceContract
git cagents initGuided service/workspace/project setup and local binding; idempotent resume of partial setup
git cagents joinAuthenticate or accept an invitation for the already bound workspace/project
git cagents bindExplicitly choose an existing workspace/project for this code repo or worktree; preserve pending destinations
git cagents resumeVerify startup, recover pending operations, read role context, establish the session
git cagents pullRetrieve instructions, state, messages, and receipts; preserve drafts and later edits
git cagents pushSubmit prepared operations; in a coordination checkout, also capture staged coordination edits
git cagents syncRetrieve updates, submit prepared operations, reconcile results, refresh the managed view
git cagents statusDisplay identity and destination, connection route, freshness, drafts, pending operations, and conflicts
git cagents forward D123 --to worker-bProposed provenance-preserving relay of an instruction; keep additions distinguishable from the original
git cagents inbox, task show, send, lessonRetain the domain command families; installed help and conformance tests define supported subcommands/flags

Ordinary git add, git diff, and source-code commits retain their normal meanings. A bare git push is a Git push; it is not silently replaced. The Cagents extension chooses the application route and owns its transport machinery. A Git alias can add a command but cannot override an existing built-in command.

07 / PREPARE ONCE

Commands and file edits converge on semantic operations.

A domain command directly constructs a validated request. For participants who prefer files, provide a private editable coordination checkout with familiar paths. Staged edits become a request bundle with their base record revisions; arbitrary exported-file diffs never become unchecked database writes.

# In the private COORDINATION checkout, not the source-code checkout:
git cagents pull
# Edit a lesson or other supported coordination record.
git add -- path/to/record.md
git cagents push
git cagents status

The client captures the exact staged content and constructs an immutable operation ID before transport. The envelope identifies protocol version, instance/workspace/project, producer/session, operation, payload hash, expected revisions, causal dependencies, and instruction/delegation references where relevant. The server binds the authenticated submitting identity; it does not trust a free-form actor field.

A task claim, acknowledgement, recipient change, or coordinated multi-record update must use the corresponding semantic action. If an edit has no unambiguous mapping, explain the unsupported change and the operation required. Atomic groups are accepted or rejected as a group; a rejected prerequisite blocks its explicit dependents, not unrelated work.

08 / HUMAN DIRECTION

Your instruction remains yours when an agent relays it.

Maintainer instruction → orchestrator → worker.

The instruction authorizes work within its scope. A server receipt confirms recording. A transport delay must not demote a received instruction into a new permission request.

Preserve the original source and wording, originator, authenticated submitter, authorized delegation chain, work scope, conditions, and amendments. Relaying does not change the originator or automatically expand the scope. An orchestrator authorized to organize work can issue subtasks within that delegation; an agent’s interpretation remains separately attributed.

Use source evidence from an authenticated maintainer interaction or verifiable instruction record. A branch name, Git author string, or untrusted quotation alone cannot establish maintainer authority. Provisioned connector seats must have an approved identity/delegation mechanism: actor-scoped signed requests or a trusted connector binding with explicitly limited seat authority. Shared GitHub credentials alone cannot prove which agent authored an instruction.

Keep authorized, submitted, accepted into storage, delivered, acknowledged, and completed distinct. A worker can be authorized while its task event awaits synchronization. A self-requested exclusive claim is not acquired merely by queueing it.

Amendments and cancellations explicitly reference the instructions they supersede and propagate through relays. During complete disconnection, an agent cannot know an unseen cancellation; freshness must be visible. Continue only within the received authority and its conditions, preserve local records, and apply new directions on reconnection. This does not override an explicit maintainer pause or migration gate.

09 / FAST WHEN CONNECTED, DURABLE WHEN REMOTE

API first. Git fallback. One application state.

ConditionSubmissionReading
API reachableAuthenticated direct requestAPI snapshot/events with read-your-write behavior
API unreachable, Git reachableSame operation in the producer’s Git request stream; supervised relay submits itPublished tree and operation receipts with visible cursor/time
Connector-only environmentSame envelope through GitHub connector operations; no CLI execution requiredSame authorized publication and receipt records
Neither route reachablePreserve the local queue and operation IDsLast synchronized view, explicitly stale
API recoversReconcile or retry outstanding IDs without changing destination or payloadRefresh and converge with the server

Fallback is for connectivity and configured service unavailability. An explicit authentication denial, authorization denial, or revision conflict is reported as such. The Git relay calls the same API and cannot bypass those decisions. If the API timed out after committing, resubmission through Git returns the original outcome using the same scoped idempotency key.

The Git repo has an exporter-only published branch and isolated producer request branches. One working directory and one submission stream belong to one producer/session. The relay runs near the application, polls approved streams, validates envelopes, and submits them using scoped credentials. It never executes repo-provided scripts, treats published exports as incoming requests, or asks an LLM to merge coordination facts.

Order explicit dependent operations; preserve causal references rather than guessing from wall clocks. Restart the relay from durable checkpoints, isolate malformed requests, apply fair per-workspace scheduling, and resume unrelated streams after failures. A queued Git submission is durably transported, but its domain result remains pending until the server processes it.

10 / NO LOST DRAFTS

Cleanup follows the exact captured operation.

StateWhat the client retains or retires
Draft / queuedRetain staged content, immutable request, original destination, and retry identity
Outcome unknownQuery or retry the same ID; never manufacture a new mutation to resolve uncertainty
Rejected / conflictingPreserve the proposed edit and reason; resolution creates a new operation referencing the old one
AcceptedRecord the receipt and retire that retry entry; maintain a visible accepted result if publication lags
Reflected in the viewRemove only the corresponding managed overlay once the snapshot includes the accepted transaction

Compare the captured content with the current local file before retiring it. If the participant edited the file again, retain those newer changes. Pull and sync must preserve unstaged edits, unresolved conflicts, and unrelated files. Never use a broad hard reset or clean as a synchronization strategy.

Server deduplication retention must cover the supported retry/replay horizon; a compacted journal cannot make an old operation look new. Persist receipt identity or a replay fence across compaction and backup/restore. An old restored snapshot must not silently reuse a generation that could replay previously accepted effects.

11 / SERVER STORAGE

Scale through independent workspace writers.

The intended application stack combines hey_record, hey_durable_log, and hey_sqlite3. Each workspace has its own database and journal namespace. Domain services validate authorization and revisions, order a logical transaction, durably commit it, and materialize current state and retained history.

A receipt means the mutation crossed the configured durability boundary. If the current-state materializer is behind, the service must wait for the required cursor or otherwise provide an equivalent consistent read. It must not acknowledge an in-memory queue as crash-safe completion. Git export stays asynchronous and never extends the normal API commit path.

  • Independent queues: serialize writes where a workspace needs it; avoid a machine-wide coordination lock. Bound buffers and fair scheduling prevent one slow team from monopolizing service.
  • Server-owned connections: select databases by authorized registry IDs; clients never open or share a network-mounted SQLite file.
  • Many workspaces: bound open database connections, schedule exports independently, and allow workspace placement across server workers/hosts as capacity requires. No scale number is claimed without workload measurements.
  • Recovery: back up journal, database checkpoint/cursor, receipt identity, instruction history, and required source artifacts coherently. Restore is an explicit workspace operation with generation control.
  • History: retain original Git DAGs, object provenance, events, and ordered changes needed for past-point reconstruction. Materialized current state alone is insufficient.
12 / ISOLATION IS ENFORCED EVERYWHERE

Every read, write, and export has a destination and an audience.

Use instance/workspace scope in operation IDs, actor bindings, database routing, cache keys, subscription topics, journal paths, export cursors, and retry queues. Apply project, channel, and DM audience rules to every query and export. A valid credential for one workspace cannot choose another workspace merely by changing a request field.

A workspace’s full coordination Git repo is appropriate only for readers authorized to all exported contents, including history. Git branches are not confidentiality boundaries. If project or channel audiences differ, publish separate authorized repositories/projections or provide API-only access for private content. Repository access controls must match each projection’s audience.

Removing access cannot erase copies or Git history already downloaded. This is an explicit consequence of exporting data, so publication must be scoped before disclosure. The application can enforce future access and stop future delivery; it must not imply retroactive removal from a reader’s machine.

Shared administrative infrastructure does not make per-team SQLite files an absolute process-security boundary. Stronger deployments can use separate service processes/hosts and storage credentials per workspace. The baseline contract requires enforced tenant routing and authorization plus independent storage; operational hardening follows the deployment’s needs.

13 / KEEP THE READABLE TREE

The repo remains a legible, historical view.

One canonical record/path model serves the API tree, Slack-like UI links, export, and historical reconstruction. Preserve readable names alongside stable IDs, familiar project/actor/task/message directories, record provenance, attachments, and valid links.

The exporter publishes consistent snapshots with workspace identity, migration generation, ordered cursor, and timestamp. Batch commits for reasonable eventual freshness; measure lag rather than promising instantaneous Git synchronization. API users keep working while a Git provider is slow. Remote users see publication age and pending results.

Full-fidelity administrative export can preserve all authorized workspace data and both imported Git histories. Audience-restricted projections preserve only what that audience may receive and must not masquerade as a complete administrative backup. The default readable branch is written by the exporter alone; private editable working copies are drafts submitted through the client.

Project-wide broadcasts keep their project membership meaning. Joining a channel does not join the project. A combined dashboard is a derived view. Presence and high-frequency heartbeats need not become Git commits; exclusive resources use a lease/fencing policy appropriate to their operation, not an assumed short Git-polling interval.

15 / CLIENT PARITY

One contract for humans, agents, and every interface.

Web, macOS, iOS, Android, CLI, and connector adapters share operation schemas, actor scope, validation, idempotency, revision conflicts, receipts, and record paths. Shell clients use the Git extension; connector-only agents create the equivalent envelope without hand-writing mailbox refs or task transitions.

The common instruction set describes behavior once. Each participant START adds role-specific constraints. Connection profiles and adapter help explain mechanics. Provisioning must prove the identity and operation capabilities of each seat before the restart test; a successful Git push alone is insufficient evidence of a correctly bound actor.

UIs display the active workspace/project next to actions and preserve those labels in aggregated views. They show freshness, pending versus accepted records, unread versus acknowledged delivery, and conflicts. They never require users to understand journal internals to send a message.

Implementation responsibility

CLI/core orchestrator: setup/binding interface, common operation envelope, Git extension, drafts/retry handling, connector contract, migration extraction and START rewrites. Application orchestrator: workspace provisioning/isolation, domain authorization and delegation records, journal/materialization, import/export, receipts, relay integration, and client projections. Overseer: reconcile the seam and independently review end-to-end evidence. Reuse existing task owners; this document proposes contracts and does not declare new assignments sent or implementation complete.

Cutover sequence

Prepare and rehearse before switching live agents. At the agreed freeze, capture the final legacy data and pending work, import and reconcile it, publish the new instruction generation and bootstrap, protect the published branch, and run the acceptance scenarios. Tell the maintainer when remote and local participation both work so remaining agents can be stopped or restarted against the new interface. Correct live entry points; preserve old instructions only as clearly historical records.
