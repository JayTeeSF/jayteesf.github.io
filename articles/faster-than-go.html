Faster Than Go? Certified on Linux — 2026-07-27

On 2026-07-27, on a dedicated Linux box, the pre-registered certification protocol returned green: a paired-ratio mean of 1.0087 (95% CI half-width 0.80%, lower bound 1.0007) on the matched row — both servers building the identical 364-byte JSON response, one core each — makes Hey faster than Go net/http with 95% confidence, corroborated by a frequency-invariant measure: 1.12% fewer CPU cycles per request. That follows the same-day macOS reading one day earlier, where the matched row read 125,819 requests/second for Hey against Go's 114,870 — 109.5% of Go — the direction-grade discovery that earned this certification run; it remains labeled direction-grade below while its own confirmatory rerun is queued.

1. Where it started, and the method

Nine days before the matched-row reading above, Hey's fastest web service answered this same 364-byte JSON health check at 2,251 requests/second, on the same box, against a Go net/http baseline of 61,972. That gap did not close by tuning in the dark. The method, repeated across every fix in this article, is the same four steps: measure the current mechanism with a probe that can fail as well as pass, name the specific defect a profile or disassembly points at, pre-register a gate — a spec written and committed before the fix lands, so it can be watched failing on the old code — and only then let the toolchain land the change and watch the gate flip. Every number below traces to one of those gates.

2. The four mechanism kills, in order

Four defects, killed in sequence over the campaign, account for essentially the entire gap. Each was a pre-registered gate first, a fix second.

2a. The interpreter-delegation tax

Compiled Hey code calling a pure-Hey standard-library function paid roughly 7 ms per call — each call round-tripped through a temp file and a spawned interpreter process. A persistent interpreter sidecar (v0.99.402a) replaced the spawn-per-call path; the un-tabled canary call fell from 4,479 µs to 55–58 µs, roughly an 80× cut, confirmed on three reps.

2b. HTTP keep-alive

The runtime hardcoded connection: close; every request, including ones from clients advertising keep-alive, paid a fresh TCP handshake. Landed in the same v0.99.396a release that made the accept path platform-aware: war-room's /health median fell from 2.6 ms to 79 µs in the same measurement window.

2c. The JSON-construction quadratic

Building a 46-key JSON document cost 2,280 clones per request — a quadratic in key count that survived an earlier representation change (a linked list replaced by a flat array, v0.99.420a) completely unmoved, because the fix changed how keys were stored, not how each value got copied during construction. The gate for the actual construction fix was written and watched red against that 2,280 figure; it flipped green on v0.99.423a, the day of the accept-model fix: clones per request fell to 124 (an 18.4× cut), and served throughput on that route rose 3.8×, from 16,075 to 60,687 req/s at a 61 µs median.

2d. The accept model

This is the one that produced today's headline. Since early in the campaign, a probe had shown Hey's effective concurrency pinned near min(offered connections, workers) no matter how much faster individual requests got: at 16 offered connections, a 1-worker server sat at ~0.96 in flight, 4 workers at ~3.95, 8 workers at ~7.88 — unmoved by every other fix in this article. A pre-registered accept_model_spec (gates G1/G2) was built and watched red on a quiet baseline: in-flight median 3.84–3.86 across c=4/16/64, exactly the failure the defect predicts. The waccept landing (v0.99.430a) flipped it green: in-flight at c=16 jumped to 15.35 — 15.9× scaling — and it is this single change that turns a 1-worker server from "doing one thing at a time" into "servicing all 16 offered connections," which is the entire reason the wall-clock throughput moved by 8–9× in one landing.

3. The day itself: 24% to 109%

The source log calls an earlier same-day reading "this morning's 24.1%": Hey w1 at 14,276 req/s, p50 65 µs, against a same-cell Go@1 reading of 59,151 req/s at p50 233 µs — even though Hey's median was already beating Go's by more than 3× while losing badly on throughput, an early tell that the gap was concurrency, not per-request speed. (Note honestly: that cell is timestamped mid-afternoon against a binary built minutes earlier, not literally morning — we are repeating the source log's own label rather than inventing a tidier clock than it kept. Different sessions also re-measure Go independently, by design, so 59,151 here and 114,870 later are not the same denominator; see the certification protocol's ruling on that below.)

By the evening cell, on v0.99.432a with waccept landed at 430a, the matched row read 125,819 vs Go's 114,870 — 109.5%, at p50 121–122 µs vs Go's 136–137, both lanes reconciling to in-flight ~15.3–15.7 at c=16. A supporting w4 cell read 123,481 req/s (two reps); against Go serving pre-built static bytes rather than constructing JSON — a comparison that flatters Go — Hey read 94.2% (125,819 vs 131,649). This is exactly the accept_model_spec concept working as designed: written red before the fix, watched red on the old code, flipped green on exactly the slice it was written for — not a gate that happened to agree with a result someone wanted.

A cross-platform footnote, for honesty rather than triumph: a Linux seat reported the same afternoon that a different code path — a research prototype implementing per-worker event loops rather than the shipped waccept fix — reached 91.7% of its own Go baseline on that box (one multiplexed worker beating four blocking ones, 72,436 vs 57,076 req/s). It is not the same mechanism as the fix described in 2d above, but it is the same idea from the accept-model research (per-worker event loops, "transfers to Hey" item 3 below), and its independent 91.7% is itself confirmed and then bettered by the true matched-row 109.5% on the primary box.

The same afternoon, the accept-model gate's own honesty check caught a problem in the fix it had just certified as landed: at c=64, the default relative shed thresholds and the newly-uncapped accept rate interact badly — kill_pressure crossed its soft ceiling (~5.5 GB) within seconds, producing 152,712 503 responses before the run self-protected. That c=64-vs-shed policy interaction is flagged upstream, unresolved, and described again in section 5.

4. What "matched" honestly means

The matched row — both servers building the JSON document per request — is the fair comparison, and it is the one this article's headline uses: 125,819 vs 114,870, 109.5%. The static row — Go serving pre-built bytes it never has to construct, Hey still building its response fresh — still favors Go: 125,819 against 131,649 is 94.2%. The certification protocol (docs/bench/97k-per-core-protocol.md, internal) is explicit that both rows publish together, always, and the headline quotes the matched one; a "Hey beats Go" claim built only from the flattering row would not survive its own gate.

Even granting the matched-row win, it is a win in wall-clock throughput under this accept model, not yet a win in raw per-request CPU cost. The campaign tracks a second currency for exactly this reason: microseconds of CPU time per served request, measured from process CPU counters rather than wall clock, because it is robust to exactly the kind of concurrency change described in 2d. As of this week that budget read roughly 57 µs of CPU per request for Hey w1 against a ~10.4 µs/req budget implied by Go's quiet-window denominator — a gap the accept-model fix does not touch, because it changes how many requests are in flight, not how much work each one costs the CPU. The matched-row win is real and it is concurrency, honestly earned; it is not yet evidence that a single request costs the same on both sides.

5. What's not settled

  • Certification landed for one row, on one venue. The Linux run (section 6, [CERT] table) certified the builds-JSON row with a paired-ratio confidence interval half-width of 0.80%, comfortably inside the ≤1.5% gate. The static-bytes row has not been through the protocol at all, and a separate macOS attempt at the same protocol confirmed direction (mean 1.0397) but missed the precision gate (half-width 2.03%); both remain open, and the two-pair 109.5% macOS reading in the body stays labeled direction-grade until its own rerun lands.
  • The c=64 shed-policy interaction found by the same gate's own honesty check (section 3) is unresolved: relative shed thresholds plus the newly-uncapped accept rate produced a kill-pressure spike and 152,712 503s in one run. Flagged upstream; no fix landed yet.
  • The CPU-time budget gap from section 4 (~57 vs ~10.4 µs/req) is the next honest target — the accept-model fix bought concurrency, not cheaper requests.
  • The roadmap: I5 reference-counting, then per-access boxing. A per-access decomposition probe found that reading a single integer out of a 4-key map costs 7.0 clone calls and 215 ns today — fixed boxing machinery, not representation cost — and a 4,096-element list access costs 8,198 clones and 48,550 ns, the deep-clone signature the I5 refcounting work targets directly (this is the "fewer calls per request" half of the roadmap: pre-registered floor is below 5,000 ns for that case, roughly 100×). Per-access boxing sits behind it, unstarted.

6. The certified run, and the screen that made it honest

The certification protocol from section 5 ran on its designated formal venue on 2026-07-27: a dedicated Linux box (omarchy-sys76), toolchain v0.99.433a with the multiplex prototype enabled — the productionized form of the same accept-model change measured earlier on trunk on the macOS box (section 2d); the prototype itself is still being hardened before it lands on trunk. The server process was pinned to cpu0, the load generator to cpu2 — disjoint physical cores. Eight A-B-B-A same-minute pairs, 8-second keep-alive cells, every cell at 100% 200-responses, roughly 19.5 million requests total, payload parity asserted by checksum before any clock started. (Source: Linux seat certification run, 2026-07-27, cagents bus + shared evidence, internal.)

That box turned out to be bimodal: its cores idle near 2.5 GHz and boost to roughly 4.0 GHz, and which state a given pair lands in is not something either lane controls. The protocol's pre-registered screen rejects any pair where the two lanes' mean core clock disagrees by more than 10%, precisely because a clock mismatch would let raw core speed pose as a language result. The screen is not decoration: run over all 8 pairs unscreened, the mean ratio was 1.0418 with a 95% CI half-width of ±12.44% — a number nobody could trust in either direction. The screen cut two pairs, and — worth stating plainly, because a screen that only ever removes inconvenient results is not a screen, it's a thumb on the scale — it cut both ways: it rejected the single most Hey-flattering pair in the run (ratio 1.3964) right alongside the single most Go-flattering one (0.8854). What survived was six pairs with mean 1.0087, 95% CI ±0.0081 (half-width 0.80%) — smaller than the unscreened number, and, for the first time this campaign, trustworthy. A legitimate screen makes the answer smaller and more boring; that is exactly the direction this one moved it.

A second, independent line of evidence agrees without needing the screen at all: CPU cycles per request is a frequency-invariant quantity — it does not care which P-state a core was in — and across all eight pairs, including the two the clock screen rejected, Hey used 1.12% fewer CPU cycles per request than Go (go/hey cycles ratio 1.0113). One number was screened for a known confound and came out at +0.87%; a different number immune to that exact confound came out at +1.12%, unscreened. Two independent measurements — one filtered, one that never needed filtering — agreeing on direction and rough magnitude is the strongest corroboration this campaign has produced.

That cycles-per-request result also closes a loop from section 4: this campaign's second currency was never wall-clock throughput alone but the cost of a single request, and the "fewer calls per request" thread now has evidence at both ends of it — 1.12% fewer CPU cycles per request at the measurement level, and, at the mechanism level, Hey's own clone count on the 46-key JSON route falling from 2,280 to 124 per request (section 2c), with reference counting still to land on top of that.

7. The closing thesis

The fastest path to a fast language, on this evidence, was not a faster optimizer — it was measurement discipline applied without exception. Every fix in section 2 has the same shape: a gate written and committed before the fix existed, watched failing on the old code, and only trusted once it flipped on exactly the slice it was written for. The one time a gate went green on a technicality rather than a real fix, the campaign's own certification protocol caught it: a reconciliation check that is supposed to confirm rps and latency agree passed cleanly on a poisoned mean — twelve starved requests out of 90,000 had dragged the mean estimate to 15.98 in-flight while the honest median sat at 3.92, and the check passed on the bad number. The gate was wrong, not the server; the fix was to compute the check from both the mean and the median and flag their disagreement, which is now standing procedure. A pre-registered gate is a promise you make to your future self while nobody's watching — and, true to form, the one time ours was broken, it broke in the paperwork, not the code.

None of this is new caution for this project. The earlier web-services article carries the fuller retraction history — a memory instrument that lied for a full day, a "fix" that had to be un-fixed, an arithmetic proof that died on an unmeasured premise — printed at full volume rather than quietly edited away. That track record is the reason a 109.5% reading got a provenance banner and a certification run before it got a headline, and why the banner stays up — now stating what's certified rather than what's withheld — even after the run passed.

Glossary

Accept model / effective concurrency
How many of the connections a server has been offered it is actually servicing at any instant, versus how many it merely has open. Hey's had been capped near min(offered connections, workers) all campaign; the fix in section 2d removed that cap.
Matched row
The comparison where both servers do the same per-request work — here, constructing the JSON body fresh rather than one side serving pre-built bytes. The static row (Go serving pre-built bytes) is a different, Go-favoring comparison and always publishes alongside it, never alone.
Certification / confidence interval (CI)
A confidence interval is a range that quantifies how much a repeated measurement would wobble if re-run. "Certifying" a ratio here means that range (specifically its half-width) is narrow enough — ≤1.5% — to trust the mean ratio it is built from, computed from ≥8 paired same-minute cells on a quiet box.
p50
Median latency: half of requests finish faster than this value, half slower. Reported alongside throughput because a server can win on one and lose on the other.
Deeper mechanism note: why the accept model is the ceiling, not the request path

The research brief behind this fix (internal, docs/bench/research/2026-07-26-accept-model.md) surveys three production runtimes for how they decouple "accepted" from "servicing one at a time": Go's netpoller parks a blocked goroutine on a shared kqueue/epoll descriptor and resumes it on readiness, never occupying an OS thread while idle (netpoll.go, netpoll_kqueue.go); BEAM's Ranch acceptor pool (default 10 acceptors) never serves the connection it accepts — it spawns a handler and re-accepts immediately (ranch(3), ranch.erl); and nginx sheds the herd problem either with accept_mutex or SO_REUSEPORT socket sharding, the latter measured by F5 at "2 to 3×" rps on a 36-core box (F5 socket-sharding blog). The brief's sharpest warning: SO_REUSEPORT is real kernel load balancing on Linux but "last-bind-wins" on the BSD/Darwin lineage — a portability trap with no Apple documentation confirming it either way, for which Hey's own 2026-07-25 measurement (REUSEPORT cells collapsing to plain single-worker behavior) is cited in the brief as the primary evidence (background on the platform split). The sequencing the brief recommends — a single dedicated acceptor thread first, then per-worker event loops to actually raise the ceiling, REUSEPORT only as a Linux-only optimization afterward — is the plan section 5's roadmap continues.
