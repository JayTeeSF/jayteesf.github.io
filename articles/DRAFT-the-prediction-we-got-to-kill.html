The Prediction We Got to Kill

A years-old plan blamed an 18 millisecond command-line binary's distance from a sub-5 ms goal on process startup and runtime initialization, and had shelved a "pre-warm" workstream premised on fixing it. Before re-measuring, both benchmark seats wrote down falsifiable predictions — publicly, with pass/fail bounds — so a miss would be a finding instead of a quiet retrofit. One of those predictions died within an afternoon, on both machines, and it took the pre-warm workstream's whole premise down with it.

Scope: two boxes, single-machine numbers

Every measured number below comes from exactly two machines — one Darwin (macOS/arm64) box and one Linux box — run separately, on different hardware, at different times. Cross-OS numbers are never compared to each other as if they measured the same thing. What travels between the two boxes is shape and ratios — is the workload the dominant cost on both platforms, roughly how dominant — never raw millisecond-for-millisecond magnitude. Where a figure appears from both boxes side by side in this article, it is there to compare percentages, not absolute times.

TL;DR

  • The retired hand-tuned binary and its idiomatic replacement both land at 18.2 ms on Darwin, against a sub-5 ms target — the gap the whole investigation exists to close.
  • Darwin's bare-process control (a C no-op binary, image load + dynamic linking only) measured 1.2 ms. The runtime's own no-op measured 1.1 ms — less, inside noise. Subtracting the two gives runtime init a cost of −0.0 ms: unmeasurable, free, gone.
  • That was a miss, and it was supposed to be checkable as one. The pre-registered prediction for that subtraction (P-D2) was 2–4 ms. Actual: −0.0. Stated plainly in the lab notes as MISS, not smoothed over.
  • The workload — not startup, not init — is 94% of the cell on Darwin (17.1 of 18.2 ms). Linux, measured independently on different hardware, found the identical shape: startup+init is 0.9 ms of a 13.2 ms cell (7%), with runtime init inside that 0.9 ms reading as effectively zero too.
  • A years-old plan number — roughly 2.2 ms of "runtime init" — is dead on both platforms, and the pre-warm workstream that plan justified has nothing left to pre-warm. The sub-5 ms road runs through the workload's allocation model instead.

1. The setup: an 18 ms binary, a sub-5 ms goal, and a stale number on the books

The command-line binary at the center of this investigation runs in 18.2 ms on Darwin — a figure two different implementations now share: a retired, hand-tuned build that used every optimization trick available, and its plain, idiomatic replacement, which matched it exactly once several versions of unrelated toolchain work landed underneath it [MEASURED]. Against a sub-5 millisecond target, that leaves a gap of roughly 13 ms to account for and close.

For most of this investigation's life, the standing explanation for that gap was a plan document several versions old: process startup and runtime initialization were the suspects, with a figure of roughly 2.2 ms attached to "runtime init" specifically. A workstream had been designed and then shelved around that number — a pre-warm scheme, the general idea being: if a fixed 2–plus milliseconds gets paid on every single invocation just to get the runtime's internal machinery on its feet, keep a warm copy of that machinery around and skip paying it again. It is a sensible plan for a real cost. The question this article answers is whether that cost was ever real.

Term: pre-registration

Pre-registration means writing down what you predict a measurement will show — with numeric pass/fail bounds — before you run the measurement, and committing that prediction somewhere it can't be quietly edited afterward. Example: instead of running a benchmark and then explaining whatever number comes out, you write "I predict X falls between 2 and 4 milliseconds" into a script's comment header, run the benchmark, and report the actual number next to that prediction whether it lands inside the bounds or not. The entire point is that a miss becomes a recorded finding — something you have to explain and act on — rather than a number you quietly reinterpret after the fact to fit whatever story you already believed.

2. The move: both machines staked a falsifiable claim before measuring

Rather than re-run the timing and write the explanation afterward, both benchmark seats pre-registered predictions sourced from the cold-start literature, before either machine took a single new measurement.

The Linux seat commissioned a literature brief first [SOURCE] and staked its prediction directly against it: "image load+linking <15% of 18.1ms; runtime init largest block" — consistent with the brief's own falsifiable prior for a warm-cache, ~3.2 MB binary linking roughly five shared libraries on modern hardware:

The brief was explicit about what would falsify its own prior, in its own words: "bare spawn >4-5ms ⇒ anomalous linking (check readelf -r, BIND_NOW); init-minus-spawn >8ms ⇒ snapshot techniques are the fix and OpenSSL constructor init is suspect #1; compile-lane dominance ⇒ CDS-style caching, not linking work." Every one of those is a number, not a vibe — exactly the point of pre-registering.

The macOS seat did the same thing independently, committing three numbered predictions directly into the header of the benchmark script that would produce the results, dated 2026-07-27 ~00:45 PDT, before any timing ran [MEASURED]: 

P-D1: cell1 (image load + dyld, C no-op control) < 3 ms.
P-D2: cell2 - cell1 (hey runtime init + say) = 2-4 ms.
P-D3: cell4 - cell2 (the gpi WORKLOAD) >= 60% of the full cell —

Read what that last line already concedes, written before a single hyperfine run: the script's own author expected P-D2 (2–4 ms of runtime init) to fail, and said so in the same breath as predicting it — because Linux's own decomposition, run earlier the same night, had already found the init-heavy prior false on its own hardware. Darwin's run was staged explicitly as an independent replication of that refutation, not a fresh guess. That is what pre-registration looks like when it is being used honestly: the prediction on paper (2–4 ms, sourced from the literature) and the author's private expectation (it will miss) are allowed to disagree, and both are on the record before the number comes in.

The reference points the Linux brief cited for context matter here too, because they establish that the sub-5 ms target was never a fantasy [SOURCE]: on a 2018 i5-2400S, the bdrung/startup-time benchmark measured C at 0.26 ms, Go at 0.41 ms, and Rust at 0.51 ms cold-start — while Python3 took 25.8 ms and Ruby 32.4 ms. Sub-5 ms is comfortably attained by every compiled runtime measured in that survey. The 18.2 ms binary under investigation here compiles to native code; if it behaved like the compiled-runtime column, the goal was always reachable. The question was only ever where the extra milliseconds were actually going.

3. The kill: both machines watched the same prior die

Linux measured first. Its four-cell decomposition found startup+init at 0.9 ms of a 13.2 ms cell — 7% — with runtime init specifically, inside that 0.9 ms, reading as approximately zero [MEASURED]. Not "smaller than expected." Zero. The "runtime init is the largest block" half of its own pre-registered prediction was refuted on its own hardware, the same night the prediction was written.

Darwin's run, staged explicitly to check whether that refutation would reproduce independently rather than be a one-machine fluke, ran in its own quiet window — load1 2.2–2.3, the first quiet stretch of the night [MEASURED]:

Source: docs/PERFORMANCE-FINDINGS.md, entry dated 2026-07-27 ~03:10 PDT ("QUIET CELLS"). [MEASURED]

Cell1, the bare C no-op that pays only for the operating system loading an executable and the dynamic linker resolving its shared libraries, measured 1.2 ms. Cell2, the runtime's own no-op — everything cell1 pays, plus whatever the runtime's startup machinery does before it can even print one line — measured 1.1 ms. Subtracting gives runtime init a cost of essentially nothing: statistically indistinguishable from zero, and if anything slightly negative, which is what "−0.0 ms" is reporting — not a negative cost in any physical sense, but a difference small enough that measurement noise alone explains the sign. Two independently-built binaries, on two different machines, on two different operating systems, agreed: the milliseconds the plan blamed on runtime initialization were never being spent there.

Why the literature expected otherwise

The 2–6 ms init estimate wasn't invented casually. OpenSSL's default cryptographic provider initializes lazily on first use as of 1.1.0 [DOCS] — unless something in the linked binary forces a constructor to run eagerly at process start, which is exactly what cell2 minus cell1 was built to catch. A FIPS-mode provider's self-tests can cost roughly 15 ms per process when active [SOURCE] (cited here only as the scale of what provider initialization can cost, not as a claim this binary uses FIPS — it doesn't), and Node.js 17 shipped a real-world regression where OpenSSL-3 environment parsing turned an empty-script run from 115 ms to 215 ms [SOURCE]. Eager, expensive init is a documented failure mode elsewhere. It just isn't what's happening here: the measurement says this binary's constructors, OpenSSL's included, are not forcing eager work on the hot path.

The stale plan number — roughly 2.2 ms of runtime init — is now dead on both platforms, measured independently, in the same 24-hour window. And the pre-warm workstream that number justified has nothing left to do its job on: you cannot pre-warm a cost that measures as −0.0 ms. The workstream's premise didn't fail an experiment; it evaporated the moment the experiment ran.

4. The subtractive four-cell design

None of the above works unless the measurement design is trustworthy on its own terms, so it's worth walking through what actually makes cell2−cell1 mean "runtime init" rather than "whatever noise happened to be on the box that minute."

Term: subtractive measurement

Subtractive measurement means never trusting an absolute timing number on its own, and instead always reporting the difference between two measurements that share every cost except the one you're trying to isolate. Example: instead of asserting "runtime init costs 1.1 ms" from cell2 alone — which also includes process spawn and dynamic linking, and would be wrong if the box were under different load than when cell1 ran — you build a second binary (cell1, the bare C no-op) that pays every cost cell2 pays except runtime init, and report cell2 − cell1. If both cells were measured under the same ambient conditions, whatever is common to both (spawn cost, disk cache state, the machine's current load) cancels out of the subtraction, even if you mismeasured the absolute numbers by an identical amount in both directions. The four cells in this investigation (C no-op, runtime no-op, compile-only, full workload) exist specifically so every reported cost is a difference of two adjacent cells, not a raw number trusted on its own.

That's also why cell4−cell2, not cell4 alone, is reported as "the workload": cell4 (the full binary) still carries the same spawn-and-init cost cell2 measures, so subtracting cell2 out is what isolates the 17.1 ms that the package-index generation logic itself is responsible for. Every number in the table above is a subtraction, by design, for exactly this reason.

Term: the dead-binary trap

The dead-binary trap is what happens when a benchmark measures a binary that exits cleanly (return code 0, no error) without actually doing the work it's supposed to be timing — producing a fast, clean-looking, completely meaningless number. Example: if the workload binary in cell4 had a stale build, a broken code path, or simply crashed past its first line while still returning exit code 0, hyperfine would report a beautiful, tight, fast timing for a program that generated nothing. The guard against it here is explicit and runs before every timed cell: the workload's output file is deleted, the binary is run once outside the timing loop, and the script hard-fails ("gpi DEAD") if that output file doesn't reappear with non-zero size. Only once liveness is asserted does the actual hyperfine timing run. A fast dead binary is worse than a slow live one, because a slow live one at least tells you something true.

That liveness assertion is not decorative caution; it is load-bearing for every claim in §3. The exact guard, taken directly from the benchmark script [MEASURED]: 

# liveness: gpi must recreate its output (dead-binary trap)
cd "$REPO"; rm -f packages/index.html; "$S/gpi-438a-postmake" >/dev/null 2>&1
[ -s packages/index.html ] || { echo "gpi DEAD"; exit 1; }

Term: ratio control (the ruby lane)

A ratio control is a second, unrelated benchmark run alongside the one you actually care about, specifically so ambient drift — the box getting busier or quieter between runs — shows up as a moving number you can see, instead of silently contaminating your real result. Example: this project's CLI benchmark always runs a Ruby control lane next to the two Hey lanes it's actually studying. On one occasion, box load jumped from roughly 4 to 12 between two benchmark windows, and the Ruby control's absolute time inflated from 123.8 ms to 179.3 ms right along with it — but the ratio of the Hey binary lane to the Ruby lane stayed at exactly 0.150 in both windows. Because a completely unrelated, unchanged program moved by the same proportion, the conclusion was "the box got busier," not "the toolchain regressed" — a call that would have been impossible to make with confidence from the Hey numbers alone. Put the three pieces together and the method is what actually earns the right to say "runtime init costs −0.0 ms" instead of "our benchmark returned a small number this time": every reported cost is a subtraction of two cells that share their ambient conditions, no cell is trusted until it proves its binary actually ran, and a third, unrelated lane confirms whether any given run's absolute numbers reflect the toolchain or just the moment the box happened to be in.

5. What could not be verified

The literature brief that supplied the original prior was explicit about its own sourcing limits, and that disclosure is carried forward here unedited rather than quietly dropped, for the same reason the sibling article in this series makes the same choice: a brief that only reports what it's sure of is not more credible than one that shows its gaps — it's just quieter about them.

Solidly grounded

The bdrung/startup-time compiled-language reference numbers (repo, publicly runnable); the OpenSSL lazy-default-provider behavior as documented since 1.1.0; the FIPS self-test cost scale and the Node 17 OpenSSL-3 regression, both publicly reported incidents; every [MEASURED] number in §3 and §4, produced on this project's own two boxes with the liveness and ratio-control guards described above.

6. The payoff: three roads reached the same door

With runtime init dead as a cost center on both platforms, the sub-5 ms road can only run through one place: the 94% of the cell that the workload itself occupies — the package-index generation logic's allocation model, not process startup. That is not a new idea invented to fill the gap; it is where the pre-registration in §2 already pointed, in the cell script's own words, written before the number came in: "the mass is the workload, the sub-5ms road is the allocation model (stage c), same door as Q1."

"Same door as Q1" is the detail worth sitting with. The same night, from a completely different angle — a per-access allocation probe rather than a process-startup decomposition — this project's separate access-decomposition work was independently finding that the fixed, per-access boxing machinery inside the runtime, not the container being accessed, dominates lookup and construction cost, with a large 4,096-element case running at clone counts around two per element before optimization [MEASURED]. Two investigations, run the same night for different reasons on different instrumentation, arrived at the same destination: the cost worth chasing is what the runtime does per allocation, not what it does at process boundaries. Three roads — Linux's Q3 decomposition, Darwin's independent replication of it, and the separate access-decomposition probe — and one door.

What made this collapse fast rather than slow is the whole point of the article, not a footnote to it. A wrong prior sitting quietly in a planning document can steer a quarter of a roadmap before anyone re-checks it, because there's no moment at which it's obligated to be tested against a number. Pre-registration removes that grace period: the prediction and its falsification bounds go on the record together, before the measurement exists to argue with, so a wrong prior gets exactly one benchmark run to survive. This one didn't survive its first run on either machine, and the record shows both machines saying so in the same afternoon — MISS, stated as such, not smoothed into a footnote. The pre-warm workstream is not paused pending further study. It has nothing left to warm.

Glossary

pre-registration
Committing a falsifiable prediction, with numeric pass/fail bounds, before running the measurement that will test it.
dynamic linking
Resolving a program's calls into its shared libraries at load time (or lazily, on first use) rather than baking every library's code into the executable at compile time.
subtractive measurement
Reporting the difference between two measurements that share every cost except the one under study, so shared measurement error and ambient conditions cancel out.
the dead-binary trap
A benchmark measuring a binary that exits cleanly without doing its actual work, producing a fast number that means nothing; guarded against by asserting the binary's output before timing it.
ratio control
An unrelated benchmark lane run alongside the lane under study, so ambient load drift shows up as a moving absolute number with an unchanged ratio, rather than contaminating the real result silently.
runtime init
Whatever a program's own startup machinery does before user code runs, beyond what the operating system's process spawn and dynamic linker already pay for.
cold-start cost
The total wall-clock time from process launch to a program's first useful output, with no warm caches or persistent runtime to amortize the cost across repeated invocations.
