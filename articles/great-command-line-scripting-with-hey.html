Great Command-Line Scripting with Hey

One job, two implementations, one rule: the outputs must match to the byte. On today's toolchain (v0.99.410a) the Hey version builds a documentation index 5.2× faster than the Ruby it was ported from — a smaller number than this article carried yesterday, and smaller on purpose.

TL;DR

  • 24.2 ± 0.9 ms vs 125.2 ± 2.4 ms — 5.2× faster than Ruby, rendering a 14-package documentation index on a quiet Apple M-series laptop, 20–30 runs, byte-identical output, no build step.
  • Idiomatic against idiomatic. The Ruby is plain Ruby nobody tuned, so the Hey racing it is plain Hey nobody tuned: a structural mirror, method for method. We retired our own hand-optimized version from the headline. It was faster.
  • A benchmark without an output-parity gate is a wish. Ours caught an optimization that made this program faster and wrong, and a "record" 2.3 ms result that was a dead binary timing its own death.
  • Disclosed weakness: the port is ~25% slower than the tuned version we retired, and the Ruby could be tuned the same way. 5.2× is like-for-like, not a ceiling for either language.
  • Falsifiability: both implementations are in this repository, the harness below produced every figure, and each release is a dated row below — new measurements add rows rather than replacing a headline.

Addendum — 2026-07-26 (v0.99.422a–426a)

The toolchain kept landing fixes after this article's numbers were taken, and the dated-row promise above holds: on a quiet box at v0.99.426a the same parity-gated harness reads ruby 124.0 ± 1.7 ms / Hey script 22.6 ± 0.3 ms / Hey compiled 19.8 ± 0.5 ms — the compiled lane is now 6.3× Ruby and sits within 1.6 ms of the hand-tuned version this article retired (19.8 vs 18.2 ms) while using none of its tricks. The prediction this article staked — "delete the optimizations and get the speed back from the toolchain" — is most of the way to true, from compiler landings alone, with the same byte-identical output gate on every run.

How to read these numbers

Apple M-series laptop, macOS, quiet box — nothing else running, ambient load checked before each cell. Timings from hyperfine, a runner that repeats a command and reports mean ± standard deviation: --warmup 3, 20–30 runs, same 14-package tree, fixed PACKAGES_INDEX_GENERATED_AT in every lane. Each lane deletes its output, asserts it came back non-empty, and diffs it against Ruby's before any clock is trusted — never an exit code of 0 alone. Numbers off a loaded machine are lower bounds; none here are.

Why this benchmark compares idiomatic to idiomatic

Yesterday this article reported 5.46×. The Hey it measured had been hand-optimized for speed: builtins-only inner loops, work hoisted out of the comparator, a worker pool tuned against the clock. The Ruby it beat is plain idiomatic Ruby nobody has ever tuned.

That is not a fair fight. Anyone who can hand-optimize the Hey can hand-optimize the Ruby, and a comparison only means something if both sides are written the way people actually write them. So the canonical script is now an idiomatic port — a rewrite mirroring the original's structure instead of chasing the clock — and the headline comes from that. It is slower, and that is the point. Keeping the faster number would have been the more flattering choice and the less honest one; hiding it now would be its own dishonesty, so it stays below.

The port keeps --workers N (default 4), so fan-out is priced in the table too: serial is 31.4 ms, making the worker pool worth roughly a quarter.

The row worth staring at is the compiled one. Building the readable port gets to 21.1 ms — within about three milliseconds of the hand-tuned version we retired, which had builtins-only inner loops and a comparator rewritten against the clock. Nearly everything that hand-optimization bought here can be had instead by typing heyc build and keeping the code that reads like the Ruby it came from. That is a better trade than the one this article recommended yesterday.

Both programs — the Hey and the Ruby — walk a package directory, natural-sort every versioned docs/ directory and the Markdown and HTML below it, and render one static index page. A port is the cleanest benchmark a small language has and the easiest to cheat at, since most accidental speedups come from quietly doing less. Hence the one condition on every lane: same timestamp in, identical bytes out.

Hey can read like Ruby

True before the rewrite, more true now, because the port mirrors the Ruby rather than trying to beat it. Ruby has 22 methods in 313 lines; the port has 24 functions in 523, and the names line up almost one-for-one — digit_run, trim_leading_zeroes, compare_digit_runs, sorted_unique, relative_path, package_section, render_page, on down the file. Only worker_count and package_tasks have no Ruby counterpart. 

private fn sorted_unique(paths)
  return paths.uniq.sort(PackagesIndex.compare_paths)
end

private fn linkable_files(files)
  let linkable = []

  for path in files
    let lower_path = Text.lower(path)
    if Text.ends_with?(lower_path, '.md') or Text.ends_with?(lower_path, '.html')
      set linkable = [...linkable, path]
    end
  end

  return PackagesIndex.sorted_unique(linkable)
end

With .map(fn, workers: n).collect(), %qq(...) interpolation and heredocs also on hand, a Ruby programmer reads the script cold — most of the argument for Hey as a scripting language.

The ergonomics tax, stated honestly

Identical behaviour costs 1.67× the lines, and note the direction of travel: the retired tuned version was 561, so writing the honest port made the file both slower and shorter. Some of the tax is Hey's explicitness, most is workarounds for toolchain gaps that have tickets. Today it is real; price it in.

The parity gate

The thesis, and it outranks every number here: a benchmark without an output-parity gate is a wish. Two receipts from this program.

The first optimization pass rewrote the comparator to use byte_at(string, i). It compiled — and silently returned 0 for every string argument, being a Bytes-value operation. Every path compared equal to every other, the sort collapsed into a no-op, and the benchmark got faster and wrong: the classic rewrite failure, arriving in the shape of good news. The byte-parity check caught it on the first run.

The second is worse, because the gate itself lied. The fastest result this project ever recorded was a 2.3 ms binary. It was a corpse: exit 0, zero bytes of output, dead before the first line of user code, timing its own death. The parity check blessed it, because it never deleted the output file first and so compared the one left by the previous lane — a dead program passing a correctness gate by reading a ghost. My bug, and the reason the harness below deletes first. That autopsy and four more silent-failure classes are in the case file on the Ruby port that ate 50 GB of RAM.

The most expensive line in a CLI program is its first stdlib call

The first delegated stdlib call in a process — a call the compiled program hands to the interpreter — costs about 6 ms. Every call after it costs 54 µs. Against a 26 ms budget, that is a fifth of the runtime. Not theory: a 12-line argument-validation helper added to this script made it 5 ms slower, because its one Text.int_token? call happened to be the process's first delegated call — validating a default we had written ourselves. It now returns early instead. Probe: bench/probes/cli-startup-call-cost.hey. For command-line authors this is the most useful number here.

The three rules that keep Hey fast

Rule 1: stdlib freely outside hot loops, builtins only inside them

A stdlib call from compiled code costs roughly 54 µs through the sidecar once the process is warm; natively lowered calls cost under a microsecond. At that price ordinary use is free, and the rule bites only in the innermost per-item loop.

The port declines to follow it and prices the decision for you: its comparator runs thousands of times per sort and calls Text.lower and Collections.compare freely, because that is what the Ruby does. The retired version pushed that loop onto bare builtins and never left compiled code. The gap — 24.2 ms against 18.2 — is the price of the rule: about 25%, available in either language to anyone who wants it.

What this rule used to say, and why it changed

An earlier version of this article said: avoid stdlib calls in hot loops, full stop. That was correct and is now wrong, the more interesting kind of obsolete. Before v0.99.402a a stdlib call from compiled code spawned an interpreter to service it — about 7 ms, so one careless Text.trim over a thousand items cost seven seconds. Four orders of magnitude does not refine a rule, it retires one.

Rule 2: measure output before you measure time

Delete the output, run, assert it came back, compare bytes, and only then start a clock. Both of this project's most memorable numbers — the comparator that sorted nothing, the binary that did nothing — were speedups.

Rule 3: parallelism is worth measuring in both directions

.map(fn, workers: n) hands each item to a worker pool, and this article has now published both verdicts on the same 14 packages. On the tuned script fan-out lost: each render was so cheap that scheduling cost more than doing the work in order, so the default was --workers 1. On the port each render does more and the same fan-out wins — 24.7 ms at 4 workers against 31.4 at 1 — so the default is 4. The machine did not change. Fan-out is a property of how much work an item does, so you re-earn it by measuring whenever the code moves.

A harness that cannot lie to you

All of it reduces to one script whose ordering is load-bearing — rm before run, assertion before comparison — so a program producing nothing fails here instead of posting a record. 

set -eu
STAMP=2026-07-25T00:00:00Z

lane() {                      # $1 = label, $2.. = command
  rm -f packages/index.html
  PACKAGES_INDEX_GENERATED_AT="$STAMP" "${@:2}" >/dev/null
  test -s packages/index.html || { echo "$1: NO OUTPUT"; exit 1; }
  cp packages/index.html "out.$1.html"
}

lane ruby   ruby ./generate-packages-index.rb ./packages
lane script ./generate-packages-index.hey ./packages
lane binary generate-packages-index ./packages

cmp out.ruby.html out.script.html
cmp out.ruby.html out.binary.html

hyperfine --warmup 3 --runs 30 \
  'ruby ./generate-packages-index.rb ./packages' \
  './generate-packages-index.hey ./packages' \
  'generate-packages-index ./packages'

When a lane dies silently — exit 0, no output — suspect the caches before the compiler: a racy publish can mint a corrupted entry that deterministically produces do-nothing programs, and a dead run writes its own entry into the run cache. 

rm -rf "$HEY_COMPILER_BUILD_DIR/compiler-sidecars"   # poisoned sidecar entries
rm -rf "$HOME/.cache/hey/run"                        # the run cache they poisoned

Where Hey loses

Small-to-medium command-line work is the honest scope. On the sibling source-zip port, same box: Hey 66.5 ms against Ruby's 153.3 at 500 files, a tie at 2,000, a bad loss at 8,000 — 2.16 s against 672 ms, because building large lists is still quadratic in time. Long-list batch work is Ruby's; let it have it.

Glossary

hyperfine
A benchmark runner: repeats a command, reports mean ± standard deviation.
idiomatic port
A rewrite mirroring the original's structure rather than tuning for speed.
byte-parity
Comparing outputs byte for byte, not "looks right".
sidecar
A long-lived helper process replacing per-call process spawning.
delegation
A compiled program handing a call to the interpreter instead of running it.
builtin
A primitive the compiler lowers straight to machine code.
worker pool
A fixed set of workers taking items from a shared queue.
exit code
The integer a process returns on termination; 0 means success.
run cache
Where the toolchain stores artifacts for scripts already run.
quadratic
Cost growing with the square of the input.
