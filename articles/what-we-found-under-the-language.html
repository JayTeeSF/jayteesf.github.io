What We Found Under the Language

For months the maintainer asked a version of the same question: does this language have architectural problems, or just bugs? Every time, the honest answer we had was “here is the bug we just fixed.” On the night of 1 August we stopped investigating defects and told four agents to enumerate instead — not “find problems” but “list every place that decides X.” The answer came back before morning. The largest part of it is that the thing users compile with does not have a parser.

TL;DR

  • The verdict: this needs a new front end, not more fixes. The front end that ships carries every expression — every a + b * c — as an opaque string, and two later stages each re-read that string character by character to work out what it meant. There is no token type anywhere in the tree; a repo-wide search for one returns comments, plus a handful of unrelated uses of the word in libraries that have nothing to do with compiling.
  • The same decision is made in dozens of places and they disagree. Operator precedence is decided at at least 45 sites across 5 mutually inconsistent notions of what precedence even is. What counts as a letter in a name is decided by 16 separate scanners, and no two of them agree.
  • Keyword arguments are used about 1,900 times and are not a feature. No front end has a rule for them. They work because two built-in functions re-parse their own raw argument text — one of them by testing for a single hard-coded option name. A function you write yourself cannot take one.
  • Disclosed weakness: this was a reading, not a run. No build was executed — a release battery had the machine. The grammar report alone flags 36 of its claims as needing a run to confirm, and where the reports disagreed we left the disagreement standing rather than picking a winner.
  • Reproduce the headline in one line: search your own compiler for its token type. If the grep is empty, every stage downstream is re-deriving the same facts from raw text — and they will not all agree.

For months, the answer was always a bug

We have a good record on defects. Fifty-eight were catalogued and classified last week, each with how it was found and what would have caught it earlier. That work is useful, and it never once answered the maintainer's question, because a defect investigation is a sample of size one. Fifty-eight in a row tell you fifty-eight things about fifty-eight lines.

So the instruction changed. Not “go find what is wrong” — four agents were each given a complete, boring list to produce. Every operator, in every implementation. Every construct one emitter refuses. Every rule the grammar actually enforces. Complete lists, with a file and line number beside every cell. Six things fell out, ordered here by how much they should surprise you.

Finding one: there is no parser

Parser

The stage that reads source text once and turns it into a tree that says what the program means. Everything after it works on the tree and never looks at the text again. That is the point: the text is read once, so there is only one opinion about it.

The front end users actually compile with reads a line, decides what kind of statement it is, and hands the expression part downstream as text. The meaning-and-types stage scans that text for operators to guess at types. The LLVM emitter — the stage that writes the low-level text a toolkit called LLVM turns into machine code — scans the same text again to decide what instructions to emit. Two independent readings of the same characters, by two separately written pieces of code, with no shared definition of what a - is.

Above all of that sits something stranger. Before any of this begins, the source is rewritten four times, and one of those passes deletes lines outright. Nothing we could find maps the surviving lines back to the originals. That is the best explanation we now have for a complaint we have carried for months — the line number in an error message is not reliably the line the error is on — and it is one of the 36 claims that report still has queued for a run. There has never been a column number either, because there is nothing smaller than a line to attach one to.

Finding two: keyword arguments are used 1,900 times and are not a feature

Programs across our corpus write things like Jobs.define('Reliable', Worker, count: 2, capacity: 8). A scan finds roughly 1,900 such argument sites. There is no rule for name: value in any front end. None. The general argument evaluator splits on commas and hands each piece to the ordinary expression evaluator, which has no idea what a colon is.

It works because two built-in functions take their arguments as one raw string and parse the options themselves — one of them by testing whether the text starts with the literal characters workers:. That is the mechanism, described in full.

The consequence is worth sitting with: a function a user writes cannot take a keyword argument, because there is nothing to give it one. That last sentence is read from the source and is one of those 36 claims queued for a run — it is the single one we would most like to be wrong about. Either way, the corpus already depends on syntax the language does not have.

Finding three: one decision, forty-five places, five different answers

Precedence is the rule that makes 2 + 3 * 4 equal 14 and not 20. In a normal compiler it is a number in a table. Here it is the shape of a call chain — which function calls which — and there are five different chains, so there are five different notions of what precedence is. Counting every site that decides it gives at least 45. Splitting an expression on a plus sign happens at 16 places in one file alone.

The pattern repeats at every size. Sixteen scanners decide whether a character belongs to a name, and no two agree: four accept an exclamation mark, some accept a dot, one accepts a dollar sign. Four lists say which keywords open a block, holding 5, 13, 11 and 12 keywords — one list knows a keyword no other layer has heard of. Eleven separate places decide whether a leading - is a subtraction, a negation, or part of a number, and nothing decides it once. None of these is a bug. Each is a place where a future bug is already paid for.

Finding four: the shipping emitter cannot see a+b

The LLVM emitter that plain heyc build uses — the Hey-written one, and the primary shipping path — finds operators by looking for a space, then the operator, then another space. Every one of its scanners does this. So a + b is an addition and a+b is not: the second is invisible to the addition scanner and falls through as if it were one strange name. Of the four other implementations, three split on the bare character and do not care about spaces; the fourth requires spaces too.

Nobody decided that whitespace is significant in Hey. It is significant anyway, in one implementation, as a consequence of how the scanners were written. It is also the single largest mechanical change on the open-questions list: answering “no, spaces do not matter” changes the shape of five scanners at once.

Finding five: two of the five implementations are the same file

Five separate implementations of Hey's expressions exist today. Two of them are the interpreter — the thing that runs a program without compiling it — and the older LLVM emitter written in C, and we have spent months describing those two as independent implementations that check each other. Line 4 of the C emitter is #include "hey_repl.c". It includes the interpreter. The compiler builds the two as a single file, so every function in the interpreter is already available, by name, inside the C emitter.

Their duplication is therefore not structural. It is voluntary — and the code says so out loud: one file carries a comment reading “both tables must stay identical” directly above a verbatim second copy of a function that same file already contains. That is good news. Voluntary duplication can simply be deleted, and deleting it is the cheapest possible test of whether one shared operator table would work.

Finding six: fifteen things the shape cannot hold

One of the four reports closed by asking a different question: not what is wrong, but what this architecture structurally cannot express. Fifteen answers. Seven of them:

Cannot expressWhat that means in practice
A tokenNo unit smaller than a line exists, so no error can ever carry a column number.
Precedence as a numberPrecedence cannot be queried, tested or printed — only executed.
Associativity — whether a - b - c groups from the left or the rightNowhere written down. It falls out of whether a scan loop stops at the first operator it sees or the last. Four independent choices exist.
Balanced delimitersAll three depth counters count up and down without matching, so (] balances.
A keywordKeywords are a text prefix test including the trailing space. letters = 1 is safe from let only because of that space.
Two spellings of one operatornot and ! are unrelated string tests everywhere — which is how the shipping emitter came to implement one and not the other.
“Invalid” versus “unsupported”Every refusal returns the same not-handled result and falls back, so a broken program and an unimplemented one are told apart only by accident.

The delimiter row deserves a second read. Whether (] is an error is now a decision someone has to make on purpose.

Why fifty-eight investigations in a row found nothing

Here is the part that generalises past our project. Every one of those defect investigations was competent, and every one produced a fix, a test and a lesson. The sum of all fifty-eight still contained no information about the shape of the system, because sampling cannot find an architecture problem. You cannot sample your way to “there are 16 of these and no two agree.” You have to count all 16.

The same failure showed up inside the project at every scale, which is how we know it is not a story about carelessness. A verified memory-leak fix probed five expression shapes, reported all five balanced, and shipped code that still leaked where users run it — because none of its five shapes put arithmetic inside an actor, and neither did any of the 90 reference outputs guarding the change. What caught it was not a sharper test. It was a survey of 106 programs: enumeration, not sampling. Elsewhere, a report said five sites needed fixing; there were nine, and the ninth kept the defect alive after the other eight were repaired.

Five probes that all happen to hit the one path that works will produce a clean report every time, and the report will be honest. That is what makes this failure mode expensive: nothing in it looks like a mistake while it is happening.

What follows, and what this does not yet prove

Six findings, one conclusion: the work is not a longer defect queue, it is the three missing stages at the front of that first diagram. Tokens once. Tree once. Names resolved once. Then the 45 precedence sites have somewhere to collapse to, the 16 name scanners become one, and “do spaces matter?” becomes a decision recorded in one place instead of an accident repeated in five.

What is not proven: any of it by execution. All four reports were read from source with the machine busy, and 36 claims are queued as needing a run before they can be called facts. The reports also disagreed with each other, and we left that standing: one counted six operator scanners in the shipping emitter, another counted thirteen; one was briefed that there were nine name scanners and found 16. Where they conflict, the conflict is the finding.

The uncomfortable version: none of these six facts required a clever technique. They required somebody to make a complete list. We had spent months asking a question only a complete list can answer, and answering it with samples.
