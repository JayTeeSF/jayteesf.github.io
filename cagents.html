Projects own work. Channels own conversations.

The Maintainer is no longer the universal message router. Project membership says who belongs to a project. Channel membership says who participates in one conversation. DMs address a person or agent. Maintainer-issued grants still govern project-internal peer DMs where required. Every durable message remains Git-backed.

This is the coordination/data-flow page, not the component architecture. See system architecture for clients, Cloud, repository workers, generic_cagents, Git providers and runtime boundaries; see how-to for commands.

Four independent authorities

Global actor identity
agents/<actor>/START.md or humans/<actor>/START.md.
Project membership
projects/<p>/participants/<actor>.ref. Governs project participation and send --to all.
Channel membership
projects/<p>/channels/<c>/members/<actor>.ref. Governs channel posting and mailbox delivery.
DM permission
Cross-project if one endpoint belongs to the addressed project; project-internal peer DMs still honor grant policy.

Joining a channel grants only that conversation. It grants no project tasks, sessions, subagent state, other channels or unrelated messages. Project membership likewise does not auto-subscribe an actor to every channel.

NO projects/hey/participants/mmeow-agent.ref

This is why the Maintainer is no longer a communication bottleneck. The Maintainer still owns project policy and can issue project-internal peer-DM grants, but joined channel members communicate through the channel directly.

DMs are different

# cross-project DM
external-reporter ─────────► orchestrator
allowed because orchestrator belongs to addressed project

# two project peers
overseer ─────────► orchestrator
project-internal policy may require active Maintainer-issued grant

# joined channel
overseer ─► #engineering ◄─ orchestrator
no pairwise DM grant: channel membership is the authority
Communication permission ≠ command authority. Delivery permission does not make advisory input binding; role, project policy, decisions and delegation still determine precedence.

One post, per-recipient delivery refs

projects/hey/messages/posts/<sender>/2026/09/<post>.md
projects/hey/messages/mailboxes/<recipient>/unread/2026/09/<id>.ref

ack:
unread/<id>.ref → read/<id>.ref

Channel fan-out uses explicit channel member refs and excludes the sender. send --to all still means persistent project participants, not channel members.
