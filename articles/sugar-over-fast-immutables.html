Sugar Over Fast Immutables

Six language teams solved the same problem in the same way. Koka, Roc, Swift, Clojure, CPython, and Erlang all found a way to keep code that looks like it copies data on every change, while running like it copies nothing at all. Here is the trick, the paper that proves it holds up at 42 million insertions, and the ranked list of which part of it a young language like Hey should steal first.

TL;DR

  • Purely-functional Koka is within 10% of hand-mutated C++ std::map on a 42-million-insertion red-black tree benchmark — immutable-looking code, competitive with a human writing raw pointer mutation.
  • On that same benchmark, Java matches Koka's speed but needs about 10× the memory: 1.7 GiB versus Koka's 170 MiB.
  • Two specific compiler passes — reuse analysis and drop specialization — are worth more than 2× on their own: disable just those two and the identical Koka program gets more than twice as slow.
  • CPython 3.12 stopped compiling comprehensions as disposable nested functions and inlined them instead: 1.96× on a microbenchmark, 11% across the whole pyperformance comprehension suite, zero regressions elsewhere (PEP 709).
  • The thesis: you do not have to choose between a language that feels friendly and one that runs fast — the compiler can hide a fast mutable builder behind immutable-looking syntax.

The false choice

For a long time the deal seemed to be: write in an immutable style and pay for every "change" with a fresh copy of whatever you changed, or drop into mutation and lose the guarantee that made the immutable style worth wanting in the first place — that nothing you didn't touch can ever move out from under you. Framed that way, it was less a choice than a hostage negotiation.

Term: immutability

Once a value is created, it cannot be changed in place. Instead of editing it, you produce a new value and the old one is left exactly as it was. Example: in an immutable language, let a = [1, 2, 3] followed by let b = append(a, 4) leaves a as [1, 2, 3]; b is a separate, new list, [1, 2, 3, 4]. Anything else still holding a reference to a never sees a 4 appear in it. This makes programs far easier to reason about — but built naively, every "change" becomes a copy of the whole structure, which is exactly the tax this article is about avoiding.

Two more pieces of vocabulary make the rest of this precise. Most of what feels friendly about a modern language — pipelines, comprehensions, pattern matching, literal map updates — is syntactic sugar: syntax whose only job is to be pleasant to write.

Term: syntactic sugar

Syntax that exists purely for the writer's convenience. The compiler translates it into more primitive code before anything runs, and only the primitive code ever executes — sugar adds no new capability, only convenience. Example: a for x in list { ... } loop is sugar for a lower-level iteration call; nothing distinguishes the sugared program from the unsugared one once it's running.

The step that does the translating is lowering: the compiler stage where a convenient surface form is rewritten into something closer to what the machine actually executes.

Term: lowering

Rewriting one representation of a program into a different, more primitive one, at compile time, before any code runs. Example: the pipe operator a |> f(b, c) is lowered — rewritten before execution, not at runtime — into the ordinary call f(a, b, c). "Lowers to" and "compiles to" mean the same thing everywhere in this article.

Put those together and the question this brief answers is: can the sugar lower to code that runs as fast as if you'd written the mutation yourself? Six language teams — working independently, on different runtimes, for different reasons — landed on the same answer, and it holds up under a real benchmark, not just a demo.

The trick: a hidden builder

The shallowest version of the trick predates all of this: hide a mutable scratch structure inside a function that looks pure from the outside.

Term: transient / builder

A temporary, mutable structure that a function builds up privately, then freezes into an ordinary immutable value before returning it. The caller never sees the mutable phase, only the finished, safe-to-share result. Example: Clojure's into looks like it builds three separate immutable vectors one at a time; internally it opens one private transient vector, mutates it three times, and calls persistent! once to freeze it — the caller gets back an ordinary vector and cannot tell the difference.

Clojure's own rules for this are strict, which is exactly what makes it safe: a transient has a single owner, every mutating call must capture and use its return value (a stale handle throws rather than silently doing nothing), and persistent! is O(1) and kills the transient — reusing it afterward is an error, not undefined behavior. Both the freeze and the original build are O(1) because the transient shares structure with the persistent trie underneath; only the nodes actually touched get an internal "edit" marker. into and mapv use this internally, so a function that looks pure hides an internally-mutable builder for the duration of one call.

Erlang's small maps (32 keys or fewer) push the same idea into literal syntax. A small map is a flat, sorted array of keys plus a parallel array of values. Writing several keys in one literal update, 

M#{k1 => v1, k2 => v2}

lowers to one rebuild pass over the map, not one pass per key — "essentially constant regardless of the number of keys updated," in the documentation's own words. The sugar is a single literal; the lowering hides a batch rebuild that would look like ordinary mutation if you wrote it by hand. (Above 32 keys, Erlang switches representation to a hash trie, a real complexity cliff at the boundary — a useful precedent for any language considering a similar size-based switch.)

CPython's PEP 709 is the same story at the bytecode level. Before Python 3.12, every comprehension — [x*2 for x in xs] — compiled to its own single-use nested function: a frame push and teardown on every execution, even though the function is called exactly once and thrown away. 3.12 inlines the comprehension's bytecode directly into the enclosing function instead: 

# before 3.12: a hidden one-shot function, called once, discarded
def <listcomp>(.0):
    result = []
    for x in .0:
        result.append(x * 2)
    return result
squares = <listcomp>(iter(xs))

# 3.12: the same bytecode, inlined — no function, no frame
squares = []                 # LIST_APPEND builds directly on the value stack
for x in xs:
    squares.append(x * 2)    # (illustrative — the real form is bytecode, not source)

A new opcode, LOAD_FAST_AND_CLEAR, handles variables the comprehension shadows without needing a closure at all. The builder — the list being appended into — lives only across the loop and is handed back once, reified exactly one time. Measured: 1.96× on a microbenchmark and 11% across the pyperformance comprehension suite, with no regression anywhere else. Elixir's for compiles through the same kind of pipeline and even exposes the builder directly with an opt-in :reduce clause, turning the hidden accumulator into a visible fold when you ask for it. Erlang's own list comprehension goes one step further: the compiler lowers [E || X <- L, Cond] to a recursive function that conses forward, so list order falls out of the recursion structure with no reverse and no accumulator at all.

Every one of these examples shares one shape: a preallocated or cheaply-grown mutable accumulator, local to a single construction, never aliased anywhere else, turned into an immutable value exactly once. That is also, not coincidentally, the shape of the transient-lowering work already landing in Hey's own object and array literals.

The deeper magic: mutate only when nobody's looking

Hiding a builder inside one function call is the shallow version. The deep version does the same trick for every mutation in the program, decided at runtime by a single question: is anyone else looking at this value right now?

Term: reference counting

A bookkeeping scheme where every value carries a counter of how many places currently hold a reference to it. Copying a reference increments the count; giving one up decrements it; the count reaching zero means the memory can be freed immediately, with no separate garbage-collector sweep needed. Example: Koka's compiler inserts a dup call everywhere a value is duplicated and a drop call everywhere one is discarded, so a header word's rc field always reflects exactly how many live references exist: 

static inline void drop(block_t* b) {
  if (b->header.rc <= 1) drop_check(b);   // maybe free
  else b->header.rc--;                     // fast path
}

That is the mechanism behind Koka's Perceus (PLDI 2021) and the FBIP ("functional but in place") style it enables. Perceus is precise: ownership of every value is tracked linearly through the whole program — a "linear resource calculus," in the paper's terms — rather than scoped the way shared_ptr or Rust's Rc are. All of it is compile-time instrumentation, not a runtime garbage collector.

Three passes on top of plain reference counting do the actual work:

  • Drop specialization inlines the generic drop-or-decrement decision separately for each constructor at each match branch, and cancels adjacent dup/drop pairs. On the paper's own map example, almost every reference-count operation on the fast path disappears entirely — the count is 1 everywhere, the uniqueness check always succeeds, and the value frees immediately with no further bookkeeping.
  • Reuse analysis pairs a pattern that's being matched away with a same-size value being constructed in the same branch. It emits a check that returns either "not unique, do a real free-and-allocate" or the address of the old cell, unique, ready to reuse. Same-shape old cell becomes new cell, zero allocation, decided at runtime by one refcount == 1 check the compiler inserted ahead of time.
  • Reuse specialization skips rewriting fields that provably didn't change — a red-black tree rebalance that only touches the left pointer stores only that field.

This is where "immutable-looking code as fast as C++" stops being a slogan: on the paper's rbtree benchmark (42 million insertions, 6-core AMD 3600XT), purely-functional Koka lands within 10% of hand-mutated C++ std::map, and matches Java's speed at roughly a tenth of Java's memory (170 MiB versus 1.7 GiB). Disable reuse analysis and drop specialization and the identical program gets more than 2× slower — those two passes alone are worth that much. A cheaper, always-assume-shared atomic reference count costs 5% (rbtree) to 59% (nqueens), which is what buys the fast non-atomic path its keep. And Swift, which does something similar (below) but with weaker static guarantees, underperforms Koka on the same benchmark — evidence that the compile-time analysis is doing real work, not just the reference-counting runtime underneath it.

None of this is free at the representation level. Perceus needs every heap object to carry a header word with an integer refcount field, plus (in Koka specifically) a thread-shared sign bit in that same word — negative means shared, so use the slower atomic path; positive means uncontended, so use the fast one — and a saturating count for effectively-immortal objects so it never wraps. It also needs fully explicit control flow, so the compiler can determine every drop point statically, with no implicit non-local exits to hide from it.

Term: copy-on-write

Defer a "copy" until the moment something would actually mutate shared data, and skip it entirely if nothing else still holds a reference by then. Example: Swift's Array looks like a plain value type — let b = a reads like a full copy — but underneath, a and b share one buffer until either is mutated. Every mutating method calls isKnownUniquelyReferenced(&buffer) first: unique, mutate in place; shared, copy then mutate. A real copy happens only if something else is still holding on at the exact moment of the write.

Swift's COW is the library-level, opt-in version of Koka's is-unique check: the same "mutate only when nobody's looking" primitive, hand-authored per collection type instead of derived by the compiler for every value in the program. Roc takes a third position, closer to Swift's promise but Koka's ambition: its Morphic system does whole-program borrow/alias inference, trying to prove a value is never aliased so it can skip inserting reference-count operations at all, falling back to RC only where the proof fails — the inverse emphasis from Perceus, which inserts RC everywhere and then optimizes it away. Roc's own pitch reads identically to FBIP's: "array updates logically copy the array, but are automatically performed in-place when safe." At least one academic thesis is reported to explore grafting Perceus-style reuse onto Roc (unlinked in the source brief), because pure borrow inference alone leaves some of that reuse gain on the table.

What Hey adopts — near-term and long-term

Six teams, six different prices for the same trick. The question that matters for Hey isn't which is most elegant on paper, but which piece is cheapest to build first. Sorted by what it costs to build, not by how impressive the ceiling is:

Pipe |>NoPure compile-time rewrite: a |> f(b, c) → f(a, b, c), zero runtime cost

Near-term, needing no runtime changes at all: the transient-builder for object and array literals is already landing in Hey — Clojure's transients, PEP 709, and Erlang's comprehension lowering converged on that exact shape independently, which is a strong validation of work already in flight, not a new idea. Pipe, pattern matching with guards, with-chains, keyword-list sugar, and the Erlang-style batch update above are all pure compile-time rewrites on top of what Hey's compiler already has. String interpolation belongs on this list ergonomically, but it has a runtime prerequisite of its own — see the next section.

Long-term, each needing a new runtime primitive Hey doesn't have yet:

  • Morphic-style whole-program borrow/alias inference. No refcount field required in the common case — the highest ceiling of the three without touching the object header — but it is a substantial new compiler subsystem, not a small patch.
  • Swift-style copy-on-write per collection type. The same is-unique primitive as Perceus, hand-authored per type instead of compiler-derived. Needs a refcount field on the object header; buys little over full Perceus except that it can be built incrementally, one collection type at a time.
  • Full Perceus: reuse analysis plus drop specialization. The deepest, most general win — more than 2× on rbtree, within 10% of hand-mutated C++ — and the largest prerequisite gap: a refcount field on every heap object header, a thread-shared bit once concurrency arrives, compiler-inserted dup/drop everywhere via a whole-program linear-resource pass, and fully explicit control flow. The honest answer to "what does Perceus need that Hey lacks" is a new object header format plus a new whole-program instrumentation pass — not a small patch either.
  • Swift-style COW again, but positioned last on purpose: it needs the same header field as full Perceus and delivers less, so it only makes sense as an interim step if the full analysis is still far off.

The honest cost: naive lowering can be quadratic

Every trick above has one failure mode in common, and string interpolation is where it bites hardest. Elixir's rule is simple: "foo#{bar}" is exactly "foo" <> to_string(bar). That's fine for one substitution. Chain several together, though, and a naive lowering reproduces the same class of bug this project has already identified — and not yet closed out — in its own list-literal machinery: each <> allocates a full new string, so a chain of N interpolations does O(N²) work and holds every intermediate string in memory on the way, not just the final one. The sugar is harmless; the straightforward way of lowering it is not.

The fix has the same shape as everything above it: hide a builder. Instead of lowering straight to nested <> calls, lower to an iolist or rope — a list of fragments that gets joined exactly once, at the end, rather than re-copied at every step. It is the transient trick again, just for strings instead of lists or maps, which is why this item is ranked behind the transient-lowering work already in flight rather than ahead of it: it should reuse the same builder, not invent a second one.

Glossary

immutability
Once created, a value cannot be changed in place — only replaced by a new value.
syntactic sugar
Syntax that exists purely for the writer's convenience; the compiler lowers it to more primitive code before anything runs.
lowering
The compile-time rewriting of a convenient surface form into something closer to what the machine actually executes.
transient / builder
A temporary, mutable structure a function builds up privately, then freezes into an ordinary immutable value before returning it.
reference counting
A bookkeeping scheme where every value carries a counter of how many places hold a reference to it; the count reaching zero frees the memory immediately.
copy-on-write
Deferring a copy until the moment something would actually mutate shared data, skipped entirely if nothing else still holds a reference by then.
