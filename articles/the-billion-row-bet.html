The Billion-Row Bet

Last July, this project ran all one billion rows of the One Billion Row Challenge in 43.242 seconds on this machine. Then it deleted the code that did it — because the fast part wasn't Hey. The hot loop was a hidden native C routine, and “written in Hey” has to be true or it means nothing. The bet: earn that number back honestly, with immutable, zero-copy Hey and no hidden C anywhere.

Status: the mark is a retired, hidden-C result — nothing built on the immutable side yet

The all-immutable 1brc.hey this article bets on does not exist yet. What's real, dated 2026-07-27: reference lanes measured on this machine, the July figure and what actually produced it established from the project's own commit history, and a first honest look at how far today's all-Hey code sits from that mark.

1. The bet

TL;DR

  • We're betting that honest, immutable Hey can beat 43.242 seconds — a mark this project set in July with a hidden native C routine doing the work, then deliberately destroyed. A rule in this language says the code has to be Hey. The July hot loop was one C call per chunk that scanned, parsed and tallied a whole byte range at once. The rule won: that call was banned and deleted, and the number went with it.
  • This is Hey against its own ghost. Not a race against C, Python, or the world record — those stay on the chart as scenery. The mark to beat was set on this machine, on this file, by code wearing a Hey jersey over a C engine.
  • Disclosed weakness, stated first: today's ordinary Hey code, already immutable-style, projects months, not seconds — that is the true size of what the C routine was doing for us, and what we now have to build honestly (§4).
  • Falsifiable, on purpose: 43.242 s is the July era's own recorded full run — and it cannot be re-run, because the code that produced it no longer compiles here by design. Its rivals below were measured this week; the data file was lost to a tooling accident and regenerated. Every number traces to the project log.

Here's the wager, plainly. In July this project processed all one billion rows on this machine — 15 GB, 44,693 stations, the hard file — in 43.242 seconds. That isn't a target; it already happened. But it happened with a cheat we didn't fully own at the time: the entire hot loop was a single native C call per chunk that scanned, split, parsed and tallied a whole range of bytes at once, into a native table. Hey handed it chunk boundaries. C did the billion rows.

So the project killed it. A rule here says a Hey program has to be Hey; hidden native shortcuts make that claim false, so the call was banned, the code deleted, and the speed went with it — knowingly, at enormous cost. Today's honest all-Hey version projects months. The bet is whether we can earn 43.242 seconds back the honest way: immutable, zero-copy Hey, no hidden C, same machine, same file, beaten by any margin. There's a smaller stake riding along — the language's one mutable type, byte_buffer, an accidental output builder that now only formats the last 400 lines of results. If the immutable version doesn't need it, it goes too.

The world's numbers stay on the chart, but only as scenery. The fastest publicly known C we could measure on this file needs 18.8 seconds; a fast Python needs about 143. The official world record is 1.5 seconds — easier dataset, different hardware, not a fair comparator here. None of those are the bet. The bet is Hey against Hey.

2. What is 1BRC?

Term: the One Billion Row Challenge

The One Billion Row Challenge (1BRC, Gunnar Morling, January 2024) asks for exactly one thing: read one billion station;temperature text rows and print the minimum, mean, and maximum temperature per station, as fast as possible. The winning entries all leaned on the same handful of tricks — reading the file straight into memory instead of calling read(), scanning several bytes at a time instead of one, and skipping text allocation until the very last step.

3. Why we think we can make it

We measured where the time actually goes, and the real work is already fast. The scanning-and-comparing logic alone costs about 7 nanoseconds (ns, billionths of a second) per row on this machine — world-class pace. That 7 ns is buried under roughly a thousand times its own cost in memory bookkeeping. We don't need to invent speed; we need to stop paying for overhead the algorithm never needed.

That single measurement is what makes this bet winnable rather than romantic, and it took both machines to see it. The banned C routine's trick was fusing the whole scan into one native pass — but fusion is not what today's code is missing. Its scanning already runs at world-class pace; it is drowning in memory bookkeeping around every row. So the honest rebuild never has to re-cross the line the project drew. It has to stop allocating.

Most of the machine we need already exists. A fast 1BRC pipeline needs a handful of pieces: mapping the file without copying it, scanning it without copying it, parsing numbers without allocating, and fanning work across workers sharing one view of the data. Five of those six already exist in Hey, as immutable, zero-copy code. Only one real gap remains — accumulating results without copying the whole running tally on every row — and it's scheduled, not speculative.

We've done exactly this before, twice. The web server went from ~500 to over 120,000 requests per second the same way — measure, name, delete — in "From 500 to 100,000 Requests per Second." An idiomatic Hey port of a Ruby tool now matches the hand-tuned version it retired, and a separate Ruby port's own memory story — a 481× reduction, printed in public — is the same discipline on a harder problem. This team publishes bets before results, in public.

And we already know a fast program shape exists. Hey itself ran this benchmark, on this machine and data, in 43.242 seconds in July; that shape was then deliberately removed for breaking a rule the language keeps — a hidden native-code path the compiler's own integrity rule bans, with today's slow sort riding in as collateral in the same commit; the bet rebuilds that speed without breaking any rules, immutable and zero-copy, no hidden native code.

4. What we actually did

  • 2026-07-27 — What the mark actually was. Digging through the project's own commit history settled it: July's 43.242 s came from a native C scan-and-tally routine, removed wholesale when the language banned hidden native shortcuts — the sorting shortcut that now dominates today's code rode in as collateral in that same commit. Reference lanes measured this week: fastest known C, 18.8 s; fast Python, ~143 s. Today's honest all-Hey code projects months, which is the true size of the job the C routine had been doing. (An earlier 20.53 s prefix-extrapolated projection was refuted by that same full run — projections losing to measurements is this project's oldest lesson.) Those receipts were overwritten by later builds, and the data file was lost to a tooling accident; regeneration is underway from the same generator and station list. Locating the July-era implementation is next.

A few honesty notes: 43.242 s is the July era's own recorded measurement, not yet reproduced byte-for-byte, and is labeled as such everywhere it appears. The world's-fastest figure is different hardware and an easier dataset — context, not a comparator here. And today's much-slower lanes aren't evidence the bet is lost; they're evidence something changed between July and now, and finding out is this campaign's first job.

Glossary

1BRC
The One Billion Row Challenge: read a billion station;temperature text rows and print the min/mean/max per station, as fast as possible.
byte_buffer
Hey's one mutable value type -- an append-many-times output builder. In this program it only formats the final results; it was never in the hot loop.
zero-copy
Reading or sharing data by pointing at it, instead of duplicating it first.
The planned reference-counting upgrade
Values share until written, copy only when needed, instead of always copying. See the shared glossary. The in-place-aggregation gap in §3 is a small, scoped preview of this larger program.
