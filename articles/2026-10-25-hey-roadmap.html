Hey roadmap: what is decided and when it lands

Six release trains are lined up behind each other. One is in qualification today. One has a fifteen-phase plan and a realistic estimate, with low confidence. Three more wait on those two, so they don't have honest estimates yet, and one is held for a repair. This page shows which is which.

Estimates move. Every estimate here was re-read from the release records. They're engineering estimates, not measurements, and they're reforecast after each phase's native build. When this page and the records disagree, the records win (links in Sources).

1. The whole roadmap in one picture

Read the timeline from the top. A solid bar is the clean path: the time if nothing goes wrong. The pale bar after it is the realistic time, which assumes the usual review fixes. A dashed box isn't scheduled at all: it starts when the thing before it finishes, and nobody has set that start yet. The scale counts days from the start of the consolidation port.

Three things to take from the picture:

  • 0.99.606a is today's release. Its source is frozen and being qualified.
  • The consolidation release is the big one. It turns the compiler into one road from source to native code, then makes compiles and programs faster. Realistic estimate: about day 13 of the port, low confidence.
  • Everything else waits. The performance release, Phase S Strings and native ABI v2 don't have estimates, because their start depends on the trains before them.

2. Each train: what you get, how we'll know, how sure we are

Each card says what you get, which features it finishes, the gate that proves it (a gate is an automated check that must pass before a release ships) and the confidence.

0.99.606a: the repair batch Partly works (built, in qualification)

Status: source frozen for the 0.99.606a candidate. The native build was running. All four published release branches still point at 0.99.605a. Ship estimate: first in line, ahead of everything below (the forecast's row 0, medium confidence).

What you get. Fixes that stop ordinary code from paying for copies in common shapes: a map put inside a branch no longer copies the whole map,1 borrowed parameters, shared exits,2 String runtime fixes, the actor store, Alpine (musl) recovery,3 shadowing fixes, and the new small-block allocator (see Values, memory and Strings).

What it isn't. It was planned as "the performance release". The Maintainer re-ruled: ship this batch once the correctness and platform gates pass; beating 0.99.604a's speed belongs to the dedicated performance release after the consolidation. One-line ruling; the full card is in the decision ledger.

Gate. Mac acceptance: 54 of 61 rows passed on the build before this one. The records disagree on how many of the seven failures the last ownership fix clears (one row, or four), and three need reviewed regeneration of their expected-output files. Then Ubuntu and Alpine CI and Linux qualification. Then the landing script (which merges the release into the four release branches), the toolchain image hey-toolchain:0.99.606a (the prebuilt compiler that apps build with), and a check that a fresh app can use the release without building the compiler.

Confidence: medium. 606a's own benchmark numbers haven't been measured yet; the Linux machine is waiting for the frozen SHA.

The consolidation release: one road Decided, coming

What you get. One compiler path: source → syntax tree → HIR (what the program means, with types) → MIR (evaluation order, representation and ownership) → LLVM (the code generator) → native code. Every construct is read from the new parser's syntax tree. Runtime builtins are bound to the compiler through one declaration table inside the toolchain. Type inference and call-site specialization are both built. heyc app.hey --run compiles and runs natively with no interpreter. Then all the old paths are deleted, and compiles and programs get faster. The design is in the compiler architecture article; this page only covers the schedule.

Where it stands. Task 0 (the inventory) is done: 62 syntax-tree node kinds and 115 construct rows, 78 of them still read only by the old parser; a retirement ledger of 76 rows4 and up to about 48,000 production lines to delete. The expression slices (phase 1) pass at the source level; there's no native build of them yet. A new stop condition was logged: runtime builtins have no typed result fact yet, and that needs a Maintainer decision card.

Gate. Native self-build, every gate, the differential corpus (programs run both by the interpreter and compiled, outputs compared), the apps, and old entry points made to crash so nothing can quietly use them again.

Finishes: the consolidation release, compile-time optimizations and incremental per-module builds (phase 13), run-time optimizations (phase 14), and the typed half of Perceus ownership (phase 9). Details of 13 and 14 are in Performance.

Confidence: low. The forecast assumes agents running round the clock, the Mac's two heavy build slots once 606a ships, the Linux machine for platform runs, and no new design blocker.

The performance release Decided, coming

What you get. The release that has to beat 0.99.604a and move toward the bar of C speed on every benchmark and real app (Performance). The release-line plan lists the allocator follow-on branch, MIR uniqueness and last-use facts, and the map and hash redesign.

Estimate: none yet. It comes after the consolidation release. See where the records disagree: phases 13 and 14 of the consolidation plan cover the same ground.

Phase S: 16-byte Strings Decided, coming

What you get. Hey's String becomes a 16-byte value: short Strings (12 bytes or fewer) live inside the value with no allocation; long ones carry their first four bytes next to the pointer, so most comparisons finish without following it. Slices and splits can borrow instead of copying, maps get a faster table, and a + b + c builds once. The design and the S0 baseline numbers are in Values, memory and Strings. Ruled.

Size: 128–224 specialist work hours, two workers plus an integrator, the two heavy build slots.

Estimate. The reforecast says: from the day dedicated work starts (call it D), the first compiled demonstrator is D+1–2 days on the clean path; the full S2–S7 and S9 is D+5–9 days clean, D+10–18 days loaded. That reforecast assumed D would come before 606a shipped, which didn't happen. The current release-line order puts Phase S after the performance release, so there's no estimate today. (If D were the day after the consolidation's realistic finish, the full work would take another 5–18 days after that. That's arithmetic, not a forecast.)

Already done: S0 (the baseline benchmark) and S1 (the 16-byte type in the runtime, merged but unused by compiled code). Step S8 (ropes) is excluded from the estimate.

Gate. Every step is measured with a String micro-benchmark set (equality, ordering, hashing, split, slice, concatenation, map lookup) against Rust and C, plus W7, W8, 1BRC and the self-compile; S9 reports the numbers to the Maintainer.

Native ABI v2: calling C directly Decided, coming

What you get. A native package function becomes an ordinary import and an ordinary call, bound statically, instead of going through a name lookup and an argument array. Measured, a native call cost about 5,374 instructions. The static design is estimated at 40 to 90 (an estimate, not a measurement), and the release goal is at most 200 per call, measured, not promised. Work in progress is. Full mechanism: Native code and C.

Estimate. 56–100 work hours plus the dependent package releases. The earlier clean and loaded windows are now marked historical in the release-line runbook: the schedule is uncalibrated until Phase S's S2 String ABI is frozen and the package inventory is done. Preparation (semantic summaries, package inventory, tests) can overlap; the String bridges can't.

Gate. Real source through resolve, HIR, MIR and the native plan with positive and negative controls, lock and hash refusal checks, a fresh full product, dependent packages against a pinned SDK, and an honest measured per-call cost.

The runtime-index release Proposed

What it was going to be. A small runtime release making maps cheaper to copy and grow: hash index slots that remember their probe position, so growing an index never re-hashes keys.

Why it's held. The candidate built and passed its correctness checks, but 360 paired measurements found real losses: one ordinary program shape (a variable holding a shared, copy-on-write map, followed by len) used 102% more instructions; the hash spread keys badly (the top 32 bits of the FNV hash, the simple string hash Hey uses, clustered into the same buckets); and copying an index nobody uses cost real work. It must not be merged as a general win.

Next: repair the hash distribution and the eager-copy trade-off with watched controls, then reforecast. Its earlier planning window no longer applies.

3. What waits on what

Two links matter most. Phase 12 before 13 and 14: the optimizations go into one road only after the other roads are deleted, so nothing gets optimized twice. S2 before the native String bridges: the native calls pass Strings, so they need the final shape of a String first.

5. How the estimates are made

From real counts. The consolidation forecast starts from the inventory: 62 node kinds, 115 construct rows (78 still read only by the old parser), and the 76-row retirement ledger.
From observed pace. Expression typing on the syntax tree took about 2 hours at the source level; the first statements about 4 hours, each followed by review fixes.
Two estimates, not one. "Clean" assumes no surprises. "Realistic" or "loaded" assumes the usual review fixes and waits. Neither is a probability.
Reforecast often. After each phase's native build, and whenever a start slips: a slip moves the schedule, it never shrinks the work.

The trains also share machines. The Mac allows two heavy jobs at once (a full build takes about 45 minutes), and timed benchmarks need a quiet machine, so they can't overlap builds. The Linux machine builds and measures on its own as soon as a source SHA is pushed.

Release lines and version numbers Works today

Versions look like 0.99.606a. Every landing bumps the number, because the toolchain image is cached by version tag. The published releases today are 0.99.604a and 0.99.605a.5 The command reference is Commands and platforms.

6. Where the records disagree

These are stated rather than resolved. The Maintainer or the release owner decides.

  • Where do the optimizations ship? The consolidation forecast puts compile-time and runtime optimizations inside the consolidation release, as phases 13 and 14. The release-line runbook's ordered to-do list says "after consolidation: the dedicated performance release (allocator branch, MIR uniqueness and last-use facts, map and hash redesign, C parity on all benchmarks and apps), then Phase S". Either way the order is the same: one road first, optimizations next, Phase S after.
  • Phase S's place in line. The article plan gives a target with low confidence. The task's own reforecast says the date is D-relative and D hasn't happened. Inside the runbook, the ordered to-do puts Phase S after the performance release, while its handoff prompt says "Phase S has dedicated priority after 606a" and its milestones table says "do not place Phase S behind an open-ended roadmap". This page gives no estimate.
  • 606a's ship time. The runbook's milestones table still says "No ETA set" for 606a; its checkpoint says it ships first. This page uses the checkpoint.
  • Native ABI v2's estimate. The feature inventory still lists an older clean and loaded window; the runbook marks those windows historical. This page follows the runbook.
  • "Decided but not scheduled". Six of the eight items in section 4 are proposals, not rulings.
  • Stale inventory rows. The inventory row for 606a still calls it "the performance release", the Phase S row still carries the old target and the native ABI v2 row still lists the old windows; they need updating.
  • release-cycle.json in the project records still describes 0.99.600a; it isn't a source for current estimates.
