Apps from one Hey file: Apple TV, iPhone and iPad, Android

You write the app's brain in ordinary Hey: a couple of functions that say what the screen shows and what a button press does. A small native host, supplied by Hey or a Hey package, draws real tvOS, UIKit or Android views and calls your functions. This guide builds one of each and says exactly how far each one is proven: a plan on disk, a simulator, a device, or a store.

The short version

  • Apple TV is the quickest. Three commands (test, lock, launch) take a one-file Hey app to running on the Apple TV simulator in seconds.
  • iPhone and iPad come from one command in Hey itself: hey mobile ios native-app. It needs your button function to take a plain integer, which the compiler's type inference gives it in 607a Decided, coming.
  • Android has two roads. Hey's own hey mobile android app generates a Gradle project (same integer rule as iOS); the hey_android package builds an APK with no Gradle at all, and a Hey program and a Hey actor run on the emulator with output identical to the Mac.
  • Your code is ordinary Hey. No annotations, no Swift, no Kotlin. It goes through the same compiler road as any program and comes out as a native object file (compiled machine code, not yet linked into an app) for the device's chip.
  • Desktop means a native command-line or server binary. There is no desktop window or GUI package, and nothing has been decided about one.
  • No store receipts yet. Nothing on this page has been through App Store or Google Play review.

One Hey program, four kinds of screen

Every target uses the same deal. Your Hey file exports a few named functions. The host calls them:

The contract each host expects
TargetFunctions your file exportsWhat they return
Apple TV (scene contract v2)tv_scene_init(), tv_scene_step(scene, event)a JSON "scene document": background plus widgets (text, image, QR code, cards)
iPhone / iPadios_app_manifest(), ios_action_code(action_id)a JSON manifest of list and form screens; an integer per button press
Android (Hey's Gradle road)android_app_manifest(), android_action_code(action_id)the same shape as iOS
Android (hey_android, no Gradle)a normal program blockyour program owns an event loop and draws rows through pkg:hey_android/android_ui
Android TVandroid_tv_app_manifest(), android_tv_action_code(id)a manifest with "profile":"public-display"

Two words used below. Mach-O is Apple's format for compiled code; ELF is Linux's and Android's. A served-screen app (also called api_screens) is one whose screens are described in JSON by your server and drawn by a renderer on the device; more below.

A host here means the few hundred lines of native code (Objective-C on Apple, Java or C on Android) that own the window, read the JSON and draw real platform views. It knows nothing about your product. Hosts live in Hey packages (for TV and the served-screen renderers) or in Hey itself (the iOS and Gradle Android commands).

Predict before you scroll. The Apple TV app below is one Hey file (a third of it is the test) and one small package manifest. How many commands does it take to go from those two files to the app running on an Apple TV simulator? The answer is in the next section.

Apple TV: a running app in three commands

Works today on the simulator, through the hey_ios_tv package. It pulls in hey_tv (screen descriptions that don't care which TV) and hey_ios (Apple capability contracts).

The whole app

A lamp: press Select on the Siri Remote and it switches on (yellow screen) or off (dark screen). The state lives in the scene document itself, as a "lamp" field the app reads back by name with find: no hidden variables. (Why find and not Json.decode? Inside a TV app, Json doesn't work yet; see known limits.)

# A lamp for Apple TV: press Select on the remote to switch it on and off.
spec 'select switches the lamp; other buttons leave it alone'
  expect stdout "off\non\non\noff\n"
end

fn scene(lamp)
  let color = '#101820'
  let words = 'The lamp is off'
  if lamp == 'on'
    set color = '#F2C14E'
    set words = 'The lamp is on'
  end
  return '{"schema":"hey-tv-scene-v2","lamp":"' + lamp + '","background_color":"' + color + '","widgets":[{"kind":"image","id":"bulb","symbol":"lightbulb.fill"},{"kind":"text","id":"state","text":"' + words + '","style":"title","align":"center"},{"kind":"text","id":"hint","text":"Press Select","style":"caption","slot":"bottom","align":"center"}]}'
end

fn lamp_of(scene_json)
  if find(scene_json, '"lamp":"on"') >= 0
    return 'on'
  end
  return 'off'
end

fn tv_scene_init()
  return scene('off')
end

fn tv_scene_step(scene_json, event_json)
  if find(event_json, '"button":"select"') < 0
    return scene_json
  end
  if lamp_of(scene_json) == 'on'
    return scene('off')
  end
  return scene('on')
end

program
  let a = tv_scene_init()
  let b = tv_scene_step(a, '{"kind":"remote","button":"select"}')
  let c = tv_scene_step(b, '{"kind":"remote","button":"up"}')
  let d = tv_scene_step(c, '{"kind":"remote","button":"select"}')
  says lamp_of(a)
  says lamp_of(b)
  says lamp_of(c)
  says lamp_of(d)
end

The answer to the puzzle: three commands (heyc --test, hey package ensure, hey ios-tv-app --launch), a few seconds each, plus booting the simulator the first time. Pressing Select isn't driven from a script (there's no command-line remote), but the spec checks what a press does.

On a real Apple TV the same tool takes --device [ID]: it builds for arm64-apple-tvos, signs with your Apple Development identity and a tvOS provisioning profile, and installs with devicectl. Add --distribution (needs a paid Apple Developer Program account) and it emits an .ipa for TestFlight instead; --icon DIR adds the icon and top shelf image the App Store requires.

hey ios-tv-app --out build/tvos-device --source app/tv.hey --hey-root "$TOOLCHAIN" --device
hey ios-tv-app --out build/tvos-store  --source app/tv.hey --hey-root "$TOOLCHAIN" --device \
  --distribution --icon icon/ --export-compliance exempt
What the TV renderer can draw (scene contract v2)
  • Backgrounds: a flat colour, a felt-table gradient, or a top-level background_color.
  • Text in four styles (title, headline, body, caption), wrapped at the screen margin, with **bold**, *italic* and `code`.
  • Images (SF Symbols), QR codes with captions, rounded rectangles, and a playing-card family: card, stack, hand.
  • Remote presses arrive as {"kind":"remote","button":"select|up|down|left|right|playpause"}. Menu arrives as back only when the scene says "handles_back": true.
  • Unknown widget kinds draw a visible placeholder instead of crashing.

iPhone and iPad: one command

Decided, coming This command lives in Hey itself, not a package. The example ships with Hey: examples/mobile/native_ios_app.hey. It exports ios_app_manifest() (two screens: a list and a form with a secure password field) and ios_action_code(action_id).

# Ordinary Hey source compiled directly into a native UIKit application.

fn ios_app_manifest()
  return %q({"title":"Hey Native","screens":[{"id":"home","title":"Native Hey","type":"list","header":"Compiled through HIR, MIR, and direct LLVM","items":[{"id":"details","title":"Native view stack","subtitle":"Push a second UIKit controller","system_image":"iphone","destination":"details"},{"id":"action","title":"Call native Hey","subtitle":"Invoke an exported Hey function","system_image":"bolt.fill","action":1}]},{"id":"details","title":"Native form","type":"form","footer":"Secure fields use UITextField secureTextEntry.","fields":[{"id":"account","label":"Account","kind":"text","placeholder":"name@example.com"},{"id":"secret","label":"Secret","kind":"secure","placeholder":"Stored only after explicit save"}],"primary":{"id":"save","title":"Save locally","action":2}}]})
end

fn ios_action_code(action_id)
  if action_id == 1
    return 1001
  end
  if action_id == 2
    return 1002
  end
  return action_id + 1000
end

program
  says ios_app_manifest()
  says ios_action_code(1)
end

The host calls ios_action_code with a plain 64-bit integer. Nothing in the source says so; the compiler works it out from action_id == 1 and action_id + 1000. That inference is the 607a compiler's job (types inferred from the operations in a function's own body), and until it lands the command refuses the file with Hey source must export fn ios_action_code(action_id) returning an integer.

Android: two roads

Road A: Hey's own command Decided, coming

hey mobile android app compiles your Hey into ELF objects for arm64-v8a, x86_64 and armeabi-v7a and generates an Android Studio / Gradle project with a JNI library and a Java Activity. Minimum API 21, target API 35. --build needs Gradle. Like iOS, it needs the integer parameter that 607a's inference provides.

Road B: the hey_android package Works today

hey_android builds an API 36 APK with no Gradle: NDK r28 clang, aapt2, zipalign, apksigner. Your Hey program plus the Hey runtime go into one shared library under NativeActivity.1 It also has a Java renderer for served screens that can produce a signed Play upload bundle (AAB).

Road B: doctor, then a Hey program on the emulator

Three Android words: NativeActivity is Android's built-in screen that hands control straight to compiled code, so the app needs no Java; an AVD (Android Virtual Device) is a saved emulator; logcat is Android's system log, where the app's output lands. The program, android/app/hello.hey, is the one hey_android ships as examples/hello_runtime.hey:

# hello_runtime: a Hey program that uses the Hey runtime, built for Android.
#
# Maps, arrays, a string join, JSON parse and print, and SHA-256 of a string.
# specs/android_emulator_spec.sh builds it into an APK, runs it on an API 36
# emulator and requires its logcat output to equal the Mac run byte for byte.

program
  let queue = {title: 'Up next', rows: []}
  let names = ['Ada', 'Grace']
  set names = [...names, 'Linus']
  let i = 0
  while i < names.length
    let row = {id: i + 1, label: 'Row ' + names[i]}
    set queue = {...queue, rows: [...queue.rows, row]}
    set i = i + 1
  end
  let joined = Text.join(names, ', ')
  let parsed = Json.decode('{"kind":"list","items":[1,2,3],"ok":true}')
  let doc = Json.encode({queue: queue, joined: joined, parsed: parsed, count: parsed.items.length})
  says doc
  says doc.length
  says joined
  says Crypto.sha256_text(joined)
  says Crypto.sha256_text(doc)
end

What the program says shows up in logcat under the tag hey.out, byte for byte the same as on the Mac. A Hey runtime error ends the activity cleanly and appears under hey.err.

What hey_android can't do yet
  • The Hey lane draws only text rows and taps: no buttons, text entry, scrolling or back handling from Hey yet.
  • One CPU target: arm64-v8a, minimum API 35, target API 36.
  • No TLS from the Hey runtime on Android;2 the served-screen renderer uses the platform's HTTP.
  • A runtime error ends the app.
  • Some stdlib calls are refused at build time because they would need a Hey toolchain on the phone (use Files.write_atomic, not Files.write_text).

Android TV and Google TV

Partly works hey_android_tv adds a TV launcher entry, landscape, D-pad focus and no touchscreen requirement. Under the hood it calls Road A (hey mobile android app), so building an APK needs Gradle and the integer parameter above. Two package problems stand in the way today: its version() still says 0.1.0, so hey android-tv-app looks in the wrong folder, and it pins hey_tv 0.1.0 exactly while hey_ios_tv needs ^0.2.0, so no project can lock both TV adapters.

One description, many screens: hey_mobile

Works today (packages). The served-screen idea: describe the whole app in Hey (every screen, the JSON route that feeds it, what every button sends), serve that description from your Hey web server, and let a native renderer on each device draw it. The renderer holds no product knowledge, so one description serves iPhone and Android. In a folder called screens:

{
  "manifest_version": 1,
  "name": "screens",
  "version": "0.1.0",
  "registry": "https://www.jayteesf.com/packages/registry-v1.json",
  "dependencies": {
    "hey_mobile": "0.3.6"
  }
}
import 'pkg:hey_mobile@0.3.6/api_screens'

program
  let row = {title: 'title'}
  let library = HeyMobileApiScreens.list_screen('library', 'Library', HeyMobileApiScreens.tab('Library', 'books.vertical'),
    [HeyMobileApiScreens.section('Recent', HeyMobileApiScreens.route('GET', '/v1/items', nil), 'items', row, nil, 'Nothing saved yet')])
  let signin = HeyMobileApiScreens.form_screen('signin', 'Sign in', nil, [HeyMobileApiScreens.field('username', 'Name', 'text', true)],
    {title: 'Sign in', request: HeyMobileApiScreens.route('POST', '/v1/session', {username: '$username'})})
  let session = {sign_in_screen: 'signin', check: HeyMobileApiScreens.route('GET', '/v1/session', nil), sign_out: HeyMobileApiScreens.route('POST', '/v1/session/revoke', {})}
  let app = {schema: HeyMobileApiScreens.schema_version(), tabs: ['library'], session: session, screens: [library, signin]}
  says HeyMobileApiScreens.problems(app)
  says HeyMobileApiScreens.routes(app)
end

Actors inside an app

Works today on Android through hey_android. An actor is a small independent worker with its own mailbox and its own private state; you send it messages and it handles them one at a time (Actors and failure has the details). This one keeps a running total, android/app/actor.hey:

# An actor on Android: it keeps a running total and reports each step.
spec 'the counter actor adds what it is sent'
  expect stdout "total=5\ntotal=12\ntotal=12 done\n"
end

actor Counter(label)
  state total = 0
  receive amount
  if amount == 0
    says label + '=' + total + ' done'
    exit
  end
  set total = total + amount
  says label + '=' + total
end

program
  let c = spawn Counter('total')
  send c, 5
  send c, 7
  send c, 0
  join c
end

What "desktop" means

Works today for command-line tools and servers: hey build app.hey -o build/app makes a native executable for macOS (arm64) or Linux (x64). Guide 3 builds a tool; Guide 4 builds a web server, which you can open in a browser.

Nothing planned Desktop windows (a macOS, Windows or Linux GUI app with native windows and menus) have no package and no ruling. The nearest thing is a served-screen description from hey_mobile plus a browser.

How far is each target proven?

A receipt is the receipt.json each tool writes into --out, with flags like mach_o=true or device_launch. A simulator receipt never claims device evidence, and nothing here claims store evidence.

Known limits

  • The tvOS build road accepts less than hey does. Inside a TV app, joining a String and an integer ('Pressed ' + count) and Json.encode don't build yet, though both run with hey app.hey. Build the text with to_s and keep JSON as text, as the lamp does.
  • Every tvOS app is named HeyPartyTV.app on disk, whatever --display-name says (the name on screen does change).
  • The actor examples that ship with Hey don't route button presses through the actor (native_ios_actor_app.hey, native_android_actor_app.hey): the actor runs in the program block, and the exported action function is a plain function.
  • Two Android roads. Nothing yet says which one is the future.

Notes

  1. Runtime thread-local storage uses the initial-exec model only in executables, so a shared-library build such as Android's works: 1bea7c.
  2. A TLS server is a platform capability, not a dependency of every program, and an unsupported capability must not exist as a fake linked implementation: 36e862, e3eabe.
