No VM needed

Splitting a Hey program across machines is runtime-and-library work on the actor runtime Hey already has — not a bytecode VM — and Erlang's own C-node ships the proof.

Explored · not shipped This is a design note, not a feature announcement. Distributed Hey has not been built or shipped. Everything below is analysis of what the runtime would need, grounded in a research brief — no distribution code exists in the tree today.

Part 1 of a three-part series, "Distributing Hey." This part answers the maintainer's yes/no question — can Hey distribute with no VM? Part 2, "The wire format is the easy part," covers Hey's acyclic data model and what maps over. Part 3, "Seven choices for distributed Hey," argues the open design decisions. Each part carries its own TL;DR and visual.

The short version

  • Yes — a Hey program can be split across machines with no VM. Distribution is five runtime services on the actor runtime Hey already has, not a bytecode feature.
  • Erlang's own C-node library proves it. A plain C program running no BEAM, no bytecode, no interpreter already joins a distributed Erlang cluster and exchanges messages, links, and monitors with real Erlang processes.
  • Native, no-VM precedents exist. Cloud Haskell does full Erlang-style distribution as a library on natively-compiled code; Lumen compiles Erlang to native via LLVM — Hey's exact compilation model.
  • LLVM contributes nothing to distribution. It only lowers Hey to fast native code per node — no networking, serialization, scheduling, or membership. All of that is runtime and stdlib work.
  • Disclosed weaknessNo VM has a real cost: Hey loses hot-code distribution (BEAM's ship-the-code trick), and the native-distribution leg leans on Cloud Haskell (Ray proves the services-shaped variant) — Lumen proves native OTP but never shipped node-to-node distribution.
  • Check it yourselfRead Erlang's erl_interface/ei C-node docs: a program with no BEAM registers with epmd and exchanges messages, links, and monitors — confirm the VM is absent.

Hey compiles to native code through LLVM and has no virtual machine. So the honest question a maintainer has to ask is: can a Hey program be split across several machines purely as a runtime capability, the way Erlang does it — or does distribution secretly smuggle in a bytecode VM like BEAM? It does not, and the proof lives inside Erlang's own distribution.

Distribution is five services, not a VM

Strip Erlang's distribution down to what it does and you get a short list. A distributed Erlang system is a set of nodes — runtime instances named name@host — and the pieces that let them cooperate are all runtime services:

  • Naming and discovery. The Erlang Port Mapper Daemon (epmd) runs per host and maps symbolic node names to machine addresses. Service discovery, nothing more.
  • Location-transparent addressing. A pid carries its node of origin, so Pid ! Msg routes locally or across the network with identical source — message passing, links, and monitors are, per the docs, "transparent when pids are used."
  • Value serialization. Erlang terms are serialized to the External Term Format (ETF) and reconstructed on the far side — a format defined independently of how any node executes code.
  • Transport + handshake. The carrier is TCP/IP sockets with a handshake and a shared-secret (magic cookie) check. Erlang's own docs concede the cookie comparison is done "not in a cryptographically secure manner" — a cluster fence, not real auth.
  • Cross-node supervision / failure detection. net_kernel owns the local node's name, monitors every live connection, and on a lost link propagates a nodedown message to interested processes.

Two facts settle the "do we need a VM" question. First, the carrier is a defined, replaceable protocol — a protocol over a transport, not something welded into the bytecode interpreter. Second — the crux — a non-VM program already participates in the cluster today.

The C-node: a cluster member running no BEAM

Erlang ships a library, erl_interface/ei, whose entire purpose is to let a C program act as a node in a distributed Erlang system. In the docs' words, "a C node is a C program written to act as a hidden node in a distributed Erlang system." Erlang processes that know its name send to it in the normal manner. This is the whole argument in one existence proof — quoting the research brief verbatim:

A C node runs no BEAM, no bytecode, no interpreter. It joins the cluster purely by implementing four runtime services: the epmd registration + handshake (naming/discovery), ETF encode/decode (serialization), the TCP distribution protocol (transport), and the message/link/monitor semantics (supervision). Distributing a Program Across Systems (research brief), §1.2

Four services here, five above — that seam is worth naming, not hiding. It is two regroupings, not one clean cut. The five-service decomposition splits location-transparent addressing out on its own, where the C-node folds addressing into the pid and the message/link/monitor semantics; and the handshake moves — the C-node's four-list files it under naming/discovery ("epmd registration + handshake"), while the five-list folds it into "transport + handshake." Same machinery, sliced differently — a description choice, not a contradiction in what has to be built.

BEAM the VM provides preemptive scheduling, hot code loading, and per-process isolated GC — none of which is distribution. The one place it genuinely leaks in is hot code loading, the Unison-style "send the code with the message" trick — the single VM-flavored piece, and optional, not load-bearing, for splitting a program across machines.

The no-VM precedents

The pattern across every mature actor system is the same: membership, addressing, serialization, failure-detection, and supervision live in a runtime or library; the execution substrate — VM or native — is orthogonal. Two precedents matter most for Hey.

Cloud Haskell is the closest architectural twin. It is natively compiled (GHC, the Glasgow Haskell Compiler), a "process" is literally a forkIO thread with a mailbox, and distribution is a library — distributed-process — not a feature of the compiler. It "abstracts over a network transport layer," exactly like Erlang's alternative-carrier design, and reproduces Erlang's whole model — message passing, links, monitors, remote spawn — with no VM. That is the existence proof that a native language gets Erlang-style distribution as a library — and it works. Ray is the shipped no-VM distribution, its native C++ core moving values as ObjectRefs with no language VM at all.

Lumen is Erlang compiled to native via LLVM — the exact compilation model Hey uses. Per its README, "rather than being constructed as a compiler that produces bytecode which is then executed by a virtual machine, Lumen is instead an ahead-of-time compiler that produces native code," on a Rust runtime over LLVM. It shows Erlang/OTP semantics — processes, mailboxes, scheduling, supervision — survive the move to native ahead-of-time (AOT) compilation with no VM. The honest caveat: its README does not document node-to-node distribution (its target was WebAssembly/embedded, and it drops hot code loading). So Lumen proves native OTP; Cloud Haskell supplies the native distribution half. Together they close the argument.

The wider field fills in the design menu Part 3 argues — Orleans' virtual-actor identity, Akka Cluster's gossip membership and phi-accrual failure detector, Ray's distribution-as-services moving values as ObjectRefs — and one warning: Pony designed native actor distribution but never shipped it, proof that transparency is easy to design and hard to finish. One guardrail on that list: Orleans runs on the .NET CLR and Akka on the JVM — both virtual machines. The brief calls each VM "incidental," and they belong here only for their VM-independent distribution designs (virtual actors, gossip, phi-accrual), not as no-VM proof. The load-bearing no-VM-distribution evidence is Cloud Haskell and Ray; Erlang's C-node is the no-VM-membership proof.

Where LLVM sits: entirely to one side

It is worth being blunt about LLVM, because the name misleads. It is a target-independent optimizer with code generation for many CPUs — no networking, no RPC, no serialization, no scheduling, no membership, no distributed runtime. Its own site says it plainly: "despite its name, LLVM has little to do with traditional virtual machines."

So the split is total. LLVM lowers Hey to fast native code on each node and contributes literally nothing to distribution. Every distribution service is runtime and standard-library work — the same kind of code that already lives alongside Hey's scheduler in runtime/hey_runtime.c (home of HeyActor, HeyWorkerPool, and the HeyMessage mailbox), plus .hey stdlib surface. There is no VM to add and none is needed.

Bottom line for Part 1

Hey needs no VM. Distribution is five runtime services layered on an actor runtime — proven by Erlang's own C-node running with no BEAM and by Cloud Haskell's native library. LLVM contributes nothing but fast per-node native code; the one honest cost, hot-code distribution, is optional. Glossary

BEAM
Erlang's bytecode virtual machine (the runtime that executes compiled Erlang/Elixir). It supplies preemptive scheduling, hot code loading, and per-process isolated GC — none of which is distribution. Hey has no equivalent and needs none.
C-node
A program written in C — no BEAM, no bytecode, no interpreter — that joins a distributed Erlang cluster as a hidden node via the erl_interface/ei library. The load-bearing existence proof that cluster membership is runtime services, not a VM.
epmd
Erlang Port Mapper Daemon: a per-host service-discovery registry that maps symbolic node names to TCP ports so connecting nodes can find each other.
ETF
External Term Format: Erlang's wire serialization for values sent between nodes, reconstructed on the far side. Defined independently of how any node executes code — Hey would need an ETF analogue for its own values (Part 2).
phi-accrual
Akka Cluster's failure detector: instead of a boolean "is it down?", it returns a tunable suspicion value (phi) representing the likelihood a node has died, trading false positives against detection latency.
virtual actor
Microsoft Orleans' addressing model: an actor is addressed by logical identity, and the runtime freely places, migrates, activates, and recovers it. Contrasts with node-tagged pids, which pin an actor to where it was spawned (a Part 3 choice).
ObjectRef
Ray's distributed pointer/future to a value in its shared object store, pinned by distributed reference counting. Relevant because Hey is already refcounted, so a "copy small, ship large by reference" split maps onto machinery Hey has (Part 2).
