Great Command-Line Scripting with Hey

One job, two implementations, one rule: the outputs must match to the byte. On today's toolchain (v0.99.410a) the Hey version builds a documentation index 5.46× faster than the Ruby it was ported from. That number is not the interesting part; the gate that makes it mean anything is.

TL;DR

  • 23.5 ms vs 128.1 ms — 5.46× faster than Ruby, rendering a 14-package documentation index on a quiet Apple M-series laptop, 30 timed runs, byte-for-byte identical output. The script lane, no build step at all, does it in 26.3 ms.
  • A benchmark without an output-parity gate is a wish. Ours caught an optimization that made this program faster and wrong, and a "record" 2.3 ms result that was a dead binary timing its own death.
  • Two lanes: the script you run, the binary you build. The binary leads by only 1.12× today — a story about a bare print in a help function, not about compilation.
  • Disclosed weakness: the parallel lane is slower than serial at this size, big-list workloads still lose to Ruby (8,000 files: Ruby 672 ms, Hey 2.16 s), and the Hey source is 1.79× the Ruby line count.
  • Falsifiability: both implementations are in this repository, the harness below produced every figure, and each release is a dated row in the progression table — new measurements add rows rather than replacing a headline.

How to read these numbers

Apple M-series laptop, macOS, quiet box — nothing else running, ambient load checked before each cell. Timings from hyperfine, a benchmark runner that repeats a command and reports mean ± standard deviation: hyperfine --warmup 3 --runs 30, same 14-package tree, fixed timestamp via PACKAGES_INDEX_GENERATED_AT for every lane. Each lane deletes its output first, asserts it came back non-empty, and diffs it against Ruby's before any clock is trusted — never an exit code of 0 alone. Anything measured on a loaded machine is a lower bound; nothing here was.

The running example, and why a port is a legitimate benchmark

generate-packages-index.hey and generate-packages-index.rb both walk a package directory, natural-sort every versioned docs/ directory and every Markdown or HTML file below it, and render one static index page.

A port is the cleanest benchmark available to a small language and the easiest to cheat at: a real program doing real filesystem work, but most accidental speedups in a rewrite come from quietly doing less — a sort that no longer sorts, a directory that no longer gets walked. So the pair is held to one condition: same timestamp in, identical bytes out. Take that away and the multiplier means nothing.

Hey can read like Ruby

Receiver chains, predicates ending in ?, string interpolation, heredocs:

private fn linkable?(path)
  let lower_path = Text.lower(path)
  return Text.ends_with?(lower_path, '.md') or Text.ends_with?(lower_path, '.html')
end

private fn linkable_files(package_files)
  return PackagesIndex.sorted_unique(
    package_files.filter(PackagesIndex.linkable?)
  )
end

private fn package_directories(packages_dir)
  return Files.entries(packages_dir)
    .filter(PackagesIndex.visible_directory?)
    .sort(PackagesIndex.compare_paths)
end

Also on hand: .uniq, .map(fn), .map(fn, workers: n).collect() for parallel fan-out, .empty?, value.length, %qq(...) interpolation with #{expr}, and <<~'TEXT' heredocs. A Ruby programmer reads the whole script cold, which is most of the argument for Hey as a scripting language.

The ergonomics tax, stated honestly

Identical behaviour costs Ruby 313 lines, Hey 561 — 1.79× for this script; on the sibling source-zip tool it is 606 versus 861, or 1.42×. Some is Hey's explicitness; most is workarounds for known toolchain gaps — bound intermediates where chained indexing will not lower, plain helpers where worker bodies reject assignment. Those gaps have tickets, so the tax should shrink. Today it is real and you should price it in.

The parity gate

The thesis, and it outranks every number here: a benchmark without an output-parity gate is a wish. Two receipts from this program.

The first optimization pass rewrote the natural-sort comparator to use byte_at(string, i). It compiled. It also silently returned 0 for every string argument — it is a Bytes-value operation — so the comparator declared every path equal to every other, the sort collapsed into a no-op, and the benchmark got faster and wrong: the classic rewrite failure, arriving in the shape of good news. The byte-parity check against Ruby caught it on the first run.

The second is worse, because the gate itself lied. The fastest result this project ever recorded was a 2.3 ms binary. It was a corpse: exit 0, zero bytes of output, dead before the first line of user code, timing its own death. The parity check blessed it, because it never deleted the output file before running and so compared the one left by the previous lane. A dead program passed a correctness gate reading a ghost. That one is my bug, not the compiler's, and it is why the harness below deletes first and asserts before it compares. The autopsy, plus four more silent-failure classes, is in the case file on the Ruby port that ate 50 GB of RAM.

Two lanes, in plain English

There is the script you run, and there is the binary you build. Same source file either way: 

# the script you run — no build step, shebang is #!/usr/bin/env hey
./generate-packages-index.hey --workers 1 ./packages

# the binary you build — a standalone native executable
export HEY_ROOT="$HOME/dev/hey-lang-bootstrap-plan"
"$HEY_ROOT/bin/heyc" build --backend llvm \
  ./generate-packages-index.hey \
  -o "$HOME/bin/generate-packages-index"

You would expect the compiled artifact to crush the interpreted one. It beats it by 12%. That is not a verdict on compilation, and the reason is almost funny: this program has a help function whose entire body is a bare print of a heredoc. A v0.99.382a-era emitter guard cannot prove a bare module-function call in statement position terminates, so it declines to lower the program fully natively and drops the whole thing onto the shared consumer path — leaving roughly 31 sites going through delegation instead of compiled inline. Both lanes then run most of the same machinery, and the binary's lead is mostly a startup difference.

So today's binary-versus-script gap measures a usage banner, not a compiler. The emitter slice that removes the fallback is queued for v0.99.411a. When it lands the spine gets a row; if the gap does not widen, that is a finding and it gets printed at the same size.

The three rules that keep Hey fast

Rule 1: stdlib freely outside hot loops, builtins only inside them

A stdlib call from compiled code now costs roughly 60–80 µs through the sidecar; tabled and natively lowered calls cost under a microsecond. At that price ordinary use is free — parse arguments, read a config, format a report with whatever reads best. The rule bites only in the innermost per-item loop. This script's comparator runs thousands of times per sort, so its inner loop uses bare builtins (slice, len, direct !=) and never leaves compiled code. Everywhere else in the file, the stdlib is used without ceremony.

What this rule used to say, and why it changed

An earlier version of this article said: avoid stdlib calls in hot loops, full stop. That was correct and is now wrong, the more interesting kind of obsolete. Before v0.99.402a a stdlib call from compiled code wrote a temp file and spawned an interpreter subprocess to service it — about 7 ms per call, so one careless Text.trim over a thousand items cost seven seconds. The v0.99.402a sidecar replaced that subprocess with one long-lived helper and took it to ~60 µs. Four orders of magnitude does not refine a rule; it retires one.

Rule 2: measure output before you measure time

Delete the output, run, assert it came back, compare bytes, and only then start a clock. Both of this project's most memorable numbers — the comparator that sorted nothing, the binary that did nothing — were speedups.

Rule 3: parallelism has a floor, and it is above 14 packages

.map(fn, workers: n) hands each item to a worker pool, and at this size that is a straight loss: scheduling and collecting 14 quick renders costs more wall clock than doing them in order. Default to --workers 1 and treat fan-out as something you earn with a measurement. One sharp edge: pool sizes in Jobs.define must be integer literals — a variable will not lower, and it says so at compile time rather than at 3 a.m.

A harness that cannot lie to you

All of it reduces to one runnable script. The ordering is load-bearing: rm before run, assertion before comparison — so a program producing nothing fails here instead of posting a record. 

set -eu
STAMP=2026-07-25T00:00:00Z

lane() {                      # $1 = label, $2.. = command
  rm -f packages/index.html
  PACKAGES_INDEX_GENERATED_AT="$STAMP" "${@:2}" >/dev/null
  test -s packages/index.html || { echo "$1: NO OUTPUT"; exit 1; }
  cp packages/index.html "out.$1.html"
}

lane ruby   ruby ./generate-packages-index.rb ./packages
lane script ./generate-packages-index.hey ./packages
lane binary generate-packages-index ./packages

cmp out.ruby.html out.script.html
cmp out.ruby.html out.binary.html

hyperfine --warmup 3 --runs 30 \
  'ruby ./generate-packages-index.rb ./packages' \
  './generate-packages-index.hey ./packages' \
  'generate-packages-index ./packages'

When a lane dies silently — exit 0, no output, no diagnostic — do not start by blaming the compiler or rewriting your code. A racy cache publish can mint a corrupted entry that deterministically produces do-nothing programs, and the poison propagates: a dead run writes its own entry into the run cache. Sweep both layers, then rebuild. 

rm -rf "$HEY_COMPILER_BUILD_DIR/compiler-sidecars"   # poisoned sidecar entries
rm -rf "$HOME/.cache/hey/run"                        # the run cache they poisoned

Alive after that, you had a cache problem. Still dead, bisect — same file by a different path, a copy under a different name — then file it. A publish lock and a loud guard are queued upstream. Until they land, the rule is unglamorous and absolute: always assert output, never trust exit 0.

Where the next speed comes from, and where Hey loses

Three known items. The v0.99.411a emitter slice that stops a help function dragging the program off the native path. Copy elimination in ordinary compiled paths: profiling shows no single hotspot, just boxed values allocated and copied, plus real filesystem syscalls. And a queued fix for list-append time cost, which matters most outside this article — it is where Hey loses today, measured on the sibling source-zip port, same day, same box.

A memory fix moved that crossover to around 2–3 thousand items and halved the deep deficit; the remaining half is building large lists, still quadratic in time, fix queued and not landed. So the honest scope for Hey today is small-to-medium command-line work, where it is several times faster than Ruby and ships as one file — and not large-list batch processing, where Ruby wins and you should let it. The instruments behind every figure here are committed beside the source, which is the only reason I can name the losses as confidently as the wins.

Glossary

hyperfine
A benchmark runner: repeats a command and reports mean ± standard deviation.
byte-parity
Comparing outputs byte for byte rather than "looks right".
sidecar
A long-lived helper process replacing per-call process spawning.
delegation
A compiled program handing a call to the interpreter instead of running it natively.
builtin
A language primitive the compiler lowers straight to machine code.
LLVM
The compiler backend Hey targets to produce native executables.
worker pool
A fixed set of workers processing items in parallel from a shared queue.
exit code
The integer a process returns on termination; 0 means success.
run cache
Where the toolchain stores compiled artifacts for scripts it has already run.
quadratic
Cost growing with the square of the input.
