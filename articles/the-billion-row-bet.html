The Billion-Row Bet

Hey has exactly one mutable value type — byte_buffer, a write-in-place output builder that entered the language by accident, during an earlier attempt at this exact benchmark. Using it, Hey's own recorded runs from July finished all one billion rows of the One Billion Row Challenge in roughly 43.242 seconds, on this same machine, on this same hard file. The bet: rebuild the program on immutable, zero-copy pieces alone, beat that time by any margin, and the mutable type gets deleted from the language.

Status: bet re-centered on Hey's own recorded result — nothing built on the immutable side yet

The all-immutable 1brc.hey this article bets on does not exist yet. What's real, dated 2026-07-27: reference lanes measured on this machine, the maintainer's recorded July figure adopted as the mark to beat, and a first honest look at how far today's ordinary Hey code is from matching it.

1. The bet

TL;DR

  • We're betting that Hey, using only immutable, zero-copy code, can beat Hey's own fastest recorded 1BRC run — and if it does, the one mutable type that made that run possible gets deleted from the language. Hey's July-era code, using its single mutable value type, finished all one billion rows in 43 seconds on this machine. That's the number to beat, by any margin.
  • This is Hey against Hey. Not a race against C, Python, or the world record — those stay on the chart as scenery, for scale. The whole bet is purity against its one compromise, same machine, same file, same language.
  • Disclosed weakness, stated first: today's ordinary Hey code, already immutable-style, projects months for the same job, not seconds. Something is very different between July and today; finding out is step one (§4).
  • Falsifiable, on purpose: the 43.242-second figure is maintainer-recorded, its original receipts overwritten by later builds — on the books as recorded, pending re-measurement, not a finished number. The billion-row file it was measured against was lost to a tooling accident and is being regenerated; every number below is dated and traces to the project log.

Here's the wager, plainly. Hey has one mutable value type in an otherwise all-immutable language: byte_buffer, a write-in-place output builder that entered the language by accident during an earlier attempt at this exact benchmark. Used, Hey has already done the job: the project's own July-era runs on this machine processed all one billion rows — 15 GB, 44,693 stations, the hard file — in 43 seconds. That isn't a target; it already happened, once, with the compromise left in.

The bet is whether Hey can do it again without the compromise: rebuild on immutable, zero-copy pieces alone, same machine, same file, and beat that 43.242-second mark by any margin. Win, and byte_buffer is deleted — the accident that made the fast run possible no longer gets to justify its own existence. Lose, and the type stays, as the thing purity couldn't yet beat.

The world's numbers stay on the chart, but only as scenery. The fastest publicly known C we could measure on this file needs 18.8 seconds; a fast Python needs about 143. The official world record is 1.5 seconds — easier dataset, different hardware, not a fair comparator here. None of those are the bet. The bet is Hey against Hey.

2. What is 1BRC?

Term: the One Billion Row Challenge

The One Billion Row Challenge (1BRC, Gunnar Morling, January 2024) asks for exactly one thing: read one billion station;temperature text rows and print the minimum, mean, and maximum temperature per station, as fast as possible. The winning entries all leaned on the same handful of tricks — reading the file straight into memory instead of calling read(), scanning several bytes at a time instead of one, and skipping text allocation until the very last step.

3. Why we think we can make it

We measured where the time actually goes, and the real work is already fast. The scanning-and-comparing logic alone costs about 7 nanoseconds (ns, billionths of a second) per row on this machine — world-class pace. That 7 ns is buried under roughly a thousand times its own cost in memory bookkeeping. We don't need to invent speed; we need to stop paying for overhead the algorithm never needed.

Most of the machine we need already exists. A fast 1BRC pipeline needs a handful of pieces: mapping the file without copying it, scanning it without copying it, parsing numbers without allocating, and fanning work across workers sharing one view of the data. Five of those six already exist in Hey, as immutable, zero-copy code. Only one real gap remains — accumulating results without copying the whole running tally on every row — and it's scheduled, not speculative.

We've done exactly this before, twice. This project's web server went from ~500 to over 120,000 requests per second by the same method — measure the real cost, name it, delete it — in "From 500 to 100,000 Requests per Second." An idiomatic Hey port of a Ruby command-line tool now matches the hand-tuned version it retired, and a separate Ruby port's memory story — a 481× reduction, printed in public — is the same discipline on a harder problem. This team publishes bets before results and corrections in public; this article is doing that now.

And we already know a fast program shape exists. Hey itself ran this exact benchmark, on this exact machine and data, in 43.2 seconds in July. We're rebuilding that shape without the one compromise that made it possible.

Glossary

1BRC
The One Billion Row Challenge: read a billion station;temperature text rows and print the min/mean/max per station, as fast as possible.
byte_buffer
Hey's one mutable value type — an append-many-times output builder that writes to its own memory in place, added by accident during an earlier attempt at this exact benchmark. Deleted if this bet's immutable approach wins.
zero-copy
Reading or sharing data by pointing at it, instead of duplicating it first.
The planned reference-counting upgrade
Values share until written, copy only when needed, instead of always copying. See the shared glossary. The in-place-aggregation gap in §3 is a small, scoped preview of this larger program.
