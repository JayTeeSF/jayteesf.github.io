What Should a Byte Buffer Be?

Hey is a value-semantics language: values copy, nobody ever observes your mutations, and that one rule is what makes the language's whole in-flight plan to share memory by reference count (I5) safe to build. One type refuses to fit: byte_buffer, the append-many-times string builder. A falsifiable guard suite built to pin value semantics found the proof that no refcount rule can rescue it — the required behavior is non-monotonic in the refcount itself. This is a measured walk through five ways the language could resolve that, arithmetic-checked against the one workload that actually uses it at scale. The verdict, up front: this is a recommendation, not a ruling — the decision is the maintainer's. The team's pick, with high confidence, is to stop pretending byte_buffer is a value at all.

Status: pending maintainer decision

Nothing in this article is shipped. It analyzes five options for an open language-design question — how byte_buffer should be classified — that blocks one ticket in Hey's refcount program (I5) and is on the maintainer's open-questions list as item 4 (docs/agents/in-progress.md:8-17). Every measured number below is real and reproducible; the choice among the five options is not this article's to make.

TL;DR

  • RECOMMENDATION, NOT A RULING — the decision is the maintainer's: reclassify byte_buffer as a mutable handle, the same family as HEY_IO_HANDLE and HEY_ACTOR (option (i) below), high confidence. It costs nothing extra beyond what the runtime already does, and it breaks none of the three specs that already pin the accumulate-into-a-buffer idiom.
  • No refcount predicate can implement byte_buffer's measured contract. A direct append must write through at refcount 3, a nested append one function-call deeper must NOT write through at refcount 4, and three appends in a row (spec 926) must all write through at refcounts 3, 3, and 5. Write-through is required at rc 3 and rc 5 and forbidden at rc 4 — no threshold (rc == 1, rc <= n, anything) can express that.
  • The mechanism is call depth, not sharing. Bytes.append is an ordinary Hey function whose first parameter is the buffer (stdlib/Bytes.hey:64) — so a direct call and a call through one wrapper function are the identical construct, one stack frame apart. byte_buffer was never partially shared; it is already an unconditional mutable handle. The only open question is whether the language admits it.
  • Always-copying instead is dead on arithmetic alone. Building the 1BRC product lane's output (spec 936) for 10,000 stations takes 79,999 appends into a ≤ 1 MiB buffer; in place, that moves about the output's own size, ~260 KB. Copying the whole buffer on every append instead would move ~10.4 GB — about 40,000× more bytes physically moved for the identical result.
  • Disclosed weakness: the recommendation is a documented convention, not a compiler-enforced one. Go's strings.Builder panics at runtime if you copy it by value; nothing in this recommendation makes Hey do the equivalent yet. The guard suite retires the three affected cases as by-design, but nothing today stops a byte_buffer from being handed to two actors at once. The two riders in §5 are how that gap gets managed until, or unless, the language decides to enforce it.
  • Falsifiable, and already run twice. The rc table was measured with both lanes agreeing (the interpreter and the LLVM backend). Reproduce it from specs/language/1218_byte_buffer_isolation_is_not_an_rc_problem.hey and its fixture, test/fixtures/compiler/value_semantics_guard_byte_buffer.hey, in the wi5a worktree.

How to read this article

Every claim below traces to one of two kinds of evidence, tagged inline: [MEASURED] for numbers taken directly off the pinned specs and fixtures in this codebase, and precedent tags — [DOCS], [SOURCE], [PAPER] — for how other languages have handled the identical problem. Nothing here is a guess about what other languages "probably" do; every precedent claim links to the primary source at first use, and again in the Sources list. The workload used for every performance number is the same one throughout: Hey's 1BRC (One Billion Row Challenge) product example, whose output builder is pinned at exactly Bytes.buffer(1048576) by spec 936.

1. The type that refused to fit

Every value in Hey copies. Pass an array to a function, get a message back from an actor, store a struct in another struct — nobody downstream can ever observe you mutating what you handed them, because what they hold is, semantically, a brand-new copy. That single guarantee is what makes Hey's in-flight plan to actually stop copying — sharing values by reference and a reference count instead, tracked as I5 — safe to build at all: if nobody can observe a mutation, sharing the backing memory instead of copying it changes performance, never behavior.

Term: byte_buffer

byte_buffer is Hey's append-many-times output builder: you allocate one with a starting capacity, append chunks of bytes to it repeatedly, and flatten it once at the end. It exists because building output byte-by-byte through Hey's normal immutable arrays would mean re-copying the whole growing result on every single append — the exact quadratic cost this article measures for option (iv) below.

One type was expected to refuse to cooperate with that plan from the day it was designed: a falsifiable guard suite (the project's internal name is 439a) was built specifically to pin value semantics down as a measurable contract rather than a vibe, and its BYTE_BUFFER family of test cases was expected-red from day one — three fixtures, kept deliberately failing, that record exactly how byte_buffer disagrees with everything else in the language.

2. The measurement that sharpened it

The fixture that pins the disagreement lives at test/fixtures/compiler/value_semantics_guard_byte_buffer.hey. Its own header states today's runtime behavior plainly: HEY_BYTE_BUFFER is "the one value kind that is already refcount-shared: hey_value_clone bumps refs and hands back the SAME backing... and append/clear mutate that backing in place" [MEASURED] (fixture header, lines 6–13). The fixture demands three specific, contradictory-looking things: a direct append must be visible afterward (length 4 after seeding), the identical append performed one function call deeper must be invisible, and a third case appends through an object-literal field. All three are pinned as expected-red — deliberately failing, on record, because nobody had yet ruled on what they should do instead.

What sharpens the story from "one annoying type" into "no fix is possible without a ruling" is an instrumented measurement: reading the actual refcount at the moment each append mutates the buffer, on both compiler lanes (the interpreter and LLVM), agreeing [MEASURED].

Read that table as a single claim: write-through is required at rc 3 and rc 5, and forbidden at rc 4, sitting strictly between them. That is non-monotonic in refcount — there is no threshold predicate, of any shape, that returns true at 3 and 5 and false at 4. Converting receiver-position clones to borrows (a Swift-4.2-style change, worth doing on its own merits) shifts every number in the table down by the same amount and changes nothing about the ordering [MEASURED] (spec 1218:32–41).

Term: call depth vs. ownership

Bytes.append is not a compiler builtin bolted onto the runtime; it's an ordinary Hey function, fn append(buffer, value), whose first parameter is the buffer (stdlib/Bytes.hey:64), delegating to a byte_buffer_append builtin underneath. So fixture case (A) is "append through one parameter binding" and case (B) is "append through two" — the identical construct, at different call depths, with the buffer reachable at both mutation sites from exactly one program-visible root (the binding buf) plus the live call chain. It was never a question of who owns the buffer at either site — it's the same owner both times. The count that changes is stack depth, not sharing.

That mechanism reframes the whole question. byte_buffer was never a value with an occasional leak. It already is an unconditional mutable handle — the runtime shares its backing memory and writes through it in place, every time, regardless of refcount. The guard suite isn't broken; it's accurately reporting that the language's surface claims something the runtime doesn't do. The only real question left is whether the language admits that on purpose.

3. What any fix has to preserve

Three call sites in the codebase are pinned specs, not incidental usage, and every option below is judged against what it costs each of them:

  • Spec 926 (specs/language/926_byte_buffer_linear_builder.hey) pins the exact stdout "0\n2\n4\ntrue\nabcd\n8\nabcdabcd\n0\n". Two things in that output are load-bearing: Bytes.append returns the new length (an int), not a buffer, and the accumulation happens through the same binding across calls (lines 10–11) — write-through, at the direct-call depth, is not incidental, it's the point. Line 14 additionally pins self-append aliasing: Bytes.append(output, output) must read the pre-append contents and produce "abcdabcd".
  • Spec 936 (the compiler's product-lane contract) pins the literal Bytes.buffer(1048576) (1 MiB) as the "linear byte-buffer output" inside an otherwise pure, immutable-style example (spec 936:36) — the accumulate idiom is the deliberate single mutable builder inside a program that is pure everywhere else.
  • one_brc.hey's result-formatting function appends into one buffer binding, 8 times per station (7 for the first), across a stdlib call boundary, inside a loop (lines 143–168), flattening once at the end (Bytes.decode(Bytes.freeze(output), 'utf-8')).

Any option that can't reproduce all three, unmodified, is not free — it's a migration.

4. Five options, weighed

(i) Reclassify byte_buffer as a mutable handle

Make it official: byte_buffer joins HEY_IO_HANDLE and HEY_ACTOR as a value kind that was never meant to have value semantics in the first place (spec 1218:53–58). This is the least invasive option in the strict sense that it changes zero runtime behavior — it just gives a name to what hey_value_clone already does.

Consistency: Hey's own course material states the doctrine plainly — "Actors: the only home for changing state" is a chapter-five section heading, not a footnote [DOCS]. But the runtime already carves a narrow, explicit exception into that rule for IO handles — sequential resources that are mutated in place because they represent something external, not actor-owned application state. A builder used inside one call chain, never legitimately shared across two actors at once, fits that same narrow exception; it doesn't open a new one.

The external precedent is a mutable handle that refuses value semantics at runtime. Go's strings.Builder documents "Do not copy a non-zero Builder" and then enforces it: a copyCheck method stores the receiver's address on first use, and if a later method call runs on a copy instead of the original, it panics with "strings: illegal use of non-zero Builder copied by value" [SOURCE]. bytes.Buffer is the plainer version — "a variable-sized buffer of bytes... ready to use," passed by pointer by convention, no apology offered for being a handle [DOCS]. Clojure's transients are the second precedent: an officially blessed "mutable builder inside a pure function," explicitly non-value, with a usage discipline instead of a type-system proof — thread isolation, and "you must capture and use the return value in the next call" [DOCS].

Performance: unchanged from today, by construction — option (i) doesn't touch the mutation path, it just stops calling it a defect. Migration cost on the three pinned sites: zero. All three already pass under today's runtime behavior, because today's runtime behavior is option (i)'s behavior; the fixture header says as much (lines 6–13). Guard suite: the three BYTE_BUFFER cases retire as by-design — not fixed, not deleted, reclassified, with a one-line doctrine note where spec 1199's expected-red list used to carry them. Forecloses for I5 (b)/(c): nothing. byte_buffer holds no HeyValue fields and so can never form a reference cycle (spec 1217, via spec 1218:65–67) — it was never a candidate for I5's cycle-free refcount sharing in the first place. The rest of the value-semantics guard (arrays, strings, structs) is untouched.

(ii) A call-depth ownership rule

Take the mechanism in §2 literally: write through at call depth 1 (a direct call), copy or isolate at any depth beyond that. It would satisfy the fixture exactly as measured — case (A) at depth 1 writes through, case (B) at depth 2 doesn't.

Consistency: the project's own working notes are blunt about this one — "novel semantics — orchestrator prior: no" (docs/agents/in-progress.md:14, spec 1218:53–58). None of the five languages surveyed for this article — Swift, Go, Clojure, Erlang, Koka/Lean, Rust — key mutation permission off how many stack frames deep a call happens to sit; every one of them keys it off sharing (a uniqueness check, a refcount, a compile-time borrow). Tested honestly and rejected: it canonizes a calling-convention artifact. Extract append_to's three lines into the caller as an inline block, or inline the caller into a one-off helper for readability, and the buffer's mutation semantics flip — forbidden becomes required, or the reverse — with the actual data flow completely unchanged. A rule where refactoring for readability silently changes what your program does is not a rule a language should adopt on purpose.

Performance: identical to (i) at depth 1, but it requires new runtime machinery to actually enforce depth-tracking at every mutation site — work option (i) needs none of. Migration: the three pinned sites survive only if their existing call shapes happen to sit at the depths the rule expects, which is true today by coincidence, not by design — and the rule itself still has to be built and specified precisely enough to say whether the delegation from Bytes.append down to the byte_buffer_append builtin counts as a frame or not (spec 1218:63–67). Guard suite: the three cases would need to become enforced, not merely observed — new machinery, new failure modes. Forecloses for I5 (b)/(c): this is the option's sharpest cost. I5's later stages are exactly where Hey has to design a calling convention for borrowed vs. owned parameters, and the Linux seat's ownership research names the trap by name: Swift's guaranteed-by-default (borrowed) parameters once made its copy-on-write check see refcount 2 at ordinary mutation sites and forced spurious copies, until Swift 4.2 moved most parameters to owned-by-default to stop it. Canonizing call depth as semantically load-bearing now would pre-commit I5's future calling convention to treat a parameter-passing detail as meaningful — precisely the mistake Swift already paid to unlearn.

(iii) Value-returning append (the rebind idiom)

Redesign the surface so byte_buffer behaves like every other Hey value: set buf = Bytes.append(buf, x), the buffer flowing through the return value on every call, no binding ever aliased.

Consistency: the purest option on the table — it doesn't carve out an exception, it makes byte_buffer conform. The precedent is Erlang's iolists: Erlang has no mutable builder at all, because output accumulates as cheap nested cons cells ([Acc, Chunk] instead of Acc ++ Chunk), and the efficiency guide explicitly warns off flattening early when the consumer — a port, or iolist_to_binary/1 — accepts a deep list as-is [DOCS]. Build a tree, flatten once at the boundary: genuinely good engineering, and it's the model a pure companion API would follow.

Performance: unchanged asymptotically — the rebind idiom, done right, is still one write per append; the cost is entirely in what it breaks. Migration cost on the three pinned sites: breaks all three. Spec 926 pins Bytes.append returning a length, not a buffer — the pinned stdout itself ("...2\n4\ntrue\nabcd\n8\n...") is those lengths printed directly, so this option changes a pinned return type, not an implementation detail. Spec 926's self-append aliasing (line 14) needs a fresh definition once "append" no longer mutates anything in place. And one_brc.hey's 8-appends-per-station loop, written today as bare statement calls whose return values are bound and discarded, would need to become a chain of rebinds through every one of those calls — a user-facing migration across the corpus, not a compiler change. Guard suite: the three cases become the enforced, intended contract — but only once the migration lands. Forecloses for I5 (b)/(c): nothing — and it doesn't have to compete with option (i). The right home for it is as a future pure-companion API, offered alongside the handle, if I5 stage (c) surfaces real demand for it.

(iv) Always-copy (value purity by brute force)

Give byte_buffer no special classification and no special surface: deep-copy its backing on every append, exactly like every other Hey value clones today.

Consistency: purest by construction, no exception anywhere in the type system. Performance is where this option dies. one_brc.hey's result builder makes A = 8S−1 appends into a buffer capped at 1 MiB, for S stations. In place, each byte gets written once, so total bytes moved is about the final output size, F. Copying the whole buffer on every append instead moves roughly Σ current-length ≈ A × F / 2:

At S = 10,000, that's ~10.4 GB moved to produce a ~260 KB result — about 40,000× the in-place cost. Even the small, canonical 413-station set pays ~1,600× (~18 MB moved for a ~10.7 KB result) [MEASURED] (spec 936 / one_brc.hey arithmetic). Migration: deep-copy clone breaks pinned case (A) directly, and with it spec 926 and the spec-936-pinned 1BRC product lane — "the accumulate-into-a-buffer idiom is load-bearing and spec-pinned; it is not a corner case" (spec 1218:43–51). It also converts the builder's O(n) linear cost into O(n²). Guard suite / I5: moot — the option is dead on arithmetic before it reaches either question, though it's a useful negative result: it's the concrete demonstration of exactly why a refcount system without a mutable-handle escape hatch can't cheaply support a builder workload, which is the argument for option (i) in reverse.

(v) Status quo — leave it undecided

Make no ruling. Keep byte_buffer nominally a value, keep the runtime doing exactly what it does today (refcount-shared, mutated in place), and keep the three guard cases permanently expected-red.

Consistency: none — this isn't a design, it's an unresolved contradiction left standing. Performance: identical to today, because nothing changes. Migration: zero, right now — which is exactly what makes this option look cheaper than it is. The rc table in §2 is the argument that it's worse than it sounds: whether an append writes through depends on how many stack frames deep the call happens to sit, which means correctness depends on an implementation detail — call depth — that no programmer has any reason to track and no compiler warning surfaces. Refactor a call site, extract or inline a helper for ordinary readability reasons, and behavior silently flips between "mutates my buffer" and "silently doesn't." That is the textbook definition of a trap. Guard suite: the three BYTE_BUFFER cases stay expected-red forever, by policy rather than by finding — a permanently red light nobody expects to turn green stops functioning as a signal at all. Forecloses for I5 (b)/(c): every future refcount decision has to keep carving around one deliberately undecided type, with no resolved example to build the next stage's calling-convention design against.

5. The recommendation

Recommendation, not a ruling — the decision is the maintainer's

Option (i): reclassify byte_buffer as a mutable handle, high confidence. It costs nothing the runtime doesn't already pay, breaks none of the three pinned specs, and matches two independent external precedents (Go's handle types, Clojure's transients) plus Hey's own existing carve-out for IO handles. Two riders come with it:

  1. Adopt a transients-style usage discipline in the docs: a byte_buffer has a single logical owner at a time, the same spirit as Clojure's rule that "it is an error if more than one thread manipulates a transient at once" [DOCS]. It's a documented convention today, not a compiler-checked one — the disclosed weakness from the TL;DR.
  2. Leave option (iii) open as a future pure-companion API — an Erlang-iolist-style tree builder — if I5 stage (c) surfaces real demand for a value-returning surface alongside the handle, rather than instead of it.

The reasoning that rules out trying to patch the refcount predicate instead (option (ii), or any future variant of it) comes from Swift, and it's worth stating precisely because it's the same lesson I5's later stages will need directly. Swift's own NIOCore ByteBuffer avoids the rc==2 copy-on-write trap structurally, not by refcount arithmetic: its mutating methods take self as inout (exclusive access), so the caller's binding is never counted as a second reference at the mutation site, and the uniqueness check that decides copy-vs-in-place (isKnownUniquelyReferenced) runs against the backing class under that exclusive borrow, not against the value's own binding count [SOURCE]. Swift learned this the hard way at the language level: guaranteed-by-default (borrowed) parameters once made copy-on-write checks see refcount 2 at ordinary mutation sites and forced spurious copies, until Swift 4.2 moved most parameters to owned-by-default specifically to stop it (Linux seat's ownership research notes, research-rc-ownership.md:43–47). Under Hey's current calling convention — where Bytes.append's "ownership" of its buffer parameter is indistinguishable, at the refcount level, from an accidental extra reference — that class of rc-predicate fix cannot be rescued cheaply. Option (i) sidesteps the whole predicate design space instead of trying to patch it.

Deeper: why not fix the predicate with a Perceus-style reuse check instead?

Koka's Perceus (Reinking, Xie, de Moura, Leijen; PLDI 2021) and Lean's runtime both do get in-place mutation out of a refcount check — but by checking for runtime rc==1 at the actual mutation site (a drop-then-reuse token: the paired constructor writes in place only if nothing else references the value, else it allocates), not by inferring "am I the direct caller or a nested one" from call depth [PAPER]. That's a genuinely different design axis from options (ii) or (v): it would require I5 to already have precise, per-mutation-site refcount checks with borrowed parameters that don't inflate the count — exactly the calling-convention machinery Swift's lesson says has to be built carefully, not exactly the "count stack frames" shortcut option (ii) proposes. It's a real future direction for I5 stage (b)/(c) in general; it is not a fix for byte_buffer's specific non-monotonic contract measured in §2, because that contract was never actually about sharing in the first place.

6. What the guard suite becomes

Under option (i), the BYTE_BUFFER family in the value-semantics guard suite flips from expected-red to retired-by-design: the same three cases stay in the fixture file as a record of the reasoning, with a one-line doctrine note in place of the open question — byte_buffer is HEY_BYTE_BUFFER, a mutable handle kind, company of HEY_IO_HANDLE and HEY_ACTOR, and these three cases are retired, not pending. Nothing else in the guard suite moves. The rest of it — arrays, strings, structs, every ordinary value kind — stays exactly as load-bearing for I5's later stages as it was before this question was ever raised.

Glossary

byte_buffer
Hey's append-many-times output builder; allocate once, append repeatedly, flatten once.
value semantics
Every Hey value copies on handoff; nobody downstream can ever observe a mutation you make to what you passed them.
refcount (rc)
A count of how many live references point at the same backing memory; the basis for deciding whether a mutation can happen in place.
write-through
A mutation to shared backing memory that is visible through every binding pointing at it, not just the one that made the change.
call depth
How many nested function calls separate a mutation site from the original binding that holds the value.
copy-on-write (COW)
Share a backing store until the moment of mutation, then copy first if anything else still references it.
transient (Clojure)
A scoped, explicitly mutable builder over an otherwise-persistent data structure, used only inside the function that produced it.
iolist
Erlang's alternative to a mutable builder: nested lists and binaries consed cheaply, flattened once at the output boundary.
I5
See the shared glossary.
