Articles · Hey on Windows · a practical guide

You built a Windows app with Hey. Now make Windows trust it.

You cross-built MyQueue.exe on a Mac. You copy it to a Windows PC, double-click it, and a blue box fills the screen. This guide gets you from that box to a program that opens for your customers, including the ones on locked-down work laptops. It also covers making command-line tools and windowed apps that feel native, and what changes when Hey itself runs on Windows in release 607a.

What you'll see

Windows protected your PC

(the rest of the wording varies)

Run anyway

A drawing, not a capture, showing only the two phrases Microsoft documents; the colour is from memory. Microsoft's own table says an unsigned download gets "Windows protected your PC" and the user "must choose 'Run anyway' before the app can run"C9. On some PCs you won't even get the button.

By the end you'll be able to:

  • say exactly why Windows stopped your program, and which of four checks did it;
  • test it on your own PC, a free evaluation virtual machine (VM), and someone else's work machine, the honest way;
  • pick a signing route that fits who you are, and know what it does and doesn't fix;
  • make a Hey command-line tool (CLI) or windowed app (GUI, graphical user interface) that behaves like a native Windows program.
Do this first: a two-minute win

See what Windows will see. On your Mac, with Homebrew's LLVM installed, in the folder that holds your MyQueue.exe (or give its full path):

$(brew --prefix llvm)/bin/llvm-objdump -p MyQueue.exe | grep -E 'Subsystem|DLL Name|Security'

For the hey_windows 0.1.0 exe that ran on Windows (its SHA-256 fingerprint starts 07ef5053), that prints a GUI subsystem, six system DLLs (dynamic-link libraries, the files Windows functions live in), and this:

Entry 4 0000000000000000 00000000 Security Directory

All zeros means no signature. Run the same command on the WebView2Loader.dll beside it and entry 4 has an offset and a size (00002850): Microsoft signed that file, as "Microsoft Corporation" through "Microsoft Code Signing PCA 2011". Your exe is the unsigned half of the folder.

Where your exe travels, and where Windows can stop it

Hey isn't on the Windows PC at all yet. Hey checks your app's settings on the Mac, a C compiler in a Linux container builds the exe, and the customer's PC does the rest. Two of the six stops are where things go wrong, and one of them is a stop you haven't made yet.

Four checks decide whether it opens

When the browser saves your download, Windows attaches a small hidden note to the file that says it came from the internet. Microsoft calls it the Mark of the WebC30. That note is what makes SmartScreen look. Then three other things may look too.

CheckWhat it looks atWhat fixes it
SmartScreenReputation of the file and its publisher. Unsigned files start from nothing every versionC9.Downloads over time. "It can take several weeks and hundreds of clean installs"C9. Signing "can allow certificate reputation to build, potentially avoiding warnings on new files"C9.
Smart App Control (Windows 11)"Unknown, unsigned code [is] blocked by default"C26. Its checks "apply to all executable files, not just those downloaded"C9.A signature from a certificate authority (CA) in Microsoft's Trusted Root Program. When the service can't make a prediction, it "will still allow an app to run" that's signed that wayC26. There's "no way to bypass" it per appC27.
Defender antivirusWhether the file looks like malware. Go's own FAQ says scanners are "often confused by the structure of Go binaries"C13; Nim has the same historyC14. A new language like Hey should expect it (our inference).Submit the file to Microsoft as a "Software developer", choosing "Incorrectly detected as malware/malicious"; 50 MB maximumC15C16.
IT policyWhatever the organisation set: no "Run anyway", allow-lists, managed installsC21C23.IT's approval. See what to hand them.
There are no dumb questions

Doesn't paying for a signature make the warning go away? Not on day one. Microsoft's Artifact Signing FAQ says the prompt "stops appearing once the file hash has sufficient download history"C1. Its SmartScreen page says "EV certificates no longer bypass SmartScreen"C9: EV means extended validation, the most expensive kind. What a signature buys at once is your publisher name in the prompt, a way through Smart App Control when it has no verdict on your appC26, and reputation that can carry over to your next releaseC9.

Test on real Windows, easiest first

Every rung below tests your exe, the one you built. Climb only as far as you need.

  1. Lowest frictionYour own PC, unsigned build. Download the zip through a browser so it carries the internet mark, then choose Run anyway. Or right-click, Properties, Unblock, which removes the mark; PowerShell's Unblock-File does "the same operation"C29. Do this only for a file you built or checked. It won't help if Smart App Control is on, because that checks every executable, marked or notC9.
  2. Free, repeatableA Windows 11 evaluation VM. Microsoft offers a 90-day evaluation with no product keyC36; dockur/windows runs it in a container on a Linux host and says the licence is your responsibilityC37. This is where 0.1.0 passed. Next time, download the file through the browser inside the VM, so it carries the mark like a customer's copy, and write down whether Smart App Control is on.
  3. After signingThe same VM, signed build. Expect your publisher name in the prompt, and maybe still "unrecognized" until reputation buildsC9. Smart App Control should let it through when it has no verdictC26.
  4. A real personA friend's own Windows 11 PC. Same as rung 1 or 3. On a clean install with Smart App Control on, an unsigned exe is blocked, and signing is the only fix Microsoft offersC27.
  5. Highest frictionSomeone's work machine. IT decides. Don't ask the person to work around policy; send IT the package in the next section.
Watch out

Copying the exe into a VM over a shared folder may skip the internet mark, so you'll see a friendlier Windows than your customers do. Download it inside the VM.

On a work machine, IT decides: hand them this

Microsoft tells administrators to set SmartScreen to "Warn and prevent bypass"C21, so a laptop set up the way Microsoft recommends has no Run anyway button at all. That's the policy doing its job. Your job is to make the yes easy for IT.

IT's toolHow it can allow your appWhat it needs from you

AppLockerPublisher rules need a signed file; otherwise hash or pathC24.A signed file.

Do this: the IT page for your app
  • The signed, timestamped files, and the publisher name exactly as it appears in the certificate. Keep it the same every releaseC9.
  • Every executable file in the folder: MyQueue.exe and Microsoft's WebView2Loader.dll. Hash rules are per file.
  • Product name, original file name and file version from the version resource, unchanged in meaning between releasesC23.
  • SHA-256 of each file, and a note that App Control builds its hash rules from the files themselves, since it hashes differentlyC23.
  • A fixed, versioned HTTPS download address whose bytes never change.
  • A silent installer, so IT can deploy it through IntuneC25.

Sign it, so Windows knows who made it

Authenticode signing, Windows' code-signing format, writes a certificate into the exe that says who published it. The CA/Browser Forum, the body that sets rules for public certificate authorities, now requires the private key to live in hardware, a logged cloud key or a signing serviceC10, so there's no longer a .pfx key file to keep on a build box. Which route you can take depends on who you are.

You areRouteCost and catch
An individual in the US or Canada, or an organisation in the US, Canada, EU, UK, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway or IsraelC2Azure Artifact Signing (formerly Trusted Signing)$9.99 a month for 5,000 signatures; $99.99 for 100,000C5C4. Needs a paid Azure subscriptionC1. Identity check, 1 to 20 business days for organisationsC2. Certificates last three days, so every signature must be timestampedC3.
An open-source project with public buildsSignPath FoundationFree, but the certificate names "SignPath Foundation" as publisher, and every release needs manual approvalC12.
Anyone elseAn OV certificate (organisation-validated) from a certificate authorityA hardware token or cloud keyC10; at most 460 days per certificateC10. Price not researched.
Anyone, for an MSIX package (Windows' signed app-package format)Microsoft StoreMicrosoft re-signs Store MSIX packages and users "will never see a SmartScreen warning"C9. Individual registration is freeC32. A Store listing of a plain exe or an MSI (Windows Installer package) must already be signed by youC31.

Our case: a US LLC, JayTeeSF LLC

My Queue's publisher is a company, so it takes Artifact Signing's organisation route. That's open to US organisationsC2, and Microsoft's quickstart lists what the request needsC2:

  • the legal business name, which becomes the publisher name. You "can't use a custom Common Name (CN) or a custom Organization (O)": the name "must always be the legal entity's validated name"C1. For us that's the LLC's registered name, presumably "JayTeeSF LLC" (we haven't checked the state record);
  • the company's website, a business identifier, its business address, and a monitored email on the company's own domain plus a second address on the same domainC2;
  • one person who represents the company and passes an ID check against a government-issued IDC2;
  • if Microsoft asks for documents, things like the business registration or articles of incorporation and the domain registration, "issued within the previous 12 months"C2.

It takes "from 1 to 20 business days"C2, and costs $9.99 a month on the Basic planC5.

Watch out: a young company may be refused

Microsoft's pages list no minimum company age and don't mention D-U-N-S numbers (Dun & Bradstreet's company IDs). But a volunteer moderator on Microsoft's Q&A site writes that a business "must have been in operation for at least three years"C41; that's not a Microsoft statement, and we couldn't confirm it. What Microsoft does say is final: "if we can't validate the information, we can't onboard you"C1. If JayTeeSF LLC is young, apply anyway, and keep the next best thing ready.

Next best: an OV certificate from a certificate authority. The CA/Browser Forum rules ask the CA to verify the company's legal identity and address through a government registry, a reliable third-party database, a site visit or an attestation letter, and to verify that the person asking is authorised. A company formed less than three years ago doesn't fail; the CA must also verify the requester's own identity. Three years in existence is one way a CA may verify "operational existence", and that check applies only to EV certificatesC10.

Signing from a Mac or Linux. Jsign is "platform independent" and has an Artifact Signing store type that timestamps automaticallyC6. It isn't on Microsoft's list of supported integrationsC3. Microsoft's own GitHub Action "can only be executed on Windows runners"C8: a hosted Windows machine that only signs, so you still never own one. osslsigncode signs exe files with a token, but doesn't mention Artifact SigningC7.

# Jsign with Artifact Signing (shape from Jsign's documentation; names are placeholders)
jsign --storetype TRUSTEDSIGNING \
      --keystore eus.codesigning.azure.net \
      --storepass "$AZURE_ACCESS_TOKEN" \
      --alias my-account/my-profile \
      MyQueue.exe
Watch out

Don't re-sign WebView2Loader.dll. It already carries Microsoft's signature, and Microsoft's advice is not to modify signed filesC9. Sign your own exe after the last byte changes, never before.

Checklist: before customers download MyQueue.exe

My Queue's Windows app

  • Icon, version details (CompanyName and copyright JayTeeSF LLC) and an embedded manifest built in 0.1.2, not yet run on Windows
  • Run 0.1.2 on the evaluation VM, downloaded inside it to do
  • Sign in on the VM, close, reopen: does it stay signed in? to do
  • Apply for Artifact Signing as JayTeeSF LLC; if refused, buy an OV certificate to do
  • Sign and timestamp MyQueue.exe; leave Microsoft's DLL alone to do
  • Scan the signed build; submit any false alarm as a software developer to do
  • Versioned HTTPS download on the app's own domain, with SHA-256 published to do
  • The IT page from the section above to do
  • A note for early users: expect an "unrecognized app" prompt showing our name for a whileC9 to do
  • An installer and a winget entry (winget is Windows' built-in install command), or MSIX in the Store planned (hey_windows roadmap)

Any Hey Windows app or CLI

  • Sign every release with the same identity, an RSA key, and a timestampC9C23C3. Self-signed counts as unsignedC9.
  • Embed a version resource and a manifest in every exe.
  • Never change a file after signing it.
  • Publish SHA-256 hashes and versioned URLs.
  • Expect antivirus false alarms on a new toolchain; report themC13C15.
  • Behave plainly and uninstall cleanly: Microsoft's unwanted-software criteria include skipping "standard install or uninstall features"C17.
  • Test on a fresh VM with a real download, and note Smart App Control's state.
  • Write the IT page; never tell users to defeat policy.

Make a Hey CLI behave like a Windows tool

A Windows developer types hey-tool in PowerShell and expects it to act like git or dotnet: Unicode output that reads right, Ctrl+C that stops cleanly, tab completion. Try one prediction first.

Predict it

Your manifest sets the UTF-8 code page (the character encoding Windows assumes for text). You print "café ✓" to the console. Is it right?

Not guaranteed. The console has its own code page, "the system's OEM code page" by defaultB38 (an older, locale-specific encoding). Microsoft doesn't say the manifest changes it, so assume it doesn't (our reading). Rust and Go both sidestep it: when the output is a console they convert to UTF-16, Windows' native text encoding, and call WriteConsoleW; when it's redirected they write the bytesB40. Hey should do the same.

Make a Hey GUI: three ways to draw a window

Hey has no user-interface toolkit of its own, and neither do Go or Zig. So the question is which of Windows' three ways you borrow. Three terms first: Win32 is the programming interface Windows itself offers; COM (Component Object Model) is the binary object interface much of Windows is built on, and WinRT (Windows Runtime) is the newer layer over it that WinUI 3, Microsoft's newest UI kit, uses.

XAML is WinUI's markup language, and Microsoft says its compiler "is not yet fully shared"A6; a community commenter says it's supported only through MSBuildA9. A community sample calls WinUI without XAML "an unsupported scenario"A19.

Our recommendation: WebView2 now, because it works; native Win32 next, because nothing blocks it; WinUI 3 written in code, with no XAML, as a later option once Hey can call COM and WinRT. The Windows App SDK (software development kit) starts its runtime through three C functionsA15, which any language that can call C should be able to use (our inference).

Native AOT is C#'s ahead-of-time compiler. Delphi's documentation site refused every request, so its cells come from Embarcadero's product page and Wikipedia. "Not sourced" and "none found" mean we found no page either way. The last row's "no" means Microsoft names only C# and C++A14.

The answer: nobody outside Microsoft fully matches C# and C++, and Rust comes closest. Microsoft's own windows-rs gives Rust Win32, COM and WinRT generated from metadata, lets Rust write COM and WinRT objects, and now drives WinUI 3 from codeA17A18. Swift's flagship Windows app, Arc, used WinUI 3 the same way, and Arc is now being shut downA25. What no one outside Microsoft has is the XAML compiler, the Visual Studio designer and official support.

Hey can match this (Rust shows how)

Bindings generated from win32metadata; calling and writing COM; WinRT; PDB debugging in Visual Studio and WinDbg; services, pipes, registry; signed installers; package identity for notifications, which an identity-only package gives without full MSIXA46.

Blocked, and the next best thing

XAML compiler: not buildable from source, and one WinUI DLL "will not be OSS" (open source)A6. Next best: WinUI written in code.
Metadata licence: the win32metadata repository is MIT-licensed, but the package holding the .winmd metadata files is under Windows SDK termsA1A3. Next best: generate bindings at build time, and check before shipping the file itself.

What works now, what's planned, what's proposed

The five open questions, answered in full

If you're the Maintainer deciding 607a, these are the answers the research supports, with what each costs. Each is a recommendation until the Hey team records it.

1. Does 607a also take the cross-compile work pencilled for v608?

Yes. Build for every target from every host, as Go and Zig do.

Who does it
Go: "you are always cross-compiling"B61. Zig "builds for all supported targets independently of the host"B62. C#'s Native AOT "does not support cross-OS compilation"S32, which is the opening.
Cost
The Hey team's estimate: 5 to 9 engineer-weeks for the cross-compile work, plus 3 to 6 for Windows itself.
Next best
If 607a runs long (our suggestion): Windows to Linux first, Windows to Mac after, because the Mac also needs a code signature Hey computes itself.

2. How much C library do Hey's Windows programs use?

None as the goal; Windows' own Universal C Runtime (UCRT) while the runtime is still C. The Hey team's provisional pick stands.

Who does it
Go calls kernel32 directlyS16; Zig's standard library now sits on ntdllS23. For the C stage: the UCRT "is a Microsoft Windows operating system component" on Windows 10 and later, and a bundled copy is ignoredB1. mingw-w64 made it the default in version 12B9; Rust's gnullvm targets and Zig use it tooB13B11.
Cost
A C dependency stays until the runtime is rewritten in Hey, which the Hey team sized at 9 to 18 engineer-months.
Avoid
vcruntime, whose redistribution is limited to Visual Studio licenseesS35, and the old msvcrt.dll. Our 0.1.0 exe imports msvcrt.dll, so hey_windows should move to the UCRT flavour too.
Unsourced
No Microsoft page says ucrtbase's exports are a stable contract for other toolchains. It works for mingw-w64, Rust and Zig in practice.

3. Encrypted connections (TLS, Transport Layer Security)

Changed: Hey's own TLS with Windows checking the certificates is the end state; Windows' built-in TLS (Schannel) is the first step, not the destination.

Why Schannel was a fair pick
Hey stays one file, outgoing HTTPS already works this way, and Windows' own curl.exe uses itB27.
Why it changed
Schannel has no TLS 1.3 on Windows 10B16, and its quirks are machine-wideB31. Go builds chains with CertGetCertificateChain and checks them with the SSL policy (SSL is TLS's older name)B26; rustls-platform-verifier exists for "enterprise CA deployments"B25. That fits the no-C goal, gives TLS 1.3 everywhere, and still honours the roots IT installs.
Cost
Hey owns protocol and crypto code, and its security fixes. Windows' verifier has had bugs too: Go double-checks ECDSA signatures because of the published vulnerability CVE-2020-0601B26.
Never
A bundled root list or OpenSSL as the default: Microsoft's own page says Git and Python break behind company TLS inspection for exactly that reasonB32.

4. Signing

Sign every exe and installer from the first public release, with the same identity.

How
Artifact Signing if the publisher is eligibleC2, which a US LLC such as JayTeeSF LLC is by country, signed from a Mac or Linux with JsignC6 or on a Windows runner with Microsoft's ActionC8. Otherwise an OV certificate on a hardware key, or MSIX through the Store.
Cost
$9.99 a month, an identity check of 1 to 20 business days, and a paid Azure subscriptionC5C2C1.
Correction
Signing doesn't end SmartScreen warnings at onceC1; it gets a CA-signed app past Smart App Control when there's no verdict, and lets reputation buildC26C9. Artifact Signing has country and individual-versus-organisation limitsC2.

5. Is the C++ and C# integration bar a requirement?

Yes. The bar is what Rust reaches with windows-rs: everything except the XAML compiler, the designer and Microsoft's support list.

607a
The Hey team's ten items: call-trace tables for debuggers; debugging in Visual Studio; default app settings (UTF-8, long paths); a correct console; calling any Windows system file, and being called back; icon and version details; Windows crash reports; ready-made Hey names for Windows functions; services, pipes, registry, Event Log and process groups; a signed installer, winget entry and published debug files.
Cost
About sixteen pieces of work by the Hey team's estimate, on top of question 1's weeks.
Later
Calling and writing COM, WinRT, WinUI 3 from code, package identity, Windows on Arm.
Next best
Where XAML is blocked, WinUI from code, or native Win32 with version 6 controls, PerMonitorV2, and the DWM dark title bar and Mica.
