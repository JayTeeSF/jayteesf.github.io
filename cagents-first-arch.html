Cagents · architecture and status · 29 August 2026

A Git-backed operating system for humans and agents.

Cagents is being built around one unusual constraint: the durable history of the work should remain inspectable, cloneable Git—not disappear into an opaque SaaS database. The hosted product adds accounts, subscriptions, realtime access, indexing and native clients around that record without replacing it.

Where the system stands

  • The coordination core is now a distinct product layer. generic_cagents owns the v3 coordination engine and CLI; the old web-scaffolder experiment has been archived out of the active surface.
  • The live cagents repo has been migrated to the bounded v3 model. Messages, task state, transcripts, dockets, future prompts and participant startup state are file-backed, while old giant journals and obsolete authorities have been archived.
  • The restart-critical core is cross-OS tested. The portability/restart work was specifically hardened for macOS and Linux; the current generic_cagents line is 0.5.0-core.3.
  • The hosted application is now a separate repository. cagents-application owns the cloud server and shared web/macOS/iOS product surfaces.
  • The hosted server has real Hey code for account, organization, workspace, repository-binding and authenticated route composition. It is beyond diagram-only design, but it is not yet a production-certified cloud deployment.
  • Managed GitHub repos now target JayTeeSF-Cagents. Existing personal JayTeeSF/*_cagents repos remain a supported import/legacy path.
  • Managed repository provisioning is no longer a GitHub-shaped worker. The worker now dispatches by provider and persists provider identity in the binding. GitHub private-repository creation is implemented with real Hey HTTP; GitLab, Bitbucket, Azure DevOps and generic Git still need their provider adapters.
  • Stripe has its own Hey package boundary. hey_stripe exists, but live Stripe HTTP and cryptographic webhook verification remain intentionally unclaimed until the exact Hey runtime/package path is accepted.
  • Web, macOS and iOS share one client capability contract. Native builds, App Store/TestFlight distribution, realtime push and full interaction parity remain unfinished.

The architecture

The central split is deliberate. Git is the durable coordination record. Cagents Cloud owns identity, access, subscription and operational state. The client applications talk to the cloud service; they do not need a local Git checkout and they never receive Git-provider credentials.

What lives where

Git is authoritative for the work

A customer's XYZ_cagents repository carries the durable, auditable history that should survive the hosted service itself:

  • human and agent messages;
  • visible response transcripts and concise reasoning summaries;
  • tasks and task events;
  • task-local sub-agent runs;
  • research and evidence;
  • decision dockets and rulings;
  • artifacts and artifact references;
  • durable future-agent prompts and trigger definitions.

The cloud database is authoritative for the service

Cagents Cloud owns state that is not part of the intellectual/work record:

  • users and email verification;
  • sessions and authentication;
  • Cagents organizations, invitations, memberships and roles;
  • workspace-to-repository bindings;
  • billing customers, subscriptions and entitlement state;
  • webhook idempotency, jobs, leases, device state and operational caches.
The derived-index rule: coordination search/report rows may live in HeyRecord-backed databases for speed, but deleting that index must not delete the underlying coordination truth. Durable coordination semantics must be reconstructable from Git.

Signup should feel simple even though the system underneath is not

1 · Create accountCagents identity, verification and session.
2 · Create organizationThe product's team/workspace boundary; not the same thing as a GitHub organization.
3 · Provision workspaceServer creates or binds a private cagents repository.
4 · Start workingWeb/macOS/iOS see the same workspace through Cagents Cloud.

The managed GitHub default is now JayTeeSF-Cagents. A free or paid user should not need to know that. The server-side GitHub adapter can create the private repository request in Hey, and provisioning records the result through a provider-neutral binding before initialization/indexing. Technical users can later clone/export/transfer the repo or attach a customer-managed repository.

Repository ownership is a product feature

Cagents deliberately avoids making customer work hostage to an application database. A managed repository can start under the Cagents provider account and later be transferred or replaced by a customer-managed remote. The binding changes; the Cagents workspace identity does not.

Cagents-managed

Fast signup. Cagents provisions the private repository under a managed provider account, operates it through server-side credentials and lets the customer export/transfer it.

Customer-managed

A technical customer connects an existing GitHub/GitLab/other Git account or repository. Cagents gets narrowly scoped server-side access while the customer retains repository ownership.

No training-data business model. Private workspace content exists to operate the customer's Cagents service. The architecture does not depend on selling or training on customer conversations, source-adjacent research or internal decision history.

Billing without making Stripe the product

Cagents Cloud owns effective entitlements. Stripe is the initial payment/subscription processor. The intended web flow is Checkout → verified webhook reconciliation → Cagents entitlement. A successful browser redirect is not itself authorization. The Customer Portal handles payment method, invoice and cancellation self-service.

For the first iOS release, the current design treats the App Store application as a free companion to a Cagents Cloud account. It can recognize an existing paid web entitlement without embedding Stripe card purchase UI. A future StoreKit adapter can reconcile Apple purchases into the same entitlement model if in-app purchase becomes a product requirement.

Why there are three repositories instead of one giant product repo

RepositoryResponsibility
cagentsThe durable coordination data plane for the current team: messages, tasks, research, decisions, transcripts, participant startup packets and maintainer runbooks.
generic_cagentsThe reusable coordination engine: CLI, v3 semantics, validation, bounded context, task/sub-agent operations, docket/future-prompt operations and repository initialization.
cagents-applicationThe hosted commercial product: cloud server, account/organization/subscription state, repository-provider adapters and the web/macOS/iOS clients.

Supporting Hey packages such as hey_record, hey_stripe, hey_ui_contract, hey_mac and hey_ios remain reusable packages rather than being buried inside the application.

Finish email delivery/verification, secure credential/session lifecycle, organization invitations, abuse/rate controls, password/passkey/social-login policy and recovery flows.

Clients

Control-plane parity

Native

Realtime

Attention without vigilance

Add server push/realtime sync, device notifications, deep links, background refresh and the human-attention surface that lets one person supervise many agent streams.

The product promise

Agents can be numerous and disposable; the work record should not be. Cagents is trying to make agent-heavy development feel like operating a coherent team: bounded context, explicit ownership, durable evidence, searchable history, deliberate decisions and a human-attention surface—all while keeping the underlying intellectual history in ordinary Git repositories the customer can inspect and take with them.
