How to run distributed Hey across two machines

A copy-pasteable guide to bringing up two Hey nodes over TLS — one on Linux, one on macOS — and running send, call, monitor, and incarnation rejection across the wire between them. Everything below was run on real hardware, and the transcripts are the real output, not a mock-up.

Verified on real hardware. The four-example gate is green over a real macOS ↔ Arch Linux Ethernet link on Hey 551a (01 and 04 over TLS, 02 and 03 over TCP). The commands and output here are exactly what those runs produced.
Interpreted today. The examples run through the interpreter (build/heyc <ex> --run), not the native binary: the LLVM back-end does not yet lower the cross-unit distribution and codec calls — the extern-facade frontier. Interpreted over real TLS across real NICs is still a genuine distributed run.

TL;DR

  • You can run two Hey nodes on your own two boxes today. Build heyc, set the HEY_DIST_* seam — two of its variables carry your server's LAN IP, the rest the accept window and TLS material — and run examples 01–04 from examples/distributed/.
  • One fixture certificate authenticates any peer. The client sets SNI=localhost; OpenSSL checks the cert's DNS:localhost name against that, independent of the peer's actual IP — so the same test cert works at 127.0.0.1, a container bridge, or 192.168.1.188. No per-host cert.
  • The only porting edit is the HEY_DIST_* env seam. The examples are hard-coded to 127.0.0.1; the environment variables override bind host, peer host, the accept window, and the TLS material — nothing in the source changes.
  • Distribution is a library, not a VM. Remote.send is at-most-once, Remote.call is ordinary messaging with a correlation id, and a restarted node presents a new incarnation so stale references are rejected, not routed.
  • Disclosed limits. The accept is single-shot — do not probe the port with nc — and everything runs interpreted for now. Both are explained in the gotchas box below.
  • Falsify it yourself. The exact commands, the fixture cert path, and the real transcripts are all here. Two boxes on one LAN reproduce the whole gate.

What distributed Hey actually is

Distributed Hey is stdlib-first: no distributed VM, no bytecode shipping. Distribution is runtime and library services on the actor runtime, so joining two nodes means starting an explicit node value and sending messages, not deploying a cluster. Four small primitives carry the model, and you watch each one run below: Node.start, an at-most-once Remote.send, a correlated Remote.call (a request_id, a reply_to, an ordinary send and a bounded wait — not a second RPC protocol), and a Distributed.monitor that reports observed peer loss (suspicion, never perfect detection — a partition and a death look the same). The safety net is the incarnation: a NodeId carries a fresh cryptographic id minted each process start, so a restart is a genuinely new logical runtime and a RemotePid bearing a prior incarnation is rejected, not routed. No registry, no Rinda-style tuple space, no gossip in v0 — and one documented deviation you will not trip over here: socket IO stays in its owning context.

Set up the TLS certificates

You do not generate anything. The repository ships a complete fixture chain under test/fixtures/tls/: a CA (CN=Hey Test Root CA), a server certificate (CN=localhost, with subjectAltName = DNS:localhost, IP:127.0.0.1), and the openssl.cnf that produced them. That is everything both sides need.

The key insight, verified on the wire: the client presents SNI=localhost, and OpenSSL checks the certificate's DNS:localhost name against that SNI — independent of the peer's real IP.

That is why this is easy. You are not verifying "the machine at this address" but "a peer holding the key for the name localhost," and the name travels in the handshake — so the same fixture cert authenticates node B at 127.0.0.1, a container bridge, or 192.168.1.188, with no per-host cert and no regeneration when the IP changes. A client that presents the wrong CA fails the handshake closed, no application data exchanged — the failure mode you want.

Walk-through: run 01–04 across the two boxes

Prerequisites, on both boxes: the repository cloned, heyc built (its build/heyc present), and the test/fixtures/tls/ and examples/distributed/ trees in place. Server runs on the Linux box (node B), client on the macOS box (node A). On each machine, first source the toolchain environment in the same shell you run from — . ./bin/htgz-env.sh — which is what puts build/heyc on your path for the commands below. Every command is verbatim.

01 — ping/pong over TLS

Start the server on node B. The wide accept window gives you time to start the client by hand on the other box:

# node B (Arch Linux) — server
. ./bin/htgz-env.sh
HEY_DIST_CERT=test/fixtures/tls/server-cert.pem \
HEY_DIST_KEY=test/fixtures/tls/server-key.pem \
HEY_DIST_BIND=192.168.1.188 \
HEY_DIST_ACCEPT_MS=900000 \
build/heyc examples/distributed/01_ping_pong.hey --run -- server 9101 tls

Then dial from node A. The client points HEY_DIST_PEER at B's IP, verifies against the fixture CA, and presents SNI=localhost:

# node A (macOS) — client
HEY_DIST_CA=test/fixtures/tls/ca-cert.pem \
HEY_DIST_SNI=localhost \
HEY_DIST_PEER=192.168.1.188 \
build/heyc examples/distributed/01_ping_pong.hey --run -- client 9101 tls

Node A prints its handshake and the reply — the real output:

A handshake ok with peer=B incarnation=inc-8c48db05...
A got reply=pong echo.ping=hello from A from=node-B

A observed B's advertised incarnation, so the peer on the other end of the TLS session is genuinely the remote node over the wire, not a loopback stand-in — the whole point of the first leg.

02–04 — send, monitor, and incarnation rejection

The remaining three examples run the same way — same server 9101 / client 9101 positional pattern — swapping the example file and the transport argument. Legs 02 and 03 run over tcp, so drop the four TLS variables (HEY_DIST_CERT/HEY_DIST_KEY on B, HEY_DIST_CA/HEY_DIST_SNI on A) and keep only the addressing seam:

# 02 send / 03 monitor — transport arg is literally "tcp"
# node B (server): HEY_DIST_BIND=192.168.1.188 HEY_DIST_ACCEPT_MS=900000 \
    build/heyc examples/distributed/02_remote_actor.hey --run -- server 9101 tcp
# node A (client): HEY_DIST_PEER=192.168.1.188 \
    build/heyc examples/distributed/02_remote_actor.hey --run -- client 9101 tcp
# 03 monitor: same as 02, swap 02_remote_actor.hey -> 03_remote_monitor.hey

# 04 — over TLS, same variables as 01, transport arg "tls"
#   swap the file to 04_stale_incarnation.hey

02 remote_actor (send) demonstrates at-most-once delivery. Node A prints A sent (accepted for transport, at-most-once); node B prints B inbox received event=user_joined. "Accepted for transport" is the honest phrasing — the send call succeeded, and on this run the event did land in B's inbox.

03 remote_monitor demonstrates real-NIC failure detection. Node A prints A monitoring remote pid actor=pong on node=B; then you take B away — Ctrl-C or kill the server process on the Linux box — and A observes the loss and fires both notifications (this is observed loss: a network partition would look exactly the same):

A observed connection loss code=peer_closed
A watcher NODE_DOWN node=B reason=peer_closed
A watcher DOWN remote_pid.node=B actor=pong reason=peer_closed

04 stale_incarnation demonstrates the safety net over TLS. Node A handshakes, then deliberately sends to a prior-incarnation reference, then makes a current call:

A handshake ok peer_incarnation=inc-239d4256...
A stale-incarnation send dispatched (server must reject, not route)
A current-incarnation call reply=pong

The prior-incarnation reference is rejected server-side while the current call is answered. A restart presents a different incarnation, so there is no silent resurrection of an old reference.

Gotchas

  1. The accept is single-shot. establish_accept serves exactly one connection and then the server exits. Do not probe the port with nc or any raw-TCP tool first — a non-TLS connect burns the one accept and your real client will find nothing listening. Connect once, cleanly, with the client command.
  2. Everything runs interpreted today. Use build/heyc <ex> --run. The native LLVM path does not yet lower the cross-unit distribution and codec calls (the extern-facade frontier). Interpreted over real TLS across real NICs is still a valid distributed run — it is how the gate above was measured.
  3. Watch string building on large frames. Codec.encode is O(n) (measured slope near 1.0 — a chunk-list plus a join), so keep large frames on that path. A bare s = s + x accumulation is still O(n²) at the language level; do not hand-roll frame assembly with string concatenation.

Two nodes in Docker, on one Linux host

No second machine? Two containers on a Docker bridge are two separate network stacks talking over a real veth/bridge — not the loopback kernel shortcut — so it is a genuine cross-node run. This was verified container-to-container (reply=pong) on Linux; the commands below are that verified run.

Fix the image first (five real build breaks)

The stock docker/linux/alpine/Dockerfile cannot build this version as shipped — most notably a genuine regression: the distributed TLS work added #include <openssl/err.h> to the runtime, so build-base ruby alone fails with openssl/err.h: No such file or directory. The full package line the build needs:

apk add --no-cache build-base ruby openssl-dev openssl python3 clang llvm

openssl-dev/openssl supply the TLS headers, python3 builds the stdlib archive, and clang/llvm emit it; also mkdir -p /usr/bin/subcmds before the subcommand symlinks. Build the build target — the slim dev/dist image ships the hey runner but not a --run-capable heyc plus compiler source, so you want the full /src tree:

docker build -f docker/linux/alpine/Dockerfile --target build -t hey-build .
# inside: /src/build/heyc --version

Run two containers on a bridge

Create a user-defined bridge, start node B bound to 0.0.0.0 inside its container, then dial from node A by container name — Docker's DNS resolves it to the bridge IP:

docker network create heynet

# node B (server) — bind 0.0.0.0 inside the container
docker run -d --name heyNodeB --network heynet \
  -e HEY_ROOT=/src -e HEY_STDLIB_PATH=/src/stdlib -e HEY_COMPILER_BUILD_DIR=/src/build \
  -e HEY_DIST_BIND=0.0.0.0 -e HEY_DIST_ACCEPT_MS=300000 -w /src hey-build \
  /src/build/heyc examples/distributed/01_ping_pong.hey --run -- server 9101 tcp

# node A (client) — connect by CONTAINER NAME (docker DNS -> bridge IP)
docker run --rm --network heynet \
  -e HEY_ROOT=/src -e HEY_STDLIB_PATH=/src/stdlib -e HEY_COMPILER_BUILD_DIR=/src/build \
  -e HEY_DIST_PEER=heyNodeB -w /src hey-build \
  /src/build/heyc examples/distributed/01_ping_pong.hey --run -- client 9101 tcp

Node A reaches B by container name across the bridge — two separate network stacks — and prints the real reply:

A handshake ok with peer=B incarnation=inc-23514a08...
A got reply=pong echo.ping=hello from A from=node-B

For TLS, bind-mount the fixture certs (the distribution bundle excludes test/fixtures, so they come from the host): add -v "$PWD/test/fixtures/tls:/certs:ro", then HEY_DIST_CERT/HEY_DIST_KEY=/certs/server-*.pem on B and HEY_DIST_CA=/certs/ca-cert.pem HEY_DIST_SNI=localhost on A. As on real hardware, SNI=localhost verifies the fixture cert over the bridge IP — no regeneration.

Partition demo. With a monitor (03) live, docker network disconnect heynet heyNodeB and node A observes NODE_DOWN; docker network connect and reconnect, and B comes back with a new incarnation — the same failure and restart semantics as the physical peer kill above.

The Docker image fixes are committed on the Linux verification branch; the two-container run above was executed end-to-end on Docker 29.6.2.

What's next, and what you can build

You now have the mechanism: two nodes, a TLS link with a verified server identity, at-most-once send, correlated call, monitored failure detection, and incarnation-guarded references — enough to build a real distributed program, with the runtime carrying the coordination so your code stays ordinary message-passing Hey. Two showcase demos already ride this path: 05_mandelbrot, a distributed tile render, and 06_wordcount, a MapReduce — pointers to what the four primitives compose into.
