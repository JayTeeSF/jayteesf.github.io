Commands, tools and platforms

Two public commands cover everyday Hey work: hey runs, checks, tests and builds programs, and hirb starts the interactive REPL (in a source checkout, hey-interp is the reference interpreter and test oracle). This page lists every subcommand and flag, shows the help each one prints, and ends with where Hey runs and how versions work.

The commands you'll use dailyhey app.hey compiles (once, then cached) and runs; hey -e 'says 42' runs inline code; hey -- -dash.hey runs a file whose name starts with -. hey build app.hey -o build/app makes a native executable to ship. hey test app.hey runs the spec blocks in the file. hey check app.hey checks the file without running it. hirb opens the interactive REPL.

Exit status contract. A clean run exits with status 0. An uncaught runtime fail or runtime error in program (such as division by zero or an out-of-bounds index), or a failed hey test spec, exits with status 1—whereas an uncaught fail inside an actor terminates only that actor in isolation. Command-line usage errors (unknown options, missing files, or running hey repl instead of hirb) and compile-time syntax, name-resolution, or static type errors exit with status 2. Status 70 (EX_SOFTWARE) is reserved for internal compiler or interpreter invariant bugs4.

3. Look inside the compiler

Each stage of the compiler (admission, HIR, MIR, LLVM, native link) can be replayed on its own and saved to a file, so you can see exactly what the compiler made of your code. The eight-stage pipeline and two-layer specialization are explained in Compiler 1: From source to native code. Works today

tiny.hey
fn square(n)
  return n * n
end

program
  says square(7)
end
$ mkdir -p build && hey phase admit tiny.hey -o build/tiny.admitted.json && ls build/tiny.admitted.json
build/tiny.admitted.json
Types here are the compiler's notes, not yours. You never write a type in Hey. In the HIR and MIR artifacts below, HeyHirInference infers the call-instance signature [Int] -> Int for square(7) automatically (Compiler 1 §4), and physical planning maps specialized workers onto unboxed registers (Compiler 1 §6).
$ hey phase hir tiny.hey -o build/tiny.hir && ls build/tiny.hir
build/tiny.hir
$ hey phase mir tiny.hey -o build/tiny.mir && ls build/tiny.mir
build/tiny.mir
$ hey phase llvm build/tiny.mir -o build/tiny.ll && grep -c . build/tiny.ll
80
$ hey phase build build/tiny.mir -o build/tiny && ./build/tiny
49

To time each stage of a compile, set HEY_PHASE_PROFILE=FILE; the compiler appends one record per phase to that file. A --phase-profile flag replaces the variable. Decided, coming

Scheduler profiling. Actors, workers, Jobs and streams share one scheduler. HEY_SCHEDULER_PROFILE=1 makes a program print one JSON record at exit1 with lock waits, queue depths, steals, turns and clone counts; HEY_SCHEDULER_STATS=1 prints a shorter summary; ./libexec/perf scheduler --max-workers 8 --runs 5 --out DIR runs four ordinary workloads (actors, workers, Jobs, streams) across 1 to N worker threads and writes matrix.tsv and summary.tsv. The counters cost nothing unless switched on. The scheduler() builtin returns the live numbers inside a program. Works today

6. Cache and checkout maintenance

hey FILE.hey keys its cached executable by the absolute source path, every file in its import graph, the compiler inputs and the target. To find imports quickly, the key is computed by scanning only top-level import lines (no full parse), resolving them the same way the compiler does, and hashing each file once with SHA-256. Change one imported file and the next run recompiles; change nothing and it reuses the executable.3 Compiled HIR and MIR ("sidecars") are cached under the same key. You never need to clear a cache to see a change. Works today

$ hey cache path
cache_home=...
parser_cache=.../parser
run_cache=.../run
source_index_cache=.../source-index
runtime_object_cache=.../runtime-objects
compiler_build_dir=...build
compiler_ir_cache=...build/compiler-sidecars

The last two lines matter: compiled HIR and MIR sidecars go into the toolchain's own build/compiler-sidecars, not under HEY_CACHE_HOME, so a shared or read-only toolchain directory gets written to.

`gc` removes unused parser, source-index, runtime-object, and LLVM application

## Source-handoff format

Source-development handoffs are accepted by tests and a reviewable diff, not by a SHA-256 checksum or byte-for-byte ZIP identity. A complete replacement file or executable overlay script is acceptable during focused iteration. When you return a full Hey source ZIP, include one directly copyable command block that applies the provided archive:

```sh
cd "$HOME/dev/hey-lang-bootstrap-plan"

HEY_VERIFY_MODE=full \
HEY_RUN_PROMOTION=1 \
./PROCESS-HEY-SOURCE-HANDOFF.sh \
  "$HOME/Downloads/EXACT-RETURNED-SOURCE-ZIP-BASENAME.zip"
```

Replace `EXACT-RETURNED-SOURCE-ZIP-BASENAME.zip` with the basename of the source ZIP provided in that response. Recompression or regeneration is allowed and no source-handoff checksum comparison is required. Full and report handoffs require `HEY_RUN_PROMOTION=1`; promotion is the final commit-blocking gate.

Some of these help screens print internal paths such as ./bin/subcmds/hey-clean; type the hey clean / hey rebuild form instead. hey clean and hey rebuild deliberately throw away build products; you don't need them for everyday work. hey zip --downloads makes a safe, complete source ZIP. `target matrix` reports all desktop target families without promoting structural

cross-target structural gates; `--json` emits one machine-readable object.

`target release` builds the actual self-contained Hey compiler distribution for
a matching native host. It is not the Windows runtime-test ZIP. The unfinished
Windows product archive has no `target release --target windows-x64` equivalent

The SDK must already report self_contained_sdk=true. The archive includes
portable SHA-256 checksums, release provenance, third-party inventory, and user/system install and uninstall scripts. Publication readiness remains false until signing, license, SBOM, and native-receipt evidence are attached.
Verification executes the compiler only on a matching native host. The release
command first runs the strict target-contained SDK gate, then packs and verifies
that exact exported SDK. Native releases are checkpointed: `prepare` preserves the
identity-bound SDK and closure log, while `finish` packages and verifies it. The
one-command form performs both phases and resumes a completed matching preparation.

In a source checkout, bin/hey sets HEY_ROOT, HEY_STDLIB_PATH and HEY_COMPILER_BUILD_DIR itself. If you have several checkouts, clear inherited HEY_* variables first (unset $(env | grep -o '^HEY_[A-Z_]*')) or one checkout's paths will leak into another's run.

11. Glossary

Run cache
Where hey FILE.hey keeps compiled executables, keyed by content; see hey cache path.
Sidecar
A cached HIR or MIR file stored next to a compiled program so an unchanged program skips those stages.
Import graph fingerprint
One SHA-256 over every file a program imports; part of the cache key.
Target
An operating system and processor pair Hey builds for, such as darwin-arm64 or linux-x64.
Target archive
One download containing the compiler, runtime, linker and standard library for one target, installable without a C compiler.
Receipt
A small JSON record proving a step happened (a build, a native run, a verification), with hashes.
Spec block
A spec … end block in a source file stating expected output; run with hey test FILE.
Conformance spec
A spec in specs/ that pins one language rule.
Gate
A check that must pass before a change lands.
Landing
A change merged into the release line; every landing bumps the version.
Runtime archive
The compiled native runtime linked into every Hey executable; in 0.99.607a ordinary builds compile the stdlib modules each program reaches directly through the unified eight-stage pipeline.
Built-in
A function implemented in the runtime and declared by the toolchain; it lives in a namespace such as Path or Json, and a small core set is visible with no prefix.
Native package
A package that wraps a C library through a manifest (Native code and C).
Syntax tree, HIR, MIR, LLVM
The compiler's stages; defined in the compiler article's terminology table.
