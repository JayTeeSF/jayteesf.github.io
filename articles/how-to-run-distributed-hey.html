Distributed Hey · practical guide

Imagine if adding a machine felt like adding another worker.

Your web process accepts a burst of work. Hey actors spread that work across cores, containers, and other machines. One machine disappears; the rest keep going. A replacement joins. Your application still mostly talks in actors, immutable values, and jobs.

New to the language? Guide 1 is the quick tour; this page assumes you already know what an actor is. Reference 5 is the full reference for what this guide shows by hand.

The goal

Add a machine; your existing Jobs use it

That is the ruling: an operator admits a machine to a trusted pool, and existing Jobs use its capacity without application changes. No socket names, no hand-built peer records, no retry loops in your code. There is no special cluster API to learn. Decided, coming

The layer underneath already works: separate Hey programs, on one machine or two, connect, authenticate with TLS, send, call, and watch each other die. The rest of this guide runs it.

not this

A distributed VM

No bytecode shipping. No shared distributed heap. No raw pointers sent across the network.

→
this

Normal native programs exchanging immutable values

Each node is an ordinary compiled Hey program. Distribution is a library and runtime layer beside the actor model.

Quick start · one machine

See a real remote call in about a minute

The demos ship with Hey, in the toolchain's examples/distributed folder. Copy them into an empty folder, build one, and start it twice: once as the server (node B) and once as the client (node A).

one terminal
$ hey build 01_ping_pong.hey -o ping_pong
...
$ ./ping_pong server 9311 tcp > b.log &
$ sleep 1
$ ./ping_pong client 9311 tcp
A up mode=tcp incarnation=inc-...
A handshake ok with peer=B incarnation=inc-...
A got reply=pong echo.ping=hello from A from=node-B
$ sleep 1
$ cat b.log
B up mode=tcp incarnation=inc-...
B listening on 127.0.0.1:9311
B handshake ok with peer=A app=pingpong
B stats frames_recv=3 frames_sent=2

What just happened?

Node A built a RemotePid (an actor address on another node), sent a request through Remote.call, and node B answered with an immutable structured reply. Each run gets a fresh incarnation id, so an address from an earlier run can never reach a restarted node by accident.

The tcp argument is the easy development mode: no certificates, and the same protocol above the connection.

Same machine · secure path

Now run the same demo over TLS

The toolchain carries test-only certificates in test/fixtures/tls. Copy the three files next to the demo. The demo reads its certificate paths from environment variables it names itself: the server needs its certificate and key, the client needs the authority that signed them and the name to check.

one terminal
$ hey build 01_ping_pong.hey -o ping_pong
...
$ HEY_DIST_CERT=server-cert.pem HEY_DIST_KEY=server-key.pem ./ping_pong server 9312 tls > b.log &
$ sleep 1
$ HEY_DIST_CA=ca-cert.pem HEY_DIST_SNI=localhost ./ping_pong client 9312 tls
A up mode=tls incarnation=inc-...
A handshake ok with peer=B incarnation=inc-...
A got reply=pong echo.ping=hello from A from=node-B
$ sleep 1
$ cat b.log
B up mode=tls incarnation=inc-...
B listening on 127.0.0.1:9312
B handshake ok with peer=A app=pingpong
B stats frames_recv=3 frames_sent=2

Those certificates are for the demo.

Never put the fixture's private key into a real service. A real deployment issues a server certificate for the name the service actually uses.

Two real machines

Move node B to another computer

Build the demo on each machine (a Mac program doesn't run on Linux, and the other way round). Say node B is reachable at 192.168.1.20. The server binds to that address and waits longer for the client; the client connects to that address but checks the certificate against the name localhost, because that is the name the fixture certificate was issued for. A real certificate would carry the real service name.

Machine B: server

$ HEY_DIST_BIND=192.168.1.20 HEY_DIST_ACCEPT_MS=15000 \
    HEY_DIST_CERT=server-cert.pem HEY_DIST_KEY=server-key.pem \
    ./ping_pong server 9101 tls

Machine A: client

$ HEY_DIST_PEER=192.168.1.20 \
    HEY_DIST_CA=ca-cert.pem HEY_DIST_SNI=localhost \
    ./ping_pong client 9101 tls

The output is the same as on one machine, with B listening on 192.168.1.20.

Break it on purpose

Distribution matters when something dies

A restarted node is a new node. Here node A sends one message addressed to an earlier incarnation of B, which B must refuse, and then makes a normal call, which B answers.

one terminal
$ hey build 04_stale_incarnation.hey -o stale
...
$ ./stale server 9313 tcp > b.log &
$ sleep 1
$ ./stale client 9313 tcp
A up mode=tcp incarnation=inc-...
A handshake ok peer_incarnation=inc-...
A stale-incarnation send dispatched (server must reject, not route)
A current-incarnation call reply=pong
$ sleep 1
$ cat b.log
B up mode=tcp incarnation=inc-...
B listening on 127.0.0.1:9313
B handshake ok
B serve event=stale_incarnation
B serve event=answered
B serve event=bye

Reference 5 runs the other two demos the same way: 02_remote_actor shows Remote.send reaching a remote mailbox, and 03_remote_monitor shows the surviving node told NODE_DOWN when its peer dies.

What still feels manual

Today's friction, and the piece that removes it

You create peers and connections yourself.

Application code knows host names, ports and handshakes. Fix: a node service, a supervised runtime part that owns listeners, peer connections, reconnects and backoff. Proposed

You build remote actor addresses yourself.

You call Remote.pid(node, name) and keep track of where the actor lives. Fix: a registry with discovery and placement; admitted machines advertise what they can run. Proposed

Jobs don't spread across machines.

The transport moves messages, but Jobs still run on one machine. Fix: ordinary Jobs, unchanged, running across nodes, with accepted work recorded before the receipt and numbered attempts so a stale worker can't overwrite a result. The goal is decided, coming

What a send promises across machines isn't written down yet.

Today a remote send is accepted for transport, at most once. Fix: the delivery contract: what send, call, monitor and a Job receipt promise, tested against lost acknowledgements, duplicates and reordering. Decided, coming

You can't see the cluster as a whole.

Each demo prints its own facts. Fix: one record shape for node health, actors, mailbox and Job depth, latency, traffic, backpressure, dead letters and supervision history. Proposed

State that survives a machine

Durability is a named promise

A peer accepting bytes is not the same as a change surviving that peer's disk. The hey_durable_log package makes the difference explicit: a local append reports local_durable only after the storage barrier, and the cluster layer reports quorum_durable only after a majority confirms its own durable copy. A missing majority is an error, never a quiet downgrade. Reference 5 covers how to use it.

Why this is worth finishing

Hey starts from unusually good distributed assumptions

Immutable values

Messages already cross an ownership boundary. A machine boundary is another copy boundary, not a shared-memory illusion.

Actors

Concurrency is already message-oriented. Distribution extends that model instead of replacing it with remote procedure calls. Why the actors are built the way they are: Designing Hey's Actors and How Hey Runs a Million Actors.

Native programs

No distributed VM. Each node is a normal compiled program with a small networking layer beside the actor system.

The goal is not to prove that two computers can exchange pong. That part works. The goal is to make adding a computer feel like giving the same Hey program more places where actors and jobs can run, and to make the cluster observable enough that you trust it when something goes wrong.
