The wire format is the easy part

The piece everyone braces for — turning a live value into bytes another machine can rebuild — is, for Hey, a plain structural tree-walk, because immutable acyclic refcounted values give the serializer no cycles to chase, no aliasing to preserve, and no concurrent mutation to reconcile.

Explored · not shipped Still a design note, not a feature announcement. Distributed Hey has not been built or shipped; no distribution code exists in the tree today. Everything below is analysis of what the runtime would need, grounded in a research brief.

Part 2 of a three-part series, "Distributing Hey." Part 1, "No VM needed," answered the yes/no question: distribution is five runtime services on the actor runtime Hey already has, not a bytecode VM. This part takes the service everyone fears most — serialization — and shows why Hey's data model makes it the easy one, then walks all five services in detail and what maps over. Part 3, "Seven choices for distributed Hey," argues the open design decisions.

The short version

  • Serializing a Hey value is a straightforward tree-walk. Hey values are immutable, acyclic, and refcounted with no cycles — so a value is a tree by construction, and encoding it is a plain recursive walk into bytes.
  • Hey has none of the three things that make serialization hard. No cycles (no cycle-detection pass), no aliasing (no shared-reference table to preserve on the far side), no shared mutable state (nothing to lock against mid-encode).
  • BEAM's special case becomes Hey's general case. BEAM can share only its immutable, pointer-free refc binaries by reference with no cycle collector; in Hey that carve-out is the rule for every value.
  • Three of the other four services reuse or extend machinery Hey already has; only node membership is built from nothing. Addressing extends the actor registry, transport reuses the accept/worker-pool code, and supervision extends existing links, monitors, and supervisors with phi-accrual detection and distributed refcounting. Membership is the one service with no single-node analogue to reuse — in concept or code. The wire format is new code too, but a distinct case: it stands on Hey's existing value representation.
  • Actors, stateless workers, Jobs, and worker-backed streams all cross a node boundary the same way: add a node-tagged address, and add one serialize-at-the-boundary step.
  • Disclosed gapOutside the five services, one piece is genuinely new: the callee's code must exist on the remote node. Homogeneous-binary deploy solves it now; Unison-style content-addressing is the long-term option, not a requirement. (Partition handling is the other genuinely-new problem — argued in Part 3.)
  • Check it yourselfRead BEAM's refc-binary rule: immutable, pointer-free binaries are shared by reference with no cycle collector. Every Hey value has that shape — confirm the special case is Hey's default.

Ask anyone who has built cross-node messaging what the scary part is and they will say serialization: taking a live, in-memory value and flattening it to bytes the other machine can faithfully rebuild. In a language with mutable object graphs that fear is earned. Hey is not that language, and the reason the wire format is the easy part is the same reason Hey is fast on one machine: its values are immutable, acyclic, and refcounted.

Why serialization is hard — and why Hey skips all of it

Serializing a value in a mutable-graph language means solving three problems at once, and the brief names each one. You must detect cycles, or a naive walk loops forever on a structure that points back at itself. You must preserve aliasing — when two references point at one object, that sharing has to survive the round-trip, so the encoder keeps an identity table and the decoder rebuilds the shared links rather than duplicating the object. And you must guard against concurrent mutation: if another thread can change the graph while you are walking it, you either lock the whole structure or risk shipping a torn, half-updated value.

Hey has none of these problems, by construction. Its values are immutable, acyclic, and refcounted with no cycles — a fact the runtime already leans on for single-machine performance. The brief is blunt about what that deletes:

Serializing an immutable acyclic value is a straightforward structural walk — a tree, by construction. Mutable-graph languages must contend with cycles, aliasing (two references to one object must stay shared after transfer), and concurrent mutation during serialization; Hey has none of these. Distributing a Program Across Systems (research brief), §4.1

Line them up: no cycles means no visited-set and no cycle-detection pass — the walk terminates because the data terminates. No aliasing means no identity table on the way out and no shared-reference reconstruction on the way in — every child is walked and emitted exactly once, and the decoder rebuilds a tree without bookkeeping. And because the value is immutable, nothing can change it mid-encode, so there is no lock, no snapshot, no torn read — the encoder and any number of readers coexist with zero barriers. What is left is the boring middle of the job: walk the tree, emit bytes, and on the far side read bytes and rebuild the identical tree.

BEAM's special case is Hey's general case

There is a precise precedent for what Hey gets. BEAM, Erlang's virtual machine, can share some data across processes by reference with no cycle collector — but only its refc binaries: reference-counted binaries that are immutable and pointer-free, and therefore safe to point at from many places without ever forming a cycle. Everything else BEAM copies. The brief's observation is that this is the same shape as a Hey value, generalized:

This is the same reason BEAM's refc binaries (immutable, pointer-free) can be shared by reference with no cycle collector — except in Hey that carved-out special case is the general case for every value. Distributing a Program Across Systems (research brief), §4.1

The consequences fall out cleanly. A local send can pass by reference — immutability makes that safe with zero barriers, because no receiver can mutate what the sender still holds. A cross-node send serializes the acyclic tree with no cycle-detection pass and no aliasing-preservation bookkeeping. And the same refcount opens a size strategy borrowed from Ray: copy small values outright, and ship large ones by reference with a lazy fetch — Ray's ObjectRef pattern, which the brief notes "drops straight onto Hey's refcount."

The five runtime services, in detail

Part 1 named the five services distribution needs; here is what each one actually is, and — the point of this part — how much of it Hey already has. The wire format is one of the five, and it is the one Hey mostly gets for free. Three of the other four reuse or extend machinery already in the tree. Only the first — node membership — is built from nothing, with no single-node analogue to reuse in either concept or code. The wire format, though also new code, is a distinct case: it stands on Hey's existing value model.

1 Node membership & discovery

A way for a Hey process to name itself as name@host and find its peers. The cheapest first cut is an epmd-equivalent — a per-host registry mapping node names to ports — or a static seed list. For clusters that must self-heal, the brief points at Akka's design instead: gossip membership with phi-accrual failure detection, decentralized with no coordinator, rather than Erlang's fully-meshed net_kernel, which "scales poorly past a few dozen nodes."

Built from nothing: this is the one service with no single-node analogue to reuse — in concept or code. New: the whole membership protocol.

2 Location-transparent actor addressing

An actor reference has to carry its node identity, so a send routes locally or remotely from identical source. Two designs: Erlang's node-tagged pid (the address names the node it was spawned on), or — the brief's preferred option — Orleans' virtual-actor identity, where you address an actor by logical identity and let the runtime place, migrate, and recover it. The brief calls this "the single most important design choice," because logical identity keeps the runtime free to move actors; Part 3 argues it.

Reuses: Hey's existing actor references and registry (the on-disk 120_actor_registry.hey surface). New: a node tag on the address, and — if virtual identity is chosen — a runtime directory.

3 The wire format itself

An ETF analogue: a serialization for Hey values, and the subject of the first half of this article. It is genuinely new code, but easy given acyclicity — a structural walk of a tree, with no cycle-detection and no aliasing bookkeeping. Unlike membership, though, it is not built from nothing: it stands on a data model Hey already ships. This is where that model "pays off enormously," in the brief's words.

Stands on: the immutable, acyclic, refcounted value representation Hey already ships. New: the encode/decode code — the bounded, boring part.

4 Transport & handshake (over TLS)

A TCP carrier — or QUIC/TLS — with a connection handshake and a cluster-secret check. The brief is pointed about security: Erlang's magic cookie is the minimum bar and its own docs call it non-cryptographic, so Hey should start with TLS-authenticated node identity rather than reproducing the plaintext-cookie weakness. Crucially, this is "ordinary systems code next to the existing accept/worker-pool machinery" — the acceptor-queue integration already merges accepted connections into the scheduler's message domain, and remote message delivery "is the same shape with an fd payload from another host."

Mostly reuse: Hey's accept path and worker pool — the acceptor queue that already feeds the scheduler. New: the handshake and TLS node identity; the delivery path is the same shape it already runs.

5 Distributed supervision & failure detection

Extend Hey's existing supervisor, link, and monitor semantics across nodes: a monitor on a remote actor fires a down-signal when the peer node is declared unreachable — the nodedown-equivalent. For the "is the node dead?" judgment, reuse phi-accrual from Akka. And to decide when a remote value can be freed, use Ray's distributed reference counting, which "maps naturally onto Hey's refcount."

Extends: Hey's existing links, monitors, and supervisors (155_links_and_monitors.hey, 165_monitor_delivery.hey, 170_link_propagation.hey, 160_supervisor_strategy.hey), and the refcount itself. New: making the down-signal network-triggered, plus phi-accrual and distributed refcounting.

phi-accrual Akka Cluster's failure detector. Instead of flipping a node to "dead," it accrues a continuous suspicion score (phi) that climbs as expected heartbeats go missing, and a threshold you tune decides when to act — the approach Hey would adopt for judging whether a remote node is still reachable. What actually maps over: actors, workers, Jobs, streams

The reason distribution is an extension and not a rewrite is that Hey's four concurrency constructs already have the shape distribution needs. Each one crosses a node boundary the same two-step way — add a node-tagged address, and add a serialize-at-the-boundary step — over machinery that already exists in the tree, and nothing about the local semantics changes. The table takes the four constructs one at a time.

Runtime-managed Job Already a runtime-scheduled unit Distributed scheduler places it on a remote node — spawn(Node, …)

The gap the five services miss: is the code even there?

Everything above extends something Hey has. One thing does not, and it is the single place, outside the five services, where the missing VM from Part 1 is actually felt. When you say "run this function on that node," a value can be serialized and shipped — but the code that runs it has to already exist on the target. Unison sidesteps this by shipping code with the work; BEAM sidesteps it by loading modules hot at runtime — hot code loading is the distribution-adjacent trick a VM buys you. A native, ahead-of-time-compiled binary cannot assume the callee's code is present, so it has to arrange for it.

The brief gives two answers, cheapest first, and is careful about which is required:

Two answers to "does the remote node have this code?"
Approach How it works Status
Homogeneous-binary deploy The same Hey binary runs on every node, so any spawn(Node, fn) refers to code already present; identify the function by a stable symbol or hash. Enough to shipdistribution v1 needs nothing more

Bottom line for Part 2

The wire format is the easy part. Because Hey's values are immutable, acyclic, and refcounted, serializing one to cross a node boundary is a plain structural tree-walk — no cycle detection, no aliasing bookkeeping, no lock against concurrent mutation. BEAM shares only its refc binaries by reference for exactly this reason; in Hey every value has that shape, so the special case is the default. Of the five runtime services, only node membership is built from nothing — it has no single-node analogue to reuse, in concept or code. The wire format is new code too, but it stands on Hey's existing value representation; addressing and supervision extend existing runtime machinery, and transport mostly reuses the accept path. Actors, workers, Jobs, and streams all cross a node boundary by adding a node-tagged address and a serialize step. The one genuinely-new gap outside the five services is making sure the code is present on the far node — solved now by homogeneous deploy, and by content-addressing later if dynamic shipping is ever wanted. (Partition handling is the other genuinely-new problem distribution raises; Part 3 takes it up.) The piece that sounds hardest is the one Hey nearly gets for free — and Part 3 turns to the choices none of this settles.

Glossary

acyclic value
A value whose references never form a loop. Hey's values are acyclic by construction, which is why serializing one is a terminating tree-walk with no cycle-detection pass.
aliasing
Two references pointing at the same object. In mutable-graph languages a serializer must record aliases and rebuild the sharing on the far side; Hey's tree-shaped values have no aliasing to preserve.
refc binary
Erlang/BEAM's reference-counted, immutable, pointer-free binary — the one kind of Erlang data shared by reference with no cycle collector. Every Hey value has the same immutable, acyclic shape, so BEAM's special case is Hey's general case.
ETF analogue
Hey's own equivalent of Erlang's External Term Format — the wire serialization for Hey values. New code, but easy given acyclicity: a structural tree-walk, not a graph traversal.
ObjectRef
Ray's distributed pointer/future to a value in a shared store, pinned by distributed reference counting. Because Hey is already refcounted, a "copy small, ship large by reference with lazy fetch" split maps onto machinery Hey has.
phi-accrual
Akka Cluster's failure detector: instead of a boolean "is it down?", it returns a tunable suspicion value (phi) for how likely a node has died — the design Hey would reuse for cross-node failure detection.
distributed reference counting
Ray's mechanism for deciding when a remote value can be freed, by refcounting references held across nodes. It extends Hey's existing local refcount naturally.
content-addressing
Identifying code by a hash of its definition (Unison's model), so a node can fetch and cache any definition it is missing. The long-term answer to remote code presence; a research path, not a v1 requirement.
muting
Pony's retrofit for backpressure: pausing a sender whose target's mailbox is overloaded. The cautionary lesson for cross-node streams — unbounded mailboxes are worse across a network than locally.
