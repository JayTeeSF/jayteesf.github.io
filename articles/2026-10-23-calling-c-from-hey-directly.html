Calling C from Hey Directly

Asking SQLite how many rows changed takes about 90 machine instructions on the C side. Asking from Hey costs about 5,400. Most of the difference is Hey building a one-item list to carry the argument, then freeing that list, a result record and a few strings. This page shows where the instructions go, a design for 0.99.606a that removes them, and five decisions the Maintainer has to make.

Status, 24 October 2026: being built now, each pick reversible

As of about 05:00 PDT, GippiPiTy is implementing the recommended picks so the work isn't blocked waiting for rulings. Each pick goes in its own change, so any one can be reversed. The five decisions each show the options, what's being done, and what a "no" costs.

Short version

  • The C side of a Hey SQLite call is under 2% of its cost on the 606a branch. Building the argument list and freeing things afterwards take about half.
  • The fix: the compiler finds the C function at build time and checks every call against the package's declaration.
  • Expected: 40 to 90 instructions per call. An estimate, not yet a measurement.
  • The 16 native packages re-release once. Old packages keep working.
  • Five questions need the Maintainer's ruling.

First, a few terms

Result
The record Hey returns from anything that can fail: an ok flag, a value, an error.
HIR, MIR
Two of the compiler's internal forms. HIR says what the program means; MIR decides how each value is stored and who owns it.
LLVM, emitter
LLVM turns Hey's output into machine code; the emitter is the Hey stage that writes LLVM's input.
gate
An automated test a change must pass. Each one is committed first while it still fails.
native package
A Hey package that wraps a C library, such as hey_sqlite3.

The rest are in the glossary at the end.

1. One SQLite call today: about 5,400 instructions, under 2% of them in C

This asks SQLite how many rows the last statement changed, the cheapest function hey_sqlite3 has:

import 'stdlib:Native'

let changed = Native.call(extension, 'changes', [database])
set rows = rows + changed.value

On the 606a branch each call costs about 5,374 instructions measured; on the 0.99.605a release it was 11,537. Both were measured at 22:39 PDT on October 23 on an Apple M3 Pro. A profile of 40 million calls on the 606a branch splits it like this:

  • 22% build the one-item list [database]
  • 30% free the list, the Result, strings and boxes
  • 9% build the Result, read .value
  • 11% build 'changes', find it by name
  • 26% copies, boxes, C buffers, mutex, the loop, unitemised
  • 1.6% the real work: C dispatch, wrapper, SQLite

Shares are of profile samples, not exact instruction counts. "Boxing" wraps a raw value in Hey's general value container. On 605a the Result alone was about half; the 606a branch already builds it in one block.

2. Seven steps to fetch one integer

Today, every call (606a branch)

  1. Build the string 'changes' and the list [database]27%
  2. Find the package by handle, then changes by comparing names6.5%
  3. Copy each argument into a freshly allocated C array
  4. Lock the package's mutex
  5. A generic switch picks function 8; SQLite runs1.6%
  6. Unlock, convert the answer, build a Result5%
  7. Read .value; free the Result, list, strings and boxes34%

After, every call

  1. Call the C function by its linker name, passing the handle as a plain 64-bit integer
  2. Lock, SQLite runs, unlock
  3. The answer is a plain Int. Nothing to free.

The lock stays because the package declares changes not thread-safe.

3. After: an ordinary import and an ordinary call

import 'native:hey_sqlite3'

let changed = Sqlite3Raw.changes(database)
set rows = rows + changed

No new syntax. native: finds the package the way stdlib: finds the standard library, and the package's manifest (its declaration file) names the module. Functions the manifest marks as able to fail still return a Result; changes returns an Int. Each step below belongs to the stage that already owns that kind of decision:

  1. packageManifestdeclares each function's types and ownership
  2. package toolLock filegenerated: index, C name, signature, manifest hash
  3. resolverIdentitySqlite3Raw.changes is @n1.8: package 1, function 8
  4. MIRRecordsignature, and how each argument is held and owned
  5. verifier, then emitterChecked callcall checked against record, record against lock; emitter writes a plain call
native_fn @n1.8 symbol=hey_native_hey_sqlite3_changes_flat (handle borrow) -> i64 failure=none serialized nonblocking
local b3 changed:i64 = call @n1.8 (b2)

After estimate

An estimate, added up from parts: the call (about 5), the wrappers (about 10), SQLite's function (5 to 15) and an uncontended lock (20 to 50). Gate 2 will measure it. If it holds, that's 60 to 130 times fewer than the 606a branch today.

Why the estimate is below today's C side

Without the lock the parts come to 20 to 30, while today's C side, also without the lock, is about 90 by profile. The design puts that gap down to the generic switch and its type checks; nobody has measured it.

5. It stays inside the compiler's rules

The call is bound by the resolver's identity, decided in MIR, checked by the verifier after every pass, and nothing in it knows about SQLite.

The four rule checks
  • Identity, not spelling. Bound by @n1.8 from the lock file. No list of names; the string in Native.call is never turned into a direct call.
  • MIR decides, the emitter obeys. MIR picks how each argument is passed and marks it borrowed; the emitter copies the record into a call.
  • Every call checked. A checker (the verifier) runs after every compiler pass. A test hook corrupts one record and must make the gate fail.
  • One language, one resolver. An import and ordinary calls; every version 2 package gets the same path.

6. What each native package needs: one re-release

"schema": "hey-native-package-v2",
"module": "Sqlite3Raw",
"binding": "static",
  {"name": "changes", ..., "failure": "none"},
  {"name": "step",    ..., "failure": "result"}

Add those fields (types and ownership don't change), regenerate the lock file, switch the package's own code to Sqlite3Raw.name(...), bump, run bin/package-check, publish through hey_packager, then re-release dependents with "hey": ">=0.99.606a". All 16 native packages are in the Maintainer's own repositories and on version 1 today. Version 1 keeps working through Native.call; only import 'native:' refuses it.

Eight steps; gates 1 to 3 are committed failing first; gate 2 caps a call at 200 instructions.

Optional detail

Glossary
instructions (retired)
Machine instructions the processor finished, counted by the operating system. Steadier than wall time.
manifest
The package's hey.native.json: each C function's name, argument types, return type and ownership.
lock file
A generated file recording exactly what the compiler may rely on, with the manifest's SHA-256 hash so a changed manifest is caught.
handle
An opaque number standing for a C object, such as an open database.
resolver
The compiler stage that decides which definition each name refers to and gives it an identity.
verifier
A checker that runs after each compiler pass and stops the build if MIR breaks a rule.
borrow
Passing a value without transferring ownership, so neither side adds or drops a reference.
linker name (symbol)
The name a compiled C function is known by when programs are linked together.
view
A (pointer, length) pair pointing into a string's existing bytes, valid only until the call returns.
flat wrapper
A generated C function that takes only plain numbers and pointers, so the C compiler, not Hey, handles each platform's calling rules.
static / shared binding
Static: the package's C code is compiled into the program. Shared: it stays in a separately built library, opened once at start-up.
ABI
Application binary interface: the rules for how compiled code passes arguments and lays out data. "ABI v2" is Hey's current native boundary.
Job, bounded worker
Hey's ways to run work off the shared threads that run actors, so waiting doesn't stall other actors.

The AI agent that wrote the design and this page's recommendations.
Why not just make Native.call faster?

Caching the name lookup would save its 6.5%. The argument list, the Result, the frees and the boxing would remain, because Native.call takes any function name and any list at run time; it can't know the types in advance. Recognising the string 'changes' at compile time and calling it directly would be a fact taken from a spelling, which the compiler's rules forbid. The 606a branch has already halved the call by building Result as one block (commit 647f26a81); what's left is the general path itself.

Linking, platforms, errors and memory safety
  • Static (default). hey build compiles the package's declared C sources and the generated wrapper with the target's clang, caches the objects by lock hash, target and toolchain version, and links the declared libraries.
  • Shared only (a library without source). Before user code runs, the runtime opens the library once, checks its manifest hash against the lock, and fills a table of function pointers. A missing library or symbol stops the program at start-up.
  • Why flat wrappers. A 16-byte (pointer, length) view travels in two registers on arm64 (AAPCS64, rule C.12) and on x86-64 Linux and macOS (x86-64 psABI, aggregate classification), but by reference on Windows (Microsoft x64 calling convention: "16-byte arguments are passed by reference"). Splitting it into (data, length) keeps those rules inside clang.
  • iOS. Apple's App Review Guideline 2.5.2 forbids apps that "download, install, or execute code which introduces or changes features"; signed libraries inside the app bundle are allowed. Hey's runtime opens a package with dlopen on a path given at run time. Whether that works inside an iOS app bundle today hasn't been tested; static binding avoids the question by compiling the package in. (This is inference, not a measured result.)
  • Android. SQLite is behind the Java API (SQLiteDatabase: "Exposes methods to manage a SQLite database") but isn't on the NDK native API list. Since Android 7.0 "the system prevents apps from dynamically linking against non-NDK libraries", and apps should "bundle all your non-NDK libraries with your APK".
  • Windows. The Win32 runtime refuses to load native packages at all today. Compiling them in would not need loading; nobody has tried it yet.
  • Memory safety. No Hey value crosses into C: arguments are numbers, handles or views that end at return, and results are fresh values Hey builds afterwards. A test-only mode copies each view into a buffer that's poisoned at return; a deliberately bad package must be caught, and every real package's tests must pass under it.
  • Interpreter and REPL keep the dynamic path but look each function up once at import.
The eight gates
  1. gate_native_static_call_direct: the compiled output has a direct call and no generic native call.
  2. gate_native_static_call_cost: at most 200 instructions per call, by doubling the call count.
  3. gate_native_call_verifier: wrong arity, wrong representation, stale lock hash and early view release are each refused; the corruption hook makes the gate fail.
  4. gate_native_dynamic_static_differential: every boundary type gives byte-identical output through the interpreter and a compiled build.
  5. gate_native_view_poison: the bad fixture is caught; good packages pass.
  6. gate_native_shared_resolve_once: the same number of symbol lookups at n and 2n calls.
  7. The existing native loader and generator regressions stay green (the version 1 path).
  8. Android and iOS fixture builds link the symbol statically, where the SDKs exist.
