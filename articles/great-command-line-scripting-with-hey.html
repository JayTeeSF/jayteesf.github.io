Great Command-Line Scripting with Hey

The week of: 2026-10-10 · re-measured on 601a and Ruby 4.0.7

One job, two implementations, one rule: the outputs must match to the byte. Re-measured on today's toolchain, Ruby 4.0.7 beats the Hey script this site ships — 299 ms against 743 ms. The loss comes from two lines the Hey had to give up in September. On 601a they work again, and with Ruby's own two-word spelling put back the same Hey runs 2.6× faster than Ruby.

TL;DR

  • Ruby wins against the script as shipped. On today's 34-package tree, Ruby 4.0.7 + YJIT takes 298.6 ms. The Hey port committed in this repository takes 743.4 ms compiled and 762.1 ms as a script: Ruby is 2.5× faster. Byte-identical output, every lane.
  • The cause is a workaround, and it is now obsolete. In September, paths.uniq.sort(cmp) silently returned garbage on that day's Hey, so the port got a hand-written insertion sort. That sort makes 10× the comparator calls and 13× the list copying of a merge sort. On 601a the two-word spelling works. Putting it back (two lines, nothing else) gives 113.5 ms compiled — 2.6× faster than Ruby — and 133.6 ms as a script (2.2×). That fix is measured here but not shipped: the script in the repository is unchanged, and whether to change it is the site owner's call, not this benchmark's.
  • Hey is ahead on start-up (a compiled binary starts in 1.2 ms, Ruby in 28 ms) and on per-item work once both sides run the same algorithm. Hey is still behind on building long lists (appending copies the list: 16,000 appends take 1.17 s against Ruby's 2.7 ms), on parallelism (there's no parallel map on 601a), and on length: 646 lines against Ruby's 313.
  • Not a quiet box. A Hey compiler build was running throughout, load average 2.2–3.0. Interleaved rounds agreed within 2%, but treat every figure as measured under that load.
  • Not 602a. The newest release's install refuses every script, hello world included: its compiler front end was built from older sources than the checkout and won't run until it's rebuilt, which the Hey team is doing, so these numbers come from 601a.

How to read these numbers

Apple M3 Pro (6 performance + 6 efficiency cores, 18 GiB), macOS 26.6.2. Hey 601a from hey-lang-bootstrap-plan at 565e6ddad, set explicitly per lane with HEY_ROOT. Ruby 4.0.7 (newest stable on ruby-lang.org on 2026-10-14) and 4.0.6, with YJIT (Ruby's built-in just-in-time compiler) on unless a lane says otherwise. Each Ruby is called as its real binary: rbenv, the Ruby version manager, normally runs ruby through a small wrapper script (a shim) that costs 53 ms per launch here and would have been charged to Ruby. Timings from hyperfine, which repeats a command and reports mean ± standard deviation: --warmup 3, 30 runs per Hey lane and 20 per Ruby lane, fixed PACKAGES_INDEX_GENERATED_AT. Every lane deletes its output, asserts it came back non-empty, and byte-compares it with Ruby's before any clock is trusted.

The box was loaded. A single-threaded Hey compiler build held about one core for the whole session, and the 1-minute load average (roughly, how many processes wanted a CPU at once) sat between 2.2 and 3.0, this benchmark included. Benchmarks ran at nice -n 10. Lane order rotated each round, the full set ran three times and the follow-up set (the restored-sort lanes) twice, and each lane's round means stayed within 2% of each other. The old version of this article said numbers off a loaded machine are lower bounds; these are offered as measured under that load, not as quiet-box figures. Every raw number, the harness and the controls are in the evidence file.

  • The headline is a loss. The idiomatic-against-idiomatic rule is what this article stands on, and the Hey that's in the repository today loses by 2.5× on the tree it actually runs against. On July's smaller tree it beats Ruby compiled by 18% (1.18×) and loses as a script (0.95×). That's the honest current number for the shipped code.
  • The fix doesn't make the Hey less idiomatic. It makes it more so. The Ruby says paths.uniq.sort { |left, right| compare_paths(left.to_s, right.to_s) }; the fixed Hey says paths.uniq.sort(PackagesIndex.compare_paths). The shipped version is the one that was hand-written, and it was hand-written to dodge a bug, not to win.
  • The bigger tree hurts the shipped Hey far more than Ruby. Going from July's tree to today's, Ruby takes 3.2× longer and the fixed Hey 4.6× longer. The shipped Hey takes 9.5× longer. That shape is the insertion sort's, and the counts below explain it. The fixed Hey still grows faster than Ruby, so its lead narrows on bigger trees: 3.75× on July's, 2.63× on today's.

What the September workaround costs, counted

Timings on a loaded box move with the load; counts don't. A small Ruby program replays each strategy on the exact lists the generator sorts and counts two things: how many times the comparator is called, and how many list elements get copied. Copies matter because on 601a [...xs, x] behaves as if it copies every element of xs into a new list (see the append timings under Rule 1).

Today's tree: 68 lists, 1,222 items, longest 181Comparator callsElements copied
Shipped Hey: full-scan unique, then insertion sort building each pass with [...merged, x]34,9761,629,983
Hey on 601a: .uniq then .sort(cmp) (a merge sort in stdlib/Collections.hey)3,372121,248
Ruby: Array#uniq then Array#sort with a block4,311(appends in place)

Ten times the comparator calls and thirteen times the copying, and the comparator isn't cheap: it lower-cases both paths (Text.lower measured 3.9 µs a call) and walks them a character at a time. The insertion sort is quadratic in comparisons and, because each pass rebuilds its output one append at a time, roughly cubic in copies. On July's tree, where the longest list is 55 paths, that is 3,129 comparisons and 47,287 copies, small enough that the shipped Hey still edged out Ruby. At 181 paths it isn't.

Why the workaround was written

On 2026-09-24 a sibling generator, generate-articles-index.hey, was found writing an index with zero entries while printing “Generated” and exiting 0. On that day's Hey, .uniq, .sort(cmp) and .empty? on an array didn't exist; each returned the runtime's #<stop> sentinel, which is truthy. Both generators were rewritten around it with hand-written loops (commit 0631ba3), and the comments in the script still say those methods don't exist. On 601a they do: a small test prints ["b","a"] for .uniq, false for .empty? on a three-element list, and a sorted list for .sort(cmp). Restoring them passes the byte-parity gate on both trees. Those are the only four methods re-tested; nothing here says every dotted spelling works.

Where Hey is ahead, and where it's behind

Ahead of Ruby today

  • Start-up. A compiled Hey hello world runs in 1.2 ms. Ruby 4.0.7 needs 28.3 ms to run nothing, 30.6 ms once this script's three requires load. Running a script through the hey command (its first line is #!/usr/bin/env hey) costs 19.4 ms.
  • Per-item work, same algorithm. Subtract each side's separately measured start-up floor (1.2 ms and 30.6 ms) on July's tree and the fixed Hey binary does its work in about 24 ms against Ruby's 62. That's an estimate from two measurements, not one.

Still behind Ruby

  • Building long lists. An append copies the list. 16,000 appends take 1.17 s on 601a; Ruby's << does it in 2.7 ms. Even the stdlib merge sort builds its output that way.
  • Parallelism. There's no parallel map on 601a. --workers still parses and does nothing; 1 and 4 workers time the same.
  • Length. 646 lines and 27 functions against Ruby's 313 lines and 22 methods: 2.06×. Without comments and blank lines, 469 against 265: 1.77×.
  • Catching up with itself. The four dotted array methods that returned a truthy sentinel (a stand-in value meaning “nothing here”) in September work on 601a, and .map(f, workers: n) is now a compile error rather than a quiet wrong answer. Ruby never had that failure; this is Hey closing its own gap.
  • The lead shrinks as the tree grows. Even with the sort restored, Hey is 3.75× Ruby on July's tree and 2.63× on today's: its time grew 4.6× against Ruby's 3.2×. List copying is the likely reason (Rule 1 below).
  • Toolchain churn. The July version of this port no longer compiles; the newest release won't run a script on this machine.

Why this benchmark compares idiomatic to idiomatic

In July this article reported 5.46×. The Hey it measured had been hand-optimized for speed: builtins-only inner loops, work hoisted out of the comparator, a worker pool tuned against the clock. The Ruby it beat is plain idiomatic Ruby nobody has ever tuned. That isn't a fair fight. Anyone who can hand-optimize the Hey can hand-optimize the Ruby, so the canonical script became an idiomatic port, a rewrite that mirrors the original's structure instead of chasing the clock, and the headline came from that.

The same rule cuts the other way this time. The shipped port isn't slower because Hey is slow at sorting; it's slower because it stopped being a port of the Ruby. Publishing the fixed number alone would hide the code that's actually in the repository. Publishing the shipped number alone would blame the language for a workaround. Both are in the table, and the shipped one is the headline because it's the one you'd run today.

The Ruby isn't tuned either. Instrumenting it shows about half its 276 ms of work on today's tree inside compare_paths, which converts each Pathname to a string and lower-cases it on every comparison. A sort_by with a precomputed key would cut that, and the Hey could do the same. Neither side gets it here.

Hey can read like Ruby — when it's allowed to

The names still line up almost one-for-one: digit_run, trim_leading_zeroes, compare_digit_runs, compare_paths, sorted_unique, relative_path, package_section, render_page, on down the file. The Hey has five functions the Ruby doesn't: new, worker_count and package_tasks as before, plus the September pair unique_paths and sort_paths. Side by side:

Ruby (generate-packages-index.rb)

def sorted_unique(paths)

def linkable_files(files)
  sorted_unique(
    files.select { |path| LINKABLE_EXTENSIONS.include?(path.extname.downcase) }

Hey on 601a (the two-line fix)

private fn sorted_unique(paths)
  return paths.uniq.sort(PackagesIndex.compare_paths)
end

private fn linkable_files(files)
  let linkable = []

  for path in files
    let lower_path = Text.lower(path)
    if Text.ends_with?(lower_path, '.md') or Text.ends_with?(lower_path, '.html')
      set linkable = [...linkable, path]
    end
  end

  return PackagesIndex.sorted_unique(linkable)
end

sorted_unique reads the same in both. linkable_files shows the gap that's left: Ruby filters with select and a block; the port filters with a loop that rebuilds the list with [...linkable, path]. A Ruby programmer reads it cold, but it's longer, and every one of those appends copies the list.

What the shipped sorted_unique looks like instead (48 lines) 
private fn unique_paths(paths)
  let seen = []

  for path in paths
    let found = false

    for kept in seen
      if kept == path
        set found = true
      end
    end

    if not found
      set seen = [...seen, path]
    end
  end

  return seen
end

private fn sort_paths(paths)
  let out = []

  for path in paths
    let placed = false
    let merged = []

    for existing in out
      if not placed and PackagesIndex.compare_paths(path, existing) < 0
        set merged = [...merged, path]
        set placed = true
      end
      set merged = [...merged, existing]
    end

    if not placed
      set merged = [...merged, path]
    end

    set out = merged
  end

  return out
end

private fn sorted_unique(paths)
  return PackagesIndex.sort_paths(PackagesIndex.unique_paths(paths))
end

Correct, byte-for-byte, and the reason for every number in the first table's faded rows.

The ergonomics tax

Identical behaviour costs 2.06× the lines as shipped (646 against 313), up from 1.67× in July. Some of that is comments: the Hey file carries long notes about the September bugs, and without comments or blank lines the ratio is 1.77× (469 against 265). Restoring the dotted sort would delete about 48 more. What's left is Hey's explicitness: let/set, return, and loops where Ruby has blocks. Price it in.

The parity gate

The thesis, and it outranks every number here: a benchmark without an output-parity gate is a wish. Three receipts from this program and its sibling.

In July the first optimization pass rewrote the comparator to use byte_at(string, i). It compiled, and silently returned 0 for every string argument, being a Bytes-value operation. Every path compared equal to every other, the sort collapsed into a no-op, and the benchmark got faster and wrong. The byte-parity check caught it on the first run.

The second is worse, because the gate itself lied. The fastest result this project ever recorded was a 2.3 ms binary: exit 0, zero bytes of output, dead before the first line of user code. The parity check blessed it because it never deleted the output file first, and so compared the one left by the previous lane. My bug, and the reason the harness below deletes first.

The third arrived in September and is the one behind this revision: the articles generator wrote an empty index, printed “Generated”, and exited 0. Its own header admitted it hadn't been run since a restructure. A twin that's never run isn't a twin.

And a caution the other way: the parity gate passed the insertion sort, correctly. It's byte-identical and 6.5× slower than it needs to be. Parity tells you a number measured the right output. It doesn't tell you the code is any good.

The gate was itself made to fail before any number here was trusted. A lane that runs true exits 0 and the gate reports NO OUTPUT; the real binary run with a different timestamp exits 0 and the gate reports PARITY FAIL; the real binary with the right timestamp passes.

Running it

There are three ways to run one source file.

# the site's way: builds once into .hey-bin/ (gitignored), then execs the binary
bin/hey-run generate-packages-index ./packages

# the script lane: no build step, shebang is #!/usr/bin/env hey
./generate-packages-index.hey ./packages

# the binary you build yourself: a standalone native executable
export HEY_ROOT="$HOME/dev/hey-lang-bootstrap-plan"
HEY_STDLIB_PATH="$HEY_ROOT/stdlib" HEY_COMPILER_BUILD_DIR="$HEY_ROOT/build" \
  "$HEY_ROOT/bin/heyc" build --backend llvm \
  ./generate-packages-index.hey -o "$HOME/bin/generate-packages-index"

bin/hey-run pins 601a and rebuilds only when the script, a stdlib file it imports, or the compiler changes. The catch is that it works out whether to rebuild on every run, by walking the script's stdlib imports and hashing them together with the compiler (hashing the two compiler binaries alone took 23 ms here). On July's 14-package tree it took 133.6 ms against 78.3 ms for the same binary run directly, about 55 ms of overhead a call. That's more than the 19 ms the hey command adds to a script. For a page generator you run by hand it doesn't matter; in a loop, call the binary.

The first stdlib call is no longer the expensive one

In July, at 410a, the first delegated stdlib call in a process (one the compiled program handed to an interpreter) cost about 6 ms and every later one about 54 µs. A 12-line argument check made the script 5 ms slower because its Text.int_token? was the first such call. Re-run on 601a, the same probe (cli-startup-call-cost.hey) reports Text.int_token?'s first call at 4–23 µs, and every call it checks at 0–1 µs once warm. The largest one-time cost left in that list is Time.utc_iso8601, 0.37–0.51 ms on first use. The whole program agrees: --workers 1, which pays for that validation, times the same as no flag. The comment in worker_count that still quotes 5.8 ms is out of date.

The three rules, revised

Rule 1: watch how you build lists, not how often you call the stdlib

The July rule was “stdlib freely outside hot loops, builtins only inside them”, because a stdlib call from compiled code cost about 54 µs through the sidecar. On 601a, Collections.compare costs 0.11 µs a call and Text.lower 3.9 µs. Calls aren't what bites any more.

Lists are. On 601a [...xs, x] and xs.push(x) behave as if each returns a new list: they time the same, and appending n items one at a time is quadratic, which is what copying the whole list on every append produces:

AppendsHey 601a, [...xs, x] or pushRuby 4.0.7, xs = [*xs, s]Ruby 4.0.7, xs << s
1,0004.8 ms1.3 ms0.3 ms

Each doubling costs Hey four times as much. Ruby written the same copying way grows too, but Ruby's idiom is <<, which appends in place, and Hey has no equivalent. For a few hundred items per list, as here, it's fine. For tens of thousands, it's the cost that decides the run. The fix for this generator is to use the stdlib's sort rather than write one; the fix for the language is a list that can grow without copying, which Hey doesn't have on 601a.

Rule 2: measure output before you measure time

Delete the output, run, assert it came back, compare bytes, and only then start a clock. Every memorable failure in this article's history — the comparator that sorted nothing, the binary that did nothing, the index with no entries — looked like success from its exit code.

Rule 3: parallelism has to exist before it can be measured

In July, at 410a, this article reported that .map(fn, workers: n) made the port faster: 24.2 ms at 4 workers against 31.4 at 1 (its Rule 3 said 24.7, its table 24.2), so the default became 4. That verdict doesn't carry over. By September the .map spelling returned the truthy sentinel instead of running, a version built on worker and Jobs timed out, and the script was left serial. On 601a .map(f, workers: 2) doesn't compile (“unresolved callable: map”), --workers is parsed and ignored, and 1 and 4 workers time the same on both trees. Ruby's version is serial too. Any fan-out verdict for Hey waits until there's a fan-out to measure.

A harness that cannot lie to you

The ordering is what matters — rm before the run, the assertion before the comparison — so a program producing nothing fails here instead of posting a record. This is the shape of the one used for every figure above (the full script is in the evidence file). 

set -eu
export PACKAGES_INDEX_GENERATED_AT=2026-10-14T00:00:00Z
R="$HOME/dev/hey-lang-bootstrap-plan"                       # 601a, pinned per lane
export HEY_ROOT=$R HEY_STDLIB_PATH=$R/stdlib HEY_COMPILER_BUILD_DIR=$R/build
export PATH="$R/bin:$PATH"                                  # the shebang's hey
RUBY="$HOME/.rbenv/versions/4.0.7/bin/ruby"                 # the real binary, not the shim

lane() {                      # $1 = label, $2.. = command
  rm -f packages/index.html
  "${@:2}" >/dev/null
  test -s packages/index.html || { echo "$1: NO OUTPUT"; exit 1; }
  cp packages/index.html "out.$1.html"
}

lane ruby   "$RUBY" --yjit ./generate-packages-index.rb ./packages
lane script ./generate-packages-index.hey ./packages
lane binary ./generate-packages-index ./packages

cmp out.ruby.html out.script.html
cmp out.ruby.html out.binary.html

uptime; ps -Ao pcpu,pid,comm -r | head -6                   # load travels with the number
hyperfine -N --warmup 3 --runs 30 \
  "$RUBY --yjit ./generate-packages-index.rb ./packages" \
  './generate-packages-index.hey ./packages' \
  './generate-packages-index ./packages'
uptime; ps -Ao pcpu,pid,comm -r | head -6

When a lane dies silently (exit 0, no output), suspect the caches before the compiler: in July a racy publish minted a corrupted entry that deterministically produced do-nothing programs, and a dead run wrote its own entry into the run cache. The cache layout has moved since then; the July advice's ~/.cache/hey/run doesn't exist any more. Ask Hey where its caches are, look before deleting, then delete: 

hey cache path          # run_cache=~/Library/Caches/Hey/run, compiler_sidecar_cache=$HEY_ROOT/build/compiler-sidecars, ...
hey cache clear --dry-run   # lists every entry it would remove
hey cache clear             # removes all Hey caches
rm -rf .hey-bin             # bin/hey-run's own build cache, in the site repo

Checked on 601a on 2026-10-14: hey cache path and hey cache clear --dry-run report the paths above. No poisoned entry was reproduced this time, so this is layout advice, not a re-test of the July failure.

Where Hey loses

On this job, as shipped: everywhere on today's tree, by 2.5×. With the sort restored, nowhere on these two trees. Beyond them, long-list batch work is still Ruby's. The append table above is the re-measured reason, on 601a, today. The sibling source-zip port that first showed it was published here in July 2026 as Hey 66.5 ms against Ruby's 153.3 at 500 files, a tie at 2,000, and 2.16 s against 672 ms at 8,000, without the release it was measured on. (The project's findings log has a 402a run of the same port, 2026-07-24, with different figures and the same shape: Hey ahead at 500 files, behind from 2,000, Ruby 5× faster at 8,000.) It hasn't been re-run on 601a, so read those as July's numbers.

Glossary

hyperfine
A benchmark runner: repeats a command, reports mean ± standard deviation.
idiomatic port
A rewrite mirroring the original's structure rather than tuning for speed.
byte-parity
Comparing outputs byte for byte, not “looks right”.
sidecar
A long-lived helper process that serviced stdlib calls for compiled programs in the July-era toolchain.
delegation
A compiled program handing a call to the interpreter instead of running it.
builtin
A primitive the compiler lowers straight to machine code.
worker pool
A fixed set of workers taking items from a shared queue.
exit code
The integer a process returns on termination; 0 means success, and doesn't mean the output is right.
run cache
Where the toolchain stores compiled artifacts for scripts already run (hey cache path prints it).
quadratic
Cost growing with the square of the input: double the items, four times the work.
