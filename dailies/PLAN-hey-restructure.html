The plan

What gets built, in what order, and how we will know it worked — including the parts we cannot yet size.

Updated 2 August — one reordering and five corrections

1. The front end comes first. The emitter is finished last, against the new MIR. An earlier version of this page scheduled “finish the Hey-written LLVM emitter” before the front end existed. That is backwards. Today's intermediate form still carries raw source expressions which the emitter re-parses, so every handler written against it is a handler that must be migrated or thrown away — and each one enlarges the surface that has to move. Keep the fallback counter from day one; finish the emitter when it is being handed real instructions.

2. The parser decides what - means, not the tokenizer. The tokenizer always emits one MINUS token and never inspects the previous character; the parser decides prefix or infix from grammar context, which is what Pratt parsing was designed for. This doesn't just tidy the current lexical guess — it makes the arr[0] - 1 bug family unrepresentable, because the previous-character set stops existing.

3. The compiler's core data structure is ruled, and the reasoning we used to get there was wrong. Compiler nodes stay map-shaped and become a generated subsystem produced from one schema. Records and pattern matching are not prerequisites and the front end waits for neither. The old argument — Hey's defects are missing cases, so exhaustive matching would protect us — was tested against five real defects and zero of the five would have been caught.

4. The byte-for-byte tests have an exit, and it is not a date. They retire per test: each one states what it was really protecting, is replaced by a test of that, and the replacement is proven able to fail before the old fixture is marked superseded.

5. The runtime does not stay unchanged. It gains an exact-sized constructor for compiler nodes, then a direct borrowed read, and one bug fix that belongs to it alone.

6. “Non-copying access” is two jobs at opposite ends. Verification found that construction must move earlier — every node currently costs a JSON parse of the two-character document {}, and there is no sized constructor in that lane at all. But reading must stay late: a child fetch is spelled at fifteen sites across five modules today and in exactly one generated file afterwards, so doing it early means doing the hard version and then doing it again.

Done means three things

  1. Fast web servers at the per-core bar — within 3% of Go under the same conditions, about 97,000 requests per second on one core.
  2. Fannkuch.
  3. 1BRC — the billion-row challenge.

When all three run on the restructured pathway at or above where they run today, we are ready. These are the exit criteria. Nothing else is. Not “all specs green”, and no phase below is finished because it feels finished.

One thing you said reorganises the work more than anything else: you will keep running the current version until the new one is good. Until now every landing had to leave the shipped compiler working, which forced small reversible steps. That constraint is lifted here. The obvious risk is a path nobody checks, so the specs replace the release cadence as the thing that keeps us honest. A spec, here and below, is an executable test: a small Hey program checked in beside the answer it is required to produce.

What we keep and what we rebuild

This is a new front end on a retained back end, not a rewrite. The heaviest work already done — the runtime and the LLVM emitter, the stage that writes the low-level text LLVM turns into machine code — is the future and stays.

Machine shapes and operators — MIR, the stage between meaning and instructions — is the one you should see now rather than discover in month two. It is supposed to turn meaning into instructions. Today it renames types and rewrites a header, and that is all: compare the checked-in before-and-after files for one program and the right-hand side of every line is still raw Hey source text. Its own source says so — "expressions are raw text". Search it for a single arithmetic operator and you get nothing.

So the LLVM emitter downstream re-reads expressions itself, with thirteen hand-written scanners — a second census of the same file counted six, on a narrower definition, and neither count has been reconciled — while the comment at the top of its own file forbids exactly that. It is not disobedient. It is stranded.

The runtime's three additions

The earlier version of this page said the runtime was unchanged. That was wrong, and the correction is small but load-bearing — two of the three are the only reason the node subsystem is affordable at all.

1. An exact-sized constructor for compiler nodes. Today making a node means parsing the two-character JSON document {} and then inserting fields one at a time, growing the map as it goes. The new call is told up front how many fields the node has, fills them, and freezes the node when it is complete. No parsing, no repeated insertion, no growth. This is runway step 3, and it is early because it is cheap and everything after it is measured with it.

2. A direct borrowed read of one slot. Fetching a child currently copies. Borrowing does not. This is the late half of the same performance fix — runway step 8 — and it is late on purpose: a child fetch is spelled at fifteen sites across five modules today and in exactly one generated file afterwards.

3. Json.encode must refuse a callable. It currently writes null, silently, with no error and no warning — the exact class of defect this whole effort is about. It must fail with an error that names the path: Json.encode cannot encode Callable at $.key. This one is a bug fix, not architecture, and it does not wait for anything.

The runway — fifteen steps, in this order

The phases below are built on this. It is one ordered list because most of the ordering is forced: you cannot generate walkers before there is a schema, you cannot rename a physical key before every read goes through a generated accessor, and you cannot finish the emitter before it is being handed instructions instead of text.

 0  preserve behaviour — counters and regression tests, nothing else changes
 1  census every node population — syntax, HIR, MIR, diagnostics
 2  the explicit-index node schema, and the host-side generator that reads it
 3  the exact-sized node constructor
 4  generate the compatibility layer — constructors, accessors, walkers, validators
 5  move every node CONSTRUCTION onto the generated constructors
 6  move every READ and every child traversal onto the generated accessors
 7  cut the physical keys over to n_ names — one deliberate cutover
 8  direct borrowed slot reads — the late half of the performance fix
 9  source manager, tokenizer, parser
10  resolver, imports, operator bindings, module graph
11  rebuild HIR and MIR so that neither carries a raw expression
12  interpreter and its prompt onto the shared HIR
13  drive both legacy counters to zero
14  delete the bootstrap compatibility paths

Three things about that list that are easy to miss

Steps 5, 6 and 7 are one migration in three passes, and the order is the whole trick. First every place that makes a node goes through a generated constructor. Then every place that reads one goes through a generated accessor. Only then do the physical key names change — and because nothing outside the generated file types those names any more, the rename is a single deliberate cutover rather than a migration. There is no dual-key period. A period where both the old and the new key work is precisely the shape this whole effort exists to eliminate: one fact, live in two places, with nothing forcing them to agree. If a hand-written access survives step 6, step 7 is where it fails loudly — which is the point.

The generator is written in a host language that is already in the build environment — Ruby, Python or C — and never in the Hey being built. Its output is checked in. The build does not run it; make verify regenerates it and diffs against what is committed. There is no bootstrap cycle, because Hey is never on the generating side. The host language is a prerequisite for changing the schema, not for building the compiler, and that distinction is the whole of it.

Step 13 is two independent counters, not one. The first counts uses of the legacy local set — changeable local variables, which the language no longer has and the current compiler is full of, available only to a named list of compiler files. The second counts builds that fell back to the old front end. Either can reach zero while the other is nowhere near it, which is exactly why they are counted separately and why step 14 waits for both.

The phases

0  Make the silent hand-off loud — runway 0

When the Hey-written LLVM emitter meets something it cannot handle, the build quietly hands that program to the older C one. The precise reason is computed and then thrown away, and no switch prints it. About six lines of work. The legacy-set counter starts here too, and the existing regression suite is pinned before anything moves.

Verified by: every build becomes a counter. Until this exists, “finish the port” has no finish line. It goes first because everything after it is measured with it.

1  Specs, to excellent coverage

Grow them across where a value sits crossed with what you do to it, not by subject area. Ten positions: a literal written inline, a literal held in a local variable, a parameter, a call result, a field, an array element, a map value, an argument to an actor, an actor's own state, and nested combinations. (An actor is Hey's unit of concurrency: it holds private state and is reached only by sending it a message.) The reason is our own record: a fix that covered one position missed the next one along. The two positions nothing has ever swept are the actor ones — no test in the tree does arithmetic inside an actor.

Verified by: both lanes — the interpreted one and the compiled one — producing identical output, and a ratchet — a known gap may sit red without blocking anyone, but anything that has been green and goes red stops the build.

2  The node subsystem — runway 1 to 8

How the compiler stores your program, decided once and then generated. A node stays a map — maps are the language's own thing and they are not being taken away from it — but no compiler code writes or reads one by hand any more. One schema produces the constructors, the field slots, the accessors, the child lists, the walkers, the rewriters, the validators and the coverage checks. Count the populations first (step 1), because that census is what sizes everything after it.

Verified by: a build that fails when a new node kind has no resolver and no lowering — the generated coverage check. Plus make verify regenerating the whole layer and finding no difference from what is committed. And, at steps 3 and 8, the node-construction and node-read costs measured before and after.

3  The front end — runway 9 to 12

The three missing stages, in order: a source manager that gives every file a stable id so an error can name the file it came from; the tokenizer; the parser. Then the resolver, with imports, operator bindings and the module graph. Then HIR and MIR are rebuilt so that neither carries a raw expression in operand position — that is the step that turns the LLVM emitter from a compiler into a printer. Last, the interpreter stops parsing for itself and walks the same HIR the compiler produces; its values and built-ins already live in the shared runtime, so only its parser dies.

Verified by: shadow mode — run the new front end on every build while the old back end still executes, which establishes parse coverage across the whole repository without the back end being finished. Then the existing interpreter-driven specs passing unchanged, which is also the payoff: that one change takes the overwhelming majority of our specs from exercising none of the compile pathway to exercising four stages of it.

4  Finish the Hey-written LLVM emitter — against the new MIR

Pure addition, and now against a form that hands it lowered instructions rather than text. Two independent counts agree that it can do nothing the C one cannot, so this is a one-directional port and never a merge. The work list is a specific 344 runtime facilities it does not yet reach, plus floating point, which it has none of. This is the phase that moved. Doing it earlier would have meant writing hundreds of handlers around the shape the front end replaces.

Verified by: phase 0's fallback counter reaching zero across the example corpus — after the corpus is checked for selection bias, since at least one example in it was written around a gap rather than exposing one, and says so in a comment.

5  Delete the old paths — runway 13 and 14

Only now, and per the standing rule: a path is switched off after the specs that pin its behaviour exist and have been proven able to fail. Record what it was catching before it goes. Both legacy counters must read zero first. The C LLVM emitter cannot be dropped until phase 4 completes — integer division and remainder still run through it.

Verified by: deleting the implementation and watching the spec go red, one path at a time.

6  Apps on top

Run the real applications, find the regressions and the new bugs, write a spec for each. Your own loop — and the app teams already file exactly this kind of report.

Verified by: the three exit criteria at the top of this page.

Why this can move fast

We are not designing in the dark. There is a working language to check every answer against, and it is the one nearly every fix in our record was measured with. A new implementation that disagrees with it has to explain itself.

The regression suite is real software, not test files. An Apple TV app, an Android app, web servers, web clients, actor programs. These have found defects no test file in the tree could see — including a class where one platform could not build at all.

And the port is addition only. Measured twice, by two different methods, which is why it is worth stating flatly: the Hey-written LLVM emitter can do nothing the C one cannot. Both declare the same 573 facilities; the Hey one reaches 205, the C one about 549, and the 344-item difference is the work list. Nothing has to be reconciled or merged. Honest caveat: that proof is at the level of runtime calls, so a construct handled entirely inline by one and not the other would be invisible to it. Settling it to certainty needs a build we have not run.

The risk that turned out not to be one

The core data structure — ruled, and the reasoning reversed

This page used to carry, as its largest risk, the sentence “the compiler's core data structure needs features the compiler cannot compile”: the front end is written in Hey, a syntax tree wants records and pattern matching, Hey has neither, so nothing can start until one of three unsized options is chosen. That framing is retired.

Compiler nodes stay map-shaped and become generated. Records and pattern matching are not prerequisites for anything on the runway; if they are added later they are added as a language feature on their own merits, not as something the front end is waiting on.

The reason matters more than the ruling, because the argument we were both making was tested and failed. We wanted pattern matching because it catches forgotten cases. Research took five real defects from our own record and asked which would have been caught. Zero of five. They are not “a dispatch missing a variant”. They are one fact decided in several places that disagree, and a walk that omits a child.

the same fact implemented differently in N places  →  one source of truth
a walk forgets a child field                       →  generated child lists
a dispatch forgets a kind                          →  generated coverage check

Only the third of those is a pattern-matching problem, and only if you ban the catch-all arm. So the live bug where one walker forgets to visit for bodies — while six sibling walkers get it right — is evidence for generating the walkers, not for adding a language feature.

Two large compilers already paid for the alternative. Python describes its syntax tree in a small declaration file and generates the structures, the constructors and the visitors from it — in a language that had no pattern matching at all when it did so. LLVM built a whole declaration language for the same reason and says so plainly: to remove structural knowledge that would otherwise be written out by hand in many places and drift apart. Neither reached for a type-system feature. Both reached for one declaration and a generator.

The risks, named

The interpreter is a third implementation at 0%

Called out twice on purpose. The compile half has a written list of what is missing; the interpreter half has none, because both surveys can only see what the new pathway refuses, and the interpreter never asks it anything. Runway step 12 is where it joins, and the HIR walker is genuinely new code — not a port of the existing evaluator, because it consumes a different input. Size it as new construction.

Some of our tests cannot currently fail

An audit of all 276 gate scripts found 215 that no automated lane invokes, 51 with no way to run them at all, and — the larger problem — 83 of the 159 that print a summary line make at least three claims the script never measured. A hard-coded summary cannot go partly red. Phase 1 is not just more specs; it is specs whose failure has been watched. The audit is written up in The Answer Key Cannot Be One of the Contestants.

The middle of the runway is not costed

Steps 2 through 8 are sized by the census at step 1, and that census has not been run. We know the shape of the work and the order it has to happen in; we do not yet know how many node kinds, how many construction sites, or how many read sites there are. The census is cheap and it is first for that reason.

How the byte-for-byte tests retire

Every change to the Hey-written LLVM emitter must currently reproduce the C one's output byte for byte, against 90 stored samples. A new front end will change those bytes. This used to be listed here as a risk with no exit; it is now a procedure, and the exit is per test rather than a date or a milestone.

for each stored sample:
  1. say what it was ACTUALLY protecting
  2. write a test of that
  3. deliberately break the code and prove the new test fails
  4. put the code back
  5. mark the old one superseded

then delete all the superseded ones in a single reviewed change

What replaces what:

what it actually protected        what replaces it
program result                    semantic output / error test
interpreted vs compiled agree     cross-lane behaviour test
diagnostic wording and spans      normalised diagnostic snapshot
token / tree / HIR / MIR shape    canonical structural snapshot
an optimisation happened          MIR or LLVM pattern assertion
instruction selection             assembly pattern test
reproducible public artifact      exact-byte test REMAINS
ABI or serialised format          exact-byte test REMAINS

Step 3 is the one that is easy to skip and must not be. A replacement test that has never been watched failing is not a replacement; it is a second thing that cannot fail, which is the problem this page already names two sections up. And exact bytes survive only where the bytes are themselves a promise to somebody else — a reproducible artifact, an ABI, a stored file format — not because the old compiler happened to emit them.

Answered before code is written

This section used to be a list of open questions. They are ruled, and the answers are recorded here because the parser is what makes each of them one answer rather than five. Full statements are on the decisions page.

How and, or, not and ! bind

!1 == 2        is   (!1) == 2         !  binds very tight
not 1 == 2     is   not (1 == 2)      not binds very loose

a && b || c    is   (a && b) || c     && binds tighter than ||
a and b or c   is   (a and b) or c    and/or are EQUAL, and loosest

Ruby's rules exactly, and && and || are being added — Hey does not have them today. Two spellings on purpose: && and || for combining values, and and or for control flow. Measured against Ruby rather than copied from a table.

Three of the five places that answer this today have to move, and one of them does not recognise the word not at all. One thing we get for free: Ruby's famous trap is y = 1 and 2 quietly binding 1, because in Ruby = is an expression that binds tighter than and. Hey has no assignment expression, so = has no precedence to lose and the trap is ungrammatical, not merely unlikely.

The other five, in one place

Whole-number division stays as it is. -7 / 2 is -3, rounding toward zero, like C and Go. Ruby's answer is -4 and it is available by an opt-in import, per file, for anyone who wants it.

** is a library function that declares a symbol, not something built into the compiler — which makes it the first real exercise of the import system on something that matters. It is non-associative: 2 ** 3 ** 2 is an error asking which you meant, rather than a guess.

Default arguments are worked out at call time, left to right, each one able to see the parameters before it and none of the ones after. So fn f(a, b = a * 2) is fine and fn f(a = b, b = 1) is an error.

Operator overrides are lexically scoped to one file. A file that imports Ruby's arithmetic gets Ruby's arithmetic; the libraries it calls keep the behaviour they were written and tested against.

Precedence comes from the symbol, and never from the module. Two languages that let modules set precedence were tested, and in both an import silently changed how an expression parsed. An import supplies meaning, never shape.

Keyword arguments were on the old list as “a real feature or removed?”. They are a real feature: the function signature is settled, the parameter order is enforced, and about 1,900 existing call sites stop being a thing the compiler fakes by re-reading its own text.

What is not yet sized

Three things, stated so they are not a surprise later. The middle of the runway — steps 2 through 8, pending the census at step 1. The interpreter — 0% and unmeasured, and new construction rather than a port. Actor lowering — whether actors get their own instruction family or ride the ordinary call path is undecided, and one actor operation is missing from all three implementations.

Two places our own documents disagree, reported rather than quietly picked. Spec coverage: the program directive says 42 of 760 specs invoke a real build; a fresh count says 18 of 988. Part of that is the denominator — the 760 is one directory, the 988 is the whole spec tree, and a live count of that one directory returns 773 rather than 760. Unreconciled, and quoting either fraction without naming its directory is how the next drift starts. Both describe the same shape: the overwhelming majority of our specs never compile anything. Chained comparisons (a == b == c): one survey reads the interpreter as grouping to the right, a later one reads the same code as rejecting it outright and marks its own claim as needing a run to confirm. Neither has been executed.
