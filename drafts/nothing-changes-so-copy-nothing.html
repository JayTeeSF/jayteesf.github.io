Nothing Changes, So Copy Nothing

In a language where no value can ever change, no copy should ever be necessary — and when a value loses its last reference, it should simply cease to exist, without the program ever stopping to let a collector run. That sounds like a slogan. It's actually an engineering program with a peer-reviewed literature, a measured ledger of exactly which copies Hey still makes today, and a fix queue that deletes them one counted slice at a time.

Status: measured research, program in flight

Every count and timing in this article was measured, with dated evidence, on our own machines. The fixes it describes are at different stages and section 6 states which is which: one has landed (471a), one is branch-ready but not merged, one is designed with its pricing measurements in progress, and two are explicitly not yet started. Nothing unlanded is claimed as built.

TL;DR

  • The zero-copy program is worth building, and we are building it — because the whole design reduces to one runtime question, “am I the only owner of this value?”, and the languages that ask it well run immutable code within 10% of hand-mutated C++ on a 42-million-insertion tree benchmark (Koka's Perceus, PLDI 2021).
  • We counted the copies Hey still makes, on our macOS box at 474a with the runtime's own allocation counters: reading one array element costs exactly 1.000 clone-plus-box per read (32 bytes each); a read feeding arithmetic costs 3 boxes; and 10,000 push() calls performed 50,005,000 element copies — the n(n+1)/2 quadratic signature, read straight off a counter.
  • First deletion measured: the store path's two allocations per write went to one (exactly 2.000 → 1.000 by counter) for −22.7% time per store — that fix is branch-ready, not yet merged. An earlier fix, landed at 471a, already removed a whole-array clone from the swap store.
  • Disclosed weakness: a comparison between two array elements currently leaks 64 bytes per iteration (2 boxes allocated, 0 released) on the measured shape — and the biggest design choice here, eager freeing versus handing reclamation to a collector actor, is not decided. It will be decided by a pre-registered measurement, and we will publish whichever verdict wins.
  • Reproducibility: the counts come from a small counting probe run with the runtime's allocation counters enabled (HEY_ALLOC_STATS=1; with the flag off they read zero, and the evidence cell archives that blindness check plus a positive control). Every target is an exact integer — 2.000 → 1.000, 1.000 → 0.000 — so success and failure are both unambiguous.

How to read these numbers

The copy counts come from the runtime's own allocation counters — enabled by an environment flag (HEY_ALLOC_STATS=1); with the flag off they read zero, and the evidence log archives both that blindness check and a positive control that proves the counters can see real allocations. Counts are load-independent: they don't care whether the machine was busy. The timings (the −22.7% per store) were taken on a quiet Linux box (i7-1165G7), medians of 5 interleaved runs, output-checked so a wrong answer can never score as a fast one. Counts and timings from different machines are stated separately and never merged. Every number carries its Hey version; versions are shown short (474a means v0.99.474a).

1. The promise: if nothing ever changes, no copy is ever necessary

Immutability's classic sales pitch is about safety: if no value can ever change, then no value can ever change under you. Share a list with ten thousand actors and none of them can scribble on it, so nobody needs locks, defensive copies, or house rules about who writes when. We made that argument at length in “What Makes an Actor Cheap?”.

But there's a second, less-advertised consequence, and it's the thesis of this article: in an immutable language, copying is never semantically necessary. A copy of a value that can never change is indistinguishable from the original — so every copy the runtime makes is pure overhead, there for the runtime's convenience, not the program's meaning. And a value that loses its last reference can never be observed again, so it should simply go away — immediately, without the program pausing for a garbage collector to come find it.

The research literature adds one precision that keeps this from being a slogan. The goal state is not literally “zero copies under all circumstances.” It is: no copy when you are the only owner of a value, and a cheap share — a pointer and a counter bump, never a deep copy — when you aren't. Even the most aggressive fully-in-place systems keep exactly one runtime test: am I the only owner? Asked as rarely as possible, that one question decides everything — when to update in place, when to share, and when memory can be handed back. Section 3 walks through the languages that ask it well.

First, though: how far is Hey from that goal state today? Not “roughly” — exactly. We counted.

2. The receipt: the copies Hey still makes, counted exactly

Term: box / boxing

A box is a small heap allocation that wraps a value together with a type tag, so the runtime can pass “some value” around without knowing at compile time whether it's a number, a string, or an array. In Hey's runtime a box is 32 bytes. Boxing an integer means allocating that wrapper and putting the integer inside; unboxing means reading it back out. The integer itself is 8 bytes; the ceremony around it is the cost.

We wrote a small counting probe: three one-line shapes, each run one million times over a 64-element integer array, with the runtime's allocation counters switched on. Here is what compiled Hey at 474a does today, per iteration, on our macOS box — alongside the store-path and push measurements that complete the ledger:

Look at the first row for a moment, because it is the whole story in miniature. Hey's arrays are immutable. Nothing can ever change the element sitting at a[1]. And yet, to let your program look at that number, the runtime clones it and gift-wraps the clone in a fresh 32-byte heap box, which your program unwraps, uses, and throws away. One read, one small ceremony. A million reads, a million ceremonies — each individually cheap, none of them necessary, and the counter says exactly 1.000 per read, so we will know the moment it becomes 0.000.

Does this actually matter? Here's the calibration pair. On a benchmark that lives entirely in registers — an integer recurrence with no array accesses — compiled Hey runs at 1.056× the speed of C: five percent off, essentially done. On fannkuch-redux — a classic array-permutation benchmark whose inner loop is nothing but element reads, compares, and swap stores — the same compiler was 161× slower than C (quiet Linux box, 471a, medians of 5, output-checked). Hey's arithmetic is already competitive. The entire gap is what an access costs — which is to say, the entire gap is the table above.

3. One runtime question deletes them all: “am I the only owner?”

Term: reference counting

Reference counting is the bookkeeping scheme where every value carries a small counter of how many references point at it. Take a new reference: the count goes up. Drop one: it goes down. When it hits zero, nothing can ever see the value again and its memory is freed on the spot. Think of a library book with a list of borrowers stapled inside the cover — when the last borrower crosses their name off, the book can be pulped immediately; nobody has to search every house in town (which is roughly what a tracing garbage collector does instead).

The reason we're confident these copies can be deleted — rather than merely shaved — is that a family of research languages has already deleted them, in production, with measured results. They all pivot on the same single question, asked at a write site: is this value's reference count exactly 1? If yes, you are the only owner; nobody can ever observe the difference between “build a modified copy” and “update the original in place” — so update in place, with zero allocation. If no, share the original by reference and bump the counter. That's the whole trick:

Perceus (Reinking, Xie, de Moura, Leijen — PLDI 2021), the reference-counting engine of the Koka language, is the deepest version. The compiler tracks ownership of every value through the whole program and inserts precise count-up/count-down operations at exactly the right places — then spends two more passes deleting most of them again. Its reuse analysis notices when a pattern match consumes a value and the same branch allocates a new one of the same size, and emits a single runtime uniqueness check: if the old cell is unshared, the new value is written straight into it. Their measured result on a 42-million-insertion red-black tree: purely-functional Koka within 10% of hand-mutated C++ std::map — while Java on the same benchmark matched the speed but used roughly 10× the memory (1.7 GiB (gibibytes) versus Koka's 170 MiB). And when the authors disabled just the reuse and specialization passes, Koka got more than 2× slower on that tree — the in-place trick isn't a garnish; it's the meal.

The runtime half of the trick is small enough to quote. Perceus's entire “drop a reference” fast path is: 

static inline void drop(block_t* b) {
  if (b->header.rc <= 1) drop_check(b);   // slow path: maybe free
  else b->header.rc--;                     // fast path
}

Counting Immutable Beans (Ullrich & de Moura — IFL 2019) is the production version of the same idea inside Lean 4, and it adds the concept most relevant to Hey's read path: borrowed references. A function that only looks at a value — never stores it, never outlives the caller — can borrow it with no reference-count traffic at all. That is precisely what an array read should be. Hey's read path already half-does this: the collection itself is borrowed. The element clone-and-box from section 2's first row is the remaining violation, and the read slice exists to delete it.

Swift proves the same primitive works as a library convention rather than a compiler pass: its arrays and dictionaries are values on the surface, backed by a reference-counted buffer, and every mutating method calls isKnownUniquelyReferenced — count is 1, mutate in place; count is higher, copy first. Same question, asked by hand.

Two more results mark the edges of the map. First, the question must be asked rarely: Perceus's specialization pass hoists uniqueness checks out of hot paths so the fast loop asks once instead of every iteration — and the paper measures what happens when you get this wrong, in a different guise: forcing every count operation to be thread-safe-atomic (the always-assume-shared worst case) costs 5% to 59% across their benchmarks. The check is cheap; asking it constantly is not. Second, the endpoint exists: FP²: Fully in-Place Functional Programming (Lorenzen, Leijen, Swierstra — ICFP 2023) defines a checked discipline under which a pure function is guaranteed to run with zero allocation, entirely in place, whenever its arguments are unshared. Not “usually avoids copies” — a theorem-shaped guarantee that the immutable program and the hand-mutated one compile to the same thing. That is what “nothing changes, so copy nothing” looks like when it's finished.

4. A value that loses its last reference should simply vanish

The second half of the promise is about death rather than birth. Precise reference counting of the Perceus family is garbage-free: a value's memory is returned at the moment of its last use — not at the next collector cycle, not when a heuristic fires. There is no floating garbage, no collector run, and no pause, because there is no collector: freeing is just the zero branch of the drop function above.

The classic reason this doesn't work is cycles — two values pointing at each other keep both counts above zero forever, which is why most reference-counted systems (Python, for one) bolt a cycle-detecting collector back on. Hey doesn't have to. In Hey, every value is immutable and can only ever point at values that existed before it was built — so a reference cycle is structurally impossible, and plain reference counting is complete. This isn't a hope; it's an invariant, adopted into the language plan with an automated guard test that would trip if any future feature broke it. It is the same argument the Erlang virtual machine has quietly relied on for decades for its reference-counted large binaries: immutable and pointer-free, therefore countable with no race machinery and no cycle collector, ever.

And when the bookkeeping is wrong, our own counters can see it — that is what section 2's compare row is. Two boxes allocated per iteration, zero released: a missing decrement on one code path, observed as a steady 64 bytes lost every time the loop runs the comparison. The flip test at the heart of fannkuch-redux is exactly this shape. The allocations-versus-releases counter pair is, in effect, the acceptance instrument for the whole second thesis: for every shape the language can express, allocations minus releases must read zero. Today, on that shape, it doesn't. The fix is queued at the front of the next slice, and the read slice independently makes those boxes never exist on the shapes it covers.

5. Reclamation that never stops the program — and the question we won't decide by taste

The third thesis says reclamation should be asynchronous: cleanup should never make the program stand still. This one also has a literature, and its headline system is ORCA (Clebsch, Drossopoulou, Blessing, McNeil — OOPSLA 2017), the garbage collector of the Pony language. Every Pony actor owns a private heap and collects it only when that actor is idle between messages; no actor's cleanup ever freezes another, there are no read or write barriers on ordinary memory accesses, and there is no stop-the-world phase, ever. Values shared across actors are reclaimed by reference-count messages that ride along with normal traffic — garbage collection conducted entirely by asynchronous messages, without stopping current processing. The Erlang VM gets a gentler version of the same property from per-process heaps: collections are per-process and tiny by construction, so pauses are microscopic even though they exist.

Both systems paid something for it. Erlang deep-copies every message between processes — the price of keeping heaps isolated. Pony shares even mutable data zero-copy, and its authors are candid about what that cost them:

“In a purely functional actor language such as Erlang... it would be trivial to implement a collector such as ours... One of the early decisions in the design of Pony was to support mutable data structures and, for efficiency reasons, to implement zero-copy message passing. Mutability introduce[s] challenges...” — ORCA, §1–2

Pony's answer to those challenges was an entire compile-time capability type system. Hey is immutable, actor-based, and cycle-free — which means the safety half of ORCA's machinery is simply unnecessary here. Sharing by reference across actors needs no barriers, no capability annotations, and no cycle protocol, for the same reason Erlang's big binaries need none.

But one genuine design question remains open, and we are deliberately not answering it in prose. Eager freeing and actor-deferred freeing have opposite cache behavior. Eager reference counting frees a value at its last use — and Perceus's wins come partly from what happens next: the just-freed cell is still hot in the CPU cache, and the reuse trick writes the next value straight into it, often in the same loop iteration. Handing frees to a collector actor instead buys clean decoupling — the hot path never even branches on death — but by the time the collector touches the memory, it's cold, and the hot loop has lost its recycled cell. Which effect dominates, on Hey's workloads, on real hardware? That is a measurement, not an argument. The counting and timing instruments that priced every row of section 2 can A/B the two designs the moment a prototype exists; the predictions will be pre-registered, and both verdicts are publishable. If the collector actor loses, you will read that here too.

6. The punchline for Hey: the best cell in the table

Every other row bought its strengths with something Hey doesn't have to spend. Pony's capability system exists to make sharing safe under mutability; Hey's values can't mutate. Erlang's message copies exist to keep heaps isolated; Hey can share by reference with no machinery at all. The cycle collectors of the reference-counted mainstream exist because cycles exist; Hey proved they can't. What remains is engineering: stop making the copies, one measured slice at a time. The reference-counting upgrade that all of this builds toward is an adopted “go” in Hey's roadmap, and the queue against section 2's ledger currently stands exactly here:

  • Landed: the move fix (471a) — the whole-array clone on the swap store is gone.
  • Branch-ready, not merged: the fusion fix — two allocations per store to one, exactly 2.000 → 1.000 by counter, −22.7% time per store.
  • Designed, pricing in progress: the read slice — return a bare integer from an element read instead of a cloned, boxed one. The counting half of its pricing is done (that's how section 2's exact 1.000 was established, with a pre-registered target of 0.000); the timing half waits its turn on a quiet machine, because we don't time benchmarks on a busy box and we don't build fixes before pricing what they should save.
  • In progress: the push fix — delete the n(n+1)/2 behind push() — and the arithmetic re-boxing convention behind the three-box row.
  • Queued: the compare-shape leak fix, at the front of the next slice.
  • Not yet owned, stated plainly: the uniqueness-check hoist (asking section 3's question outside hot loops instead of inside them) and the eager-versus-deferred reclamation A/B from section 5. Both are natural next claims once the read slice reports; neither has an owner as of this writing.

The method doesn't change as the queue advances: every fix gets a pre-registered exact-integer target from the allocation counters — 2.000 to 1.000, 1.000 to 0.000, allocations minus releases equal to zero — measured before and after, with the evidence archived, the way the web-throughput campaign and the 50 GB case file were run. A copy that an immutable language never needed to make is the most satisfying kind of performance bug: the correct amount of that work is zero, the counter says exactly how far from zero we are, and “done” is not a judgment call.

Glossary

box / boxing
A small heap allocation (32 bytes in Hey) wrapping a value with a type tag so the runtime can handle values of unknown type; boxing is putting a value in, unboxing is taking it out.
clone
A runtime copy of a value. For a small integer it's a cheap field copy; for a collection it can be a full O(n) duplication.
reference counting
Tracking, per value, how many references point at it; the memory is freed the instant the count reaches zero.
borrowed reference
A reference used only for the duration of a call, never stored — so it needs no reference-count traffic at all (Lean 4's term).
in-place reuse
Writing a new value directly into the memory of a dead old value of the same size, skipping both the free and the allocation (Perceus's reuse analysis).
uniqueness check
The single runtime test refcount == 1: if it passes, you are the only owner and may mutate in place with no observable difference.
copy-on-write (COW)
Sharing one buffer among many logical values and copying it only at the moment someone writes while it's shared — Swift's collection strategy.
garbage-free
The property of precise reference counting that memory is returned at a value's last use — no floating garbage awaiting a collector cycle.
cycle
A loop of references (A points at B, B at A) that keeps naive reference counts above zero forever. Impossible in Hey: immutable values can only reference values older than themselves.
stop-the-world pause
A garbage-collection phase during which the whole program is frozen. ORCA and per-actor designs exist to have none.
per-actor heap
Giving each actor its own private memory region so it can be collected independently, while that actor alone is idle.
fannkuch-redux
A classic array-permutation benchmark (from the Computer Language Benchmarks Game) whose inner loop is almost entirely element reads, compares, and swap stores — which is why it prices Hey's access path so well.
