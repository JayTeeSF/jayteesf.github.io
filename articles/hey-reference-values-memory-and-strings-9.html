Hey values, memory and Strings

In Hey a value never changes. "Updating" a map gives you a new map, and the old one is still there. That sounds like a copy every time. Usually it isn't, and this page shows why, what it costs when it is, and what's decided to make it cheaper.

Implementation scope: 16-byte HeyStr, 63-bit InlineInt & MIR-SSA lifetimes in 0.99.610a

Shipping in the 0.99.610a runtime and unified native compiler (Works today): Every String uses the 16-byte German String layout HeyStr (section 5, runtime/hey_str.h11). Strings of 0–12 UTF-8 bytes store their length and bytes inline inside two 64-bit registers with zero heap allocation and zero reference-count traffic; strings over 12 bytes store a 4-byte length, a 4-byte prefix, and an 8-byte tagged pointer (class bits 54..55) to a 32-byte-header reference-counted Simple Dynamic String (SDS) block (section 4) with geometric slack growth on unique appends, or live borrowed bytes. Unbounded integers travel in a single CPU register as a 63-bit Least Significant Bit (LSB)-tagged InlineInt up to ±4.61 × 1018 before touching heap BigInt storage; homogeneous arrays pack int64_t[], double[], or contiguous shaped-record scalar slots (HEY_ARRAY_REPR_SHAPED); flat value-specialized maps update in one probe via Map.increment and Map.update; and generic dynamic HeyValue cells remain 32 bytes. Stages 5–8 pass unboxed registers across specialized define linkonce_odr workers (HeyMirPhysical.hey, Compiler 1 §6), track transitive owner-scoped zero-reference-count (RC) borrows, fuse dynamic receiver copy-on-write updates (own_fuse_cow_take_receivers), place Perceus drop-guided reuse and dynamic hey_region_push/hey_region_pop arenas on lexical block_scopes, and verify all 8 invariants in HeyMirVerify.hey3.

Planned extensions (Decided, coming / Proposed): Unboxed register passing for standalone flat user records of up to 4 scalar fields across call boundaries (Decided, coming) and SwissTable string-key map probing (Proposed; docs index).

1. Immutable values, and the cost puzzle Works today

Every Hey value (number, String, array, map, record) is immutable. put, push, merge and the spread {...doc, visits: 1} all return a new value:

immutable.hey

program
  let fruit = {apples: 1}
  let more = fruit.put('pears', 2)
  let doc = {name: 'Ada'}
  let next = {...doc, visits: 1}
  says fruit
  says more
  says doc
  says next
end

Run it

$ hey immutable.hey
{"apples":1}
{"apples":1,"pears":2}
{"name":"Ada"}
{"name":"Ada","visits":1}

fruit and doc are untouched. (hey file.hey compiled this to native code and ran it.)

Measured on an Apple M3 Pro baseline; see Note 1.

That's the safe part: no function can change a value you passed it, and an actor can be handed a value (copied or moved) without locks, because nothing can change it. Now the puzzle. This is how everyone counts things in Hey:

set counts = counts.put(word, counts[word] + 1)

If put copied the map each time, counting a million words over a thousand-key map would copy about a billion entries. Does it?

count.hey: count a million words over a 1,000-word vocabulary

import 'stdlib:Cli'
import 'stdlib:Text'
import 'stdlib:Time'

fn count_words(n)
  let counts = {}
  let i = 0
  while i < n
    let word = 'w' + (i % 1000)
    if counts.has?(word)
      set counts = counts.put(word, counts[word] + 1)
    else
      set counts = counts.put(word, 1)
    end
    set i = i + 1
  end
  return counts
end

program
  let n = Text.parse_int(Cli.args()[0])
  let started = Time.now_ns()
  let counts = count_words(n)
  says counts['w7']
  says Time.ns_to_ms(Time.elapsed_ns(started))
end

2. Reference counts and copy-on-write Works today

Heap-backed maps, arrays, records and owned long String SDS blocks (> 12 bytes) use atomic reference counts: sharing that backing increments the count, while short Strings (<= 12 bytes) copy inline inside two 64-bit registers with zero reference-count traffic. Copy-on-write is on by default;2 it removed the clone-per-put on values with one owner.

The runtime has one uniqueness test, hey_rc_count_is_unique: is the count exactly 1? Every in-place decision passes through it, which is what makes the falsification switches in Performance possible: sabotage that one test and the ownership specs must fail. HEY_RC_COW=0 turns copy-on-write off (every update copies), for comparisons.

3. Perceus: release at last use, update in place

A count of 1 only helps if the old name lets go before the update. In set counts = counts.put(...), the old counts is never read again, so the compiler can hand the map straight to put instead of holding a second reference. That idea, from the Perceus paper (Reinking, Xie, de Moura and Leijen, PLDI 2021, used in Koka and Lean 4), has four parts:

Release at last use. HeyMirLiveness.hey and HeyMirOwnership.hey release an owned value immediately after its final read, never waiting for the end of the function.
Consume a dead value (move). A call receiving an owned value nobody reads afterwards takes over its sole credit: no extra retain, so a unique map or SDS string stays unique (refs == 1).
Zero-RC owner-scoped borrows (view live => owner live). Read-only parameters and interior slices track their transitive backing owner across blocks and joins, executing 0 retain/drop operations while the owner stays live.
Perceus drop-guided reuse. A dead unique cell (F4, zero live loans, compatible storage) becomes the in-place memory for a same-size allocation—holding peak RAM flat at 1x instead of spiking to 2x.

Where it lives: in Stage 7 of the compiler (HeyMirLiveness.hey + HeyMirOwnership.hey), audited by Stage 8's independent HeyMirVerify.hey before HeyMirLlvm.hey emits native code (Compiler 1 §7–§8). The LLVM emitter obeys MIR's verified plan one-for-one and never guesses cleanup actions; nothing imported may claim ownership without an explicit signature contract.

In 0.99.610a (Works today), HeyMirLiveness.hey, HeyMirOwnership.hey, and HeyMirVerify.hey enforce typed SSA-MIR ownership end-to-end: last-use moves, transitive view live => owner live borrows, Perceus drop-guided cell reuse (measured 19× faster on a 40,000-step functional update prototype), dynamic receiver copy-on-write fusion (own_fuse_cow_take_receivers -> hey_llvm_json_put_value_take_receiver / hey_llvm_json_push_value_take_receiver, preserving box_refs == 0 && backing->refs == 1 across HeyValue* map and array accumulators), unwind cleanup shadows, and independent credit verification across every control-flow path, while runtime hey_rc_count_is_unique keeps dynamic sharing safe.3

4. How long Strings keep their bytes: SDS

In 0.99.610a, only long Strings (> 12 UTF-8 bytes) allocate a backing block; short Strings (<= 12 bytes) live inline inside the 16-byte HeyStr value (section 5). Long OWNED and STATIC Strings point to an SDS block ("simple dynamic string", the layout Redis popularized): a 32-byte header (refs, base, length, capacity + flags), followed immediately by the UTF-8 payload bytes, slack capacity, and a trailing NUL byte for C interoperability. An OWNED block is atomically reference-counted; a STATIC block has immortal count (2^62) and is never freed; a BORROWED view points into live foreign or interior bytes with zero reference-count overhead.

  • One backing allocation for a long owned String, header and bytes together. Short Strings store bytes inline. Conversion from a separately allocated C buffer copies into canonical String storage.
  • Boxing preserves ownership. Short values copy inline; long owned values can share their block with a count change. A borrowed view is promoted before a generic value stores it.
  • The permanent backing of a long literal is never freed. Its String value still follows the ordinary ownership rules; dropping it does not free that backing. Short literals copy their inline bytes.
  • The NUL byte is only for C. Hey Strings can hold any byte, including zero; the NUL check happens only where a value crosses a declared C boundary.
  • Appending can reuse an exclusively held owned backing block when its capacity permits. Otherwise the runtime obtains suitable storage and preserves aliases. The loop below is a language example; its earlier documentation-test result is not new compiler qualification.

import 'stdlib:Cli'

Zero-copy Bytes views & in-place slice parsing Works today

Bytes is immutable binary data backed by a reference-counted byte buffer (or an mmap view from Files.map_readonly). Bytes.slice shares the parent's block in O(1) (one reference-count increment, zero byte copies), and 0.99.610a adds zero-copy scanning helpers so you don't allocate temporary per-line strings when streaming multi-megabyte inputs:

  • Bytes.each_line(buf, line_fn) scans newline boundaries via memchr and passes integer [start, end_off) byte offsets to a named function (or bind(...) callable) with zero slice allocation;
  • Bytes.parse_int_slice(buf, offset, length) and Bytes.parse_fixed_slice(buf, offset, length, scale) parse signed integers or scaled fixed-point numbers straight from byte offsets;
  • Bytes.slice_equals?(buf, offset, needle_bytes) compares an interior span against needle_bytes without allocating a slice.

bytes.hey

import 'stdlib:Bytes'

program
  let data = Bytes.from_text('station;12.5', 'utf-8')
  let name = Bytes.slice(data, 0, 7)
  says len(data)
  says Bytes.decode(name, 'utf-8')
  says Bytes.find_byte(data, 59, 0)
end

Run it

$ hey bytes.hey
12
station
7

12 bytes; the first 7 decode to station; byte 59 (;) is at index 7.

5. How a String is stored: the 16-byte value Works today

Hey has a single String layout: the 16-byte German String HeyStr (implementation scope). Strings of 0–12 UTF-8 bytes live completely inline inside two 64-bit registers; strings over 12 bytes cache a 4-byte prefix alongside a tagged 64-bit pointer. OWNED and STATIC long Strings point to 32-byte-header SDS blocks; a BORROWED String is a zero-RC length-delimited view into live external or interior bytes governed by view live => owner live in HeyMirLiveness.hey and HeyMirOwnership.hey.

The rules, in plain English

  • Always 16 bytes, 8-byte aligned—carried in two 64-bit registers ({ i64, i64 }) across specialized linkonce_odr workers on AArch64 and x86-64 LP64 (Compiler 1 §6). The first 4 bytes hold the unsigned 32-bit byte length, capping one String at 4 GiB; larger binary payloads belong in Bytes.
  • The length is the only authority. A String can hold any byte, including zero. Nothing ever searches for a terminating NUL to find the end.
  • Short if and only if 12 bytes or fewer. Bytes 4–15 hold the UTF-8 bytes directly, zero-padded to 16 bytes, requiring 0 heap bytes, 0 pointer dereferences, and 0 atomic reference-count operations regardless of whether the String came from a literal, a slice, or a concatenation. Equal short Strings have identical inline bytes; equal long Strings may point to distinct backing blocks.
  • Long Strings keep a 4-byte prefix. Bytes 4–7 copy the first 4 bytes of text, and bytes 8–15 pack a 2-bit storage class in bits 54–55 alongside the byte address. Bits 56–63 stay untouched for Android and ARM memory tagging (top-byte-ignore).
  • Four classes. Owned: a reference-counted SDS block whose count updates atomically. Static: immortal SDS backing that is never freed (dropping its HeyStr value is a no-op). Borrowed: a zero-RC length-delimited view into live foreign or interior bytes; HeyMirLiveness.hey keeps its transitive backing owner live across every read (view live => owner live), and HeyMirOwnership.hey promotes it via hey_str_to_owned before it escapes into an owning collection, field, return value, or actor message. Concat: reserved bit pattern; unused.
  • The bytes never change. Appending mutates an SDS buffer in place only when the String is OWNED, uniquely held (refs == 1), and has slack capacity; otherwise it allocates fresh storage while leaving aliases untouched.
  • Comparing. Equality compares the first 64-bit register (len + pfx[4]) in one instruction—rejecting unequal lengths or mismatched 4-byte prefixes with zero RAM reads—before checking inline/remaining bytes. Ordering uses unsigned byte order (memcmp).
  • Crossing into C. C expects NUL-terminated text. An OWNED or STATIC SDS block already carries a trailing NUL, and a short String of 0–11 bytes has inline zero padding; a 12-byte short String or an interior borrowed slice materializes a NUL-terminated caller scratch copy after checking for embedded zero bytes.

What this layout can avoid

Length and prefix can reject equality. Unequal lengths or unequal cached prefixes prove the Strings differ. Lexicographic ordering compares text from the start: a difference in the cached prefix can decide order, but length alone cannot.
A short carrier needs no backing allocation. A result of 12 bytes or fewer keeps its bytes inside the value. An operation producing it may still allocate temporary builder storage; the carrier itself has no backing count or block to release.
Sharing preserves the bytes. The bytes never change, so any number of threads and actors can read one String at once. Sharing an owned String is one atomic count change; a short one is just copied.
Borrowing needs a live owner. An internal view can point into a parent String. Before an owning collection, field, message or returned value takes that view, it must acquire owned storage. A pointer into short text also becomes invalid when that particular String value moves or dies.

This design isn't new. It comes from the Umbra database at TU Munich and its successor CedarDB,9 and DuckDB, Meta's Velox and Apache Arrow's StringView use the same 16-byte layout.10

6. InlineInt, flat maps, and unboxed arrays

63-bit register InlineInt keeps unbounded integers off the heap Works today

When HeyMirFacts.hey proves an integer stays inside signed 64-bit bounds, it runs in a raw i64 register. What if a loop bound comes from a file or recursive accumulator so static bounds aren't known? In 0.99.610a, Hey carries it in a single 64-bit CPU register using a Least Significant Bit (LSB) tag ((word & 1) == 0 for any integer in ±4.61 × 1018), allocating a heap BigInt only when a hardware overflow flag fires:

Single-probe Map.increment & Map.update on flat specialized maps Works today

Map.put, bare put, Map.increment(map, key, delta), Map.update(map, key, default_val, updater), and push update uniquely held receivers in place. Writing if counts.has?(k) ... counts.put(k, counts[k] + 1) hashes and probes k three separate times; Map.increment and Map.update hash k once, probe once, and mutate flat value-specialized slots (i64, f64, or fixed-shape records) in place when HeyMirOwnership.hey proves sole ownership3.

SwissTable string-key probing follow-up Proposed

A Robin-Hood design that stored each index slot's probe position was measured and set aside because it cost 102% more instructions on one lookup shape and clustered high hash bits. SIMD SwissTable control-byte probing keyed directly on 16-byte HeyStr remains proposed on top of today's flat value-specialized map storage.

Homogeneous unboxed arrays, HEY_ARRAY_REPR_SHAPED record arrays & spread appends Works today

Appending to an array you alone hold (push(xs, item) or set xs = [...xs, item]) mutates in place with geometric capacity growth. Homogeneous Int and Float arrays store raw unboxed int64_t[] and double[] buffers (8 bytes per element instead of 32-byte boxes), while homogeneous arrays of static-key records pack scalar fields into contiguous flat slots (HEY_ARRAY_REPR_SHAPED) with {data_ptr, len} hoisted once before hot loops (Performance §7).

7. Regions and flat records

Reference counting frees values one at a time. A program that builds a tree, reads it and throws it away pays one allocation, one count update per share and one free per node. Two old, well-studied ideas remove that cost without changing what the program means.

The four facts and lexical block_scopes arenas Works today

Which values bump-allocate in a dynamic region—and which dead cells get reused in place—comes from four monotone dataflow facts in HeyMirFacts.hey and placement in HeyMirOwnership.hey (Compiler 1 §5 & §7):

  1. F1 fresh result: every value returned by a function is newly built by that call.
  2. F2 escape: whether a value outlives its lexical scope via return, heap store, closure capture, or actor send, solved over call SCC summaries.
  3. F3 smallest lexical block_scopes region: the innermost statement, call, or single loop-iteration scope (preserved across split critical edges by HeyIr.hey) enclosing every use of a non-escaping fresh value—never a whole loop, so loop scratch cannot accumulate across iterations.
  4. F4 unique and dead: the value has one owner, zero live borrowed views, and no later reads, enabling Perceus in-place reuse.

One worklist solver computes F1–F4 over sealed-block SSA-MIR with zero special cases: no rule ever inspects a function spelling, field name, file path, or benchmark (Performance §3). In 0.99.610a, HeyMirOwnership.hey places hey_region_push and hey_region_pop on block_scopes6 and HeyMirVerify.hey checks LIFO nesting and loan non-escape before codegen3.

Flat scalar records and regions Decided, coming

Hey combines both mechanisms: standalone records of up to four scalar fields will unbox straight into CPU registers across specialized workers (Compiler 1 §6; homogeneous arrays of static-key records already pack into contiguous HEY_ARRAY_REPR_SHAPED slots), compact shaped headers shrink heap-allocated records, and dynamic block_scopes arenas (Works today) reclaim whole groups of short-lived scratch records in a single pointer reset.

Actor and turn regions Proposed

The same arena machinery extends naturally to actor turns: reclaiming temporary allocations from a single message-handling turn (including unwinds on failed turns) in one step when the turn finishes. Actors: Actors and failure.

8. The small-block allocator Works today in 0.99.610a

Record headers, array headers, 32-byte HeyValue boxes, and small long-String SDS blocks sit between 32 bytes and 1 KiB, and ordinary programs allocate and free them constantly. In 0.99.610a they come from Hey's 27-size-class thread-local page allocator instead of general malloc,7 following mimalloc's free-list sharding (Leijen, Zorn and de Moura, 2019), while short Strings (<= 12 bytes) stay inline in HeyStr and 63-bit InlineInt values stay in CPU registers with zero backing allocations.

Three allocator changes finished it: medium blocks up to 1 KiB, the String lifecycle inlined (a 320-byte String's allocate-and-release went from 750 to 298 instructions), remote frees settled before a thread abandons a page, and pages that dead threads leave empty retired.8 It runs under AddressSanitizer too, with every free block poisoned, so the sanitizer tests the allocator that ships.

Size-specialized allocation Proposed

The next step goes further: allocate each value from the exact size class known at compile time, skipping the size lookup. The size classes above are its foundation.

9. Watching memory yourself Works today

Three builtins: reset_allocations() zeroes the counters, allocations() returns them as a map, and memory_rss_bytes() gives the process's resident memory.

watch.hey: count in place, then count while keeping the old map

fn count_alone(n)
  let counts = {}
  let i = 0
  while i < n
    let word = 'w' + (i % 100)
    if counts.has?(word)
      set counts = counts.put(word, counts[word] + 1)
    else
      set counts = counts.put(word, 1)
    end
    set i = i + 1
  end
  return counts
end

fn count_keeping_old(n)
  let counts = {}
  let sizes = 0
  let i = 0
  while i < n
    let word = 'w' + (i % 100)
    let before = counts
    if counts.has?(word)
      set counts = counts.put(word, counts[word] + 1)
    else
      set counts = counts.put(word, 1)
    end
    set sizes = sizes + len(before)
    set i = i + 1
  end
  return counts
end

fn report(label)
  let stats = allocations()
  says label + ': in place ' + stats.json_write_inplace + ', copied ' + stats.json_write_cow_copy
end

program
  let ignored = reset_allocations()
  let a = count_alone(1000)
  let first = report('alone')
  let reset = reset_allocations()
  let b = count_keeping_old(1000)
  let second = report('keeping the old map')
  says memory_rss_bytes() > 0
end

Two environment variables help outside the program: HEY_ALLOC_STATS=1 prints every counter as one JSON line on exit (it also turns on the six allocation counters, such as xmalloc_calls, which read 0 without it), and /usr/bin/time -l (Mac) or /usr/bin/time -v (Linux) gives instructions and peak memory. HEY_ALLOC_STATS=1 hey watch.hey printed the same three lines, then (shortened) HEY_ALLOC_STATS {"xmalloc_calls":6722,"xmalloc_bytes":4034208, … "json_write_inplace":0,"json_write_cow_copy":1000, …}; its totals are for the whole run after the last reset.
