The plan

What gets built, in what order, and how we will know it worked — including the parts we cannot yet size.

Updated 2 August — two corrections and a reordering

1. The parser decides what - means, not the tokenizer. The tokenizer always emits a MINUS token; the parser decides prefix or infix from context, which is what Pratt parsing was designed for. This doesn't just tidy the current lexical guess — it makes the arr[0] - 1 bug family unrepresentable, because the previous-character set stops existing.

2. Don't complete the self-hosted emitter against the old intermediate form. Keep the fallback counter. But that form still carries raw source expressions which the emitter re-parses, so every handler written against it is a handler that must be migrated or thrown away — and each one enlarges the surface that has to move.

3. “Non-copying access” is two jobs at opposite ends. Verification found that construction must move earlier — every node currently costs a JSON parse of the two-character document {}, and there is no sized constructor in that lane at all. But reading must stay late: a child fetch is spelled at fifteen sites across five modules today and in exactly one generated file afterwards, so doing it early means doing the hard version and then doing it again.

Done means three things

  1. Fast web servers at the per-core bar — within 3% of Go under the same conditions, about 97,000 requests per second on one core.
  2. Fannkuch.
  3. 1BRC — the billion-row challenge.

When all three run on the restructured pathway at or above where they run today, we are ready. These are the exit criteria. Nothing else is. No phase below is finished because it feels finished.

One thing you said reorganises the work more than anything else: you will keep running the current version until the new one is good. Until now every landing had to leave the shipped compiler working, which forced small reversible steps. That constraint is lifted here. The obvious risk is a path nobody checks, so the specs replace the release cadence as the thing that keeps us honest. A spec, here and below, is an executable test: a small Hey program checked in beside the answer it is required to produce.

What we keep and what we rebuild

This is a new front end on a retained back end, not a rewrite. The heaviest work already done — the runtime and the LLVM emitter, the stage that writes the low-level text LLVM turns into machine code — is the future and stays.

Machine shapes and operators — MIR, the stage between meaning and instructions — is the one you should see now rather than discover in month two. It is supposed to turn meaning into instructions. Today it renames types and rewrites a header, and that is all: compare the checked-in before-and-after files for one program and the right-hand side of every line is still raw Hey source text. Its own source says so — "expressions are raw text". Search it for a single arithmetic operator and you get nothing.

So the LLVM emitter downstream re-reads expressions itself, with thirteen hand-written scanners — a second census of the same file counted six, on a narrower definition, and neither count has been reconciled — while the comment at the top of its own file forbids exactly that. It is not disobedient. It is stranded.

The phases

0  Make the silent hand-off loud

When the Hey-written LLVM emitter meets something it cannot handle, the build quietly hands that program to the older C one. The precise reason is computed and then thrown away, and no switch prints it. About six lines of work.

Verified by: every build becomes a counter. Until this exists, "finish the port" has no finish line. It goes first because everything after it is measured with it.

1  Specs, to excellent coverage

Grow them across where a value sits crossed with what you do to it, not by subject area. Ten positions: a literal written inline, a literal held in a local variable, a parameter, a call result, a field, an array element, a map value, an argument to an actor, an actor's own state, and nested combinations. (An actor is Hey's unit of concurrency: it holds private state and is reached only by sending it a message.) The reason is our own record: a fix that covered one position missed the next one along. The two positions nothing has ever swept are the actor ones — no test in the tree does arithmetic inside an actor.

Verified by: both lanes — the interpreted one and the compiled one — producing identical output, and a ratchet — a known gap may sit red without blocking anyone, but anything that has been green and goes red stops the build.

2  Finish the Hey-written LLVM emitter

Pure addition. Two independent counts agree that it can do nothing the C one cannot, so this is a one-directional port and never a merge. The work list is a specific 344 runtime facilities it does not yet reach, plus floating point, which it has none of.

Verified by: phase 0's counter reaching zero across the example corpus — after the corpus is checked for selection bias, since at least one example in it was written around a gap rather than exposing one, and says so in a comment.

3  The interpreter

The scheduling surprise. The interpreter — the thing that runs a program without compiling it, and whose interactive face is the prompt — shares no code with the new pathway. Not one reference. So "one pathway serving both compiling and typing a line" is at 0% for the interpreter half. The recommendation is that it stops parsing for itself and walks the same typed form the compiler produces. Its values and built-ins already live in the shared runtime; only its parser dies.

Verified by: the existing interpreter-driven specs passing unchanged — which is also the payoff, because that one change takes the overwhelming majority of our specs from exercising none of the compile pathway to exercising four stages of it.

4  Delete the old paths

Only now, and per the standing rule: a path is switched off after the specs that pin its behaviour exist and have been proven able to fail. Record what it was catching before it goes. The C LLVM emitter cannot be dropped until phase 2 completes — integer division and remainder still run through it.

Verified by: deleting the implementation and watching the spec go red, one path at a time.

5  Apps on top

Run the real applications, find the regressions and the new bugs, write a spec for each. Your own loop — and the app teams already file exactly this kind of report.

Verified by: the three exit criteria at the top of this page.

Why this can move fast

We are not designing in the dark. There is a working language to check every answer against, and it is the one nearly every fix in our record was measured with. A new implementation that disagrees with it has to explain itself.

The regression suite is real software, not test files. An Apple TV app, an Android app, web servers, web clients, actor programs. These have found defects no test file in the tree could see — including a class where one platform could not build at all.

And the port is addition only. Measured twice, by two different methods, which is why it is worth stating flatly: the Hey-written LLVM emitter can do nothing the C one cannot. Both declare the same 573 facilities; the Hey one reaches 205, the C one about 549, and the 344-item difference is the work list. Nothing has to be reconciled or merged. Honest caveat: that proof is at the level of runtime calls, so a construct handled entirely inline by one and not the other would be invisible to it. Settling it to certainty needs a build we have not run.

The risks, named

The compiler's core data structure needs features the compiler cannot compile

The front end is to be written in Hey. A syntax tree wants records and pattern matching; Hey has neither, so a tree node has to be a general-purpose map and every step through the tree becomes a map lookup. Collections are 45 of the 344 facilities the Hey LLVM emitter cannot yet reach, integer division and remainder are on the same list, and it cannot compile itself today for that reason.

Three ways out — write the front end against the interpreter first, finish the collections work first, or add a record type to the language — and none can be sized without a build we have not run. This is a schedule risk and it is not on the phase list.

The interpreter is a third implementation at 0%

Called out twice on purpose. The compile half has a written list of what is missing; the interpreter half has none, because both surveys can only see what the new pathway refuses, and the interpreter never asks it anything.

The rule that pins the new emitter has no exit

Every change to the Hey-written LLVM emitter must currently reproduce the C one's output byte for byte, against 90 stored samples. A new front end will change those bytes, and nobody has defined the moment when those samples stop being "whatever the old path emits" and become the new pipeline's own. Until that moment is defined, the contract that protects us also blocks us.

Some of our tests cannot currently fail

An audit of all 276 gate scripts found 215 that no automated lane invokes, 51 with no way to run them at all, and — the larger problem — 83 of the 159 that print a summary line make at least three claims the script never measured. A hard-coded summary cannot go partly red. Phase 1 is not just more specs; it is specs whose failure has been watched. The audit is written up in The Answer Key Cannot Be One of the Contestants.

Decide before code is written

What does not bind to?

not a == b

  the interpreter reads it as   (not a) == b
  the compiler reads it as      not (a == b)
  a third path doesn't recognise the word at all
  the language reference asserts a fourth thing:
    that they all agree

The same split, spelled ! rather than not, is the first decision on the architecture page. Those readings come from reading the source, not from running it — the survey that found them says so and marks the printed values as still needing a build. What is not in doubt is that the orderings cannot all be right.

Whichever way this is ruled, three of the five places that answer it today have to move. This is the one item where writing the rule down changes the language rather than recording it, so measurement cannot settle it. And it has to be settled before the parser is written, because the parser is what makes it one answer.

Two smaller ones in the same category: whether keyword arguments (f(count: 2)) are a real feature or get removed, and whether Hey gets an exponent operator. The second is cheap now and expensive later — the moment modules can reuse operator symbols, the built-in list becomes a public contract.

What is not yet sized

Four things, stated so they are not a surprise later. The bootstrap route above — three options, none costed. The interpreter — 0% and unmeasured. The byte-for-byte exit — no trigger defined. Actor lowering — whether actors get their own instruction family or ride the ordinary call path is undecided, and one actor operation is missing from all three implementations.

Two places our own documents disagree, reported rather than quietly picked. Spec coverage: the program directive says 42 of 760 specs invoke a real build; a fresh count says 18 of 988. Part of that is the denominator — the 760 is one directory, the 988 is the whole spec tree, and a live count of that one directory returns 773 rather than 760. Unreconciled, and quoting either fraction without naming its directory is how the next drift starts. Both describe the same shape: the overwhelming majority of our specs never compile anything. Chained comparisons (a == b == c): one survey reads the interpreter as grouping to the right, a later one reads the same code as rejecting it outright and marks its own claim as needing a run to confirm. Neither has been executed.
