TL;DR#

The attached note found a real and important signal, but its opening conclusion is too strong.

  1. The evidence points to Hey’s array-access path, not yet to one cause. A 161× gap on an array-heavy benchmark, compared with 1.058× on a register-only loop, makes arrays the first place to investigate. It does not isolate the cost of representation from calls, bounds checks, ownership checks, tag dispatch, copying, or boxing at runtime boundaries.
  2. Hey’s 32-byte HeyValue is a wide tagged value. That is not automatically the same thing as a heap box. It can avoid allocation and pointer chasing for integers while still paying for wide loads/stores, copying, tags, and reduced density.
  3. Fast languages do not all solve the problem “the same way.” They use several compatible techniques: tagged immediate values, NaN boxing, specialized collection layouts, primitive or typed arrays, JIT-generated monomorphic paths, type-check elimination, escape analysis, scalar replacement, and deoptimization when assumptions fail.
  4. Specialized numeric arrays are well-supported by the literature. PyPy’s storage-strategy work, V8’s element kinds, Julia’s inline isbits storage, OCaml array specialization, and Java primitive arrays all demonstrate the value of keeping homogeneous primitives out of general object layouts.[2][3][8][11][14]
  5. Compact tagging and specialized arrays are different ideas. LuaJIT stores a general TValue in one 64-bit word, but its ordinary table array part is still an array of TValue slots. It is therefore evidence for compact tagged values—not proof that NaN boxing provides homogeneous unboxed arrays “with no guards.”[13]
  6. Inlining may help before representation changes, and it can help even with 32-byte values. Once the compiler can see the access path, it may eliminate calls, propagate known tags, hoist checks, remove bounds checks, or scalar-replace temporary values. Representation and optimizer visibility compound, but neither strictly requires the other.[4][5][6][10]
  7. The next sound step is decomposition, not a wholesale redesign. Separate reads from writes; compare 8-byte and 32-byte storage; add one cost at a time; inspect LLVM IR and machine code; sweep working-set sizes; and measure representation-boundary crossings.

Reader checkpoint — Think “shipping,” not “types.”
A number can travel as a small parcel containing only its bits, or inside a larger package that also carries a label saying “I am an integer.” The larger package is easier for generic code to handle. The smaller parcel is cheaper to copy and lets more values travel together. Fast runtimes try to keep the small parcel on hot routes and only repackage it when necessary.

The short correction to the attached research#

The note deserves credit for three things:

  • It separates a fixed asymptotic defect from the remaining constant cost.
  • It explicitly refuses to use cache capacity to explain a 320-byte working set.
  • It lists important unknowns instead of pretending the 33 ns store has already been decomposed.

Its central overreach appears in this sentence:

◆

“The largest measured Hey-vs-C gap … is a VALUE REPRESENTATION problem, and every fast dynamic language has solved it the same way.”

A more defensible replacement is:

◆

The largest reported Hey-vs-C gap strongly implicates the generic array-access path. Wide tagged elements are one credible contributor, but the current measurements do not separate representation cost from call boundaries, checks, copying, ownership logic, or other work in that path. Fast runtimes address these costs with several different and often complementary techniques.

That revision preserves the useful finding without claiming more than the measurements establish.

Interesting, but easy to miss
“Boxing” is often used for three different things: allocating a primitive inside a heap object, storing a tagged machine word, and storing a wide tagged union inline. Those designs have different costs. A useful performance discussion must name the actual representation rather than using “boxed” as a catch-all.

1. What “boxed” means#

A program needs some way to distinguish an integer from a floating-point number, string, array, function, or object. There are four common representation families.

1.1 Heap boxing#

A variable contains a pointer to an allocated object. The object contains a header—often including type, garbage-collector, or synchronization information—and the primitive payload.

For a numeric hot loop, this can add:

  • an allocation when the box is created;
  • an extra pointer load before reaching the number;
  • object headers and alignment padding;
  • more objects for the garbage collector to trace;
  • less predictable memory placement.

Java’s Integer is the familiar conceptual example, although the JVM can eliminate some temporary boxes through escape analysis and scalar replacement. OpenJDK’s JOL exists precisely because actual object layouts depend on the selected VM and configuration.[6][15]

1.2 Tagged immediate values#

The value fits in one machine word. A few bits identify its type, while the remaining bits hold an integer or pointer. Integers can often be created and passed without heap allocation.

This is a common design in dynamic-language runtimes. It trades some payload range and a small amount of decoding for compact, uniform values.

1.3 NaN boxing#

IEEE-754 floating-point numbers reserve many bit patterns for NaNs. A runtime can use those patterns to encode non-floating values—pointers, integers, booleans, nil, and tags—inside one 64-bit word. LuaJIT’s source defines TValue as an aligned union containing a uint64_t, a Lua number, and other views, and documents the NaN-tag encoding in the same source file.[13]

NaN boxing is a form of compact tagging. It does not automatically make an array homogeneous, remove all type tests, or guarantee that every pointer layout is portable.

1.4 Wide tagged values stored inline#

Hey’s reported representation is in this family: a tag plus a union large enough for the widest inline alternative, totaling 32 bytes. An integer does not necessarily point to a separate integer object. Instead, every array slot reserves enough room for the largest union member.

That avoids one classic boxing cost—per-integer heap allocation—but retains others:

  • every element load/store may move 32 bytes rather than 8;
  • copies may consume more registers or spill to the stack;
  • the tag still needs to be created, propagated, or checked;
  • generic helper calls may force the full value through the ABI;
  • large arrays consume more cache and memory bandwidth.

This distinction matters because a proposed fix should attack the costs Hey actually pays.

Putting the payload directly inside the array slot removes a pointer chase. But if the slot is four times wider than the useful number, the CPU still has to transport the larger package through caches, registers, and function-call boundaries.

2. Why representation can make a language fast—or slow#

Representation affects performance through several mechanisms. They overlap, but they should be measured separately.

2.1 Bytes moved and values per cache line#

A 64-byte cache line holds eight 8-byte integers or two 32-byte HeyValue slots. For large sequential scans, compact values let each memory transaction deliver more useful payload. They also reduce pressure on caches and memory bandwidth.

The 2024 paper Compact Representations for Arrays in Lua examines this directly. Ierusalimschy and Rodriguez report that conventional tagged structures can waste substantial space to padding and investigate compact layouts for arrays.[9]

But cache capacity is a size-dependent explanation. The attached fannkuch case uses ten 32-byte values—about 320 bytes. That fits in a typical L1 data cache. A large-array sweep may reveal a footprint penalty, but the small case requires an explanation in instructions, calls, branches, copies, dependencies, or some combination of them.

2.2 Allocation, pointer chasing, and garbage collection#

Heap boxing creates more objects and more references. Removing boxes can reduce allocation traffic and collector work. Leroy’s 1992 work on unboxed objects addresses the core problem: efficient unboxed representations must coexist with polymorphism without losing type safety.[1]

Modern optimizing compilers also remove boxes after the fact. Partial escape analysis and scalar replacement can keep an object’s fields in registers or stack-like compiler temporaries when the object does not need to exist as a material heap allocation along a path.[6]

This is one reason “source language uses objects” does not imply “machine code allocates an object for every value.” The generated code is the evidence.

2.3 Repeated type and tag checks#

Generic code often asks, “What kind of value is this?” If a loop repeats the same answer a million times, a fast implementation tries to prove the answer once and reuse it.

Research systems do this in several ways:

  • TraceMonkey recorded hot traces and specialized them for observed types, reporting large gains on traceable JavaScript workloads.[4]
  • Lazy basic block versioning generates versions of code for the type information available at each point. Chevalier-Boisvert and Feeley report eliminating an average of 71% of type tests in their experiments, with speedups up to 50% on some benchmarks.[5]
  • SELF’s customization work cloned and optimized methods for receiver types, helping turn dynamic dispatch into code the compiler could optimize.[10]

These results are not directly comparable with Hey, but they establish the mechanism: known types are valuable only when the compiler can keep and exploit that knowledge.

2.4 Function calls and optimizer visibility#

An out-of-line helper can cost more than its call and return instructions. It can also hide facts from the optimizer:

  • the array kind may no longer be visible;
  • the bounds may appear unknown;
  • aliasing may look worse than it is;
  • a value may need to be materialized in the runtime ABI’s general representation;
  • loop-invariant checks may remain inside the loop;
  • temporary structures may escape in the compiler’s model.

Inlining can expose those facts. That can help a 32-byte tagged representation as well as an 8-byte unboxed one. Conversely, changing array storage without changing a boundary that immediately reboxes every value may leave much of the benefit unrealized.

2.5 Branches, guards, and deoptimization#

Specialization begins with an assumption such as “this array contains only 64-bit integers.” The runtime needs a guard that checks the assumption. If it fails, the implementation must transition the container, call a generic path, or deoptimize compiled code.

Dynamic deoptimization is not merely an implementation detail. Flückiger and colleagues formalized correctness requirements for speculative optimization with deoptimization, showing why optimized and unoptimized states must correspond precisely.[7]

The performance lesson is simpler: specialization moves work. It removes repeated per-element generality from the common case, then pays for guards and uncommon transitions elsewhere.

✦

The surprising bit
A guard is not a failure of specialization. It is the receipt that lets the optimizer borrow a faster representation safely. The engineering question is whether the receipt is checked once per useful region or repeatedly inside the innermost loop.

3. What fast language implementations actually do#

There is no single winning representation. Successful runtimes layer techniques.

3.1 Specialized collection storage: PyPy storage strategies#

Bolz, Diekmann, and Tratt’s OOPSLA paper describes storage strategies for collections in dynamically typed languages. A collection object delegates storage behavior to a strategy selected for its contents. A list containing only integers can use a compact integer-oriented representation; if an incompatible value arrives, it can switch strategies.[2]

The paper reports an 18% performance improvement on real Python programs and a 6% reduction in peak memory for its evaluated implementation. Those are system-specific results, but the design is directly relevant: specialization is attached to the collection, so a single collection-kind check can replace a tag in every element.

The important design property is not “have many kinds.” It is:

  1. choose a representation whose invariant is cheap to test;
  2. keep the invariant stable through hot code;
  3. provide a correct transition to a general representation;
  4. avoid oscillating between representations.

3.2 V8 element kinds: specialization plus transitions#

V8 documents multiple elements kinds for JavaScript arrays, including packed small integers, packed doubles, general tagged elements, and “holey” variants. Its documented transition lattice is mostly one-way toward more general representations, with a later exception for Array.prototype.fill in some cases.[11]

This buys V8 several opportunities:

  • raw double storage for double arrays;
  • simpler paths for dense packed arrays;
  • code specialized to a known elements kind;
  • predictable widening when an incompatible value is stored.

It also creates costs:

  • checks when compiled code depends on a kind;
  • transitions when an array changes shape;
  • slower paths for holes or polymorphic sites;
  • deoptimization or generic fallback when assumptions fail.

V8 is strong evidence for specialized arrays. It is not evidence that every language needs V8’s number of kinds or exact transition policy.

3.3 LuaJIT: a compact general value, not automatically a typed array#

LuaJIT’s TValue demonstrates another lever: make the general value itself small. Its source represents a value in an aligned 64-bit union and uses NaN-tagging rules to distinguish non-number values.[13]

This can improve:

  • array-slot density relative to a wide tagged union;
  • copying through generic runtime interfaces;
  • register and ABI friendliness;
  • overall table footprint.

But LuaJIT’s ordinary table array part is still described in source as storage for TValue entries. It does not follow that a table containing integers becomes a raw int64_t[] with no type interpretation. Compact tagged values and specialized homogeneous arrays are complementary, not interchangeable.

For Hey, NaN boxing would be a major whole-runtime representation change with portability, pointer-layout, floating-point, debugging, FFI, and garbage-collector implications. It should not be described as the cheap no-guard alternative.

3.4 Julia: preserve concrete bits when the type system permits it#

Julia’s implementation documentation distinguishes values that can be stored inline from values represented by pointers. Arrays of suitable “bits” types can store data inline. Julia also supports compact storage for certain small unions by keeping raw data and a separate tag byte per element.[14]

Julia’s broader compiler strategy uses specialization on concrete argument types. The language’s numerical-performance story therefore combines:

  • concrete, inline data layouts;
  • method specialization;
  • inference that carries type facts into optimized code;
  • generic fallback when types remain abstract.

The lesson is not that a static type declaration is always required. It is that representation facts and compiler facts need to agree.

3.5 Java: primitive arrays, objects, and scalar replacement#

Java makes a visible distinction between int[] and Integer[]. The former stores primitive integers contiguously. The latter stores references, whose target objects have VM-dependent layouts. JOL is the authoritative way to inspect those layouts for a specific OpenJDK configuration.[15]

Java’s optimizing compilers add a second line of defense: escape analysis and scalar replacement can remove some temporary object allocations.[6] Project Valhalla explores value classes and flattened layouts to reduce the semantic and physical gap between values and objects.[16]

So “Java solved this in the type system” is incomplete. It uses language-visible primitive representations, optimizer transformations, and evolving VM support.

3.6 OCaml: the generic-array boundary made explicit#

OCaml historically uses a specialized representation for floating-point arrays. Generic array access may therefore need to distinguish a float array from other arrays. Tokuda, Sumii, and Abe studied specializing those generic accesses after inlining and reported speedups of up to 21% in their evaluation.[3]

This is especially relevant to Hey because it exposes the trade:

  • specialized storage makes the fast path cheaper;
  • polymorphic access needs a representation decision;
  • inlining can reveal enough context to remove that decision from hot code.

The paper supports both halves of the proposed work: storage specialization and optimizer visibility.

4. What the Hey measurements do establish#

Taken as reported, the local measurements establish four useful facts.

4.1 The old store path had an asymptotic problem, and that problem was fixed#

The pre-change timings grew sharply with N; the reported post-change timings remain near 33–34 ns across N = 8, 64, and 512. That is consistent with removing an O(n) clone from this measured shape.

This is a real win even if the remaining constant is still too large.

4.2 The remaining store path is expensive enough to deserve decomposition#

A reported 33 ns per put is many CPU cycles on a modern processor. A loop that performs large numbers of reads and writes can amplify that cost into a large benchmark ratio.

But the timing is an aggregate. Without controlled variants, it cannot say how many nanoseconds belong to:

  • moving a 32-byte value;
  • constructing or copying its tag;
  • a helper call and ABI materialization;
  • bounds checks;
  • reference-count uniqueness checks;
  • aliasing constraints;
  • reference-count updates for overwritten values;
  • fallback or error checks;
  • missed inlining and downstream optimization losses.

4.3 Synchronization and the old clone are not leading explanations for that measured path#

The note’s source reading reports a plain uniqueness load rather than an atomic read-modify-write, and its size sweep no longer shows clone-like growth. Those observations narrow the search.

They do not show that the uniqueness logic is free. A plain load, branches, aliasing effects, and inability to hoist the check may still cost time when repeated.

4.4 The array-heavy benchmark changes the performance regime#

The 1.058× register result suggests that some scalar integer computation can compile efficiently. The 161× result says that conclusion does not carry over to an array-heavy program.

The safe inference is architectural:

◆

Hey can be close to C when values remain in a simple scalar path, while its current generic array path prevents comparable optimization in this benchmark.

That is enough to justify focused work. It is not enough to pick the final representation.

5. What the measurements do not establish#

5.1 They do not separate reads from writes#

fannkuch reads and writes arrays. The 33 ns microbenchmark describes a particular store shape. A read may have a different cost profile, and a read-modify-write sequence may introduce dependencies that neither isolated measurement captures.

5.2 They do not measure the cost of 32 bytes alone#

A useful control is an array of 32-byte plain structs copied by inlined code, with no tags, ownership, or helper calls. Without it, “32-byte copies are the cause” remains a hypothesis.

Modern CPUs can move 32 bytes efficiently when code is inlined and data is hot. The difficulty may be materializing that value through the runtime’s calling convention, not merely the byte count.

5.3 They do not prove a function call is present in optimized machine code#

The note says the shim is non-inlined but also says no LLVM IR was inspected. Link-time optimization, attributes, compiler version, and build mode can change that conclusion. Read the optimized IR and disassembly.

5.4 They do not test cache levels#

N = 512 at 32 bytes is roughly 16 KiB, still small enough for many L1 caches. A meaningful locality sweep should cross L1, L2, last-level cache, and main memory, and should report the actual processor’s cache sizes.

5.5 They do not test representation transitions or boundaries#

A specialized array can look excellent in a homogeneous microbenchmark and regress when values repeatedly cross an API that accepts only HeyValue. The research predicts this risk; only a boundary-heavy benchmark measures it for Hey.

5.6 They do not show causality from benchmark ratios alone#

A ratio between two complete programs is an outcome, not a profile. Hardware counters, sampled profiles, call counts, IR, and incremental controls are needed to connect the outcome to a mechanism.

6. A research-backed decomposition for Hey#

The following sequence minimizes the chance of implementing a sophisticated representation that attacks the wrong part of the 33 ns.

Step 1 — Build a cost ladder#

Use one benchmark body and add exactly one feature at a time:

Variant Element storage Access path Added feature
A 8-byte integer inlined direct load/store baseline
B 32-byte plain struct inlined direct load/store copy width only
C 32-byte tagged union inlined direct load/store tag construction/copy
D same as C inlined bounds check
E same as D inlined uniqueness/ownership check
F same semantics out-of-line helper call and optimizer boundary
G 8-byte specialized storage helper returning/accepting HeyValue reboxing boundary
H 8-byte specialized storage typed internal helper specialization preserved across boundary

Run reads, writes, swaps, and read-modify-write operations separately. Report cycles and instructions per element, not only wall time.

Step 2 — Inspect generated code before redesigning data#

For each variant, capture:

  • optimized LLVM IR;
  • final assembly;
  • whether the helper is inlined;
  • loads/stores and their widths;
  • branches in the inner loop;
  • spills and stack traffic;
  • calls to retain/release or error paths;
  • vectorization remarks.

This determines whether “the compiler sees a simple indexed store” is true.

Step 3 — Sweep sizes that cross real cache boundaries#

Use sizes based on bytes, not only element counts. Include working sets near:

  • half of L1;
  • twice L1;
  • half of L2;
  • twice L2;
  • last-level cache;
  • substantially larger than last-level cache.

Compare 8-byte and 32-byte layouts at equal element counts and equal total bytes. Those two views answer different questions.

Step 4 — Count hardware events#

At minimum, collect:

  • retired instructions;
  • cycles;
  • branches and branch misses;
  • L1 data-cache loads and misses;
  • last-level-cache loads and misses;
  • allocated bytes and reference-count operations, if available;
  • code size for specialized variants.

A 4× footprint hypothesis predicts a size-dependent increase in cache and bandwidth costs. A helper-boundary hypothesis predicts extra instructions, branches, and calls even when the working set is tiny.

Step 5 — Test homogeneous, mixed, and transitioning arrays#

A specialized design needs three classes of benchmark:

  1. arrays that remain integers;
  2. arrays that are general from creation;
  3. arrays that begin specialized and receive one incompatible value.

Measure transition latency, steady-state speed after transition, memory use, and whether an array can thrash between representations. A monotonic widening policy is often attractive because it prevents repeated conversion, but the right policy depends on Hey’s semantics and workloads.[2][11]

Step 6 — Make boundaries visible#

Benchmark a hot loop that:

  • reads an unboxed element;
  • calls a generic runtime function;
  • returns a value;
  • stores it back.

Then compare it with a typed internal path that preserves the primitive representation. This directly tests the “box only at the edge” strategy.

Step 7 — Use statistics appropriate to small timings#

Publish:

  • exact hardware, governor, compiler, flags, and commit;
  • warm-up policy;
  • number of independent process runs;
  • median and a confidence interval or distribution;
  • correctness oracle;
  • raw result data.

For sub-100-ns operations, benchmark enough operations per sample to dominate timer overhead, while preventing the compiler from deleting the work.

7. What to optimize first if the decomposition confirms the hypotheses#

This is an implementation order, not a conclusion that all stages will be needed.

7.1 First: make the common access visible to the optimizer#

Expose array base, index, kind, and bounds in IR or an inlineable primitive. The goal is not merely to save a function call. It is to let the compiler:

  • reuse a known array kind;
  • hoist bounds and uniqueness checks;
  • remove redundant tags;
  • keep values in registers;
  • scalar-replace temporary HeyValue objects;
  • vectorize simple loops where semantics allow.

Research on customization, trace specialization, basic block versioning, escape analysis, and OCaml array access all supports this direction.[3][4][5][6][10]

7.2 Second: add the smallest useful specialized storage set#

If copy width and per-element tag handling remain material, start with a narrow set such as:

  • signed 64-bit integers;
  • 64-bit floating-point numbers;
  • generic HeyValue elements.

Add other kinds only when profiles justify them. Each new kind increases transition, testing, GC, FFI, serialization, and compiler complexity.

7.3 Third: keep primitives unboxed through internal operations#

A specialized array is most valuable when get, arithmetic, comparisons, and put can pass a primitive representation through the hot region. Box at a genuinely generic boundary, not at every runtime helper.

This may require typed runtime entry points or compiler intrinsics rather than changing the entire public runtime ABI at once.

7.4 Fourth: define widening and fallback semantics#

For a store incompatible with the current array kind, choose an explicit policy:

  • widen once to a general array;
  • allocate a new representation under copy-on-write semantics;
  • trap if the language’s type rules prohibit the value;
  • deoptimize compiled code and continue generically.

The policy must preserve aliasing, ownership, exceptions, and observable identity.

7.5 Fifth: optimize allocation and ownership with representation knowledge#

Once primitive elements stay primitive, ownership checks for each element may disappear, while the backing allocation still has ownership. Loop-level alias facts may allow a uniqueness check to be hoisted. Escape analysis may eliminate temporary wrappers.[6]

Do this after measuring. Ownership logic is semantically delicate, and an apparently redundant operation can protect an aliasing case not present in the microbenchmark.

■

A useful stopping rule
Stop adding representation complexity when the next mechanism is no longer a top contributor in profiles of real programs. “As fast as theoretically possible” is not a finish line; “the remaining cost is elsewhere” is.

9. The broader answer: what makes a language fast with respect to values#

A fast implementation does not merely choose a small struct. It keeps useful facts intact from source semantics to machine code.

The recurring pattern across the literature is:

  1. Represent common values compactly. Avoid unnecessary headers, pointers, padding, and per-element tags.
  2. Keep homogeneous data homogeneous. Let one container-level fact describe many elements.
  3. Specialize code as well as data. A compact layout helps memory; specialized code removes repeated interpretation.
  4. Expose hot operations to optimization. Inlining and typed IR let the compiler remove checks and temporary materializations.
  5. Avoid boxes that never need to exist. Escape analysis and scalar replacement can erase temporary objects.
  6. Pay for generality at real boundaries. Do not repeatedly cross boxed/unboxed or generic/specialized interfaces inside the inner loop.
  7. Make failed assumptions safe and uncommon. Guards, widening, fallback, and deoptimization must be correct and cheap in realistic workloads.
  8. Measure the complete path. Representation, compiler, runtime ABI, ownership, GC, and hardware behavior interact.

This is why two languages with the same 8-byte value size can perform differently, and why a 32-byte value is not automatically 4× slower. The representation creates opportunities and constraints; the compiler and runtime determine whether hot code exploits them.

Conclusion#

The attached research found the right area and named several real mechanisms. Its strongest sentence should nevertheless be rewritten.

The reported 161× result does not yet prove that the 32-byte representation is the dominant cause, nor that specialized arrays are the only remedy. It proves that Hey’s current performance story changes dramatically when the program enters its generic array path.

The research literature supports a disciplined response:

  • decompose the path;
  • inspect generated code;
  • make access operations visible to optimization;
  • specialize homogeneous storage when measurements justify it;
  • preserve primitive representations across hot internal boundaries;
  • provide safe widening or deoptimization;
  • measure mixed and boundary-heavy workloads, not only the ideal homogeneous case.

The best near-term question is therefore not “Should Hey copy V8 or LuaJIT?” It is:

◆

Which part of Hey’s current array path consumes the 33 ns, and what is the smallest representation-and-compiler change that removes that cost without moving it to a more common boundary?

That question is answerable. The proposed cost ladder should answer it before the runtime commits to a representation architecture.

Glossary#

ABI (Application Binary Interface)
The low-level rules for passing values between compiled functions: registers, stack layout, alignment, and calling conventions.

Aliasing
The possibility that two references name the same storage. Aliasing can prevent the compiler from moving or removing loads, stores, and ownership checks.

Box / boxing
Placing a primitive value into a more general representation. This may mean a heap object, a tagged word, or a wide tagged struct; the exact meaning must be stated.

Bounds check
A test that an array index is within the valid range.

Cache line
The fixed-size block moved between memory and a CPU cache, commonly 64 bytes on contemporary desktop processors.

Deoptimization (deopt)
Returning from specialized compiled code to a more general execution state when an assumption fails.

Elements kind / storage strategy
A container-level description of how elements are represented, such as packed integers, doubles, or general values.

Escape analysis
Compiler analysis that determines whether an object can be observed outside a region. Non-escaping allocations may be removed.

FFI (Foreign Function Interface)
The boundary between a language runtime and code written under another language or calling convention, often C.

Guard
A runtime check that validates an optimization assumption, such as “this array still contains integers.”

Heap
Memory used for dynamically allocated objects whose lifetime is managed explicitly, by reference counting, or by a garbage collector.

Hoisting
Moving an operation—often a check—out of a loop when its result does not change between iterations.

Inline / inlining
Replacing a function call with the called function’s body, exposing more code to optimization.

JIT (Just-In-Time compiler)
A compiler that generates or improves machine code while a program runs, often using observed types and behavior.

Monomorphic / polymorphic
A monomorphic site sees one relevant type or representation; a polymorphic site sees several.

NaN boxing
Encoding multiple value kinds inside the bit patterns available in a 64-bit floating-point representation, especially NaN payload space.

Pointer chasing
Following one or more memory pointers to reach data, potentially causing dependent cache misses.

Reference counting (RC)
Memory management that tracks how many owners reference an allocation and releases it when the count reaches zero.

Scalar replacement
Replacing an aggregate object with separate compiler values, often registers, so the object need not be allocated or copied as a whole.

Tagged value
A representation containing both a payload and information identifying its kind.

Typed array / primitive array
An array whose element representation is fixed, allowing raw contiguous storage such as 64-bit integers or doubles.

Unboxed value
A primitive stored directly in its machine representation rather than inside a general object. The term is relative to the surrounding system.

Widening / representation transition
Changing a specialized container to a more general representation when it receives a value its current layout cannot store.
