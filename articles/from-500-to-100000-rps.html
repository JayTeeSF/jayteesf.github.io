From 500 to 100,000 Requests per Second

Nine days ago Hey's fastest web service answered a health check at about 490 requests/second. Today a single worker sustains over 123,000 — and the matched-row comparison against Go's net/http is CERTIFIED faster, with 95% confidence, on both macOS and Linux. This is the whole arc, in ten verified numbers, each tagged to the toolchain release that produced it.

TL;DR

  • The verdict: Hey now beats Go net/http, certified. A single Hey worker went from ~490 req/s to 123,000–125,000+ req/s in nine days, and the matched comparison — both servers building the identical 364-byte JSON document, one core each — is certified faster than Go with 95% confidence on macOS (paired ratio 1.0218) and Linux (1.0087). This article's own chart, right below, plots the whole climb; the certification protocol and the full certified table live in Faster Than Go? and are not re-printed here.
  • Two early fixes did most of the first climb. Keep-alive (v0.99.396a) took war-room's /health route from 5,977 to 12,274 req/s, p50 2.6 ms → 79 µs (microseconds). A persistent interpreter sidecar (v0.99.402a) then cut the ~4,479 µs delegation tax on every standard-library call to 56 µs.
  • One bug explains the biggest single jump. The server had been capped at min(open connections, workers) all campaign — never truly concurrent no matter how fast one request got. Fixing it (v0.99.430a) took the matched-row ratio against Go from 24% to 109% in one working day.
  • Disclosed weakness: this campaign has been wrong in public before, twice. A "memory leak fixed" verdict (v0.99.413a) had to be retracted when the real instrument landed at v0.99.410a — the leak was real all along, hidden by a macOS memory counter that can't see compressed pages. And today, a second, unrelated retention floor was found still open in the web dispatch layer (v0.99.443a); the fix has not landed yet.
  • How to falsify any of this: every number below carries its version tag and traces to a dated, timestamped entry in this project's evidence log (docs/PERFORMANCE-FINDINGS.md); rebuild that tag and rerun the same probe to reproduce it.

The arc, in ten numbers

1. ~490 req/s — the interpreted-era taxpre-v0.99.396a

Hey's fastest service answered a 364-byte JSON health check at about 490 requests/second. The cause was structural, not incidental: compiled Hey code calling a pure-Hey standard-library function paid roughly 7 ms per call — each call wrote a temp file and spawned an interpreter subprocess. A handler making one such call capped out near 117 req/s no matter what else it did.

Term: the delegation tax & keep-alive

The delegation tax is that per-call interpreter round-trip — the price of treating a compiled program's own standard library as a foreign process instead of code it can just call. Keep-alive is the HTTP feature that reuses one TCP connection for many requests instead of opening and closing a fresh one every time; Hey's runtime hardcoded connection: close for its first year, so every request paid a full handshake on top of whatever the handler itself cost.

2. Keep-alive lands: 5,977 → 12,274 req/sv0.99.396a

The same release that stopped closing every connection also removed a stretch of needless per-request copying. War-room's /health route went from 5,977 to 12,274 req/s, and its median latency fell from 2.6 ms to 79 µs — a single toolchain landing, no application code touched.

3. The facade table: ~4,400 µs → 3 µs per callv0.99.397a

Rather than waiting on a full fix to the delegation tax, the toolchain first tabled the common calls directly into compiled code. Text.trim fell from 4,355 µs to 3 µs (~1,450×); Crypto.sha256_text fell from 3,402 to the same 3 µs. Calls outside the table stayed exactly where they were — by design, as the marker for the next fix.

4. The sidecar kills the tax: 4,479 → 56 µsv0.99.402a

A persistent interpreter sidecar replaced the spawn-per-call path entirely: the un-tabled canary call fell from 4,479 to 56 µs (~80×). All three production apps set new throughput records the same day, reaching 28,270–30,896 req/s on their health routes.

5. Honest instruments: a leak verdict gets retractedv0.99.410a

This release taught the server to report its own memory and terminate loudly instead of dying silently. It also exposed a mistake: an earlier fix (v0.99.413a) had been credited with a 10.6× cut in per-request memory retention. The real number came from resident_size, a macOS counter that excludes compressed pages — so it can report memory falling while the process's true footprint keeps climbing. Measured on the counter that includes compression (phys_footprint), the leak was real all along, and the "fix" credit was withdrawn in public, not quietly edited away.

6. The worker ladder climbs: 83.3K, then 87.7K at w8v0.99.409a → 417a

More workers used to make every server slower — the "8-worker crater." It died at v0.99.409a, when 8 workers became the new optimum at 83.3K req/s. The ladder kept climbing: a quiet-box rescan at v0.99.417a clocked w8 at 87,732 req/s, with w1 up to 16,617 req/s in the same pass — a curve that had been flat or inverse since the campaign began.

7. Killing the quadratic: 2,280 → 124 clones/requestv0.99.420a–428a

Building a 46-key JSON document cost 2,280 clones per request — a quadratic in key count that an earlier representation change had left completely untouched, because it changed how keys were stored, not how each value got copied during construction. The real fix cut that to 124 clones (18.4×), and throughput on that route rose ~3.4×, paired, 100% success across every rep.

8. The accept model: 24% of Go → 109% in one dayv0.99.430a

The single biggest jump in this whole story came from one bug, not a speedup: Hey's effective concurrency had been pinned near min(offered connections, workers) all campaign, so a 1-worker server could only ever be doing about one thing at a time, no matter how fast that one thing got. Removing the cap took the matched-row ratio against Go from a same-day morning reading of 24.1% to an evening reading of 109.5% — on the same box, the same day.

Term: effective concurrency

Effective concurrency is how many connections a server is actually servicing at one instant, as opposed to how many it merely has open. A server can accept 16 connections and still process them one at a time if nothing lets the other 15 make progress while the first is being handled — which is exactly what capped Hey at roughly one in-flight request per worker for most of this campaign, regardless of how fast any single request had gotten.

9. Certified faster than Go, on two operating systemsv0.99.435a

The pre-registered certification protocol — both servers building the identical JSON document, ≥8 same-minute paired cells, a 95% confidence interval narrow enough to trust — passed on Linux (paired ratio 1.0087, half-width 0.80%) and, independently, on macOS (1.0218, half-width 1.39%, 11 clean pairs). Both clear the ≤1.5% precision gate: faster than Go net/http, with 95% confidence, on both venues. The full protocol, the clock-screening that made the Linux number trustworthy, and the certified table are in Faster Than Go? Certified on Linux and Darwin.

10. Today: ~123K req/s at p50 ~125 µs, one workerv0.99.442a

A quiet-box, pre-registered full-protocol run this week reads a single Hey worker sustaining 122,900–123,500 req/s on the health route, median latency 125 µs — flat across the 1/4/8-worker ladder now, because the accept-model fix removed the reason workers used to matter for concurrency at all.

What's still not settled

The campaign's other headline number moved the same way the leak verdict did: per-request memory retention fell from ~76,420 bytes to ~1,445 bytes (53×), a real and durable fix. But a second, unrelated retention floor was found today, v0.99.443a: a pre-registered gate built to confirm a language-level loop fix found instead that the web server's own dispatch layer never releases a handler's response values after serialization — a separate bug the loop fix cannot reach. It is precisely located, it is not fixed yet, and it is stated here rather than left for the next article to discover. The earlier web-services article carries the fuller retraction history this campaign has already printed at full volume.
