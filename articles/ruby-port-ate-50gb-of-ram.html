A Ruby Port Ate 50 GB of RAM. The Bug Wasn't in My Code.

A 606-line Ruby archiver, ported to Hey, killed a terminal at roughly 50 GB of resident memory. Chasing that number over one night surfaced five failure classes, every one of which failed silently. This is the case file: what we saw, what we believed, what was true, and — the only part that generalizes — what makes each one loud now.

TL;DR

  • ~50 GB of RSS and a dead terminal, from a file-reading loop that could never terminate. The reduced reproducer hit 4.9 GB in ~20 seconds on a ten-file fixture.
  • That loop was my bug. Underneath it sat a compiler bug: the idiomatic list append retained every intermediate copy. 16,000 appends cost 2,741 MB; after the fix (v0.99.406a, 2026-07-25) the same list costs 5.7 MB — 481×. The same defect explained a web server idling at 919 MB.
  • Three more silent classes fell out: a benchmark baseline that was a dead binary timing its own death at 2.3 ms, a compiler that deleted statements, and a path prefix (./) that made scripts do nothing.
  • Disclosed weakness: these are the bugs a young self-hosting language has. The story is the detection method and the ~24-hour fix loop, not an absence of bugs.
  • Falsifiability: the parity gate is bin/check in the source_zip repo (9/9 green, both lanes); the probes are in the war-room repo under bench/probes/; every figure has a dated entry in docs/PERFORMANCE-FINDINGS.md.

How to read these numbers

Apple M-series machine throughout. Memory figures are RSS — the RAM a process occupies right now — sampled immediately after each run, before macOS compresses idle pages and flatters the result. CLI timings are hyperfine over a synthetic git corpus, one output directory per lane, and every timed cell asserts expected output bytes rather than merely an exit code of 0. "Quiet box" means nothing else was competing; anything measured under load is a lower bound.

The crash

The task was mundane: port source-zip, a Ruby tool that walks a git tree and packs it into an archive, to Hey. The port passed its parity gate. Then someone ran it on a real tree and the terminal died — not slowed, died, the way processes go when the OS's jetsam mechanism reclaims memory from whoever is asking for the most of it. Last observed RSS: roughly 50 GB. No exception, no warning, no log line. That is the one thing all five exhibits have in common. A crash is a gift: it tells you where and when. Every bug in this file declined to do that.

Exhibit A: the loop that could not end

SYMPTOM. Memory climbing at gigabytes per second during a file read. No output, no error, no termination. Killed by the OS.

WHAT WE BELIEVED. A pathological input — an enormous file, or a symlink cycle.

WHAT WAS TRUE. Io.read does not return a string. It returns a record, {data, count, eof}. My drain loop came from Ruby muscle memory, where the read returns a string and an empty string means "done". Reduced to its bones: 

let chunk = Io.read(handle, 65536)   # {data, count, eof} — never a string
while chunk != '' {                  # a record is never equal to ''
  set out = out + chunk              # '+' stringifies the record, forever
}

The comparison can never be true, so the loop never exits, and + stringifies the record onto a growing buffer every pass. Two forgiving behaviours — a comparison that returns false instead of objecting to mismatched types, and an operator that stringifies rather than refusing — compose into an unbounded allocator. On a ten-file fixture: 4.9 GB in about 20 seconds before SIGKILL. On a real tree, the 50 GB class.

WHAT MAKES IT LOUD NOW. Honestly, not enough: a committed reproducer and an operator rule ("never compare an Io.read result to a string"). A type error on that comparison is the real fix and it belongs upstream. This is the one exhibit where my code was genuinely at fault, and also the one with the weakest guard today.

Exhibit B: the ghost of every list that ever existed

SYMPTOM. Two, believed unrelated for weeks. The Hey port beat Ruby on small trees and lost badly on big ones, memory growing far faster than the data. And a Hey web server sat at a 919 MB footprint while idle — spotted not by a dashboard but by the maintainer looking at Activity Monitor.

WHAT WE BELIEVED. That the append idiom was merely quadratic in time — annoying but survivable — and, separately, that the server leaked in request handling.

WHAT WAS TRUE. set xs = [...xs, item] was quadratic in peak memory. Every intermediate list stayed alive: add 16,000 items and you hold not one 16,000-item list but the ghost of every list that existed on the way there. Measured: 2,741 MB for 16,000 appends in the spread form, 3,058 MB in the push form. A 30–60,000-file tree reaches the 50 GB class on its own, no infinite loop required. Exhibit A was not the whole crash; it was the fast half.

The server was the same bug in office clothes. A controlled cell on a fresh instance: RSS 2 MB → 577 MB across 99,314 keep-alive requests, dead linear, about 5.8 KB retained per request. The photographed server had served roughly 310,000 requests, and 310,000 × 5.8 KB is 919 MB. The screenshot became the acceptance test.

The correction that matters more than the fix

Our first diagnosis was wrong, and it belongs here at the same size as the result. We said the compiler "forgot to free the old value" on reassignment. Plausible, pointed at the right file, and it would have justified exactly the same patch — which is what made it dangerous. The upstream red team refused it and found the real mechanism: clone-and-abandon. The compiler built the new value, made a full deep copy, stored the copy, and orphaned the original. Not a missed release — an extra allocation, abandoned once per loop pass. A fix built on the wrong mechanism passes the same benchmark and leaves the class alive elsewhere.

WHAT MAKES IT LOUD NOW. v0.99.406a (2026-07-25) fixed the reassignment path: 16,000 appends went 2,741 MB → 5.7 MB (481×) in the spread form and 3,058 MB → 7.2 MB (425×) in the push form, verified twice on independent harnesses. The permanent guard is not the patch but the instrument: an RSS-versus-N flatness probe that fails if memory grows with list size at all. The pre-registered server cell confirmed it too — a fresh instance served 2.05 million further requests and RSS went down (877 → 576 MB), which is what a bounded working set looks like next to a leak.

Mechanism: why "byte-identical emission" was the receipt that mattered

Three acceptance criteria worth stealing. byte-parity of the compiler's own output: for every program that did not have the bug, the emitted code was unchanged byte for byte — proof the change touched only the broken case. ASAN clean: AddressSanitizer watches every memory access during the test run and reports use-after-free, overruns and leaks; it found nothing. (Its sibling TSAN catches data races, and covered the separate dispatch fix that stopped worker threads deep-copying shared route data per request.) And borrow-safety: the fix works by not copying where it used to, so the shortcut had to be proven incapable of leaving a reference pointing at freed memory. The verifier, allowed to argue back, also found a third instance of the defect in actor-state storage that the work order had not listed.

Exhibit C: exit 0, no output

SYMPTOM. A benchmark binary appeared to run 9× slower after an innocuous toolchain update. Alarms, a routing-regression theory, a cache-key theory.

WHAT WE BELIEVED. That the fast measurement was the truth and the slow one was the regression — the default assumption of every performance investigation ever conducted, and load-bearing in a way nobody examines.

WHAT WAS TRUE. The fast baseline was a corpse. The 2.3 ms binary exited 0, printed zero bytes, and died before reaching the first line of user code — every invocation, deterministically. It had been timing its own death. The "slow" binary was the only one doing work, and there was no regression.

The part I own: my parity check had declared that binary's output correct. It did not delete the output file before the run, so the comparison read a file left on disk by the previous lane. "Output matches" was true and completely vacuous. A dead program passed a correctness gate because the gate was reading a ghost.

WHAT MAKES IT LOUD NOW. Two rules, in the lessons file where they survive between sessions. One: rm the output, then run, then assert it was recreated, then compare — baselines included. Two: never trust a clean exit code without evidence of output. A harness that cannot see death is not a harness.

Why the parity gate outranks the test suite

The port's gate compares the Hey program's behaviour against the Ruby original's on identical inputs: member lists, extracted trees, normalized stdout, nine checks, both lanes. It is not a unit-test suite and it tests nothing about the language. It caught more real bugs in one night than any test suite in this project, because it does not have to imagine failure modes in advance — it only needs the two programs to disagree. (Archive bytes are excluded: an access-time field makes even Ruby-versus-Ruby unstable, and a flaky gate is an ignored gate.)

Exhibit D: the compiler that deleted my code

SYMPTOM. Programs that compiled cleanly, ran, exited 0, and did some — sometimes none — of what their source said. Partial output. One tool's entire entry point absent from the binary.

WHAT WE BELIEVED. Five successive explanations: a routing regression, a cache-key problem, my dead baseline, worker wake-storms, CPU oversubscription. Each was falsified by a measurement. Five wrong theories from experienced investigators about one defect should calibrate anyone's confidence in their own first hypothesis.

WHAT WAS TRUE. A silent miscompile. The native emitter misread a bare module-function call in statement position as the block's implicit return value, and dropped that call along with every statement after it — the enclosing block truncated at compile time. Nor was it confined to the compiled lane: the interpreter got the same shapes wrong, not truncated but wrong. A three-function reproducer printed 900 where the correct answer is 4. A wrong answer with a clean exit is the worst outcome in this article. What finally pinned it was Exhibit C's corpse, preserved rather than deleted; the false alarm paid for itself several times over.

WHAT MAKES IT LOUD NOW. The case file's best answer, in two releases on one day. v0.99.408a added the guard: if any statement lowers to zero IR — the compiler's internal instruction form between source and machine code — the build fails loudly. Fleet-wide and structural: it does not fix the bug, it makes the whole class unable to ship quietly again. v0.99.409a landed the fix, blast radius measured across all 1,143 files of the upstream corpus rather than guessed at. A milestone rode along: hey_run, one of the toolchain's own tools, compiled to a working native artifact for the first time — which for a language pursuing self-hosting is the whole point.

Pre-registered predictions

Twice in one night a confident theory died because somebody wrote down the expected result before running the experiment. That is a pre-registered prediction, borrowed from clinical trials for the reason clinical trials use it: a result you interpret after seeing it will agree with you. The worker "wake-storm" theory led the field until its own criterion failed; the real cause, proven from disassembly, was per-request deep-copying of route data. The discipline costs one sentence in a log file before you press enter.

Exhibit E: one character

SYMPTOM. Committed probe scripts, previously alive, producing nothing. Exit 0, zero output, no diagnostic — and a compile-cache entry minted, as if work had been done.

WHAT WE BELIEVED. In escalating order of drama: a stale cache; a regression in how a binding form was spelled; then, after preserving 45 files of build artifacts and finding three distinct compilers keyed to the same version plus orphaned temporaries, a poisoned compiler — a racy publish step leaving a corrupted toolchain minting bad binaries. Those racy twin-mint receipts were real. They were also irrelevant.

WHAT WAS TRUE. hey ./x.hey silently does nothing. hey x.hey works. Same file, same caches, same minute. A leading ./ sent the run down a path that missed an index lookup and returned nil, and the nil was never checked. The spelling "regression" was a confound: every dead cell happened to use the prefix and every live one did not.

The best detail is why this surfaced only now. The nil-returning path is old, hidden for ages behind Exhibit D — the truncation bug had been deleting the very code that would have hit it. Fixing the miscompile un-truncated a latent bug. The old defect was accidentally protective, which happens in real systems and which no amount of clean architecture prevents.

WHAT MAKES IT LOUD NOW. Least of the five, and still open upstream at the time of writing: a bisection that eliminated content, name and all caches before naming the invocation form; an interim rule (never invoke Hey scripts with ./); probes switched to the unprefixed form. Diagnosed within hours, not fixed within hours. The other four are fixed or guard-blocked; this one is bounded by a rule, and rules are the weakest kind of guard.

The record of retractions

In a case file, discarded theories belong in the record at full size. Each was believed by competent people with evidence, and each was killed by a measurement rather than an argument:

  • "The compiler forgot to free the old value." The mechanism was clone-and-abandon. Caught by the upstream red team before the fix landed on the wrong story.
  • "A 9× runtime regression." There was none; the baseline was a dead binary. Every conclusion built on its 2.3 ms number was invalidated in the evidence log by name and timestamp.
  • "Binary output parity green." Vacuous — no delete before the run, so the diff compared a stale file. Mine.
  • "A binding-form spelling regression." Spelling was never the variable; it was confounded with invocation form in every cell.
  • "A poisoned compiler from a racy publish." The artifacts were real and the theory was wrong. It dissolved into one character of path prefix.
  • "Return type triggers the truncation." Two variables changed at once during debugging. Statement position is the trigger.

The guard is the hero

The satisfying story would be the 481×. It is the wrong story — one fix to one defect, and next month there will be a different defect. What survives is the instrument: a flatness gate that fails on any list-shaped retention whatever causes it; a build that refuses to emit a program where a statement lowered to nothing; a harness that asserts output bytes so it can never again time a corpse; a parity gate that compares against a working Ruby program and does not care what the language does internally. Each converts a silent failure into a loud one, the only transformation that compounds.

That is also the honest answer to "why should I believe your throughput numbers?" — the question our companion article on taking three Hey web services from 500 to 60,000 requests per second has to answer, and the reason this case file was published first. That methodology was not designed in the abstract; it was beaten into shape by these five bugs.

The benchmark, since you asked

The same port, re-measured on a quiet box on 2026-07-25 after the memory fix — Hey compiled against the Ruby original, same corpus, same machine, parity gate 9/9 green in both lanes:

500 files153.3 ms66.5 msHey 2.31× faster

Hey wins small, ties in the middle, still loses badly on large trees. The memory fix moved the crossover and halved the deep deficit, but it only addressed retention: building big lists remains quadratic in time, and that fix ("slice B") is queued, not landed. Until it lands, this article's own subject program is the wrong tool for an 8,000-file tree. Not a hedge; a measurement.

The ergonomics tax, stated honestly

Identical functionality: Ruby 606 lines, Hey 861 — 1.42×. Some of that is Hey's explicitness and some is workarounds for the defects in this very article. It is a real cost no benchmark table will show you. Two more lanes where Hey loses today: the compiled build loop is minutes where Go is seconds and Ruby is zero, and the ecosystem is a rounding error beside either.

So would you actually ship this?

The question deserves an answer in print rather than in the comments: yes, with conditions, and the conditions are the interesting part.

You are buying a language whose defects, when it has them, tend to be silent — and a team that fixes or guard-blocks them within about a day of a reproducer landing. Five classes in one night: four fixed or made structurally unshippable within roughly 24 hours, the fifth diagnosed to its mechanism the same morning and bounded by an operator rule while the fix sits upstream. Weigh that against Ruby's and Go's decades of hardening, an enormous advantage Hey cannot buy at any price this year. Against that, a defect filed at 2 a.m. had a guard in the compiler by breakfast, which the decades-old ecosystems do not offer either.

Practically: ship it where you can hold a parity gate against a reference implementation, or where your tests assert real output rather than exit codes. Do not ship it where a wrong-but-quiet answer is expensive and you have no independent check — not because that is likely today, but because Exhibit D happened, and the correct response to Exhibit D is a policy, not a reassurance. If you run Hey servers, restart long-lived processes after heavy load until you are on 406a or later, and re-measure your worker count every release; the optimum moved three times in nine days.

What I would defend is narrower than the language and more useful: the loop. A crash report from a human looking at Activity Monitor, a reduced reproducer, a pre-registered prediction, a red team allowed to contradict the going story, a guard that makes the class unshippable, and a correction printed at the same volume as the original claim. That loop found five silent-failure classes in a night. Speed was the reward. It was never the subject.

Glossary

byte-parity
Comparing outputs byte for byte rather than "looks right" — port versus original, or emitted code before versus after a fix.
RSS
Resident set size: the physical RAM a process occupies right now. The number that matters when the OS decides who dies.
jetsam
The macOS mechanism that reclaims memory by killing processes under pressure. It leaves no stack trace.
quadratic
Cost growing with the square of the input. Tolerable in time at small sizes; fatal in memory at any size.
deep copy
Duplicating a value and everything it references instead of sharing a reference. Safe, and expensive per loop pass or per request.
clone-and-abandon
This file's headline defect: build a value, deep-copy it, store the copy, orphan the original. Looks like a leak; is an unclaimed allocation.
ASAN
AddressSanitizer: an instrumented build that watches every memory access and reports use-after-free, overruns and leaks.
TSAN
ThreadSanitizer: catches data races, the class that works 999 times and corrupts on the thousandth.
silent miscompile
A compiler emitting a program that does not match its source, with no error. It builds, runs, exits 0, and is wrong.
self-hosting
A language whose compiler and tools are written in itself — why one tool compiling to a working binary counts as a milestone.
IR
Intermediate representation: the compiler's internal instruction form between source and machine code. "Zero IR" means nothing was emitted.
pre-registered prediction
Writing down what a measurement should show before taking it, so the result can falsify the theory instead of being fitted to it.
working set
The memory a program genuinely needs in flight, which plateaus under load. Told apart from a leak by whether it comes back down.
sidecar
A long-lived helper process serving requests from the main program instead of spawning one per call. Hey's cut a stdlib call from milliseconds to microseconds.
exit code
The integer a process returns on termination; 0 conventionally means success. Every exhibit that managed to exit at all returned 0.
