How the Hey compiler turns source into native code

You should be able to explain why a program produced a wrong answer, why an immutable update copied memory, or why a build refused. Each question belongs to a particular compiler stage. Follow one small program, then use the same map to inspect Hey’s progress against its original plans.

The design is useful; the consolidation is unfinished

  • Keep a decision with the stage that owns it. Syntax records structure; resolution chooses declarations; high-level intermediate representation (HIR) carries language meaning; mid-level intermediate representation (MIR) plans execution and ownership; LLVM generates native code from that plan.
  • Immutable code can reuse memory. This requires a valid lifetime plan and the necessary runtime checks. A syntax tree alone supplies neither.
  • June, July and August progressively tightened the same goal: one account of the program, carried into code generation. Self-compilation was a milestone along that route.
  • Disclosed weakness: the October candidate still has an older parser-to-HIR path, textual expression consumers, and a public interpreter entry point. The fuller frontend migration is scheduled after the current release.
  • Check the boundary: a required identity or ownership fact withdrawn from an artifact must produce a refusal. Withdrawing an optional optimization must preserve the correct general behavior.

Start with a result you can predict

fn add_fee(total)
  return total + 2
end

program
  let subtotal = 3
  says add_fee(subtotal * 4)
end

The answer is 14. To preserve that answer, the compiler has to know that multiplication happens before the call, that add_fee names this particular function, and that the values reaching the arithmetic are numbers with the appropriate representation.

A wrong answer is easier to investigate when those decisions are separate. An incorrectly grouped expression is a parser problem. A call to the wrong declaration is a resolution problem. Passing a String as an integer is a type or representation problem. None should be repaired by teaching the LLVM emitter to recognize the spelling add_fee.

The tree keeps grouping from becoming somebody else’s guess

A token is a recognized piece of source, such as a name, number or parenthesis. A parser arranges tokens into a tree. An abstract syntax tree, or AST, records the meaningful structure rather than just a flat sequence of characters.

Call
├── callee: add_fee
└── argument: Multiply
    ├── Name: subtotal
    └── Integer: 4

Teaching notation: this shows relationships, not the exact serialized Hey node format.

Now an analysis can visit the multiplication’s two children. It does not need another text scanner to rediscover where the call’s argument ends. Source positions remain attached so a diagnostic can point back to your code.

Hey already has a generated final syntax tree. HeySyntaxTree builds it, generated readers expose its children, and HeyProgramResolution admits source units through it. But the older HeyParser tree is still used by HIR. In that older tree, a binding can contain expr: "2 + 3" rather than two structured operands. The benefit still to earn is consistent consumption of the admitted structure, not inventing another parser. [Current source]

What a source location does—and does not—prove

A location tells you which bytes a node came from. A node identity distinguishes occurrences, even when two expressions have equal text. A binding identity says which declaration a reference selects. These are related facts, but none substitutes for the others. Searching a line for a familiar function name loses that distinction.

The parser’s schema generates node construction and access rules. Code using an exact compiler node must use those rules; it cannot assume that the node behaves like an ordinary user map. That representation mismatch caused the AST-export defect described in the inspection section.

Resolution chooses which function your call means

A resolver joins a name in your code to a particular declaration, accounting for scope, imports and module exposure. In the example, the call must select our add_fee, not another function with the same spelling.

Hey’s program resolver reads a source unit, records its digest, builds its admitted syntax tree, and resolves names across the import graph. It assigns identities that later stages can carry. A digest is a content fingerprint; it helps establish which source the facts describe. [Current source]

This is why “put the special cases in a table” is insufficient. A generated table may describe a function’s calling agreement. It cannot independently decide that every function spelled put has a particular ownership effect. That agreement must belong to the resolved function.

HIR says what the program does before choosing machine details

An intermediate representation, or IR, is a compiler’s representation of a program between source and machine code. High-level IR, or HIR, carries operations, language types and structured control flow. It should consume the parser’s structure and the resolver’s identities.

For the example, HIR needs a numeric multiplication, a call to the selected function, and an output operation. If an analysis cannot prove a useful specialization, correct general behavior must remain available. A missing proof must not become an invented type.

The August 19 architecture report showed why this matters: a String argument was classified as an integer in HIR, and the emitter compiled that incorrect fact. Fixing the emitted instruction alone would leave the false fact upstream. [August report]

Current gap: the resolver’s structured admission and HIR’s older parser consumption have not been fully joined. A clean diagram in the documentation does not close that gap. The later frontend work must carry admitted structure into HIR and remove redundant semantic reconstruction after its consumers have migrated.

Program resolution already owns admitted trees and source identities. HIR still calls the older parser and joins the published resolution facts. Before/after source fingerprints help catch changes, but this is not a fully frozen, single-read frontend throughout lowering.

There is an additional entry-point seam: heyc build first runs the C source-graph validator; the compiled application runner calls the selected compiler driver directly. Consolidation must account for both. Replacing one command’s dispatcher alone cannot establish a single semantic frontend.

MIR makes execution and ownership explicit

Mid-level IR, or MIR, lowers the program into smaller operations. Its intended form names intermediate results and makes execution paths explicit. The current compiler names intermediates in supported lowering paths; some MIR expressions remain nested. MIR owns representation and lifetime planning before LLVM emission.

t0 = multiply subtotal, 4
t1 = call resolved_add_fee, t0
output t1

Teaching notation, not executable Hey MIR. Real MIR also carries types, resolved identities, calling agreements and ownership facts.

A language String and the bits passed to a native function are different levels of description. The compiler must distinguish an owned boxed value from a borrowed string view, keep the view’s owner alive through its last use, and make a checked conversion when a native boundary requires a different representation.

That is the connection to the recent Boolean and String repairs: correct language values were not enough; the pipeline also had to materialize the right representation and preserve the right owner. Cleanup must cover normal returns, branches and failures—not just the successful example.

Reading an ownership plan without becoming a memory-management expert

Own means this reference carries a lifetime obligation. Borrow means a value can be read while another owner keeps it alive. Move transfers an obligation. Duplicate records another live reference; drop retires one. These are compiler facts, not a new surface language you must write.

The current design requires named MIR values and explicit lifetime operations. Hey has working ownership mechanisms and focused tests, but their presence is not proof that every possible update has a complete last-use/reuse analysis. The current compiler brief requires the verifier to check the facts MIR relies on. [Design rules]

In the pinned implementation, the explicit consume-exactly-once checker applies to modules declaring ownership hey-ownership-v1. Other ownership annotations and bounded planners still coexist. Current receiver-rebuild reuse does not establish a general ability to recycle every dropped cell into a same-sized allocation.

Perceus helps immutable programs avoid unnecessary copies

Immutable behavior means an update must preserve any earlier value your program can still observe. It does not require a fresh physical allocation for every update.

The earlier value is still needed

let before = {tea: 3}
let after = put(before, 'tea', 4)
says before.tea
says after.tea

The outputs must remain 3 and 4. Reuse cannot overwrite the version still observable as before.

The old version is no longer used

let prices = {tea: 3}
let updated = put(prices, 'tea', 4)
says updated.tea

This creates an opportunity: if the operation supports reuse, last-use analysis permits consumption, and storage is unique, the implementation may update that storage in place.

Perceus places precise reference-count operations over explicit control flow and combines them with reuse analysis. Koka’s “functional but in-place” explanation shows how functional code can benefit from uniqueness and reuse. These are design references for Hey; they do not confer Koka’s guarantees on Hey.

Explore ownership: does this example read the earlier value again?
Preserve the earlier version. If both versions use the same mutable storage, the update needs a copy or another representation that preserves the old value.

This is an interactive teaching example, not a request for a compiler-design decision. Choose either case to see why preserving an observable earlier value matters. Last use permits a reuse opportunity; it does not guarantee uniqueness, supported layout, or a particular optimization. This example is not a benchmark or a claim about its current lowering.

The division of work matters: syntax preserves the update’s shape; HIR preserves its meaning; MIR establishes order and lifetime; the runtime performs the required uniqueness check. LLVM must not invent ownership because it recognizes an update-looking expression.

Removing copies also does not remove an algorithm’s repeated searches. If each insertion scans everything already inserted, ownership improvements alone do not make the algorithm linear. General indexing and traversal improvements need their own measurements.

The Mojo influence is a method for building passes

The August design borrowed five principles from the infrastructure associated with Mojo and MLIR: parseable IR, ownership and reuse, verification, structural rewriting, and one surface language. The proposal explicitly declined to adopt the MLIR framework itself. It was a plan for Hey’s compiler substrate, not a proposal to turn Hey into Mojo. [August 20–22 designs]

What those principles let you check

The MLIR reference distinguishes textual, in-memory and serialized forms of the same semantic content. Text is not inherently the problem. The problem is losing structured meaning and asking later consumers to reconstruct it independently.

LLVM translates the plan; linking supplies its implementations

Hey emits LLVM IR, a lower-level instruction representation. LLVM optimizes and generates machine code. The linker joins the resulting object code with the runtime and native providers needed by the program.

An application binary interface, or ABI, specifies how compiled code passes arguments and results. A mismatch between a boxed result and a raw Boolean is not a spelling problem. The producing and consuming stages must agree on that interface.

Hey’s emitter should mechanically consume resolved calls, representations and lifetime plans. It must refuse a required agreement that is missing or contradictory. It must not silently move the application to another compiler backend to make a green build.

Logical ownership and call location differ: the current LLVM entry point invokes a checked-String planner implemented inside MIR before emitting instructions. That is MIR-owned normalization at the emission boundary, not permission for the emitter to invent lifetimes.

The native program still needs a runtime

Native means machine code is executing; it does not mean there are no support routines. Hey’s runtime implements values, reference counting, collection operations, actor scheduling and operating-system boundaries. Ordinary compiled library code and runtime primitives have different jobs.

Hey’s standard-library archive packages compiled providers for linking. A native call boundary must carry its calling and ownership agreement. An unavailable library implementation must not be concealed by running the ordinary algorithm through a hidden interpreter service.

Actors add lifetime boundaries: messages and state must preserve isolation, and temporary values must be retired after their last authorized use. A failure inside a contained operation must run its cleanup without incorrectly destroying a healthy sibling. A pass that handles a successful return but omits an error edge has an incomplete ownership plan.

Strings, collections and the later Phase S work

Hey’s String work uses SDS-backed storage: backing allocations hold bytes and lifetime information, while views and boxed values can expose different representations. A temporary borrowed view cannot outlive its backing owner.

Phase S is a later representation project: a compact 16-byte string value over SDS blocks. It is not the AST migration, and neither project should be presented as already shipped in the current candidate. Reducing a value’s size and proving fewer copies are separate improvements; each needs its own behavioral and performance tests.

Collections likewise need both lifetime rules and suitable algorithms. A uniqueness test cannot fix a poor hash distribution, and an index cannot excuse releasing an aliased value too early.

Static linked providers and dynamically loaded native extensions are separate boundaries. The dynamic interface checks descriptors and distinguishes declared blocking calls. Complete borrowed-view, result and effect transport across every package/native boundary remains unfinished; a working archive does not certify that broader rollout.

Self-hosting, running an application and interpreting are distinct

A self-hosted compiler is built using the language it compiles. A bootstrap is the earlier compiler or seed used to construct that compiler. Neither term proves that every ordinary program follows the desired path.

The required public behavior is compile, then run. The command must reuse the existing native runner and HIR → MIR → LLVM stages, preserve arguments, input/output, exit status and failures, and refuse compilation failures without interpreting the application.

Some compiler tools currently depend on interpreted bootstrap calls. Those internal dependencies need explicit bootstrap entry points so changing public --run cannot recursively invoke the compiler tool it is constructing. Independent interpreter comparison controls likewise need explicit entry points so differential tests do not compare the native implementation with itself. These migration dependencies do not justify retaining the interpreter as the public application route. The isolated execution draft is not merged or qualified.

A useful green check must fail when the contract is broken

A verifier checks that an artifact satisfies the invariants its next consumer relies on. A negative control deliberately breaks a required fact and confirms that the check detects it. This guards against tests that pass because they never inspect the important behavior.

Golden snapshots record expected compiler output. Differential tests compare observable behavior across implementations. Roundtrip tests check decoding and reconstruction. None can replace all the others: two consumers can agree on a wrong producer fact, and a stable snapshot can preserve wrong behavior.

The source compiler and its generated products also need separate identities. Cache keys must account for the source, compiler, providers and relevant options. A cache hit proves reuse of a recorded artifact; its reliability depends on the validity of that identity.

Which verification actually runs?

Direct pipeline checks can validate intermediate pass outputs. Ordinary builds disable repeated per-pass checking through an explicit option; the LLVM input boundary still validates MIR. Therefore “verify the IR” is a design requirement with specific enforcement points, not evidence that every pass always runs every verifier.

The text-recovery census limits known residual scanning/recovery sites and detects newly introduced ones. Passing it does not mean the count is zero. The old C consumer also still refuses some golden cases; current classifications distinguish refusal, known oracle defects, behavioral checks and actual IR parity.

Inspect what exists, then improve the stage that owns the problem

You can inspect the generated expression tree today. This uses the lexical admission and syntax parser also used by program resolution:

import 'stdlib:HeyTokens'
import 'stdlib:HeySyntaxTree'

program
  let code = "program\n  let total = 2 + 3\n  says total\nend\n"
  let lexical = read_source_text_into_lexical_admission(code)
  let parsed = HeySyntaxTree.parse_unit_lexical_admission(lexical, 0)
  if !parsed.ok
    fail parsed.error
  end
  says json_canonical_text(parsed.value.tree)
end

This example was exercised with the frozen candidate host. It produces a syntax_tree containing an infix_expr for the addition, with sealed unit/node identities. The 0 selects this unit’s identity. This is syntax inspection of one unit; it does not resolve its imports or prove the resulting program’s semantic correctness.

Inspect the older compatibility tree separately

The older parser tree remains available through HeyParser.parse_text(source_name, code) or HeyParser.parse_file(path). Its exact compiler nodes require explicit conversion at the JSON inspection boundary:

import 'stdlib:HeyParser'
import 'stdlib:HeyCompilerNodes'

program
  let tree = HeyParser.parse_text(
    'example.hey',
    "program\n  let total = 2 + 3\n  says total\nend\n"
  )
  says json_canonical_text(HeyCompilerNodes.to_legacy(tree))
end

This example was also exercised with the frozen candidate host. Its binding contains expr: "2 + 3". This is the older statement tree, not the generated expression tree shown above.

The public hey phase ast command is broken in that frozen candidate. Its consumer assumes ordinary record access on an exact node and rejects valid input. An isolated repair now uses generated readers, validates nested nodes and rehydrates the artifact before HIR. Its tests replay HIR after deleting the original source; independent review and integration remain separate.

That is a useful distinction when improving the compiler. Repairing serialization does not finish structural HIR migration. Nor should modifying an inspectable JSON snapshot let a caller smuggle an unchecked ownership claim into LLVM. Each consuming boundary must validate the facts it accepts.

Three questions to ask before proposing a compiler optimization
  1. Which stage owns this decision? Grouping belongs to syntax; selected declarations to resolution; language types to HIR; representation and lifetime to MIR.
  2. What fact permits the optimization? For example, an explicit resolved effect, last use of a named value and a successful uniqueness check.
  3. What happens when the fact is absent? Missing required semantics must refuse; an unavailable optimization must retain correct general behavior.

Then test the real path. A focused MIR fixture can prove a mechanism; a source program must prove the ordinary producer emits the fact, and platform qualification must prove the resulting application behaves correctly.

Glossary
AST
Abstract syntax tree: the structure recognized in source code.
Resolution
Choosing the particular declaration a name denotes.
HIR
High-level intermediate representation: operations and language meaning before lower-level choices.
MIR
Mid-level intermediate representation: explicit execution steps, representations and lifetime plans.
LLVM
The compiler infrastructure that accepts Hey’s low-level IR and generates optimized machine code.
ABI
Application binary interface: how compiled functions pass values and results.
Ownership
The compiler/runtime accounting for who keeps a value alive and when that obligation ends.
Copy-on-write
Preserving old observable values by copying shared storage when an update requires it; unique storage may allow reuse.
Bootstrap
The seed compiler path used to construct or recover a newer compiler.
Self-hosting
Building a compiler with a compiler for its own implementation language.
Verifier
A checker for the invariants an artifact’s consumer relies on.

This guide compares dated design intent with a pinned implementation. It does not announce a 606a deployment. The frontend transition remains later-release work; a performance improvement needs a measurement of the corresponding production path.
