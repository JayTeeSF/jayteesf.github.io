Four Releases Landed. Three of My Claims Were Wrong.

Today Hey's compiler stopped telling one part of a program that the number 5 and the text "5" are the same thing. A web application can finally send a file. A memory leak in a running service was cut roughly in half by one line. And three things I said earlier in the day turned out to be false, which is the part of this report worth reading closely.

TL;DR

  • Four releases landed and were certified — 491a through 494a, six commits, all three check suites clean. They are committed and through the battery. Nobody has built them yet; a separate page today carries the build receipt.
  • A silent wrong answer is gone. A background worker sent the number 5 and asked whether it equalled the text '5'. The compiled program said yes. It said yes only in the path we actually ship, and it exited reporting success.
  • A real service's memory leak went from failing its budget to passing it — 13,776 KB down to 8,768 KB against a 12,288 KB allowance, over 20,000 requests. The change was one line in their application, not in the compiler. The underlying compiler defect is not fixed.
  • Three claims are retracted below, with the mechanism of each. One fix was built against the wrong copy of the problem and moved the reporter's number by 3%. One "this doesn't apply here" check passed because it tested something the other compiler refuses outright. One branch comparison proved nothing at all.
  • The through-line: every one of those errors was caught by an instrument someone built earlier for a different reason. That, not the four releases, is the day's actual result.

What shipped

Six commits reached the mainline today, carrying four version bumps. In this project's vocabulary they are landed — committed and through the full check battery — and not yet deployed, because the toolchain image that users actually install still has to be built from them. The build instructions went out separately today as 0.99.494a is ready to build.

The compiler said 5 and "5" were equal

Hey has actors: independent units that hold their own state and communicate by sending each other messages. A message can carry any kind of value, so the receiving side often has to ask what it got.

Asking that question gave the wrong answer. When an actor received the number 5 and compared it against the text '5', the comparison came back true. The program then took the branch meant for text, and exited reporting success.

Two details make this worse than an ordinary bug, and both are the reason it is written up first.

It was wrong only in the path we ship. Hey currently has two pieces of code that turn a program into machine instructions, and the whole point of the current work is to retire one of them. The surviving one — the newer, Hey-written one — was the one that got this wrong. Run the same program through the older generator and it answered correctly.

It exited reporting success. There was no crash and no error message. A check that looks only at whether the program succeeded calls this green. The bug was found by a check that compares the two generators' actual output against each other, and it had only just become able to run at all — the four declaration lines that landed earlier the same day are what let it get far enough to notice.

What this class of bug costs. A program that crashes tells you something is wrong. A program that quietly takes the wrong branch and reports success does not. Every one of the three most serious wrong answers this project has recorded has been of the second kind.

An application that could not send a file

A separate application built on Hey found that it could not put raw bytes into a web response. Anything that was not text came out empty — content-length: 0. In practice that means the application could not serve an image, a PDF, or any file it was holding in memory.

They sent a patch. It landed close to verbatim. The more useful thing they sent was a finding: during their own testing they saw a response come back partially truncated rather than empty. That is why the check now added upstream does not merely confirm the response is non-empty — it compares a checksum of the bytes received against the bytes sent. A length check would have passed on a body that was subtly wrong.

A memory leak, and the one line that closed it

A service running on Hey was failing its own memory budget. Its check sends 20,000 requests to a health endpoint and measures how much memory the process is holding at the end. It was ending at 13,776 KB against an allowance of 12,288 KB, and the team had switched the check off in order to deploy.

It now ends at 8,768 KB, comfortably inside the allowance. The change was one line, in their application, not in Hey:

let payload = {ok: true, service: 'elders_prayer_app'}
let response = HeyWebResponses.json(payload)

The value being sent was previously written directly inside the call. Giving it a name is the entire change. That sounds like superstition, and it is not: Hey's compiler reclaims memory by tracking things that have names. A value written inline never gets a name, so the machinery that would have reclaimed it cannot see that it exists. Naming it hands it to machinery that already worked.

This is a workaround, not a repair, and their note says so on its first line. Roughly 461 bytes per request are still leaking, from twelve separate allocations that happen deeper inside the call than any naming at the top can reach. Four more places in their application have the same shape and have not been measured. We asked them to keep the memory check in their deploy path precisely because it is the instrument that will tell them when the real fix arrives.

The real fix is a compiler change and it is not simple. The obvious version of it — reclaim the value automatically at the call — is unsafe, because a function is allowed to hand its argument straight back to you. Reclaiming it then would free something still in use. This project has already measured what that costs: an earlier attempt using the obvious rule broke 40 of 106 test programs, and the damage showed up as a freed value being read back as an entirely different kind of thing. Leaking is the safe direction. Freeing too early produces wrong answers at exit code zero that vary between runs of the identical binary.

Retractions

Three claims made earlier today were wrong. Each is stated here with what caused it, because the correction alone is not the useful part.

1. I fixed a copy of the problem instead of the problem

Claimed: that a memory fix shipped and certified as 493a addressed the leak the service above had reported.

Actually: it moved their number from 763 to 742 bytes per request. About 3%.

Mechanism: they sent a small standalone program demonstrating the leak, and I built the fix against that. Their small program passed the value written inline. Their real application passes a value it received as a parameter. Those are different shapes to a compiler, and I fixed the one in the demonstration. The lesson is narrow and I have written it down: build the reproduction from the reporter's production code path, not from the probe they were kind enough to reduce it to.

2. A check passed because it tested something impossible

Claimed: that the 493a change did not need to be made in both code generators.

Actually: it did. A comparison check that had been green for a long time went red, which cost an extra commit and an extra version bump to put right.

Mechanism: I did check whether the other generator needed the change. I checked using one spelling of the operation — and that generator refuses that spelling outright, so the check could only ever come back "not applicable". The spelling the failing comparison actually used is one the other generator handles perfectly well. The check passed without testing anything. This is the same failure as writing a test that cannot fail, and this project has now produced that shape four separate times.

3. A branch comparison that proved nothing

Claimed: that a second repository was missing commits, on the evidence that git reported one branch was not an ancestor of the other.

Actually: both repositories carried identical content. The commits had been copied across rather than merged, which gives every copy a new identifier. The ancestry test was answering a question about identifiers, not about content.

Mechanism: the wrong instrument. Comparing two repositories after commits have been copied has to be done on file contents. A missing identifier is not a missing change.

A fourth correction is smaller but belongs here: I first said the byte-response fix belonged in the shared web package. It does not. By the time that package receives the value, the caller has already built it, so nothing the package does can help. Reading the application's actual source before writing the note is what caught it — the same discipline that was missing in retraction 1.

The through-line. Every error above was caught by an instrument built earlier, usually for an unrelated reason: a comparison check that had just become able to run, a gate that had been green so long it was easy to assume it would stay green, and the reporter's own memory measurement. Four releases is the visible output of today. The instruments holding is the real one.

The full ladder

This is the complete retirement ladder, R2 through R8, with every rung's position stated whether or not it moved today. Two rungs moved. Five did not, and saying so is the point of listing them.

RungPositionWhere it stands on August 12
R2 — narrow the ordinary build path Active · moved The Hey-written generator's opening section now matches the older one exactly, which is what let a 51-program comparison run for the first time. It reports 42 of 51 programs producing byte-identical output, up from 38. Ordinary programs still fall back to the older generator when they contain a shape the new one refuses.
R3 — delete the native code generation Blocked · newly diagnosed Unmoved, but the reason is now understood rather than guessed. The 90 reference files this rung depends on are pinned at 478a, sixteen releases stale, deliberately. Their checker fails on its very first program for a genuine disagreement between the two generators — a legacy path lowers two file operations through a generic route where both other paths have specialised ones. Regenerating the references would bake that disagreement in and destroy the instrument. The stale pin is a second problem queued behind the first.
R4 — label the comparison-only generator, guard new callers Not closed · unmoved No work today. Requires making the comparison-only role explicit in naming, and preventing ordinary tools from adding new callers of the native backend outside the seed, recovery and reference set.
R5 — verify by compiling rather than interpreting Foundation only · unmoved No work today. Requires running the specification suites as compiled programs, running both ways until they are proven to agree, then making compile-and-run the default.
R6 — retire the native script evaluator Future · unmoved, and newly complicated No work today, but a serious defect in that evaluator was measured this week and is now fully characterised: it destroys a loop's own header text while parsing it, so the second time round the loop it evaluates a truncated condition. One of its three outcomes is a program that prints the wrong number and exits reporting success. It still has no ledger row, and writing one is queued.
R7 — bootstrap fixed point, delete the seed Future · unmoved No work today. Requires publishing seed artifacts and proving the compiler rebuilds itself to byte-identical output, before the native backend and its subcommands can be deleted.
R8 — thin launcher, zero semantic debt Future · unmoved No work today. C remains only as command-line and linker mechanics; requires reconciling every document and ledger and shipping the fully self-hosted release receipts.
Past R8 — the language program itself Moved Of the 56 published language decisions, 19 now hold in both lanes, 2 are blocked on primitives that do not exist yet, and 35 are not yet implemented. The automated suite reports 112 checks: 38 hold, 70 not yet, 4 blocked, 0 regressed. "Not yet" is the normal state here and is not a bug list — most of these decisions describe a language still being built.

Two things about that table are worth saying plainly. R3's blockage is the most consequential item on the board, because it is the rung that would let the older generator actually be deleted, and it cannot move while its own measuring instrument is red. And the past-R8 row is no longer a story about two compilers disagreeing — after this week's precedence repair there are zero decisions where the two lanes give different answers. What remains there is building a language, not reconciling two implementations of one.

Where this leaves things

Four releases in a day is not the headline, and treating it as one would be the easiest available distortion. The releases were small. Two of them exist only because the first attempt at a fix was incomplete and something caught it.

What actually happened today is that a compiler which had been quietly giving one wrong answer stopped, a service that could not meet its memory budget now does, an application that could not serve a file now can — and three confident statements were shown to be false by instruments built for other purposes. The last of those is the one that predicts whether the rest will keep working.

Glossary

Reference for the shorthand used above. Terms marked new were coined since the previous daily.

Actor
An independent unit of a program that owns its own state and talks to other units by sending messages rather than by sharing memory.
Boxed value new
A value carried together with a label saying what kind of thing it is, so code that does not know in advance can ask. Messages between actors carry boxed values.
Tag-typed comparison new
Comparing two boxed values by first checking their kind labels and answering "not equal" immediately if the kinds differ — instead of converting both to text and comparing characters. Today's fix.
Lane
One of the routes a Hey program can take to become a running program. The two that matter here are the newer Hey-written code generator and the older C one. "Shipping lane" means the one users' programs actually take.
Fallback
What happens when the newer generator meets a shape it does not handle: the whole program is quietly handed to the older generator instead.
Gate
An automated check with a recorded expected result. A gate can be registered as expected-green or as expected-red; a known-failing gate is not a surprise, it is a tracked defect.
Tier
A group of gates run together. The fast tier is 110 checks and takes about twelve minutes; the heavy tier is 8 slower checks and takes about ten.
Ratchet
A gate that records a running count of known debt and fails if the count goes up — it permits the number to fall but never to rise.
Ledger
The file listing every gate and its expected result. Suite totals are derived from it independently of any particular run, which is how a run and the ledger can be checked against each other.
Flaky row
A gate registered as sometimes passing and sometimes failing. Neither outcome is treated as news, and it is deliberately never promoted to expected-green.
Binding new
Giving a value a name. In Hey this is also an ownership boundary: the compiler's memory-reclaiming machinery works from names, so a value that never gets one is invisible to it.
Escape proof new
The argument a compiler needs before it may automatically reclaim a value it passed to a function — proof that the function did not keep it or hand it back. Without one, reclaiming is a use-after-free.
Use-after-free
Reading memory that has already been handed back. It usually does not crash. It produces wrong answers that can differ between runs of the identical program, which is why only a sanitiser reliably catches it.
Byte-identical
Two paths producing exactly the same output, byte for byte. This project uses it as the standard of proof in place of "it seemed to work".
Negative control
A test written to confirm the compiler still refuses what it should refuse, or that an unrelated measurement stayed put. Without one, a fix and a fix that silently disables the check look identical.
Cherry-pick new
Copying a commit from one branch to another. The copy gets a new identifier, so comparing branches by identifier after one has happened proves nothing about content.
Landed / Verified / Deployed
Verified: on a branch, with reproduced evidence. Landed: committed and through the check battery. Deployed: available to users through the released route — the only one users feel. Everything on this page is landed. Nothing on it is deployed.
