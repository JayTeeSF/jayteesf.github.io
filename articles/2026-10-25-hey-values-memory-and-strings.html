Hey values, memory and Strings

In Hey a value never changes. "Updating" a map gives you a new map, and the old one is still there. That sounds like a copy every time. Usually it isn't, and this page shows why, what it costs when it is, and what's decided to make it cheaper.

November 13 update: 0.99.606a stores the 16-byte String

In 0.99.606a, released November 13, 2026. This update was written on October 31 for the development line; that work is now released. In 0.99.606a a String is the 16-byte value of section 5 (Phase S, step S1): a boxed String stores it, compiled code passes String locals, parameters and results as that value, and every String operation reads the length through one accessor, never by searching for a zero byte. In 0.99.605a every String was a pointer to an SDS block (section 4). The rest of the String overhaul is 0.99.607a: String literals are still built by a call, a builtin call with a String argument still boxes it, map keys are still C strings, and the fast paths for comparison, borrowed views and single-allocation concatenation are not built yet.

A short String keeps its bytes inside the value. 'hello' needs five bytes of text, so it fits inside the 16-byte String without a separate text allocation. Longer text lives outside the value; the owned form uses a reference-counted backing block. The cutoff counts bytes, not characters. A generic HeyValue still occupies 32 bytes: its separate Bytes payload is larger.

In 0.99.606a the boxed runtime and its owning stores use this layout. Native C tests cover optimized and unoptimized builds, address and undefined-behavior checks, embedded zero bytes, aliases and borrowed views. Counted literal transport and a small program built by the maintained compiler now pass native checks too. The compiler migration and release qualification remain open. When this was written, control flow, Windows indirect calls, typed job names, the full product/archive and Linux qualification still needed work; the release's own known failures are listed on the docs index. The measurements below were not taken on this code.

To check the storage promise, read the String definition and the owning-store test. This update changes storage, not the language's String semantics.

1. Immutable values, and the cost puzzle Works today

Every Hey value (number, String, array, map, record) is immutable. put, push, merge and the spread {...doc, visits: 1} all return a new value:

immutable.hey

program
  let fruit = {apples: 1}
  let more = fruit.put('pears', 2)
  let doc = {name: 'Ada'}
  let next = {...doc, visits: 1}
  says fruit
  says more
  says doc
  says next
end

Run it

$ hey immutable.hey
{"apples":1}
{"apples":1,"pears":2}
{"name":"Ada"}
{"name":"Ada","visits":1}

fruit and doc are untouched. (hey file.hey compiled this to native code and ran it.)

Measured on a Mac M3 Pro with a pre-release 0.99.606a build (October 2026), not the released 0.99.606a.

That's the safe part: no function can change a value you passed it, and an actor can be handed a value (copied or moved) without locks, because nothing can change it. Now the puzzle. This is how everyone counts things in Hey:

set counts = counts.put(word, counts[word] + 1)

If put copied the map each time, counting a million words over a thousand-key map would copy about a billion entries. Does it?

count.hey: count a million words over a 1,000-word vocabulary

import 'stdlib:Cli'
import 'stdlib:Text'
import 'stdlib:Time'

fn count_words(n)
  let counts = {}
  let i = 0
  while i < n
    let word = 'w' + (i % 1000)
    if counts.has?(word)
      set counts = counts.put(word, counts[word] + 1)
    else
      set counts = counts.put(word, 1)
    end
    set i = i + 1
  end
  return counts
end

program
  let n = Text.parse_int(Cli.args()[0])
  let started = Time.now_ns()
  let counts = count_words(n)
  says counts['w7']
  says Time.ns_to_ms(Time.elapsed_ns(started))
end

No. Double the words, double the work: about 1,600 instructions per word at every size, and memory stays flat. The map isn't copied. The binary is 182,328 bytes. Sections 2 and 3 explain why, and here's the version that does copy.

2. Reference counts and copy-on-write Works today

Heap-backed maps, arrays, records and owned long String backing use reference counts. Sharing that backing increments a count. In 0.99.605a every String had a counted backing; in 0.99.606a a short String copies its inline bytes instead. Copy-on-write is on by default;2 it removed the clone-per-put on values with one owner.

The runtime has one uniqueness test, hey_rc_count_is_unique: is the count exactly 1? Every in-place decision passes through it, which is what makes the falsification switches in Performance possible: sabotage that one test and the ownership specs must fail. HEY_RC_COW=0 turns copy-on-write off (every update copies), for comparisons.

3. Perceus: release at last use, update in place

A count of 1 only helps if the old name lets go before the update. In set counts = counts.put(...), the old counts is never read again, so the compiler can hand the map straight to put instead of holding a second reference. That idea, from the Perceus paper (Reinking, Xie, de Moura and Leijen, PLDI 2021, used in Koka and Lean 4), has four parts:

Release at last use. A value is released right after its last use, not at the end of the scope.
Consume a dead value. A call that receives a value nobody uses afterwards takes it over (a move): no extra reference, so a unique map stays unique.
Borrow what you only read. A parameter the function only reads costs no count change on either side.
Reuse. A cell being freed can become the memory for a new value of the same size in the same function.

Where it lives: in MIR, and only there. MIR decides; the LLVM emitter obeys MIR's plan and never guesses; nothing imported may claim ownership. The mechanism is in the compiler article.

Today MIR writes these plans for the shapes it recognizes, which covers the counting loop above, a put inside an if, a helper that takes the map over, and maps of maps. Works today For every other shape the runtime's "refs is 1" test still does the work, so updates stay correct but can copy. Ownership as typed MIR facts, with a verifier on every module, covers every program shape.3 Decided, coming

4. How long Strings keep their bytes: SDS

In 0.99.605a every String was an SDS block, and a String value was a pointer to its first byte. The rest of this section describes 0.99.606a, where only long Strings have one. Long Owned and Static Strings use an SDS block ("simple dynamic string", the layout Redis made famous): a small header, then the bytes, then a NUL byte. An Owned backing is allocated and reference-counted; a Static backing is permanent and is never freed. The 16-byte value in section 5 points to those bytes. Borrowed text may instead point into live foreign or interior storage; short Strings need no backing block.

  • One backing allocation for a long owned String, header and bytes together. Short Strings store bytes inline. Conversion from a separately allocated C buffer copies into canonical String storage.
  • Boxing preserves ownership. Short values copy inline; long owned values can share their block with a count change. A borrowed view is promoted before a generic value stores it.
  • The permanent backing of a long literal is never freed. Its String value still follows the ordinary ownership rules; dropping it does not free that backing. Short literals copy their inline bytes.
  • The NUL byte is only for C. Hey Strings can hold any byte, including zero; the NUL check happens only where a value crosses a declared C boundary.
  • Appending can reuse an exclusively held owned backing block when its capacity permits. Otherwise the runtime obtains suitable storage and preserves aliases. The loop below is a language example; its earlier documentation-test result is not new compiler qualification.

append.hey: build a long String with +

import 'stdlib:Cli'
import 'stdlib:Text'
import 'stdlib:Time'

fn build(n)
  let out = ''
  let i = 0
  while i < n
    set out = out + 'line ' + i + "\n"
    set i = i + 1
  end
  return out
end

program
  let n = Text.parse_int(Cli.args()[0])
  let started = Time.now_ns()
  let text = build(n)
  says len(text)
  says Time.ns_to_ms(Time.elapsed_ns(started))
end

Bytes Works today

Bytes is immutable binary data in a block of the same shape. slice on Bytes is a view: it shares the parent's block (one count increment) instead of copying. There's no mutable buffer: build output by joining immutable pieces.

bytes.hey

import 'stdlib:Bytes'

program
  let data = Bytes.from_text('station;12.5', 'utf-8')
  let name = Bytes.slice(data, 0, 7)
  says len(data)
  says Bytes.decode(name, 'utf-8')
  says Bytes.find_byte(data, 59, 0)
end

Run it

$ hey bytes.hey
12
station
7

12 bytes; the first 7 decode to station; byte 59 (;) is at index 7.

5. How a String is stored: the 16-byte value Partly works

This section describes 0.99.606a, where the 16-byte value is the String carrier; it was not in 0.99.605a. The parts of the overhaul still to come are listed in the November 13 update. Hey has one String carrier: a 16-byte value in the “German string” family of layouts. Its short form contains the bytes; its long form describes separately stored bytes. Owned and Static long Strings use SDS backing. A Borrowed String is a length-delimited view into live external or interior storage. The runtime implementation is tested; using this carrier throughout every compiled program is still being qualified.

The rules, in plain English

  • Always 16 bytes, 8-byte aligned. How a call passes it depends on the target calling convention; it is not always two registers. The first 4 bytes are the length, a 32-bit number, so one String holds at most 4 GiB; asking for a longer one fails fast. Large binary data belongs in Bytes.
  • The length is the only authority. A String can hold any byte, including zero. Nothing ever searches for a terminating NUL to find the end.
  • Short if and only if 12 bytes or fewer. Bytes 4–15 hold the string itself, and the unused bytes are always zero. It doesn't matter how the String was made (a literal, a slice, a concatenation): a 12-byte result is always short and a 13-byte result is always long. Equal short Strings have identical inline bytes. Equal long Strings can point to different backing blocks.
  • Long Strings keep a 4-byte prefix. Bytes 4–7 copy the first 4 bytes of the text, and bytes 8–15 hold the address of the entire text's first byte, with a 2-bit class in bits 54–55. The top byte of the address is left exactly as the system gave it, so the layout is safe with Android and Arm memory tagging and with top-byte-ignore.
  • Four classes. Owned: a reference-counted SDS block, its count changed atomically. Static: permanent SDS backing that is never freed. Its String value still follows ordinary ownership rules; dropping it does not free that backing. Borrowed: a length-delimited view into live foreign storage or another value's bytes that owns nothing. Its backing must remain live for every use. Before an owning collection, field, returned value or message takes a borrowed range, it must be promoted to owned storage; long interior ranges copy unless a proved owner link supports sharing. Short results copy their inline bytes. Concat: reserved for a possible rope form; nothing makes one.
  • The bytes never change. Appending is done in place only when the String is owned, has exactly one holder, and its block has room; otherwise append makes a copy. So a String one thread is reading can never change under it.
  • Comparing. Equality compares the first 8 bytes (length and prefix), then the next 8, and only then the rest of the bytes. Ordering is plain byte order, as C's memcmp gives it.
  • Crossing into C. C wants a NUL-terminated string. An owned or static String already has one at the end of its block; a short String under 12 bytes has zero padding to spare. A 12-byte short String (no spare byte) and a borrowed view get a NUL-terminated scratch copy.

What this layout can avoid

Length and prefix can reject equality. Unequal lengths or unequal cached prefixes prove the Strings differ. Lexicographic ordering compares text from the start: a difference in the cached prefix can decide order, but length alone cannot.
A short carrier needs no backing allocation. A result of 12 bytes or fewer keeps its bytes inside the value. An operation producing it may still allocate temporary builder storage; the carrier itself has no backing count or block to release.
Sharing preserves the bytes. The bytes never change, so any number of threads and actors can read one String at once. Sharing an owned String is one atomic count change; a short one is just copied.
Borrowing needs a live owner. An internal view can point into a parent String. Before an owning collection, field, message or returned value takes that view, it must acquire owned storage. A pointer into short text also becomes invalid when that particular String value moves or dies.

This design isn't new. It comes from the Umbra database at TU Munich and its successor CedarDB,9 and DuckDB, Meta's Velox and Apache Arrow's StringView use the same 16-byte layout.10

An empty String, including the all-zero value, is a valid result. Ordinary compiled failures leave the active work unit instead of using empty text as a failure marker. At a C boundary that requires terminated text, the runtime checks for embedded zero bytes before effects. A pointer into short text must refer to a live, stable String value, or to caller-owned scratch storage. Returning a pointer into a temporary copy would leave the caller with a dangling pointer.

6. Maps and arrays

A map put takes over a dead, unique map Works today

Map.put is declared as consuming its receiver. When MIR proves the map is dead after the call, it moves the map in, and if the count is 1 the runtime writes in place. That works today for the shapes MIR recognizes (section 3); every program shape comes with the typed ownership facts. Decided, coming

The map hash index redesign Proposed

A design that stored each index slot's probe position (so growing never re-hashes) was measured and set aside: on ordinary programs it lost in places (102% more instructions on one shape), and its use of the top 32 bits of the hash clustered keys into the same buckets. SwissTable-style probing, keyed by the 16-byte String value, replaces it.

Arrays and get never copy Decided, coming

Appending to an array you alone hold is in place today. A few array spreads, appends and reads still copy, which makes some array loops quadratic; every one of them is being fixed.

7. Regions and flat records

Reference counting frees values one at a time. A program that builds a tree, reads it and throws it away pays one allocation, one count update per share and one free per node. Two old, well-studied ideas remove that cost without changing what the program means.

The four facts and one solver Decided, coming

Which values go in a region, and which get reused, is decided from four facts, all computed in MIR:

  1. F1 fresh result: everything a function returns is newly built by that call.
  2. F2 escape: a value can be reached after its scope ends (returned, stored, sent, captured).
  3. F3 region scope: the smallest scope (one statement, one loop iteration, one call) that holds every use of a fresh value that doesn't escape. Never a whole loop, so a loop can't pile up garbage.
  4. F4 unique and dead: the value has one owner and isn't read after this operation, so it can be reused in place.

One worklist solver computes F2 and F4 over the same control flow. The rule above all of them: no special cases. No fact mentions a function name, a field name, a file or a benchmark. A first planner that classified calls by their names was reverted, and a version whose rule only fit the binary-trees benchmark was deleted (Performance tells both stories). The runtime half is built and tested, but it is not in a released build yet;6 the MIR facts and their lowering are coming.

Flat records, then regions Decided, coming

The direction is both, in order: first a compact record header and then shaped records that store fields flat then regions for whole lifetimes. They solve different costs: flat records make each record cheaper; regions make freeing many records cheap.

Actor and turn regions Proposed

The same machinery applied to actors: an actor's memory, or the temporaries of one message-handling turn, freed in one step when the actor stops or the turn ends. A development runtime, not in 0.99.606a, has regions and a failure path that pops them, so a failed turn closes its region too; the ownership proofs that would open one per turn aren't built. Actors: Actors and failure.

8. The small-block allocator Decided, coming

This allocator is built and tested; 0.99.605a took these blocks from malloc, and the allocator's commits are in the 0.99.606a tree, which this page has not measured. Record headers, array headers and small long-String backing blocks are 32 bytes to 1 KiB, and ordinary programs make and free them at a furious rate. With the allocator they come from Hey's own pages instead of malloc,7 after mimalloc's free-list sharding (Leijen, Zorn and de Moura, 2019). With the 16-byte String, released in 0.99.606a, short Strings keep their bytes inline and have no separate backing allocation; producing one can still use temporary builder storage.

Three allocator changes finished it: medium blocks up to 1 KiB, the String lifecycle inlined (a 320-byte String's allocate-and-release went from 750 to 298 instructions), remote frees settled before a thread abandons a page, and pages that dead threads leave empty retired.8 It runs under AddressSanitizer too, with every free block poisoned, so the sanitizer tests the allocator that ships.

Size-specialized allocation Proposed

The next step goes further: allocate each value from the exact size class known at compile time, skipping the size lookup. The size classes above are its foundation.

9. Watching memory yourself Works today

Three builtins: reset_allocations() zeroes the counters, allocations() returns them as a map, and memory_rss_bytes() gives the process's resident memory.

watch.hey: count in place, then count while keeping the old map

fn count_alone(n)
  let counts = {}
  let i = 0
  while i < n
    let word = 'w' + (i % 100)
    if counts.has?(word)
      set counts = counts.put(word, counts[word] + 1)
    else
      set counts = counts.put(word, 1)
    end
    set i = i + 1
  end
  return counts
end

fn count_keeping_old(n)
  let counts = {}
  let sizes = 0
  let i = 0
  while i < n
    let word = 'w' + (i % 100)
    let before = counts
    if counts.has?(word)
      set counts = counts.put(word, counts[word] + 1)
    else
      set counts = counts.put(word, 1)
    end
    set sizes = sizes + len(before)
    set i = i + 1
  end
  return counts
end

fn report(label)
  let stats = allocations()
  says label + ': in place ' + stats.json_write_inplace + ', copied ' + stats.json_write_cow_copy
end

program
  let ignored = reset_allocations()
  let a = count_alone(1000)
  let first = report('alone')
  let reset = reset_allocations()
  let b = count_keeping_old(1000)
  let second = report('keeping the old map')
  says memory_rss_bytes() > 0
end
