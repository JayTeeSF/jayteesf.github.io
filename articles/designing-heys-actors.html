Designing Hey's Actors

Hey runs millions of actors on a small, fixed set of operating-system threads. That takes five engineering decisions: a fixed worker pool, receive only at the top of an actor's loop, a lock-free mailbox, a work-stealing scheduler, and messages shared by reference instead of copied. This article explains each one: the evidence behind it, what it buys, and what it costs. Reference 3: actors and failure says which parts run today.

TL;DR

  • An idle Hey actor costs about 150 bytes. That is below Pony's roughly 240-byte actor, far below Go's 2,048-byte starting goroutine stack and BEAM's roughly 2,616-byte process, and about two and a half times Tokio's 64-byte task.
  • The main way to make an actor cheap is to remove its private call stack. Tokio and Pony are small because a task or actor does not pause in the middle of an arbitrary function call. Go and BEAM allow that kind of suspension, so each worker needs a real stack.
  • Hey allows receive only at the top of the actor loop. Hey briefly planned to support receives in the middle of a handler by compiling handlers into state machines, but rejected that plan after estimating its compiler complexity and memory cost.
  • The mailbox and scheduler were redesigned together. The mailbox is a lock-free many-sender, one-reader queue. The scheduler gives each worker its own queue and lets idle workers steal, instead of routing messages through one global lock.
  • Messages are to be shared by reference instead of copied. The design uses reference counting so that sending a value can usually update a counter rather than duplicate the entire value.
  • The open risks have answers. Blocking calls belong in a Job or a worker pool, not an actor; a fast sender is slowed down and a mailbox past its ceiling fails fast; and reference counting stays fast only while the compiler keeps a cheap single-owner path.

This article is a follow-up

Reference 3 explains the actor model as you write it. This article gives short reminders where needed, but does not repeat full explanations of actors, stacks, mailboxes, work stealing, or immutability.

1. Turning the research into an implementation plan

Hey is an immutable-first language that wants to run millions of actors on roughly one worker thread per CPU core. Actors communicate by sending messages, and the runtime schedules each actor when it has work to do. The difficult part is making each idle actor small enough, and each send cheap enough, that the system still works at very large scale.

The research compared the memory and scheduling models used by BEAM, Pony, Go, and Tokio, and converted that comparison into an engineering program. Each part of the program names an existing runtime, paper, or algorithm to use as a model. Each part also has a measurable completion condition, such as actor size, lock contention, mailbox behavior, or benchmark results.

Five decisions define the design: remove per-actor stacks, restrict where actors may receive messages, replace the mailbox queue, replace the scheduler's global bottleneck, and share immutable values by reference. These choices are related, but they solve different problems and carry different risks.

2. Why the stack matters more than mutability

The most important result from the earlier research is that the smallest runtimes do not give every task or actor its own call stack. Tokio tasks use about 64 bytes, and Pony actors use about 240 bytes. In both systems, a handler does not pause halfway through an arbitrary call chain and later resume from that exact point. — Tokio Tutorial: Spawning, Pony Runtime FAQ

Go goroutines and BEAM processes do allow that kind of suspension. A Go goroutine begins with a 2,048-byte growable stack. A BEAM process uses about 2,616 bytes at its minimum size and includes space for a stack, heap, mailbox, and garbage-collection state. Go uses mutable data and BEAM uses immutable data, yet both pay for a stack. That is why the comparison concludes that the strongest predictor of per-worker memory is whether the worker can suspend anywhere, not whether its values are mutable. — golang/go, runtime/stack.go, Processes — Erlang System Documentation

This finding determines the rest of Hey's design. Hey cannot reach the memory range of Pony or Tokio while preserving one operating-system thread and one C stack per actor. The runtime must schedule actors as short pieces of work on a fixed pool of worker threads.

3. Decision one: actors run on a fixed worker pool

A thread-per-actor runtime calls pthread_create, which gives every actor an operating-system thread and a C stack. Hey started that way. The replacement is a pooled design: a fixed number of workers repeatedly take runnable actors from queues and execute one step of each actor.

A message handler must run to completion before the actor waits for another message. It may call ordinary functions while it runs, using the current worker thread's stack, but the runtime does not preserve that stack after the handler yields. The actor therefore needs state and a mailbox, but not its own suspended call stack.

Benefit

This is the only design in the comparison that has already reached the intended memory range. Pony and Tokio both demonstrate that millions of lightweight workers are practical when the runtime does not reserve a stack for each one.

Cost and risk

A handler cannot block a scheduler worker while waiting for file I/O, DNS, or a long native call. Hey therefore needs a separate, bounded pool for blocking work, similar to Tokio's blocking pool, Go's ability to hand blocked work to another thread, and BEAM's dirty schedulers. Without that bridge, a few blocking handlers could stop all actor progress.

BEAM provides a useful sizing reference: its dirty I/O pool defaults to ten threads regardless of CPU count. Hey does not have to copy that exact number, but it does need the same separation between ordinary actor work and calls that may block for an unpredictable amount of time. — Erlang NIF documentation

4. Decision two: receive stays at the top of the actor loop

This was the most debated decision. The research considered three models:

  • Allow receive only at the top of the actor loop, as Pony effectively does.
  • Use LLVM coroutine support to suspend a handler in the middle of its body.
  • Compile each handler into an explicit state machine, similar to async implementations in Rust, Kotlin, C#, and Swift.

The initial research recommendation was the first option. It is the smallest design and already has a production example at the target actor size. It also avoids a new compiler intermediate representation and a new transformation pass. The language documentation shows the canonical shape: an actor is a loop that receives a message at its top — see the simplest example in the Hey docs. — Reference 3: actors and failure

In code, the whole model fits in ten lines. This is a complete Hey program: an actor whose loop top is a single receive, and a program block that spawns it, sends it one message, and stops it. 

actor echo
  receive msg
  says msg
end

program
  let p = spawn echo
  send p, 'ping'
  stop p
end
$ hey echo.hey
ping

Running it prints ping. The receive msg line is the actor's entire waiting behavior: the actor sleeps until a message arrives, binds it to msg, runs the body below it, and returns to the top of the loop for the next message. There is no way to pause partway down the body — everything this article says about “top-only receive” is a statement about where that one keyword may appear. A gentler walk through the same model is in Guide 1.

For a while Hey chose the more expressive state-machine design instead. Under that plan, every mid-handler receive would become a suspension point. The compiler would record a state number, preserve only local variables that remain in use after the suspension, and resume the handler at the correct state when another message arrived. Rust's coroutine lowering was one of the main references for this approach. — rustc coroutine transform

That design was not merely discussed in the abstract. It had a proposed memory limit for each suspended frame because compiler-generated async state machines can become unexpectedly large. One documented Rust case produced a state machine of roughly 400 kilobytes, and embedded developers have sometimes removed async code to reduce binary size. — Tyler Mandry, “How Rust optimizes async/await”, Rust Project Goals 2026

The decision was reversed. Hey will keep receive at the top of the actor loop. The state-machine research remains available in case the language revisits the trade later, but it is no longer part of the current actor-runtime plan.

Benefit

Each actor remains a small, fixed record. The runtime does not need to allocate and preserve a different suspended frame for every point at which a handler might wait.

Cost and risk

Programs cannot stop halfway through a handler and wait for one particular reply. They must store explicit state and continue in a later handler invocation. This is less convenient than Erlang's receive-anywhere model and may require real program restructuring.

Erlang demonstrates the other side of the trade. Selective receive lets a process scan past messages that do not currently match, but the scan may be O(N) in the number of queued messages. Supporting that model also requires the process to preserve its suspended execution state. — Erlang process documentation

5. Decision three: replace the mailbox lock with a Vyukov MPSC queue

An actor mailbox has many senders but only one reader: many actors may enqueue messages, while only the receiving actor removes them. That makes it a multi-producer, single-consumer queue, usually abbreviated MPSC.

Hey's first mailbox was a linked list protected by a mutex. Its replacement is an intrusive, lock-free MPSC queue based on Dmitry Vyukov's design. “Intrusive” means the message object contains its own queue link; the runtime does not allocate a second wrapper object merely to put the message in the queue. Hey's message structure already contained a value and a next pointer, so it already has the required shape.

On the producer side, the algorithm performs one atomic exchange followed by a normal pointer store. It does not use a retry loop. The single consumer usually removes messages without an atomic operation. Rust's futures-rs channel and the published cordyceps::MpscQueue use versions of the same design. — Vyukov's queue description, “Ode to a Vyukov Queue”, cordyceps documentation

Benefit

Sending no longer requires a mailbox mutex, and the queue adds no separate allocation for a node. The message and the queue node are the same object.

Cost and risk

If a producer is paused after publishing the new tail but before linking the previous node, the consumer can briefly encounter a gap and must wait for the producer to finish. This is a known property of the algorithm. The queue also does not solve overload by itself: an unbounded mailbox can still consume all available memory.

Hey's overload answer: the scheduler slows a sender that outruns its receiver, as Pony's "muting" does, and a mailbox past a hard ceiling makes the receiving actor fail fast. Nothing is dropped. Should Hey's Mailboxes Have Limits? compares the options. — Pony muting change

6. Decision four: finish the work-stealing scheduler

Hey's first scheduler had the outline of work stealing: worker-local queues, a shared injection queue for work submitted from elsewhere, and counters for stealing, spinning, parking and waking. It got little of the benefit, because nearly every send from outside a worker thread went through one global mutex. Adding cores made it slower.

The replacement follows techniques Tokio and Go already use:

  • Each worker receives a fixed 256-slot lock-free ring buffer for ordinary runnable actors.
  • An idle worker steals roughly half of another worker's queue in one operation instead of synchronizing once per task.
  • Each worker has a one-task LIFO slot for the actor most recently awakened by the current task, improving cache locality for short request-and-response chains.
  • At most about half of the workers search for work at the same time, reducing unnecessary wakeups when the system is mostly idle.

Tokio documents the 256-slot queue, packed head state, steal-half operation, and LIFO slot. Go's per-processor runnext slot serves a similar purpose and includes an anti-starvation rule so that ordinary queued work is not ignored indefinitely. — Tokio queue source, Tokio scheduler article, Go scheduler source

Benefit

Most scheduling operations become local to one worker. Idle cores can take work from busy cores without forcing every send through a shared lock. Existing runtime counters can show whether the global bottleneck has actually disappeared.

Cost and risk

Scheduler wakeup code is easy to get subtly wrong. Too many wakeups create a thundering herd; a lost wakeup can leave work queued while a worker remains asleep. Tokio has documented why its unpark path uses an unconditional swap rather than a compare-and-swap: the apparently narrower operation can lose a real notification when it races with a spurious wakeup.

These failures often do not crash the program. They appear as unexplained stalls, poor scaling, or excessive CPU usage, which makes them difficult to reproduce. Reusing established algorithms and validating them with stress tests is therefore part of the design, not an optional cleanup. — Tokio parking source

7. Decision five: share immutable messages by reference

Immutability does not make an actor stack smaller, but it can make message passing much cheaper. If a value cannot change after it is created, two actors may safely point to the same value. A send can therefore share a pointer instead of recursively copying the value and everything it contains.

Hey plans to manage those shared values with reference counting. Each heap value records how many live references point to it. Sharing increments the count; releasing a reference decrements it; the value is reclaimed when the count reaches zero.

The compiler strategy is based on Perceus, the precise reference-counting system used by Koka. Perceus tracks ownership through the program and inserts increment, decrement, and reuse operations at compile time. In its red-black-tree benchmark, purely functional Koka code came within roughly 10% of a hand-mutated C++ std::map, while a comparable Java program used about ten times as much memory for similar speed. — Perceus, PLDI 2021

Pony's ORCA collector provides the contrasting example. Pony also shares objects between actors without copying them, but its objects may be mutable. It therefore needs reference capabilities to prove which actor may read or modify an object, plus a collector designed around those guarantees. The ORCA paper explicitly notes that immutable actor data makes this problem much simpler. Hey intends to use that simpler case: shared values cannot be modified, so the runtime does not need Pony's capability system merely to prevent concurrent writes. — ORCA, OOPSLA 2017

Why copying costs so much

Today every send makes one copy of the message. Within one thread a copy of an object or list is just a count increase, but a value handed to another thread is copied deeply, so the cost of a send grows with the size of the message: a list of four thousand elements is walked and copied element by element. Reference sharing flattens that: sending a large, already-built immutable value should cost about as much as updating its ownership record, whatever its size.

Benefit

Large values can be sent between actors without being duplicated. This removes the deep copy described above.

Cost and risk

Reference counts add space and update work to heap values. The design only wins if the compiler avoids unnecessary atomic updates, recognizes single-owner values, and reuses storage when safe. Perceus measured slowdowns of 5% to 59% when key static optimizations were removed; disabling reuse analysis and drop specialization more than doubled the time of its red-black-tree benchmark.

Reference counting also requires a clear rule for cycles. Immutability prevents write races, but it does not by itself make cyclic object graphs impossible. If Hey's value model guarantees that shared heap values are acyclic, ordinary reference counting is sufficient. If cycles can be created, the runtime will need a separate strategy for them. The implementation and language rules should state that assumption explicitly rather than treating it as an automatic consequence of immutability.

8. Where the five decisions stand

Together, the five decisions combine ideas that existing runtimes usually provide separately. BEAM provides immutable data and very scalable processes, but its receive-anywhere semantics require a stack and its isolated heaps usually require messages to be copied. Pony removes the actor stack and supports zero-copy messages, but it needs a capability type system and the ORCA collector because the shared data may be mutable. Hey combines stackless actors with reference-shared immutable values.

DecisionStatus
1. Actors run on a fixed worker poolWorks today. Supervised actors still take their own threads; moving them onto the pool is decided, coming.
2. receive stays at the top of the actor loopWorks today
3. A lock-free many-sender mailboxWorks today. Backpressure and the fail-fast ceiling are decided, coming.
4. A work-stealing schedulerWorks today
5. Messages shared by referenceDecided, coming. Today each send copies the message.

Blocking calls are kept off the worker pool by a rule rather than a second pool inside the actor runtime: a blocking native call is allowed only in a Job, a worker or the program block. Reference 4 says when to use each, with measured costs. How Hey Runs a Million Actors shows the scheduler in pictures and how one actor's failure stays its own.

Glossary

actor
An independently scheduled unit with private state that communicates by sending messages.
run to completion
A handler finishes its current step before the actor waits for another message.
receive
The operation that removes a message from an actor's mailbox for processing.
selective receive
A receive operation that scans past messages that do not match and leaves them queued for later.
mailbox
The queue of messages sent to an actor but not yet processed.
MPSC queue
A queue with multiple producers and one consumer, matching an actor mailbox's send/read pattern.
intrusive queue
A queue in which the queued object contains its own link field, avoiding a wrapper allocation.
backpressure
A policy that slows, suspends, rejects, or redirects sends when a receiver cannot keep up.
work stealing
A scheduling method in which an idle worker takes runnable tasks from another worker's queue.
LIFO slot
A one-item fast path that runs the most recently awakened task before returning to the normal queue.
reference counting
Memory management that tracks how many live references point to a value and frees it at zero.
single-owner fast path
An optimized path for a value known to have one owner, avoiding unnecessary shared-reference updates.
dirty scheduler / blocking pool
A separate thread pool for work that may block or run too long for the normal actor workers.
