Hey · overseer review · 22 October 2026

Make the compiler fast where the work actually is.

The Kokoa → semantic HIR → ownership/ABI MIR → real LLVM design is sound. The fastest implementation will come from making each boundary one-way, typed, identity-preserving, cacheable, and cheap—not from replacing the architecture with a fashionable framework.

Verdict

The compiler team’s current release plan is the right immediate queue for correctness: finish H12, remove project-facing Stage0/product-lane ambiguity, repair lower-MIR memory explosions, and prove ordinary consumers. It is not yet a complete performance strategy. Add a compiler-performance track with phase budgets and measurements before making broad claims about speed.

Current architecture

tokens → final syntax → name resolution → semantic HIR → ABI MIR → LLVM

The repository has generated schemas for syntax, structural HIR, real HIR, resolution, MIR, physical representations, ownership/ABI, and runtime callables. That is a strong authority model. The risk is that generated readers, native mirrors, compatibility paths, shadow frontends, and serialized artifacts can still repeat work or diverge unless receipts prove their identity and cost.

The dated project evidence already identifies the dangerous class: self-host frontend work was once dominated by boxed value/JSON cloning and showed approximately quadratic scaling; a short doubling sweep hid the next failure until the sweep was extended. This is why the next optimization must begin with phase curves and allocation/copy counts.

The branch the compiler team is actually changing

What the current differential corpus is telling us

test/fixtures/differential/known.tsv has 21 recorded rows at this tip. The rows include range-inside-expression parsing, shadowed-let binding identity, actor for receive lowering, bytes literal arguments, multiline block headers, text-parse split fields, and file-object reads. These are not merely “known reds”: they cluster around the exact boundary where semantic identity is reconstructed from strings.

Review of the compiler team’s plan

Keep and strengthen

  • Keep H12’s syntax/semantic boundary and add a “desugared once” receipt.
  • Keep staged lower-MIR memory repairs; require peak RSS, allocation/copy counts, emitted-IR size, and exact lane identity.
  • Keep fail-closed Stage0/product closure; every ordinary compile should report lane, selected binary digest, fallback count, source graph, schema, target, and runtime identity.
  • Keep byte-scan repairs only after focused semantic checks and one authorized product rebuild confirms the source win survives native compilation.
  • Keep the ordinary-consumer sweep after product-lane proof.

Add before calling the compiler fast

  1. Instrument tokenizer, syntax, resolution, HIR, MIR, validation, LLVM, link, cache, and subprocess time, with tokens/nodes/facts/ops, RSS, allocations, clone calls, serialized bytes, and worker count.
  2. Run three-size and five-size doublings; retain the long sweep that exposed the hidden bad doubling.
  3. Count compiler-owned Text.split, source scans, JSON encode/decode, record clones, and concatenations. Replace the largest internal transport family with typed records or IDs.
  4. Design red/green cache identity only after source/schema/compiler/target/runtime/pipeline fingerprints are complete.
  5. Require native and Hey-owned emitters to agree on ownership guards, releases, ABI calls, and IR fingerprints; source parity alone is insufficient.
  6. Parallelize only after identity and transport are stable; measure RSS and determinism with wall time.

Refutation

  • “Move to MLIR and it will be faster.” Unproven. MLIR supports extensible multi-level IR, but conversion and allocation overhead can rise. Existing generated HIR/MIR can realize the same separation at lower migration risk.
  • “Use e-graphs by default.” Unproven. Equality saturation is powerful but can grow rapidly; use it only for measured, bounded domains.
  • “LLVM is the main lever.” Not supported by current evidence; clone/materialization/scanner and lane-selection costs come first.
  • “More parallelism is always faster.” False when memory pressure and allocator contention dominate.
  • “Generated schemas solve performance.” They prevent drift, but generated code can still box, copy, and serialize repeatedly.
  • “A warm cache proves incrementality.” False. Test leaf edits, public signature edits, imported-module edits, and schema/compiler/target changes.

Every algorithmic seam, not just one map

The compiler team’s proposed declaration map is valid: the five find(globals_text, declaration) sites turn declaration membership into a repeated scan of an ever-growing buffer. But it is one member of a larger family.

Confirmed repeated scans

globals_text declaration checks; register-definition searches in hey_llvm_str_result_fresh_cstr?; ownership searches in emitted regions; numeric runtime-ABI lookup in giant delimiter strings; runtime prelude symbol scans; MIR summary membership in fenced strings.

Repeated materialization

HIR → serialized MIR → string-carrier pass → range pass → ownership/reuse/move passes → LLVM text. Each pass reparses or rebuilds text that should be typed records.

Keep the good parts

HIR assignment postings and binary search, local-type dependency worklists, iterative parsing, and least-fixed-point ownership reasoning are sound algorithms. Replace their storage, not their semantics.

Rule for every optimization: write down the asymptotic model, add a source-level work counter, prove semantic/byte equivalence, then measure cold, warm, and one-file-edit builds with peak RSS. A map replacement is a good local fix; it is not the compiler-wide answer until neighboring scans and materializations are accounted for.

Ordered overseer plan

P0 — release truth

Finish H12 and product-lane gates. Do not publish speed claims until receipts identify compiler, lane, fallback count, and artifact digests.

P1 — compiler cost map

Add phase profiles to the ordinary self-host route and run cold, warm, and one-file-edit doubling corpora with RSS and allocation/copy counters.

P2 — repeated materialization

Replace the largest internal string/JSON/boxed transport family with typed compact records or IDs, retaining serialization adapters for published artifacts.

P3 — ownership-aware storage

Use region-based, ID-indexed HIR/MIR storage where lifetimes permit; add liveness/escape/copy elimination before LLVM; verify semantics, lifetime safety, RSS, and IR.

P4 — incrementality and parallelism

Add query-level red/green caching and parallel module/backend execution with exact invalidation, deterministic outputs, RSS, and 1/2/N-worker receipts.

P5 — backend tuning

Only now tune LLVM pipelines, ThinLTO, PGO, target features, and code generation, reporting compile cost and runtime quality together.

Handoff

Continue the compiler team’s current plan, but add a performance track. The first requested artifact is a phase-cost receipt for the H12 product compiler on a small source-size doubling corpus. Until that exists, algorithm choices are hypotheses. Do not begin an MLIR migration, e-graph optimizer, or broad parallel rewrite. The likely fastest path preserves Kokoa → semantic HIR → ownership/ABI MIR → LLVM while eliminating copies, text scans, stale/fallback lanes, and unnecessary whole-graph recomputation.
