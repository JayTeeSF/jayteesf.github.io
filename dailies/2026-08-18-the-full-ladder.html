Printed True, Arrived Zero

An optimization shipped, passed every fast test, and broke the compiler's own build. The theory that explained it was wrong. The real bug was fifteen lines: a value that prints the word true arrived at a function as zero.

TL;DR

  • An array-read optimization that broke the compiler's own build is back, and the build is green. It shipped on at version 526a, passed the fast test tier, and broke the full self-host build. It was honestly withdrawn at 527a, root-caused, and restored at 528a with the whole build passing. All of this is landed — committed and through the battery. Nothing is deployed; this checkout has no remote.
  • The real cause was a yes/no flag stored as text. A value that prints as the word true was read back across a function call as 0: false, and that single wrong "false" waved a wrong optimization through. The fix is two guards; a flag stays a flag.
  • The payoff the win was blocking now stands: arrays tie C. Re-measured on this machine, streaming shapes finish at 1.09x C on sum and 1.08x on search over 100 million elements, and every one of eight workloads finishes. Full table below.
  • Correction, at claim volume: the "scale-only miscompilation" theory was wrong. It was stated across two handoffs. A memory sanitizer ran the failing build clean and the bug survived with every optimization off — so it was neither scale nor memory, but a plain logic bug.
  • Disclosed weakness: strings are still slow, and not every wall fell. The string workload lands about 4.5x C and a hair behind Ruby — a constant factor, no longer a program that never finishes. The parse-deadline wall from the last daily still stands, and a separate check was already red before this work and stays red.
  • Falsifiability: a string-array call site now emits row:Value, a real integer-array site still emits row:Int, and a new regression gate asserts the flag round-trips to true. Revert either guard and the gate goes red.

The win that passed the tests and broke the build

Start with the good idea. When a Hey program writes arr[i] inside a function, the compiler normally reads that element cautiously, as a value of unknown type. But if it can prove — by inspecting every call site — that every caller hands in an array of plain machine integers, it can read the element as a raw integer and skip the caution. That is the cross-function read optimization at the center of this story, and real speed on the array workloads below.

It shipped on at 526a. It passed the fast test tier — the quick battery that runs on every change — and it passed the compiler-level checks. Then it broke the full self-host build.

Those are two different gates, and the difference is the whole lesson. The self-host build is the compiler compiling its own roughly four-thousand-line pipeline — a copy of its own internals — after which that fresh compiler must work. On this run it did not: it mis-typed one boxed string-array element as an integer, a length call on it could not be lowered, and the build fell onto a legacy path and died with exit code 70. Deploy-ready is that whole build passing, and 526a is the proof it differs from the fast tier — green on the quick battery, unable to build itself.

The honest retreat

The fix at 527a was not to paper over the broken build. It withdrew the optimization while keeping every piece of the machinery that decides when to apply it: a single named switch flipped to off, so the call-site proof still runs but never fires the fast read. The self-host build went green again, and the version bump documents the lost speed win rather than hiding it.

The theory that was wrong

The prevailing diagnosis, in two separate handoff notes, was a scale-only miscompilation: every helper was correct tested on its own, and wrong only when assembled into the full module — a resource counter, a string-constant table, a temporary, or a label that collided once the program got big enough.

That guess has a shape: the bug lives at scale, or in memory. So the test attacked that shape. A memory sanitizer was compiled into the seed compiler and into the pipeline it emits, so the failing configuration ran under a watcher for out-of-bounds reads, use-after-free, and overflow. It ran completely clean — and the bug still reproduced with every optimization off.

That pair falsifies both theories at once: clean under the sanitizer means it is not memory corruption, and still wrong with the optimizer disabled means it is not an optimizer bug. What is left is the boring kind — valid machine code that computes the wrong answer.

Retraction — the "scale-only miscompilation" theory

Two handoffs stated that the failure was a miscompilation that only manifests at whole-module scale, likely a counter or table collision. That was wrong. The bug has a fifteen-line reproduction with no scale involved, survives with every optimization off, and leaves a memory sanitizer completely silent. It was never about scale and never about memory. It wore a "scale-only" disguise for two releases only because of the narrow path that triggered it, described next.

The reveal: a value that prints true, and arrives zero

The root cause is small enough to hold in your head. In the call-site proof, a yes/no flag arrives as a parameter and is copied into a local — the ordinary let cur = seen. The part of the compiler that decides how to display a value classified cur as a string, on purpose: a yes/no flag prints as the text true or false, so for display, treating it as a string is convenient.

Convenient for display, wrong for everything else. That classification bled into storage: when the function packed its answer into a small record — {seen: cur, ok: ok} — the flag was stored down the string path, as the literal text "true". A caller then read that field back and passed it where a yes/no flag was expected. To turn text into a flag, the runtime parses it as a number; "true" is not a number, so the parse returned 0 — which, read as a flag, is false.

So a value that every human eye would read as true travelled across a function boundary and came out as false. That is the whole bug, and the rule worth carrying is this: a value that prints as "true" can arrive as 0 whenever it is stored as the text of its name and later read back as a number. The print is a rendering; the storage is the truth; here the rendering had quietly become the storage.

It only ever surfaced through the array optimization because that was the one place threading a record of two yes/no flags back out and reusing those fields as flag arguments. The proof deciding whether a call site is "all integer arrays" returns a {seen, ok} record; one field came back a wrong false, so the proof waved through a call site it should have refused — one passing an array of strings — and the fast integer read was emitted over string data. Every isolated copy of the helper looked correct because nothing else ran a two-flag record through that round trip: the trigger was rare, not large, which is exactly why it looked like scale.

The fix is two guards. Where the compiler decides to treat a local as a string, it now also asks whether that local is really a yes/no flag — and if it is, leaves it a flag. Two lines, in the two places that made the classification, matching an idiom already used elsewhere in the same file. Then the optimization's switch was flipped back on. The full self-host build is green with the win firing.

The two string rows are the honest part. Before the append mechanism landed, those workloads did not finish at ten million elements — appending to a boxed string copied the whole backing store each time, a quadratic build already ~38 seconds at a hundred thousand. That wall fell at 526a, where an amortized append replaced it; a size sweep here confirms it linear:

What remains is a constant factor, not a wall: each element is still a heap-allocated string, so Hey lands about 4.5x C and a hair behind Ruby, 2.09 seconds against 1.46. A "slower," never again a "does not finish" — the disclosed weakness, stated plainly.

Back to the walls

The last daily left one wall open: two functions that call each other still overflowed at depth 500, because the interpreter's tail-call fix handled a function calling itself, not a pair. That wall is down at 516a, where the interpreter learned to eliminate mutual tail calls too. The fourth wall still stands, though — parsing past about 2,850 functions still trips a thirty-second deadline, and nothing here made parsing faster.

A separate check was already red, and stays red. One native-C smoke build fails at the exact starting commit for this work, confirmed by stashing every change and re-running — so it predates the fix and was not caused by it. It looks like the same native-C miscompile family as a known number-parsing bug on that path. It is disclosed here rather than quietly carried.

What this page owes you

Two things to walk away with. First, a value that prints as true can arrive as 0 wherever it is stored as the text of its name and read back as a number — the rendering replaces the truth. Second, "passes the fast tests" is not "deploy-ready": only the gate that makes the compiler build itself caught this. The optimization is back on with that build green — landed, not deployed, because this checkout still has no remote.

Evidence used for this report

  • All numbers measured on this machine — Apple M3 Pro, macOS darwin arm64 — at version 0.99.528a on the local trunk, which has no remote. Work is landed, not deployed.
  • The benchmark table is best-of-three wall-clock, output verified byte-identical to a C reference before timing. Sizes: sum, search and histogram at 100 million elements; transform and append at 50 million; the string rows at 10 million; fannkuch at 11. The box was under light load, so absolute Hey seconds run a few percent high; the ratios and the finish/no-finish verdict are the claim.
  • The string linearity sweep — 100k at 0.02s, 1M at 0.21s, 10M at 2.07s — is a size sweep on this machine at 528a. The pre-fix non-finish and the ~38s-at-100k quadratic are from the earlier campaign build.
  • The sanitizer result — a clean run of the failing self-host configuration with the bug still reproducing at the lowest optimization setting — was produced by building the seed compiler and the emitted pipeline's link with a memory/undefined-behaviour sanitizer, in one session.
  • The regression sweep found every one of 150 self-host-path failures failing identically at the 527a starting commit (pre-existing, mostly unsupported features on that path); specs 000–308 pass; the code-generation goldens are green.
  • The mutual-recursion close is at 0.99.516a from the commit history; the parse-deadline wall and the pre-existing red native-C smoke build are re-checked as still standing at this commit.
  • Version numbers appear short in prose: 528a means v0.99.528a. Hovering a short version shows the full string.

Glossary

Reference for the shorthand used above. Terms marked new were coined or first used here since the previous daily.

Cross-function read optimization new
Reading an array element as a raw machine integer instead of a cautious unknown value, allowed only when the compiler has proven — by inspecting every call site — that every caller passes an integer array. The proof is what a wrong "false" corrupted.
Self-host build new
The compiler compiling its own roughly four-thousand-line pipeline, including a copy of its own internals, after which the freshly built compiler must work. The largest, hardest program the compiler ever meets. Passing it is the bar for deploy-ready; passing the quick fast tier is not.
Fast test tier
The quick battery that runs on every change — small programs that compile and run. It was green on all three releases in this story, which is exactly why it did not catch the broken self-host build.
Yes/no flag, boolean
A value that is only ever true or false. It prints as the words true or false, which is what let it be mistaken for a string. Stored correctly it is a single bit; stored as its printed text it stops behaving like a flag.
Coercion new
Turning a value of one kind into another — here, text into a flag, done by parsing the text as a number. The text true is not a number, so the parse returned 0, and 0 read as a flag is false.
Memory sanitizer new
An instrumented build that watches a running program for memory errors — reading past a buffer, using freed memory, overflow — and names the exact site. It ran the failing build completely clean, which is how "memory corruption" was ruled out.
Optimization level, "-O0"
How hard the compiler works to make code fast. The lowest setting does almost nothing clever. The bug still appeared there, which ruled out an optimizer defect and left a plain logic bug.
Amortized new
A cost that averages out cheap over many operations, even when one occasional operation is expensive. The new string append only rarely grows its backing store, so a run of appends is linear overall — the change that made the string wall fall.
Constant factor new
A fixed multiple of overhead that does not grow with the size of the input. The remaining string slowness is a constant factor — about 4.5x C — not a wall: it makes the program slower, never unable to finish.
Linear, quadratic
How work grows with size. Linear means ten times the data costs about ten times the time. Quadratic means ten times the data costs about a hundred times the time — the shape the old string append had, and the reason it never finished.
Landed / Verified / Deployed
Verified: on a branch, with reproduced evidence. Landed: committed and through the check battery. Deployed: on the mainline and felt by users. Everything on this page is landed; nothing is deployed, because this checkout has no configured remote.
