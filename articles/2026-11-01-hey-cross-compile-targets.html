Hey Cross-Compile Targets

You write Hey on your Mac. You type one command. You get a binary for every one of these devices: Macs, iPhones, Apple TVs, Linux servers, Windows PCs and Android phones. No C compiler on your machine. This page shows what each of those binaries needs, what works today, what it costs, and the order to build it in.

Why we want this at all: Hey Without a C Compiler. This page is the extended target table that page promised.

Short version

  • 14 targets across 7 platform families. Three of them come first, in v608: macOS arm64, Linux x86-64 and Linux arm64. All three can be tested from the Mac.
  • Every target uses lld and stubs Hey writes itself. No Apple, Microsoft or Android NDK files are copied into Hey.
  • Effort is an estimate. The first three targets take 2.5–5 weeks of the 5–9 week step 1. Everything else adds about 15–30 weeks. All figures are engineer-weeks for one person who knows the code.
  • One hard limit: Apple only takes App Store uploads built with Xcode 26. Development and simulator builds can skip Xcode; store builds can't.
  • Eight decisions are waiting for you at the bottom of the page, each with a recommendation.

One build, every device

Here's the end state. One hey build --target on your Mac, and a binary falls out for each box on the right. The colour says when it's planned.

WebAssembly isn't on the picture. The Hey repo doesn't target it today; question 7 asks whether it should.

What's in the box for each target

A binary isn't just your compiled code. Each one needs four more things: a linker that knows the file format, small stubs that tell the linker which system functions exist (names only, no code), a way to sign and package it, and a way to run a test. Here's what each family gets.

Notice that Android uses the same linker as Linux. Once step 1 proves ld.lld on Linux, Android's new work is mostly its stubs. That's why it comes before Windows, which needs a third file format.

The order, and roughly how long

The rule behind the order: prove the cheap, testable-from-the-Mac targets first, then reuse what they proved. Each bar's solid part is the low estimate; the dashed part runs to the high estimate.

Why Android before Windows? Android is ELF and ld.lld, both proven by step 1. Its new parts are the generated bionic stubs and crt objects. It's the cheapest way to take an existing, shipping product target off the C compiler.

Why iOS last? It has the most Apple-specific work (framework stubs, bundles, signing), and store builds still need Xcode anyway.

Licensing: what we know and what's open

The pattern is the same everywhere: where a vendor's files can't be shipped, Hey writes its own list of names and generates the stub. A list of function names copies nobody's file.

Known

Android NDK: not redistributable

The SDK License Agreement (3.4) forbids redistributing "the SDK or any part of the SDK". So Hey generates bionic stubs instead of shipping the NDK sysroot.

Open, likely fine

Bionic stubs and crt objects from AOSP

Bionic is BSD/Apache source. Generating stubs from its .map.txt lists and building crt objects needs a NOTICE audit first.

Known

Windows import libraries Hey generates

A .def list of DLL export names, written by Hey, copies no third-party file. Preferred.

Open

mingw-w64 import libraries and CRT

Mostly permissive, but the runtime notice lists Wine-derived headers under LGPL-2.1+ and an unresolved Cephes note. Avoided by generating our own.

Known

MSVC runtime and Windows SDK .lib files

Don't ship them. Hey's own mainCRTStartup removes the need.

Known

musl: MIT

Fine to build from source and ship inside Hey.

Known

glibc link files: LGPL-2.1

Stubs and libc_nonshared.a can be redistributed with a notice.

Known for our route

Apple SDK stubs: we generate our own

Hey writes its own .tbd files from its own import list, framework stubs too. Copying Apple's .tbd files stays open: no Apple or Zig statement on it was found.

Known constraint

App Store needs Xcode 26

Since 28 April 2026, App Store Connect accepts only apps built with Xcode 26 or later against the iOS 26 / tvOS 26 SDKs. A store build without Xcode won't be accepted even if it links. Simulator and development builds are unaffected.

Known

LLVM and lld inside Hey

Apache-2.0 with LLVM Exceptions. The archive carries the notice; the programs Hey builds carry nothing.

How hey_ios and hey_android plug in

The packages have their own native glue (Objective-C on Apple, C on Android). The rule is simple: that glue is built once per target on the release builders and shipped prebuilt in the package release, just like the runtime. Your machine only links.

  • hey_android / hey_android_tv. Today hey-android-app.sh compiles your program, the runtime, the glue and the crypto profile with NDK clang, then links with clang -shared. Under the plan, only the APK tools stay: aapt2, zipalign, apksigner, bundletool, and a JDK for the Java renderer's d8. None of those is a C compiler. The hasCode=false NativeActivity lane needs no JDK at all.
  • hey_ios / hey_ios_tv / hey_carplay. The UIKit and TV hosts are Objective-C, built today with -fobjc-arc -fmodules. They ship as static archives per Apple target. actool (asset catalogs) and store signing stay Xcode tools until question 1 is answered.
  • hey_mobile / hey_tv. Plain Hey code, no target-specific parts. Nothing changes.

What you can do after reading this

  • Say yes or no to the v608 starting set: macOS arm64, Linux x86-64 glibc, Linux arm64 glibc.
  • Answer the eight questions below. Most are a one-word yes or no; each has a recommendation you can take as is.
  • Rule on the TLS approach for static Linux, which unblocks step 2 (from the why page).
  • Ask for the AOSP NOTICE audit, the one licensing item standing between Android and "no C compiler".

Eight decisions for you

Q1

Must iOS and tvOS store builds be Xcode-free?

Apple rejects uploads not built with Xcode 26 and the 26 SDKs.

Recommend: no. "No C compiler" covers simulator and development builds. Store builds keep Xcode for the final link check, actool and signing.

Q2

May package native glue stay C, if it's prebuilt per target at release?

It's the same bridge the runtime uses.

Recommend: yes, for now. Port it to Hey along with the runtime in step 3.

Q3

Windows C runtime: kernel32/ws2_32 only, or also ucrtbase?

The main runtime still calls some C functions on Windows.

Recommend: Hey's own mainCRTStartup plus generated import libs for ucrtbase (ships with Windows 10+), shrinking to kernel32-only with step 3.

Q4

Android: generate bionic stubs from AOSP, or make users install the NDK?

The NDK can't be shipped inside Hey.

Recommend: generate from AOSP, after the NOTICE audit.

Q5

Keep darwin-x64 and the x86_64 Apple simulators?

Intel Macs are still around; Apple Silicon Macs run arm64 simulators.

Recommend: keep darwin-x64 (cheap); drop the x86_64 iOS/tvOS simulators unless a user needs them.

Q6

Android minimum API: 21 or 35?

Hey's structural objects use 21; hey_android pins 35.

Recommend: one value, 35, matching the shipped package. 21 only if a user needs older devices.

Q7

Add WebAssembly (wasm32-wasi, browser) to the table?

The repo doesn't target it today.

Recommend: not before step 3. The C runtime's threads, signals and dlopen don't map to WASI, and wasm-ld is a fourth format. Revisit when the runtime is Hey.

Q8

Are Windows arm64 and Android armeabi-v7a in scope?

One is a growing platform; the other is 32-bit.

Recommend: Windows arm64 yes (after x86_64); drop armeabi-v7a (Play's 64-bit rule makes it optional).

Where the runtime stands per platform
  • hey_runtime.c branches on __APPLE__, __linux__ and _WIN32. tvOS/watchOS get a capability closure: no process spawn, no sigaltstack, no TLS, no AEAD, no password KDF.
  • Windows has its own boundary files that compile without Windows SDK headers; WinHTTP is loaded at run time.
  • There is no musl or __GLIBC__ branch. A musl port must decide on malloc_usable_size, pthread_getattr_np and dlopen (OpenSSL, native modules).
  • The Android stdlib archive task was accepted on 2026-09-29: the Android libhey_stdlib.a builds and links into a signed APK and no longer goes through the Apple crypto path. It still compiles with NDK clang.
  • Product archives exist only for linux-x64 and darwin-arm64, and refuse host/target mismatches.
