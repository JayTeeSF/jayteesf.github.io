Hey language · status reference · 25 August 2026

The parts of the Hey language, current at 553a+

This is the language-focused ladder: what a Hey programmer can write, what the standard runtime/library exposes, and which pieces are merely ruled versus actually implemented. The version string is still 0.99.553a; this status includes later commits in the supplied source snapshot.

Implemented = code + current public contractActive = exists but compiler/product closure is incompleteDecided = semantics ruled, implementation may lag
What changed since the previous language page: the explicit import/export module system is no longer accurately described as “largely not built,” and Distributed Hey is now a substantial programmer-facing capability. The core immutability/type/function syntax did not undergo a comparable redesign.

1 · Values and types

Immutable values
implemented

Integers, floats, strings, booleans, nil, bytes, arrays and JSON-shaped maps are values. Ordinary local bindings are immutable; updates create new values or use compiler-proven ownership reuse under the hood without changing source semantics.

Type-conveying casts
implemented core

Conversions such as to_i, to_f and to_s are ordinary callable operations used by the compiler's type reasoning. A current native-reference floating-point wrong-code bug is a backend correctness defect, not a change to the language's float semantics.

2 · Functions and callable values

Named functions
implemented

fn name(...) ... end remains the basic abstraction. Functions can be referenced and passed as values.

First-class callable value
implemented

Hey has a real callable value and uses it in collection operations and compiler/runtime callbacks. Hey still deliberately has no lexical closures; a callable does not implicitly capture surrounding mutable state.

Callable machine ABI
settled internally

The current compiler work settled an implementation fact that matters for status but not syntax: a callable already travels as an ordinary boxed pointer at the machine ABI. The remaining cross-unit problem is linking and program-wide dispatch, not inventing a new callable representation.

3 · Modules, imports and exports

This is the biggest language-surface status change since the previous version of this page. Modules are lexical and static; the resolver chooses imported names, receiver forms and operator bindings before HIR.

module BankAccount fn deposit(account, amount) return {...account, balance: account.balance + amount} end private fn valid_amount?(amount) return amount >= 0 end exposes deposit forms: [:qualified, :unqualified, :dotted] end import './bank_account.hey' as Accounts import './bank_account.hey' exposing: [deposit] import './bank_account.hey' exposing: [deposit] forms: [:dotted] import 'stdlib:Json' exposing: [generate as stringify] import 'stdlib:BuiltIns' conceals: [length]
exposes
implemented

A module declares its complete public surface and the forms each binding supports. Non-exposed bindings are unavailable outside the module; private helpers remain usable inside it.

Bare import
implemented

A bare import adds the qualified namespace only. It does not inject every public name into the caller.

as, exposing:, forms:
implemented

as renames the module namespace. exposing: adopts selected public bindings into the lexical scope. forms: can narrow the import to dotted, unqualified, qualified or infix use as declared by the module.

Selector aliases + conceals:
implemented

old as new aliases one selected binding. conceals: removes adopted/default names without removing qualified access. Builtins participate in the same outer lexical surface instead of living in an unshadowable magical namespace.

Explicit re-export
implemented

Imports never expand a module's public surface by accident. Facades deliberately import and re-export, including exposes * over eligible public declarations/re-exports.

Static namespace vs runtime module value
implemented distinction

The namespace created by source imports is compile-time. Separately, Module.load(...) can return a runtime value, but it cannot create identifiers, receiver forms or operator bindings in already-compiled lexical scope.

4 · Receiver calls and operators

Receiver syntax
implemented

When an imported exposure permits dotted form, account.deposit(25) resolves statically to deposit(account, 25). This is lexical sugar, not runtime method lookup.

Operators
implemented contract

Operator spelling/precedence is parser-owned and closed. A module may expose an allowed operator form for a named function, but it cannot invent arbitrary punctuation or change parse structure.

5 · Actors, state and IO ownership

Actor-owned mutable state
implemented

Actors are the intentional state boundary: one mailbox, private persistent state, serial message handling. Ordinary values remain immutable.

Raw IO crossing actors
explicit move v1

A socket/listener/TLS handle is not ordinary shareable data. Sending one across an actor boundary without authorization is rejected. Io.into_actor(handle) explicitly transfers a sole-owned top-level handle, poisons the source reference after success, and rejects aliases. Nested handles inside arrays/records are not auto-moved in v1.

6 · Distributed Hey

Distributed Hey is new enough that it deserves its own language-status section. It is mostly a standard-library/runtime capability rather than new syntax, but it changes what ordinary Hey programs can do.

Codec + DistTransport implemented

Codec defines a versioned compact tagged binary wire format with limits. DistTransport adds framed, bounded streams, handshake/capability/app/build compatibility, heartbeat, counters/backpressure and TCP/TLS establishment seams.

DistNode + DistRemote implemented

Nodes have stable identity plus process incarnation. RemotePid is an immutable value, not a remote pointer. Remote.send is at-most-once “accepted for transport”; Remote.call is ordinary correlated request/reply over messages.

Remote monitors + stale incarnation implemented

The substrate can surface node-down events, and a RemotePid from an old node incarnation is rejected rather than silently delivering into a restarted process.

Two-machine TLS verified milestone

The 551a milestone exercised real macOS↔Linux nodes over the network, including TLS call and stale-incarnation legs. This is runtime evidence, not a claim that the current default compiler can yet build every distributed example without fallback.

Current product boundary: examples 01_ping_pong through 06_wordcount exist, but P2 compiler closure still has to make the entire stack default-native Hey. Registry/Jobs/cluster membership work is intentionally held until that gate is green.

7 · Collections and immutable performance

Arrays/maps as immutable values
implemented

Source semantics stay immutable even where the compiler/runtime proves sole ownership and reuses backing storage internally.

Copy-on-write / ownership reuse
implementation technique

Map and string performance work changes allocation strategy, not the meaning of assignments. Track C2's self-append optimization is one example: the compiler may keep a persistent owned string backing only when the source shape proves it safe.

8 · Specs

Built-in spec blocks
implemented base

Specs are part of the language toolchain rather than an external test runner. The broader immutable fixture/property/actor-expectation design remains a separate design track; do not read that future surface as fully shipped merely because core specs exist.

9 · The compiler programmers actually get

One public frontend
implemented direction

The public compiler path is Hey-owned. Source and imports resolve into semantic HIR, ABI MIR and direct LLVM. Native C frontend/emitter machinery is internal bootstrap/recovery/validation rather than a second public language definition.

Resolve-once semantics
landed

ProgramResolution is produced before HIR and carries exact call identities/signatures so later phases consume resolver truth rather than reopening source meaning.

Cross-unit direct linking
active P2

The provider closure is now computable, but the final P2-LINK steps still have to compile/link the providers, lower resolved pure-Hey calls directly to hey_fn_Module__fn, and build one program-wide callable dispatcher. Until that closes, compiler status is not equivalent to language-surface status.

10 · What has not changed

  • Hey is still immutable by default.
  • Hey still has actors, not shared mutable objects and locks.
  • Hey still has no lexical closures.
  • Distributed Hey does not introduce distributed shared memory or bytecode shipping.
  • The new module system remains compile-time lexical resolution, not Ruby-style runtime monkey patching.
  • Compiler ownership/reuse optimizations are not permission for source-level mutable locals.
