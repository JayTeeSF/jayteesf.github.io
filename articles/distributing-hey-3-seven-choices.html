Seven choices for distributed Hey

Distributing Hey is not one decision but seven — and each one is a tradeoff the precedents have already mapped, so the maintainer's job is to pick a coordinate on every axis, not to hunt for a single right answer.

Explored · not shipped This is a design note, not a feature announcement. Distributed Hey has not been built or shipped. Everything below argues open decisions, grounded in a research brief — no distribution code exists in the tree today, and nothing here is settled.

Part 3 of a three-part series, "Distributing Hey." Part 1, "No VM needed," answered the yes/no question: distribution is runtime services on the actor runtime Hey already has, not a bytecode VM. Part 2, "The wire format is the easy part," covered Hey's acyclic data model and what maps over. This part lays the seven design decisions on the table and argues each as a choice with a cost — not a verdict.

The short version

  • There is no single "distributed Hey." There are seven independent decisions, and the brief's precedents stake out both ends of each. Choosing wrong is cheaper to design than to un-ship.
  • The seven axes: transparent vs explicit sends; at-most-once vs at-least-once delivery; consistency vs availability on a partition; node-tagged pids vs virtual actors; fully-meshed vs gossip membership; homogeneous-binary vs content-addressed code; magic-cookie vs real TLS auth.
  • Hey's data model nudges two of them. Immutable messages make at-least-once replay safer, and the existing content hashing makes Unison-style code shipping less exotic — those two axes, and no more. (The same refcount also makes Ray-style ship-by-reference natural, but that is a bonus outside the seven, not one of the decisions.) These are nudges, not answers.
  • Cautionary talePony designed native actor distribution — transparent local-or-remote sends — and never shipped it. Transparency is easy to draw and hard to finish; the choices below are where that difficulty lives.
  • Check it yourselfRead the brief's §5, "Open questions for the maintainer" — the same seven decisions, each with at least one shipped precedent, the opposite pole sometimes just a well-understood technique.

Part 1 established that Hey can split a program across machines with no virtual machine, and Part 2 established that the wire format — the piece everyone fears — is a plain tree-walk for Hey's immutable, acyclic values. Neither part told the maintainer what kind of distributed system to build. That is this part. The research brief closes with seven open questions, and each is a genuine fork with at least one shipped precedent — often a shipped system on both sides, and where not, a well-understood technique on the other. Below, each fork gets its two poles, the precedent or technique that anchors each pole, the cost of picking it, and — where Hey's own data model tilts the ground — an honest note on which way it leans. None of these is decided.

Choice 1 — Transparent or explicit remote sends

SEND · transparent (Erlang, Pony) ↔ explicit (Ray)The first fork sets the texture of the whole language surface. Erlang and Pony chose transparent distribution: Pid ! Msg reads identically whether the target actor is on this node or another, and Pony was designed so actors "communicat[e] the same way whether local or remote." Ray chose the opposite — an explicit .remote() call marks the network boundary in the source.

Transparency is ergonomic: one send, one mental model, no ceremony at the boundary. The cost is that it hides the two things a distributed program most needs to see — network cost and partial failure, the classic "fallacies of distributed computing." An explicit remote call makes both visible at the call site, at the price of a second, uglier way to talk to an actor. This is not a small stylistic pick; it decides whether a Hey programmer is ever surprised by a local-looking line that quietly crosses a wire.

This axis is one of two exceptions to the pattern that holds across the other five. On those five the Erlang-shaped pole is the lighter one to build, because it promises less. Here it is reversed: Erlang and Pony took the ambitious ergonomics — transparent sends do more for the programmer and demand more of the runtime — so the Erlang-shaped pole is the harder one to finish, and the explicit pole is the honest, lighter default.

Cautionary talePony designed transparent local-or-remote sends and never shipped network distribution — production Pony is single-node. Transparency is the pole that is easiest to draw on a whiteboard and hardest to finish, because it promises the runtime will paper over failures it cannot actually hide.

Choice 2 — At-most-once or at-least-once delivery

DELIVERY · at-most-once (Erlang) ↔ at-least-once (acks + idempotency)Erlang is at-most-once: a message is delivered zero or one times, with no automatic redelivery. A nodedown tells you a message might not have arrived, and you rebuild the lost work through supervision — the "let it crash and supervise" discipline. At-least-once is the other pole, and it is a technique rather than a single named system: the sender retries until it sees an acknowledgement, which means the receiver must be idempotent, because a retried message can land twice.

The tradeoff is where you put the complexity. At-most-once keeps the transport simple and pushes recovery into the supervision tree you already have. At-least-once buys stronger delivery but demands acks, retry state, and idempotent handlers throughout. This is one place Hey's data model genuinely tilts the ground.

Hey leansImmutable messages make idempotent replay safer than in a mutable language — a message re-applied cannot have been mutated in flight, so "the same message twice" is far closer to a no-op by construction. That lowers the cost of at-least-once. It is a lean, not a verdict: the maintainer may still prefer Erlang's crash-and-supervise simplicity over built-in retry.

Choice 3 — The partition stance (CAP)

PARTITION · consistency ↔ availabilityWhen the network splits a cluster in two, a distributed system cannot be both fully consistent and fully available — it must lean one way. Favor consistency and the minority side refuses to proceed until the partition heals — that is the general CP cost, minority unavailability. Akka's cited behavior reaches further: "gossip convergence cannot occur while any nodes are unreachable," so in Akka's specific shape membership convergence is blocked cluster-wide, not only on the minority. Favor availability and both sides keep serving through the split, then reconcile their divergent state once the link returns — at the risk of split-brain.

The brief is blunt that this is not a knob you tune late: it "drives the whole membership design." A consistency-first cluster and an availability-first cluster are different systems from the first line of the membership protocol, because the failure detector, the quorum rules, and the reconciliation machinery all follow from it. It is the one choice on this list with no cheap default and no single-node analogue — the genuinely hard distributed-systems problem.

Choice 4 — Node-tagged pids or virtual actors

ADDRESS · node-tagged pid (Erlang) ↔ virtual actor (Orleans)How does a Hey actor reference name its target across the wire? Erlang's answer is the node-tagged pid: the reference carries its node of origin, so a send routes locally or remotely from identical source — simple, but it pins an actor to the node where it was spawned. Orleans' answer is the virtual actor: a reference "contains only the grain's logical identity, and the Orleans runtime transparently handles translating the grain's logical identity to its physical location and routing messages accordingly." Grains activate on demand and deactivate when idle, "like virtual memory … page out / page in."

Virtual-actor identity buys automatic placement, migration, and activate-on-demand — the runtime keeps the freedom to move an actor and recover it elsewhere. The price is a runtime directory that must always resolve a logical identity to a current location. Node-tagged pids are simpler and need no directory, but they surrender that freedom: the actor lives where it was born. The brief calls addressing "the single most important design choice" precisely because logical identity is what preserves the runtime's room to maneuver.

Choice 5 — Fully-meshed or gossip membership

MEMBERS · fully-meshed net_kernel (Erlang) ↔ gossip + phi-accrual (Akka)How do nodes learn who is in the cluster and who has died? Erlang's net_kernel keeps connections transitive and fully-meshed — connect to one node and you mesh with all — which is simple and fine to a few dozen nodes, but scales poorly past that. Akka Cluster is the other pole: "a fault-tolerant decentralized peer-to-peer based Cluster Membership Service with no single point of failure … using gossip protocols and an automatic failure detector," where each node is monitored by up to five others and suspicion spreads by gossip.

The failure detector is the sharp end of this choice. Akka's is phi-accrual: instead of a boolean "is it down?", it returns a phi value — a tunable likelihood the node has died (default threshold 8) — trading false positives against detection latency. Meshed membership is dramatically less to build; gossip plus phi-accrual scales to thousands of nodes but is a real protocol to implement and get right. The honest driver here is a number the maintainer has to name: what cluster size is Hey targeting? A few dozen nodes and the meshed pole is enough; thousands, and gossip earns its complexity.

Choice 6 — Homogeneous binary or content-addressed code

CODE · homogeneous binary ↔ content-addressed (Unison)This is the one place a native, no-VM language feels the absence of a bytecode VM: when you spawn a function on a remote node, that node has to actually have the code. The cheap pole is homogeneous deploy, a technique rather than a named system: the same Hey binary runs on every node, so any remote spawn refers to code already present, identified by a stable symbol or hash. That is enough to ship a first distributed Hey.

The ambitious pole is content-addressed code, Unison-style: every definition is identified by a hash of its syntax tree, and to run a computation remotely "the sender ships the bytecode tree to the recipient, who inspects the bytecode for any hashes it's missing," requests the missing pieces, and caches them — and because hashes are immutable, code ships "without versioning nightmares." It is a heavier commitment (content-address everything), but it is the principled answer to dynamic code shipping.

Hey leansContent-addressing is less exotic for Hey than for most native languages because Hey already hashes — the brief notes content-addressed shipping "interacts with Hey's existing hashing." That lowers the cost of the ambitious pole. Still a lean, not a verdict: homogeneous deploy is enough for v1, and dynamic code shipping may simply be out of scope.

Choice 7 — Magic-cookie-equivalent or real TLS auth

AUTH · magic cookie (Erlang) ↔ TLS node identityThe last fork is how a joining node proves it belongs. Erlang's mechanism is the magic cookie: nodes compare a shared secret on connect and reject the link if the cookies do not match. Erlang's own documentation concedes the comparison is done "not in a cryptographically secure manner" — the cookie is a cluster fence, not real authentication. The other pole is TLS-authenticated node identity — the standard technique for real node auth: cryptographic proof of who each node is, at the cost of certificate management and handshake overhead.

The tradeoff is minimum-bar simplicity versus actual security. A cookie-equivalent is trivial to build and adequate inside a trusted network segment; it is also, by its own designers' admission, not a security boundary. The brief's suggestion is pointed — start with TLS-authenticated node identity rather than reproducing the plaintext-cookie weakness — but that is a security recommendation, not a data-model lean, and it remains a choice, weighed against how much the target deployment can lean on network-level trust instead.

One thread runs through all seven: don't out-promise the failure model

The seven choices look independent, and on the design table they are — but Pony's warning ties them together. Pony designed transparent distribution and never shipped it, and the brief is specific about one reason why: unbounded mailboxes across a network are worse than locally, and Pony had to retrofit "muting" for backpressure. The lesson generalizes across the forks above. On five of the seven axes the left pole is lighter to build precisely because it promises less; each pole on the right does more for the programmer, which means more the runtime must actually deliver under partition, loss, and load. Two axes break the pattern. The first is transparent sends — the Erlang-shaped pole, yet the harder one to finish, because Erlang and Pony chose the ambitious ergonomics there, and that is exactly the corner Pony could not turn. The second is CAP, which has no cheap default on either pole: pick consistency and the cluster goes unavailable during the split; pick availability and you inherit split-brain state to reconcile — so neither pole is free. The failure model is where distributed systems are finished or abandoned — so the safe way to read this map is to pick the pole whose promises the runtime can keep, not the pole that reads best in a demo.

That is why none of these is presented as decided. Hey's data model genuinely lightens two of the seven — at-least-once replay (immutable messages) and content-addressed code (Hey already hashes) — and, outside these seven, it makes Part 2's wire format a plain tree-walk and Ray-style ship-by-reference natural. It lightens neither of the two the model cannot erase — partition semantics and addressing — which are distributed-systems problems no data model dissolves. A distributed Hey is whichever seven coordinates the maintainer picks — and the honest first move is to pick them deliberately, one axis at a time.

Glossary

at-most-once / at-least-once
Delivery guarantees. At-most-once (Erlang): a message arrives zero or one times, with no automatic redelivery — you recover through supervision. At-least-once: the sender retries until acknowledged, so the receiver must be idempotent because a message can arrive twice.
CAP
Consistency, Availability, Partition-tolerance. On a network partition a system cannot be both fully consistent and fully available; it must lean toward refusing to proceed (consistency) or continuing on both sides and reconciling later (availability).
split-brain
The state after an availability-first partition, where both sides kept serving and now hold divergent data that must be merged when the link heals — the cost of favoring availability over consistency.
node-tagged pid
Erlang's actor reference, carrying its node of origin so a send routes locally or remotely from identical source. Simple, but pins the actor to the node where it was spawned.
virtual actor
Microsoft Orleans' addressing model: an actor is named by logical identity, and the runtime places, migrates, activates, and recovers it freely — at the cost of a runtime directory that resolves identity to location.
gossip / phi-accrual
Akka Cluster's decentralized membership: nodes spread state peer-to-peer by gossip with no coordinator, and the phi-accrual failure detector returns a tunable suspicion value (phi) for how likely a node has died, rather than a boolean.
content-addressed code
Unison's model: every definition is identified by a hash of its syntax tree, so code ships across nodes by hash — the recipient requests any hashes it lacks — without versioning conflicts, because hashes are immutable.
magic cookie
Erlang's cluster secret: nodes compare a shared token on connect. Erlang's own docs note the comparison is "not in a cryptographically secure manner" — a cluster fence, not authentication.
