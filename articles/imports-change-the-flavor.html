Hey language · design note · 22 August 2026 · substantially revised 29 August 2026

Imports that change the flavor of the language

Hey is removing the privileged built-in layer entirely. Every operation ends up in a real module, and a normal program opens by importing the recommended one. That single decision is what makes an import in Hey more than a name lookup: the same language reads differently from file to file, because each file chose its own vocabulary — and it chose it lexically, once, before the optimizer ever sees the program.

TL;DR
  • There will be no privileged ambient built-in layer. Every operation ultimately lives in a real module. A normal program may begin import 'stdlib:Sys' exposing *.
  • Sys is an ordinary facade module. The compiler does not special-case the string. A project may write import './System.hey' exposing * instead and reuse, narrow, conceal or replace the standard surface. The mechanism does not depend on whether the eventual public spelling is Sys or System.
  • Exposure metadata describes capability; lexical imports decide activation. exposes says what a module may be called as. exposing / forms / conceals / as say what this scope actually adopts.
  • Dotted selector resolution is lexical, not type-directed. There is no receiver-type dispatch. One put is selected per scope by ordinary scope rules, and it wins for every x.put(...) in that scope, whatever x holds at runtime.
  • All call forms should be equally fast. map(items, f), items.map(f) and Collections.map(items, f) may be three spellings of one resolved function. Syntax affects resolution. Resolved identity affects optimization.
  • The measured split where builtin put(m, k, v) reaches flat ownership behavior while stats.put(k, v) still reaches O(map) is a compiler defect, not a cost of dot notation.
  • Status is transitional, not finished. The resolver machinery is substantially built and publishes qualified and bare identity; receiver identity publication is active cutover work; the old ambient layer still exists; the authority flip is not complete.

1 · Defaults without hidden defaults

Most languages give you a comfortable starting vocabulary by making some names special. There is a built-in layer the compiler knows about, it is always present, and nothing in your source explains where len or sort came from. That is convenient right up to the moment you want to know what a name means, replace it, or reason about how it compiles.

Hey's answer is to delete that layer. Every operation gets a real module home, and the comfortable feel comes back through an ordinary import at the top of the file:

import 'stdlib:Sys' exposing *

program
  let names = users.map(user_name)
  says join(sort(names), ', ')
end
Maintainer ruling — 31 July 2026 There should be no built-ins at all. Every function lives in a module; the language is consistent because there is no privileged ambient layer. The built-in feel returns because programs naturally open with a Sys import. Sys is not a home for functions — it imports and re-exposes the real domain modules that house them.

The important part is what Sys is not. It is not a keyword, not a compiler concept, and not a fallback the resolver consults when a name is otherwise unknown. The compiler does not special-case the string Sys. It is a facade module written in Hey, which imports domain modules and re-exposes a chosen subset under chosen names. Anything you can do to any other module you can do to it.

The same treatment already reaches down to the names that look most privileged. Built-ins are defined as the outer lexical surface of stdlib:BuiltIns, and they follow the same conflict and concealment rules as any other import. That single sentence does most of the work in this design: a built-in is not a special case the resolver checks first, it is an exposure sitting at the outermost scope. Your own import is inner, so by rule one it simply wins — no override mechanism, no compiler exception, no escape hatch to learn. And conceals: [length] is an ordinary thing to write.

So a project that dislikes the standard surface writes its own:

import './System.hey' exposing *   # our house vocabulary, not stdlib's

System.hey can import stdlib:Sys and narrow it, conceal the three names the team finds ambiguous, add four of its own, or ignore the standard surface entirely and curate from the domain modules directly. Sys is the working name in this note; the mechanism is independent of whether the eventual public spelling turns out to be Sys or System. What matters is that the recommended vocabulary arrives through machinery every user already has, rather than through a compiler exception nobody can reach.

This is a language change, not a stdlib change. Name lookup becomes module-only, which touches the resolver and every emitter lane — and it breaks every existing program that does not add the import. Section 8 is about how that happens without a flag day.

2 · Modules publish; imports activate

Hey's import surface is built from a handful of words, and the split between them is the whole idea. Two of them belong to the module being published. The rest belong to the file doing the importing.

The distinction that matters Exposure metadata describes capability. Lexical imports decide activation. A module says what its functions may be called as. A scope says which of those it actually wants. Nothing a module declares changes how any other file reads until that file asks.

A module names its public surface explicitly. Nothing leaks unless the module says so, and private fn is never exported at all:

module BankAccount
  fn deposit(account, amount) ... end
  private fn valid_amount?(amount) ... end
  exposes deposit forms: [:qualified, :receiver]
end

That forms: list is capability, not activation. It says deposit is publishable as BankAccount.deposit(a, n) and as a.deposit(n). It does not put either spelling into anybody's scope.

The importing file then chooses its posture. Same module, five different answers:

import "stdlib:RubyMath"                    # qualified only: RubyMath.div(-7,2)
import "stdlib:RubyMath" exposing *         # adopt the whole surface into THIS scope
import "stdlib:RubyMath" as RM              # rename the namespace, adopt nothing
import './Actions.hey' exposing: [on_save]  # selective
import 'stdlib:RubyMath' as RM \
  exposing: [div] \
  conceals: [mod]                           # multi-clause with \ continuation

A bare import is the restrained default: you can see the module and call it qualified, and nothing about how the rest of your file reads has changed. Everything else is a deliberate step toward pulling a module's vocabulary into your own.

Two sides of one boundary. The first two are written in the module; the rest are written at the import site.
WordWhere it livesThe job it does
exposesIn the moduleDeclares the public surface — which names leave the module at all.
forms:In the exposesDeclares which call spellings that exposure supports: qualified, bare, receiver. Capability only.
exposingAt the importWhich published names this scope adopts — * for the whole surface, a list for a selection.
forms: (import clause)At the importWhich supported spellings this scope activates. Narrowing, never widening.
conceals:At the importSubtracts from an adopted surface — the one way to take a name back out of an exposing *. Removes the local binding only: it does not make the declaration private in its own module, and it does not remove qualified access.
asAt the importLocal naming. Renames the namespace without adopting anything into the bare vocabulary.
privateIn the moduleA declaration that is never exported, and so never has capability to describe.

Capability metadata is meant to be read

The point of writing exposure down as data, rather than leaving it implicit in the compiler, is that other things can read it. The same record that tells the resolver which forms are legal should be able to tell a person: the public name, the forms it supports, its operator symbol when it has one, and where it was declared. That is what makes a receiver form discoverable instead of folklore — a reader who meets items.map(f) can find out which module supplied it and how, and an editor can complete after a dot, explain an override warning, or offer the qualified spelling that sidesteps a conflict.

This is also the honest version of removing the built-ins. Today a built-in is a name scattered through a parser and several emitters, and nothing outside the compiler can enumerate it. Under the module system it becomes an ordinary exposure of an ordinary module — one a file can conceal, shadow with a visible warning, or import explicitly to compare against something else. Built-ins stop being exceptions only the compiler remembers and become inspectable language data. The generated exposure catalog is the current, temporary stand-in for exactly that record.

Because activation is lexical, flavor is a per-scope decision. Math exposes an operator — exposes pow infix: '**' — so a file that writes import "stdlib:Math" exposing * is not only borrowing functions; it is activating that module's forms, including **. Arithmetic in that one file can read the way Ruby's reads. The file next door, importing nothing, still sees plain Hey.

Two rules keep this from becoming chaos. Precedence is owned by the symbol, never the module — an import supplies meaning, never shape — and a module may claim an existing symbol except the state-mutation operators. And when adopted names collide there is a stated order rather than a coin flip. Section 5 gives the exact rule, because it is also the rule that governs dotted calls.

3 · What dot notation actually does

Hey has method-like syntax without objects. It is worth walking one call all the way down, because every wrong intuition about Hey's dot notation comes from skipping a step.

items.map(f)
One dotted call, end to end. Nothing in this sequence happens at runtime.
StepWhat happens
1 · ImportsThe scope's imports, and the exposure surfaces they adopted, are already known. Some module published map with receiver among its supported forms.
2 · ResolveThe resolver selects one binding for the selector map in this scope — for a program that adopted collection vocabulary, Collections.map.
3 · Form checkThat exposure's forms include receiver, so the dotted spelling is legal here. If it were qualified-only, this is a compile-time error, not a fallback to something else.
4 · Receiver slotThe receiver becomes the first argument. items.map(f) is map(items, f).
5 · HIRThe resolved identity is written down: owning module, link name, arity, per-parameter ABI kinds, return kind. The spelling is gone.
6 · CallAn ordinary direct native call to a known symbol.

In the current generated exposure catalog, Collections.map is recorded with arity 2 and forms ["qualified", "receiver"]; AVLTree.put with arity 3 and the same pair. Those forms lists are exactly the capability record step 3 consults.

State it plainly There is no runtime method lookup. There is no global method table. There is no type-directed receiver dispatch. The dot is compile-time sugar over a function call, and by the time the program runs, the dot is not a thing that exists. The specification puts it in two sentences: "HIR stores the selected binding identity. Runtime does not search again."

Chains follow the same rule, one segment at a time:

The candidate resolver already emits this shape. Each resolved call site carries the owning module, a stable link name, arity, parameter kinds and return kind, plus a flag recording that the first argument came from a receiver. The backend has no receiver concept and needs none: the dotted sugar is gone before it looks.

4 · All call forms should be equally fast

This is the design idea the rest of the article exists to protect.

If Collections.map is adopted with both its supported forms, then these three lines may name exactly one function:

map(items, f)                 # bare
items.map(f)                  # receiver
Collections.map(items, f)     # qualified

Three spellings, one meaning, one resolved identity. Which one you wrote is a fact about your source file. It should stop being a fact about your program the instant the resolver is finished with it.

The design rule Syntax affects resolution. Resolved identity affects optimization. After resolution, the optimizer and the code generator must not be able to tell which spelling was written. If they can, that is a defect in the compiler, not a property of the language.

Hey does not meet that rule everywhere yet, and the clearest violation is worth stating in full, because it is exactly the failure the rule exists to prevent.

The put split

Map update has two spellings a Hey programmer would reasonably treat as identical: put(m, k, v) and m.put(k, v). Both denote the same map-update operation. But ownership analysis in the middle-end matched on printed text — it looked for a call whose text began with put( followed by the parameter's name. The builtin spelling matched. The method spelling did not. Missing that match meant the callee never earned its consume marker and the caller never earned its move, so the map was cloned on every update instead of being updated in place.

The consequence, from the project's own measurements: once the interprocedural ownership repair landed, the builtin-form fixture went flat across a key-count sweep, while the method-form control at the same key counts kept growing — the same operation, written the other way, still O(map) per update. The honest 1BRC program uses the method form, which is why that benchmark stayed pinned to the slow path after the fix that was supposed to free it.

Say the true thing This is a compiler defect, not an intended cost of dot notation. Nothing in the language says a dotted call is slower. Two spellings were allowed to remain two things further down the pipeline than they should have been, and an analysis keyed on text rather than identity noticed the difference.

The repair follows from the rule, not from the symptom. The wrong fix is to teach the ownership matcher a second spelling, or to make .put a case the compiler recognizes specially. The right fix is to canonicalize meaning before ownership: at the point where a call's identity is established, lower m.op(args) to the same canonical node as op(m, args), so every pass downstream sees one operation and cannot key on a spelling that no longer exists. That also retires the duplicated dual-spelling logic other parts of the analyzer had already grown for the read-only cases — a sign, in hindsight, that the canonical form was missing rather than that the matcher was incomplete.

The general lesson is the one the architecture page states as a rule: names are for people, identities are for the compiler. Two source spellings can be different text and the same operation. Any pass that reads text instead of identity will eventually disagree with the language.

5 · Dot resolution is lexical, not type-directed

Readers arriving from Ruby, C++ or Swift will make one specific wrong assumption, and it is worth defusing directly: Hey does not choose a dotted function by looking at the receiver.

There is no rule of the shape "if the receiver looks like a map, use the generic map put; if it looks like an AVL tree, use AVLTree.put." A dotted selector is chosen the way any other name is chosen — by scope:

  • An inner lexical scope beats an outer scope.
  • Within one scope, a later declaration or import beats an earlier one.

That is the whole rule, and it is deliberately stated in general terms. There is no separate case for a selector arriving from two different modules — the same two rules decide it. Given:

import 'stdlib:A' exposing: [put]
import 'stdlib:B' exposing: [put]   # later, same scope

B's put wins the adopted selector, and the compiler warns. An override is never silent: the warning names the winner and the shadowed declaration, and offers the fixes — renaming the module, a narrower exposing: list, aliasing the selector, or conceals:.

One rule, not two A collision does not become a different kind of event because the two candidates came from different modules. Inner beats outer; later beats earlier; the override warns and tells you how to fix it. What the language does not do is pick by looking at the receiver — that is the part a Ruby or Swift reader has to unlearn, and it is unrelated to how collisions resolve.

Implementation gap, not design: today's candidate resolver refuses a cross-module selector collision outright instead of applying later-wins with a warning. That is a known conformance defect recorded against the compiler, not a narrowing of the rule above. The specification is the contract; the resolver has to come to it.

Whatever that produces is the put for that scope, and it applies to every x.put(...) written there. Consider a scope that has adopted a curated put and also uses an AVL tree:

import 'stdlib:Sys' exposing *      # Sys curates ONE `put` into this scope
import 'stdlib:AVLTree' as Tree     # namespace only — adopts nothing

program
  set stats = stats.put(station, reading)   # the Sys `put`
  set index = Tree.put(index, key, value)   # qualified — unambiguous

  # index.put(key, value) would ALSO reach the Sys `put`.
  # Not because `index` is the wrong shape — because the selector
  # was decided by this scope, not by what `index` holds.
end

Both AVLTree.put and a generic map put are receiver-capable — the exposure catalog records the receiver form for both. Capability is not the deciding factor. Activation is. This scope activated one of them under the bare selector put, and that is what the dot reaches.

The other meanings do not disappear. They stay available four ways: qualified (Tree.put(...)), aliased (adopted under a different local name), after concealing or replacing the curated one in this scope, or through a different curated facade that made the other choice. What is not available is having both under the same bare spelling and letting the compiler guess from the value.

The qualified route is guaranteed, which is what makes the rest of this safe to use. Adopting a selector, losing it to a later import, or concealing it outright all act on the local vocabulary only — none of them can take Tree.put(...) away from you. conceals: in particular removes a binding from the current scope without making the declaration private in its own module and without removing qualified access. There is always a spelling that says exactly which module you meant.

Why the constraint is worth it Lexical resolution is what makes section 4 possible. A type-directed dot would mean the meaning of x.put(k, v) depends on a value, which either forces a lookup at runtime or forces the optimizer to reason about types before it can reason about identity. Deciding once, by scope, is what lets three spellings collapse to one symbol before any optimization runs.

The precedent is extension methods, not methods

If Hey's rule feels exotic, it is not. The dot-without-dispatch shape is well travelled, and the languages that took it took it for the same reasons.

C# extension methods are ordinary static methods callable with instance-looking syntax, with the receiver as the first parameter. Kotlin states outright that extensions do not add members to the extended class and are resolved statically — the declared type at the call site decides, not the runtime value. That is Hey's rule with the serial numbers filed off, and it is why a Ruby or Swift reader's instinct mis-transfers: those languages dispatch on the receiver, and these do not.

The scope half has equally good precedent. Elixir's imports and aliases are lexical and narrowable with inclusion and exclusion lists. Haskell keeps a module's export list and an importer's hiding list as two separate decisions — which is exactly the capability-versus-activation split of section 2, arrived at independently. Those are better guides for Hey than any runtime method table.

Rust is worth naming for the one collision Hey has not settled. Where a callable field and a receiver function could claim the same dotted spelling, Rust removes the ambiguity in the grammar: value.name(...) is a method call, and a callable field must be written (value.name)(...). Hey's open decision is whether to do something similar, apply the normal latest-lexical-binding rule with a warning, or reject the ambiguous spelling outright. Kotlin and C# both generally favour a real member over an extension; Hey has not ruled.

6 · Sys is curation, not merge

The moment a facade exists, a lazy implementation suggests itself: import every domain module, re-expose everything, and let import order settle the overlaps. That implementation must not be built.

The overlap is not hypothetical. Reading the generated exposure catalog for the current standard library, one name after another is housed in several modules with genuinely different semantics:

Real collisions in the current standard library, from the generated exposure catalog. Selected modules shown.
NameHoused inWhy they are not one operation
putDictionary, OrderedMap, AVLTree, RedBlackTree, SplayTree, Matrix, Web, and moreGeneric map insert; a balanced-tree insert with a rebalance; a matrix cell write; an HTTP PUT.
getEnv, Http, Web, Dictionary, the tree modulesRead an environment variable; perform an HTTP GET; look up a key. Same three letters, three different worlds.
joinFiles, TextJoin path segments the way the platform wants, versus join strings with a separator you supply.
mapCollections, List, Set, Streams, Matrix, SchemaStructurally similar, semantically distinct — and the right universal one still has to be chosen on purpose.

The project's own census of the generic name set found fourteen of roughly sixty generic names housed in two or more modules with different semantics. A facade built by merging would resolve those by accident of import order.

The hard rule Import order must never silently define the Sys API. Every overlapping name in the facade is a decision somebody made and wrote down.

Notice that the language will not stop a merge-everything facade. It has no reason to: by the ordinary rule, the last import of a colliding selector simply wins. A facade that imports every domain module and re-exposes everything would compile, and it would have a real API — one determined by the order its import lines happen to sit in. The warnings would fire, but they fire inside the facade, where its author can stop reading them, and the programs downstream would inherit whatever fell out.

That is precisely why the discipline has to live in the facade rather than in the compiler. Because later-wins is order-dependent, a curator has to choose; a merge lets the file's line ordering choose, and then a reordering that looks like tidying silently changes what put means for every program that adopted the surface. Curation is not a safety net the compiler provides — it is the work, and nothing else does it.

Which leaves three legitimate moves per collision, and only three:

  1. Choose one universal meaning. If a generic map put is what nearly every program means by put, the facade re-exposes that one and no other.
  2. Give conflicting meanings distinct curated names. The facade may re-expose Files.join as path_join and Text.join as join — or expose neither under a bare name.
  3. Leave them qualified. Http.get and Web.put are perfectly good names. A program doing HTTP should say so.

7 · What belongs in Sys

The membership list is deliberately not frozen here, and it should not be frozen by an article. It is being derived from a census over real Hey applications rather than from anybody's taste, and the principle behind the census matters more than any snapshot of its output:

  • Include common everyday vocabulary — the operations that appear in most programs regardless of what the program is for.
  • Exclude domain APIs unless they are genuinely universal. A name being useful is not the same as a name being everywhere.
  • Resolve collisions intentionally, by the three moves above, before the name enters the facade.
  • Weight cross-repository breadth over generated or raw frequency. One generated file calling something ten thousand times is one program's opinion. Forty repositories each calling it twice is a language-level fact.
Examples, not promises. These are the shapes of the argument, not the membership list — the census decides membership.

One structural rule already falls out of the census work done so far: names that already carry a domain prefix and already have a domain module wrapping them must not be duplicated into the facade. Roughly half of the current ambient registry is already domain-prefixed and already housed. Re-exposing those under bare names would rebuild the grab-bag the whole exercise is meant to retire.

8 · Migration is not a flag day

Removing the ambient layer breaks every program that does not add an import — the standard library, the tools, the spec suite, the examples, and the shipped applications. Files.read_text alone has hundreds of call sites in the spec suite. That cannot be a switch thrown on a single afternoon, so it is not one. The order is:

The migration, in plain English. Each phase is useful on its own, and none of them requires the next one to already be done.
PhaseWhat it does
1 · MeasureCensus the ambient assumptions that actually exist — which names, in which programs, how often, in what semantic role.
2 · HomeGive every operation a real module. A third of the generic ambient names had no module home at all; they need one before anything else can proceed. This breaks nothing and needs no new syntax.
3 · CurateBuild the facade against the census, resolving every collision by decision rather than by order.
4 · Route authorityMake the compiler consume resolver identities — one binding identity and one authorized form per call site — instead of re-deriving meaning from a flat name table.
5 · AdaptKeep the old ambient spellings working as compatibility adapters, deprecated and warned, so existing programs keep running while they move. This needs no new mechanism: built-ins are already the outer lexical surface of stdlib:BuiltIns, so a migrated file's own import is inner and wins by the ordinary rule, while an unmigrated file keeps resolving outward exactly as before.
6 · GuideOn an unknown name, the compiler names the module that exposes it and prints the exact import line to paste. This is a table lookup over a standard library the compiler ships with, not fuzzy matching — and it is migration infrastructure, not polish.
7 · MigrateMove first-party code — stdlib, tools, specs, examples, the shipped apps — onto real imports.
8 · ProveDrive legacy-resolution hits to zero and show it, rather than assuming the adapters went unused.
9 · DeleteRemove the ambient registry and the global receiver authorities. Only after step 8 reads zero.
The phrase that keeps phase 5 honest Compatibility is an adapter into the new authority, not a second language implementation. An old spelling must resolve through the module system to the same identity the new spelling reaches. The moment the adapter has its own lookup path, its own table, or its own semantics, the project owns two languages and will ship the bugs of both.

Phase 6 deserves its emphasis. A breaking change with a good diagnostic is a guided migration; the same change without one is hostile. The error message works in CI, in an editor with no language server, and inside a container build — which is why it is sequenced before the deprecation phase rather than after it.

9 · Where this actually stands

The previous version of this article described the whole design as settled but unbuilt. That is no longer accurate in either direction: more of it exists than that suggested, and the parts that exist are not yet in charge. The honest breakdown:

Do not read this article as a description of what today's build does everywhere. It describes a settled design, a substantially built resolver, and a cutover in progress. Where the design and the build disagree today, the build is what runs.

A few narrower questions are genuinely open rather than merely unimplemented, and have been since the early-August docket: which wins when a dotted call matches both a callable field and an imported receiver function; exactly what diagnostic fires when dotted syntax names no eligible receiver; the per-binding alias spelling; and whether reusable selector sets are worth having as a compile-time-only construct. The module-path resolution algorithm — search paths, package roots — was also never fully stated.

One boundary is drawn on purpose and is not open: no dynamic binding from data. A runtime array or map cannot decide which lexical names exist after compilation. Python draws the same line and is a useful reference for it — ordinary imports are language syntax, while programmatic loading goes through a separate library call. Hey can add a module-value loader later; it would be a different mechanism, not an extension of this one. Reusable selector sets, if they are ever adopted, have to be compile-time manifests or generated source for the same reason. The lexical layer stays lexical.

10 · The promise

What a user should get out of all this is narrow and specific.

Hey should feel as if it has good defaults, without hiding where those defaults came from. You import the recommended surface, and the language reads the way you want it to read. You replace that surface when your project wants a different one, using the same import machinery every other module uses, with no compiler exception to negotiate. Every spelling of an operation is resolved exactly once, by scope, before anything downstream looks at it. And the difference between the spellings is erased before optimization begins, so choosing the comfortable one never costs you anything.

Comfortable syntax is a library choice, not a permanent compiler exception. That is the design in one line, and every open item above is work toward making it true in the build rather than only on the page.
