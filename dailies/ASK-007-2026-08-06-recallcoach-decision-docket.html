Nine things I need you to decide

Every one of these came out of running the thing rather than reading it. Some are choices with no right answer; some are places where what we promised and what the server can actually do have come apart. Where somebody else has already solved the same problem, I went and found out what they did and why.

How to use this page

Bugs are not on this page. Two were found and fixed today without asking you — see Not on this page at the bottom. These nine are choices, or things I should not decide with your money or your users.

The decisions

Decision R1

Production has no LLM. Whose key runs the generator?

This is why "run every card through AI" produces nothing usable on the live site. LLM_API_KEY ships empty and the provider falls back to fake, so the server accepts the request, manufactures distractors and returns 200. Nothing warns anybody. Every other decision on this page is downstream of this one.

Regardless of which you pick

The silence is a defect and I will fix it either way: with no real provider configured, a deployed server should refuse AI requests and say so, not return convincing fake distractors. Today the only way to find out is to read the output and notice it is wrong.

Decision R2

The import button dies after 15 minutes. Should it?

You asked this directly: do you drag the bookmark, use it, and throw it away every time? Yes, today, and that is bad. The token baked into the button is deliberately short-lived and single-use, so every import means: create a link, drag a new button to the bookmarks bar, use it once, delete it.

That design is defensible for a credential that travels — it is why a token scraped out of a proxy log is almost certainly already dead. It is just the wrong trade for a button you are meant to keep.

Decision R3

You asked for 5 MB uploads. The ceiling is 750 KB.

The runtime caps request bodies at 1 MiB and enforces it before any of our code runs — an oversized request gets a bare 400 the app never sees and cannot explain. Anki packages arrive base64-encoded, which costs 33%, so the honest cap is 768,000 bytes. I set it there and wrote honest messages rather than leaving a 5 MB promise that fails as a blank error.

This is an ordinary problem. Reverse proxies, tunnels and managed hosts all cap request bodies, and the tus resumable-upload protocol exists largely because of it. Notably, tus's own advice is not to chunk unless a server limit forces you to, because chunking costs throughput. Here it forces you.

Decision R4

Modern Anki exports. Do we learn to read them?

Anki 2.1.50 and newer compress the collection with Zstandard. We detect that by name and refuse it with the exact fix — re-export with "support older Anki versions" ticked — translated into all four languages. It is an honest refusal, but it asks every user to know that a checkbox exists.

Everyone hits this. The format write-up notes that few tools besides Anki itself handle it; Anki add-ons themselves had no bundled decompressor and reach for an external library. Nobody reimplemented zstd — they all linked the real one.

Decision R5

Where do images live in the long run?

You said blobs in SQLite would "likely be very slow, so we'll need a better long term strategy". They are stored that way now, on the same volume as everything else.

The measurement points the other way. SQLite's own benchmark, 35% Faster Than The Filesystem, finds small blobs read and write about a third faster from the database than from individual files, and several times faster on some platforms; the filesystem only wins somewhere above 100 KB. So for diagrams and thumbnails the intuition is backwards, and for full-size photos it is right.

Storage is not the real constraint. This runtime cannot emit a binary HTTP body at all — response length is measured with a C string function, so a zero byte truncates the response. Images come back base64 inside JSON or not at all, and that costs more than any storage choice on this list.

Decision R6

A worker stopped and did not say why. How hard do we chase it?

On the live server, bulk generation for a 14-card deck sat as running with nothing generated and all fourteen cards still pending, its timestamp never moving, while the page polled 257 times. The job starts as queued and marks itself running before it does anything — so the worker started, then stopped, and wrote neither progress nor a failure. Nothing was logged as an error. I do not know the cause.

What I shipped is a guard, not a fix: a heartbeat every minute and a three-minute staleness check, so the job now reports itself failed instead of spinning forever.

This failure has a standard name — an orphaned job — and two standard treatments. Sidekiq's approach moves a claimed job into a per-process private queue and reaps what is left when a process dies, and recovery can take anywhere from five minutes to three hours. Oban requires a minute of heartbeat before it rescues. Both agree on the shape — a claim with an owner, a heartbeat, a reaper — and neither tells you why a worker stopped. That is what per-attempt logging is for.

Decision R7

A student changes their answer. What happens to the first one?

You asked for revision: a student can change their answer until the teacher moves on. The trap is underneath — responses are durable rows and end-of-quiz scoring folds over all of them, so if a revision appends a row, the student who changed their mind gets counted twice.

Decision R8

Who is allowed to create an account?

The sign-in panels on the live site offer "Create an account". Pair this with R1: if the company key is funding generation, then whoever can register can spend it.

Decision R9

The TV can render emphasis now. Do we ship it and start using it?

The tvOS package renders bold, italic and code spans, with a flanking rule so that 2 * 3 * 4 does not italicise the 3 and fill-in-the-blank stems full of underscores survive intact — that rule exists because testing the parser caught what reading it did not. But the lockfile still points at the previous version and nothing on the server sends emphasis, so the feature is currently invisible.

Not on this page

Fixed today, no ruling needed

The Brainscape button was importing the web page instead of the deck. It appended .csv to whatever URL you were standing on — which is only right on a page nobody browses. From a deck's Browse, Edit or Study screen it asked the site for a route that does not exist, and the single-page app answered 200 with its own shell. That HTML parsed perfectly well as a spreadsheet, so the import produced fourteen "cards" whose fronts were the page's own JavaScript. It now takes the deck id out of the URL and builds the real export link, refuses any response that is a web page, and says so plainly when it cannot tell which deck you mean. The parser refuses HTML documents too, so neither import door can do this again.

Hidden elements were not hidden, which is why an empty text box appeared in the AI dialogs, and the password fields now have a show/hide control.

Real, but not decisions

The equation editor and image field on questions are blocked behind R5 and wait on it. The soundtrack needs a human vocalist, not a ruling. Image occlusion is deferred by your own instruction and stays deferred.
