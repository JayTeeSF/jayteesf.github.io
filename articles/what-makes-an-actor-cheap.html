What Makes an Actor Cheap?

BEAM, Pony, Go, and Tokio all promise to run huge numbers of lightweight, message-passing workers. Their per-worker cost spans a 41× range — and the reason for that spread is not the one you'd guess. A sourced walk through what each runtime actually pays for, and what of it transfers to a language built around immutability.

TL;DR

  • Per-actor memory floor spans 41×: a Tokio task costs 64 bytes, a Pony actor ~240 bytes, a Go goroutine 2,048 bytes, a BEAM process ~2,616 bytes (327 words on 64-bit). Same job — a lightweight, independently-scheduled, message-passing worker — four very different price tags.
  • The headline claim: fast is "no stack," not "immutable." Go is mutable and pays the stack tax; BEAM is immutable and also pays the stack tax. Tokio and Pony are on opposite ends of the mutability question and both dodge it. Stack-or-no-stack is the variable that predicts the cost; the data model does not.
  • BEAM's default process ceiling is 1,048,576 processes (tunable past 268 million), and its initial per-process heap is a deliberately tiny 233 words — sized, in the runtime's own documentation, "to support Erlang systems with hundreds of thousands or even millions of processes."
  • BEAM's scheduler preempts a running process every ~4,000 reductions (roughly one per function call) — a counted, deterministic budget, not a timer interrupt — which is part of why its context switches are cheap enough to do millions of times a second.
  • Pony gets its ~240-byte actors and zero-copy sharing of mutable objects, but the zero-copy part is not free: it costs an entire compile-time capability type system plus a garbage collector (ORCA) built around it. Immutability buys the same zero-copy sharing for nothing extra — a combination neither BEAM nor Pony gets in one package.

1. The goal: millions of actors

Term: what's an actor?

An actor is a small, independent worker that owns its own private state and talks to other actors only by sending messages — never by reaching into another actor's data directly. Think of it as a hotel front desk clerk: guests slide requests across the counter (messages), the clerk handles them one at a time from behind the desk (private state), and no guest ever walks behind the counter to grab the ledger themselves. A well-designed actor-based program can run thousands or millions of these clerks at once, each cheap enough that spinning one up costs about as much as allocating a small struct.

Four runtimes chase that same goal with different designs: Erlang/OTP's BEAM virtual machine (where an actor is called a process), the Pony language (built around actors from the ground up), Go's goroutines (not strictly actors, but the same "spawn a huge number of independently-scheduled workers" pitch), and Rust's Tokio async runtime (tasks, not actors, but the same lightweight-unit idea). All four exist because a real OS thread — megabytes of stack, a kernel-managed scheduling slot — cannot be spawned by the million. Something cheaper has to sit underneath.

Two benchmark efforts try to put a number on "how many, how fast." The Skynet benchmark spawns one million actors in a 10-ary, depth-6 tree, has each leaf return its ordinal, and sums a million values back to the root. Reported numbers (hardware varies per row, so these are not apples-to-apples across languages): Erlang non-HIPE (i.e., without Erlang's now-largely-retired native-code compiler) ran it in 700–1,100 ms on an i7-4771/Ubuntu box and 4,414 ms on a 2015 MacBook 12″ (Core M); Go, 200–224 ms on the same i7-4771 and 979 ms on the MacBook; Scala/Akka, 4,419 ms on an i7-4770 and 6,379 ms on the MacBook. Worth flagging plainly: the Skynet repository has directories for Pony, Elixir, and Java/Rust, but its maintained README reports no timing numbers for any of them — so this article won't quote any. That gap is itself informative: a benchmark repo can advertise a language without ever having measured it.

The Savina benchmark suite (Imam & Sarkar, AGERE! 2014) takes a different approach: 28 benchmarks grouped by what they stress, rather than by raw scale.

Both benchmark suites agree on the shape of the question — spawn cost, message throughput, and fairness under contention — even though the raw numbers can't be lined up across languages. The decomposition in section 3 below is what actually explains the spread.

2. How BEAM does it: reductions, tiny heaps, dirty schedulers

A freshly spawned Erlang process uses 327 words of memory in total, with a default initial (minimum) heap of just 233 words — deliberately small, in the runtime documentation's own words, "to support Erlang systems with hundreds of thousands or even millions of processes." It's tunable system-wide (+h) or per-process (spawn_opt(Fun, [{min_heap_size, N}])), because growing a heap step-by-step during garbage collection is more expensive than just pre-sizing it right — the 233-word default is a considered floor, not an oversight. — Processes, Erlang System Documentation

Each process is a plain C struct holding heap/stack pointers (growing toward each other in one contiguous block), the current heap size, generational garbage-collection bookkeeping, a reduction counter, and its own message queue. Critically: no shared heap — every process's heap is private to it. — theBeamBook, processes.asciidoc

Term: stack vs. heap

A call stack is the pile of "what do I do when I'm done with this" bookmarks a program keeps as functions call other functions — think of a stack of sticky notes on your desk, one added every time you get interrupted by a sub-task, popped off when that sub-task finishes. A heap is separate: the pool of longer-lived data a program allocates, like the actual documents on your desk rather than the sticky notes about them. A worker that can pause and resume mid-function — waiting on a message part-way through a computation — needs a real, growable call stack to remember where it was. A worker that only ever runs one message-handler to completion before yielding needs no stack bookmark at all, because there's nothing mid-function to remember.

Term: reduction

A reduction is BEAM's unit of "how much work has this process done," incremented roughly once per function call. It's how the scheduler decides when to pause a process and let another one run — not by a timer interrupting it mid-flight (the way an operating system preempts a thread), but by counting: after about 4,000 reductions, the scheduler swaps the process out for the next runnable one. Think of a board game where each player's turn ends not after a fixed number of minutes but after a fixed number of moves — predictable, countable, and cheap to enforce because nobody needs a stopwatch.

Concretely: CONTEXT_REDS is 4,000 (raised from 2,000 before OTP 20), and INPUT_REDUCTIONS — the threshold that also gates system-level checks like I/O polling — is double that, 8,000. Counted preemption makes context switches deterministic and, because there's no signal or trap involved, cheap. — theBeamBook, scheduling.asciidoc

Term: work-stealing scheduler

BEAM runs one OS thread per available CPU core by default, each with its own queue of runnable processes (three priority tiers: max, high, and normal/low). When one core's queue runs dry, it steals work from a busier core's queue rather than sitting idle. Picture four cashiers with separate lines: instead of standing around empty-handed, an idle cashier walks over and takes the next customer from the longest line. — erl(1) man page, theBeamBook, scheduling.asciidoc

Term: mailbox

A mailbox is the queue of incoming messages an actor hasn't processed yet — like a physical inbox on a desk. BEAM's mailbox is delivered as "signals," implemented as a linked list; an off_heap variant lets multiple senders enqueue in parallel without locking against each other, because each has its own separately-locked node. Order is preserved between any one sender and receiver, but not across different senders. msg.save implements selective receive — a process can skip past messages it doesn't want yet and leave them in the mailbox for later. — Erlang parallel signal-sending optimization, theBeamBook, processes.asciidoc

Not every scheduler thread runs at the same rules, either. Dirty schedulers keep blocking or slow native work off the reduction-counted pool: dirty CPU schedulers default to the same count as normal schedulers, while dirty I/O schedulers default to a fixed 10, independent of core count, because I/O-bound work (file access, DNS) doesn't scale with cores the way CPU work does. A NIF (native implemented function — C code called from Erlang) call that can't finish in about a millisecond, or can't be chunked, has to be marked dirty (ERL_NIF_DIRTY_JOB_CPU_BOUND / ..._IO_BOUND) — because the normal scheduler has no way to preempt native code mid-call the way it preempts BEAM bytecode by counting reductions, so a long native call would otherwise stall an entire scheduler thread. — erl(1), +SDio/+SDcpu, erl_nif docs

All of this adds up to a default process ceiling of 1,048,576 (+P), settable up to 268,435,456. — System Limits, Erlang docs

That's the bill BEAM pays to keep hundreds of thousands of processes alive at once. Set it down next to the other three runtimes chasing the same goal, and it breaks down in a way that has nothing to do with the guess most people would make first.

3. The surprising decomposition: the stack is the cost, not the data model

Lay the four floors side by side and a pattern jumps out that has nothing to do with whether the language is functional or imperative, immutable or mutable:

RuntimePer-actor floorHas a real call stack?Data model
Tokio task64 BNo — a compiler-generated state machineMutable
Pony actor~240 BNo — behaviors run to completionMutable (by design)
Go goroutine2,048 B (initial)Yes — real, growable, can suspend anywhereMutable
BEAM process~2,616 B (327 words)Yes — real, growable, can suspend anywhereImmutable

Go is mutable and pays for a stack. BEAM is immutable and also pays for a stack. Tokio is mutable and has no stack. Pony is mutable and has no stack. The variable that predicts cost is "can this worker suspend in the middle of an arbitrary function call," not "is the data immutable." Immutability turns out to be an innocent bystander here — the stack was the villain all along, and it had been standing in plain sight the whole time. Tokio's tasks and Pony's actors are cheap for the identical reason: no stack. A Tokio task is "under the hood... a single allocation and 64 bytes of memory," explicitly designed so that "spawning thousands, or even millions of tasks" is normal. — Tokio Tutorial: Spawning

Go's goroutine tells the other half of the story: its initial stack is 2,048 bytes (stackMin in runtime/stack.go), tuned down over time from 8 KB in Go 1.2 to 2 KB in Go 1.4. When a function's stack check finds insufficient room, the runtime allocates a new stack at double the size, copies the old stack's contents over, and rewrites every internal pointer that pointed into the moved frame — tractable only because the Go compiler tracks exact stack-frame layouts. It's a moving, copying stack, not a segmented one. — golang/go, runtime/stack.go

That's the price of letting a worker suspend anywhere: you need a real stack, it has to grow, and growing it is genuinely intricate machinery. BEAM pays the same tax (its heap and stack grow toward each other in one block, per the process layout above) for the same reason: a process can block waiting on a receive in the middle of any function.

The rest of the decomposition, briefly:

  • Mailbox structure is a wash — all four use linked-list queues. BEAM's is the most elaborate (off-heap variant, parallel enqueue, selective receive); Pony's is FIFO-only with no selective receive, which is part of how it stays inside 240 bytes.
  • Scheduling state differs in kind, not obviously in cost: BEAM counts reductions to interrupt long-running code fairly; Pony sidesteps the problem by convention (behaviors are short, so nothing needs interrupting); Tokio polls a state machine. Reduction counting is the one that buys fairness between actors doing arbitrarily long work.
  • What immutable message-passing lets you skip is the subject of the next section — and it's the one place the data model actually does matter.

4. The Pony/ORCA story: what mutability costs an actor runtime

Pony's actors are as cheap as Tokio's — ~240 bytes on a 64-bit system, covering the message queue header, a per-actor heap header, and garbage-collection bookkeeping. Like Tokio, there's no stack: a Pony behavior (its term for a message handler) runs to completion. — Pony Runtime FAQ

But Pony also does something BEAM never has to: it shares mutable objects between actors by reference, with zero copying, and still keeps memory safe with no stop-the-world pause. That combination is what its garbage collector, ORCA, and its type system exist to buy.

Term: garbage collection

Garbage collection (GC) is a runtime automatically finding and reclaiming memory that's no longer reachable, so the programmer doesn't have to track it by hand. The old-fashioned worry is stop-the-world GC: the whole program freezes while the collector walks memory — like a store closing entirely to do inventory. Pony's ORCA instead runs GC per actor, only when that actor is idle between messages, so one actor's cleanup never freezes any other actor — each store does inventory on its own schedule, doors open the whole time for everyone else.

Term: capability type system

A reference capability is a tag the Pony compiler attaches to every reference (iso, val, tag, ref, trn, box) that restricts what you're allowed to do with it — for example, a val reference means "you may read this, and so may anyone else, but nobody may ever write to it." Think of it as a set of colored wristbands at a venue: an "access-all-areas" band lets you do things a "spectator" band never permits, checked at the door rather than by a guard following you around all night. The payoff: the compiler can guarantee, before the program ever runs, that at most one actor can mutate a given object at a time — so the garbage collector never needs to check at runtime.

That static guarantee is what makes ORCA's core trick possible: because data races are ruled out at compile time, the collector needs no read/write barriers on individual memory accesses — no extra check bolted onto every read and write, the way most garbage-collected mutable-data runtimes require. The only synchronization ORCA needs anywhere is on message enqueue, a reference-count update that's trivially atomic. Reclaiming shared objects uses deferred, message-piggybacked reference counting (INC/DEC messages sent alongside normal traffic), specifically because naive reference counting breaks under Pony's asynchronous, causal message delivery. — Clebsch et al., "ORCA: GC and Type System Co-Design for Actor Languages," OOPSLA 2017 (full text: PDF)

The paper's own authors are candid about the trade they made:

"In a purely functional actor language such as Erlang... it would be trivial to implement a collector such as ours... One of the early decisions in the design of Pony was to support mutable data structures and, for efficiency reasons, to implement zero-copy message passing. Mutability introduce[s] challenges..." — ORCA, §1–2

Term: zero-copy sharing

Zero-copy means passing a message by handing over a pointer to the existing data, rather than duplicating it. It's the difference between mailing someone the original document versus photocopying it first: zero-copy is faster and uses less memory, but now two parties can see the same physical page — which is fine if neither can scribble on it, and dangerous if either can.

Pony's real-world failure modes underline how much careful engineering that "efficiency reason" demands. File I/O and DNS resolution are blocking by design (portable async support was judged not worth the complexity), pushed onto the programmer to chunk. Unbounded mailbox growth is a live risk, since recursive or fan-out behavior calls are asynchronous sends with no built-in backpressure — a producer can simply outrun a consumer. And at extreme scale the implementation has hit real ceilings: one tracked issue reproducibly crashed — segfaults, GC assertion failures, bus errors — when spawning 11 million actors and sending 11 million messages, though 1 million actors worked fine. A concrete data point that "millions of actors" has a ceiling in practice, not just in theory. — Pony Runtime FAQ, ponylang/ponyc issue #552

Pony also detects quiescence — the point where every actor's mailbox is empty, no aliases are pending, and no I/O events are outstanding — and shuts the program down automatically, no explicit signal required. — Pony Runtime FAQ

That's the price of letting mutable data move between actors for free. The next section asks what the equivalent bill looks like when the data was never mutable to begin with.

5. The punchline for Hey: immutability makes zero-copy free

Term: immutability

Immutability means a value, once created, can never be changed — only replaced by a new value. Think of a printed photograph versus a whiteboard: you can hand the photo to as many people as you like and none of them can alter what the others see; a whiteboard shared the same way needs house rules about who's allowed to write on it and when, or two people's edits collide.

BEAM already gets a taste of what immutability buys, in a case the research brief calls "trivial": Erlang deep-copies the transitive closure of every message it sends between processes, because per-process heaps have to stay isolated for BEAM's synchronization-free, per-process garbage collection to work — and that copy is safe with zero extra machinery purely because Erlang data can't be mutated after the fact. The one deliberate exception is refc binaries: large binary data is reference-counted instead of copied ("copying them would be too costly"), and that's safe with no locking or cycle-detection at all, because binaries are immutable and pointer-free — there are no cycles to collect.

Pony's alternative — share mutable objects by reference, zero-copy — costs the entire capability type system plus ORCA's deferred causal reference counting plus per-actor tracing at every message boundary, as its own authors say plainly above.

Put those two facts together and the shape of the opportunity is obvious: BEAM's special case (large binaries shared by reference, no cycle collector needed) can be Hey's general case — if the runtime represents non-trivial immutable values by reference rather than copying them into the receiver's arena. Since nothing can ever mutate a shared immutable value, there's no race to guard against, no reference-counting protocol needed to keep two writers from colliding, and no cycle collector required, for exactly the reason BEAM's refc binaries need none of that today — generalized to all data, not just binaries. A practical implementation would keep a "copy small, reference large" split — a size heuristic, not an immutability requirement — but it's immutability that makes either choice safe with no extra machinery bolted on.

None of the no-stack, cheap-scheduling machinery from sections 2–3 presumes anything about the data model, either: a no-stack fixed-size actor record, reduction-counted or run-to-completion scheduling over one OS thread per core with work-stealing, and dirty-scheduler- style isolation of blocking or native work off the main pool are all orthogonal to whether values are mutable. Hey can take all of it.

That's the combination neither existing runtime gets in one package. BEAM has immutability but pays the stack tax and the (mostly free, but not entirely free) deep-copy tax. Pony has no-stack cheap actors but pays the full capability-and-ORCA tax to make sharing safe under mutability. A no-stack, fixed-size actor record (tens to low hundreds of bytes), run-to-completion or reduction-counted scheduling with work-stealing, and reference-based zero-copy messages that exploit immutability for free — that's the target, and it's a target built entirely out of pieces each of these four runtimes has already proven work, just never all four at once.

Update, 2026-07-26: this research became Hey's actor roadmap

This article was written as a comparison, not a plan — but the team turned it into one anyway. Every workstream in Hey's stack-removal campaign now names a specific decision from the analysis above (loop-top-only receive, a Vyukov mailbox, a Tokio/Go-style work-stealing scheduler, reference-counted zero-copy sharing) as its "crib," with its own acceptance gate. "Designing Hey's Actors" is the follow-up: what got decided, where each piece came from, and what it costs, including one recommendation the team argued out loud and reversed on the same day.

Glossary

actor
An independent unit of computation with private state that communicates only by passing messages, never by sharing memory.
process (BEAM)
Erlang/BEAM's term for what this article otherwise calls an actor.
call stack
The pile of "return to here next" bookmarks kept as functions call other functions.
heap
The pool of longer-lived allocated data a program holds, separate from the call stack.
reduction
BEAM's per-process work counter, incremented roughly once per function call; the basis of its counted preemption.
work-stealing scheduler
A scheduler where an idle worker thread takes tasks from a busier thread's queue instead of sitting idle.
mailbox
The queue of messages an actor has received but not yet processed.
selective receive
Skipping past unwanted messages in a mailbox, leaving them for later.
dirty scheduler
A separate BEAM scheduler pool for blocking or long-running native calls, kept off the reduction-counted schedulers.
garbage collection (GC)
Automatic reclamation of memory no longer reachable by the program.
stop-the-world GC
A garbage collector that pauses the entire program while it runs.
reference capability
A compile-time tag on a Pony reference restricting how it may be read or written.
zero-copy
Sharing data by passing a reference to it, rather than duplicating it.
quiescence
The point at which every actor is idle and no events are pending; Pony auto-terminates here.
immutability
A value that, once created, can never be changed — only replaced.
refc binaries
BEAM's reference-counted (not copied) large binary values — safe with no locking because they're immutable and pointer-free.
