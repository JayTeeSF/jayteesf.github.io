Great Command-Line Scripting with Hey

The week of: 2026-10-10 · re-measured on 601a and Ruby 4.0.7

One job, two implementations, one rule: the outputs must match to the byte. Re-measured on today's toolchain, the Hey this site ships builds its package index in 115.6 ms compiled, against 310.7 ms for Ruby 4.0.7 — 2.7× faster, and 2.3× as a script. It got there on 2026-10-14 by deleting a September workaround that, until that morning, had Ruby winning by 2.5×.

TL;DR

  • Hey is 2.7× faster than Ruby on this job, compiled. On today's 34-package tree: Ruby 4.0.7 + YJIT 310.7 ms, the shipped Hey 115.6 ms as a binary, 137.2 ms as a script (2.3×), and 176.0 ms through the site's bin/hey-run (1.8×). Byte-identical output on every lane.
  • The lead shrinks as the tree grows, and the site's own runner gives most of it back on small trees. On July's 14-package tree the binary is 3.8× Ruby, but bin/hey-run, which spends about 60 ms per call deciding whether to rebuild, is roughly level with Ruby (90.1 against 98.0 ms).
  • Until 2026-10-14, Ruby won. From 2026-09-24 the port carried a hand-written insertion sort, written because .uniq and .sort were broken on that day's Hey. The bug was fixed; the workaround outlived it. Against it Ruby was 2.5× faster (298.6 against 743.4 ms). Restoring Ruby's own spelling, paths.uniq.sort(cmp), deleted 54 lines and reversed the result.
  • Hey is still behind on building long lists (an append copies the list: 16,000 appends take 1.17 s against Ruby's 2.7 ms), on parallelism (no parallel map on 601a; --workers does nothing), and on length: 592 lines against Ruby's 313.
  • Not a quiet box. A Hey compiler build ran throughout (load 2.2–3.4), and a virtual machine joined it in the last round. Most lanes held within 2% across rounds; the last round on the small tree ran up to 20% slower. Every figure is as measured under that load.
  • Not 602a. The newest release's install refuses every script, hello world included: its compiler front end was built from older sources than the checkout and won't run until it's rebuilt, which the Hey team is doing, so these numbers come from 601a.

How to read these numbers

Apple M3 Pro (6 performance + 6 efficiency cores, 18 GiB), macOS 26.6.2. Hey 601a from hey-lang-bootstrap-plan at 565e6ddad, set explicitly per lane with HEY_ROOT. Ruby 4.0.7 (newest stable on ruby-lang.org on 2026-10-14) and 4.0.6, with YJIT (Ruby's built-in just-in-time compiler) on unless a lane says otherwise. Each Ruby is called as its real binary: rbenv, the Ruby version manager, normally runs ruby through a small wrapper script (a shim) that costs 53 ms per launch here and would have been charged to Ruby. Timings from hyperfine, which repeats a command and reports mean ± standard deviation: --warmup 3, 30 runs per Hey lane and 20 per Ruby lane, fixed PACKAGES_INDEX_GENERATED_AT. Every lane deletes its output, asserts it came back non-empty, and byte-compares it with Ruby's before any clock is trusted.

The box was loaded. A single-threaded Hey compiler build held about one core for the whole session, and the 1-minute load average (roughly, how many processes wanted a CPU at once) sat between 2.2 and 3.4, this benchmark included. Benchmarks ran at nice -n 10, lane order rotated each round, and each set ran two or three rounds. Three sets ran that day: the workaround script (3 rounds), the fix before it shipped (2), and the shipped fix (3). In the last round of the last set a virtual machine started using a core, load rose to 3.0–3.4, and the small-tree lanes slowed by up to 20% (Ruby 10%). Ruby's own mean also moved 4% between the first and last sets (298.6 to 310.7 ms), so compare ratios within a set, not milliseconds across sets. The old version of this article said numbers off a loaded machine are lower bounds; these are offered as measured under that load. Every raw number, the harness and the controls are in the evidence file.

2026-09-24 to 2026-10-14: the workaround that outlived its bug

On 2026-09-24 a sibling generator, generate-articles-index.hey, was found writing an index with zero entries while printing “Generated” and exiting 0. On that day's Hey, .uniq, .sort(cmp) and .empty? on an array didn't exist; each returned the runtime's #<stop> sentinel (a stand-in value meaning “nothing here”), which is truthy. Both generators were rewritten around it with hand-written loops (commit 0631ba3): this one got a full-scan unique and an insertion sort. That was the right call on that day, and the parity gate confirmed the output stayed byte-identical.

By 601a the methods worked: a small test prints ["b","a"] for .uniq, false for .empty? on a three-element list, and a sorted list for .sort(cmp) (only those and .map were re-tested). Nobody went back. Measured on the morning of 2026-10-14, before the fix shipped:

So for three weeks the site shipped a Hey that Ruby beat by 2.5× on its real tree, while on July's smaller tree it still edged Ruby compiled (1.18×) and lost as a script. The bigger tree hurt it far more than Ruby: 9.5× slower going from July's tree to today's, against Ruby's 3.2×. The counts show why.

Timings on a loaded box move with the load; counts don't. A small Ruby program replays each strategy on the exact lists the generator sorts and counts how many times the comparator is called and how many list elements get copied. Copies matter because on 601a [...xs, x] behaves as if it copies every element of xs into a new list (see the append timings under Rule 1).

Ten times the comparator calls and thirteen times the copying, and the comparator isn't cheap: it lower-cases both paths (Text.lower measured 3.9 µs a call) and walks them a character at a time. The insertion sort is quadratic in comparisons and, because each pass rebuilds its output one append at a time, roughly cubic in copies. On July's tree, where the longest list is 55 paths, that is 3,129 comparisons and 47,287 copies. At 181 paths it's the whole run. The parity gate passed the workaround the entire time, correctly: it was byte-identical and 6.5× slower than it needed to be. Parity tells you a number measured the right output. It doesn't tell you the code is any good.

The owner decided to ship the fix the same day. fb5fee2 restores paths.uniq.sort(PackagesIndex.compare_paths), deletes the 54-line workaround, passes the parity gate on both trees for both the script and bin/hey-run, and leaves every error message unchanged.

Where Hey is ahead, and where it's behind

Ahead of Ruby today

  • This job, compiled. 2.7× on today's tree, 3.8× on July's.
  • Start-up. A compiled Hey hello world runs in 1.2 ms. Ruby 4.0.7 needs 28.3 ms to run nothing, 30.6 ms once this script's three requires load. Running a script through the hey command (its first line is #!/usr/bin/env hey) costs 19.4 ms.
  • Per-item work, same algorithm. Subtract each side's separately measured start-up floor (1.2 ms and 30.6 ms) on July's tree and the Hey binary does its work in about 24 ms against Ruby's 64–67. That's an estimate from separate measurements, not one.

Still behind Ruby

  • Building long lists. An append copies the list. 16,000 appends take 1.17 s on 601a; Ruby's << does it in 2.7 ms. Even the stdlib merge sort builds its output that way.
  • The lead shrinks as the tree grows, 3.8× to 2.7× from July's tree to today's, for the same reason.
  • Parallelism. There's no parallel map on 601a. --workers is parsed and validated and does nothing; 1 and 4 workers time the same.
  • Length. 592 lines and 25 functions against Ruby's 313 lines and 22 methods: 1.89×. Without comments and blank lines, 435 against 265: 1.64×.
  • The site's runner. bin/hey-run adds about 60 ms a call, enough to bring Hey level with Ruby on a small tree.
  • Catching up with itself. The four dotted array methods that broke in September work on 601a, and .map(f, workers: n) is now a compile error rather than a quiet wrong answer. Ruby never had that failure; this is Hey closing its own gap.
  • Toolchain churn. The July version of this port no longer compiles; the newest release won't run a script on this machine.

Why this benchmark compares idiomatic to idiomatic

In July this article reported 5.46×. The Hey it measured had been hand-optimized for speed: builtins-only inner loops, work hoisted out of the comparator, a worker pool tuned against the clock. The Ruby it beat is plain idiomatic Ruby nobody has ever tuned. That isn't a fair fight. Anyone who can hand-optimize the Hey can hand-optimize the Ruby, so the canonical script became an idiomatic port, a rewrite that mirrors the original's structure instead of chasing the clock, and the headline came from that.

The same rule cut the other way for three weeks. The workaround wasn't slower because Hey is slow at sorting; it was slower because it stopped being a port of the Ruby. The headline is the script in the repository today, which is a port again; the workaround's numbers stay in the dated section above, because they were the honest numbers for what shipped at the time.

The Ruby isn't tuned either. Instrumenting it shows about half its 276 ms of work on today's tree inside compare_paths, which converts each Pathname to a string and lower-cases it on every comparison. A sort_by with a precomputed key would cut that, and the Hey could do the same. Neither side gets it here.

Hey can read like Ruby

The names still line up almost one-for-one: digit_run, trim_leading_zeroes, compare_digit_runs, compare_paths, sorted_unique, relative_path, package_section, render_page, on down the file. Ruby's initialize is Hey's new, and the Hey has three functions the Ruby doesn't: worker_count, package_tasks and rendered_sections, left from the parallel path that no longer runs. Side by side, as committed:

Ruby (generate-packages-index.rb)

def sorted_unique(paths)

  sorted_unique(
    files.select { |path| LINKABLE_EXTENSIONS.include?(path.extname.downcase) }

Hey (generate-packages-index.hey)

private fn sorted_unique(paths)
  return paths.uniq.sort(PackagesIndex.compare_paths)
end

private fn linkable_files(files)
  let linkable = []

  for path in files
    let lower_path = Text.lower(path)
    if Text.ends_with?(lower_path, '.md') or Text.ends_with?(lower_path, '.html')
      set linkable = [...linkable, path]
    end
  end

  return PackagesIndex.sorted_unique(linkable)
end

sorted_unique reads the same in both. linkable_files shows the gap that's left: Ruby filters with select and a block; the port filters with a loop that rebuilds the list with [...linkable, path]. A Ruby programmer reads it cold, but it's longer, and every one of those appends copies the list.

private fn unique_paths(paths)
  let seen = []

  for path in paths
    let found = false

    for kept in seen
      if kept == path
        set found = true
      end
    end

    if not found
      set seen = [...seen, path]
    end
  end

  return seen
end

private fn sort_paths(paths)
  let out = []

  for path in paths
    let placed = false
    let merged = []

    for existing in out
      if not placed and PackagesIndex.compare_paths(path, existing) < 0
        set merged = [...merged, path]
        set placed = true
      end
      set merged = [...merged, existing]
    end

    if not placed
      set merged = [...merged, path]
    end

    set out = merged
  end

  return out
end

private fn sorted_unique(paths)
  return PackagesIndex.sort_paths(PackagesIndex.unique_paths(paths))
end

Correct, byte-for-byte, and the reason for every workaround number in the dated section above.

The ergonomics tax

Identical behaviour costs 1.89× the lines (592 against 313), against 1.67× in July and 2.06× while the workaround was in. Some of that is comments: the Hey file carries long notes about the September bugs, and without comments or blank lines the ratio is 1.64× (435 against 265). What's left is Hey's explicitness: let/set, return, and loops where Ruby has blocks. Price it in.

The parity gate

The thesis, and it outranks every number here: a benchmark without an output-parity gate is a wish. Three receipts from this program and its sibling.

In July the first optimization pass rewrote the comparator to use byte_at(string, i). It compiled, and silently returned 0 for every string argument, being a Bytes-value operation. Every path compared equal to every other, the sort collapsed into a no-op, and the benchmark got faster and wrong. The byte-parity check caught it on the first run.

The second is worse, because the gate itself lied. The fastest result this project ever recorded was a 2.3 ms binary: exit 0, zero bytes of output, dead before the first line of user code. The parity check blessed it because it never deleted the output file first, and so compared the one left by the previous lane. My bug, and the reason the harness below deletes first.

The third arrived in September and is the one behind this revision: the articles generator wrote an empty index, printed “Generated”, and exited 0. Its own header admitted it hadn't been run since a restructure. A twin that's never run isn't a twin.

And a caution the other way: the gate passed the September insertion sort, correctly, for three weeks while it ran 6.5× slower than it needed to. Parity says the output is right, not that the code is.

The gate was itself made to fail before any number here was trusted. A lane that runs true exits 0 and the gate reports NO OUTPUT; the real binary run with a different timestamp exits 0 and the gate reports PARITY FAIL; the real binary with the right timestamp passes.

Running it

There are three ways to run one source file.

# the site's way: builds once into .hey-bin/ (gitignored), then execs the binary
bin/hey-run generate-packages-index ./packages

# the script lane: no build step, shebang is #!/usr/bin/env hey
./generate-packages-index.hey ./packages

# the binary you build yourself: a standalone native executable
export HEY_ROOT="$HOME/dev/hey-lang-bootstrap-plan"
HEY_STDLIB_PATH="$HEY_ROOT/stdlib" HEY_COMPILER_BUILD_DIR="$HEY_ROOT/build" \
  "$HEY_ROOT/bin/heyc" build --backend llvm \
  ./generate-packages-index.hey -o "$HOME/bin/generate-packages-index"

bin/hey-run pins 601a and rebuilds only when the script, a stdlib file it imports, or the compiler changes. The catch is that it works out whether to rebuild on every run, by walking the script's stdlib imports and hashing them together with the compiler (hashing the two compiler binaries alone took 23 ms here). With the shipped script it took 176.0 ms on today's tree against 115.6 ms for the same build run directly, and 90.1 against 25.6 on July's: about 60 ms of overhead a call (the morning's workaround script measured 55). That's more than the 19 ms the hey command adds to a script. For a page generator you run by hand it hardly matters, but it's the difference between beating Ruby clearly and roughly tying it on a small tree. In a loop, call the binary.

The first stdlib call is no longer the expensive one

In July, at 410a, the first delegated stdlib call in a process (one the compiled program handed to an interpreter) cost about 6 ms and every later one about 54 µs. A 12-line argument check made the script 5 ms slower because its Text.int_token? was the first such call. Re-run on 601a, the same probe (cli-startup-call-cost.hey) reports Text.int_token?'s first call at 4–23 µs, and every call it checks at 0–1 µs once warm. The largest one-time cost left in that list is Time.utc_iso8601, 0.37–0.51 ms on first use. The whole program agrees: --workers 1, which pays for that validation, times the same as no flag. The comment in worker_count that quoted 5.8 ms was corrected in fb5fee2.

The three rules, revised

Rule 1: watch how you build lists, not how often you call the stdlib

The July rule was “stdlib freely outside hot loops, builtins only inside them”, because a stdlib call from compiled code cost about 54 µs through the sidecar. On 601a, Collections.compare costs 0.11 µs a call and Text.lower 3.9 µs. Calls aren't what bites any more.

Lists are. On 601a [...xs, x] and xs.push(x) behave as if each returns a new list: they time the same, and appending n items one at a time is quadratic, which is what copying the whole list on every append produces:

Each doubling costs Hey four times as much. Ruby written the same copying way grows too, but Ruby's idiom is <<, which appends in place, and Hey has no equivalent. For a few hundred items per list, as here, it's fine. For tens of thousands, it's the cost that decides the run. This generator's fix was to use the stdlib's sort rather than write one (shipped in fb5fee2); the fix for the language is a list that can grow without copying, which Hey doesn't have on 601a.

Rule 2: measure output before you measure time

Delete the output, run, assert it came back, compare bytes, and only then start a clock. Every memorable failure in this article's history — the comparator that sorted nothing, the binary that did nothing, the index with no entries — looked like success from its exit code.

Rule 3: parallelism has to exist before it can be measured

In July, at 410a, this article reported that .map(fn, workers: n) made the port faster: 24.2 ms at 4 workers against 31.4 at 1 (its Rule 3 said 24.7, its table 24.2), so the default became 4. That verdict doesn't carry over. By September the .map spelling returned the truthy sentinel instead of running, a version built on worker and Jobs timed out, and the script was left serial. On 601a .map(f, workers: 2) doesn't compile (“unresolved callable: map”), --workers is parsed and ignored, and 1 and 4 workers time the same on both trees. Ruby's version is serial too. Any fan-out verdict for Hey waits until there's a fan-out to measure.

A harness that cannot lie to you

The ordering is what matters — rm before the run, the assertion before the comparison — so a program producing nothing fails here instead of posting a record. This is the shape of the one used for every figure above (the full script is in the evidence file). 

set -eu
export PACKAGES_INDEX_GENERATED_AT=2026-10-14T00:00:00Z
R="$HOME/dev/hey-lang-bootstrap-plan"                       # 601a, pinned per lane
export HEY_ROOT=$R HEY_STDLIB_PATH=$R/stdlib HEY_COMPILER_BUILD_DIR=$R/build
export PATH="$R/bin:$PATH"                                  # the shebang's hey
RUBY="$HOME/.rbenv/versions/4.0.7/bin/ruby"                 # the real binary, not the shim

lane() {                      # $1 = label, $2.. = command
  rm -f packages/index.html
  "${@:2}" >/dev/null
  test -s packages/index.html || { echo "$1: NO OUTPUT"; exit 1; }
  cp packages/index.html "out.$1.html"
}

lane ruby   "$RUBY" --yjit ./generate-packages-index.rb ./packages
lane script ./generate-packages-index.hey ./packages
lane binary ./generate-packages-index ./packages

cmp out.ruby.html out.script.html
cmp out.ruby.html out.binary.html

uptime; ps -Ao pcpu,pid,comm -r | head -6                   # load travels with the number
hyperfine -N --warmup 3 --runs 30 \
  "$RUBY --yjit ./generate-packages-index.rb ./packages" \
  './generate-packages-index.hey ./packages' \
  './generate-packages-index ./packages'
uptime; ps -Ao pcpu,pid,comm -r | head -6

When a lane dies silently (exit 0, no output), suspect the caches before the compiler: in July a racy publish minted a corrupted entry that deterministically produced do-nothing programs, and a dead run wrote its own entry into the run cache. The cache layout has moved since then; the July advice's ~/.cache/hey/run doesn't exist any more. Ask Hey where its caches are, look before deleting, then delete: 

hey cache path          # run_cache=~/Library/Caches/Hey/run, compiler_sidecar_cache=$HEY_ROOT/build/compiler-sidecars, ...
hey cache clear --dry-run   # lists every entry it would remove
hey cache clear             # removes all Hey caches
rm -rf .hey-bin             # bin/hey-run's own build cache, in the site repo

Checked on 601a on 2026-10-14: hey cache path and hey cache clear --dry-run report the paths above. No poisoned entry was reproduced this time, so this is layout advice, not a re-test of the July failure.

Where Hey loses

On this job, as shipped since fb5fee2: nowhere on these two trees, though through bin/hey-run on the small tree it's close to a tie. With the September workaround it lost everywhere on today's tree, by 2.5×. Beyond them, long-list batch work is still Ruby's. The append table above is the re-measured reason, on 601a, today. The sibling source-zip port that first showed it was published here in July 2026 as Hey 66.5 ms against Ruby's 153.3 at 500 files, a tie at 2,000, and 2.16 s against 672 ms at 8,000, without the release it was measured on. (The project's findings log has a 402a run of the same port, 2026-07-24, with different figures and the same shape: Hey ahead at 500 files, behind from 2,000, Ruby 5× faster at 8,000.) It hasn't been re-run on 601a, so read those as July's numbers.

A rewrite mirroring the original's structure rather than tuning for speed.
byte-parity
Comparing outputs byte for byte, not “looks right”.
sidecar
A long-lived helper process that serviced stdlib calls for compiled programs in the July-era toolchain.
delegation
A compiled program handing a call to the interpreter instead of running it.
builtin
A primitive the compiler lowers straight to machine code.
worker pool
A fixed set of workers taking items from a shared queue.
exit code
The integer a process returns on termination; 0 means success, and doesn't mean the output is right.
run cache
Where the toolchain stores compiled artifacts for scripts already run (hey cache path prints it).
quadratic
Cost growing with the square of the input: double the items, four times the work.
