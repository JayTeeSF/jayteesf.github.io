The Argument That Refuted Itself

We argued, confidently and with receipts, that a single mechanism — the event loop — had to win on both platforms. It was wrong as stated. Its own commissioned literature research refuted the slogan; its own hardware, re-measured cleanly, crossed sides in the middle of the argument; and a design ruling made months earlier, for entirely different reasons, had already answered the real question. This is the story of how a claim survives being wrong, by being willing to say so out loud.

Scope: two boxes, not a law of nature

Status: the event-core mechanism discussed here is not in the shipping toolchain. The measured prototype is an opt-in branch, off by default, pending integration; the shipping server still uses the thread-per-connection path. This article documents a decision and its evidence, not a released feature.

Every measured number below comes from exactly two machines: one macOS (Darwin) box and one Linux box, run separately. Cross-OS numbers are never compared to each other directly — a rps figure from the Darwin box is not held up against a rps figure from the Linux box as if they measured the same thing. What travels between the two is ratios and directions (this mechanism ahead of that one, by roughly this much, on this box), never raw magnitudes. Literature numbers (kernel 2.6.x poll benchmarks, a WhatsApp fleet, a Netflix incident report) are cited as external context, tagged as such, and are never averaged in with either box's own measurements.

TL;DR

  • The claim: "the event loop must win, on both platforms." The first same-machine measurement of proto-vs-trunk at one worker put the poll-loop prototype at 0.582 of the thread-pool's throughput — a bad ratio, and it turned out to be measuring a stale ancestor build. Corrected, on a single binary with zero version skew, the honest number (Darwin box) is 0.765 — still behind, but the size of the gap itself was an artifact.
  • At four workers, the mechanisms cross: the poll loop wins — +3.8% throughput, better latency, holding the same connection load on 6 threads where the thread pool needed 70 (Darwin box).
  • The literature commissioned to back the slogan did the opposite. Every system that actually runs at million-connection scale — BEAM (WhatsApp's folklore claim of 2 million connections per box), Go, Java's Loom, Seastar — is lightweight units scheduled over an event core, not a pool of raw threads and not a hand-written event loop either.
  • Pariag and Brecht's 2007 re-measurement put events as well as or better, by up to ~18% at saturation, versus thread-per-connection, reversing an earlier parity finding from the same research lineage.
  • A thread-cost number the arguer had wrong, in public: an 8 MB per-thread stack figure is virtual address space, not memory actually touched — a cited measurement puts 10,000 idle threads at roughly 80 MiB of real (resident) memory, not the gigabytes the naive multiplication implies.
  • The deciding axis was never single-worker throughput. It was what a blocked connection costs to hold, and which of the two current mechanisms composes with where the language is already committed to end up.

1. The setup: what a blocked connection costs

A language that wants to run a million actors has to decide, somewhere, what it costs to hold a connection that has nothing to do right now — a client that sent a request and is waiting on the response, or one that opened a keep-alive socket and then went quiet. Get that answer wrong at small scale and nothing breaks; get it wrong at scale and the program cannot grow past a few tens of thousands of connections no matter how much hardware you throw at it.

Term: blocked connection

A blocked connection is a network connection whose next byte hasn't arrived yet, so whatever is "holding" it — an OS thread parked in a read call, an event-loop registration waiting for a readiness notification, a lightweight actor sitting idle — has nothing to do until data shows up. Example: a browser tab that opened a keep-alive HTTP connection and then sat idle for ten seconds while the user reads the page. Someone or something has to hold that connection's state for those ten seconds. This entire article is about what that someone-or-something should cost, and who should be it.

We measured two mechanisms head to head, on two machines: a thread-per-connection pool (one OS thread blocks on each live connection) against a poll-loop prototype (one thread services many connections by asking the kernel which ones are ready). and we argued the shape of the answer before the numbers were even in: the event loop had to win, on both platforms, because that is how you get to a million connections. The argument was confident. It had receipts. It was wrong as stated — and the correction came from two directions the arguer had set in motion itself.

Term: event loop

An event loop is a single thread that asks the operating system, in one call, which of many file descriptors are ready to read or write (via poll(), epoll, or kqueue), handles whichever ones are ready in small steps, and asks again. Example: nginx's worker process holding thousands of idle keep-alive connections on one core, without a thread per connection, by checking off ready sockets in a tight loop.

2. First reversal: the arguer's own literature refuted the slogan

Before leaning any further on the claim, we commissioned a literature review with explicit instructions to find the strongest case against its own position. The brief did its job. [SOURCE] Every system that actually operates at the million-connection scale — Erlang/OTP's BEAM (WhatsApp's often-repeated claim of 2 million connections per box, which the brief itself flags as folklore-grade and secondary, not a paper), Go's goroutines over its netpoller, Java's virtual threads under Project Loom, and Seastar — is lightweight units scheduled over an event-driven I/O core. Not a pool of raw OS threads (which categorically cannot reach a million: the cited 1M-task survey couldn't even spawn 100,000 raw threads on the test hardware). And not a hand-written event loop with per-connection state machines either — that is a real, workable stopgap, but every system that got to the finish line put a scheduler and a lightweight-task abstraction on top of it, so application code never has to be written as an explicit state machine.

Term: M:N scheduling

M:N scheduling means mapping M lightweight logical units (green threads, actors, goroutines) onto a much smaller number N of real OS threads, with a userspace scheduler doing the mapping instead of the kernel. Example: a million Go goroutines running across 8 OS threads on an 8-core box, or a BEAM VM scheduling millions of Erlang processes over one scheduler thread per core. It is the shape underneath every runtime in this section.

The harder number in the pile: Pariag and Brecht's EuroSys 2007 study [PAPER] re-ran the same research group's own earlier server (Capriccio, SOSP 2003) under tighter tuning, and reversed its predecessor's finding. Where Capriccio had argued threads and events reach parity, the harder-tuned event and pipeline servers performed as well as or better than thread-per-connection (Knot), by up to roughly 18% throughput at saturation. The reason had a number attached: Capriccio's user-level threading carried a measured 6.84–10.52% of profiled CPU spent on user-level scheduling — a tax that the event server paid 0.00% of. Even the best M:N threading library taxes you something, relative to a raw event core sitting directly underneath it.

So: neither of the two mechanisms actually on the table is the end-state shape. The thread pool has no event core and cannot reach a million connections by construction. The prototype has the event core but exposes it directly to application code as hand-rolled state machines, rather than hiding it behind a scheduler the way BEAM, Go, and Loom all do. Both are stopgaps — just stopgaps on different sides of the real fork in the road.

3. Second sharpening: a design ruling had already answered half the question

The real fork the literature exposes is: does application code eventually get to write ordinary, sequential-looking logic over a scheduler (the Go/BEAM/Loom shape), or does it write explicit state machines forever (the nginx/Envoy shape)? That choice is not a mechanism question at all — and it turns out to already have an answer on the books, made for unrelated reasons.

Term: run-to-completion

A run-to-completion task is one that, once started, runs straight through to the end of its current turn without ever suspending in the middle of a function to wait on something; if it needs to wait, it only does so at the very top, between turns, never mid-frame. Example: an Erlang process's message-handler function running start to finish before the next message is even looked at — contrast a thread that can call a blocking read() halfway through a loop and get swapped out with a half-finished stack frame still live.

A prior design ruling already settled this for the language in question: receive happens only at the top of an actor's turn — no mid-body suspension, ever. A state-machine transform workstream built around mid-turn suspension was struck for exactly this reason (a recorded maintainer ruling: top-only receive is the design). That ruling, made before either the literature brief or the clean hardware A/B existed, already points at the answer: the language's end state is run-to-completion actor turns scheduled over an event core — the same M:N shape every million-connection runtime converged on, minus the one piece none of them strictly required for their own scale claims: mid-turn suspension. The "block anywhere, like a thread" model that Go and Loom offer their programmers is off the table by design, not by oversight. Hand-written state machines are still fine — but only inside the runtime, as the plumbing under the scheduler, where application code never has to see them.

4. The measured receipts

4.1 A stale build, corrected in public

The first same-day A/B between the two mechanisms [MEASURED] ran interleaved, optimized, with proper repetitions (n=3/n=2, tight spreads) — and disclosed, in the same entry, a real confound: the prototype's branch was based on an ancestor build ten versions behind trunk. At one worker, sixteen connections: the thread pool ran 123,322 requests per second (p50 125 µs (microseconds)) against the prototype's 71,801 (p50 191 µs) — a ratio of 0.582, prototype to trunk. At four workers the two were statistically even on throughput (0.992) with the prototype actually ahead on latency (406 vs 447 µs p50). The entry that reported 0.582 said so itself: this is not yet mechanism-isolated, the version skew needs closing, and the honest number waits on a rebase.

The rebase happened. The corrected A/B ran on a single binary with both mechanisms behind an environment flag — zero version skew, same process, same build, interleaved A-B-B-A windows. [MEASURED] One worker, sixteen connections: thread pool 123.5K rps at p50 125 µs, prototype 94.4K rps at p50 138 µs (Darwin box) — ratio 0.765. Still behind, but the honest gap is smaller than the stale build made it look: nearly half (0.183 of the 0.418 gap, 44%) of the original 0.582-vs-0.765 shortfall was the ancestor build, not the mechanism.

4.2 The crossover at four workers

The same clean cell, pushed to four workers and sixty-four connections, is where the mechanisms swap places [MEASURED]: the poll-loop prototype wins — on the Darwin box, 151.0K rps against the thread pool's 145.2K (+3.8%), at a p50 of 370–372 µs against 414–430 µs (roughly 12% faster at the median), while holding that load on 6 threads where the thread pool needed 70.

Memory footprint mid-cell sat at roughly 2.0–2.1 GB in both lanes — retention turned out to be mechanism-independent at this scale, which is worth stating plainly because it means memory is not the axis this decision turns on. Thread count is. The mechanisms cross between one worker and four; whichever one "wins" at a given worker count is not, by itself, the deciding fact.

4.3 The thread-cost arithmetic, corrected

We had also, earlier, argued the thread pool's cost using an 8 MB-per-thread stack figure — overstating the case against threads, in the arguer's own later assessment. The correction, disclosed alongside the rest: that 8 MB is virtual address space reserved for a stack, not memory actually touched and resident. A cited measurement [SOURCE] puts 10,000 untouched-stack threads at roughly 80 MiB of real (resident) memory — nowhere near the tens of gigabytes naive multiplication implies. A second cited comparison [SOURCE] found Rust threads against Go goroutines at 10,000 workers apiece differ by only about 3× in resident memory, not the 100× a stack-size-only comparison would suggest. The million-actor argument survives this correction — the 1M-task survey still couldn't spawn 100,000 raw threads on its test hardware, while every green-thread runtime handled a million in 16–200 MB — but the per-thread arithmetic needed the correction, and it is worth recording that the person who overstated it is the one who corrected it in public.

One more measured wrinkle, local to this project rather than the literature [MEASURED], Darwin box: a separate idle-connection ladder found that the thread-pool server does not, in fact, hold idle keep-alive connections indefinitely — it closes them itself, on its own timeout, well before any of the theoretical thread-cost arguments would matter. Five hundred and twelve idle connections produced 518 OS threads at first, then collapsed to 6 threads within about 20 seconds, with every probe connection dead by 30 seconds of idle. "Memory per standing idle connection" is a number that is only well-defined inside that closing window — past it, the server has already let the connection go. That is a real, separate finding about this server's current keep-alive behavior, not a restatement of the thread-vs-event argument, and it is disclosed here because it bears directly on how much the thread-cost question actually costs in practice, today, on this build.

5. What could not be verified

The brief that refuted the original slogan was explicit about the limits of its own sourcing, and that honesty is the whole reason to trust the parts that are load-bearing. It survives into this article unedited, in kind:

Solidly grounded

Pariag/Brecht EuroSys 2007 (primary text extracted, numbers checked); the 1M-task spawn survey; the Loom pinning incident and its JEP 491 fix; SEDA's own 2010 retrospective retracting its 1999–2001 rationale; every [MEASURED] number in §4, produced on this project's own two boxes.

Could not be verified this round

The 2004 OLS epoll/poll/select paper would not text-extract — flagged unverified, not used for any number above. Drepper's linker-cost PDF likewise would not extract. JEP 444's own rationale text was reached only via secondary sources, not the primary JEP itself. The poll()-vs-epoll crossover figures (roughly 5–8% CPU under ~100–250 live file descriptors per loop, 15–22% at 400–600+) come from 2007-era kernels and are explicitly dated, needing local replication before they can be trusted at face value. The WhatsApp "2 million connections per box" figure is folklore-grade and secondary — widely repeated, never traced to a primary measurement in this research pass.

None of that unverified material was used to compute any ratio or percentage in §4. It is kept here, visibly, because a research brief that only reports what it's sure of and hides what it isn't is not more credible than one that shows its gaps — it is just quieter about them.

6. The payoff: three lines of evidence, one refined claim

Line up what actually decided this. It was not single-worker throughput — if it were, the w1c16 cell (thread pool ahead, 0.765) would have settled it, and the w4c64 cell (poll loop ahead, +3.8%) would then have to be treated as a contradiction rather than the second half of one consistent story. It was not memory, either — both mechanisms retained about the same 2.0–2.1 GB mid-cell. The two things that actually decided it were: what a blocked connection costs to hold (a thread that the kernel schedules, versus a small state record that a userspace scheduler holds), and which of the two current mechanisms composes with the shape the language is already committed to — run-to-completion actor turns over an event core.

Three independent lines of evidence converged on that answer, and none of them was built to agree with the others in advance. The commissioned literature review said the destination is M:N scheduling over an event core, full stop, regardless of which of today's two stopgaps wins this week's benchmark. The clean, zero-skew hardware A/B showed the two stopgaps trading places between one worker and four — which by itself proves that "one shape must win, on raw throughput" cannot be the right frame, since neither shape wins consistently even on a single box. And a design ruling made earlier, for reasons that had nothing to do with either the literature or this benchmark, had already fixed the language's turn-taking model to run-to-completion — which is the event-core-plus-scheduler shape minus mid-turn suspension, the exact combination the literature converged on independently.

The slogan — "the event loop must win, on both platforms" — died exactly as stated. What survived is smaller, more specific, and considerably harder to knock over: neither of the two things actually built today is the destination; the destination was already chosen for unrelated reasons; and the benchmark's job, from here, is to measure the cost of the connection you're holding, not to crown a winner at one worker count and stop looking.

Glossary

event loop
A single thread that polls many file descriptors for readiness and services whichever are ready, in small steps, before asking again.
M:N scheduling
Mapping M lightweight logical units onto N real OS threads via a userspace scheduler, rather than one OS thread per unit.
run-to-completion
A task model where a turn, once started, runs to its end without suspending mid-function; waiting happens only between turns.
blocked connection
A connection with no data currently available to read or write, and therefore nothing to do until some event arrives.
thread-per-connection
A server design that dedicates one OS thread to each live connection for its whole lifetime.
version skew
Comparing two builds that differ by more than the change under test — here, a prototype branch based on an ancestor build ten versions behind trunk.
resident memory (RSS)
Memory a process has actually touched and that occupies real physical pages, as opposed to virtual address space merely reserved.
keep-alive connection
An HTTP connection left open after a response, so a future request can reuse it without a new handshake.
