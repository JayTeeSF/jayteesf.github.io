Hey’s Arrays Now Tie C on Numbers. The String Wall Just Fell.

An immutable language changes an array by copying it. For fifty million writes that used to mean fifty million copies — and two of eight benchmarks timed out at full size. Here is what a flat, typed-storage rewrite bought on the numbers — and how the shipped compiler went on to close the string wall this article was first titled after, proven on the very same machine.

TL;DR

  • Verdict: rewriting Hey’s arrays from boxed per-element cells to flat, typed storage moved the numeric workloads from not-finishing to native class — two that timed out at full size now run, and the five numeric shapes beat Ruby with YJIT by roughly 10–19×. The string wall the original title named has since fallen on the shipped compiler: at 528a, re-measured on the same M3 Pro, both string workloads finish (~2.0 s) — but at ~4.5× C and a hair behind Ruby, so the constant-factor loss is stated straight.
  • Strongest result: in-place transform of a 50-million-element array went from timeout (>120 s) to 0.233 s — within 1.9× of C (0.123 s) and 14.7× faster than Ruby (3.417 s). Histogram over 100 million went 2.533 s → 0.145 s, a 17.5× self-speedup.
  • Mechanism: four changes, no new API. Flat i64/f64/bool storage instead of boxed cells; the element read and write inlined; strings borrowed on comparison; and an alias gate that lets an in-place write mutate the backing store when nothing else can see it, instead of cloning the whole array. Ordinary a[i] and put source, unchanged.
  • Ties, reported straight. Sum and search tie C before and after (1.02–1.03× after) — pure streaming, no array to fix. Hey stays 1.65–2.5× slower than C on the array and fannkuch shapes, and slower than Go on fannkuch.
  • Disclosed weakness, now bounded: on the campaign build (584147e6) the string-scan and mixed workloads did not finish at ten million — boxed string-array push copied the whole backing on every append (~38 s already at 100k). Later work made that append amortized, so on the shipped compiler both complete; the residual loss is a constant factor, not a curve. The build was never rescued by the string-borrow change — that speeds the element read, not the array build.
  • Falsifiability: every language prints byte-identical stdout, checked against the C oracle before any time is recorded; best-of-3 wall-clock on one Apple M3 Pro; sources under bench/src/<lang>/. Reproduce with bench/run_matrix.sh; the campaign numbers trace to bench/MATRIX_LOG_2026-08-17.md, and the shipped-compiler re-measure (528a, same M3 Pro, all eight verified against C) is the “the wall fell” table below.

How to read these numbers

Eight workloads, the same deterministic algorithm in each language, each printing one line of output that is checked byte-for-byte against the C result before any time counts. Sizes: 100 million elements for streaming shapes (sum, search, histogram), 50 million for the array shapes (transform, append), 10 million strings for the string shapes, and fannkuch-redux (a pancake-flipping permutation benchmark) at n = 11. Every time below is a lower bound in the usual sense — the fastest of three runs. Hey uses ordinary subscripts and put; there is no special fast-path API to call.

Why a write used to copy the whole array

Every value in Hey is immutable. You do not change an array; you produce a new array that differs from the old one. The transform benchmark says exactly that, in ordinary Hey:

set a = put(a, i, ((a[i] * 3) + 7) % 2147483647)

Read it literally and it is expensive: put returns a new array equal to a with index i replaced. On the old build the array was boxed — a vector of pointers, one heap cell per element — and each put copied the whole vector. One write is O(n); fifty million writes down the array is O(n²). At fifty million that is not slow, it is unfinished: the transform and the fannkuch workloads both ran past the 120-second timeout and were killed. To even measure the shape we had to shrink it: at fifty thousand elements the old build took 12.543 s on transform. The curve was the diagnosis.

What the rewrite changed

The fix is four independent levers, and none of them adds a keyword or an API. The programmer still writes a[i] and put; the compiler does more with them.

Flat, typed storage. When Hey can prove an array holds only 64-bit integers — or only floats, or only booleans — it stores them as a flat block of raw machine numbers instead of a vector of pointers to boxed cells. The proof runs at compile time and is conservative: if the element type is not proven a plain number, the array stays boxed and correct. On these workloads the fast path was taken throughout.

Inlined access. With flat storage, reading a[i] and writing an element become a single indexed load or store, emitted inline, rather than a call through the general boxed-array machinery.

The alias gate. This is the one that turns O(n²) into O(n) without touching the language’s meaning. set a = put(a, i, x) still means “a new array,” but when the compiler can prove the old a has no other live reader — nobody else can observe it — mutating the backing store in place is indistinguishable from allocating a fresh copy. So it mutates in place: O(1) per write. Value semantics are preserved because the optimization only fires when the copy would have been unobservable. The same gate makes push amortized O(1), which is why append at fifty million dropped from 0.778 s to 0.179 s.

String borrowing. Comparing and printing an array’s string element no longer forces a fresh owned copy of that string; the element is borrowed for the length of the read. This is what lifts the string scan — and, as the next section shows, it is also the lever that cannot save the string build.

The ties, reported straight

Sum and search did not move, and they were not supposed to. Both stream: they read the generator and accumulate, with no array to store, grow, or copy. There was nothing for the array rewrite to touch, so Hey after ties Hey before, and both tie C to within a couple of percent (1.02× and 1.03×). Search after is a hair slower than before — 0.118 s against 0.116 s — which is a tie inside the noise, and it is reported as one rather than rounded away.

Where Hey lost — and where it no longer does

On the campaign build, two workloads did not finish, and they mattered more than the wins for anyone deciding whether to trust the rest. Both build an array of ten million strings by appending:

set strs = push(strs, '' + (s % 1000))

A string array cannot be flat machine numbers, so it stays boxed. On build 584147e6 boxed push copied the whole backing on every append — the same O(n²) curve the numeric transform had, already about 38 s at a hundred thousand strings, so ten million was out of reach. The string-borrow lever could not rescue it: borrowing speeds the element read in the scan, but the cost was in the array build, before the scan begins. Right optimization, wrong phase. What did rescue it was later work on the append itself: the same alias gate that made numeric push amortized O(1) reached the boxed case too. On the shipped compiler the build is one linear pass, not a quadratic curve — and the next section proves it on the same machine that timed out here.

The loss that remains is a constant factor, not a wall. The string scan finishes, but Hey pays the full immutability tax on it: at 528a on this M3 Pro the scan takes 2.09 s against C’s 0.45 s (~4.6×) and a hair behind Ruby’s 1.46 s — a genuine loss, reported straight, now on time rather than as a did-not-finish.

Fannkuch is the smaller, honest loss. Hey completes it in 4.204 s: 6.45× faster than Ruby, but 2.51× slower than C and slower than Go’s 1.827 s. The rewrite made array permutation fast enough to be measurable, not fast enough to beat an optimizing native compiler.

What a reader can take from this

The useful lesson is not a leaderboard, it is a boundary that moved. An immutable-value language can reach C’s class on array code — ties on streaming, within about two times on mutation — provided two things hold: the element type is proven concrete enough to store flat, and the write can be proven unobservable so the copy can be elided. Where both hold, Hey runs ~10–19× past Ruby and beside C. The string case shows the boundary is not fixed: the “next wall” this article first named — make boxed-array append amortized O(1) the way the numeric path already is — is the wall that has since fallen, so ten million boxed strings now build in one linear pass instead of timing out. What is left on strings is a constant factor, not a curve: the element is still a heap object, so Hey lands ~4.5× C and just behind Ruby. That is the honest shape of an immutable language on this hardware — native class where the type goes flat and the copy elides, a bounded constant-factor tax where it cannot.

Terms used here

Boxed value
A value stored as a pointer to a heap object — one allocation per element — rather than inline as a raw machine number. A boxed array is a vector of such pointers; copying it copies the vector.
Flat / unboxed storage
Elements kept inline as raw machine numbers in one contiguous block. Reading or writing one is a single indexed load or store, and the block is proven safe only for concrete element types (i64, f64, bool).
Alias gate
The compile-time check that an array being replaced has no other live reader, so an in-place mutation is indistinguishable from allocating a fresh copy. It is what lets an immutable put or push run in O(1) without changing the language’s meaning.
O(n²) build
Growing an array by copying its entire backing on every append: n appends, each up to n long. It does not read as slow at small sizes and as unfinished at large ones — the same curve, two verdicts.
