Using third-party packages

A Hey package is a folder of Hey source with a version and a hash for every file. You list the ones you want, Hey picks versions, downloads them, checks every byte, and writes a lock file. Commit that lock, and every other machine gets exactly the same bytes, or nothing at all.

Badges: Works today Partly works Decided, coming Proposed (meanings in the index).

Every command here is run by Hey's documentation test against the live registry at https://www.jayteesf.com/packages/registry-v1.json, and its output must match. A line with ... stands for text left out: a folder that differs on your machine, or lines that don't matter here.

1. Why packages are locked and hashed

Think of a package download as a chain of signed receipts. Each link carries the SHA-256 fingerprint (a 64-character hash that changes completely if one byte changes) of the next link. Your lock file keeps a copy of every fingerprint.

So there are no "it worked on my machine" upgrades. A version that's in the lock can't silently change: a new download that reuses a locked name and version with different bytes is refused.1

2. Add a package to a new project

Works today

We'll use hey_cache, a read-through cache. Make a folder called pages_app with one file, hey-package.json:

{
  "name": "pages_app",
  "version": "0.1.0",
  "registry": "https://www.jayteesf.com/packages/registry-v1.json",
  "dependencies": {
    "hey_cache": "~0.1.0"
  }
}

Now ask Hey to resolve, download, check and lock:

$ cd pages_app
$ hey package ensure --project . --update-lock
ensured hey_cache@0.1.1 from project
updated ./hey.lock.json packages=1 edges=0
$ ls -a
.
..
.hey
hey-package.json
hey.lock.json

Two new things appeared:

FileWhat it isCommit it?
hey.lock.jsonThe exact version of every package (including the ones your packages need), and the hash of the registry entry, release file, archive, manifest, combined content and each file.Yes.
.hey/The downloaded, checked packages. Rebuilt from the lock any time.No. Add .hey/ and **/.hey/ to .gitignore.

When a package needs other packages, ensure fetches those too. Add hey_config to the same manifest:

{
  "name": "pages_app",
  "version": "0.1.0",
  "registry": "https://www.jayteesf.com/packages/registry-v1.json",
  "dependencies": {
    "hey_cache": "~0.1.0",
    "hey_config": "^0.1.0"
  }
}
$ cd pages_app
$ hey package ensure --project . --update-lock
ensured hey_cache@0.1.1 from project
ensured hey_packager@0.1.13 from hey_config
ensured hey_config@0.1.1 from project
updated ./hey.lock.json packages=3 edges=1

hey_config brought hey_packager with it. Here's one lock entry, shortened (the real one lists every file of hey_config with a hash each):

  "version": "0.1.1",
  "requirement": "^0.1.0",
  "direct": true,
  "archive": "https://www.jayteesf.com/packages/hey_config/0.1.1/hey_config-0.1.1.zip",
  "archive_sha256": "e2470d76ad3f8107b2952d3ff3e5422a823005d6e320d47d61be4e4a38f028db",

  "manifest_sha256": "7d5a4e0a642336e2897e9a4cb7a06af4bd2d72e5d59d6f193a2de743ef4e2215",
  "content_sha256": "853b13c2a441ba6757e5b524dc7d0f3185a0035355918ce612805b5403482d67",
  "file_sha256": { "src/main.hey": "cd02d024...e6010211", "README.md": "d59d81f2...6108f82f", ... },
  "modules": { "main": "src/main.hey" },
  "dependencies": { "hey_packager": ">=0.1.11 <0.2.0" }
}

The full catalog is at jayteesf.com/packages.

3. Version ranges

A requirement says which versions you'll accept. Hey picks the highest version that fits every requirement in the whole graph, and backs up when a later choice makes an earlier one impossible.

RequirementMeans
0.1.1exactly this one
~0.1.00.1.0 or a later patch release, below 0.2.0
^0.1.0compatible with 0.1.0 (caret)
0.1.*any 0.1 release (wildcard)
>=0.1.0 <0.2.0both comparisons must hold
0.1.0 || 0.1.1either one

Write all three numbers. The short forms ~0.1 and ^0.1 are refused. Try it in a second folder, ranges:

{
  "name": "ranges",
  "version": "0.1.0",
  "registry": "https://www.jayteesf.com/packages/registry-v1.json",
  "dependencies": {
    "hey_cache": "~0.1"
  }
}
$ cd ranges
$ hey package ensure --project . --update-lock
hey error: package_ensure_failed: package_resolution_failed: no hey_cache version satisfies ~0.1
...

When no version fits, ensure fails and your old lock stays as it was: it never writes half a graph.

4. Import it

A package's manifest gives each public file a short name (a module alias). hey_cache publishes main and cache. You import them by package, exact version and alias. Save this as pages_app/app.hey:

import 'pkg:hey_cache@0.1.1/cache'
import 'pkg:hey_cache@0.1.1/main'

fn render(key)
  says 'rendering ' + key
  return 'page:' + key
end

program
  let cache = HeyCache.open({
    namespace: 'pages',
    layers: [HeyCache.memory_layer('mem', {})],
    default_ttl_ms: 60000,
    clock: HeyCache.fixed_clock(1000),
  })
  let first = HeyCache.fetch(cache, 'home', render, {})
  let second = HeyCache.fetch(first.cache, 'home', render, {})
  says first.value
  says second.value
  says 'hey_cache ' + HeyCacheInfo.version()
end

Predict: fetch is called twice for 'home'. How many times does rendering home print?

$ cd pages_app
$ hey app.hey
rendering home
page:home
page:home
hey_cache 0.1.1

Once. The second fetch found the page in the memory layer. (It's first.cache, not cache: values don't change in Hey, so fetch hands back an updated cache along with the value.)

Each source file imports what it uses directly. Leave out the /cache import above and compilation stops with HeyCache.memory_layer requires a direct import in this source unit.

Partly works Modules in a package subfolder can't be imported yet. hey_cache's files sit at the package root, so it works. hey_config keeps its main module at src/main.hey, and the compiler looks for main.hey at the package root instead of reading the alias from the manifest:

import 'pkg:hey_config@0.1.1/main'

program
  says HeyConfig.layer('base', {}, []).name
end
$ cd pages_app
$ hey config.hey
hey error: could not open read file

Until that's fixed, use packages whose modules sit at the package root.

5. Restore exactly on another machine; verify; audit

Works today

On a second machine you have only what you committed: the manifest, the lock and your program. Here a fresh folder, machine2, plays that machine. --locked restores from the lock alone: it doesn't consult the registry's version list and can't change the lock.

$ mkdir machine2 && cp pages_app/hey-package.json pages_app/hey.lock.json pages_app/app.hey machine2/
$ cd machine2
$ hey package ensure --project . --locked
restored hey_cache@0.1.1 to ./.hey/.package-locked.../packages/hey_cache/0.1.1
restored hey_config@0.1.1 to ./.hey/.package-locked.../packages/hey_config/0.1.1
restored hey_packager@0.1.13 to ./.hey/.package-locked.../packages/hey_packager/0.1.13
restored locked project packages=3
$ cmp ../pages_app/hey.lock.json hey.lock.json && echo "lock unchanged"
lock unchanged

(The .package-locked... folder is a temporary staging name; the finished tree is moved into .hey/packages in one step, so a half-restored tree is never visible.)

Two checks, for two different questions:

$ cd machine2
$ hey package verify --project .     # offline: do the installed bytes match the lock?
verified hey_cache@0.1.1
verified hey_config@0.1.1
verified hey_packager@0.1.13
verified project packages=3
$ hey package audit --project .      # online: does the registry still serve the same releases?
verified hey_cache@0.1.1
verified hey_config@0.1.1
verified hey_packager@0.1.13
audited hey_cache@0.1.1 release/archive/content immutable
audited hey_config@0.1.1 release/archive/content immutable
audited hey_packager@0.1.13 release/archive/content immutable
audited project packages=3

Now tamper with an installed file and see who notices:

$ cd machine2
$ perl -pi -e "s/return '0.1.1'/return '6.6.6'/" .hey/packages/hey_cache/0.1.1/cache.hey
$ hey package verify --project .
hey error: package_project_verify_failed: installed_content_tampered: ./.hey/packages/hey_cache/0.1.1
...
$ hey build app.hey -o build/app
heyc: package module checksum mismatch: .hey/packages/hey_cache/0.1.1/cache.hey
heyc: file not found: pkg:hey_cache@0.1.1/cache
$ hey app.hey
rendering home
page:home
page:home
hey_cache 6.6.6

Partly works verify and hey build catch the change. hey app.hey runs the tampered code and prints hey_cache 6.6.6. Until the run path checks the lock too, run hey package verify in CI and build anything you ship with hey build. hey package ensure --project . --locked puts the original bytes back.

6. Commands that come with a package

Works today

A package can ship commands written in Hey. Make a project that depends on hey_secret_lint, plus a file with a password check in it:

{
  "name": "lint_app",
  "version": "0.1.0",
  "registry": "https://www.jayteesf.com/packages/registry-v1.json",
  "dependencies": {
    "hey_secret_lint": "0.1.2"
  }
}
fn admin?(supplied, expected)
  return supplied == ('Basic ' + expected)
end

program
  says admin?('Basic abc', 'abc')
end

Run ensure, and a new hey subcommand appears for this project:

$ cd lint
$ hey package ensure --project . --update-lock
ensured hey_packager@0.1.13 from hey_secret_lint
ensured hey_secret_lint@0.1.2 from project
updated ./hey.lock.json packages=2 edges=1
$ hey package commands --project .
secret-lint hey_secret_lint@0.1.2 bin/secret-lint.hey
$ hey secret-lint lintdemo; echo "exit status: $?"
lintdemo/login.hey:2: == on '('Basic ' + expected)' looks like a secret; use Crypto.constant_time_equal?(bytes(a), bytes(b))
secret-lint: 1 finding in 1 file (1 .hey file scanned)
exit status: 1

Why it flags this: == on two Strings stops at the first byte that differs, so how long it takes leaks how much of a secret an attacker guessed right. Crypto.constant_time_equal? always compares every byte.

Built-in commands can't be shadowed, two packages can't claim the same name, and Hey verifies the installed tree before each run of a package command. Guide 5 uses the TV packages' commands.

7. Packages with C inside

Works today with a build step you run yourself.

Some packages wrap a C library, for example hey_sqlite3, hey_postgres, hey_mysql and hey_zstd. They carry a hey.native.json file. Installing one proves its source bytes, not that its C half was compiled for your machine. You build that half once per target with the package's own bin/build-native, and point the app at the result:

$ .hey/packages/hey_sqlite3/0.5.2/bin/build-native --out build/native
$ HEY_SQLITE3_LIBRARY=build/native/libhey_sqlite3.dylib hey app.hey

Guide 4 builds and uses hey_sqlite3 step by step.

8. Write your own

Works today

$ hey package init demo_pkg --path $PWD/demo_pkg --description "A tiny demo package"
created Hey package demo_pkg@0.1.0
path=.../demo_pkg
packager=hey_packager@0.1.0
next: cd .../demo_pkg && bin/check
$ cat demo_pkg/src/main.hey
# A tiny demo package

module DemoPkg
  fn version()
    return '0.1.0'
  end

  fn hello()
    return 'hello from demo_pkg'
  end
end

You get the source, a spec, VERSION, hey-package.json, docs, and the scripts bin/check, bin/release, bin/publish, bin/package-zip and bin/source-zip. The scripts need to know where your Hey source checkout is, through HEY_ROOT; below, $TOOLCHAIN stands for that folder.

$ cd demo_pkg && HEY_ROOT=$TOOLCHAIN bin/check
PASS: demo_pkg basic contract
verified demo_pkg@0.1.0
manifest sha256 57d19658604f98771280e1021f0527b78f168032ded6121331e9741791c7569c
content sha256 bb7945697e1152b6ee13ab7bbcf6929588d42c8081d0d4ac924cdb0986a20d81
demo_pkg v0.1.0 checks passed

Every file you ship must be listed under "files" in the manifest, and every importable file under "modules". Released versions never change: new bytes need a new version. Releasing and publishing live in a separate package, hey_packager, so website policy stays out of Hey itself: bin/bump moves the version everywhere it's written, bin/release builds the ZIP, the release file and checksums under dist/, and bin/publish copies them into a registry folder and commits there (it never pushes).

Remember section 4: init puts your module at src/main.hey, which can't be imported through pkg: yet.

9. Known limits

  • pkg: imports of modules under a package subfolder fail (section 4). Packages with root-level modules work.
  • hey file.hey runs package code that no longer matches the lock (section 5). Run hey package verify in CI and ship with hey build.
  • Two-number ranges such as ~0.1 are refused (section 3). Write ~0.1.0.
  • The scripts hey package init generates need HEY_ROOT set to your Hey source checkout.
