The Server That Answered 200 and Sent Nothing

I spent a morning measuring what a web framework layer costs, and got a beautiful answer: 0.2%. A framework that costs nothing is a wonderful result. A framework that costs nothing because it is not doing anything is a different article, and this is that article.

TL;DR

  • The documented way to start a Hey web service returns HTTP 200 with a zero-byte body — your handler never runs. Same route, same machine, the other spelling served 364 bytes. Measured on macOS and Linux, versions 0.99.459a / 460a.
  • The shorthand works. The standard library defines Web.serve(routes, options) as exactly Web.start(Web.service(routes, options)). Calling it serves the page. Writing out its own body does not.
  • Cause measured, not guessed: the documented form's listening socket is owned by a helper process that has never seen your routes. Both spellings compile into a delegation that round-trips values through JSON, and that mechanism's own written rule excludes exactly the live sockets the service descriptor holds.
  • Disclosed weakness: this cost me a whole performance table. My gate asserted status 200 and a zero error rate. Both were true, and both are blind to an empty body.
  • Reproduce it in two files that differ only in how the server is started, then read content-length instead of the status line. That is the whole test, and it is the one I did not have.

A number too good to be true

The job was ordinary: what does the web framework package cost against the standard library's HTTP support? I ran both lanes at matched load, asserted 200 with a success rate of 1.000, and read off the difference. 0.2%. I nearly wrote it up.

The control lane saved it — the bare standard-library server, same route, same payload, 364 bytes. The framework lane returned content-length: 0. I had spent the morning comparing something doing the work against something doing none of it, and my gate waved it through, because a server that does nothing is extremely good at returning 200.

Then it stopped being a harness bug

The obvious next suspect was my harness. It was not. The empty response depends on how the server is started, and nothing else:

Web.serve(stack)empty list200, body served
Web.serve(stack)error recovery200, body served
Web.start(Web.service(stack))empty list200, content-length 0

Web.start(Web.service(stack))error recovery500, error JSON

That last row is the tell: error-recovery middleware does not cause the failure, it makes an already-failing path audible. And here is the part that reads like a typo. The standard library defines the working call in terms of the broken pair: 

fn serve(routes, options)
  return Web.start(Web.service(routes, options))
end

Calling serve works. Writing out the two lines that are serve does not. Whatever is wrong is not in the logic — it is in what the compiler does with those names.

What the compiler does with those names

Certain standard-library calls are not compiled into direct machine code. They are emitted as a delegation: arguments are serialised, the real implementation runs, and the result comes back — through JSON. The compiler's source states the rule for that mechanism in a comment, immediately above one of the two name lists that use it: 

/* Keep real socket/process/runtime builtins on dedicated shims;
 * delegate descriptor, parser, and formatting facades that
 * round-trip through JSON exactly. */

That is a precondition, and it is a good one: only values that survive a JSON round-trip may take this path. Now look at what the service descriptor contains — a live listening socket and a live worker pool: 

let listener = Web.listener(host, port, options)
let pool = Net.worker_pool(listener, workers, options)
return {kind: 'web_service', listener: listener, worker_pool: pool, ...}

Live handles are the one thing the rule excludes, and they are on the delegated lists anyway. There are two such lists sharing one delegation function; the rule is written above the second, while Web.service sits on the first, which carries no comment at all. They share the mechanism without sharing the warning — and the governed list holds a live thread pool of its own.

Web.serve is on the same list and is fine, because it hands back the result of serving rather than a live handle for someone to use later. The question was never which list you are on. It is whether anything living has to survive the trip.

Who is actually answering the request

For a day that was where the trail ended. Everything above is read out of the source; the last step — that the violated precondition is what empties the response — was an inference, and nobody had watched a listener die in transit.

Nothing dies in transit. The listener is never in your program at all. Delegated calls run in a helper process, so when Web.service is delegated the socket is created and held there. Ask the operating system who owns the listening port: 

broken lane, port 8840        200, content-length 0
  heyc  24808  TCP *:8840 (LISTEN)      <- the helper process owns it
  24803 ./svc_8840.bin
  24808 └ heyc stdlib-sidecar-loop

working lane, port 8841       200, content-length 364
  serve_8841.bin  24892  TCP *:8841 (LISTEN)   <- your program owns it
  24892 ./serve_8841.bin
  24897 └ heyc stdlib-sidecar-loop      <- exists, holds no socket

Your program receives JSON: a descriptor whose listener and worker pool are now inert data. The process accepting connections is the helper, which has never heard of your routes. A 200 with nothing in it is exactly what that arrangement should produce.

The control that makes it mean something

The working lane spawns the same helper process and serves the full 364 bytes. So “delegation is running” does not predict the failure — only which process ends up holding the socket does. Written down before the run: if the program itself owned the socket in both lanes, this explanation was dead. Two replicates, both lanes, one machine, version 0.99.465a.

Why this is worse than a bug report

The documentation teaches the broken form first — build the descriptor, then consume it, with the shorthand offered further down “for the common case” — so a developer reading top to bottom writes the failing version. The page even asserts the exact property the implementation lacks: “Web.service is not decorative metadata. Web.start validates and executes it.” And the web framework package built on the standard library starts its servers the same way, so as shipped it does not serve real responses. Our three production apps all use the shorthand, which is why this survived: everything anyone actually ran was on the working path.

What we withdrew

Every framework-layer number from that morning is withdrawn: that the layer costs 0.2%, that request IDs and request logging are free, that security headers cost 38%, and the inline-versus-middleware comparison. All were measured against empty responses, and there is no salvaging a ratio whose numerator was a server declining to work.

Then I re-read all 289 archived measurement cells looking for the same contamination. Five had empty bodies; all five were overload responses already excluded for being overload responses. No published number was affected. The archive's empty responses were loud. This class is silent, which is the only reason it needed finding.

The two rules that came out of it

Assert the bytes, not the status. A status code tells you a server replied, not that it did anything. Every web measurement we take now asserts a body length and a marker from the page, and a cell that cannot produce them is void rather than fast. A dead server does a superb impression of a quick one.

A rule in a comment is not a check. The precondition was written down accurately by someone who understood it — and then functions that violate it were added to the list anyway. Membership is mechanically checkable: require every delegated name to survive a JSON round-trip in a test, and the check refuses Web.service the moment it is added. That gate does not exist yet, and I want it before the fix that makes this particular call work.

Behaviour measured at 0.99.459a and 0.99.460a on macOS (Apple silicon) and Linux (kernel 7.1.4, i7-1165G7); source facts and the socket-ownership cell re-run at 0.99.465a on macOS, two replicates per lane. The ownership half has not been run on Linux; one command would settle it there. Found on the measurement seat, traced jointly with the Linux seat, each half confirmed on the other's machine.
