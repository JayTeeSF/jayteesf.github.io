Waiting on you — two things, both needed before a parser is written

1  What does not bind to?

not a == b

  some parts of the system read it as   (not a) == b
  others read it as                     not (a == b)
  the language reference says            a third thing

Three different answers ship today, and the documentation asserts a position none of them takes. This is the one place where writing the rule down changes the language — we can't record a fact that doesn't exist yet.

It has to be settled before the new parser is written, because the parser is what makes it one answer.

2  Are keyword arguments a real feature?

tasks.map(work, workers: 4)      used about 1,900 times

  but there is no rule for `name: value` anywhere in the language.
  it works because two built-ins re-read their own raw text,
  including a hard-coded check for the word "workers:".

  so a function YOU write cannot take one.

It looks like a feature, it's used throughout, and it isn't in the language. Make it real, or remove it and change the ~1,900 call sites?

This is also the root of the bug where workers: 4 fails in your own site tooling. Same cause.

What “done” means

fast web servers   at the per-core bar
fannkuch
1BRC

Three benchmarks. When the restructured language runs all three at or above where they run today, we're probably ready. Nothing else counts as an exit criterion — no phase is finished because it feels finished.

Then the existing apps get ported: iOS, Android, AppleTV, web servers, web clients, actors. That's its own milestone, and those apps are simultaneously the thing at risk and the best regression suite a new language could have.

One path, not five

Hey source → tokens → syntax tree → HIR → MIR → machine code

One pathway serving both compiling and the interpreter. No doubled-up paths. Nearly every problem found this week is an instance of the same thing — one decision made in several places that disagree: 45-plus places deciding precedence, 28 deciding what counts as a name, two code generators, one of which cannot do division at all.

The order is yours: specs first, then remove the duplicate paths. A path is deleted only once the tests that pin its behaviour exist and are proven able to fail.

Function names read like sentences

read_source_text_into_tokens(source_text)
group_tokens_into_expression_tree(tokens)
can_this_operator_be_overridden?(symbol)

not:   lex()    parse()    process_data()

Verb first, name the input and the output, no abbreviations, questions end in ? — so anyone can read the diagrams and jump straight to the right part of the code.

Binding on all new code. The name is the only documentation that cannot go stale, because it travels with every call site.

Ruby drives the tests; it does not define the language

While we rebuild, the new version cannot be its own answer key — and “matches the old one” would pin the bugs along with the behaviour. So something outside both computes the expected value and checks ours against it.

This is not a statement that Hey should equal Ruby. Where you have deliberately chosen differently — division rounding, for one — the driver simply is not consulted. Three other candidate tools were rejected by measurement, not taste: one has no decimals at all, one answered a large multiplication wrongly and reported success, and one could not reproduce a standard floating-point result.

Your version is pinned, and we build the new one separately

git checkout stable          ← what you run; only moves when you say so
last-known-good-2026-08-02   ← the same commit, as a permanent tag

Your checkout is on stable now rather than on our deploy branch, so nothing we push can move it under you. The tag's message lists everything known broken at that point, with workarounds, so you don't rediscover them.

The restructured language is built on separate branches. Nothing touches your version until you ask — and when it does, the existing apps have to be ported, which is its own milestone.

Hey gets a real front end

There is currently no parser. Expressions are carried as plain text and re-read by later stages; a four-pass rewriter runs over the source first and one of its passes deletes lines, which is why error locations can't be trusted.

The new pipeline is Hey source → tokens → syntax tree → HIR → MIR → machine code, one path serving both compiling and the interactive shell. The runtime and the code generator are kept; the front end is new.

How decimals print

says 100.0                  1e2  →  100.0
says 100000000000000.0      exactly what Ruby prints

Ruby's real rule, not “whichever is shorter” — the two disagree above about a hundred trillion, and we checked Ruby's actual behaviour against 2,000 random numbers rather than assuming it.

When a number gets too big

9223372036854775807 + 1   →   9223372036854775808

Your design: ask the chip whether it overflowed — it already knows — and redo that one calculation in a wider type. Almost always no, so almost always free. That's how Ruby and JavaScript engines actually do it, and all three of my original options were worse.

Negative division stays as it is

-7 / 2   is   -3

Rounds toward zero, like C and Go. Ruby says -4. You reversed an earlier choice here after it measured at 15% slower on the benchmark that certifies our speed. Ruby's version is available on request — see Overrides.

Reversing it also removed a real bug: our benchmark's averaging code rounds on top of the current behaviour, and Ruby's version would have made it compute wrong averages silently.

Overrides are per-file, and cost nothing unless you ask

import "stdlib:RubyMath"              → RubyMath.div(-7,2) to compare
import "stdlib:RubyMath" exposing *   → this file gets Ruby's math

A file that asks gets Ruby's arithmetic. Libraries it calls keep the behaviour they were written and tested against. The system will report every override in effect.

Known trade, taken knowingly: the number-one documented reason nobody uses Ruby's equivalent feature is having to write the import in every file. We took the safe option over the convenient one. Revisit if the friction bites.

How you write an operator

fn add(a, b) ... end
exposes add infix: '+'

You never name a function +. You name it something pronounceable and declare the symbol separately — so an error says add failed, not + failed, and a stack trace has a word in it. Redefining + still works; you just keep the name.

Precedence comes from the symbol, never from the module. Two languages that let modules set precedence were tested: an import silently changed how an expression parsed, with no warning.

Function names

ok?     yes     already used by 217 stdlib functions
save!   yes     newly decided; it was previously undefined
?       no      a name can't be only punctuation
2       no      a digit can't start a name

The last one is what stops 3.2 being ambiguous with a call to a function named 2.

Dividing by zero

1   / 0     stops with an error     ← shipped
1.0 / 0.0   Infinity
inf.to_i()  stops with an error

Whole numbers and decimals differ on purpose — that's what Ruby does and what the floating-point standard requires. Infinity is a real decimal value; no whole number means it, so that's where it stops.

One bug must be fixed first: Infinity inside JSON output currently writes a wrong number instead of failing.
