Acknowledging RAM: What a Durable Log Actually Costs

There is a gap between “we replied ok” and “those bytes survive a power cut,” and it is invisible until the one moment it matters. We shipped a bug in that gap and fixed it this session. The fix cost 4× throughput — which is the honest shape of this entire subject, because the fast number had been measuring a lie.

Status: 0.2.0, local-durable only, not yet integrated

hey_durable_log 0.2.0 is a packaged, gated C storage core with a Hey write path. Its guarantees are local-disk: process crash, OS crash and power loss on this host. There is no replication, no segment rotation, and no position back-link in the frame header yet. The benchmark host was contaminated by concurrent load and we have not run a power-cut test on this hardware. Everything in the comparison section is read from primary source at a pinned upstream tag; nothing in it was re-benchmarked here except SQLite. Read the limits before quoting any of it.

TL;DR

  • We acknowledged on a barrier that does not reach the platters. macOS's own fsync(2) page says that after it returns “the drive itself may not physically write the data to the platters for quite some time,” and that on power loss “the application may find that only some or none of their data was written.” We were calling fdatasync. Switching to fcntl(F_FULLFSYNC) took us from 3,602 records/s to 888 records/s at 8 writers. Same code, same host, same parameters. The 3,602 was not a measurement of durability.
  • One barrier is the unit of cost, so batch into it. Group commit is worth 22.3–23.0× at a batch of 32, and p50 latency falls from 131–260 ms to 5–13 ms as batching rises. 3,200 records need 3,200 device flushes one at a time and about 104 batched.
  • Above two concurrent writers this journal beats SQLite; at one writer it loses. Measured on Linux with both engines on the same fdatasync barrier: 0.78× at 1 writer, 8.08× at 8, 30.51× at 32 — and SQLite’s p99 at 32 writers is 532 ms against this journal’s 2.5 ms. SQLite gets slower as writers arrive. See The comparison, done properly.
  • “SQLite is slow” is false as a blanket claim, and that is still the most important thing in this article. With fullfsync off, SQLite does 23,354 rows/s single-writer and beats this broker outright. The comparison only inverts once a real barrier is required, where SQLite goes 83.4 → 77.0 → 66.2 txn/s at 1 → 4 → 8 writers — throughput falling. A benchmark that does not state which barrier both sides used is not a statement about durability.
  • Where we are stronger: per-frame checksums (neither Redis nor Valkey has any on the AOF record path — a payload bit flip is silently replayed as data); a bounded queue with real backpressure (Redis's aof_buf is unbounded and explicitly excluded from maxmemory); and failing closed on a complete corrupt frame, where SQLite's recovery treats a torn tail and a corrupt frame identically and discards silently with no error.
  • Where we are weaker, plainly: no replication of any kind, against etcd's consensus and Kafka's ISR; no segment rotation, so the journal grows; and no position back-link, where PostgreSQL's xl_prev is — in Tom Lane's words — “our ONLY defense against replaying stale data.” Ours chains CRC values, which is position-independent, so we do not have that defence.

Movement I — What it costs to acknowledge RAM

Every service that writes something down has one line in it that decides everything else about its failure modes: the point at which it tells the caller yes. Before that line, a crash is a non-event — the caller retries and nothing was promised. After that line, a crash that loses the write is a broken promise, and no amount of later cleverness repairs it.

The trouble is that the line is drawn in code that looks nothing like a promise. It is a write() that returned the right number of bytes. It is an fsync() that returned zero. It is a library call whose documentation used the word “durable” and was, at the level of the sentence, telling the truth.

A record you have written passes through at least four custodians on its way to being real, and each one will happily tell you it has the data while holding it somewhere volatile:

  • Your process's own buffer. Lost on SIGKILL.
  • The kernel page cache, after write() returns. Survives your process dying. Lost on OS crash or power loss.
  • The storage device's volatile write cache, after a plain fsync/fdatasync on some platforms. Survives an OS crash. Lost on power loss.
  • Non-volatile media. The only one of the four that is what anybody meant.

Three of those four look identical from the caller's side. All four return success. All four are fast, and the wrong three are faster, which is the trap: the incentive gradient points directly at the bug, and every benchmark you run rewards you for having it.

The bug we shipped

Our acknowledgement rule was already written down and already gated: an append returns only after its DATA frames are written, its COMMIT frame is written, and the durability barrier returns. What we had wrong was which call is the barrier.

On Linux, fdatasync is a barrier. On Darwin it is not, and Apple says so in the platform's own manual page for fsync(2) — not in a mailing-list thread, not in a blog post, in the man page you get by typing man 2 fsync:

man 2 fsync, Darwin 25.6.0

After fsync returns, “the drive itself may not physically write the data to the platters for quite some time.” On power loss, “the application may find that only some or none of their data was written.” And, in the platform vendor's own words: “this is not a theoretical edge case.”

That last sentence is the platform vendor pre-emptively refusing the excuse. We had built a journal whose entire reason for existing is that acknowledgement must not be a lie, and on the development platform the acknowledgement was a lie — the same defect as acknowledging RAM, one layer down. Commit e7f9ca4 switched the Darwin barrier to fcntl(fd, F_FULLFSYNC).

What correctness cost, exactly

Same host, same code, same parameters — 8 writers, 250 records each, max_batch 64, 250 µs window:

A 4× regression, published as a regression. There is no way to present this as an improvement and there should not be: the fast number was measuring a lie, and the correct response to discovering your benchmark was measuring the wrong thing is to publish the slower, true one.

The generalisation is worth stating as a rule, because it survives this specific bug: a throughput number for a durable system is uninterpretable unless it states which barrier it used. Two builds of the same software on the same laptop can differ by 4× on nothing but that question, and the faster one is not better. We will return to this in the comparison, because it is also the single fairest thing that can be said about SQLite.

Two ways to make the barrier honest, and we needed both

Picking the right call is only half of it. The other half is refusing to quietly pick a different one. hdl_sync_barrier_name() is a public function that reports which barrier this build issues, and the recovery gate asserts it per platform — so the stated promise cannot drift away from the code without a test going red. A filesystem that refuses F_FULLFSYNC gets the error returned and the batch is not acknowledged. There is no silent fallback to a weaker barrier, because degrading silently would leave the promise stated and unmet, which is worse than never making it.

The second half is what happens after a barrier fails, and here we had a gate asserting the wrong thing. Our test required that an append following a failed sync return HDL_OK. That is the fsyncgate defect exactly: continuing to acknowledge on a descriptor whose fsync has already failed. PostgreSQL's answer, after the 2018 incident, was to PANIC. Ours is to poison the handle.

Poisoned

A handle whose durability barrier has failed. Further appends return HDL_POISONED rather than an acknowledgement. Reads still work — you may still need to get data out. Only a reopen, which re-runs recovery, clears it. A failed write deliberately does not poison: the bytes did not all reach the file, the batch is rolled back, and the handle is provably back where it started. That distinction is itself gated.

Inverting a gate is not a refactor. A test that asserts the opposite of what it used to assert is either a bug fix or a regression, and the difference is a judgement someone has to make and record. So it was recorded, as a decision document (poison-the-log-after-a-failed-durability-barrier), before the assertion was flipped — commit c9fee2a.

Worth knowing about the PANIC-on-fsync-failure answer: it is necessary but not sufficient. Rebello et al. (USENIX ATC '20) showed that ext4 in data=journal mode reports the error one fsync late, and measured that mounting with errors=remount-ro does not rescue it. We inherit that problem too; poisoning does not solve it.

Movement II — How this one works

The design is small on purpose. There are four moving parts: a byte format that makes damage detectable, an acknowledgement boundary that sits after the barrier and nowhere else, a broker that amortises the barrier across concurrent callers, and a recovery scan that makes exactly one of three decisions about what it finds.

The frame format, and where a lie could hide

The format is explicitly little-endian and never writes native C structs — a journal whose layout depends on your compiler's padding rules is a journal that cannot be read by the process that has to recover it. Three structures, and all the recovery rules fall out of them.

On-disk format v1. Full field table in docs/FORMAT.md.
StructureSizeWhat it carries
Segment header64 bytes HDLGv001 magic (8), header size (4), format version (4), segment generation (8), creation time in Unix nanoseconds (8), 28 reserved zero bytes, and a CRC32 of bytes 0–59 at offset 60. The creating process writes the header, synchronises it, and synchronises the parent directory, all before the segment may accept a single mutation.
Frame header48 bytes HDLF magic (4), version (2), type — DATA=1 or COMMIT=2 (2), complete frame length (4), payload length (4), sequence (8), batch id (8), stream id (8), the preceding frame's CRC32 at offset 40, and at offset 44 a CRC32 over the header with that last field zeroed followed by the payload.
Commit payload24 bytes First sequence (8), last sequence (8), DATA-frame count (4), and a CRC32 over the ordered DATA-frame CRC values (4). A COMMIT frame therefore states how many records it is claiming and fingerprints the exact set.

Two properties of that layout do most of the work. First, every frame carries its own checksum, so a flipped payload bit is a detectable event rather than a record. Second, the previous-frame CRC makes deletion and reordering detectable too, not just accidental damage — you cannot excise a frame from the middle and leave a chain that validates. It is not a cryptographic authentication mechanism and we do not claim it as one; an adversary with write access can recompute the whole chain. It is a defence against damage, not against malice.

Because those sizes are fixed and documented, the first record's payload byte is at offset 64 + 48 = 112. That number matters in a moment, because our corruption spec writes a single byte there.

The acknowledgement boundary, in Hey

  • max_batch_records — the most records one durability barrier may be amortised across. At the limit, the batch closes and syncs.
  • batch_window_microseconds — how long the writer waits to collect a batch before closing it.

From examples/quickstart.hey, which is executed as written. A journal that accepted queue_capacity: 0 and substituted 4096 would be running with a bound its caller never chose and does not know about — which is precisely how an unbounded-growth incident starts, with everyone believing a number that was never in force. So it is refused, as durable_log_open_invalid.

Now the append. The important word in the following snippet is only.

A receipt describes durability that has already happened. It is not a promise about the future and there is nothing to poll.

The four receipt fields, and why each is a named value rather than an implied one:

  • sequence — the record's identity in this journal. Dense and monotonic from 1, so a consumer can detect a gap. It continues across a clean close and reopen and never restarts; restarting it would hand two different records the same identity, which is the exact thing a consumer uses sequence numbers to prevent.
  • batch_id — which durable batch carried the record. Several records share one batch_id when group commit combines them, which under load is the normal and desirable case. It is how you can tell, from the outside, that amortisation happened.
  • durable_offset — how far the journal is durable, in bytes. Strictly advancing. A receipt reporting a non-advancing offset would be describing bytes that are not there, so the spec asserts the inequality directly.
  • durability — the guarantee actually achieved. Today it is always local_durable. It is a field rather than an assumption so that a future stronger level is a value your code can branch on, not a silent redefinition of what the old value meant.

local_durable means local

It survives process crash, OS crash and power loss on this machine. It does not survive loss of the host or the disk. That requires quorum replication before acknowledgement, which is not implemented. DurableLog.capabilities() reports quorum_replication as false, and a spec asserts that it stays false until it is real — a package must not advertise a durability it does not have.

Group commit: one barrier, many callers

A device flush costs about the same whether it carries one record or thirty-two. That single fact is the whole economics of this design. hdl_broker_submit feeds a bounded in-memory queue; one writer thread drains it, combines whatever concurrent requests are pending into a single durable batch — DATA frames, then one COMMIT frame, then one barrier — and releases every receipt in that batch together.

The number this design cannot improve

Single-writer throughput is 1 / barrier_cost and nothing else: 102 records/s against a ~10 ms flush on this host. No batching setting changes it, because there is nothing to batch with. This journal cannot help a single-writer workload. Its entire value is amortising one barrier across concurrent callers, and a workspace with one active agent gains nothing at all from it.

What these numbers are not. The host was contaminated — five research subagents and repeated C builds were running on the same laptop, and every condition got monotonically faster from round 1 to round 3 by roughly 2× as that load drained. The absolute figures are a floor. The ratios within an interleaved round are the trustworthy part, because interleaving exposes every condition to the same drift. Specifically not supported by this data: any claim that batch 64 differs from batch 32. It wins one round, loses one, and ties one, and with 32 writers the achieved batch is ~31 either way, so the setting is not binding. An earlier single-shot sweep appeared to show batch 32 beating batch 64 by 2.5×; the interleaved repeats refute that. It was drift.

The test barrier needed its own test

The group-commit gate proves “fewer durable batches than records,” and it can only prove that if the writer threads genuinely contend — which is a test barrier's job. pthread_barrier_t is an optional POSIX feature that Darwin does not provide, so the gate did not build on this platform at all until a shim supplied a cycling mutex/condition-variable barrier where the real one is absent. That shim has its own gate, because a barrier that released early would leave the group-commit proof passing on timing luck rather than on group commit — a green test measuring nothing, which is the failure mode this whole article is about, one level up.

Recovery makes exactly one of three decisions

Reopen the same path and recovery runs automatically. It validates the segment header, every complete frame, sequence and batch monotonicity, the previous-frame chain, and the commit summary — and then it does one of three things. The difference between the first two is the whole design.

What is on diskWhat recovery doesWhat the caller sees
A physically short final frame, or complete valid DATA frames with no following COMMIT Truncates back to the last committed boundary open succeeds; the committed prefix is intact
A complete frame whose checksum fails Fails closed. Never silently skipped durable_log_open_corruption
Anything else that stops the open Fails closed, with the reason durable_log_open_io, durable_log_open_invalid

The rule underneath the table is one sentence: a torn tail was never acknowledged, so discarding it loses nothing anyone was promised; a complete-but-damaged frame was acknowledged, so discarding it would silently lose a mutation someone was told had succeeded. Those two must never be confused, and skipping the second would silently publish a prefix the writer never acknowledged.

Both halves are gated, and the corruption spec is deliberately precise about which case it is creating. It writes one byte at offset 112 — the first payload byte of the first DATA frame, which is followed by a valid COMMIT. The frame stays physically complete; only its CRC breaks. That is what distinguishes it from a torn tail, which is legally truncatable.

Replay cursors, and why they refuse to grow

A replay cursor snapshots the last validated COMMIT boundary at the moment it opens, then streams one record at a time up to that snapshot and stops. Records appended later are invisible to it by design.

That sounds like a limitation and is actually the safety property. A cursor that quietly extended itself to whatever is now on disk would expose a half-written batch at exactly the wrong moment, and the bug would only appear under load. Because the cursor cannot observe anything committed after it opened, it cannot observe a batch that is still being written. A materialiser applies a finite, committed prefix and then opens another cursor.

The first of those refusals is the one people argue about, so it is worth defending. The library fallback chain — explicit library_path, then HEY_DURABLE_LOG_LIBRARY, then .hey/native/…, then .native-build/… — is exactly right when the caller expressed no preference. It is exactly wrong when they did. A caller who names a build is choosing which code writes their bytes. Silently loading a different one because the named one is absent makes the durability of every subsequent write depend on ambient environment state the caller did not choose, and does it without a word of warning. Commit 2f5a81d made that a refusal.

The one failure no journal can fix for you

If your caller crashed, timed out, or lost its connection after the COMMIT was made durable but before it saw the receipt, then the mutation is in the journal and the caller does not know it. Recovery finds a complete, correctly-committed batch and retains it, which is the only correct thing it can do — the writer was, at the moment of the crash, entitled to that acknowledgement.

No journal closes this gap, and it is worth being blunt about why: the failure is in the space between “durable” and “told you so,” which is outside the journal. Adding a cleverer format does not help. Adding replication does not help; it moves the gap, it does not close it. An error, a timeout, or a lost response is not proof that the mutation was absent.

The only correct resolution is application idempotency: give each mutation a caller-supplied idempotency key, and on retry make the second attempt observe the first one's effect instead of duplicating it. Design that in before you take traffic, not after you have two of something. This is the one place where a durability library's honest answer is “this is your problem, and here is exactly why it has to be.”

Movement III — How everyone else draws the same line

Five systems, read at pinned upstream tags rather than from memory or documentation: Redis (8.10.1), Valkey (9.1.2), PostgreSQL (REL_18_6), SQLite, and etcd/Kafka. The interesting result is not that we win somewhere. It is that every one of these systems draws the acknowledgement line somewhere defensible and somewhere surprising, and several of them draw it in a place their users do not expect.

Read this before you read the table: “SQLite is slow” is false

This is the intellectual heart of the comparison and it goes against us, so it goes first.

Update, same day. Everything in this box is still true, and it was still not a fair comparison — because I had diagnosed the unfairness only halfway. The numbers below put a real device flush on one side and an ordering barrier on the other. Once both sides are held to the same barrier, on Linux, the answer flips above two writers. The corrected measurement is in The comparison, done properly; this box is kept as written rather than quietly edited.

With fullfsync off, SQLite does 23,354 rows/s single-writer and 13,043 txn/s at 8 writers, at a p99 of 0.09 ms. That is not close to our broker. That beats our broker outright, by more than an order of magnitude. Anybody who tells you SQLite is a slow database has not measured one.

That comparison is not fair to us, and it is not meant to be — it is the exact unequal-barrier comparison this article exists to warn about, put here deliberately with a label on it, because it is the shape every misleading durability benchmark has.

The comparison only inverts once a real barrier is required. With fullfsync on, SQLite goes 83.4 → 77.0 → 66.2 transactions/s at 1 → 4 → 8 writers. Read that again: throughput falls as concurrency rises. p99 goes from 9.9 ms to 215 ms to 480 ms, and SQLITE_BUSY stays at zero throughout — so the symptom is latency, not an error a caller can retry on. The cause is structural: a WAL writer holds the exclusive WAL_WRITE_LOCK across its fsync, so the durable commit rate is 1 / barrier_cost and does not improve with writers. SQLite has no group commit, and that is not a defect — it is a consequence of one writer at a time.

Two numbers make the point without any journal in the picture at all. One SQLite writer batching 64 rows per transaction does 6,217 rows/s — 75× the single-row figure, from batching alone. And 23,354 versus 83.4 is the price of the barrier, in one database, on one machine, changing one PRAGMA.

So: any benchmark that does not state which barrier both sides used is not a statement about durability. It is a statement about how much of the write path the faster side skipped. We published a 4× regression on exactly this question in Movement I; we are not going to turn around and quote a number against SQLite that depends on the same confusion.

Two builds, one machine, different durability

It gets worse than a PRAGMA you might forget. Apple's /usr/bin/sqlite3 3.51.0 ships DEFAULT_WAL_SYNCHRONOUS=1 (NORMAL); another SQLite build on the same laptop ships 2 (FULL). Same machine, same library name, different durability, depending on which binary you happened to link. At NORMAL, WAL commits do not sync at all, and what a power failure costs you is not the last transaction but everything since the last WAL sync. Pin synchronous explicitly at startup and fail startup on a mismatch; the compiled default cannot be relied upon.

Where we are stronger

Per-frame checksums, against nothing at all. This is the finding that most surprised us. Neither Redis nor Valkey computes any checksum over an AOF record. There is no length prefix, no LSN and no CRC on that path — a payload bit flip produces bytes that parse as a perfectly valid command, and the command is silently applied on load. Redis has an open issue about it — redis/redis#3730, open since 2017. Valkey's own src/aof.c returns nothing for a case-insensitive grep of crc or checksum. That is not a subtle difference in strictness; it is the difference between detecting damage and replaying it as data.

Stated precisely, because the scope matters: what we read is the AOF record path, in src/aof.c at those tags. That is the path carrying the mutations you replay, and it is the path our own frame format is the direct counterpart of. We did not audit the rest of either codebase, and nothing here should be read as a claim about it.

A bounded queue that actually refuses. Redis's aof_buf grows without a bound, and is explicitly excluded from the maxmemory accounting (evict.c:354-356) — so the memory that absorbs a stalled disk is memory the eviction policy cannot see. Our queue has a capacity you chose, and at that capacity submissions are refused rather than accepted into growth. This is the same argument as the queue_capacity: 0 refusal: an unbounded-growth incident begins with everyone believing a bound that was never in force.

Failing closed on a complete corrupt frame. SQLite's WAL recovery has one line that decides this — src/wal.c:1511, if(!isValid) break; — and it makes the opposite choice from ours: the scan breaks out of its loop as soon as a frame does not validate, and it makes no distinction between “this frame is physically incomplete” and “this frame is complete and its checksum is wrong.” Everything after the break is discarded, and no error is returned to anybody. That is the exact inverse of our rule, and it is not a small difference: the first case is a write nobody was promised, and the second is a write somebody was told had succeeded.

Redis moved toward SQLite's behaviour in 8.10 with aof-load-corrupt-tail-max-size (config.c:3507), which truncates on a format error and discards the valid records sitting behind the corruption. Valkey declined to take it. On this one question, Valkey is stricter than current Redis — and it is the one place in this comparison where the two projects meaningfully diverge on the AOF write path, which is otherwise barely diverged at all: no AOF default has moved. Valkey's own repair tool is no gentler, mind: valkey-check-aof --fix truncates from the first bad byte to EOF, discarding every valid record after it.

And Valkey knows. Issue #3515, “Modernizing Valkey AOF,” proposes per-entry length/LSN/checksum headers, recycled fixed-size segments, and disk-capacity backpressure. That is, near enough, a description of the format in Movement II, arrived at independently by people with far more operational scar tissue than we have. It has not landed. We read that as corroboration of the shape rather than as a win — the argument was already being made inside the project we are comparing ourselves to.

Where we are weaker, and it is not close

1. We have no replication. None. etcd will not send any response that counts toward a quorum until the entry and the hard state are on stable storage — a stronger guarantee than ours in kind, not merely in degree, because it survives the loss of the machine. Kafka has an in-sync replica set. We have a file on one disk. Lose the host, lose the journal. “Local-durable” is the honest name for what we have and there is no reading of it that competes with consensus.

The comment in etcd-io/raft:raft.go:544-590 states the general principle better than we did, and it is exactly our acknowledgement rule one layer up the stack:

etcd-io/raft:raft.go:544-590

“response messages that relate to ‘voting’ on either leader election or log appends require durability before they can be sent. It would be incorrect to publish a vote in an election before that vote has been synced to stable storage locally. Similarly, it would be incorrect to acknowledge a log append to the leader before that entry has been synced to stable storage locally.”

Two honest asterisks on etcd, for symmetry with the ones we put on ourselves. It ships an --unsafe-no-fsync flag whose own help text reads “Disables fsync, unsafe, will cause data loss” — which is the right way to offer a dangerous option, named for what it does. And it is not strictly fail-closed: isTornEntry (etcd-io/etcd:server/storage/wal/decoder.go:166-201) reclassifies a CRC failure as a torn write whenever any 512-byte sector of a complete record reads all-zero. That is a deliberate, documented trade against sector-granularity torn writes, and it is a place where our rule is stricter than a system that is otherwise well ahead of us.

2. We have no segment rotation, so the journal grows. Forever, until the filesystem fills. Both etcd and Kafka rotate segments; etcd's sequence is the one worth copying (wal.go:745-827): truncate and fsync the old tail, take a preallocated N.tmp from a background filePipeline, write the CRC chain, metadata and hard state into it, fsync, rename, then fsync the directory — and crucially it writes no acknowledgeable payload into the new segment before publishing it, so there is no window in which an acknowledged record lives in a file that is not yet visible. The filename carries the first sequence number, so the directory listing is the manifest, with no separate file to corrupt.

For contrast, Kafka's log roll performs zero fsyncs — not on the file, not on the directory — and publishes the new segment by a ConcurrentSkipListMap.put (UnifiedLog.java:2212-2214). That is a coherent choice for a system whose durability story is replication rather than local flush, and a bad model for a system whose durability story is local flush. Redis's MP-AOF manifest sequence is closer to what we want — write a temporary file, fsync the file, rename, fsync the directory (aof.c:540-612) — though its manifest is unchecksummed plain text, which we would not copy.

3. We have no position back-link, and this is the subtle one. Our frame chain links the previous frame's CRC value. That is position-independent: a frame chain that validates does not prove the frames are where the writer put them. PostgreSQL's xl_prev stores the previous record's position, and Tom Lane explained on pgsql-hackers in January 2018 exactly why that matters:

Tom Lane, pgsql-hackers, 12 January 2018

“recognizing that the new record has an old xl_prev is our ONLY defense against replaying stale data.”

The scenario is not hypothetical. WAL segment recycling in Postgres is a bare rename with no zeroing (xlog.c:4022-4031), so a recycled segment is full of complete, correctly-CRC'd, stale records. The checksum cannot save you, because the stale records' checksums are perfectly valid — they were valid when they were written. Only the position can save you.

We do not have that defence today. We do not yet need it, because we do not recycle segments — but that is the same as saying the missing defence and the missing feature are the same gap. Which is why the position back-link is format v2 and it lands before segment rotation, not after. Shipping rotation onto a position-independent chain would be shipping the stale-replay bug deliberately.

4. Nothing we have approaches Postgres's maturity, and its refinements show it. Consider one detail: Postgres never makes a solitary committer wait. commit_delay defaults to 0, and even when it is set, the commit_siblings guard means a transaction that is the only one in flight does not pay a group-commit delay for a group that does not exist. Our broker has a fixed configurable window and no such refinement. That is a small thing, and it is exactly the kind of small thing that decades of production produce and a fortnight does not.

We were not the first to make the Darwin mistake, and that is the point

Two of the systems in this comparison already resolve their sync call to fcntl(fd, F_FULLFSYNC) on Darwin: Redis does it through a platform macro (redis:src/config.h:125-132), and etcd maps its Fdatasync to the same fcntl — with a comment (etcd-io/etcd:client/pkg/fileutil/sync_darwin.go:25-38) that reads like a summary of our bug report: “Fsync on HFS/OSX flushes the data on to the physical drive but the drive may not write it to the persistent media for quite sometime and it may be written in out-of-order sequence. Using F_FULLFSYNC ensures that the physical drive's buffer will also get flushed to the media.”

So the correct answer was sitting in two widely read codebases the whole time, and we still shipped the wrong one — because the wrong one compiles, passes every test that does not cut the power, and benchmarks four times better. Four of the five research briefs written for this article independently flagged the same Darwin gap as an open question, in five different projects, without coordinating. That is what makes this class of bug worth an article. It is not hard to fix. It is hard to notice.

Kafka disagrees with itself, usefully

Kafka's data plane does not fsync on produce — flush.messages and flush.ms both default to Long.MAX_VALUE, and the project states the position in its own documentation: “durability in Kafka does not require syncing data to disk” (docs/operations/hardware-and-os.md:64). But Kafka's own metadata log, KRaft, flushes before acknowledging (KafkaRaftClient.java:673-677). The same project, in the same repository, uses a stronger rule for the data it cannot afford to lose than for yours. That is not hypocrisy — it is an accurate statement about which losses replication can absorb and which it cannot — but it is worth noticing which side of that line your data is on.

Kafka argues its side of that line explicitly, and the argument is good enough that it belongs here rather than in a footnote. From apache/kafka:docs/design/design.md:335: “disk errors are the most common problem we observe in real operation of persistent data systems and they often do not leave data intact. Secondly, even if this were not a problem, we do not want to require the use of fsync on every write for our consistency guarantees as this can reduce performance by two to three orders of magnitude.” That is the same 4× we measured, several times over, and it is the reason a system with replication is entitled to a different answer than a system without one. We do not have replication, so we are not entitled to that answer.

One trap in it, though, and Kafka names it too (design.md:353): “when acks=all, acknowledgement happens as soon as all the current in-sync replicas have received the message… if a topic is configured with only two replicas and one fails (i.e., only one in sync replica remains), then writes that specify acks=all will succeed. However, these writes could be lost if the remaining replica also fails.” With min.insync.replicas at its default of 1, acks=all can mean one machine's page cache.

“everysec” is not a one-second bound

Redis's appendfsync everysec is widely read as “you can lose at most one second.” The documentation says one second; antirez has said two; and the code can postpone the write() itself for under 2000 ms (aof.c:1448) while server.aof_last_fsync is updated outside the sync_in_progress guard (aof.c:1601-1605), so a stalled disk can stretch the window indefinitely. Separately, no-appendfsync-on-rewrite yes silently downgrades always to no during a rewrite (aof.c:1575-1579) — and redis.conf:1555-1556 admits it in a comment. We have left the one-second-versus-two-seconds contradiction unresolved rather than picking whichever reading suits us; the point is that the bound is not a bound.

The comparison, done properly

Everything above about SQLite was measured honestly and compared dishonestly, and it took three more probes to see why. The first comparison put a real device flush on one side and an ordering barrier on the other, and I did not know that at the time because macOS does not have one “sync” — it has three, and they differ by two orders of magnitude.

Darwin has three durability tiers. M-series laptop, APFS.
PrimitiveCostWhat it actually guarantees
fsync / fdatasync0.045 ms Reached the drive, not the platters. Not power-safe.
F_BARRIERFSYNC0.239 ms I/O ordering barrier. Still not a media flush.

Eighty-nine times between the fastest lie and the truth. Then the second probe: what does Apple’s SQLite actually issue? At journal_mode=WAL, synchronous=FULL, fullfsync=ON a commit costs 0.377 ms. The pragma does change behaviour — 0.080 ms without it — but 0.377 ms lands in the barrier tier, nowhere near the 4.0 ms flush tier. Meanwhile this journal’s single-writer p50 was 3.99 ms: exactly one F_FULLFSYNC, with no waste around it.

The most dangerous shape a durability setting can have

On macOS that SQLite profile is not media-durable. On Linux the same profile costs 0.605 ms/commit against a bare fdatasync of 0.514 ms — one real barrier per commit. So the configuration is durable on the production platform and not on the development one. It will never fail a test on the machine where it is wrong.

So the fair test has to run on Linux, where both engines use the same primitive. Both lanes in one process, back to back, 80 records per writer, each SQLite writer on its own connection with a 30-second busy timeout, no multi-row batching on either side because neither caller batches:

Two things there matter more than the headline ratio. SQLite gets slower as writers arrive — 1,630 down to 797. That is not noise, it is the WAL write lock: a committing writer holds it across its fdatasync, so the durable commit rate is 1 / barrier_cost however many are queued, and the queueing itself costs something. The journal goes the other way, 1,279 up to 24,305, because more concurrent callers mean a bigger batch under one barrier. Different asymptotes, not different constants.

And the tail is the real story. At 32 writers SQLite’s p99 is 532 ms against 2.5 ms. Throughput ratios can be argued about; a half-second p99 on a coordination write cannot.

Where SQLite still wins

At one writer, SQLite is faster — 1,630 against 1,279, a ratio of 0.78×. There is no batch to amortise, so the journal pays a barrier plus a queue handoff for nothing. The crossover is between one and four writers.

That is not a caveat to be buried. If your hottest workload has one active writer, this package is a cost and you should not adopt it.

Two platforms that disagree about what “sync” means

Development is Darwin; production is x86 Linux. They do not share a durability primitive, and the gap is not cosmetic. On Darwin only F_FULLFSYNC reaches the media, and it costs 4.0 ms. On Linux fdatasync is the real barrier (given a filesystem and device with write barriers enabled) and costs 0.514 ms — correct and eight times cheaper.

So the journal issues a different call per platform, reports which one it issued through hdl_sync_barrier_name(), and the recovery gate asserts the right one per platform so the promise cannot drift from the code. There is no fallback to a weaker barrier: a filesystem that refuses the strong one gets the error back and the batch is not acknowledged. And because a green gate on Darwin proves nothing about a platform using a different primitive, Linux is gated separately in Docker.

A 3.5× optimisation we measured and did not take

On Linux, fdatasync still has to flush the file-size metadata when an append extends the file. Preallocate the segment, write inside it, and that disappears: 0.454 ms → 0.131 ms per barrier. On Darwin it changes nothing, because the device flush dominates.

It is not implemented, and the reason is the whole ethic of the package. A preallocated segment is full of zeros past the last commit, so recovery would have to tell “space we reserved and never wrote” from “a complete frame that has been damaged” — and the cheap way to do that is the all-zeros heuristic we refuse etcd for. Doing it properly means the segment header must record the reserved extent, which makes it a format change. A 3.5× speedup is not worth a recovery rule that guesses.

Surviving the host, not just the process

Everything so far is local durability, and local durability has a hard edge: it survives the process, the OS and the power cable, and it does not survive the machine. For that a record has to be durable somewhere else before the caller is told yes.

Hey has a distributed substrate, and the interesting part of building on it was that its documentation is honest enough to constrain the design. Remote.send is at-most-once, and success means “accepted for transport”, explicitly not “processed remotely”. Monitors report suspicion of loss, because partition and death are observationally indistinguishable. Both facts point the same way:

A successful send is never durability

An acknowledgement counts only when a follower sends back an explicit receipt saying it completed its own local barrier. A missing or late reply is a refusal, never an optimistic success. Anything else would be acknowledging RAM again — just somebody else’s.

The rest follows. Local durability happens first, as in PostgreSQL, which never substitutes a replica for the local flush — replicating first would let a node acknowledge a record it cannot itself replay. A quorum is a majority including this node; a quorum of one on a three-node cluster is a split brain with good manners. Every append carries a term, and a higher term seen anywhere invalidates the write, because a partitioned leader has no other way to learn it has been replaced.

The part worth stating loudest is what happens when the majority is unreachable: the append fails, with durable_log_quorum_unavailable. It does not quietly hand back a local_durable receipt. The record really is on local disk, and saying so would even be true — but returning success there would claim host durability that does not exist, and silent degradation is exactly how a system comes to believe it survives host loss when it does not.

Two of the gates for this exist because I broke the code deliberately to check: counting a transport-accepted-but-not-durable reply as an acknowledgement, and degrading to local durability when the quorum is missing. Both go red. The network itself is not tested here — the replication seam is injected, so what is proven is the decision, not the transport. Whether TCP works is the substrate’s problem; whether we acknowledge a write a majority never confirmed is ours.

The limits, stated plainly

A durability article that oversells is worse than no article, so here is everything this package cannot currently do, without softening.

  • Local disk only. The guarantees are process crash, OS crash and power loss on this host. Losing the host or losing the disk loses the journal. Quorum replication before acknowledgement is not implemented, and until it is, nothing built on this package can be described as surviving host loss because it has a journal.
  • No segment rotation. The journal grows. There is no manifest, no retirement, no snapshot-and-truncate. A journal that cannot rotate is a journal that grows until the filesystem fills, and we have not tested against a genuinely full filesystem — only a mocked ENOSPC is not the same thing, and we have not claimed otherwise.
  • No position back-link. The v1 chain links CRC values and is position-independent, so it provides no defence against replaying stale records from a reused segment. This is scheduled as format v2 and must land before rotation.
  • The benchmark host was contaminated. Concurrent research subagents and C builds ran on the same laptop throughout; every condition sped up by roughly 2× across three rounds as that load drained. Absolute figures are a floor, not a measurement of the hardware. Only the ratios within an interleaved round are being claimed.
  • No power-cut test has been performed on this hardware. That F_FULLFSYNC is the right call to issue is documented by Apple. That this particular drive honours it end to end is asserted by that documentation, not by a test we ran. Nobody has pulled the plug on this laptop mid-write and checked.
  • Group-commit statistics are not reachable from Hey. hdl_broker_get_stats exposes records, durable_batches, largest_batch and max_queue_depth, and that is what lets the C gate prove combining happened, and the queue bound hold, rather than assume either. From Hey you can infer it from shared batch_id values, but you cannot query it.
  • The comparison is a source reading, not a bake-off. Only SQLite was benchmarked alongside us. Everything said about Redis, Valkey, PostgreSQL, etcd and Kafka comes from reading their source at a pinned tag. We did not run any of them.
  • Queue depth and backpressure under saturation are not measured, and neither is replay lag while writers saturate the log. The bounded queue is asserted by the specs; its behaviour at the limit is not instrumented.

What we would tell somebody building one of these

Four things, in the order we learned them.

  • Name the barrier in a public function and gate it per platform. Not a comment, not a constant — a function like hdl_sync_barrier_name() that a test can assert against. The reason we found this bug is that somebody went looking for what the code actually called; the reason it cannot come back is that a test now fails if the answer changes.
  • Publish the regression. When the correct barrier costs you 4×, the number to put in the document is the slow one, with the fast one next to it labelled as not power-loss durable. Anything else trains your future self to trust the wrong measurement.
  • Distinguish “never acknowledged” from “acknowledged and damaged.” These look similar in a recovery scanner and they are opposites. Every system in this comparison has a position on it, and only two of the five fail closed on a complete corrupt record by default. SQLite silently truncates, PostgreSQL treats it as end-of-WAL and starts, Kafka truncates and deletes later segments, and etcd fails closed except when the damage looks sector-shaped. That is not a field consensus you can inherit; it is a decision you have to make on purpose.
  • Say what you do not have. The most useful sentence in our documentation is quorum_replication: false, asserted by a spec so it cannot quietly become aspirational. The second most useful is the one admitting we never pulled the plug.
