Hey language · design note · 22 August 2026

Testing Hey, immutably

Hey has no mutable instance state, no closures, and no try/rescue — the three things almost every test framework leans on. So the framework became a plain module instead: Minispec, a pure Hey file whose assertions are functions on an immutable value, whose fixtures are data you pass as an argument, and whose raise tests run the subject on a throwaway isolated worker — all of it running on today's runtime with no compiler change.

Built and running. This is no longer a paper design. stdlib/Minispec.hey landed additively in the 545a-era build (22 August 2026) and needs no compiler, emitter, or runtime change — you opt in by importing it. The earlier version of this note said "nothing here is built yet"; that is now false.
Not shipped yet. The ergonomic surface the design still wants is deferred behind the unfinished module system: block sugar (spec "…" / it "…"), the import … exposing: [names] spec-file convention, and observing a hard fail's structured reason (that would need OS-subprocess isolation). Today you thread the suite by hand and import by path. None of this blocks what Minispec already does.

TL;DR

  • It's a module, not a language change. Minispec is pure Hey — functions, no emitter or runtime work. The existing declarative spec … expect stdout golden blocks are untouched; Minispec is opt-in.
  • Assertions are pure suite -> suite functions. A test run is one immutable "suite" value; each assertion returns a new suite with one more pass/fail recorded. You thread it with let/set — no closures, no mutable accumulator, no @ivars.
  • Fixtures are data, not state. A builder fn returns a fresh immutable value; an Elixir-ExUnit-style context map is passed to each test as an argument. Immutability makes "fresh per test" automatic.
  • Three failure levels, kept apart. An expected failure is a Result value asserted in-process; a recoverable failure is to_raise on a temporary isolated worker; a hard fail is a process-fatal exit(70) that cannot be caught in-process — by design. Raises come back as an immutable Returned | Raised(reason) | TimedOut.
  • Disclosed weakness. The nice block/it sugar is not built (it waits on the module system), and a hard fail's reason is not observable in-process — Level 3 is fatal on purpose, so you assert only the first two levels' reasons.
  • Falsify it yourself. The receipts are seven green specs under test/minispec/ — math_spec (adoption + immutable fixtures), actor_spec, minispec_self_spec, finish_exit_spec, raise_spec, supervision_spec, and hard_fail_fatal_spec — all run by test/gate_minispec.sh under the unmodified golden harness.

Every test framework you have used makes the same quiet assumption: that setup can stash something in a mutable slot — an @ivar, a closure-captured beforeEach variable — and each test reads it back. That is impossible in Hey: no mutable instance state, no closures to capture a fixture, and no try/rescue to wrap a crash in a handler. The tempting fix would be to bend the language — a mutable class-based sublanguage, or stack-unwinding exceptions. The maintainer ruled the opposite on both counts: the core stays immutable, and the compiler pays no unwinding cost for test ergonomics. So the framework lives entirely inside the language as it already is — and here is the single through-line:

Minispec tests real Hey code — values, actors, raises, timeouts, and retries — as a pure immutable module, with no closures, no mutable state, and no compiler change.

Assertions are functions on an immutable value

The whole framework rests on one idea that sounds austere and turns out to be freeing: a test run is an immutable value. Minispec calls it a suite — a map holding the subject name, a pass count, a fail count, and a list of failures. Every assertion is a pure function suite -> suite that returns a new suite with one more result recorded. There is no registry of test closures and no mutable accumulator anywhere; the suite value is the accumulator, and you thread it with let/set.

import '../../stdlib/Minispec.hey'
import './math.hey'

let s = Minispec.suite('Math.scale')
set s = Minispec.to_equal(s, 'scales an int by a float', Math.scale(2, 2.5), 5.0)
set s = Minispec.to_be_close(s, 'float result within tolerance', Math.scale(0.1, 3), 0.3, 0.0001)
Minispec.report(s)        # -> "Math.scale: 2 passed, 0 failed"  (illustrative excerpt)

Because the suite is just data, it composes the way data composes: fold several with Minispec.merge, then report once. Minispec.report prints a stable one-line summary plus a FAIL: line per failure and returns the suite unchanged, so it drives the existing golden spec … expect stdout harness; Minispec.finish reports and then aborts (exit 70) if anything failed. No framework lifecycle — the ethos minitest states as "minitest is ruby," small and free of DSL magic, carried into Hey as functions over a value.

The assertion surface

The vocabulary is minitest's, mapped onto Hey values. Ordinary checks compare immutable values directly — value equality, not type equality, because a cast already conveys type — while the error-path and actor rows are where Hey's constraints shaped the surface.

The three failure levels, up close

The figure at the top is the spine; here is each level in turn. Hey deliberately does not have one uniform "an error happened" mechanism, and Minispec deliberately does not pretend it does. There are three kinds of failure, they escalate in severity, and each is tested with a different tool. Conflating them is the mistake; keeping them apart is the design.

Level 1 — expected failure is a value

The everyday failure — a lookup miss, a bad parse, a division a caller should handle — is not a raise at all. The code returns an error Result, and the test asserts on that value the ordinary way: to_be_error, to_error_with(message), or the success side to_be_ok. The match here is on the error's message, not on a structured kind — that distinction is a Level-2 concept. No isolation, no worker, no ceremony — an expected failure is just data flowing back. This is where most "failure" tests live.

Level 2 — a recoverable failure runs on an isolated worker

Some failures are genuine raises: the subject hits a runtime error and should. Here Hey's lack of try/rescue bites — there is no in-process handler to wrap the call in — so Minispec's answer is isolation, not interception. to_raise / to_fail run the subject as a temporary, unlinked, non-restarting isolated worker — a count: 1, retries: 0 Jobs pool over a named worker and its args (no closures, no new language feature). Minispec.observe reads back an immutable Returned(value), Raised(reason), or TimedOut, so a failing subject is ordinary data the test process never dies for; on TimedOut the stuck subject is terminated and its resources reclaimed, so nothing leaks. This block is adapted from raise_spec.hey:

# the named callable under test (closure-free; referenced by name below)
fn divide(a, b)
  if b == 0
    return Result.error_with('div_zero', 'cannot divide by zero')
  end
  return Result.ok(a / b)
end

# the isolated subject bridges its Result into a structured outcome
worker DivSubject(message)
  return Minispec.attempt(divide(message.a, message.b))
end

# a temporary, unlinked, NON-restarting pool: count 1, retries 0
job DivGuard
  worker DivSubject
  count: 1
  capacity: 8
  retries: 0
  result_capacity: 8
  dead_letter_capacity: 4
end

program
  let s   = Minispec.suite('divide')
  let bad = DivGuard.enqueue({a: 6, b: 0})
  let outcome = Minispec.observe(DivGuard, bad, 1000)   # Returned | Raised | TimedOut
  set s = Minispec.to_raise(s, 'divide by zero raises', outcome)
  set s = Minispec.to_raise_with(s, 'reason is div_zero', outcome, 'div_zero')
  Minispec.report(s)
  let done = DivGuard.stop()
end

One rule matters here more than any other: reasons are structured. An assertion matches on outcome.reason — a kind or code like div_zero — never on brittle diagnostic text or a source location. to_raise_with(reason) checks the kind; to_raise_from(source) attributes the raise to its isolating subject; to_time_out asserts the subject hung. Match on what failed, not on the sentence the runtime happened to print.

Level 3 — a hard fail is fatal, and that is the design

The deepest level is not recoverable and is not meant to be. A hard fail — or any true runtime panic — reaches hey_runtime_error, which on any non-REPL run ends the process with exit(70) (line 4427; code 70 is the Unix sysexits convention for an internal software error). The receipts pin it fatal under a supervised pool (hard_fail_fatal_spec hard-fails a worker under a retries: 1 pool and the whole run exits 70), and by construction from the unguarded exit(70) it is fatal in any configuration — no trap or unlink can isolate it. No in-process handler can catch it, because Hey deliberately has none: try/rescue would make the compiler pay for stack unwinding on every call just to sharpen test ergonomics. A hard fail is reserved for invariant violations, and when one fires the process is supposed to die. Minispec tests the first two levels precisely so the third stays rare and absolute.

The other lanes — follow-ups in this series

Three more lanes round out the framework; each is its own future note, so here they are in brief. Fixtures are data. The dominant xUnit fixture — mutable @ivars in setup, or closure-captured beforeEach state — is exactly what Hey cannot host, so Minispec uses two closure-free forms from ExUnit and Go: a builder fn that returns a fresh immutable value, or one immutable context map handed to each test as an argument. That is exactly what math_spec.hey demonstrates — a fresh_account() builder and a setup_context() map, with the fixture asserted "untouched after deposit." Immutability makes "fresh per test" automatic, and there is no teardown — pytest's yield-teardown exists to release side-effecting resources, and immutable values have nothing to release.

Supervision is a separate test. "Let it crash" is bounded: a supervised worker that keeps failing deterministically must escalate or dead-letter, never loop. That behavior is real and Minispec tests it — but with a different pool (one carrying retries: R and a dead_letter_capacity) and a different assertion, to_retry(outcome, min_attempts), which checks the subject was actually retried to its bound. Folding retry into to_raise would blur one observed failure with a restart policy; raise isolation and supervision are two questions with two answers.

Actors wait for the message, never sleep. The naive sleep(100); assert mailbox empty is the trap; Minispec adopts ExUnit's discipline and waits for the event. expect_receive rides the runtime's timeout-bounded receive (Jobs.result(job, receipt, ms)) so the assertion is deterministic, with expect_receive_within as a liveness probe and expect_no_receive as the negative. Hey needs no mocking subsystem: you substitute a collaborator by passing a value and verify interactions by asserting on what lands in a test-controlled mailbox.

The payoff, and the honest limits

Put it together and the maintainer's cautious "try immutable first, keep a mutable module only as a last resort" has a clean answer that is now running, not just ruled. Every dimension is closed with a closure-free, immutable-safe mechanism, and none of it required a compiler, emitter, or runtime change. Still, two limits are worth stating plainly — pretending they are gone would be the same dishonesty the old note carried in reverse:
