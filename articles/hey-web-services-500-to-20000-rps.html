From 500 to 20,000 Requests per Second

How three real Hey web services — a prayer-journal app, a blind-ciphertext sync server, and a church scheduling tool — went from three-digit to five-digit requests per second in eight days, through measurement, application fixes, and four toolchain releases.

TL;DR

  • We built a load-test harness in Hey itself, cross-checked with oha, and profiled with macOS sample.
  • Three findings explained everything: a ~7 ms interpreter-delegation tax on stdlib calls from compiled code, inverse worker scaling, and no HTTP keep-alive.
  • Application fixes (de-delegated hot paths, right-sized workers, smaller assets) bought 3–10×. Four toolchain releases (v0.99.394a–397a) bought the rest.
  • Result: all three services now exceed 20,000 req/s — sync server 29,001, scheduling app 26,875, war-room 23,862 — at median latencies of 60–160 µs; scheduling pages fell from 103 ms to 3.8 ms.

Where we started

On hey v0.99.390a, our fastest service answered a 364-byte JSON health check at about 2,251 req/s with a median latency of 7 ms (16 connections, oha). Page routes in the scheduling app sat near 110 ms per render. A Go net/http baseline on the same machine served the identical payload at 61,972 req/s. The gap was not mysterious after three days of measurement — it decomposed into exactly three mechanisms.

Finding 1: the delegation tax

Compiled Hey code calling a pure-Hey stdlib: or pkg: function paid ~7 ms per call — each call wrote a temp file and spawned an interpreter subprocess. A handler making one such call caps at ~117 req/s. Our probe made this a single number you can watch: Text.trim ×1000, ~7,344 µs each.

Finding 2: inverse worker scaling

More workers made every server slower: 1 worker = 5,977 req/s; 8 workers = 1,589 req/s. Root cause (found upstream later): macOS SO_REUSEPORT does not load-balance, so per-worker listeners degraded to single-worker serving — plus a per-request deep clone of the routes tree that multiplied with worker count.

Finding 3: no keep-alive

The runtime hardcoded connection: close; every request paid a fresh TCP connection, and response bytes cost ~0.2 ms/KB in a copy-heavy write path.

Application-side fixes (what you can do in your own code)

  • De-delegate hot paths. Handlers must not call pure-Hey stdlib per request. We built local response helpers from builtins (to_json, get, len) and dropped per-request middleware. The scheduling app's health check went 408 → 3,933 req/s from this alone (9.6×).
  • Right-size workers by workload. CPU-light handlers wanted workers: 1 (2.7× for war-room); I/O-blocking handlers wanted more. Measure, don't guess — the optimum flipped twice across toolchain releases.
  • Ship fewer bytes. esbuild-minifying a 35.5 KB client bundle to 25 KB bought +46% throughput on that route, because the write path scales with size.
  • Use native packages, not subprocess fallbacks. Swapping the scheduling app's per-query sqlite3 CLI forks for the native hey_sqlite3 package took pages from 103 ms to single-digit milliseconds of server time.

Where Hey sits between Ruby and Go

To place these numbers in a language hierarchy, we ran four servers back-to-back in the same minute, on the same machine, serving the byte-identical 364-byte JSON payload (oha -z 4s -c 16, keep-alive, 100% success on every lane):

Serverreq/sp50 latency
Ruby 3.4, WEBrick (single process)9,5891.59 ms
Hey v0.99.399a, stdlib Web (compiled, 4 workers)23,1030.161 ms
Ruby 3.4, puma (4-worker cluster)58,1460.259 ms
Go 1.26, net/http103,0700.135 ms

The honest read: eight days ago Hey lost to every lane on this chart — including WEBrick on latency. Today it beats stdlib Ruby by 2.4× on throughput and 10× on latency, and it already beats a tuned 4-worker puma cluster on median latency (0.161 vs 0.259 ms) while still trailing it 2.5× on throughput. That specific shape — fast per-request, limited fan-out — is the fingerprint of the two remaining named ceilings: the 8-worker poll-wakeup storm (queued for the kqueue event-loop stage) and residual boxed-value costs (the stdlib-archive program). Go remains the target, not the peer: 4.5× ahead on throughput, 1.2× on latency. Given that this gap closed from “46× behind Go” to “4.5× behind Go” in eight days of named, probe-verified fixes, we publish the ladder as-is and intend to update this table rather than argue with it.

How the collaboration worked

Two AI seats shared one machine: a benchmark seat owning harnesses, probes, and profiles; and a compiler-orchestrator seat landing verified toolchain slices. They exchanged findings through an append-only relay file — measured claims with reproduction commands, not vibes. The benchmark seat's profiles named upstream stages (a dispatch-path clone elimination is on the roadmap because of a 5-second sample trace); the orchestrator's landing notes predicted probe readings that were then confirmed to the microsecond. Every number in this article is reproducible from the repos' committed probes.

What's next

The remaining delegation tax (~4.4 ms per un-tabled stdlib call) falls to a persistent interpreter sidecar (measured ceiling: ~6 µs warm) and then a precompiled stdlib archive. The one residual scaling anomaly — a uniform dip at 8 workers, now route-count-independent — matches the poll-wakeup storm queued for the kqueue event-loop stage. The 60,000 req/s target is no longer speculative: three production apps sit at 24–29K today, and each remaining ceiling has a named fix and a probe watching it.
