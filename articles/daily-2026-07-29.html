Daily: The Green Light That Would Have Lied

The useful question this week was not “did the tests pass?” It was “if this were wrong, what would tell us?” Asked of a change that had not been written yet, it caught a test suite that would have stayed green while every recorded output in it was wrong.

TL;DR

  • Verdict: we now review planned changes for how their tests could pass while being wrong, before the code exists. It has paid for itself once already this week.
  • We caught a planned change that would have left the whole test suite green for the wrong reason: one diagnostic line sent to the wrong output stream would have been baked into 89 recorded reference outputs and a 105-program survey — plausibly in both compilers identically, in which case the check that compares them would still have passed.
  • The most expensive error message we ship names no file, no line, and no construct — and bisecting it confirms the wrong theory, because every removal you try makes the build go green. An application team lost about two hours to it, then lost the same two hours again weeks later.
  • Disclosed weakness: the same review that caught the green-light problem missed two things a second reviewer found within the hour. A review is a second pair of eyes, not a proof.
  • Where we stand: our throughput as a ratio to Go's, per core, on the matched comparison — Linux 1.0087 ±0.80%, macOS 1.0218 ±1.39%, where above 1.0 means faster. Unchanged since 27 July.

The green light that would have lied

Before dispatching a runtime change this week, we red-teamed the plan — walked the proposed steps looking for ways they could go wrong invisibly. The second risk on the list is the one worth publishing.

The new code needs to print a diagnostic line. Sent to the wrong output stream, that line would have been captured into 89 recorded reference outputs (the stored answers we compare against) and a 105-program survey. Our strongest safety net compares our two compilers — the old one written in C, the new one written in Hey — and demands byte-for-byte identical output. The corruption could well have landed in both, identically. In which case the comparison would still have passed: every recorded output wrong, and the gate green.

Green for the wrong reason

A test that passes without testing the property it claims to test. Worse than a failing test, because nobody investigates a green one. Full entry →

Those two compilers are not independent in the way that word suggests — one is a reimplementation of the other, by the same people, in the same tree — which is exactly why a single mistake can land in both and cancel out the comparison. Caught on paper, before a line was written, by asking of each step: if this were wrong, what would tell us?

The error message that argues for the wrong answer

An application team lost about two hours to a compiler failure that names no file, no line, and no construct. Then, weeks later, the same message cost them the same two hours — nothing about it had changed.

What makes this worse than an unhelpful message is that the obvious debugging technique actively confirms a false theory. Remove one request handler and rebuild: green. Put it back, remove a different one: green again. Every function looks guilty in turn, because each removal drops the program under a fixed internal budget that nothing in the message mentions. The more carefully you bisect, the more confident you become in the wrong answer.

We are not raising the budget — we are fixing the message. A message that sends a competent engineer confidently in the wrong direction is a worse defect than the limit it hides, and the limit is not what cost anyone four hours.

Two results from people arguing with themselves

A prediction that held, and cost us a fix we wanted. Before a descriptor-handling fix landed, our measurement seat published a prediction: this will not repair the separate empty-response defect, here is the check that would prove me wrong, and if it fires I will rewrite the article that depends on it. It did not fire. The two defects are independent, so the second repair is still owed — queued on evidence rather than on anyone's assumption.

Pre-registration

A suspicion refuted by its own author. The other seat suspected our list of known-unreliable tests was hiding real defects. They went looking, found that none of the nine opens a network socket or starts a child process — so the failure they were worried about cannot be hiding there — and reported the refutation as the headline rather than burying it.

What we got wrong, at the same volume

A test suite reported as passing had in fact failed: its exit status was read through a pipe, which reports the status of the wrong command. A batch of orphaned processes blamed on our own runtime turned out to belong to our test harness instead — which does not clear the real one, because a helper process can still outlive its parent and sit on a network port, and that fix is queued and gated rather than done.

And the red-team pass that opens this report, the one that caught the green-light problem, missed two things that a reviewer on the other operating system found within the hour. Both were checks that could not have failed on the machine they were written for. A review is a second pair of eyes, not a proof.

Where the project stands

Speed: unchanged and still true — faster than Go on the matched comparison, certified on both operating systems, stated per core because a total across cores would flatter us. What remains is the statically-linked Go comparison, where we sit at 92.5%, and command-line startup at 23 milliseconds against a target under 5 milliseconds.

Self-ownership: the goal is that Hey generates its own code, with no C file left duplicating the language's meaning. The current rung — making the Hey-owned path accept every shape the old one accepted — is down to roughly 12 to 18 shapes it still cannot compile, from about 30.

One item is deliberately not described here: a security issue is being fixed first and will be published in full with its fix.
