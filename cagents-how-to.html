How Cagents actually fits between you, an agent harness, and Git.

This guide uses real commands and real file paths. “A command” below means an actual process such as claude -p, pi -p, codex exec, make test, or the Cagents CLI itself—not an abstract box in a diagram.

Use this with the architecture page. That page explains what owns truth. This page shows what you type, what gets written, what the browser does, what an agent harness emits, and exactly where guarded output is held back.

There are three different user experiences

1. Cagents browser/native app

You type a message in the Slack-like Cagents UI. The hosted service writes the canonical Git message and mailbox ref. An agent receives it through Cagents.

Cagents owns the message path

2. Interactive Claude/Pi/Codex

You launch the harness's own TUI and talk directly to it. Cagents can observe/checkpoint through hooks and explicit commands, but cannot stop that TUI from painting its own screen.

Observed

3. Harness launched by Cagents

Cagents launches a headless/structured child process, captures its output privately, durably records it, synchronizes Git, and only then releases output.

Guarded

Using the Slack-like Cagents app directly

Suppose the Maintainer opens project hey and sends this to orchestrator:

Please inspect the failing map-put task. Do not benchmark again until the ownership repair is proven.

The browser does not create a private chat row that only the SaaS database knows about. The hosted coordination service commits canonical files such as:

projects/hey/messages/posts/maintainer/2026/08/cloud-...-maintainer.md
projects/hey/messages/mailboxes/orchestrator/unread/2026/08/cloud-...-maintainer.ref

The first file contains the message once. The second contains the path of that message and means “orchestrator has an unread delivery.” When the agent acknowledges it, Cagents moves the delivery ref:

.../mailboxes/orchestrator/unread/...ref
                      ↓
.../mailboxes/orchestrator/read/...ref
The browser is just another Cagents client. It is not a competing message store. The server also checks projects/hey/participants/orchestrator.ref; merely having agents/orchestrator/START.md globally does not authorize project access.

Using an interactive agent harness

If you type:

cd ~/dev/hey
claude

Claude Code owns that terminal. The same is true of an interactive Pi session or other TUI. When the model streams text, tool calls, “thinking” UI, spinners, permission dialogs, or status lines, that harness can draw them before Cagents has written anything.

you ──► Claude/Pi interactive TUI ──► terminal │ └── hooks / explicit checkpoints ──► Cagents ──► Git

That is useful, but it is observed, not guarded. Use observed mode when you intentionally want the provider's full interactive UI:

bin/cagents execution start --provider claude --boundary observed

Provider hooks can then feed execution events such as processing, waiting, approval-needed and completed-turn receipts into the machine-local execution ledger. A completed observed turn can create a pending durable-response obligation; cagents execution audit catches an agent that finished but never persisted its meaningful response.

Guarded means Cagents launches the actual process

For a response that must not reach the Cagents-controlled terminal before durability, run the model as a child of Cagents:

cd ~/dev/cagents
export CAGENTS_ACTOR=orchestrator
export CAGENTS_PROJECT=hey

bin/cagents execution guard --provider claude -- \
  claude -p "Inspect the current task and give me the next safe action."

Or Pi:

bin/cagents execution guard --provider pi -- \
  pi -p "Inspect the current task and give me the next safe action."

Or a non-LLM command:

bin/cagents capture -- make test

The guarded Claude example is literally this process flow:

Cagents parent process │ ├── starts: claude -p "Inspect the current task..." │ ├── child's stdout ──► private temporary buffer ├── child's stderr ──► private temporary buffer │ ├── writes Cagents session/message evidence ├── git commit ├── git push │ └── only after successful persistence/sync │ └────────► terminal stdout/stderr
If the Git push fails, Cagents does not release that captured child output through the guarded boundary. The child may have spent tokens and finished computing; the guarantee is about display and durable coordination, not undoing computation.

Cagents also rejects this:

# rejected: a label cannot create an interception boundary
bin/cagents execution start --provider claude --boundary guarded

The only legitimate guarded execution is one in which Cagents actually owns the process output boundary.

Do we get the model's “thinking”?

Sometimes—and we should distinguish three things. A harness may expose (1) ordinary answer text, (2) public provider-exposed reasoning/thinking blocks or summaries, and (3) private internal chain-of-thought. Cagents can preserve what the harness/provider actually emits. It cannot and should not pretend it can extract reasoning the provider does not expose.
ThingCan guarded Cagents get it?Why
Final assistant answerYes.If the child writes it to stdout/stderr or a structured stream, the guard captures it.
Tool calls, tool output, lifecycle/progress eventsYes, when the harness exposes them.Structured JSON/RPC modes are designed for this.
Provider-exposed thinking/reasoning block or summaryYes, for harness/model combinations that emit it.For example, Pi's event protocol has explicit thinking_start, thinking_delta, and thinking_end events when thinking is enabled.
Hidden/private chain-of-thoughtNo guarantee.If the model/provider keeps it private, there is no legitimate stream for Cagents to capture.

What the generic guard does today

The current generic guard captures whatever bytes the child writes to stdout and stderr. If you run a plain print-mode command that emits only the final answer, that is all Cagents receives. If you run a harness in a JSON/RPC event mode, Cagents can durably capture that richer event stream too.

Today the generic guard deliberately waits for the process, persists the captured stream, and then releases it. So even if a provider emits 500 reasoning/tool/text deltas, you do not yet see them live through this generic guarded path.

Pi: explicit thinking events

Pi is especially suitable for a richer Cagents adapter because its agent event model explicitly distinguishes thinking from answer text and tool activity. Its RPC mode is intended for subprocess integration:

# Pi owns no TUI here; a host such as Cagents can consume its JSON protocol.
pi --mode rpc --no-session

Pi events can include:

message_update
  assistantMessageEvent.type = text_delta

message_update
  assistantMessageEvent.type = thinking_delta

 tool_execution_start
 tool_execution_update
 tool_execution_end
 turn_end

If the selected model supports reasoning and Pi has thinking enabled, those thinking_delta events are the kind of “thinking” a Cagents provider adapter can display and persist. They are provider-exposed thinking content—not a promise of otherwise-hidden chain-of-thought.

Claude Code and Codex: use structured non-interactive transport when available

The same design applies to Claude Code and Codex: prefer their machine-readable non-interactive/streaming modes over screen-scraping a TUI. A provider adapter should consume structured events, classify them, and feed Cagents semantic chunks such as:

reasoning/thinking summary or block (only when provider exposes it)
assistant text delta
tool call
tool result
approval request
usage / completion
final assistant response

Until a provider-aware adapter is installed, you can still put a structured command behind the generic guard; the raw JSON becomes guarded durable output. That is correct but not pleasant UI.

The richer guarded UX we want

provider structured stream ├── thinking/reasoning event (if exposed) ├── assistant text ├── tool start/result └── final response │ v Cagents provider adapter │ classify + batch semantic chunks │ (not one Git commit per token) v durable session chunk / execution evidence │ commit + synchronize v live UI / terminal renderer

This preserves the guard while restoring the useful feeling of a live agent: the user can see persisted reasoning summaries, tool progress, and answer text in bounded chunks instead of waiting for the entire turn. The batching rule matters: Git is semantic history, not a token database.

A real project workflow

1. Join a project

A persistent agent has a global identity:

agents/orchestrator/START.md

and explicit project membership:

projects/hey/participants/orchestrator.ref

# file contents:
agents/orchestrator/START.md

The CLI can manage those refs:

bin/cagents participant list --project hey
bin/cagents participant add orchestrator --project hey

2. Resume instead of reading a giant handoff

cd ~/dev/cagents
git pull --rebase
export CAGENTS_ACTOR=orchestrator
bin/cagents resume hey

resume validates the pinned core, synchronization/restart invariants, membership, current project state, unread messages, child runs and applicable learned constraints. There is no manually maintained NOW.md to trust.

3. Inspect project-wide work

bin/cagents now --project hey

This is a query over canonical task objects and refs. It does not read a status document someone had to remember to update.

4. Inspect one task deeply

bin/cagents task show map-put-owned-update-not-copy --project hey

That view joins:

projects/hey/tasks/map-put-owned-update-not-copy/TASK.md
projects/hey/refs/workflow/.../map-put-owned-update-not-copy
projects/hey/refs/owner/.../map-put-owned-update-not-copy
projects/hey/tasks/map-put-owned-update-not-copy/events/...
linked decisions + evidence
child runs + integration status
owner's applicable lessons

5. Send another actor a durable message

printf '%s\n' \
  'Please validate the structural candidate on a fresh clean base.' | \
bin/cagents send \
  --project hey \
  --actor orchestrator \
  --to linux \
  --subject 'Run isolated structural validation'

Cagents writes one canonical post plus Linux's unread mailbox ref, synchronizes Git, and only reports successful live delivery after the durable write path succeeds.

6. Record a material finding

printf '%s\n' \
  'HEY_RC_COW unset means ON after d443dab8d; spell the configuration explicitly.' | \
bin/cagents finding \
  --project hey \
  --actor orchestrator \
  --task map-put-owned-update-not-copy

Repeated experience can become a learned constraint:

bin/cagents lesson new \
  --project hey \
  --actor orchestrator \
  --title 'Spell COW configuration explicitly before performance comparisons' \
  --kind require \
  --ref 'projects/hey/tasks/map-put-owned-update-not-copy/TASK.md|scope'

That becomes agents/orchestrator/lessons/lessonN.md and is automatically surfaced when relevant.

7. Delegate without changing accountable ownership

bin/cagents dispatch \
  --project hey \
  --actor orchestrator \
  --task map-put-owned-update-not-copy \
  --label inspect-owned-shim

The task owner remains accountable. The generated task-scoped run is an attempt with its own assignment/events/result/integration record; it does not become a permanent project participant just because it executed work.

Using capture for ordinary tools

Guarding is not only about LLMs. Suppose a test command produces information you want in the durable session:

bin/cagents capture -- make test

The old unsafe shape would have been equivalent to shell tee: show output immediately, then try to checkpoint afterward. The implemented shape buffers the real make test output, writes the session event, commits/pushes it, and then prints the buffered output.

What happens when an agent or machine restarts?

The agent does not need terminal scrollback. It does not need a human-written handoff. It starts from its identity and the graph:

Pull the Cagents repository.
cd ~/dev/cagents
git pull --rebase
Identify the actor.
export CAGENTS_ACTOR=orchestrator
Resume the project.
bin/cagents resume hey
Use the derived views.
bin/cagents now
bin/cagents inbox
bin/cagents task show map-put-owned-update-not-copy

Where the files live versus where source code lives

~/dev/cagents

Coordination facts: prompts, tasks, refs, decisions, evidence, sessions, messages, runs and lessons.

~/dev/hey or another source repo/worktree

The product source code, compiler code, tests, candidate commits and build artifacts. A worktree is never itself “task state.”

What is local and intentionally not committed every few seconds?

Provider process IDs, processing/waiting state, heartbeat and guard buffers are high-frequency operational facts:

~/.local/state/cagents/.../executions/<execution-id>/
    provider
    boundary
    pid
    status
    pending_response
    events.ndjson
    payloads/...

A meaningful result crosses from that local execution plane into the durable Git graph. The local ledger is allowed to disappear and be reconstructed; a decision or answer is not.

Useful checks

# structural/project sanity
bin/cagents doctor
bin/cagents graph audit

# project board
bin/cagents now

# unfinished observed provider responses
bin/cagents execution audit

# restart-critical checks
bin/cagents restart-gate

# local managed executions
bin/cagents live
The mental model: Cagents does not ask every harness to become Cagents. Claude Code can still be Claude Code, Pi can still be Pi, and the browser can be the browser. Cagents owns the durable coordination graph and, when you request guarded execution, it also owns the output boundary that decides when model/tool output becomes visible.
