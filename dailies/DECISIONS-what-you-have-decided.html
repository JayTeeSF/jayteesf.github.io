What you've decided

Every decision in plain English, with what it means and where it stands. Kept current — bookmark this rather than the numbered Ask pages, which are snapshots of a moment.

Waiting on you — three things

1  The compiler needs language features the compiler can't compile

a syntax tree wants:   records with named fields
                       "if it's one of these shapes, do that"

Hey has today:         maps with string keys, and if/else

The new front end has to build a tree of the program. In most languages that's a record type plus pattern matching. Hey has neither — so either we build the tree out of plain maps and live with it, or we add those features to the language first.

This is the biggest unsized risk in the whole plan. Maps work and cost nothing to start; they're slower and easier to get wrong. Adding the features is the right long answer and delays everything behind it. I'd start with maps and measure — but you should know the choice is being made.

2  Two details of the new function signature

fn f(a, b = 1, ...rest, k:, kw: 2, ...kw_rest)

  is the ORDER enforced?     what happens if someone writes ...rest first?
  when is `b = 1` computed?  Ruby computes it at call time, so
                             fn f(a, b = a * 2)  works

Both are cheap to decide now and awkward later, because programs will depend on whichever we pick.

My suggestion: enforce the order with an error naming the correct one, and compute defaults at call time so they can refer to earlier parameters — that's Ruby's behaviour and it's the more useful of the two.

3  When do the old tests stop being the standard?

About ninety of our tests currently check that the new compiler produces byte-for-byte what the old one produced. A real front end will change those bytes — correctly. So at some point that test stops meaning “still right” and starts meaning “still old”.

Nothing currently schedules that moment, and if we don't pick one we'll either freeze the old output forever or quietly delete a real safety net. My suggestion: keep it until the specs that describe the same behaviour in their own words exist and are proven able to fail — then retire it in one deliberate step and record what it had been catching.

The complete operator set — now closed

arithmetic     +   -   *   /   %   **
comparison     ==  !=  <   <=  >   >=
boolean        &&  ||  and  or  not  !
bitwise        &   |   ^   <<  >>
assignment     =   +=  -=  *=  /=  %=
range          ..<   ..
spread         ...

Everything in bold below is new: **, &&, ||, the compound assignments, all the bitwise ones, and inclusive ...

Why now, and why this is the last cheap moment: once a module can claim a symbol, the list is a public contract — a module may only claim something the language already has. An operator we don't add now can never be claimed later.

Does a bigger table slow the compiler? No. A tokenizer is a machine that walks characters; one more symbol is one more step it already knew how to take. Compile time grows with how much code you write, not with how many operators exist. It is expensive in the current design — every operator there is another pass over the text, which is why the same decision is made in 45-plus places. So this was a language question, not a speed question.

One pow, not two — and why the obvious shortcut is wrong

Math.pow(2, 3)       8      whole in, whole out
Math.pow(2.0, 3.0)   8.0    decimals in, decimal out

  same function. no pow_f.

Rust needs two functions because it makes you write the types down, and whole numbers and decimals are different types there. Hey doesn't — a value knows what it is at run time, so one function handles both, exactly as Python does.

It isn't slow. For 2 ** 3 the compiler already knows both are whole numbers and emits the whole-number path with no check at all. Only when it genuinely can't tell does it look — the same deal + already gets.

The shortcut you floated — convert everything to a decimal, convert back if it ends in .0 — is not slow, it's WRONG. Measured:
3 ** 40 should be 12157665459056928801; through a decimal it comes back ...768, wrong by 33.
10 ** 23 comes back wrong by 8,388,608.
Past about 9 quadrillion a decimal can't hold every whole number, so the round trip loses digits silently. You suspected it was bad; that's the reason.

Ranges — where we come out ahead of Ruby

1 ..< 5     1 2 3 4        already existed
1 ..  5     1 2 3 4 5      new

Ruby:  1...5  excludes,  1..5  includes    — one dot apart

Ruby's two ranges differ by a single dot, which is a long-standing readability complaint. Ours differ by a visible <, which reads as “up to but less than”.

And Ruby's spelling wasn't available to us anyway: Ruby's exclusive range is ..., which is already Hey's spread operator. Keeping ..< avoided a collision we would otherwise have walked into.

Raising to a power — and the first real use of the import system

2 ** 3        8        whole numbers stay whole
2 ** 0.5      1.41...  a fractional power IS a root
2 ** -1       0.5      a negative power IS a reciprocal
2 ** 3 ** 2   error    say which you meant: (2 ** 3) ** 2  or  2 ** (3 ** 2)
(-8) ** 0.5   error    that answer is a complex number; Hey has none

** is not built into the compiler. It is an ordinary library function that declares a symbol, using the import system you designed:

module Math
  exposes pow  infix: '**'
  fn pow(base, exponent) ... end
end

2 ** 3           # the operator
Math.pow(2, 3)   # the same function, by name

So adding it exercises the override mechanism on something real — if the mechanism is wrong we find out on ** rather than on division.

How the others do it, measured on this machine:

                 has ** ?   2 ** 3      2 ** 0.5
Python           yes        8    int    1.4142...  float
JavaScript       yes        8           1.4142...
Ruby             yes        8           1.4142...
Rust             no         2.pow(3)    2.0.powf(0.5)     two functions
Go               no         math.Pow → 8.0  float ALWAYS
C                no         pow()    → double

Three of the six have no such operator at all — Go, Rust and C decided a function was enough. We follow Rust's split rather than Go's single function: Go's math.Pow always returns a decimal, so 2 ** 3 would be 8.0, which would contradict the rule you already set — whole numbers grow into bigger whole numbers, and only become decimals when the maths genuinely demands it.

Why chaining is an error rather than a guess. Python and JavaScript read 2 ** 3 ** 2 right-to-left, giving 512. We could copy that, but the machinery to express it does not exist yet — so instead of guessing we refuse and ask for parentheses. JavaScript already does exactly this for -2 ** 2, which it rejects as a syntax error rather than pick a side. Refusing now costs nothing and can be relaxed later; choosing wrong now cannot be undone.

What a function signature looks like

fn ultimate_fn(req, opt = 1, ...rest, kw_req:, kw_opt: 2, ...kw_rest)
  # this is the valid order, and it is enforced
end

  req          required
  opt = 1      optional, with a default
  ...rest      everything else positional, as a list
  kw_req:      required, by name
  kw_opt: 2    optional, by name, with a default
  ...kw_rest   every other named argument, as a map

Ruby's shape, with one deliberate difference: no block parameter. Ruby needs &block because blocks are a special thing that isn't a value. Ours are — you pass a function like any other argument, so there's nothing to convert and no second syntax to learn.

Why ... and not Ruby's * and **: Hey already spreads with ..., and it already means both things depending on what it's spreading — [...items] for a list, {...options} for a map. The same rule extends here: the first ... comes before any named parameter and collects a list; the second comes after and collects a map. One spelling, no new concept. Ruby needs two because it has no general spread.

How and, or and not bind

!1 == 2        is   (!1) == 2         !  binds very tight
not 1 == 2     is   not (1 == 2)      not binds very loose

a && b || c    is   (a && b) || c     && binds tighter than ||
a and b or c   is   (a and b) or c    and/or are EQUAL, and loosest

Ruby's rules exactly, and && and || get added — Hey doesn't have them today. Two spellings on purpose: && and || for combining values, and and or for control flow.

Measured against Ruby rather than copied from a table — the first attempt used values where several readings gave the same answer and proved nothing. One good thing we may get for free: Ruby's famous trap is y = 1 and 2 assigning 1, because = is an expression that binds tighter than and. Hey has no bare = — only let and set statements — so the trap may be unwritable here. Being checked before we copy the rule wholesale.

Functions can live in lists and maps — but never in JSON

let handlers = { on_save: save_it, on_quit: quit_now }
handlers.on_save(document)              works

Json.encode(handlers)                   stops with an error

Storing a function in a list or a map is ordinary and supported. Writing one to JSON is refused.

Two reasons, and the second is the serious one. JSON has no function type, so anything we invented would be a lie to every other program that reads it — and the obvious encoding, a string starting with &, can't be told apart from a string that genuinely starts with &. More importantly: a JSON document that can name a function to call is a way in. Load an untrusted file, get a value that resolves to something destructive by name. That exact shape has burned Ruby, Python and Java. If we ever want it, it's opt-in with a list of permitted names — never the default.

One path, not five

Hey source → tokens → syntax tree → HIR → MIR → machine code

One pathway serving both compiling and the interpreter. No doubled-up paths. Nearly every problem found this week is an instance of the same thing — one decision made in several places that disagree: 45-plus places deciding precedence, 28 deciding what counts as a name, two code generators, one of which cannot do division at all.

The order is yours: specs first, then remove the duplicate paths. A path is deleted only once the tests that pin its behaviour exist and are proven able to fail.

Hey gets a real front end

There is currently no parser. Expressions are carried as plain text and re-read by later stages; a four-pass rewriter runs over the source first and one of its passes deletes lines, which is why error locations can't be trusted.

The new pipeline is Hey source → tokens → syntax tree → HIR → MIR → machine code, one path serving both compiling and the interactive shell. The runtime and the code generator are kept; the front end is new.

How decimals print

says 100.0                  1e2  →  100.0
says 100000000000000.0      exactly what Ruby prints

Ruby's real rule, not “whichever is shorter” — the two disagree above about a hundred trillion, and we checked Ruby's actual behaviour against 2,000 random numbers rather than assuming it.

When a number gets too big

9223372036854775807 + 1   →   9223372036854775808

Your design: ask the chip whether it overflowed — it already knows — and redo that one calculation in a wider type. Almost always no, so almost always free. That's how Ruby and JavaScript engines actually do it, and all three of my original options were worse.

Negative division stays as it is

-7 / 2   is   -3

Rounds toward zero, like C and Go. Ruby says -4. You reversed an earlier choice here after it measured at 15% slower on the benchmark that certifies our speed. Ruby's version is available on request — see Overrides.

Reversing it also removed a real bug: our benchmark's averaging code rounds on top of the current behaviour, and Ruby's version would have made it compute wrong averages silently.

Overrides are per-file, and cost nothing unless you ask

import "stdlib:RubyMath"              → RubyMath.div(-7,2) to compare
import "stdlib:RubyMath" exposing *   → this file gets Ruby's math

A file that asks gets Ruby's arithmetic. Libraries it calls keep the behaviour they were written and tested against. The system will report every override in effect.

Known trade, taken knowingly: the number-one documented reason nobody uses Ruby's equivalent feature is having to write the import in every file. We took the safe option over the convenient one. Revisit if the friction bites.

The import system — four words, four jobs

the module says what it offers, and the symbol if it has one
  exposes div  infix: '/'

the file that wants it chooses how much to take
  import "stdlib:RubyMath"              → RubyMath.div(-7,2); nothing else changes
  import "stdlib:RubyMath" exposing *   → / and % are Ruby's in THIS file
  import "stdlib:RubyMath" as RM        → rename, and only rename
  ... exposing * forms: [:dotted]       → reserved, not built yet

The bare import isn't a lesser version — it's how you see the difference without adopting it. Both spellings in one file, side by side, is the test for the whole feature.

Two things caught before they shipped: a second spelling of exposing was dropped, because two words for one meaning is a coin flip and then a style argument. And as was nearly given a second job as a form selector — which would have produced import "M" as RM exposing * as: :infix the day you wanted renaming. forms: exists as its own word because of that, and is reserved rather than built: adding an optional keyword later is safe, taking back a familiar one is not.

How you write an operator

fn add(a, b) ... end
exposes add infix: '+'

You never name a function +. You name it something pronounceable and declare the symbol separately — so an error says add failed, not + failed, and a stack trace has a word in it. Redefining + still works; you just keep the name.

Precedence comes from the symbol, never from the module. Two languages that let modules set precedence were tested: an import silently changed how an expression parsed, with no warning.

How WE name functions in the compiler

read_source_text_into_tokens(source_text)
group_tokens_into_expression_tree(tokens)
can_this_operator_be_overridden?(symbol)

not:   lex()    parse()    process_data()

Verb first, name the input and the output, no abbreviations, questions end in ? — so anyone can read the diagrams and jump straight to the right part of the code.

Binding on all new code. The name is the only documentation that cannot go stale, because it travels with every call site.

What YOU can name a function

ok?     yes     already used by 217 stdlib functions
save!   yes     newly decided; it was previously undefined
?       no      a name can't be only punctuation
2       no      a digit can't start a name

The last one is what stops 3.2 being ambiguous with a call to a function named 2.

Dividing by zero

1   / 0     stops with an error     ← shipped
1.0 / 0.0   Infinity
inf.to_i()  stops with an error

Whole numbers and decimals differ on purpose — that's what Ruby does and what the floating-point standard requires. Infinity is a real decimal value; no whole number means it, so that's where it stops.

One bug must be fixed first: Infinity inside JSON output currently writes a wrong number instead of failing.

While we rebuild, the new version cannot be its own answer key — and “matches the old one” would pin the bugs along with the behaviour. So something outside both computes the expected value and checks ours against it.
