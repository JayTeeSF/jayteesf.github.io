Hey  ·  architecture review  ·  2 August 2026

Review of the restructure plan

A read of the published architecture and plan against the shipping snapshot, with two corrections, six measurements the plan was missing, rulings on the three open questions, and — new in this revision — the resolution of the one contradiction the review found in the decided set. The decisions page carries the settled outcomes; this page carries the reasoning.

The conclusion the documents reach is right: Hey does not need another round of parser-like fixes. It needs one authoritative front end and a prohibition against rediscovering syntax downstream.

So the work is not write parser → connect parser → fix remaining bugs. It is define one semantic pipeline → migrate every consumer onto it → delete all alternative interpretations.

Two corrections to the plan

1  The parser decides what - means, not the tokenizer

tokenizer   always emits   MINUS

parser      decides arity from context:
              expecting an operand?  → prefix negation
              expecting an operator? → infix subtraction

Pratt parsing was designed for exactly this distinction — the same token gets a prefix rule and an infix rule, and position selects.

Why this matters more than it looks: the current implementation decides it lexically, by checking whether the previous character is in a set. That set is missing ], which is why arr[0] - 1 fails with “undefined name” today — and there are two such sets, differing by eight characters. Moving the decision into the parser doesn't just tidy it; it makes that entire bug family unrepresentable.

2  Don't finish the emitter against the old intermediate form

Keep the fallback counter as phase 0. But completing the self-hosted emitter against today's raw-text MIR risks adding hundreds more handlers around a form the new front end must replace.

The plan documents the contradiction itself: MIR still carries raw source expressions, and the emitter is forced to re-parse them. Every handler written against that shape is a handler that must be migrated or thrown away — and each one enlarges the surface that has to move.

What the snapshot actually does

Verified against stable, v0.99.475a, commit 77ae81e8.

The “parser” is a statement classifier

It identifies statements by prefix, then classifies almost anything containing (, +, -, *, /, [ or { as an expression — and stores the expression as text:

{kind: 'let',    ..., expr: "...raw source..."}
{kind: 'return', ..., expr: "...raw source..."}

The intermediate form says so outright: MIR expressions are raw text. So this function:

fn add(a, b)
  return a + b * 2
end

survives all the way down with a + b * 2 still undivided. One path emitted effectively ret i64 a+b*2; the self-hosted emitter rejected the same expression.

That reframes the emitter gap: it is not an omission. The emitter has never been handed a structured operation.

The five unknowns, now measured

fn f(a, b = 1)                    REJECTED  "invalid function parameter: b = 1"
fn f(a, ...rest)                  REJECTED  "invalid function parameter: ...rest"
{ key: some_function }            works — a map can hold a callable
m.key(3)                          FAILS
let f = m.key ; f(3)              works
Json.encode({key: some_function}) SILENTLY produces {"key":null}
2 ** 3                            fails differently per route: one reports an
                                  empty undefined name, another generates
                                  malformed C

The JSON result is a bug, not a gap. Silently replacing a callable with null corrupts data. An unsupported value must produce an explicit encoding error — which is what the decision already says it should do.

And the current parser does not scale

statements   source     parse time    peak memory
       100     ~2 KB       28.7 ms       ~11.5 MB
       500    ~10 KB      659.8 ms        ~121 MB
     1,000    ~20 KB    SEGMENTATION FAULT ~170 MB

Two patterns explain the shape: it recurses once per statement rather than per level of nesting, and it rebuilds the growing statement list on every append.

The runtime's own notes record that map lookup is linear and clone-plus-write is quadratic. So building a whole compiler tree from ordinary immutable maps, extending arrays as it goes, would be a serious problem before semantic analysis even begins — which bears directly on the first open question below.

Build, run and the interactive prompt diverge only after HIR. That is the property the whole design exists to buy.

What each stage owns — and what it must not

TOKENIZER owns          identifiers, keywords, number spelling,
                        strings and interpolation boundaries,
                        comments, and longest-match symbols
                        (... ..< ** << +=)

TOKENIZER must NOT own  unary vs binary minus
                        precedence
                        name lookup
                        imported operator meaning
                        numeric result types

One fixed operator-symbol inventory. An imported module may bind meaning to **, but an import must never teach the tokenizer that the characters exist. That is what keeps imports from changing how a file parses — they change only what names mean.

The syntax tree has no expr: "a + b" field

2 ** 3     parses without consulting any import:

  BinaryExpression(
    operator: "**",
    left:  IntegerLiteral(2),
    right: IntegerLiteral(3))

then the resolver decides whether ** is in scope
and which exported function it denotes

The three open questions — answered

1  Neither plain maps nor waiting for pattern matching

Use a closed, schema-generated node system that is private to the compiler. Don't block the front end on adding user-visible records and pattern matching — and don't build the tree from unrestricted maps either.

# generated from one schema, never written by hand
fn syntax_binary(span, left, operator, right)
  return [NODE_BINARY, span, left, operator, right]
end

fn syntax_binary_left(node)
  return node[2]
end

Generate from that one schema: constructors, accessors, required-field validation, child iteration, serialisation, debug printing, visitor dispatch, and the list of every node kind each pass handles. A build should fail when a new node kind lacks a resolver or a lowering.

No compiler code writes {kind: 'binary', left: ..., rite: ...} directly — that is how a misspelled field and an incomplete visitor become permanent defects.

The instinct about pattern matching was right, with one qualification. Its main benefit here is detecting missing and redundant cases, not speed. But static exhaustiveness requires a closed set of variants, and arbitrary dynamic maps cannot provide one. If “no user-facing types” means no required annotations, sealed variants can still be added later without losing the ergonomics. So: closed schema with generated coverage checks now; records and pattern matching as a real language feature later; the front end waits for neither.

2  Defaults evaluate at call time, left to right

fn f(a, b = a * 2)     valid   — b sees a, already bound
fn f(a = b, b = 1)     ERROR   — b is not bound yet

Evaluated in the callee's parameter-binding prologue, after earlier arguments are bound, with access to earlier parameters and none to later ones. Ruby evaluates arguments left to right and permits exactly this.

And parameter order was never actually open — the decisions page listed it as a question and then, further down, stated the order and said it was enforced. Removed from the waiting list so it isn't reopened by accident.

Calls must be represented structurally, not as one argument string: callee, positional arguments, keyword arguments, positional spreads, keyword spreads. Keyword arguments are call binding semantics, not a map passed last.

3  Byte-goldens retire one at a time, each mutation-proven

Not a date and not a milestone. Each byte-identity test must first say what it was really protecting, then be replaced by a test of that contract:

what it actually protected        what replaces it
program result                    semantic output / error test
interpreted vs compiled agree     cross-lane behaviour test
diagnostic wording and spans      normalised diagnostic snapshot
token / tree / HIR / MIR shape    canonical structural snapshot
an optimisation happened          MIR or LLVM pattern assertion
instruction selection             assembly pattern test
reproducible public artifact      exact-byte test REMAINS
ABI or serialised format          exact-byte test REMAINS

For each: name the old invariant, add the new test, deliberately break the implementation and prove the new test fails, restore, run both, mark the golden superseded. Then delete all superseded goldens in one reviewed change.

Exact bytes survive only where bytes are part of the public contract — not because the old compiler happened to emit them.

The contradiction in the decided set — now resolved

Compound assignment and immutable bindings cannot both apply — and immutability wins

let total = 0
total += 1        ← these two rules disagreed

Three coherent options were on the table: make set create mutable bindings; keep locals immutable and allow compound assignment only on actor state; or drop compound assignment entirely. The ruling takes the middle option. Bindings are immutable without exception; the six compound spellings survive as state-update statements whose target must resolve to a state slot owned by the actor executing them.

state_update_statement
  = "set" IDENTIFIER state_update_operator expression

state_update_operator
  = "=" | "+=" | "-=" | "*=" | "/=" | "%="

The structural consequence is the one that matters to this document: there is no AssignmentExpression and no assignment level in the expression grammar. The parser emits a StateUpdateStatement carrying a target name; it does not decide whether that name is updateable. Resolution does, and produces either a resolved state-slot update or a diagnostic. That keeps a semantic question out of the precedence table, which is the same separation this whole review argues for everywhere else — the parser owns shape, the resolver owns meaning.

It also pays a debt noted further up this page: = never becomes an expression operator, so Ruby's y = 1 and 2 trap is not merely unlikely here, it is ungrammatical.

Evaluate the target once. set count += amount() lowers directly rather than expanding to set count = count + amount() as text — identical in meaning today, but it is what keeps a future indexed or nested target from evaluating its subscript twice. The restriction to a bare name in the first grammar exists for the same reason: indexed and nested state targets need a persistent path-update design, and that design must not block the front end.

The bootstrap debt is real and is being counted. The current self-hosted compiler uses local set extensively. It remains available only to whitelisted compiler modules under an internal mode ordinary source cannot enable, every use increments a per-file counter, new ones fail the ratchet, and HIR marks them LegacyLocalRebind — never StateUpdate, so the two can never reach the same lowering path. The front end is not complete until the counter is zero and the mode is deleted.

“Bindings are immutable” need not mean the compiler rebuilds a thousand-element array on every append — internal transient builders stay a private facility, and the accumulator-returning helper, the token cursor and the state-machine object with an immutable identity are all still available to compiler code.

Operators

One declarative registry, everything generated from it

symbol · token length · prefix/infix/postfix forms · precedence
associativity · overridable? · short-circuit? · operand rules
result rules · HIR operation · MIR lowering · runtime fallback
failure conditions

Lexer, parser, resolver, documentation and completeness tests all generate from that one table.

** is globally known syntax with globally fixed precedence whose meaning resolves to an imported function. A missing import should say operator ** is not in scope — help: import "stdlib:Math" exposing pow, not report an empty undefined name.

&& and || are control flow, not eager calls. They need dedicated short-circuit nodes and real branches — and should be non-overridable unless we deliberately want users altering evaluation order.

Numbers: no user-facing types is compatible with speed; no internal types is not

immediate machine integer fast path
hardware overflow check
overflow promotes to arbitrary precision
IEEE-754 binary64 internally
no width names in ordinary source
integer divide-by-zero raises
JSON explicitly rejects non-finite floats
bitwise accepts integers only
negative and oversized shifts specified centrally
equality and hashing defined for 1 vs 1.0, NaN, signed zero

“C speed” should be stated as a benchmarked envelope for type-stable hot code — not a promise that every dynamic program costs what hand-written C costs.

Actors, jobs and callables

Define the measurement before claiming the target

The actor control block measures 168 bytes on Linux x86-64 today, excluding mailbox nodes, allocator overhead, interned names and side tables. A ≤300-byte target is plausible — but only once the measurement includes control block, scheduler linkage, empty mailbox, allocator overhead and minimum state. Otherwise the target is “met” by moving fields into side tables.

The struct embeds a mutex and a condition variable costing 88 of those bytes. A pooled, run-to-completion actor does not normally need a condition variable each; atomic scheduling state, an MPSC mailbox and intrusive ready-queue linkage fit the intended design better.

Jobs need semantics before syntax

worker count · mailbox capacity · backpressure
input ordering · output ordering · failure propagation
retries · cancellation · restart policy · result aggregation
must work be idempotent? · may workers hold private state?

Then job ImageResize / workers: 8 lowers into generated actor-group HIR. A job must not require its own parser or compiler pathway, and must not implicitly capture surrounding state — everything entering a job appears explicitly.

Callable values: draw the boundary explicitly

supported     references to module and top-level functions
              actor definitions as callable-like values
              explicit partial application

not           capturing arbitrary surrounding locals

And define: equality and identity, whether they are hashable, whether they cross actor boundaries, whether bound values are copied or shared, whether they can be persisted.

JSON always rejects them — Json.encode cannot encode Callable at $.key — never a silent null, which is what ships today.

The invariants worth encoding as tests

1   only the tokenizer reads characters to identify tokens
2   only the parser decides syntax, precedence and operator arity
3   only the resolver decides what names and imported operators mean
4   HIR and MIR contain no source expression strings
5   LLVM emission never string-scans to understand syntax
6   interpreter and compiler consume the same HIR
7   REPL input is a synthetic source file through the same front end
8   every node kind is covered by generated pass-completeness checks
9   every operator exists in one registry
10  every front-end operation is bounded-stack and ~linear in source size
11  no unsupported value silently becomes nil or JSON null
12  fallback use is counted and can only decrease

Bottom line

The first implementation artifact is the node schema, source manager, operator registry, and shadow-mode tokenizer and parser — not another patch to the raw-text emitter.

Shadow mode is the mechanism: run the new front end on every build while the old back end still executes. That establishes parse coverage across the whole repository, diagnostics, parser performance and import-graph correctness without requiring the back end to be finished. Every accidental old syntax the new parser rejects goes into an adjudicated compatibility ledger rather than being silently accepted or silently dropped.
