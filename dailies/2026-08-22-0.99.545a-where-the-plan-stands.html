First, the thing to hold onto: Hey is compiled

Hey is self-hosting. The compiler is written in Hey and compiles itself, through a clean pipeline — source text becomes tokens, then a syntax tree, then a typed high-level form, then a mid-level form, then LLVM, the same industrial backend that compiles Clang's C and Rust to machine code. Every shipped program, and the compiler itself, runs as native code produced that way.

That matters because a recent status note left the wrong impression: that some Hey programs are "interpreted" and others "compiled," as if Hey were not always a compiled language. It is. Below is the correction at the same volume as the claim it fixes.

Correction: Hey compiles to native machine code. Always.

Shipped Hey programs, and the self-hosting compiler, run as native machine code produced through LLVM. There is also a tree-walking interpreter — but it is not how products run. It exists for three jobs: the interactive REPL, quick one-off scripts (heyc <file> --run), and the bootstrap seed that builds the very first compiler before Hey can compile itself. The interpreter is deliberately simple and deep-copies values, which makes it roughly 19× slower than compiled code. The benchmark figures that looked alarming — tens of seconds — came from running a measurement harness inside the interpreter on purpose, to count memory allocations per character, not from how a built program runs. Concrete receipt: the same string-heavy tokenize takes 14.04 s interpreted versus 0.72 s compiled (~19×), measured 2026-08-22 on an Apple M3 Pro.

What landed: making values cheaper to move

The recent arc is all about representation — how values are stored and copied — because that is where ordinary Hey code was leaving time on the floor. Three changes shipped on trunk.

First, copy-on-write became the default: when a value has exactly one owner, an update mutates it in place instead of cloning it. Second, a byte-oriented verifier made checking the 56,077-line self-hosting program for well-formedness about 100× faster. Third, a three-step tokenizer rewrite now reads the source as raw bytes instead of allocating a boxed one-character string for every character. Token output was confirmed byte-identical before and after; the speedups below come from the allocation-counting measurement pass, which is exactly where per-character boxing showed up.

Where Hey wins today, and the loss worth naming

The honest picture is a mix. On a live cross-language fannkuch(11) — a small, compute-bound permutation benchmark with a fixed reference output — Hey clears the scripting languages by wide margins and trails the systems languages by a predictable one.

The standing eight-language matrix, measured 2026-08-17, tells the same story with more shapes. Hey ties C on a streaming reduce — 0.108 s against C's 0.106 s — sits 1.6–2.5× behind C on array and fannkuch shapes, and beats Ruby 10–18× and Python roughly 50–310×. But there is a loss to name plainly: at 10M elements Hey does not finish the two string-array-building workloads. Appending to a boxed string array copies the whole backing on every append — quadratic — and it is already about 38 s at just 100k elements. That is not a rounding error; it is the workload class Hey most needs to fix.

The loss, stated once and clearly: building a large array by repeated append is O(n²) in Hey today, so the two 10M string-array workloads never complete. Everything below is about removing that, without asking anyone to write different code.

The next lever: let the compiler prove it can reuse the buffer

Here is the surprising part. Even compiled, the tokenizer is still quadratic in the number of tokens. The evidence is direct: internal array-append operations grow about 4× each time the token count doubles — 100 source blocks produce 1,370,219 appends, and 200 blocks produce 5,389,969. Double the work, quadruple the appends. That is the fingerprint of an O(n²) pattern hiding underneath a fast front end.

The root cause is a good language decision meeting a conservative compiler. Hey is immutable, so the natural way to grow a collection is "make a new list that is the old list plus one element" — written [...x, e] for lists and {...x, k: v} for records. Semantically that produces a fresh value. Today the code generator implements it by defensively deep-copying the base every single time, because it cannot see a proof that the base is safe to reuse. Copy the base, add one element, repeat: that is the quadratic.

The wrong fix would be to make programmers hand-write a faster, mutable form — that defeats the purpose of an immutable language. The right fix is already sitting in the pipeline. The intermediate form already proves when a value is uniquely owned and therefore safe to reuse in place; both code generators simply discard that proof before emitting code. Wire the proof through, and the ordinary immutable spread reuses its buffer automatically, turning the repeated append from O(n²) into O(1) amortized. When the proof does not hold, the compiler falls back to a copy, so correctness never rides on the optimization.

This is not a novel trick; it is a known result. It is the same idea as the "functional but in-place" style and the reuse analysis in MLIR-influenced compilers — most directly the Perceus reference-counting-with-reuse work (Reinking, Xie, de Moura, and Leijen, PLDI 2021), which Modular's Mojo language adopts in practice. Hey's contribution is not the idea; it is wiring an ownership proof it already computes into a backend that currently throws it away.

Where we are, what is next, and when the dual compiler ends

The plan board above shows the whole arc; two points on it are worth stating in words. The immediate move is to land compiler-proven reuse so the ordinary immutable spread form is O(1); that removes the tokenizer's remaining quadratic and unblocks the two string-array workloads Hey cannot finish today.

When the two-generator scaffolding ends. The C reference generator is scaffolding, not the destination. It is retired only when the independent verifiers and property checks are strong enough to replace byte-for-byte comparison against C as the trust mechanism — which is exactly what the verifier work is building. The endpoint is a single Hey code generator with the checkable intermediate form as its authority. Crucially, fast code comes from the representation and reuse work and does not wait on retiring the reference generator.

Reproduce and falsify

The reuse change has a sharp, pre-registered acceptance test. It is not "it feels faster."

# After compiler-proven reuse lands, compiled cost per token must stay
# flat as input size doubles (no more 4x-per-doubling append growth):
bench/tokenizer/run.sh            # compiled nanoseconds-per-token, flat

# The two code generators must still agree byte-for-byte:
#   Hey-emitted LLVM == C-reference LLVM

# The golden suites must stay green.

# And the ownership claim must hold with the runtime's copy-on-write
# FORCED OFF — the win must come from the compiler proof, not from a
# runtime that happens to skip a copy.

If per-token cost climbs as size doubles, if the two generators diverge, if a golden breaks, or if the speed evaporates with copy-on-write disabled, the reuse claim has failed and should be treated as unshipped.
