What it would take for Hey to reach the GPU

LLVM already hands Hey a working GPU back-end for the price of a target-triple-plus-calling-convention flip — but that is only about a fifth of the job, and the hardest, most Hey-specific piece of the four-fifths that remains is one question Hey is unusually well placed to answer: which of Hey's values are legal inside a kernel.

This is a design note. Nothing here is in the shipping toolchain — Hey has no GPU path today. It is a design exploration of what one would cost, not a feature, an announcement, or a plan of record.

TL;DR

  • The first move is not GPU code. It is defining which Hey values are legal inside a kernel — the kernel-legal value subset — and finishing the planned Perceus reuse pass (in-place reuse of uniquely-owned values) on the CPU. The GPU falls out of that one piece of work, or it stays a note and never needs to exist.
  • The back-end is nearly free. LLVM ships two production GPU back-ends — NVPTX (LLVM IR → PTX, NVIDIA's virtual instruction-set architecture, or ISA) and AMDGPU (LLVM IR → GCN/RDNA/CDNA code objects). Hey already emits LLVM IR text, so it is architecturally one back-end flag away from emitting PTX. That is real — and it is only about 20% of "target a GPU."
  • The real work is four net-new pieces. The back-end accepts only a subset of LLVM IR. The other ~80% — a device runtime, a kernel-legal value subset, a host/device memory model, and an offload layer — is all net-new, and none of it is what LLVM provides.
  • Hey's runtime fights the GPU; its core helps. Boxed values, reference-count dup/drop, and actors are all kernel-illegal. But immutability plus no closures plus no aliasing means pure, race-free kernels for free — the single hardest GPU correctness property, gone by construction. Futhark, a purely functional array language, is the existence proof.
  • Disclosed weakness: this is premature — today there is no Hey workload that clearly wants a GPU. On sourcing: the two load-bearing back-end anchors — NVPTX's "subset of LLVM IR" and AMDGPU's "ISA code generation for AMD GPUs" — were read as raw text and are the firmest citations here; it is the surrounding detail (intrinsic names, the address-space count, the libdevice wording, the "code objects only" clause) that is reader-paraphrase, and the Futhark claims come from search-result summaries rather than full-text fetches. Spot-check those before quoting.
  • Check it in one line: emit one hand-written Hey kernel to an nvptx64 module with a ptx_kernel function and see whether it assembles to PTX at all. If it does, the back-end claim holds; if it does not, this piece is wrong at step one.

There is a tempting question buried here. Hey compiles native through LLVM and has no virtual machine, so how much of the GPU does LLVM just give us? The honest answer has two halves, and they point in opposite directions. The back-end half is a gift. The runtime-and-values half is a wall. This note walks both and lands on the one move that is cheap, real, and worth making first.

The universal shape: a device half and a host half

Every system that programs a GPU directly — CUDA, Mojo, Julia, Triton, Rust — splits into the same two halves, without exception. Naming that split is the most useful lens for the whole question, because LLVM sits almost entirely inside one half and none of the other.

The device half is the kernel and its back-end: a function that runs on the GPU across a grid of threads, written in a restricted language (no arbitrary heap allocation, no OS calls, a fixed set of address spaces) and compiled to a device ISA — PTX for NVIDIA, GCN/RDNA/CDNA for AMD. The host half is the runtime: from the CPU, pick a device, allocate device memory, copy inputs across the host/device boundary, launch the kernel over a grid of blocks, copy results back, and synchronize. LLVM lives inside the device half. It provides none of the host half.

What LLVM actually gives Hey for free

Hey already emits LLVM IR text through its LLVM back-end (stdlib/HeyLlvm.hey + runtime/heyc.c), so the precise question is what an LLVM-IR-emitting language gets toward the GPU at no cost. The back-end docs answer it directly.

The NVPTX user guide states plainly that "the NVPTX back-end supports a subset of LLVM IR along with a defined set of conventions used to represent GPU programming concepts." It distinguishes device functions from kernel functions (kernels use the ptx_kernel calling convention), exposes thread/block/grid coordinates through intrinsics like llvm.nvvm.read.ptx.sreg.tid.x(), defines a fixed set of address spaces, and ships libdevice — an LLVM bitcode math library reusable by any compiler that targets LLVM NVPTX.

The AMDGPU back-end mirrors this for AMD: it "provides ISA code generation for AMD GPUs," from the R600 family up through current GCN/RDNA/CDNA processors, with the amdgpu_kernel calling convention and its own address spaces — and it emits ELF code objects consumed by runtimes such as AMD's ROCm and PAL runtimes.

That last clause is the whole story of where the gift ends. Both back-ends generate code objects only. The host runtime — kernel launch, device memory, host↔device copy, device management — is explicitly out of scope; the NVPTX guide assumes familiarity with CUDA and points every host-side concern at the CUDA Driver API. And buried in "a subset of LLVM IR" is the sleeper cost: your language's values and its allocator have to be expressible in that subset. For Hey, that clause is the wall.

Why Hey's runtime is kernel-illegal — and its core is not

Three parts of Hey's runtime fight the GPU, and it is worth being blunt about each.

Boxed / tagged values. Hey's value representation is boxed — the same tagged boxing behind the tokenizer's O(n²) "boxed push clones the backing." GPUs are catastrophic at pointer-chasing and per-element heap indirection; a kernel wants flat, unboxed, statically-typed arrays. As-is, Hey's values are exactly the thing the NVPTX "subset of LLVM IR" clause rejects.

Reference-count memory management. Hey is reference-counted. Refcount dup/drop on the device means atomic contention across thousands of threads, and device-side malloc/free is generally forbidden or ruinously slow. A kernel must run with no allocation and no refcounting: pre-sized output buffers, ownership resolved on the host.

Actors. The actor/mailbox model is a host concurrency abstraction. GPUs do not run mailboxes; they run data-parallel grids. "Millions of lightweight actors" and "a grid of a million threads running one kernel" are different universes. Actors do not port to the device — at most, an actor could own a GPU stream and offload array work. Anything framed as "actors on the GPU" is a category error.

But now the other direction, which is where Hey is genuinely lucky. The single hardest correctness property in GPU programming is data races from aliased mutable state — and Hey has none by construction. Immutability, no closures, no aliasing: a pure immutable function over arrays is the ideal kernel body. No aliasing analysis, no __restrict__, no race conditions to reason about. The runtime is the liability; the value semantics are an asset.

Futhark is the existence proof. An immutable, purely functional array language does not just theoretically reach the GPU — per the project's own description, Futhark ships an optimising ahead-of-time compiler that generates GPU code, and its central trick is exactly the Hey problem: a simple type system for in-place updates that ensures referential transparency (PLDI 2017). It keeps the pure functional surface while getting in-place array mutation underneath — the GPU cousin of the planned Perceus reuse pass, the in-place reuse of uniquely-owned values that would make immutable Hey C-fast on the CPU. Perceus itself — the reference-counting-with-reuse analysis Hey's design brief cites by name — is that CPU analysis; the same mechanism is what would make Hey GPU-legal. But Futhark reaches the GPU precisely by having only flat unboxed arrays — no boxing, no device refcounting, no actors. It rescues Hey's pure-value core; it does not rescue the runtime. (These Futhark claims are drawn from search-result summaries and the PLDI'17 title, not a full-text fetch — verify before quoting.)

The compiler path, and where Hey already sits

It helps to see the pipeline as one line. Mojo — the first language built on MLIR (Godoy et al., SC'25 workshops) — lowers through MLIR's GPU dialect stack: NVVM (its NVIDIA lowering dialect) to PTX, or ROCDL (its AMD dialect) to AMDGPU, per the MLIR gpu dialect docs. Hey, with no MLIR, would lower straight through its existing LLVM-text emitter. The device half is the tractable part for both. The precedents prove it: Julia's CUDAnative did the work as a front-end restriction (a GPU-legal subset) plus driver bindings, not a new back-end. Rust does it as a codegen backend plus a restricted subset. None of them found the back-end to be the hard part.

The cheapest first move — and what is premature

Start with the caveat that outranks all the engineering: Hey's headline is actors, immutability, and Ruby-grade ergonomics, not numerics, and today there is no Hey workload that clearly wants one. So the fully honest answer may be to write this down as a note and move on until a real workload appears. If Hey ever did chase it, the order is clear — and it deliberately does the design before the code.

The cheapest first move is not code at all. It is naming the kernel-legal subset: the Hey sublanguage that is GPU-expressible — monomorphic scalar element types, flat unboxed arrays, pure map/reduce/scan-shaped functions, no allocation, no refcount ops, no actors, output buffers pre-sized. This is a specification task, it gates everything else, and it composes directly with the Perceus reuse work.

Next, prove the back-end with a toy: push one hand-written Hey kernel through the existing LLVM-text emitter to an nvptx64 module with a ptx_kernel function and the tid/ctaid intrinsics, and run it with a minimal CUDA-driver FFI harness. That is a spike, not a feature — it answers only "does our IR reach PTX at all." (It is also the one-line falsifier in the TL;DR.)

Only after that comes the first user-visible feature: a single-vendor gpu.map over unboxed arrays — allocate a device buffer, copy, launch a pure elementwise or reduce kernel, copy back, synchronize — NVIDIA-only first, mirroring early CUDAnative. Portability, a second vendor (AMDGPU), and richer kernels (tiling, shared memory) come last, and only if that first feature earns real use.

And the traps, plainly. Do not adopt the MLIR framework to get its GPU dialects — take the idea of an offload layer, not the C++ framework, on the same self-hosting grounds a sibling design brief already refuses it. Do not attempt actors on the GPU — a mailbox model does not run on a data-parallel grid; it is a category error. Do not attempt kernels over general boxed Hey values until the unboxed-array subset exists. Do not chase two vendors before one works — Julia shipped NVIDIA-only for years. And above all, do not start any of it before the Perceus reuse pass lands on the CPU: allocation-free kernels need the same unique-ownership, in-place, no-copy analysis. The CPU work is the prerequisite; the GPU is its second payoff.

The bottom line holds: LLVM hands Hey the PTX/GCN back-end nearly for free — a target-triple-plus-calling-convention flip in the emitter it already has — but that is about 20% of "target a GPU." The other 80% — device runtime, kernel-legal value subset, host/device memory model, offload layer — is real work, and Hey's boxed-value, refcount, and actor runtime makes the kernel-subset piece specifically harder than it was for Mojo, which pre-engineered flat static values — while being easier on the correctness axis than for any mutable language, because immutability kills races. The right first move is not code. It is defining the kernel-legal subset and finishing Perceus reuse on the CPU. Everything on the GPU falls out of that one piece of work — or, if no workload ever calls for it, it stays a note and never needs to.
