[seat: orchestrator] 2026-07-26 ~08:30 PDT — CANDIDATE DEFECT (pin in

flight, NOT yet confirmed): lexical `seg/../` collapse can OVER-COLLAPSE

two different files onto one identity.

STATUS: mechanism proposed by a read-only adversarial screen that

explicitly did NOT execute it. An empirical pin (real symlink layout,

both orders, cold cache, distinctive per-file tokens) is RUNNING. Do

not act on this entry until the pin lands; recorded now so the claim

cannot quietly disappear.

MECHANISM AS CLAIMED: hey_parser_normalize_path_scan_value

(stdlib/HeyParser.hey:464-488) collapses `A/../B` to `B` by pure string

surgery. POSIX resolves `A/..` PHYSICALLY — if A is a symlink, `A/..`

is the parent of A's TARGET, not of the literal string A. So

`<dir>/link/../real/t.hey` and `<dir>/real/t.hey` can be DIFFERENT

files that normalize to the SAME string. That string is used as an

identity in two places: the on-disk parser cache key

(HeyParser.hey:1457-1461) and the in-process import de-dup / cycle

guard (:1579-1602, :1676-1678).

CLAIMED SYMPTOMS: order-dependent — first spelling to populate the

cache wins and the second is silently served the first file's forms

(the dependency-hash re-validation at :1463-1477 re-hashes the LITERAL

norm string, so it cannot see which true file a given caller meant);

and in the single-process import case the second file is never read at

all, so its definitions vanish with no error and no log line.

PROVENANCE / SCOPE: the naive `..` collapse PREDATES the hygiene slice;

the slice widens where that normalizer's output is used as an identity.

So this is NOT a regression introduced by the slice, and the slice

remains a strict improvement on the pre-fix state. Requires an unusual

layout (a symlink whose target's parent differs from its lexical

parent, plus a `../` traversal through it) and is not reachable by any

of the ./ | bare | /./ | /../ shapes the slice's own regression covers.

ORCHESTRATOR RULING: NOT a transplant blocker. Filed as its own

follow-up slice. Likely fix is filesystem-aware canonicalization

(realpath-style resolution at identity-computation time) rather than

more string surgery — a syscall per path is free at compiler scale.

The import de-dup manifestation, if the pin confirms it, is the more

serious half: it is a single-process, cache-independent silent-drop.

SCREEN CORRECTION WORTH KEEPING: the same screen first claimed the

ORIGINAL no-op bug class survives for symlink / absolute-vs-relative /

case-insensitive spellings. Challenged and RETRACTED with evidence: the

no-op needed BOTH key-collapse AND a forms-spelling mismatch, so

UNDER-normalization yields separate self-consistent cache entries

(harmless duplication). The dangerous direction is OVER-normalization —

which is what this entry is about.

[seat: orchestrator] 2026-07-26 ~09:40 PDT — VERIFIED (not assumed):

Files.move IS an atomic rename-over.

runtime/hey_runtime.c:9970 hey_path_move_builtin does

`hey_mkdir_p_for_file(dest) && rename(source,dest)==0`, then fsyncs the

parent. POSIX rename(2) replaces an existing destination atomically —

no unlink, no O_EXCL, no link+unlink emulation, so there is no window

where the published path is missing or half-written. Only failure mode

is EXDEV, unreachable at the publish site because the temp is minted as

a sibling of the destination. Confirmed empirically as well as by

reading. This is the load-bearing fact under the publish design's

"last publisher wins, no torn file" claim, which was previously

ASSUMED. Pinned in test/regression_selfc_publish_lock.sh's header.

NEW, SEPARATE, PRE-EXISTING — found incidentally by the pin and NOT

chased: HeyParser.cache_path crashes on some `./`-prefixed and

[seat: orchestrator] 2026-07-26 ~10:40 PDT — MAINTAINER RULING: file

identity for the parser/HIR cache is (st_dev, st_ino), not a

normalized path string.

DECISION (maintainer, on the pin verdict above): identify a source

file by the FILESYSTEM's own identity — st_dev + st_ino from one

stat(2) — so that relative, absolute, symlinked, hardlinked and

`..`-traversed spellings all collapse correctly by construction. This

is strictly stronger than realpath: realpath still cannot tell you two

distinct paths are hardlinks to one file.

DESIGN NOTES for whoever implements it:

  • inode numbers ARE REUSED after delete+recreate, so (dev,ino) alone

can serve a stale entry for a genuinely new file. Pair it with a

change witness — (dev, ino, mtime, size) — or with the content hash

the dependency check already computes.

  • HeyHir's form matching needs A STRING, and it must be the SAME

string for every spelling: use realpath for the canonical

display/matching value, with (dev,ino) as the lookup identity.

  • DELETE the lexical `seg/../` collapse entirely. It is what

manufactured the confirmed collision, and it is also the code the

pin caught crashing ("slice expects non-negative integer start and

count") and HANGING on some inputs.

  • SCOPE LIMIT to decide once, now: (dev,ino) is MACHINE-LOCAL. A

cache that is ever shared across machines or content-addressed must

key on content hash at that layer instead. Decide it in this slice

rather than twice.

  • Path-key DIRECTION (reversed, filename-first) was considered and is

NOT part of the fix: direction is orthogonal to uniqueness — the

reversed-domain trick buys key LOCALITY (its purpose in

Bigtable/HBase row keys), and for file paths it would cluster by

basename, which is the opposite of the grouping a compiler cache

wants.

QUEUED behind 415a (it touches HeyParser/HeyHir, which 415a is

currently modifying).

REPRESENTATION: DECIDED IN PRINCIPLE. Insertion-ordered FLAT ARRAY,

and a plain HAMT is RULED OUT for the large tier.**

**Hey PRESERVES INSERTION ORDER TODAY**, unsorted. That is observable

behaviour on the JSON round-trip path, so any replacement must

preserve it. This is now a CONSTRAINT, not a preference.

THE STEP, per bench, and it is deliberately small: **replace the

linked list with an INSERTION-ORDERED FLAT ARRAY up to ~32 and do

NOTHING ELSE YET.** At n=46 that is already what Erlang, Clojure and

Immutable.js all do below their crossovers. It beats a linked list on

every axis without hashing, tries or bitmaps — sequential scan instead

of pointer chasing, no per-node allocation, and "clone the map"

becomes an array copy instead of rebuilding a chain node by node. Same

asymptotics, dramatically better constants, and **very likely most of

our measured pain.** Re-measure before adding anything.

TWO FINDINGS THAT CHANGE THE DESIGN:

1. **Erlang SORTS its small maps but does NOT binary search them** —

verified in `erts_maps_get`, it is a linear scan. It pays an O(n)

insertion sort on every write and never cashes in the O(log n)

lookup; the sort exists for cheap map-vs-map equality and merge, not

speed. **THEREFORE: DO NOT SORT.** Unsorted + insertion-order gives

the same lookup asymptotics for free AND keeps JSON key order.

2. **THE ORDER HAZARD IS WORSE THAN I SUSPECTED.** In Clojure the

crossover silently changes iteration order **and the promotion is

ONE-WAY** — `dissoc`ing back below the threshold does NOT revert to

the array map, so **the order loss is PERMANENT even if the map

shrinks back to three keys.** That is exactly why `array-map` is a

separate public constructor: anyone needing the guarantee must opt

in. For Hey, where order is already observable, that failure mode

is unacceptable silently.

**CONSEQUENCE, and it is the decisive one: a plain HAMT is RULED OUT

for the large tier.** If order must survive at all sizes — and our own

round-trip says it must — the shape is PYTHON'S COMPACT DICT: a dense

insertion-ordered entry array plus a sparse index array. CPython 3.6+,

PyPy and Rust's `indexmap` converged on it INDEPENDENTLY. Hettinger's

original numbers, 3-key dict: old 192 bytes -> compact **80 bytes,

58% smaller — and insertion order fell out FREE**, as a side effect of

the entries array being dense and append-only. It was never paid for

separately. That is the rare case where the ordering constraint makes

the design cheaper rather than more expensive.

OTHER NUMBERS FOR THE FILE: Erlang small map = keys+values **+5 words

flat**; a 33-element HAMT is **>=53 heap words** — crossing by ONE

element costs ~10x the fixed overhead. Immutable.js avoids crossover

thrashing with **HYSTERESIS** (grow at 16, shrink only below 8);

**Erlang has none and rebuilds on every operation for a map hovering

at exactly 32.** Any tiered design here needs hysteresis from day one.

CHAMP is a real 16-68% memory win but is a **v2 refinement** — plain

structure first, if at all.

[seat: orchestrator] 2026-07-27 ~01:15 PDT — **ANSWERED, FROM EMITTED

IR: an object LITERAL lowers to a put_key CHAIN. There is no batch

construction path in Hey at all.**

Bench asked whether Hey's literal construction goes through a batch

path or lowers to chained put_key calls, noting it could not answer

from outside and that the answer decides whether the fix is one

function or a lowering change. Measured — `{ 'a':1,'b':2,'c':3,'d':4 }`

emits:

%t0 = call ptr @hey_llvm_json_parse_cstr(ptr @.str.0)

%t1 = call ptr @hey_llvm_json_put_key_i64(ptr %t0, ..., i64 1)

%t2 = call ptr @hey_llvm_json_put_key_i64(ptr %t1, ..., i64 2)

%t3 = call ptr @hey_llvm_json_put_key_i64(ptr %t2, ..., i64 3)

%t4 = call ptr @hey_llvm_json_put_key_i64(ptr %t3, ..., i64 4)

**So the most idiomatic construction in the language — a literal —

is the O(n^2) path**, and it pays it in the emitter rather than in

user code. Every handler building a response literal is on it.

WHY THIS IS THE BEST NEWS IN THE THREAD: the transient/builder fix

needs **no new user-facing surface at all**. It is a LOWERING change,

entirely inside the emitter, on a shape the emitter fully controls and

can see statically. A literal has all its keys known at compile time,

and the object under construction provably has NO OTHER OBSERVER until

the literal expression completes — which is exactly Clojure's

transient invariant (creating a transient does not modify the source;

the transient is never exposed as a first-class value; the only exit is

`persistent!`). Here the "only exit" is the end of the literal.

This also matches what every immutable language actually recommends:

Erlang `maps:from_list/1`, Clojure `(into {} pairs)` — **and `into`

uses a transient under the hood**, which is precisely why it is the

idiomatic fast path. We can have that property without asking users to

write anything different, because we own the lowering.

CONSEQUENCE FOR THE QUEUE: this becomes the highest-value

value-model-neutral slice available. It needs no refcount field, no

API, no architecture ruling — and it removes the quadratic from the

construction shape that the served workload actually executes (23

put_key calls on /health, per the disassembly).

CORRECTION ACCEPTED FROM BENCH, and it applies to my own framing too:

the FLAT ARRAY does not make construction linear. It fixes the O(n)

LOOKUP (which nothing else on the list touches), kills per-node

allocation, and turns clone into a memcpy — highest value-per-risk,

but the construction curve stays quadratic with a much smaller

coefficient, exactly as with put_key_owned. Bench's key-sweep harness

fits BOTH linear and quadratic and reports R^2 for each, so the

post-landing measurement will say plainly which happened rather than

leaving it to interpretation.
