The Billion-Row Bet

During an early attempt at the One Billion Row Challenge (1BRC), a mutable type slipped into Hey — a language whose one defining rule is that every value is immutable — by accident. The maintainer's response wasn't a shrug. It was a wager, on the record, dated today: solve 1BRC — 15 GB, one billion temperature readings — in five seconds, ideally two, using nothing but immutable, zero-copy primitives. Win, and the accidental type gets deleted from the language. The verdict, up front: the bet is ON. The starting line is brutal (today's Hey needs about sixty days for the same job) and the win is not guaranteed — but the gap is arithmetic, not magic, and five of the six pipeline stages the plan needs already exist.

Status: campaign underway — baseline measured, nothing built or shipped yet

This article reports a measured baseline and a design brief, both dated 2026-07-27. The fast 1brc.hey program described in §4 does not exist yet; byte_buffer has not been deleted; nothing here is shipped. What is real: the 15 GB / one-billion-row file, timed on this box, against the real reference programs, with every projection method stated so it can be checked or falsified.

TL;DR

  • The wager is ON, and it is a real deletion, not a hypothetical: build 1BRC on Hey's existing immutable, zero-copy primitives only, hitting ≤5 s (dream: ≤2 s) on the real 15 GB file. If it lands, byte_buffer — the only mutable value type in an otherwise immutable language, and the accidental reason this campaign exists — is deleted, specs and all. The maintainer's ruling, quoted as recorded in the project's coordination log (2026-07-27): "DELETE IT and the specs…but first get the measurements and then come-up with a 1brc.hey program that can pass the 1brc fast (<5s…preferably <2s); baseline numbers, then dispatch."
  • Disclosed weakness, stated first: today's Hey needs ~4.1 milliseconds per row — a projected ~60 days for the full billion. That's the same box that just beat Go's net/http throughput with 95% confidence — on this workload, that language is roughly a million times off the 5-second target. The contrast is the point, not an embarrassment: the web path got fast by deleting per-request costs; 1BRC is the identical story at per-row scale.
  • The world bar is high but arithmetic. The 2024 official 1BRC winners ran in ~1.5 s on 8 dedicated server cores — about 1.1 GB/s (gigabytes per second) of scan-and-parse per physical core. Translated to this 12-core Apple M-series box: the 5-second target needs the equivalent of only 2–3 winner-grade cores; the 2-second dream needs 6–8. High, but not a different universe.
  • The plan already has five of its six stages built. Memory-mapping the file, scanning it with zero-copy views, parsing temperatures with an unboxed integer intrinsic, and fanning work out to worker actors all exist today as immutable primitives. Exactly two gaps stand between today's baseline and the target: a per-worker aggregation step, and the output builder — byte_buffer's only real remaining job.
  • Why believe a per-row cost can actually die: tonight's own receipts. Two fixes landed hours apart cut per-request memory retention 34% (3,640 → 2,388 bytes per request) with the leftover cost named down to the exact functions still holding it. Measured, named, deleted — the same discipline applies to 1BRC's per-row cost.
  • Falsifiable, and honestly hedged. Every projection below is a straight-line extrapolation from a measured slice, method stated inline; numbers from other machines are labeled as such; the targets are goals, not promises; and the baseline is reproducible from this repo's own 1BRC harness against the real file.

Two kinds of number appear below, tagged inline: [MEASURED] for anything timed on this box against the real 15 GB file today, and [RESEARCH] for other people's published results on other hardware, always labeled with that hardware. 1. The accident and the wager

Hey's whole design rests on one rule: every value is immutable. Copy on handoff, never mutate what someone else can see — the rule that makes the whole in-flight plan to share memory by reference, instead of copying it, safe to build at all. byte_buffer is the one type that breaks it: an append-many-times string builder that mutates its backing memory in place, on purpose, every time. According to the project's own account, it didn't arrive as a deliberate design decision — it entered the language by accident during 1BRC work — the project's own recorded account — back when an early attempt at this exact benchmark needed something fast to build output with, and a mutable handle was the quickest way to get one.

That accident has been sitting in the language ever since, failing its own value-semantics guard suite by design (the subject of a companion article, "What Should a Byte Buffer Be?"). This week the maintainer turned the open question into a program with a real stake: "mutable structures are UNWANTED unless truly unavoidable" — so prove byte_buffer is unnecessary by building the one workload that supposedly needed it, using nothing but the immutable primitives already in the language. Beat the real 1BRC file in 5 seconds (2, ideally), and the accidental type gets deleted. Miss, and it stays — recharacterized as a deliberate, documented exception instead of an accident nobody chose.

Term: 1BRC

The One Billion Row Challenge (Gunnar Morling, January 2024; github.com/gunnarmorling/1brc) asks for exactly one thing: parse one billion station;temperature text rows and emit the min/mean/max temperature per station, verified against a reference answer, as fast as possible. It's a real, played-for-keeps leaderboard — and, per a companion survey on this site, a goalpost no immutable-first language has ever won.

2. The starting line, unflinching

The measurement is not flattering, and it's stated first on purpose. Timed today [MEASURED] against the real 15 GB, one-billion-row file, warm page cache, on trunk 445a:

LaneMeasured / projectedBasis
Hey (best lane found: actors, 8 workers) ~59.7 days ~4.13–4.24 ms per row, measured across every worker/chunk case up to 10K rows — every case at or beyond that size already exceeds the harness's own 60-second timeout, so nothing crashes; it is simply that slow, projected linearly
Ruby (1brc.rb, parallel, ~2.5 cores busy) ~12.1 min 7.25 s per 10M rows, projected ×100 — our own parallel port, not a claimed competitive leaderboard entry
C reference oracle (plain, unoptimized) ~8.3 min ~500 s, the correctness oracle this project already uses to check output, not a tuned entry

Source: docs/PERFORMANCE-FINDINGS.md, 2026-07-27 ~12:15 PDT, "1BRC BASELINE." [MEASURED]

Put a single number on the gap and it's arresting: ~5,155,000 seconds projected for Hey versus a 5-second target is roughly a million times off. That arithmetic is worth sitting with, because it's the same box, the same toolchain, that just certified faster than Go's net/http on matched web throughput with 95% confidence. Nothing about that is a contradiction. The web server got fast by finding and deleting a specific, named set of per-request costs (shape-interning locks, boxed value churn, per-connection threads); 1BRC is not a different kind of problem, it's the identical story scaled down to per row instead of per request — a billion rows instead of a hundred thousand requests, and today, nothing in that inner loop has had its costs found and deleted yet. That's not unfixable physics. It's a to-do list — a long one, but a to-do list, and §4 below is most of it already checked off.

3. The world bar: high, but arithmetic

Before setting a target, it's worth knowing what the best programs on Earth actually achieve, on hardware whose size is stated plainly. The official 2024 results [RESEARCH] ran on a Hetzner AX161 (32-core AMD EPYC 7502P), using eight of those 32 cores: the top three entries (Wuerthinger/Mai/Peterssen, Korzun, Hamala — all GraalVM native binaries) finished in 1.535–1.608 s. Every top entry used the same handful of mechanisms, cited at their source: memory-mapped I/O (letting the OS page the file straight into memory, no read() calls), SWAR scanning — reading eight bytes at a time and using branch-free bit tricks to find the field separator, a technique detailed by merykitty in a dedicated write-up [RESEARCH] — and custom hash tables keyed on raw bytes, skipping string allocation until the very last step (InfoQ summary [RESEARCH]).

Do the arithmetic on that result and the file's estimated ~13.8 GB ([RESEARCH], secondary reporting; the official post doesn't state file size): about 9 GB/s aggregate, or ~1.1 GB/s per physical core. Non-Java entries land in the same neighborhood — Danny van Kooten's C port (write-up, source) does ~0.94 GB/s/core on an 8-core Ryzen; a Rust port on an 8-core Zen4 desktop lands near 1.2. Across three independent codebases and three CPU generations, roughly 0.9–1.35 GB/s per core is the practical scan-and-parse ceiling for this workload — nobody credible reports multi-GB/s per core.

Translate that to this box — a 12-core Apple M-series machine, a 15 GB file, no claim that P-cores and the EPYC's server cores run at an identical rate:

  • 5 s target = 3.0 GB/s aggregate — at the winners' 0.9–1.35 GB/s/core, that's the equivalent of about 2–3 of this machine's 12 cores running at winner-grade efficiency.
  • 2 s dream = 7.5 GB/s aggregate — the equivalent of 6–8 of 12 cores, essentially every performance core running at the same per-core rate the 1BRC winners get from their AMD server cores.

High, especially for the 2-second dream — but it is a core count, not a miracle. Page-cache warmth matters here too: every fast time cited above, official and independent, measures with the file already resident in RAM, and this article's own baseline is a warm-cache number for the same reason, stated plainly rather than left implicit.

4. The gist, in one chart

5. The plan: five of six stages already exist

A design brief written for this campaign inventories Hey's existing primitives against what a 2-second-class 1BRC pipeline actually needs, stage by stage, with file-and-line receipts for each claim. The finding: five of the six stages already exist today, as immutable, zero-copy code — nothing new to invent, just to wire together and swap in.

#StageStatus
1Memory-map the file as immutable bytesExists — a zero-copy runtime intrinsic already used by the current 1BRC program
2Zero-copy slice / scanExists — retained views over the mapped bytes, no allocation per scan
3Parse each temperature as a raw-bytes integerExists, unused — a true unboxed integer parse intrinsic sits in the standard library; today's program hand-rolls the same loop instead. A free swap.
4Fan work out across worker actors over one shared mapping Exists, already cheap — handing the mapping to a worker costs one atomic reference-count bump, not a copy; the 15 GB file maps once
5Per-worker aggregation (accumulate stats per station) The dominant gap — today's aggregation step clones its whole accumulator on every update, an O(rows × live-keys) cost that is the main reason the per-row time is measured in milliseconds instead of nanoseconds
6Sort ~10,000 stations and build the output text Exists, minus one piece — the sort is negligible; the output builder is byte_buffer's one remaining real job, and it is off the hot per-row path

Source: agents/linux/notes/1brc-design-brief.md, 2026-07-27. [MEASURED]

Two real gaps, and both already have a name and a plan. The output builder (stage 6) is small: swap byte_buffer for an array of formatted strings joined once at the end — the same "retire behind a spec ban" trick this project has already used once before for a different type. The aggregation step (stage 5) is the harder one, and it just got a ruling: rather than wait days for the full reference-counting program's later stages, a scoped transient accumulator — an object the compiler can prove never escapes the scan loop, mutated in place and frozen only once, at the very end — goes now, using a pattern this project has already shipped once for a different, narrower case. "S3 GOES NOW" is the maintainer's own ruling, dated the same day as this baseline: the 1BRC campaign and the byte_buffer deletion decision do not have to queue behind a multi-week refactor to get their answer.

Term: slice

A slice is this project's unit of work — one focused change, small enough to build, test, and land in a single sitting. Each row of the table above becomes its own slice; the aggregation gap alone is rated a bigger, multi-day slice than the output-builder swap.

When a slice clears every check, the orchestrator merges it to the mainline branch — a landing, one of a strict, ordered queue the project calls the train. The aggregation fix's long-term destination is a broader program called I5 — sharing values by reference count instead of always copying — and 1BRC's in-place aggregation, done safely, would become that program's first real showcase workload once its later stages land.

6. Why believe it: tonight's receipts

The claim that a per-row cost can be found, named, and killed isn't a hope — it happened today, on a different workload, twice, hours apart. A pre-registered memory gate at 443a measured this project's web server's per-request memory retention and found no improvement yet. A follow-up fix landed at 445a, and the same gate, re-run, told a different story [MEASURED]:

Gate checkBeforeAfter (445a)Change
Per-request memory retention3,640 B/req2,388 B/req −34%
Object-clone count (the dominant prior cost)40,09674 dead
Sustained-load collapse under a request storm100% failure 100% success, every runggone

Source: bench outbox, 2026-07-27T19:00:00Z, "445a GATE VERDICT." [MEASURED]

What makes this the right receipt for a 1BRC bet, specifically, is what happened to the leftover 2,388 bytes: it didn't stay a mystery. A live memory census named it down to individual functions — two value-construction helpers and the string duplication underneath them, byte-identical counts across three separate landings while everything else moved. That's the same discipline 1BRC's per-row cost needs: measure it, name the exact function spending it, delete that function's cost, repeat. It is not a metaphor borrowed from a different part of the project — it is the same team, the same gates, the same day.

Pre-registered, on the record

Before any deletion happens, three predictions are staked in writing: swapping in the existing parse intrinsic and the array-based output builder changes zero output bytes and no measurable timing; landing the transient-accumulator fix gets Hey's per-core scan-and-parse rate to the ~0.75 GB/s/core needed for the 5-second target on this box's cores; and byte_buffer's deletion, after that, costs nothing measurable anywhere else in the codebase. Each is falsifiable, each gets a baseline, a prediction, and a named kill condition before it's tested — and the deletion itself only happens after a receipt shows the immutable replacement genuinely costs nothing at the three places byte_buffer is pinned in specs today.

Glossary

1BRC
The One Billion Row Challenge: parse a billion station;temperature text rows and emit min/mean/max per station, checked against a reference answer, as fast as possible.
byte_buffer
Hey's one mutable value type: an append-many-times output builder that writes to its backing memory in place. Subject of a companion article, "What Should a Byte Buffer Be?"
zero-copy
Reading or slicing data by pointing at existing memory instead of duplicating it — the difference between handing someone a photocopy and pointing at the original page.
mmap
Memory-mapping a file: asking the operating system to make a file's bytes appear directly in memory, paged in on demand, with no explicit read() calls.
SWAR
SIMD-within-a-register: reading several bytes at once as one machine word and using branch-free bit tricks to scan them, instead of a byte-at-a-time loop with a conditional.
deci-degree
1BRC's temperature format (one decimal place, e.g. -3.2) represented as a plain integer in tenths of a degree, avoiding floating-point parsing entirely.
slice
See the shared glossary.

See the shared glossary.

See the shared glossary.
