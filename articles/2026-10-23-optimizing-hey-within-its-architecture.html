Fast for Every Program, Not for One Benchmark

Optimizing Hey within its architecture. Making one benchmark fast is easy: teach the compiler to recognise it. Making every program fast is harder: teach the compiler to prove things about any program and act on the proof. Hey has tried the easy way three times and removed it three times. This article shows you how to tell the two apart, using Hey's own history, so you can spot the easy way the next time it looks tempting.

Short version

  • Facts flow down. Hey compiles source → resolver → HIR → MIR → LLVM. Each stage proves some facts and hands them to the next. The last stage, the LLVM emitter, obeys the plans MIR wrote. It never guesses.
  • A cheat is a rule that knows which program it is looking at. A rule keyed on one benchmark's shape, on a hand-tuned library, or on the spelling of an operation can make a number go up while leaving every other program where it was.
  • Hey removed three of them between October 21 and 23, 2026. Removing one made the 1BRC scorecard look about 6x worse, even though the compiler had become 25% better on the same program.
  • The rule now: no release until speed comes from facts the pipeline proves for all programs, measured in time, instructions and memory.

1. The pipeline, in one picture

Before we can talk about cheating, you need a picture of the honest route. Hey's compiler is a line of stages. Each one decides a few things, writes those decisions down, and passes them on. No stage goes back and re-decides what an earlier stage already decided.

Here is what each stage owns, in plain words:

StageDecidesMust not decide
ResolverWhich binding each name means, which module exposes it, the target of each callPrecedence or grouping (the parser did that)
HIR (high-level intermediate representation)The meaning: operations and structured control flowAnything by re-reading raw source text
MIR (mid-level intermediate representation)Blocks, temporaries, how values are stored, and who owns each oneDifferent arithmetic than the language defines
LLVM emitterThe machine-level instructions for each MIR stepReinterpreting source or inventing semantics

Notice what that last row implies. If the emitter is not allowed to guess, then every speed-up has to arrive as a fact from upstream. "This map has exactly one owner, so update it in place." "This list is never used after this line, so its memory can be reused." "This value is always an integer." The emitter just does what the fact says. That is the whole design, and it is what makes the next sections matter.

2. What a cheat looks like

A cheat is not lying about a number. The numbers in each story below were real. A cheat is a rule that makes a number better by knowing which program it is looking at. Try this test on any optimization:

The swap test

Take the program the optimization was built for. Write a second program that does the same kind of work, but with different names, a different record shape, or a different library. Does the second program get the same speed-up?

Yes: you improved the compiler. No: you improved a benchmark.

3. Story one: the region that only fit one tree

Hey 0.99.603a had an optimization written into MIR as a ; regionsite annotation. When a call built a graph of records, the records went into one region (a block of memory whose objects are freed together, in one step) instead of being allocated and freed one by one. That is a good idea; the research behind it is decades old.

The problem was the rule that decided which calls qualified. Its producer rule admitted only records of integers built by recursive calls. In practice exactly one program in the benchmark suite looks like that: binary-trees (the suite's W11). The deletion commit, f8833eff0 on October 21, says it plainly: the producer rule "admitted only the binary-trees benchmark shape." The whole plan was removed end to end: the facts, the annotation, the emitter lowering and the runtime allocator.

Removing it had a visible price. On the Linux scorecard, 0.99.604a's binary-trees cost went from 426.8 to 850.8 instructions per operation. The task notes record why: the LLVM for make_tree and check_tree is identical between the two releases. The only difference is that 603a took its records from the region allocator and 604a pays malloc, free and a recursive release per record. The speed was real, but only that one program had it.

The trap

"The idea is right, so the narrow version is a fine first step." A narrow rule that happens to match one benchmark does not grow into a general one. It sits in the scorecard looking like progress, and it removes the pressure to build the general version.

What to do instead

Keep the idea; delete the rule. The new design (docs/developers/regions-and-reuse.md) restores the sound parts (a function "returns a fresh graph", a value "does not escape", a region "is tied to the smallest scope") and requires a test corpus of different shapes before any benchmark is measured: a word list of records, a station summary, an expression tree, a JSON document and a tiny parser, each with an escaping twin that must not get a region.

4. Story two: the 1BRC library, and the scorecard that got worse

The One Billion Row Challenge (1BRC) reads a huge file of station;temperature lines and prints the min, mean and max per station. Until October 21, Hey's 1BRC examples imported a shared library, examples/lib/one_brc.hey. That library memory-mapped the file (Files.map_readonly) and its code, in the words of the commit that deleted it, "was shaped around compiler limits."

Commit 3ee21f067 replaced it with ordinary Hey, written "the way anyone would write them": read each line, split it at ;, parse the number, keep the stats in a map. Here is the heart of it: 

let line = Files.read_line(file, 256)
let fields = Text.split(line.value.data, ';')
set stats = add_reading(stats, fields[0], Text.parse_fixed(fields[1], 1))

That change shipped in 0.99.604a. Now look at two views of the same week.

What the scorecard saw (Linux, 10M rows)

2,471 instr/row

15,289 instr/row (6.2x worse)

What actually happened (Mac, same plain program, 10M rows)

21,858 instr/row (25% fewer)

Read those two charts together. The scorecard compared a hand-tuned library on the old compiler with plain code on the new compiler, so it mixed two changes into one number. When the same plain program is compiled by both releases, the new compiler is 25% better. The "regression" was the benchmark becoming honest.

And look at the third bar. Plain Hey costs about 67 times C's instructions per row. That gap is the real measure of where Hey stands, and it is a gap in the compiler and runtime: map updates, string splitting, line reading. The library hid it. Now every program that reads lines and fills a map can see it, and every one of them gains when it closes.

The trap

Treating a benchmark program as something to tune. Once the benchmark has its own library, the number measures the library author, not the compiler.

5. Story three: the planner that read spellings

This one is the most instructive, because it happened after the first two lessons and still slipped through. On October 23 at 08:47 PDT, a commit added region planning to MIR (f1dedbede). It licensed a region around a statement when every runtime operation in it was "quiet": it reads its arguments and keeps none of them. To know which operations were quiet, it used a new table, runtime_region_effects.tsv, whose keys were the operations' names: 

len     quiet
has?    quiet
split   quiet
join    quiet
...

And to find the calls in a function, the planner searched MIR text for the characters call @ and for ownership suffixes such as ; own b. It was reverted a minute later, at 08:48 PDT (334c4e96f, with its regenerated bundle in 58e65c6a5).

Why does this count as a cheat, when it was not aimed at a benchmark? Because it rebuilds, from text, facts that earlier stages already decided structurally. A spelling is not who a call is; the resolver decided that. Scanning MIR text for ownership suffixes is re-deriving ownership in a place that should only read it. Even when it gives the right answer today, nobody can audit why, and the next rename or new library breaks it silently.

What to do instead

Key every fact on an identity the resolver produced, carry it as a decoded structure through HIR and MIR, and let a missing fact mean "do the safe, slower thing."

6. The rule going forward

Six minutes after that revert, at 08:54 PDT on October 23, the Maintainer ruled:

"There is NO release until we have optimized within the bounds of the architecture. We do not cheat; we learn how to use hir -> mir -> llvm work for ALL programs."

Two details in that ruling are easy to miss.

Fast paths may ask something of you

A fast path is allowed to have requirements a programmer can see. The Maintainer's example: an explicit to_i makes a value an Int, so a typed integer path applies. That is fine because any program can write to_i. What is not fine is a path only one program can reach.

Measured three ways

Speed, number of operations (instructions retired), and memory. A change that wins on wall time while doubling memory, or that wins on one machine's noise, does not count as a win.

7. How the honest version works

So what does "use HIR → MIR → LLVM for all programs" look like? It is four kinds of fact, each proven inside the existing pipeline, decoded once into structure (identities, types, ownership, effects), and never recovered by spelling or text search.

Fact 1: types and record shapes

If HIR proves a value is always an Int, MIR can store it as a raw 64-bit integer instead of a boxed value, and the emitter emits one add instruction instead of a call. If it proves every record built at a site has the same fields, the record can get a fixed layout. The proof comes from how the value is built and used, not from what the variable is called.

Fact 2: effects

An effect is what an operation might do besides return a value: keep one of its arguments, change it, send it to an actor, write a file. The safe default is "unknown: keep evaluation order, assume anything." An operation earns a stronger claim, such as "reads its arguments and keeps none," only by a declaration attached to its resolved identity and checked. That is exactly what story three skipped.

Fact 3: ownership and last use

This is the idea behind Perceus (below). If a map has exactly one owner, and the old version is never read again after set stats = put(stats, key, value), then nobody can observe the difference between copying it and changing it in place. So change it in place.

Fact 4: regions

For "build, read, discard" work (a parsed document, a list of rows, a tree), reuse does not help: nothing is being updated. Regions do. If MIR proves a freshly built graph never escapes one scope (it is not returned, not stored somewhere longer-lived, not captured, not sent to an actor), the whole graph can be allocated from one block and given back at once.

There are two layers of protection here, and the difference matters:

  1. The runtime safety net. A region's memory is reused only when the region is closed and every object in it has died by ordinary reference counting. So even a wrong compiler fact can never cause a use-after-free; it can only keep memory alive longer. A checked mode reports every region that outlives its scope, and the tests require zero.
  2. The compiler's proof. The plan is for MIR to place regions only where it can prove the graph's owners are dropped or moved out before the region ends, with a verifier that checks that proof instead of trusting it. The Maintainer has decided where they live: as typed facts inside the existing MIR, planned from decoded call identities and ownership, the same decoded facts as everything else.

Why this is auditable

Here is the payoff. Because every fact is keyed on a structural property (a resolved identity, a type, an owner, a last use), an outside reviewer can check one thing: does any rule mention a function name, a field name, a file or a benchmark? The regions design lists that as its first property: "No fact mentions a function name, a field name, a file name or a benchmark." If the answer is no, then whatever speed the benchmarks show, every program with the same facts gets it too.

8. Who did this first, and well

None of this is new, which is the point: Hey should copy the designs that have already worked.

Regions: Tofte & Talpin, the MLKit

Region inference for ML, where a type-and-effect system decides which region each value lives in (Information and Computation, 1997). The MLKit "integrates reference-tracing garbage collection with region-based memory management." Lesson for Hey: tie regions to the smallest scope, never a whole loop, or garbage piles up across iterations.

Perceus and Lean 4

Perceus (Reinking, Xie, de Moura, Leijen, PLDI 2021) inserts exact reference-count operations and reuses a dead, uniquely owned value's memory. Lean 4's reset/reuse comes from Counting Immutable Beans (Ullrich, de Moura, 2019).

Koka's FBIP

Koka calls the resulting style "functional but in place", and promises "you can rely on this optimization happening." That reliability comes from the rule being structural, not a heuristic.

Go escape analysis

Go's compiler keeps a value on the stack when it can prove it does not escape the function. The Go FAQ: "From a correctness standpoint, you don't need to know." Same contract as Hey's: a missing proof costs speed, not correctness.

HotSpot scalar replacement

HotSpot's C2 compiler breaks a non-escaping object into plain local variables; the OpenJDK wiki: "C2 eliminates scalar replaceable object allocations and associated locks." It is the typed-record-shape fact, taken all the way.

9. Spot the cheat

Five proposed optimizations. For each, decide: compiler improvement, or cheat? Then open the answer.

  1. MIR marks a put as in-place when the map's owner is unique and the old map is not used after the statement.
    Answer

    Honest.

    Uniqueness and last use are facts any program can have. This is Perceus-style reuse.

  2. The emitter uses a faster string path when the variable is named line.
    Answer

    Cheat.

    Keyed on a name, and decided in the emitter, which must not guess. Rename the variable and the speed-up disappears.

  3. A table says len, has? and split keep none of their arguments, and MIR uses it to open regions.
    Answer

    Cheat.

    This is story three. The same claim keyed on the resolver's identity for the runtime operation, and checked, would be honest; keyed on the spelling, it is not.

  4. Integer arithmetic takes a raw 64-bit path when HIR proves the value is an Int, for example because the program wrote to_i.
    Answer

    Honest.

    It asks something of the programmer, but anyone can do it. That is the Maintainer's own example of an allowed fast path.

  5. The benchmark's example program imports a helper library that memory-maps the input and walks raw bytes.
    Answer

    Cheat (of the benchmark, not the compiler).

    This is story two. If memory-mapping helps, it belongs in an ordinary library every program can import and the compiler should make ordinary code fast; the benchmark should be written the way anyone would write it.

10. What happens next, in 0.99.606a

0.99.606a is the performance release. Its work list follows the facts above. No dates are promised; the order is the plan.

  1. Facts as structure, not text. Today MIR still carries ownership as text suffixes such as ; own bN that later passes re-scan. The first job is to carry call identity, then ownership, as typed records from the resolver to LLVM, and to type HIR from resolved structure rather than rendered text.
  2. Reuse at last use. One solver for "consumed" and "last use" facts, so put, push and record rebuilding update in place.
  3. Regions and effect proofs on those same facts, with the safety net above.
  4. Typed record shapes: fixed layouts with unboxed integer fields where the types are proven.
  5. Single-probe map updates: has?, read and put on the same owned map and key find the entry once, not three times.
  6. Borrowed string views: Text.split and read_line hand out views into the existing bytes instead of copying.
  7. Actor messaging: move a uniquely owned message to the receiving actor instead of copying it.

Each item starts the same way: a failing gate first (a test that shows the slow behaviour on several program shapes), then the change, then measurements in instructions per operation, wall time and peak memory, before and after, on the same machine. Benchmarks are measured after the general tests pass. They are never used to shape a rule.

Words used here

resolver
The stage that decides which definition each name and call refers to, and gives it an ID.
HIR
High-level intermediate representation: what the program means, as structured operations.
MIR
Mid-level intermediate representation: blocks, temporaries, and who owns each value and when it is released.
emitter
The stage that turns MIR into LLVM instructions, mechanically.
escape
A value escapes a scope when it can still be reached after the scope ends.
last use
The final place a value is read. After it, the value's memory is free to reuse.
region
A block of memory whose objects are allocated together and returned together.
effect
Anything an operation might do besides return a value: keep, change or send its inputs.
instructions per row / per operation
Machine instructions retired divided by work done. Steadier than wall time on a busy machine.
