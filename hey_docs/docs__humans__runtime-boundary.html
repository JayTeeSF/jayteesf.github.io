The runtime boundary in a self-hosted Hey toolchain#

runtime/hey_runtime.c is not inherently a design mistake. A self-hosted compiler means the compiler's parsing, semantic analysis, HIR construction, MIR lowering, and backend policy are written in Hey. Programs emitted by that compiler still need a small target runtime for services LLVM and the operating system do not provide as Hey language semantics.

The maintained pipeline is:

Hey source
    |
    v
Hey-written compiler host
    |
    v
semantic HIR
    |
    v
ABI MIR
    |
    v
direct LLVM consumer
    |
    v
native executable + minimal Hey runtime

HIR precedes MIR. HIR preserves language meaning and source-level type/ownership facts. MIR makes the runtime ABI, storage, ownership, and calling conventions explicit. LLVM consumes validated MIR; it must not rediscover application semantics from source strings.

What belongs in the runtime#

A compact runtime may legitimately own:

  • tagged/boxed value representation and reference ownership;
  • allocation, retain/release, and immutable collection primitives;
  • actor mailboxes, scheduling primitives, supervision, and thread coordination;
  • filesystem, process, pipe, socket, readiness, timer, and platform syscalls;
  • child-process lifecycle normalization and authoritative exit-status collection,

including inherited operating-system signal dispositions that would otherwise auto-reap children;

  • stable ABI shims used by both native-C and LLVM consumers;
  • in-process implementations of canonical primitive-backed stdlib facades when

the alternative would launch compiler subprocesses from an executable or a runtime worker thread;

  • diagnostics that require runtime stack/source metadata.
  • a narrow source-cache dispatcher that validates already-published file stamps

and replaces itself with an immutable cached executable; parsing, graph hashing, compilation, and cache publication remain in the Hey-authored miss path.

These are target services, comparable to a language runtime, libc boundary, garbage collector, or actor VM. Rewriting the compiler in Hey does not make operating-system calls or value representation disappear.

What does not belong in the runtime#

The runtime should not own:

  • parsing or source-language syntax decisions;
  • HIR/MIR construction or optimization policy;
  • application-, benchmark-, spec-, or filename-specific branches;
  • package, docs, vendoring, or release orchestration policy that can be written in Hey;
  • duplicated semantic implementations that bypass canonical HIR/MIR;
  • decorative descriptors pretending to be live resources.

The actual cleanup goal#

The goal is not to delete hey_runtime.c; it is to make its ABI narrow, explicit, portable, and mechanically generated/validated where practical.

A useful decomposition is:

runtime core
  values / ownership / diagnostics

actor runtime
  mailboxes / scheduler / supervision

I/O runtime
  files / process / pipes / network / readiness / TLS

compiler hosts (Hey)
  parse -> HIR -> MIR

backend consumers
  MIR -> LLVM
  MIR -> C validator (secondary only)

The C source may later be split into smaller translation units or progressively replaced with portable runtime components, but that is an implementation-maintenance choice—not a requirement for self-hosting.

Exit criteria for removing C code#

Remove or replace a runtime function only when:

  1. its behavior is expressible safely and efficiently in ordinary Hey;
  2. the fixed-point compiler emits validated MIR for the replacement, with a bounded Stage-0 recovery check while that seed remains;
  3. the direct LLVM consumer and secondary validator agree;
  4. ownership, concurrency, and platform behavior remain covered outside-in;
  5. distributions do not acquire a hidden host dependency.

Focus self-hosting work on the semantic pipeline and fixed-point compiler bootstrap. Keep the runtime boring, general, and independent of any particular program.
