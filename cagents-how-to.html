Cagents · operating guide · 31 August 2026

How Cagents actually fits between you, an agent harness, and Git.

This guide uses real commands and real file paths. “A command” below means an actual process such as claude -p, pi -p, make test, or the Cagents CLI itself—not an abstract box in a diagram.

Read this together with the Cagents architecture page. The architecture page explains what the system is. This page explains what you type, what gets written, what the browser does, what an agent sees, and where the durability boundary really is.

1. There are three different ways a human can talk to agents

Cagents does not require one particular LLM interface. The important distinction is where the conversation enters the system and whether Cagents owns the display boundary.

Slack-like Cagents app

You type into the browser composer. The server writes a canonical message and an unread mailbox ref to the Cagents Git repository. The UI reports success only after that Git mutation succeeds.

Git-first

Claude Code

You can use normal interactive claude, or run a one-shot/headless turn through cagents execution guard -- ... claude -p .... Guarded mode owns stdout/stderr and can enforce persistence before display.

Observed or guarded

Pi coding agent

Same split. Interactive pi is an independently rendering TUI. Pi print mode (pi -p) can be launched under the Cagents guard so the final answer cannot reach the terminal before Cagents persists it.

Observed or guarded

The browser path

you type in Cagents web app ↓ POST /v1/workspaces/:id/actions ↓ Git commit creates post + unread ref ↓ agent's cagents watch / inbox sees it ↓ agent harness does work ↓ agent reply is committed ↓ browser polling/realtime projects committed reply

Notice that the browser is not talking directly to Claude, Pi, OpenAI, Anthropic, or another model provider. It is talking to Cagents. The durable message in Git is the handoff.

The local harness path

If you are sitting at a terminal and want Claude Code to do a single managed turn, the concrete child command can be:

claude -p "Review the failing auth tests and tell me the smallest safe fix."

Or with Pi:

pi -p "Review the failing auth tests and tell me the smallest safe fix."

Those are the “commands” Cagents can guard. They are ordinary executable processes. Cagents launches them, redirects their stdout and stderr into private temporary files, waits for the process to finish, writes the output into the durable Cagents session/message record, pushes Git, and only then copies the buffered output to your terminal.

2. The Cagents repository is the durable coordination authority

A project repository contains stable objects and small refs. It does not require a hand-maintained NOW.md or per-task STATE.md.

projects/hey/
├── PROMPT.md
├── participants/
│   ├── maintainer.ref
│   ├── orchestrator.ref
│   └── chatgpt.ref
├── tasks/
│   └── authority-identity-location-independent/
│       ├── TASK.md
│       ├── events/
│       └── subagents/
├── refs/
│   ├── workflow/in_progress/authority-identity-location-independent
│   └── owner/orchestrator/authority-identity-location-independent
├── decisions/
├── evidence/
├── messages/
│   ├── posts/
│   └── mailboxes/
└── sessions/
Rule of thumb: stable facts are objects; changing relationships are refs; high-frequency runtime facts live outside Git. The CLI derives the “what is happening now?” view from those facts.

3. A real browser message becomes two Git files

Suppose the Maintainer is in project hey and sends this in the web app to orchestrator:

Please verify the authority identity fix before the next heavy compiler run.

The server creates one canonical post, for example:

projects/hey/messages/posts/maintainer/2026/08/cloud-...-maintainer.md

Its content is a normal text record:

---
schema: cagents-post-v5
id: cloud-...-maintainer
project: hey
conversation: channel:general
from: maintainer
to: orchestrator
created_at: 2026-08-31T23:00:00Z
subject: Maintainer message
kind: message
priority: normal
needs_reply: yes
---

Please verify the authority identity fix before the next heavy compiler run.

And it creates an unread delivery ref for that recipient:

projects/hey/messages/mailboxes/orchestrator/unread/2026/08/cloud-...-maintainer.ref

The ref contains the path of the canonical post:

projects/hey/messages/posts/maintainer/2026/08/cloud-...-maintainer.md

When orchestrator reads/acknowledges it, Cagents moves that delivery from unread/ to read/. The post itself does not get copied or rewritten.

That is why the app can be Slack-like without Slack becoming the authority. The UI is a projection over Git-backed posts and mailbox refs.

What the agent runs to see new messages

cd "$HOME/dev/cagents"
git pull --rebase
export CAGENTS_ACTOR=orchestrator
bin/cagents resume hey
bin/cagents watch --interval 30

The watcher periodically pulls and reports newly observed inbound unread messages. It does not create a second inbox database. The unread refs already are the queue.

4. What guarded now means: Cagents actually intercepts the child process

boundary=guarded is no longer a descriptive label you can attach to any process. A direct command such as this is rejected:

bin/cagents execution start \
  --provider claude \
  --boundary guarded

The guarded boundary must be created by the owning launcher:

bin/cagents execution guard --provider claude -- \
  claude -p "Inspect the current task and give me the next safe action."

For Pi:

bin/cagents execution guard --provider pi -- \
  pi -p "Inspect the current task and give me the next safe action."

Both Claude Code and Pi support non-interactive print modes. Claude Code documents claude -p "query"; Pi documents pi -p "query". Their interactive TUIs remain useful, but a TUI draws directly to your terminal and therefore cannot honestly be called guarded unless Cagents itself becomes the terminal host.

Exactly what happens during the Claude example

Cagents allocates a local execution ID.
It records project, actor, Cagents session, provider claude, and boundary=guarded under machine-local Cagents runtime state.
Cagents launches the real process.
The child is literally claude -p "Inspect the current task...". Cagents supplies CAGENTS_ACTOR, CAGENTS_PROJECT, CAGENTS_SESSION, and CAGENTS_EXECUTION in its environment.
stdout and stderr are redirected away from your terminal.
If Claude prints “The authority task is ready…” that text is sitting in a private buffer. You have not seen it yet.
The process exits.
For a successful turn, Cagents marks the execution turn complete, which creates a pending durable-response obligation.
Cagents persists the answer.
The answer becomes a session kind: response event and a canonical Cagents message to the Maintainer. Any buffered stderr becomes a durable tool/session event.
Cagents commits and pushes.
If the push fails, the guard exits with failure and does not release the child's stdout/stderr to the terminal.
Only after the push succeeds does Cagents print the buffered answer.
At this point the screen is downstream of durable state, not ahead of it.
claude -p / pi -p child process ↓ stdout + stderr private Cagents buffers — not visible yet ↓ session event + response message ↓ git commit + push succeeds ↓ terminal finally receives buffered output

A non-LLM example: what capture means

The same display rule matters for ordinary tools. If an agent runs a test suite and wants its output to become part of the durable session, this is a concrete command:

bin/cagents capture -- make test

Here the child command is make test. Cagents buffers its combined output, writes that output as a session tool event, synchronizes Git, and only then prints the test output. The old unsafe shape—where tee printed test output first and checkpointed it afterward—has been removed.

Observed mode is intentionally different

If you run an interactive harness directly:

claude
# or
pi

that TUI controls the terminal. Cagents can observe lifecycle events and record execution status, but it cannot stop the TUI from drawing text first. That is boundary=observed, not guarded.

Current boundary: guarded one-shot/headless child execution is real today. A fully automated controller that takes an unread browser message, starts or resumes the correct Claude/Pi provider session, verifies provider receipt, and then acknowledges the Cagents mailbox delivery is the next larger runtime layer. Until that controller exists, the watch/inbox step and harness invocation are separate operations.

5. Project membership has one authority

Global actor files establish identity. They do not automatically make an actor part of every project.

agents/orchestrator/START.md
agents/linux/START.md
humans/maintainer/START.md

Permanent project membership is explicit:

projects/hey/participants/orchestrator.ref
projects/hey/participants/maintainer.ref

For example, projects/hey/participants/orchestrator.ref contains exactly:

agents/orchestrator/START.md

The CLI and hosted application use those refs to decide who can send, receive, view a project, and appear as a recipient. A globally known linux actor is not automatically a hey participant just because agents/linux/START.md exists.

bin/cagents participant list --project hey
bin/cagents participant list --global --project hey
bin/cagents participant add linux --project hey
bin/cagents participant remove linux --project hey
Broadcast now means project broadcast. bin/cagents send --to all ... expands over projects/<project>/participants/*.ref, excluding the sender. It does not enumerate every actor in the repository.

6. TASK.md, task show, and now are different things

TASK.md is not deprecated. It is the stable task object: identity, title, priority, durable scope, and stable references. The old per-task STATE.md model is what was removed.

Suppose this task exists:

projects/hey/tasks/authority-identity-location-independent/TASK.md

Its current workflow and owner are represented separately:

projects/hey/refs/workflow/in_progress/authority-identity-location-independent
projects/hey/refs/owner/orchestrator/authority-identity-location-independent

So the two useful queries answer different questions:

# “What across this project needs attention?”
bin/cagents now --project hey

# “Tell me everything relevant about this one task.”
bin/cagents task show authority-identity-location-independent --project hey
CommandScopeWhat you get
cagents nowwhole projectshallow board: workflow, owner, priorities, attention
cagents task show IDone taskcanonical TASK.md plus derived status/owner, linked decisions/evidence, latest events, child runs

7. A practical daily workflow

Start or resume a persistent agent

cd "$HOME/dev/cagents"
git pull --rebase
bin/install-cagents-tools

export CAGENTS_ACTOR=orchestrator
bin/cagents resume hey

# keep incoming durable messages visible
bin/cagents watch --interval 30

resume derives the project board and active task views. It also runs restart checks, including execution-response obligations that were left incomplete.

Inspect the work

bin/cagents now --project hey
bin/cagents task show authority-identity-location-independent --project hey
bin/cagents inbox --project hey
bin/cagents live --project hey

Record a finding while working

printf '%s\n' \
  'Launcher identity must use logical relative path + content hash; realpath is provenance only.' | \
bin/cagents finding \
  --project hey \
  --task authority-identity-location-independent

Reply to the Maintainer

cat >/tmp/reply.txt <<'EOF'
The authority identity fix is ready for the isolated control run.
I have not run the heavy launcher yet.
EOF

bin/cagents reply \
  --project hey \
  --to maintainer \
  --subject 'Authority identity status' \
  --body-file /tmp/reply.txt

The body becomes both a session response event and a project message. Cagents commits and pushes those files before printing the same body to the terminal.

Delegate bounded work

bin/cagents dispatch \
  --project hey \
  --task authority-identity-location-independent \
  --label verify-rename-invariant \
  --provider claude \
  --acceptance 'same content at a renamed checkout path preserves logical identity'

The parent task remains owned by the persistent agent. The sub-agent run is an attempt with its own assignment, events, result, and optional integration candidate.

8. What failure looks like

If Git push fails during a normal Cagents reply

The reply is not printed as a successful durable response. You get an error instead. There is no “terminal-only fallback.”

If Git push fails during guarded Claude/Pi execution

The child may already have completed, because the model process is local/external compute. But its buffered stdout/stderr stays behind the guard. Cagents does not release that output to your terminal as though the turn were safely recorded.

If an interactive Claude/Pi TUI is used

The TUI can display independently. Cagents can mark the execution observed and detect missing durable follow-up, but it cannot retroactively make already-drawn text satisfy a write-before-display invariant.

If the browser cannot commit

The browser composer reports that the message was not sent. It does not clear the input and pretend success before the repository write succeeds.

9. The complete mental model

DURABLE CONTROL PLANE Maintainer / browser ──message──► Cagents Git posts + mailbox refs │ ├──► tasks / refs / decisions / evidence │ └──► sessions / responses / run provenance EXECUTION PLANE Claude Code / Pi / other harness │ ┌────────────┴────────────┐ │ │ observed TUI guarded child draws itself stdout/stderr buffered Cagents observes by Cagents │ │ └────────────┬────────────┘ ▼ local execution ledger │ ▼ durable semantic writes to Git

The key is that Cagents is not trying to replace every agent harness. It supplies a common durable coordination graph and, where it owns the process boundary, a common persistence-before-display guarantee.

10. Useful commands at a glance

# bootstrap
bin/cagents resume hey
bin/cagents watch --interval 30

# project overview and task detail
bin/cagents now --project hey
bin/cagents task show TASK_ID --project hey

# communication
bin/cagents inbox --project hey
bin/cagents send --project hey --to orchestrator --subject '...' < body.txt
bin/cagents ack --project hey
bin/cagents reply --project hey --to maintainer --subject '...' < reply.txt

# membership
bin/cagents participant list --project hey
bin/cagents participant add ACTOR --project hey
bin/cagents participant remove ACTOR --project hey

# observed runtime
bin/cagents execution start --project hey --provider claude --boundary observed
bin/cagents execution event --id EXEC --event PreToolUse
bin/cagents execution audit --project hey

# guarded real child process
bin/cagents execution guard --project hey --provider claude -- \
  claude -p "Review the current task and report the next safe action."

bin/cagents execution guard --project hey --provider pi -- \
  pi -p "Review the current task and report the next safe action."

# ordinary command output with durable-before-display capture
bin/cagents capture --project hey -- make test

# graph integrity
bin/cagents graph audit --project hey
bin/cagents restart-gate --project hey
External harness references: Anthropic's Claude Code CLI documents claude -p "query" as non-interactive print mode. Pi's coding-agent CLI documents pi -p "query", plus JSON and RPC modes for process integration. Cagents uses those headless/process-oriented modes when it needs to own the display boundary; it does not depend on one LLM provider.
