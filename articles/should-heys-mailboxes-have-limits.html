Should Hey's Mailboxes Have Limits?

A decision brief. When senders outrun a receiver, something has to give: memory grows, the sender waits, the send fails, a message is dropped, or the scheduler slows the sender down. Here is what ten actor and channel runtimes choose, what each choice costs, and the options for Hey.

Short version

  • Hey today: mailboxes are unbounded and send is a statement that never waits, never fails and never drops. In a test where 8 fast senders feed one actor, the backlog reached 850–890 MB.
  • Most actor runtimes default to unbounded too (Erlang/Elixir, Akka, Pony, Swift, Ray). The ones that bound by default (Go channels, Kotlin's actor, actix) are channel-first designs where waiting is the normal way to send.
  • No option is free. Waiting can deadlock cycles of actors and needs the handler to be able to suspend. Failing turns send into an expression every caller must check. Dropping loses messages silently. Scheduler-level slowing (Pony) keeps the language unchanged but bounds memory only in practice, not as a guarantee.
  • Recommendation: keep send unbounded by default and add, in order: (1) visibility, meaning queue length and high-water marks you can read and alert on; (2) Pony-style scheduler backpressure as an automatic safety net; and (3) opt-in per-actor limits with an explicit overflow policy, for actors that need a hard bound. Details and alternatives below.

What Hey does today

  • send pid, message is fire-and-forget. It has no result, so it cannot report "full".
  • Mailboxes grow without limit. The rewritten scheduler made a send one atomic operation with no lock, which makes sending even cheaper and fast producers even faster.
  • The one existing limit is on Actor.call (request/reply): at most 1,024 callers may be waiting. Further calls fail with actor_call_overloaded. That bounds waiters, not the mailbox; requests that timed out can still sit in the queue.
  • Actors already have link, monitor and supervision, so "let it crash and restart" is available as a recovery tool.
  • Measured on the rewritten scheduler (a shared 12-core Mac, so indicative rather than qualified): an idle actor costs about 137 bytes; 8 senders × 1,000,000 messages into one actor reached 4.7–5.2 million messages per second with an 850–890 MB peak backlog, because nothing slows the senders.

The six things a runtime can do when a mailbox is full

  1. Grow. Keep queueing. Simple and never blocks, but memory is unbounded and latency grows silently.
  2. Wait. The sender blocks or suspends until there is room. This is real backpressure, but it can deadlock when actors send to each other in a cycle, and a waiting actor holds its turn.
  3. Fail. The send returns an error ("full") and the sender decides what to do. It is explicit, but every send site must handle the result.
  4. Drop. Discard the newest or oldest message, or route it to a dead-letter queue. Memory is bounded and the sender is never blocked, but messages are lost.
  5. Throttle senders in the scheduler. The runtime notices an overloaded receiver and deprioritizes or pauses the actors that send to it. The language does not change, but the bound is practical, not guaranteed.
  6. Kill on overload. Past a size limit the overloaded actor is terminated, and supervision restarts it. Crash-only, and the queued messages are lost.

A seventh pattern lives above the mailbox: demand-driven pipelines, where consumers ask for N items and producers send no more than that (Elixir GenStage, Akka Streams, reactive streams). These are libraries built on top of the mailbox, not mailbox policies.

Two patterns stand out. Runtimes built around actors default to unbounded queues and add backpressure elsewhere: in synchronous calls, in the scheduler, or in stream libraries. Runtimes built around channels bound by default, because suspending the sender is cheap and idiomatic there.

The trade-offs, in Hey's terms

Waiting (block or suspend the sender)

  • Deadlock in cycles. If actor A waits on a full B while B waits on a full A, both stop. Ring, pipeline and request/reply topologies are exactly where this happens, and Hey's own benchmarks include rings.
  • Needs a suspendable handler. On the new scheduler a handler that blocks would hold a worker thread. Making a send wait cheaply needs the same machinery as the pending sleep-as-suspension decision (below): the compiler turns the handler into a resumable state machine. Without it, waiting means burning threads.
  • Changes existing programs. Programs that relied on send never pausing would start pausing under load.

Failing (send returns "full")

  • Explicit and predictable, but send is a statement today. Making it return a result changes every call site, or needs a second form (for example try_send) alongside the existing one.
  • Callers then have to choose what to do: retry, drop, or escalate. In practice this often becomes a retry loop, which is waiting under another name.

Dropping (newest, oldest, or to dead letters)

  • Memory is bounded and senders are never blocked. This is the right choice for telemetry, progress updates, "latest value wins" state and UI refreshes.
  • Wrong for commands and requests: a dropped {kind: 'charge', ...} is a correctness bug. It also weakens "per-sender order is preserved" into "preserved for the messages that survived".

Scheduler throttling (Pony-style muting)

  • No language change: send keeps its meaning (never fails, never drops), and it fits the new scheduler, which already knows each actor's queue and batch.
  • The bound is practical, not hard: a single huge burst still queues. A muted actor can look hung, and cyclic topologies need care so that two actors do not mute each other indefinitely.
  • It does not see pressure from outside the program (slow sockets, disks); that needs an explicit API like Pony's Backpressure.

Kill on overload (Erlang-style limit plus supervision)

  • Fits Hey's existing link/monitor/supervision: the actor exits with a reason such as mailbox_overflow and its supervisor decides what happens next.
  • Loses everything queued, and is a blunt instrument. It works as a last-resort guard set far above normal use, not as flow control.

Recommendation

  1. Now: A. It changes no semantics and makes every later decision measurable.
  2. Next: B as the default safety net, built into the new work-stealing scheduler, with stress tests for cyclic topologies before it ships. It bounds the common runaway case (the 8-senders test) without touching the language.
  3. Then: C as opt-in, starting with the policies that need no suspension (fail via try_send, drop_newest, drop_oldest), and adding wait once handlers can suspend (the same compiler work as sleep).
  4. Optionally E as a high, opt-in ceiling for actors whose supervisor should restart them instead of letting memory climb.
  5. Avoid D. It changes what every existing send means and brings deadlock risk to the most common actor topologies, in exchange for a guarantee that A, B and C deliver more safely.

Decision needed: approve, adjust or reject each step. Any step marked "Yes" under language change needs your ruling on syntax and names before it is built.

Related pending decision: sleep inside actors

"Make sleep behave like await" turned out to have design consequences, because today's await does not pause the handler: it ends the handler, and the result arrives later as a new message. The options are:

  • A. Keep blocking. Unchanged meaning. On the new scheduler a sleeping actor costs one OS thread (about 16 KB) instead of a whole core.
  • B. End the handler and deliver a timer message later (the Akka and Pony style). This changes meaning: code after sleep would no longer run in that turn. If wanted, it belongs under a new name such as send_after.
  • C1. True suspension of sleeps written directly in a handler. The compiler makes the handler resumable and no other message for that actor runs meanwhile, so the meaning is unchanged and only the cost drops. Sleeps inside called functions keep option A's behavior. This is the recommended option, and it is the same machinery a waiting send (option C above) would need.
  • C2. Suspend through any call depth by making every function that can reach a sleep resumable. Complete, but a very large compiler change.
  • C3. Small pooled stacks per handler (Go-style). Covers any call depth, costs a few KB per sleeping actor and two context switches per turn.
