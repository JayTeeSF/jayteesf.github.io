Hey 547a: the front end is built, and its authority is converging.

The structural tokenizer, generated syntax tree, name resolver, structural HIR, MIR, and LLVM emitter all exist and run. The three-representation shape has not changed. What has changed since 533a is who owns cross-unit meaning: the resolver now writes its knowledge into the MIR as semantically-neutral extern facts, and the Hey-owned emitter lowers them mechanically instead of the backend re-inferring them. Authority is converging on a single source.

Source checkpoint: 0.99.547a, commit 2e6313f8 Branch trunk, tree clean Deployment: not asserted

TL;DR

  • Verdict: the core three-IR architecture — source → tokens → tree → HIR → MIR → LLVM — is unchanged. 547a is authority-convergence progress on the 533a thesis, not a new architecture.
  • Strongest result: the Hey-owned emitter now covers 111 of 132 corpus units (2 fallback, 19 fail-to-build), freshly re-measured from 547a trunk with sh tools/hey_llvm_gap_census.sh.
  • Mechanism: HeyNames signatures become semantically-neutral extern / Module.method facts carried through the MIR; the emitter lowers them mechanically via json_call. That is a backend lowering choice — the eventual flip to real hey_fn_* symbols touches only lowering.
  • Rulings: modules are not first-class runtime values (Option A — compile-time selectors only); dedicated native-C facade lowerings take precedence over the extern→json_call route.
  • Disclosed weakness: 19 corpus units still fail to build, json_call is a mechanical placeholder rather than real symbols, and the compiler-contract lane still carries 25 pre-existing failures — with zero introduced by this work.
  • Falsification: re-run sh tools/hey_llvm_gap_census.sh for 132/111/2/19, and confirm the contract lane is byte-identical to the parent after each slice, as the differential verify does.

What changed since 533a

The 533a report ended on a clean sentence: the new front end exists, but two gates still block one authority. The emitter could not lower the whole structural program, and cross-unit meaning was still being reconstructed downstream instead of established once and carried forward.

Since then this work has done one thing well: it made cross-unit calls flow the way single-unit code already did. The name resolver knows every module signature. Until recently that knowledge died at the resolver boundary, and the backend guessed the rest. Now the resolver writes those signatures into the MIR as plain, semantically-neutral facts — an extern line, or a normalized Module.method receiver — and downstream stages trust them instead of re-deriving them.

That is the whole shape of the update. The architecture did not gain a fourth IR or lose one. It moved a decision earlier and stopped repeating it.

Why json_call is a lowering choice, not a semantic one

The important discipline here keeps the architecture honest. The extern fact in the MIR says what is being called and with what shape. It does not say how the backend must reach it. Today the Hey-owned emitter reaches it through a generic json_call dispatch. The MIR source itself records the plan in a comment: json_call dispatch today, real hey_fn_* symbols later.

That separation is why the flip is cheap. When the emitter later resolves these to direct hey_fn_* symbols, nothing in the resolver, the HIR, or the MIR needs to move. Only the lowering step changes. The language semantics were fixed the moment the resolver wrote the fact down.

Two rulings keep the mechanism from over-reaching:

Option A: modules are not runtime values

A module is a compile-time selector, never a first-class value you can pass or store at runtime. Receiver-sugar module calls are canonicalized at resolve time, so the backend never has to model a module as data.

Native facade wins precedence

Where a dedicated native-C facade lowering exists for a call, it takes precedence over the generic extern→json_call route. The mechanical path is the fallback for the frontier, not a replacement for hand-tuned facades.

The most recent landing (2e6313f8) shows the convergence in miniature. A resolved boxed cross-unit call used to sit outside the normal comparison machinery. Now an expression of the form <resolved extern call> OP <literal> enters the same relational-comparison path as any other boxed comparison, through the shared helper hey_llvm_cmp_expr_value, which dispatches to hey_llvm_value_cmp_i64 — the runtime-type-aware semantic authority. Two corpus units, bits_flags and bloom_filter, flipped to covered because their cross-unit comparisons stopped needing a special case.

The durable division of responsibility

Hey's design is clearest when each stage is allowed to answer one kind of question and forbidden from rediscovering earlier answers. The 547a work is an instance of exactly that rule: cross-unit facts are answered once, at name resolution, and never re-answered downstream.

Tokenizer

Owns spelling, token boundaries, and source spans. It does not decide names or types.

Syntax tree

Owns grouping, precedence, argument shape, and generated node structure. The schema generates constructors, accessors, child lists, walkers, rewriters, and coverage checks.

Name resolution

Owns lexical bindings, module surfaces, aliases, receiver candidates, private names, and actionable missing-name diagnostics. As of 547a it also emits neutral cross-unit facts into the MIR.

Structural HIR

Owns program meaning and compiler-internal types. Users do not write type annotations; calls, casts, operators, and values carry structural facts downstream.

MIR

Owns explicit evaluation order, named temporary identities, representation choices, ownership/lifetime operations, and now the validated extern / Module.method facts.

LLVM emitters

Lower MIR decisions to typed SSA text. They must not infer source semantics from strings. The native emitter is a differential oracle today, not the permanent architecture.

Runtime

Owns values, reference counts, actor mailboxes and handles, built-ins, I/O, web primitives, and target ABI behavior.

Products and packages

Recapture web, CLI, iOS, Android, tvOS, and application behavior after authority changes. Compiler gates are necessary, never sufficient product evidence.

Two execution modes, and why only one is production

A recurring confusion is worth settling directly: the pipeline above is the compiled path, and it is how Hey actually ships. Hey programs compile to native machine code through LLVM — that is how shipped programs and the self-hosting compiler itself run. Hey is not "sometimes interpreted, sometimes compiled" in the sense of an unpredictable runtime; every product build is compiled.

There is also a tree-walking interpreter, and it has three specific jobs. It is deliberately simple and deep-copies values, so it is substantially slower than compiled code — it exists for interactivity and bootstrapping, not for production.

Compiled path (production)

Source → tokens → syntax tree → Structural HIR → MIR → LLVM → native machine code. Every shipped program and the self-hosting compiler run here. This is the entire pipeline documented on this page.

Interpreter (REPL & scripts)

Powers the interactive REPL and quick one-off scripts (heyc <file> --run). Optimized for start-up and interactivity, not throughput.

Interpreter (bootstrap seed)

Builds the very first compiler before Hey can compile itself. Once the compiler exists, ordinary builds no longer depend on it.

Why it looks slow

The interpreter deep-copies values by design, which makes it the right tool for counting allocations and the wrong tool for judging speed. Alarming tens-of-seconds figures come from running measurement harnesses inside it on purpose.

The takeaway: when reading any Hey benchmark, first ask which mode produced it. A product runs the compiled side; the interpreter's numbers describe interactivity and allocation shape, not shipped speed.

What compiler research supports—and what it does not prove

MLIR's rationale describes progressive lowering through representations suited to different abstraction levels, while the project emphasizes IR specifications, verifiers, textual round-tripping, and modular passes. That supports Hey's choice to keep syntax, structural HIR, MIR, and LLVM distinct rather than forcing one representation to answer every question — and, at 547a, to carry a neutral cross-unit fact through MIR rather than re-deriving it in the backend. It does not prove Hey's particular lowering is correct.

Rust's compiler documentation says MIR is built from typed high-level IR/THIR. That is a useful analogue for Hey's target: type and call facts should be established before MIR/LLVM emission, not guessed from expression text in the emitter.

Andy Keep's Nanopass dissertation argues for many small passes, formally described intermediate languages, well-formed output checks, and generated boilerplate. Hey's HeyMir.validate pass on the neutral facts is compatible with that discipline: each stage has a narrow input contract and a checkable output.

Python's AST documentation notes that concrete node classes derive from the Parser/Python.asdl grammar. That is direct precedent for Hey's decision to generate node construction and traversal from one schema instead of relying on every hand-written walker to remember every field.

The Csmith study by Yang, Chen, Eide, and Regehr, Finding and Understanding Bugs in C Compilers, found wrong-code defects even in unverified frontend portions of CompCert. The lesson for Hey is practical: a strong backend does not compensate for semantic facts being wrong before code generation.

Translation validation checks each compilation result rather than proving the compiler once. Hey's native-versus-Hey byte identity is inspired by the same "validate this run" instinct, but it is narrower: byte equality between two related emitters is differential evidence, not a proof of semantic preservation.

Xavier Leroy's CompCert account is the important contrast. CompCert carries machine-checked semantic-preservation proofs across defined languages and passes. Hey does not. Its current evidence is executable gates, differential text, mutation tests, and application receipts, and this page keeps those categories separate.

What not to claim

"The architecture changed at 547a."

Wrong. The three-IR structure is identical. What changed is which stage owns cross-unit meaning.

"The authority switch is done."

Wrong. The emitter frontier is a converging precondition (111/132), not the switch. 19 units still fail to build and the switch is a separate, later landing.

"json_call is the permanent calling convention."

Wrong. It is a mechanical lowering placeholder. Real hey_fn_* symbols are the intended lowering, and moving to them touches only the emitter.

"Modules are runtime values."

Wrong. Option A ruled them compile-time selectors only. The backend never models a module as data.

"Byte-identical LLVM means the compiler is verified."

Wrong. It is strong differential evidence against one independent implementation and a useful regression oracle. It is not a semantic proof.
