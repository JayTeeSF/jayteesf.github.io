A Ruby Port Ate 50 GB of RAM. The Bug Wasn't in My Code.

A 606-line Ruby archiver, ported to Hey, killed a terminal at roughly 50 GB of resident memory. Chasing that number over one night surfaced five failure classes, every one of which failed silently. The case file: what we saw, what we believed, what was true, what makes each loud now.

TL;DR

  • ~50 GB of RSS and a dead terminal, from a file-reading loop that could never terminate. The reduced reproducer hit 4.9 GB in ~20 seconds on a ten-file fixture.
  • That loop was my bug. Underneath it sat a compiler bug: the idiomatic list append retained every intermediate copy. 16,000 appends cost 2,741 MB; after the fix (v0.99.406a, 2026-07-25), 5.7 MB — 481×. That number has held up.
  • The server version of that leak took five attempts, and the fourth was a retraction I had to retract in public. It is real, at ~13,200 bytes per request, flat. It kept looking like it "came back" because macOS resident_size excludes compressed pages — so the number nearly every tool reports falls while the process keeps growing. On phys_footprint the same server reads 11,991 MB while resident claims 709 MB. My proudest disproof — "that rate implies 37 GB on an 18 GB machine" — died on a premise I never measured: the box had 5.8 GB of swap already in use. Exhibit B.
  • Three more silent classes fell out: a benchmark baseline that was a dead binary timing its own death at 2.3 ms, a compiler that deleted statements, and a cache race that published a poisoned compiler component — minting scripts that do nothing, deterministically, keyed by how you typed the path.
  • Disclosed weakness: these are the bugs a young self-hosting language has. The story is the detection method and the ~24-hour fix loop, not an absence of bugs.
  • Falsifiability: the parity gate is bin/check in source_zip (9/9 green, both lanes); probes in the war-room repo under bench/probes/; every figure dated in PERFORMANCE-FINDINGS.md.

How to read these numbers

Apple M-series machine throughout. Memory figures are RSS — the RAM a process occupies right now — sampled immediately after each run, before macOS compresses idle pages and flatters the result. CLI timings are hyperfine over a synthetic git corpus, one output directory per lane, every cell asserting expected output bytes rather than an exit code of 0. Anything measured under load is a lower bound.

The crash

The task was mundane: port source-zip, a Ruby tool that walks a git tree and packs it into an archive. The port passed its parity gate. Then someone ran it on a real tree and the terminal died — not slowed, died, the way processes go when the OS's jetsam mechanism reclaims memory from whoever asks for the most. Last observed RSS: roughly 50 GB, with no exception, warning, or log line. A crash is a gift: it tells you where and when. Every bug here declined to.

Exhibit A: the loop that could not end

SYMPTOM. Memory climbing at gigabytes per second during a file read. No output, no error, no termination. Killed by the OS.

WHAT WE BELIEVED. A pathological input — an enormous file, or a symlink cycle.

WHAT WAS TRUE. Io.read does not return a string. It returns a record, {data, count, eof}. My drain loop came from Ruby muscle memory, where a read returns a string and an empty string means "done": 

let chunk = Io.read(handle, 65536)   # {data, count, eof} — never a string
while chunk != '' {                  # a record is never equal to ''
  set out = out + chunk              # '+' stringifies the record, forever
}

The comparison can never be true, so the loop never exits, and + stringifies the record onto a growing buffer every pass. Two forgiving behaviours — a comparison that returns false instead of objecting, an operator that stringifies instead of refusing — compose into an unbounded allocator. On a ten-file fixture: 4.9 GB in about 20 seconds before SIGKILL.

WHAT MAKES IT LOUD NOW. Honestly, not enough: a committed reproducer and a rule ("never compare an Io.read result to a string"). A type error on that comparison is the real fix, and it belongs upstream. This is the exhibit where my code was at fault, and the one with the weakest guard.

Exhibit B: the ghost of every list that ever existed

SYMPTOM. Two, believed unrelated until the night they turned out to be one. The port lost badly to Ruby on big trees, memory growing far faster than the data. And a Hey web server sat at 919 MB while idle — spotted not by a dashboard but by the maintainer looking at Activity Monitor.

WHAT WE BELIEVED. That the append idiom was merely quadratic in time, and separately that the server leaked in request handling.

WHAT WAS TRUE. set xs = [...xs, item] was quadratic in peak memory. Every intermediate list stayed alive: add 16,000 items and you hold not one 16,000-item list but the ghost of every list on the way there. Measured: 2,741 MB for 16,000 appends in the spread form, 3,058 MB in the push form. A 30–60,000-file tree reaches the 50 GB class on its own. Exhibit A was the fast half of the crash, not the whole.

The server was the same bug in office clothes: on a fresh instance, memory went 2 MB → 577 MB across 99,314 requests that reused one connection rather than opening a fresh one each time — dead linear, ~5.8 KB per request (v0.99.402a-era trunk, 2026-07-25). That rate is the right order of magnitude for a server idling at 919 MB, but not the tidy arithmetic I first published: I wrote that 310,000 requests × 5.8 KB "is exactly 919 MB", and it is not — that product is about 1.7 GB. The screenshot still became the acceptance test, but the reconciliation was false precision, and both of its numbers came from the measuring method I retract two sections below. A satisfying coincidence nobody checked, in an investigation about exactly that.

The correction that matters more than the fix

Our first diagnosis was wrong, and it belongs here at the same size as the result. We said the compiler "forgot to free the old value" on reassignment. Plausible, and it would have justified exactly the same patch — which is what made it dangerous. The upstream red team refused it and found the real mechanism: clone-and-abandon. The compiler built the new value, made a full deep copy, stored the copy, and orphaned the original. A fix on the wrong mechanism passes the same benchmark and leaves the class alive elsewhere.

WHAT MAKES IT LOUD NOW. v0.99.406a (2026-07-25) fixed the reassignment path: 16,000 appends went 2,741 MB → 5.7 MB (481×) in the spread form and 3,058 MB → 7.2 MB (425×) in the push form, verified twice on independent harnesses. The lasting guard is the instrument, not the patch: an RSS-versus-N flatness probe that fails if memory grows with list size.

The third row took five attempts, and one of them was a retraction I had to retract. It read "~5.8 KB → ~500 B per request, 12×"; then a far more alarming 13,340 bytes per request; then — briefly, and in public — "there is no per-request leak at all, that figure is the slope of a warm-up ramp." That fourth answer was wrong, and the reason is worth more than the number. macOS resident_size excludes compressed pages. When the compressor starts evicting cold garbage, the number nearly every tool reports falls while the process's real commitment keeps climbing. On phys_footprint — the ledger the kernel actually kills on — the slope is 13,202 bytes per request over fourteen consecutive intervals and never once negative, ending at 11,991 MB committed against 709 MB resident: a 16.9× under-report. The leak is real; the instrument was blind; and my disproof of it rested on "the machine never swapped," which I asserted without looking at a box that already had 5.8 GB of swap in use.

Exactly what is measured, and not a word past it: retention is ~13.2 KB per request and holds linear to at least 939,000 requests (~12.4 GB); accumulation must bound somewhere at or above that point, and neither the location nor the mechanism of that bound has been measured. Something plainly stopped a 67 GB trajectory — longer runs reached five million requests at flat throughput. But I have measured a floor on where the bound is and nothing else about it, I went looking for a recycler that would explain it and the one candidate in the runtime does not fit, and a bound whose mechanism nobody can name is not reassuring — it is suspicious. This article is a list of four confident numbers that were guesses wearing a number's clothes. I am not adding a fifth to the end of it.

Exhibit B has one more retraction, and it is mine

I first reported that the server side was cured outright — that after the fix, two million further requests took memory down, a bounded working set rather than a leak. That was an artifact of a bad instrument. Sampling a process's memory with ps after a load run measures whatever macOS has finished compressing and reclaiming by the moment you look; run the same test twice and you get 3,271 MB and then 1,100 MB, which would imply memory going backwards at 4 KB per request. The correct instrument arrived the same afternoon — v0.99.410a, 2026-07-25 — when the runtime learned to report its own memory from inside the process while serving: 329 MB after 778,040 requests, about 440 bytes each. The compiler team's leak checker, run separately on a lighter handler, said 490–514 bytes; two instruments that cannot lie to each other landing within 15% is the closest thing to proof this investigation produced. So the honest number is that this fix cut per-request retention roughly 12×, from ~5.8 KB to ~500 B. It is still linear. The remaining half is a different bug — compiled functions never releasing their temporaries — and its fix is in flight as I write this.

Mechanism: why "byte-identical emission" was the receipt that mattered

Three acceptance criteria worth stealing. byte-parity of the compiler's own output: for every program that did not have the bug, emitted code unchanged byte for byte — proof the change touched only the broken case. ASAN clean: AddressSanitizer watches every memory access during the test run and reports use-after-free, overruns and leaks; it found nothing. (Its sibling TSAN catches data races, and covered the dispatch fix that stopped worker threads deep-copying shared route data.) And borrow-safety: since the fix works by not copying, the shortcut had to be proven incapable of leaving a reference into freed memory. The verifier, allowed to argue back, found a third leak site nobody listed.

Exhibit C: exit 0, no output

SYMPTOM. A benchmark binary appeared to run 9× slower after an innocuous toolchain update. Alarms, a routing-regression theory, a cache-key theory.

WHAT WE BELIEVED. That the fast measurement was the truth and the slow one was the regression — the default assumption of every performance investigation, load-bearing in a way nobody examines.

WHAT WAS TRUE. The fast baseline was a corpse. The 2.3 ms binary exited 0, printed zero bytes, and died before the first line of user code, on every invocation. It had been timing its own death; the "slow" binary was the only one doing work. And the part I own: my parity check had declared that corpse's output correct, because it never deleted the output file first and so compared one left by the previous lane. A dead program passed a correctness gate because the gate was reading a ghost.

WHAT MAKES IT LOUD NOW. Two rules. One: rm the output, then run, then assert it was recreated, then compare — baselines included. Two: never trust a clean exit code without evidence of output. A harness that cannot see death is no harness.

Why the parity gate outranks the test suite

The gate compares the Hey program's behaviour against the Ruby original's on identical inputs: member lists, extracted trees, normalized stdout, nine checks, both lanes. It tests nothing about the language, yet it caught more real bugs in one night than any test suite here — because it need not imagine failure modes in advance. It only needs the two programs to disagree.

Exhibit D: the compiler that deleted my code

SYMPTOM. Programs that compiled cleanly, ran, exited 0, and did some — sometimes none — of what their source said. One tool's entry point was absent from the binary.

WHAT WE BELIEVED. Five successive explanations: a routing regression, a cache-key problem, my dead baseline, worker wake-storms, CPU oversubscription. Each was falsified by a measurement. Five wrong theories about one defect should calibrate anyone's confidence in a first hypothesis.

WHAT WAS TRUE. A silent miscompile — in the legacy C compiler, not the new one written in Hey itself, which turned out to have been correct the whole time. The old emitter misread a bare module-function call in statement position as the block's implicit return value, and dropped that call along with every statement after it — the block truncated at compile time. The interpreter got the same shapes wrong, not truncated but wrong: a three-function reproducer printed 900 where the answer is 4. A wrong answer with a clean exit is the worst outcome in this article. What finally pinned it was Exhibit C's corpse.

The exculpatory detail, which I nearly left out because it flatters us: the two components carrying this bug were the two already scheduled for deletion, and the self-hosted replacement — the compiler written in the language it compiles — was right about these shapes throughout. That is either luck or a plan pointed the correct direction before anyone knew the bug existed, and the blast radius was measured across all 1,143 files of the compiler's own test corpus rather than estimated.

WHAT MAKES IT LOUD NOW. Two releases on one day. v0.99.408a added the guard: if any statement lowers to zero IR — the compiler's instruction form between source and machine code — the build fails loudly, fleet-wide. v0.99.409a landed a fix, blast radius measured across all 1,143 files of the corpus rather than guessed at. And hey_run, one of the toolchain's own tools, compiled to a working native artifact for the first time — the point of self-hosting.

Correction: this class was not closed when I first wrote that

The paragraph above originally ended "and the class was closed." It was not, and I am glad the sentence did not survive. Three days later the maintainer wrote a fresh port of another script in ordinary Ruby style — a validation helper called for its side effect on the first line of a method, the most unremarkable line in the file — and the program ran, exited 0, and did nothing. A second, distinct hole in the emitter had kept the same class alive for statement-position calls inside function bodies, in compiled code only. Valid source compiled clean and silently did half of what it said.

The guard from 408a could not catch it for a precise and instructive reason: the call does lower. It is read as the function's return expression, so it executes — and every statement after it disappears. A guard watching for statements that produce no code sees nothing wrong, because the offending statement produced code. The proposed replacement counts statements in versus statements out.

It is now fixed properly rather than papered over: no compile-time rejection, no recommended workaround, the shape simply behaves — verified across a 13-cell matrix of call position × callee type × enclosing context (the compiled lane truncated 6 of those 13 before the fix and none after, matching the interpreter exactly), with a 1,059-file survey showing zero regressions. It landed in v0.99.412a, and the receipt for this paragraph is that the script which exposed the bug now runs unmodified: the defensive bindings are deleted, the ordinary statement-position calls are back, and all of its output appears. Two footnotes for the record: my own report of a related "cannot bind a nil-returning call" failure did not reproduce across five variants, so treat that claim as unconfirmed; and the toolchain team's earlier all-clear rested on a sweep run against the very guard that is blind to this shape. A clean sweep by a blind instrument is not evidence of absence — which is the same mistake, one layer up, that put a retracted memory figure in Exhibit B.

Pre-registered predictions

Twice in one night a confident theory died because somebody wrote down the expected result before running the experiment. That is a pre-registered prediction, borrowed from clinical trials: a result you interpret after seeing it will agree with you. The "wake-storm" theory led the field until its own criterion failed; the real cause, proven from disassembly, was per-request deep-copying of route data.

Exhibit E: the theory that came back from the dead

SYMPTOM. Committed probe scripts, previously alive, producing nothing. Exit 0, zero output, no diagnostic — and a compile-cache entry minted, as if work had been done.

WHAT WE BELIEVED. Four theories, each killed by a measurement: a stale cache (survived every cache sweep we knew about); a binding-form spelling regression (confounded); a poisoned compiler binary from a racy publish (the preserved binary was byte-identical to a healthy one); then a path-handling bug — hey ./x.hey dead while hey x.hey lived, same file, same minute — which held for hours and was also wrong.

WHAT WAS TRUE. The poisoned-artifact theory was right after all — one shelf over. A corrupted entry in the compiler's cache of prebuilt components — its sidecar cache, which despite the shared word is unrelated to the delegation sidecar elsewhere in this story — produces artifacts that silently drop the program body, and the native loader never checks for the empty result. Clearing that cache cures it; clearing every other cache does not. The spooky per-spelling determinism was bookkeeping: each way of typing the path hashes to its own cache key, so ./x.hey deterministically hit the poisoned key while x.hey hit a healthy one.

Two theories about how it got poisoned, both wrong

I proposed a concurrency race — two builds publishing at once — and offered stranded temporary files in the build directory as evidence it had been happening for days. Both halves were wrong, and it took a purpose-built oracle to establish it: 960 trials of forced concurrent compilation, cold caches, every artifact executed and compared, produced zero failures before or after the fix. The publish path was already atomic. And the stranded files were not wreckage at all — building with -o X also emits X.ll, X.c and X.reflection.json, and only the executable was being moved into place. 304 leftover files, entirely deterministic, entirely innocent. I read a normal build byproduct as a crime scene because I was already looking for one.

The oracle earned its cost anyway: it caught a genuine time-of-check race that the fix itself had just introduced, once in 960 trials. The mechanism that actually poisons the cache is still open.

WHAT MAKES IT LOUD NOW. The one not yet fixed: an upstream slice (publish lock, cache sweeps that cascade to downstream artifacts, and a loud guard at the exact check the loader skips) is written and queued. Meanwhile the cure is verified on our own corpse — clear the sidecar cache and the run cache, then recompile — and the interim rule stands: a silent-dead script is a cache-poisoning suspect before it is anything else. Diagnosed the same morning; bounded by a rule, the weakest kind of guard, until the slice lands.

The record of retractions

In a case file, discarded theories belong in the record at full size. Each was believed with evidence; each was killed by a measurement:

  • "The compiler forgot to free the old value." It was clone-and-abandon. Caught by the red team before the fix landed on the wrong story.
  • "A 9× runtime regression." There was none; the baseline was a dead binary. Every conclusion built on its 2.3 ms number was invalidated by timestamp.
  • "Binary output parity green." Vacuous: no delete before the run, so the diff compared a stale file. Mine.
  • "A binding-form spelling regression." Spelling was confounded with invocation form in every cell.
  • "Stranded temp files prove the race has been running for days." They were ordinary build byproducts — 304 of them, deterministic, present in every version. A 960-trial concurrency oracle then found zero failures: there was no race. I had built evidence out of litter.
  • "A poisoned compiler binary from a racy publish." Half right, and that was the trap: the preserved binary was byte-identical to a healthy one, so the theory died — then came back one theory later as a poisoned cache entry from the same racy publish.
  • "A path-prefix bug: ./x.hey is broken." Reproducible, believed for hours by both of us, and wrong. The prefix only selected which cache key you hit.
  • "The server memory leak is fixed; what remains is a bounded working set." Mine, published, and an artifact of measuring memory with the wrong tool. Retracted above.
  • "Return type triggers the truncation." Two variables changed at once. Statement position is the trigger.

The guard is the hero

The satisfying story would be the 481×. It is the wrong story — one fix to one defect, and next month there will be another. What survives is the instrument: a flatness gate that fails on any list-shaped retention; a build that refuses to emit a program where a statement lowered to nothing; a harness that asserts output bytes so it can never again time a corpse; a parity gate indifferent to what the language does internally. Each converts a silent failure into a loud one — the only transformation that compounds.

That is also the answer to "why should I believe your throughput numbers?" — and the answer is not "trust us", it is a list. The same output assertion that caught the corpse in Exhibit C later invalidated two published request-rate measurements where a dead listener had been impersonating a very fast server. The same instrument scepticism that produced the retraction above retired our long-standing "Go does 103,000 requests per second" reference for bad provenance — the real figure, measured properly, was 134,663, which made our own comparison harder. And it threw out an entire "memory ratchet" finding of mine. Those corrections are why taking three Hey web services from 500 to 60,000 requests per second (where the delegation sidecar — a long-lived helper process that replaced per-call process spawning — and the dispatch fixes do the heavy lifting) and the command-line scripting piece were published after this case file, not before.

The ergonomics tax, stated honestly

Identical functionality: Ruby 606 lines, Hey 861 — 1.42×. Some of that is Hey's explicitness, some is workarounds for the defects in this very article. Two more lanes where Hey loses today: the compiled build loop is minutes where Go is seconds and Ruby is zero, and the ecosystem is a rounding error beside either.

So would you actually ship this?

In print rather than in the comments, then: yes, with conditions. You are buying a language whose defects tend to be silent, and a team that fixes or guard-blocks them within about a day. The honest tally of the five: two fixed at the root inside 24 hours (the quadratic retention, the statement truncation), one made structurally unshippable by a build guard that fails any compile where a statement produces no code, and two bounded only by rules — my own drain-loop mistake, which has a committed reproducer and no guard, and the cache race, whose lock and loud check are written but not landed. Two of five resting on a rule is the true count, and rules are the weakest guard in this article. Weigh that against Ruby's and Go's decades of hardening, which Hey cannot buy at any price this year. Against that, a defect filed at 2 a.m. had a guard in the compiler by breakfast.

Practically: ship it where you can hold a parity gate against a reference implementation, or where your tests assert real output rather than exit codes. Do not ship it where a wrong-but-quiet answer is expensive and you have no independent check — because Exhibit D happened, and the right response to it is a policy, not a reassurance.

What I would defend is narrower than the language: the loop. A crash report from a human looking at Activity Monitor, a reduced reproducer, a pre-registered prediction, a red team allowed to contradict the going story, a guard that makes the class unshippable, and a correction printed as loudly as the claim. That loop found five silent-failure classes in a night. Speed was the reward. It was never the subject.

Glossary

byte-parity
Comparing outputs byte for byte rather than "looks right".
RSS
Resident set size: the RAM a process occupies right now.
jetsam
The macOS mechanism that kills processes to reclaim memory.
quadratic
Cost growing with the square of the input.
deep copy
Duplicating a value and everything it references, rather than sharing it.
clone-and-abandon
Build a value, deep-copy it, store the copy, orphan the original.
ASAN
AddressSanitizer: reports use-after-free, overruns and leaks at runtime.
TSAN
ThreadSanitizer: catches data races between threads.
silent miscompile
A compiler emitting a program that does not match its source.
self-hosting
A language whose compiler and tools are written in itself.
IR
Intermediate representation: the compiler's form between source and machine code.
pre-registered prediction
Recording the expected result before measuring, so it can falsify the theory.
working set
Memory a program needs in flight; unlike a leak, it comes back down.
sidecar (delegation)
A long-lived helper process replacing per-call process spawning.
sidecar cache
Unrelated to the above: the compiler's store of prebuilt components, reused between builds.
TOCTOU race
"Time of check to time of use" — a file changes between being checked and being used.
run cache
Compiled artifacts the toolchain keeps so a script need not be rebuilt each run.
hyperfine
A benchmarking tool that repeats a command, discards warm-ups, and reports mean and deviation.
keep-alive
Reusing one network connection for many requests instead of opening a fresh one each time.
exit code
The integer a process returns on termination; 0 means success.
