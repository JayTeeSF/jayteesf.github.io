Build and deploy Hey programs

hey build app.hey -o build/app gives you one native file. On a Mac, hello world is a little over a hundred kilobytes and needs nothing but the operating system's C library to start. This guide opens that file up and follows it into a container and onto a server.

1. What comes out of hey build

Works today

program
  says 'Hello, world'
end
$ hey build hello.hey -o build/hello
built .../build/hello
$ ./build/hello
Hello, world
$ otool -L build/hello
build/hello:
	/usr/lib/libSystem.B.dylib (...)

Name and place: exactly what you pass to -o. Leave the folder out and it lands next to where you ran the command. otool -L (on Linux, ldd) lists the shared libraries a program loads at start: here, only the system C library.

Three layers are copied into the file when it's built. Only what your program can reach is kept: the linker drops unused code and unused libraries. A hello world carries a few dozen runtime functions; a web server carries the actor scheduler and the HTTP code too.

2. Ship the binary

Works today

Most of the time this is all you need: one file, copied to a server and started. Here is a real HTTP server, health.hey:

import 'stdlib:Web'

fn health(request)
  return Web.json({ok: true})
end

program
  let routes = Web.routes([Web.get('/health', health)])
  let served = Web.serve(routes, {host: '0.0.0.0', port: 8080})
end

Build it. The binary is called exactly what you pass to -o, here build/health:

$ hey build health.hey -o build/health
built .../build/health
$ ls -lh build/health
-rwxr-xr-x  1 ... 267K ... build/health
$ otool -L build/health
build/health:
	/usr/lib/libSystem.B.dylib (...)

A web server in about a quarter of a megabyte, linking only the system C library (libSystem on macOS; on Linux, the C library and, for a program that can reach TLS, OpenSSL). Your code, the standard library pieces it uses and the Hey runtime are all inside the file.1

Run it. It needs no environment variables and no Hey installation. This one listens on port 8080 on every network interface. Start it in one terminal with ./build/health, then point a client at it from another:

$ curl -si http://localhost:8080/health
HTTP/1.1 200 OK
content-type: application/json
content-length: 11
connection: keep-alive

{"ok":true}

Copy it to another machine of the same kind (same operating system and CPU) with scp build/health server:, and run ./health there. Nothing else needs installing. To check that it doesn't lean on anything in your build folder or your shell, copy it somewhere else and start it with an empty environment, mkdir -p elsewhere && cp build/health elsewhere/ && cd elsewhere && env -i ./health:

$ curl -s http://localhost:8080/health
{"ok":true}

Starting a built file directly takes about a millisecond; hey app.hey adds a cache check of a few milliseconds (Guide 3).

3. The run cache

Works today

hey app.hey keeps its compiled program in your user cache, keyed by the content of your file, every file it imports, and the compiler itself. hey cache path shows where:

$ hey cache path
cache_home=...
run_cache=.../run

The default is ~/Library/Caches/Hey on macOS and $XDG_CACHE_HOME/hey or ~/.cache/hey on Linux. Each cached program is a folder holding the executable and a record of which compiler made it. Entries are never overwritten; a change makes a new one. Guide 1 shows a miss and a hit.

$ hey cache gc --dry-run
cache_gc_removed=0 all=false days=30 dry_run=true ...

hey cache gc removes entries unused for 30 days (--days N to change, --all for everything) and never touches one that's in use.

4. Targets and platforms

Works today macOS arm64, Linux x64. Partly works Windows x64.

A Hey build makes a program for the machine you're on. To make Hey itself installable without a C compiler, the release command packs the whole toolchain into one archive per system: compiler, linker, standard library, a precompiled runtime and native libraries, with a SHA256SUMS file and an install.sh. Partly works: the commands work, but no signed archive is published yet.

$ hey target matrix
target matrix version=... host=darwin-arm64 verify=false
target=linux-x64 product_release=true ...
target=darwin-arm64 product_release=true ...
target=windows-x64 product_release=false ...
target_matrix_ok=true
$ hey target doctor --target darwin-arm64
target doctor target=darwin-arm64 host=darwin-arm64
clang=ready path=...
release_ready=true

The release itself is hey target release --target linux-x64 --out hey-VERSION-linux-x64.tar.gz on a matching machine (it refuses a mismatch); hey target pack and hey target verify are the separate steps. A user installs an archive with ./install.sh --user (into ~/.local/hey/VERSION) or sudo ./install.sh --system (into /opt/hey/VERSION).

Windows: there's no Windows compiler. hey windows runtime-test-bundle --out FILE.zip builds a ZIP that exercises the native Windows runtime pieces (I/O completion ports, HTTP, processes) on a Windows machine. It's groundwork, not a product. Phones and TVs are in Guide 5.

5. Containers

Works today

The toolchain image is Hey's compiler in an Alpine Linux image, tagged with the exact version and CPU (hey-toolchain:0.99.607a-amd64). Because it's cached by its version tag, every Hey release bumps the version, so an app never compiles against a stale compiler. It's big and it never ships: you compile in it, then copy the result out.

The same health.hey from section 2, in a container:

A two-stage Dockerfile: compile in the toolchain image, ship only the binary.

# Stage 1: compile with the Hey toolchain image
FROM hey-toolchain:0.99.607a-amd64 AS build
WORKDIR /app
COPY health.hey .
RUN hey build health.hey -o /out/health

# Stage 2: ship only the binary
FROM alpine:3.21
COPY --from=build /out/health /app/health
EXPOSE 8080
ENTRYPOINT ["/app/health"]
$ docker build --platform linux/amd64 -t health .
$ docker run -d --rm --platform linux/amd64 -p 18080:8080 health
$ curl -s localhost:18080/health
{"ok":true}

The result is Alpine (under 8 MB) plus one small binary. A program that uses TLS also needs apk add libssl3 libcrypto3 in the second stage. For hey_web apps, the hey_container package generates release Dockerfiles.

6. Deploy with Kamal

Works today

Kamal deploys a container image to your own servers over SSH and moves traffic only when the new container answers its health check. Hey apps deploy with hey-kamal, a small command in front of Kamal that deploys only the exact image you built and tested, by its digest (its fingerprint), and checks that digest again on every server afterwards. Once your image is built, tested and pushed, it's two commands:

hey-kamal deploy/hey-kamal.yml verify-image
hey-kamal deploy/hey-kamal.yml deploy

What you get: verified IMAGE@sha256:... service=NAME from the first, and from the second a Kamal deploy followed by verified remote IMAGE@sha256:... on HOST for each server. Anything that doesn't match stops with a one-line hey-kamal: error before a container starts. The release file, the settings and every refusal are explained in hey-kamal's own getting-started guide, which ships with the tool (docs/GETTING_STARTED.md).

7. Install layout and hidden host dependencies

Decided, coming

The rule: an installed Hey, and the programs it builds, depend on nothing on the machine that isn't declared. Toolchains live in one versioned folder (/opt/hey/VERSION or ~/.local/hey/VERSION), caches in the user cache folder, and built apps find their native libraries relative to themselves (@loader_path/../lib/hey/native on macOS, $ORIGIN/../lib/hey/native on Linux).

Partly works The one hidden dependency left is OpenSSL on macOS. The runtime opens it with dlopen (which loads a library while the program is already running) the first time a program uses TLS, searching a library path written into the binary that points at Homebrew's openssl@3. On a Mac without it, a TLS call fails with a named error (could not load OpenSSL ...); programs that never use TLS don't care. On Linux, OpenSSL is an ordinary declared dependency that ldd shows.

Notes

  1. The runtime loads OpenSSL on first TLS or crypto use, not at program start: e18214.
