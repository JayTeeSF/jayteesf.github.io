Daily: Seven Ways to Be Wrong Quietly

A compiler bug that crashes is cheap — you find it immediately. A compiler bug that returns the wrong answer and exits successfully can ship for months. In roughly 25 hours the Hey project found seven separate classes of those, killed six, and built the kind of test that makes the whole family visible from now on. Eighteen verified releases went out in the same window.

TL;DR

  • Seven classes of silent wrong answers found; six fixed, one in final work. Every one of them passed every existing test, and several had shipped for months.
  • The reason none were caught is structural, not careless: the test suite ran programs through the interpreter, and these bugs existed only in compiled code. Two execution paths, one of them unwatched.
  • One store went from 329,333 nanoseconds to 11.6, and stayed flat across a 256× range of table sizes — the memory fix that turns the billion-row challenge's aggregation from a multi-week projection into something worth timing.
  • Disclosed weakness: a survey found only 35% of ordinary standard-library calls compile through the preferred code generator. One refused call anywhere silently sends an entire program down the slower path.
  • Reproduce the interesting one: the new gate needs no expected outputs at all — it compiles each program three ways and requires the results to match.

1. What "silently wrong" actually looks like

The clearest example: comparing two numbers. In compiled code, boxed integers compared with < or >= were being compared as text. So a loop written while received >= expected, with expected set to 10, stopped at 2 — because "2" sorts after "10" alphabetically.

Nothing crashed; the program exited successfully with a wrong result. And it had a plausible cover story — it looked exactly like a worker pool dropping tasks past eight. What broke the case was predicting in advance what the numbers would do if the cause were alphabetical rather than proportional: 24 workers should collapse to 3, not to some fraction. It collapsed to 3.

2. Why the tests all passed

Hey runs programs two ways: an interpreter, and a compiler that produces a native executable. The test suite ran the interpreter. Every one of these seven bugs lived only in compiled code.

That is not carelessness — it is the sort of gap that is invisible from inside. The suite was green, comprehensive, and genuinely testing the language; it was simply testing one of the two things that ship. The single most valuable fact from this cycle is that a passing test suite told the team nothing about the code its users actually run.

Why a comment could change an answer

One of the seven: the compiler's front end never removed trailing comments before analysing code. A comment at the end of a line could change what type a value appeared to be, make a declaration unparseable — or silently discard the rest of a chained operation, so a program quietly produced a shorter list and exited successfully.

3. The test that needs no expected answers

The fix for the class, rather than the bugs, is a gate built on a relation instead of an expectation. Every program in the corpus is compiled three ways — unchanged, with all comments stripped, and with harmless comments inserted — and the three outputs must be byte-for-byte identical.

No one has to write down what the right answer is. Comments cannot change behaviour, so any disagreement is a bug by construction. It found three unknown defects before it even landed — and it was falsified on purpose first, going red against the un-fixed compiler on exactly the shape it was built to catch. A gate nobody has watched fail is not yet a gate.

4. The number that moved

Underneath the bug hunt, the performance work landed its biggest single result. Storing a value into a 65,536-slot table went from 329,333 nanoseconds to 11.6 — and stayed flat as the table grew across a 256× range, which is the part that matters. The old cost was proportional to the size of the whole table, because every store copied it.

This is the aggregation step in the billion-row challenge — read a billion station;temperature lines, report min, mean and max per station. That workload's inner loop is now measured at 99.6% of per-row time in a single remaining operation, an unusually comfortable position: one lever, precisely located, everything else established as noise.

Two datasets, never mixed

Billion-row numbers here always name their file. The official dataset has 413 weather stations; the project's stress file has 41,344. They are different problems — the second is dominated by station count — so results from one are never quoted on the other's axis.

5. Correctness came before speed, and cost three references

Before optimising, the team settled whether Hey's answer was right: 413 of 413 stations, zero value disagreements, at full scale. Getting that verdict required fixing three widely-used reference implementations first — a well-known C version has a minimum-initialisation bug, a Python comparison rounded the wrong way on exact ties, and naive parsers break on station names containing commas. "Right and slow" is a fine place to start from; it is a much worse place to arrive at after publishing a speed number.

6. The disclosed weakness

A survey of the standard library found that only 35% of ordinary calls compile through the preferred code generator. The failure is quiet: one unsupported call anywhere in a program sends the whole program down a slower fallback path, and the only evidence is a single line in the build log. Near-twin functions disagree — one search function compiles, its sibling does not — so a developer cannot predict which calls are safe.

That is the next campaign, alongside a ruled language change: imports become namespaced by default, sharing explicit and opt-in.

7. What the day cost, stated plainly

Four claims were retracted by the people who made them. A memory improvement first read as +6.5% turned out to be an artifact of a busy machine. A cost estimate that held at small scale did not survive full scale. A hypothesis about which library function blocks three applications was measured, published, and corrected within the hour. And a whole performance comparison was thrown out on discovering one side had been serving empty responses throughout — a server answering 200 OK with nothing in it, which every status check passed.

None of that is incidental to the good news above; it is the same practice. A test that cannot fail, a measurement that cannot be wrong, and a claim nobody re-checks are the same category of mistake — and this cycle's entire yield came from hunting that category on purpose.

The most telling decision of the day was a refusal to fix something. One bug had a neighbouring case — arithmetic inside an array subscript — that more compiler surgery could have made work. They left it a loud refusal instead: the compiler says no, clearly, and you hoist the expression to a variable. After seven silent wrong answers, a feature that fails visibly beat one that might quietly join them.
