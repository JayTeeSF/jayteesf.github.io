Native code and calling C: native packages, and the direct calls that are decided

Index Guide 2: Packages Reference 6: Standard library Reference 7: Native code and C Compiler 1: From source to native Reference 8: Memory Reference 9: Performance

Some things are already written in C and written well: SQLite, PostgreSQL's client, zstd, epoll and kqueue. Hey uses them through native packages. Today a call goes through a general-purpose door that costs thousands of instructions for a few nanoseconds of C. The decided fix is to make a C function an ordinary import and an ordinary call.

On one screen Today Works today (Unix): describe the C functions in hey.native.json, run hey native to generate a shim (small generated C glue between Hey and the library), and call through Native.open and Native.call. Hey's internal value type never crosses into C. Each call costs about 5,400 instructions, of which the C work is about 100. Decided Decided, coming: native ABI v2, typed calls bound at compile time, estimated 40 to 90 instructions, after the String format freezes. The way to C for your code is native packages, and that is ruled.

Badges: Works today compiled and run by the documentation test. Decided, coming ruled, not in a released build yet. Proposed not ruled.

1. Why native packages exist, and the one rule

A Hey value in memory (the runtime's HeyValue) has a layout that changes between releases: it is changing right now, as Strings move to a 16-byte form. If C code could see that layout, every release would break every C library. So the rule is: HeyValue never crosses into C. C sees only booleans, fixed-size integers, double, borrowed UTF-8 text, borrowed or owned bytes, nullable values and opaque handles. A spec fails the build if the package-facing header ever mentions HeyValue. Works today

2. Calling C today

A tiny C library with two functions, add_i64 and scale_i64. The manifest says what each takes and returns, who owns what, whether it can be null, whether it blocks (waits on disk or network), and whether it is safe to call from two threads at once:

native_math.h

#ifndef NATIVE_MATH_H
#define NATIVE_MATH_H
#include <stdint.h>
int64_t native_math_add_i64(int64_t left, int64_t right);
int64_t native_math_scale_i64(int64_t value, int64_t factor);
#endif

native_math.c

#include "native_math.h"
int64_t native_math_add_i64(int64_t left, int64_t right) { return left + right; }
int64_t native_math_scale_i64(int64_t value, int64_t factor) { return value * factor; }

Generate the shim. The descriptor symbol is the name of one exported C table that lists the package's functions and their types; Hey looks it up once when it opens the library. hey native writes the versioned C header, a deterministic wrapper, and a lock file1 recording the ABI version, target, manifest hash, sources, headers, libraries and the descriptor symbol.

Then load and call it. Native.call refuses a function marked blocking: true;2 that one goes through Native.call_blocking, here from a Job so no scheduler thread is held. Works today

native_today.hey

import 'stdlib:Native'
import 'stdlib:Jobs'

worker Scale(message)
  return Native.call_blocking(message.extension, 'scale_i64', [message.value, 6]).value
end

program
  let opened = Native.open('./libnative_math.dylib', 'hey_native_native_math_extension_v1')
  says opened.ok
  says opened.value.package
  says opened.value.abi_version

  let extension = opened.value.handle
  says Native.status(extension).value.function_count

  says Native.call(extension, 'add_i64', [20, 22]).value

  let refused = Native.call(extension, 'scale_i64', [7, 6])
  says refused.code

  let Scales = Jobs.define('Scales', Scale, count: 1, capacity: 4)
  let receipt = Scales.enqueue({extension: extension, value: 7})
  says Jobs.result(Scales, receipt, 1000).value
  let stopped = Scales.stop()

  says Native.close(extension).ok
  says Native.call(extension, 'add_i64', [1, 1]).code
end

CallWhat it does
Native.open(path, descriptor_symbol)Loads the library once, checks the ABI version and descriptor shape, returns an opaque capability (a handle).
Native.status(handle)Package, version, target, hash and function count; never a pointer.
Native.call(handle, name, args)Looks the function up by name, converts each argument by the descriptor's type tag, calls, converts back, returns a Result. Refuses blocking functions (native_call_blocking).
Native.call_blocking(handle, name, args)The same, allowed for blocking functions.
Native.close(handle)Removes the capability first, waits for active calls, then closes. Later calls get native_handle_closed.

Where may blocking calls run? In a Job, a worker, or the top-level program block, and nowhere else: the compiler will refuse a blocking call inside an actor or a web request handler, where it would hold a shared scheduler thread. Decided, coming Today nothing checks it, so keep blocking calls in a Job yourself.

blocking_in_program.hey

import 'stdlib:Native'

program
  let extension = Native.open('./libnative_math.dylib', 'hey_native_native_math_extension_v1').value.handle
  says Native.call_blocking(extension, 'scale_i64', [7, 6]).value
  says Native.close(extension).ok
end

Functions not marked thread_safe: true are serialized per extension. An immutable Hey record holding a handle does not make the C resource immutable or thread-safe; keep stateful resources under one owner, often a partitioned Job.

3. What one call costs today, and why

Predict it. add_i64 adds two integers in C. Is calling it through Native.call faster or slower than calling a Hey function that does the same addition? By how much?

On this toolchain, a million calls of the two-integer add_i64 against a million calls of the same addition written in Hey (built with hey build, timed inside the program):

call_cost.hey

import 'stdlib:Native'

fn add(left, right)
  return left + right
end

program
  let n = 1000000
  let extension = Native.open('./libnative_math.dylib', 'hey_native_native_math_extension_v1').value.handle

  let started = now_ns()
  let total = 0
  let i = 0
  while i < n
    set total = total + Native.call(extension, 'add_i64', [i, 1]).value
    set i = i + 1
  end
  let native_ns = now_ns() - started

  set started = now_ns()
  let plain = 0
  set i = 0
  while i < n
    set plain = plain + add(i, 1)
    set i = i + 1
  end
  let plain_ns = now_ns() - started

  says 'same answer: ' + (total == plain)
  says 'Native.call: ' + div(native_ns, n) + ' ns per call'
  says 'Hey function: ' + div(plain_ns, n) + ' ns per call'
  says Native.close(extension).ok
end

Run it

$ hey build call_cost.hey -o call_cost
...
$ echo $?
0

Run it (exact command and output)

$ ./call_cost
same answer: true

true
$ echo $?

The two lines with timings change from run to run. On a 12-core Mac, one Native.call of a C function that adds two integers takes a few hundred nanoseconds (360 to 560 across runs); the same loop calling a Hey function takes about 35. One run, timed with Time.now_ns() inside the program, so treat the numbers as a size, not a benchmark. The gap is the seven steps in the picture: building and freeing a list and a Result per call, not the addition.

Ruled: the way to C is native packages

Ruled. Your code reaches C through native packages: a hey.native.json manifest, Native.open and Native.call today, and the decided direct typed calls of native ABI v2 later. There is no other way to declare C functions in Hey source, and none is coming. Hey's own built-in functions are bound to the runtime inside the toolchain; your code calls them like any other Hey function. See the decision ledger.

7. Limits

  • A native call cannot be interrupted, by any scheme. Works today (a standing fact). Erlang's "dirty NIFs" (C functions run on separate scheduler threads), Wasmtime host calls and Go's cgo have the same limit. A stuck C call holds its thread until it returns; bound it inside the C library (SQLite's busy timeout, a socket deadline).
  • iOS forbids loading non-system libraries at run time, so native packages do not work there today; static binding (native ABI v2) fixes that by linking the package into the app.
  • Windows native loading and static registration, callback and thread-affinity rules, and browser targets are separate, later work. The platform probes for iOS, Android and Windows are documented with the platform matrix in Commands and platforms.
