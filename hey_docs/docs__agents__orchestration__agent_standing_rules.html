Agent handoff documentationAudience-specific Hey documentation

STANDING RULES FOR EVERY SUB-AGENT (referenced by every brief;

each rule was paid for — the ledger holds the receipt)

Environment

1. Work ONLY in your assigned worktree. FIRST ACTION: pwd +

git rev-parse --show-toplevel. Source YOUR env script in EVERY

shell (each command is a fresh shell; unsourced = trunk

toolchain silently).

2. ulimit -s 65520 before interpreted-pipeline runs. Verify

HEY_COMPILER_BUILD_DIR points into YOUR worktree before the

first ./bin/heyc (it auto-rebuilds).

3. Shared session scratchpad: prefix EVERY file you create with

your worktree name (a commit message was overwritten by a

sibling once).

4. Kill only PIDs you spawned and recorded — never pkill by

name/pattern (kills other seats' gates).

5. Load discipline: wait for load1 < 12 before gate batteries. If

the marker file wcert_window_active exists in the scratchpad,

pause compile-heavy work in 60s sleep loops until it is gone.

Method

6. A grep is a hypothesis, not a result. Verify by

compiling/running. Lane verdicts ONLY via the MIR-driven recipe;

bare heyc on source gives false native-rejects.

7. BOTH LANES, always: the shipping lane is the HeyLlvm mirror with

native as silent fallback — a green native-only fix can be

entirely inert (proven). Probe and falsify both.

8. Byte-identity or fail-closed; never a silently-diverging third

thing. Rebuild sidecars fresh before every byte-compare;

compares serial; hash OBJECTS not executables (LC_UUID).

9. Every gate WATCHED DOING BOTH: demonstrate red AND green, with

transcripts. An xmalloc gate is blind to clone-family slices —

gate on clone/strdup shape or curve form.

10. Honest headlines: per-member flip tables, not aggregates;

report what you measured, name what you did not; a

prediction-refuting result is a DELIVERABLE, not a failure.

Reporting

11. Final report includes: commit SHA (do NOT push; do NOT bump

versions — landings do that), per-gate verdicts, NAMED PASS

transcript lines for every NEW spec (a summary sentence is not

evidence — a false "all green" reached the ledger once),

falsification transcripts, out-of-scope findings CATALOGUED not

fixed.

12. If blocked or your brief's premise turns out wrong: say so

plainly and early. Corrections to the brief are prized;

satisfying its letter while leaving the defect alive is the

named failure mode.

13. THE CANONICAL VERIFICATION SET IS test/run_release_verify.sh

(maintainer directive 2026-07-27). If your slice ADDS a

verification step (gate, regression family, golden set), you

register it there IN THE SAME SLICE; if your slice retires a

subsystem, you remove its steps there in the same slice and

name the removal in your commit message. Known-red entries

carry a signature and are removed when their class is fixed.

Seat runners wrap this script; they never carry a private gate

list.

14. NEVER READ AN EXIT CODE THROUGH A PIPE. `cmd | tail; echo $?`

reports tail's status, not cmd's — two agents hit this in one

night and one nearly shipped a false-green gate receipt.

Capture rc directly (`cmd > log 2>&1; rc=$?`) and read the log

separately. A gate transcript whose rc passed through a pipe

is not a receipt.

15. COLD CACHE AFTER REBUILD. After rebuilding the compiler

(`make`), clear or redirect HEY_CACHE_HOME before re-running

any spec/probe whose verdict you will cite: the run cache is

keyed on SOURCE sha, so ./bin/hey can reuse binaries built by

the PREVIOUS compiler across a full rebuild, and a red spec

can go green (or vice versa) on stale artifacts. Discovered

by wsaypay: spec 1276 PASSED at a base where it must fail,

until the cache was cleared. Falsification runs (revert ->

red) are the highest-risk case — a stale cache silently

defeats the revert.

Sidecar security (maintainer directive 2026-07-28 — BINDING ON

EVERY AGENT, whatever your slice is about)

Read the published analysis before you touch anything that spawns,

resolves, or delegates: https://www.jayteesf.com/articles/

what-is-on-the-other-side-of-the-pipe.html

16. THE SIDECAR IS NOT A SECURITY BOUNDARY, AND YOU MAY NOT WRITE

AS IF IT WERE. Process separation is a standard way to BUILD

security only when privilege DROPS across the boundary

(OpenSSH privsep, Provos/Friedl/Honeyman USENIX 2003;

Chromium's renderer sandbox, Reis/Gribble EuroSys 2009;

Capsicum, seccomp-bpf, RLBox). Our stdlib sidecar runs as the

SAME USER WITH THE SAME RIGHTS as its parent: it is a

CONVENIENCE, NOT A BOUNDARY. "It's in a separate process" is

never a mitigation in a brief, a review, or a commit message.

17. THE RESOLUTION LADDERS FAIL OPEN AND THAT IS THE BUG CLASS.

Both spawn-feeding resolvers run off the end of their ladder

into the current working directory instead of refusing:

* hey_llvm_stdlib_heyc_path() (runtime/hey_runtime.c:16453)

— the PROGRAM to spawn. Bottom rung is an unconditional

`return hey_strdup("./bin/heyc")`. Step 4 probes THREE

plantable names via the relative[] table (:16409-16413),

first-preferred `./libexec/hey/heyc-bootstrap`, then

`./build/heyc`, then `./bin/heyc` — an advisory or

detection rule naming only the last one is wrong.

* hey_llvm_stdlib_root_path() (:16431) — the SOURCE the

sidecar compiles. Bottom rungs are `getcwd()` (if a

directory merely NAMED stdlib/ exists beside it) then

`hey_strdup(".")`, and the spawn exports both HEY_ROOT and

HEY_STDLIB_PATH from it (:17130-17137).

MEASURED (bench, 465a Darwin, both lanes): a stand-in planted

at ./bin/heyc EXECUTED, twice (the runtime respawns on death),

on the first delegated call, with the toolchain environment

cleared — the state a CUSTOMER's machine is in. The app

printed only "stdlib delegation failed" and CONTINUED, so it

reads as a bug rather than an intrusion.

THE PREDICATE IS NOT "IS IT RELATIVE". getcwd() is ABSOLUTE BY

CONSTRUCTION and passes an is-absolute validator every time

(linux, source-confirmed). The dangerous property is

DERIVED-FROM-CWD-ness. Any check you write must test that.

RULE: never add, keep, or restore a resolution step that

returns a DEFAULT. Refuse loudly. This is our own fail-closed

doctrine applied to the one place that still fails open into

the filesystem — and the same ladder has now produced a

PERFORMANCE defect (linux hazard 7: HEY_ROOT unset = silent

~150x), a CORRECTNESS defect, and a SECURITY defect. One

hardened resolver, two call sites, refuses rather than

defaults, emits the loud startup line.

18. SPAWN MECHANICS. Use posix_spawn, NOT posix_spawnp, once a

path is validated absolute — the `p` variant searches $PATH

whenever the program name has no slash, so `HEY_STDLIB_HEYC=heyc`

(the natural thing a user types) opens a third resolution lane.

Sites: :17197 and the one-shot at :11368. `access(X_OK)` at

:16417 followed by the spawn is a TOCTOU pair (CWE-367) and

access() tests the REAL uid while the spawn uses the effective

one.

ENVIRONMENT INPUTS — CORRECTED 2026-07-29, because the earlier

wording ("treat them as DEV-ONLY; prefer the executable-derived

path in shipped builds") CONTRADICTED the standing ban on

build-type sniffing, and an implementer had to resolve that

contradiction on their own. The resolution, ruled:

* HEY_STDLIB_HEYC and HEY_ROOT ARE HONOURED when absolute and

validated. An absolute HEY_STDLIB_HEYC executes what it

names. That is INTENDED — it is the documented developer

escape hatch, our own refusal message points users at it,

and anyone who can set a process's environment can generally

already execute code as that user.

* DO NOT BUILD A SHIPPED-VS-DEV DETECTOR. It is not knowable

at runtime, it would be wrong in both directions, and it

would fail SILENTLY. Honour the environment LOUDLY rather

than guessing intent quietly.

* ANNOUNCE when an environment input overrides an

executable-anchored SDK. The loud line is what makes

honouring it defensible instead of silent.

* DOCUMENT IT AS A TRUST BOUNDARY, in these words: setting

HEY_STDLIB_HEYC or HEY_ROOT chooses what code the runtime

will execute; if you do not control the environment, you do

not control the runtime. Hardened runtimes draw this line

explicitly (glibc ignores LD_PRELOAD for setuid binaries

rather than trusting the environment uniformly). We draw it

in the other place, deliberately, and say so.

* OPEN, as its own slice (wenvorder): preferring the

executable-derived SDK over the environment when BOTH

resolve. Pure ladder ordering, no sniffer required — but it

would stop a developer overriding with env when a valid SDK

sits beside the binary, which several of our own tools rely

on. Weigh that before landing it.

19. LIFETIME: THE ORPHAN IS REAL BUT NARROW, AND AN IDLE-FIXTURE

GATE GREENS FOR THE WRONG REASON. There is no lifetime

PRIMITIVE on either platform (zero hits for PR_SET_PDEATHSIG /

prctl / SET_CHILD_SUBREAPER / pidfd) — but "no primitive" is

NOT "always orphans", and the first version of this rule said

so too broadly. CORRECTED 2026-07-29 by the linux seat, who

ran their own draft gate, GOT A GREEN, distrusted it, and

traced the mechanism rather than shipping it.

THE THREE-CASE MODEL:

(a) parent exits NORMALLY -> hey_stdlib_sidecar_atexit

(hey_runtime.c:17177/17331) reaps the sidecar. Clean.

(b) parent KILLED, sidecar IDLE at its read loop -> the

request pipe's write end closes, the getline() at

heyc.c:1389 returns EOF, the loop ends, the sidecar

exits — measured within ~0ms of parent death. Clean,

with no primitive at all, via pipe EOF.

(c) parent KILLED while the sidecar is BLOCKED INSIDE a

delegated call (not sitting at getline) -> neither

atexit nor pipe-EOF is ever observed -> ORPHAN. This is

the measured case: blocked SERVING a listener it

created, alive 1h40m, still holding the port.

CONSEQUENCES YOU MUST NOT GET WRONG:

* The orphan-squat is NOT the general delegating-server

case. It needs a delegated call that BLOCKS, and the one

that does so today is the broken Web.service. Orphan-squat

and the Web.service defect therefore share ONE

reproduction condition — they are not two independent

problems, and fixing the delegation may remove the orphan

at its source.

* A gate built on an IDLE fixture observes pipe-EOF cleanup,

NOT an armed primitive, and would pass identically on a

build with no fix at all. Any lifetime gate needs a

case-(c) fixture: a delegated call that blocks.

* The PDEATHSIG/kqueue fix is STILL correct and still

needed — a signal interrupts the blocked syscall in case

(c), which pipe-EOF structurally cannot reach.

If you write that fix it is a two-body fix: PR_SET_PDEATHSIG

on Linux (re-arm across execve; it keys on the parent THREAD;

re-check getppid() right after arming to close the

already-dead race), kqueue EVFILT_PROC/NOTE_EXIT or getppid()

polling on Darwin, which has no PDEATHSIG equivalent. DO NOT

GATE ON `ppid == 1`: that is a Darwin-only orphan test and

returns FALSE NEGATIVES on systemd boxes where a subreaper

adopts the orphan. The portable predicate is "ppid is not the

pid that spawned me" — record the real parent at spawn and

compare — plus a per-platform assertion that the primitive

was actually ARMED, or the gate certifies the symptom without

the mechanism.

20. THE OTHER TWO WEAKNESSES ARE DISCLOSED AND OPEN, so do not

re-report them as discoveries and do not build on them as if

they were sound: (a) ONE sidecar behind ONE lock, with the

30-second read timeout taken INSIDE the lock — one hung call

stalls every concurrent delegated call for up to 30s; (b) the

lifetime gap in 19. Shipped in 466a: descriptor inheritance

only. NOT shipped: bounded pool, privilege drop, orphan

reaping.

21. NARROWING BEATS SANDBOXING, AND IT IS THE SAME WORK AS S1.

Every stdlib name the compiler lowers NATIVELY can never reach

the delegation path at all. So the S1 lowering-consistency

program is a SECURITY deliverable, not only a performance one,

and that is the durable fix — "sandboxing a helper that still

has to do everything is how you get a sandbox with every door

propped open." When your slice lowers a delegated name, say so

in the commit message in those terms.

22. DISCLOSURE DISCIPLINE. The ARCHITECTURE analysis is published

(URL above) and arms nobody. The PATH-RESOLUTION vector in 17

is NOT published and is NOT to be published, demonstrated in a

public repo, or written into a committed reproducer until the

fix ships. Report outcomes, not recipes. If your slice touches

this family, its commit message describes the hardening, not

the exploit.

THE EMBARGO IS ON THE COMPOSITION, NOT ONLY THE NOUNS (bench's

editor pass, 2026-07-29 — it stopped a draft that named no

file, no variable and no directory, and it was right). The

helper-process article is ALREADY LIVE and tells a reader that

the runtime spawns a helper. Anything that ADDS "there is a

lookup for where that helper is", "it returns a default when

its candidates fail", "there is more than one such sink", or

"the fix REFUSES" composes with what is live into a one-line

search: *how does the runtime locate the helper, and what does

it use when the lookup comes up empty?* That IS the

vulnerability; the withheld nouns are the last 10%. So the

test for outbound text is NOT "did I name the thing" — it is

"does this plus what is already public equal the finding".

THREE SPECIFIC TRAPS, each caught in real drafts:

(a) THE ~150x SLOWDOWN IS A DETECTION ORACLE, not colour. It

tells a reader the fallback is REACHABLE by making the

expected thing missing AND that a stopwatch reveals when

it fires — which against a closed-source binary turns a

benchmark into a scanner. Never pair the fallback's

OBSERVABILITY with its REACHABILITY in outbound text.

(b) "Will be published once users have a version to move to"

CONFIRMS IN PRINT that the shipped release is unpatched

right now. Say "published in full with its fix" — no

state, no timing.

(c) META DESCRIPTIONS, GLOSSARY ENTRIES AND INDEX BLURBS

OUTLIVE RETRACTIONS. Search engines index them and a

later edit of the article body does not reach them. Scrub

those FIRST, not last.

MECHANICAL MARKER: anything in a status report, daily, or

ledger entry that is embargoed carries an explicit EMBARGOED

tag on the bullet, so downstream filtering is mechanical

rather than dependent on a reader noticing. Writing for

public conversion (the DAILY-STATUS pipeline) is exactly

where this is load-bearing.

Instruments (added 2026-07-29 — the night's actual finding, and it

cost three seats one shift to see it)

23. THE BUGS ARE IN THE INSTRUMENTS, NOT THE PRODUCT. In one

session we found SEVEN checks that could not fail, and EVERY

ONE was in an instrument rather than in the compiler: a stale

gate literal; a fail-open resolution ladder; an eliminated

counted loop; a post-exit check with no discriminating power;

a watcher matching yesterday's filename; a lifetime gate whose

idle fixture observed pipe cleanup instead of an armed

primitive; and a process count using a flag the platform does

not support, whose `|| echo 0` fallback turned a usage error

into a plausible zero.

THE PRODUCT'S BUGS WERE CAUGHT. THE INSTRUMENTS' BUGS ARE WHAT

LET THE PRODUCT'S BUGS HIDE — and an instrument is exactly

where nobody looks, because looking at it is not the task.

So, as working rules:

(a) VALIDATE A NEW CHECK IN BOTH DIRECTIONS AGAINST GROUND

TRUTH BEFORE ARMING IT. Present -> 1 against an

independently obtained count; absent -> 0. This is rule 9

applied to your own tooling, and the tooling is where it

gets skipped.

(b) NEVER LET A FALLBACK MANUFACTURE A PLAUSIBLE VALUE. `cmd

|| echo 0` converts "the command failed" into "the answer

is zero", and those are not the same fact. If a check

cannot run, it must say SO — a failed check is not a

passed one. Same fail-closed doctrine as rule 17, applied

to measurement.

(c) PREFER A STATE TO A SUMMARY. "No processes matching X" is

a state; a load average is a lagging summary of one, and a

trough between two stages of the same job reads identical

to done. When both are available, require both, and

require them to persist.

(d) PLATFORM FLAGS ARE A SILENT-FAILURE SURFACE. GNU-only

flags (`--sort=`, `-c` on pgrep, `/proc` paths) fail on

Darwin and BSD-only spellings fail on Linux; either way

the usual shape is empty output plus a fallback that looks

like data. Scope them explicitly and name the

per-platform alternative inline.

(e) AN INSTRUMENT MUST RECORD WHAT IT COULD NOT SEE. A number

whose conditions block cannot say "the box was busy", or

"the toolchain was unpinned", or "this tier does not

exercise the fix" is a number nobody can audit later.

Logging (maintainer directive 2026-07-29 — BINDING, no exceptions

for "it's just noise")

24. CAPTURE STDERR TO A LOG. NEVER TO /dev/null. When you test,

gate, benchmark, probe, or drive software of any kind, stderr

is CAPTURED — to the same log or to a sibling file, but

captured. Sending it to /dev/null throws away the only channel

that tells you WHY something failed, and the one time it

matters is the one time you cannot see it.

MAINTAINER'S WORDS: "all logging should capture stderr into a

log (even if a separate log) while testing software.

Otherwise, we won't know what failures are occurring by

sending them to /dev/null."

THE RECEIPT, from one night: a benchmark harness ran its

generator with `2>/dev/null`, then parsed the empty output

with `2>/dev/null` on the parser. The tool had printed

`error: unexpected argument '-j' found` — loud, immediate,

correct, and naming the exact fix. Both redirects together

turned that into three pairs that LOOKED LIKE THEY HAD RUN,

on a scarce quiet-box window that produced no number. The

error message was perfect. Nobody ever saw it.

HOW, concretely:

(a) `cmd > out.log 2>&1` when interleaved is fine, or

`cmd > out.log 2> out.err` when you need them apart.

Either is acceptable; /dev/null is not.

(b) THIS APPLIES TO THE CONSUMER TOO. Silencing the tool and

then silencing the parser that reads its output is the

same mistake twice, and in series it manufactures a

plausible success. Parse failures must be loud.

(c) EMPTY OUTPUT IS NOT DATA. If a tool wrote nothing, that is

a FAILURE, not a zero, not an empty string, not a skipped

case. Assert non-empty before you parse, and say which

command produced nothing.

(d) "The stderr is just noise" is not a reason to discard it —

it is a reason to send it to a SEPARATE file. Noise you

can read afterwards costs a few KB; noise you discarded

costs a debugging session, and tonight cost a

certification window.

(e) Applies to every layer: regression scripts, gate runners,

chain scripts, benchmark harnesses, one-off probes, and

anything a sub-agent writes in a worktree. If you are

about to type `2>/dev/null` while testing, you are about

to delete evidence.

NARROW EXEMPTION, and state it inline when you use it: a

probe whose ONLY purpose is to test for existence and whose

stderr is a known, expected diagnostic (e.g. `command -v x

2>/dev/null`) may discard it — because there the nonzero exit

IS the signal and no information lives in the message. If the

command can fail for more than one reason, the exemption does

not apply.

Duplication (maintainer ruling 2026-07-29 — corrects a decision this

project already made the wrong way)

25. A DRIFT GATE OVER HAND-SYNCED COPIES IS NOT A FIX. It is a

symptom manager, and shipping one instead of merging the copies

is how an alpha language accumulates cruft it will never be

able to remove.

THE CASE THAT EARNED THIS RULE: the property/method sugar

allowlist is hand-maintained in FIVE places across TWO

languages and BOTH lanes — hey_repl.c, heyc.c, HeyC.hey,

HeyHir.hey, and check_fixed_field_ergonomics.hey. `len` drifted

out of exactly one of them, so `{a:1,b:2}.len` printed 0 in the

SHIPPING lane while the interpreter and native emitter both

printed 2 — a silent wrong answer, in shipped code. The

project's response was to BUILD A DRIFT GATE

(tools/check_property_table_drift.hey) rather than merge the

tables. The maintainer's ruling: **"We are Alpha software. We

are too NEW to be adding CRUFT to our language. Let's do it

CORRECTLY. And NOW, before beta users show up."**

THE DISTINCTION THAT MATTERS, because not every gate is cruft:

* FORBIDDEN — N hand-maintained copies of one concept, plus a

gate that watches them drift. The gate makes the

duplication survivable, which makes it permanent.

* ACCEPTABLE — ONE source of truth, N GENERATED consumers,

plus a gate asserting the generation is current. That gate

checks a build step, not a human's diligence.

So the question to ask of any drift gate you are about to write

or defend: **does it watch copies a human must keep in sync, or

does it assert that a generator ran?** The first is a bug you

are being paid to tolerate. The second is a build check.

ALPHA IS THE ARGUMENT, NOT AN EXCUSE. Hey has NO compatibility

obligations today. Every duplicated table, every parallel

spelling, every hand-synced list is cheaper to remove NOW than

it will ever be again. When you find one, the default is MERGE

IT — and if you cannot, say why in the ledger rather than

reaching for a gate.

Benchmarks (maintainer directive 2026-07-28 — the tight-loop lane)

26. THE TIGHT-LOOP BENCHMARK IS **fannkuch-redux**, AND IT WAS

ADOPTED, NOT INVENTED. Do not write your own tight-loop

microbenchmark. Do not substitute a different program because it

is easier to generate. If you need to measure raw counted-loop

Hey code, this is the instrument.

WHY THIS ONE, from the Linux seat's benchmark research: of the

cross-language programs the field already trusts, fannkuch-redux

is the one that is **pure integer / array / branch with ZERO

hot-path allocation** — so it measures the loop rather than the

allocator.

WHY NOT THE OBVIOUS ALTERNATIVES, stated so nobody re-proposes

them: **binary-trees is an allocator benchmark in disguise** —

picking it would repeat the exact category error this project

nearly committed when three architects almost optimised actor

bytes against workloads that contain no actors. n-body and

spectral-norm are FP-THROUGHPUT, a SEPARATE CATEGORY — do not

fold them into a tight-loop number. Categories stay separate or

the number means nothing.

ADOPTING BEATS INVENTING, and this is the general rule behind the

specific one: **copying the previous method is a CONTROL;

inventing a new one is an EXPERIMENT.** A seat learned that the

expensive way in one night — twice, once by inventing a

command-line flag that did not exist and once by sizing a cell so

short it measured only ramp.

ANTI-DCE RULE, MANDATORY whenever you benchmark a loop:

(a) THE LOOP RESULT MUST BE CONSUMED. An unconsumed result is

dead code and a sufficiently good compiler deletes the

thing you are timing. **An eliminated counted loop is

already one of this project's nine instrument-blindness

findings** — we have made this exact mistake.

(b) INPUTS MUST BE RUNTIME-READ AND NON-CONSTANT. A

compile-time-constant input lets the whole computation fold

away before the timer starts.

(c) If you cannot show the loop actually ran — a consumed

value, a checksum, an assertion on the answer — you have

not measured it. Report the evidence that it ran, not just

the elapsed time.

"THE FIELD TRUSTS THIS BENCHMARK" HAS A SHELF LIFE. DaCapo stopped

exposing real differences and Renaissance exists because of it;

TechEmpower was archived in March 2026 after gaming criticism.

Re-examine any adopted benchmark before leaning on it for a

headline, and say when you last checked.

Worktrees (orchestrator failure 2026-07-29 — the rule I broke was

the inverse of the one I wrote)

27. STOP THE AGENT BEFORE YOU EDIT ITS WORKTREE, AND CONFIRM IT

STOPPED. Rule 1 says agents work only in their assigned worktree.

The inverse binds the ORCHESTRATOR: do not hand-edit a worktree

while its agent is still alive in it.

THE INCIDENT: an agent stalled three times without producing the

renames it was dispatched for. I took the work over, edited its

worktree by hand, staged, committed, and THEN stopped the agent.

Between my edits and my commit the agent did a `git reset` — the

reflog shows it — and my `git add` staged only what survived. The

commit landed with a message describing work that was not in it.

WHAT MADE IT EXPENSIVE was not the lost edits, which took minutes

to redo. It was that I then spent real time diagnosing a

"compiled-lane regression" that did not exist: the runtime failure

I was chasing was the stdlib still holding the OLD name, because

my rename had been reverted underneath me. I ran a control, the

control was sound, and **the thing I was controlling had ceased to

exist.** I reported that phantom regression to the maintainer as a

finding.

THE RULES:

(a) TaskStop the agent FIRST. Verify it is stopped. Then edit.

(b) After ANY period where another writer may have touched the

tree, RE-VERIFY THE FILE CONTENT — not the diff, not your

memory of the edit, the actual bytes on disk — before you

build, measure, or commit.

(c) `git add` + commit is NOT confirmation that your change is in

the commit. Read `git show --stat` and check the file you

edited is listed. A commit message is a claim; the stat is the

receipt.

(d) TWO WRITERS, ONE TREE, AND THE LOSER IS SILENT. Nothing errors.

The tree simply stops containing your work, and every

subsequent measurement is of something else.

Concurrency instruments (linux seat finding, 2026-07-29 — the

eleventh instrument-blindness finding, and the one that bounds

every prior TSAN claim)

28. "TSAN CLEAN" MEANS "NO RACES ON THE PATHS A SPEC HAPPENS TO

DRIVE." It has never meant "no races." TSAN is a DYNAMIC

detector: it reports a race only on a code path that was

actually EXECUTED. Our TSAN battery is driven by the spec

suite, so its coverage is exactly the spec suite's coverage of

CONCURRENT paths — and nobody stated that bound until it cost

us.

THE INCIDENT: two cross-thread refcount races were found under

TSAN via specs 975 and 1191. Fixing those two and declaring the

I5(c) flip safe was the obvious next step. A STRUCTURAL AUDIT —

enumerate every raw-spawn and reactor-handoff caller and check

each against the isolation contract — found **three more sites,

two of them REAL races, that NO SPEC EXERCISES.** They would

have shipped live in the flip. The tested sites were the tip;

the class was two and a half times larger.

ALSO CAUGHT IN THE SAME PASS, and worth its own line: at one

site the mutex GUARDS THE LIST POINTERS, NOT THE SHARED REFS.

**A lock that is present, correct for what it protects, and

irrelevant to the thing that races.** A lock reading as safety.

THE RULES:

(a) A TSAN verdict must state WHAT DROVE IT. "TSAN clean under

specs X, Y, Z" is a claim. "TSAN clean" is not.

(b) FOR A CONCURRENCY CLASS, ENUMERATE THE CALLERS

STRUCTURALLY — a census over the CODE, not a sweep over the

TESTS. Same move as the stdlib name census and S3's

seven-escape-route enumeration: enumerate the family, do

not sample it.

(c) A FIX WITH NO FAILING TEST TO PROVE IT WAS NEEDED IS

INDISTINGUISHABLE FROM A NO-OP. For sites no spec reaches,

BUILD THE DRIVER FIXTURE FIRST, watch it go red, then fix.

Do not fix blind and call it certified.

(d) BEWARE THE FIX THAT SILENCES THE INSTRUMENT. The first

proposed repair here was to make the refcount field atomic.

The codebase's own comment explains why that is wrong: it

would make `refs` race-free while leaving the lazy shape

cache racing IDENTICALLY on the same misuse — TSAN goes

green, the defect survives. Ask of any concurrency fix:

does this remove the RACE, or only the REPORT?

Process killing, refined (near-miss 2026-07-29 — the refinement is

the non-obvious half, and it nearly cost a landing)

29. A PATTERN SPECIFIC ENOUGH TO LOOK SAFE IS STILL NOT SAFE, BECAUSE

SCRIPTS NAME THE WORK THEY ARE LANDING. Rule 4 says never pkill by

name/pattern. The obvious reading is "patterns are too broad, so

narrow them." That reading is WRONG and it is how this nearly went

badly.

THE NEAR-MISS: an agent cleaning up after itself searched for its

own slice name — `wp1put`, about as specific as a pattern gets,

and unique to that agent. It matched the ORCHESTRATOR'S LANDING

CHAIN, because the landing chain's script TEXT NAMES THE SLICE IT

IS LANDING while operating on a completely different tree. The

agent read each command line before acting, saw the path was

`$HOME/dev/claude_01` and not `worktrees/wp1put`, and did not kill

it. **Checking before acting is the only reason a green chain

survived.**

THE GENERALISATION, which is what makes this worth a rule:

**THE SEAT MOST LIKELY TO BE PATTERN-KILLED IS THE ONE WHOSE NAME

IS IN EVERYONE ELSE'S CHAIN.** Your slice name appears in the

orchestrator's transplant script, in landing notes, in gate

registrations, in commit messages being written by a shell. The

more central your work, the more processes mention it, and the

more dangerous a "specific" pattern becomes.

THE RULES:

(a) Kill by RECORDED PID, from a list you wrote when you spawned

the process. Not by pattern, however specific.

(b) If you must search, READ THE FULL COMMAND LINE AND ITS WORKING

PATH before killing anything, and kill by explicit PID after.

A match is a candidate, not a verdict.

(c) DETACHED CHILDREN OUTLIVE THEIR WRAPPERS. Stopping the task

you started is not the same as stopping what it spawned.

Verify no survivors rather than assuming; the agent here found

four.

Dot-methods (MAINTAINER RULE, 2026-07-29 — stated canonically, and

it is a RULE, not a preference. Quote it, do not paraphrase it.)

30. **"DOT-METHODS ARE A SYNTACTIC-SUGAR (NICE-TO-HAVE) THEY ONLY

(EVER) EXISTS BECAUSE OF AN EXPLICIT IMPORT AND THEY LOSE TO

CONFLICTING NAMES. AT WHICH POINT THE SYSTEM WILL (GENEROUSLY)

PRODUCE A WARNING MESSAGE."**

Four clauses, each load-bearing:

(a) **SUGAR, NOT SUBSTANCE.** `Module.fn(x)` is the real spelling

and is always correct. `x.fn` is a convenience layered on top.

Never design as though the dot form is the primary API — if a

feature only works through the dot form, that is a defect.

(b) **ONLY (EVER) VIA AN EXPLICIT IMPORT.** No value has default

dot-methods. **THIS IS UNIFORM ACROSS TYPES — arrays and

strings get no exemption**, even though they have no user keys

to collide with. AND IT FORECLOSES THE OBVIOUS ESCAPE HATCH:

**no implicit prelude, no auto-import, no "core methods are

always there".** "Explicit" means a line the author wrote.

(c) **THEY LOSE TO CONFLICTING NAMES.** A user's key always wins.

Never resolve a collision in the method's favour, and never

add a mechanism that lets a method reclaim a shadowed name.

(d) **THE WARNING IS OWED, AND IT IS GENEROUS.** Losing silently

is the failure this rule exists to prevent. The compiler tells

the author **they lost the `.method`**, states what it did,

and gives the qualified form as the fix. Generous means:

assume the author wanted the method and got surprised, not

that they need scolding for naming a key.

WHY UNIFORM BEATS SCOPED, since the orchestrator argued the other

way and was overruled: a type-scoped version (maps lose default

members, arrays/strings keep theirs) is cheaper ergonomically but

**requires users to learn a rule PLUS a list of which types are

exempt.** One rule with no exceptions is teachable in a sentence.

That is the same anti-cruft ruling as 25, applied to syntax.

THE COST, stated so nobody rediscovers it as a surprise:

`[1,2,3].count` and `'hey'.length` require an import too. This is

real friction against the Ruby-parity north star and it is

ACCEPTED, not overlooked. Quantify it; do not re-litigate it.

ALREADY TRUE FOR `Collections` — `import 'stdlib:Collections'`

makes `names.uniq` lower to `Collections.uniq(names)` and is

documented as explicit on purpose. **Ten builtin names currently

BYPASS this rule. That exemption is the defect; the rule is not

new machinery.**

THE RATIONALE, added by the maintainer 2026-07-29, AND IT IS

STRONGER THAN THE COLLISION ARGUMENT — cite THIS, not the

collision, when a brief needs to justify rule 30:

**THE LANGUAGE IS VERY SIMPLE.** In his words, it has "functions,

actors, json-compliant objects, strings, numbers, conditionals, and

loops" — and possibly the Jobs abstraction, "but even that ?could?

(theoretically) be written using some syntactic-sugar over our

actor / function syntax."

**IF THE ESSENCE IS THAT SMALL, THEN EVERYTHING ELSE IS SUGAR BY

DEFINITION.** Rule 30 stops being a policy about collisions and

becomes a CONSEQUENCE of what the language is: sugar is opt-in

because sugar is not the language. A dot-method that shadows a

user's data is sugar overruling substance, which is backwards.

AND SIMPLICITY IS NOT AESTHETIC HERE — IT IS THE MECHANISM THAT

KILLS TWO-LANE DIVERGENCE. Every construct with its OWN lowering

path is a place the native emitter and the HeyLlvm mirror can

disagree. Check the ledger: 467a (bool stored as the TEXT "true"),

470a (get and put dispatching by different rules for TEN

versions), the mirror refusing shape C while native accepted it,

`has`/`has?` still carrying the disease. **EVERY ONE OF THOSE

LIVED IN A CONSTRUCT THAT HAD MORE THAN ONE LOWERING.** Fewer

primitives is fewer places a wrong answer can hide, and it is a

shorter mirror to finish before native-C can be deleted (R3, R7.3).

SO THE TEST FOR ANY PROPOSED LANGUAGE FEATURE IS: does it need to

be a primitive, or can it be sugar over the core? **If it can be

sugar, it must be sugar, and rule 30 then governs it.**
