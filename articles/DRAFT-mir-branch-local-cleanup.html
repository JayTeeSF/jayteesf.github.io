Hey compiler · dated addendum · 15 September 2026

Cleanup must account for the path that creates a temporary

If a compiler reports success, you should be able to compile its output. A field-length expression in Hey exposed a gap in that promise: emission succeeded, but cleanup used a temporary on a path where that temporary had never existed. Understanding the repair gives you a useful test for compiler progress: ask which boundary the evidence actually crossed.

What this repair establishes

  • The bounded field-length cleanup repair is worth retaining: its focused checks now reach native execution.
  • The lifetime decision belongs in Hey’s middle intermediate representation, or MIR: the compiler’s explicit plan for executing operations.
  • Disclosed weakness: the complete archive build, which compiles the standard library into a linkable library, and ordinary consumer gates, which test real applications through the ordinary compiler path, remain unproved at this checkpoint.
  • To challenge the result, rebuild the reviewed compiler repair and run test/gate_llvm_nested_string_calls.sh, including its clang and native checks.

An unconditional release cannot follow both branches

In left or right, a true left operand makes the right operand unnecessary. When the right side reads a record field’s length, the compiler creates a temporary wrapper only on that side. Unconditionally releasing it after both paths join is invalid: execution can arrive there through the shortcut, without creating the wrapper. Guarded cleanup after a join can be valid; the defect is using this temporary without a definition on every incoming path.

This is a definition-dominance failure. A definition must occur on every path reaching an ordinary use of its value; releasing a value is a use too. LLVM explicitly distinguishes acceptable syntax from well-formed code, including whether a definition dominates its uses. LLVM’s well-formedness rules explain why producing plausible instruction text is insufficient.

The old focused gate passed 8 source assertions before clang rejected the generated code for dominance, as recorded in the dated validation receipt. Likewise, emission.ok established that Hey’s emitter produced a result. It did not establish that LLVM could accept that result. The missing check sat at the next boundary.

The wrapper owns a lifetime; the payload can remain shared

A field accessor returns an owned carrier: a wrapper the expression must eventually release. That ownership does not mean the underlying field payload is exclusively owned. Confusing the two can turn cleanup into premature destruction of data another value still needs.

Here the last use is unusually clear. Length borrows the field wrapper and returns an integer. The integer does not need the wrapper to remain alive. The bounded MIR plan therefore orders four operations: load the boxed binding, obtain the owned field, calculate length, release the owned field. A bare boxed binding needs no newly created field wrapper and gets no corresponding field release. “Bounded” means this plan handles a recognized subset of operands, rather than deciding every expression’s lifetime.

Keeping cleanup at statement end is tempting because it centralizes bookkeeping. This example shows its cost: bookkeeping must also understand which paths created each temporary. Recording last use with the operand makes that fact explicit before LLVM text exists.

The executing route must consume the plan

Repairing a helper named for length would look reasonable, but the failing call reached the runtime through its resolved target identity and validated calling convention. It did not use either legacy route selected by the printed spelling of length.

The repair connects HeyMir.runtime_length_plan to hey_llvm_runtime_call_value after validation of the runtime call’s application binary interface: its declared argument, result and ownership contract. The plan requires a borrowing declaration and carries the declared runtime symbol into the length operation. The LLVM emitter then renders the ordered operations. No scan of emitted LLVM decides whether this field wrapper needs cleanup.

Review found two boundaries the first repair missed

The first repair passed its focused gate but intercepted a property protocol: a special meaning attached to a selector such as .length. With a record containing its own length: [1,2] key, len(record.length) returned 2 instead of the existing behavior’s 0. Both a directly compiled reproduction and a full source gate exposed the regression. The reviewed MIR plan now refuses known protocol selectors, preserving their existing route.

Review also found that the plan bypassed the declared runtime symbol and ownership policy. The correction carries that symbol and requires the argument to be declared borrowed. The length declaration now explicitly states borrow, matching the runtime implementation. These were correctness gaps in the first repair, not optional extensions to its scope.

A successful complete archive and passing ordinary consumer gates would extend the evidence. Until then, the useful conclusion is precise: this temporary’s last use now governs its cleanup on the route that actually executes.
