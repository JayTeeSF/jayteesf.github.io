wsmoketriage — `make self-hosting-smoke` / "unclosed block depth 3" triage

Worktree: `/Users/jthomas/dev/claude_01/.worktrees/wsmoketriage`

Env script: `bin/claude01-env-wsmoketriage.sh` (own HEY_CACHE_HOME etc., copied+adapted

from `.worktrees/wvalguard`).

Scratchpad transcripts: all prefixed `wsmoketriage_` in

`/private/tmp/claude-501/-Users-jthomas-dev-claude-01/16e1cb20-d221-4aaf-a9f8-1d9aa27538f7/scratchpad/`.

Verdict (headline)

**This is a real, reproducible, deterministic false positive in the naive

line-based Hey syntax checker — NOT a real unclosed block in

`stdlib/HeyC.hey`, NOT cache-sensitive, and NOT load/flake-sensitive.**

It is a **checker limitation**: the checker scans the raw file text line by

line with zero awareness of heredoc literals (`<<~C ... C`). Three functions

in `stdlib/HeyC.hey` emit literal C source via heredocs, and those emitted C

lines (`if (cond) {`, `while (cond) {`) start with the exact prefixes `"if "`

/ `"while "` that the checker's classifier treats as REAL Hey block openers.

Because C code closes blocks with `}`, not a line that is exactly `end`, the

spurious "open" is never balanced inside the heredoc — it silently steals the

*next* real `end` in the file (LIFO stack effect), leaving the enclosing `fn`

permanently open. Three such heredocs -> three permanently-open `fn` frames

-> `unclosed block depth 3`.

1. Message source (file:line)

Two independent implementations of the same naive algorithm exist; the one

that actually runs for `make self-hosting-smoke` is the pure-Hey one

(confirmed by the error trace ending `in repl`, i.e. interpreted, not the

native/LLVM mirror):

  • **Pure-Hey (the one that fires here):**

`stdlib/HeySyntax.hey:175`

```

set next_errors = push(next_errors, source + ': unclosed block depth ' + next_depth)

```

inside `hey_syntax_scan_lines_value` (starts `stdlib/HeySyntax.hey:141`),

called from `hey_syntax_check_text_value` (`:194`) <- `check_file`/`manifest`

(`:218-226`) <- `tools/hey_syntax_check.hey:4` (`HeySyntax.manifest('stdlib')`)

<- `make self-hosting-smoke`'s first recipe line.

  • **Native/LLVM-lane mirror (same bug class, NOT what fired this run but

worth flagging as a twin defect):**

`runtime/hey_runtime.c:17461` (message construction) and the classifier it

depends on at `runtime/hey_runtime.c:15588-15607`

(`hey_llvm_tool_line_kind_raw`) / `:15609-15611`

(`hey_llvm_tool_kind_opens`). Same `"if "` / `"while "` prefix rule, same

lack of heredoc/string awareness. This mirror was NOT exercised by the

failing `make self-hosting-smoke` invocation (that goes through the

interpreted Hey module), but it has the identical latent bug and would

reproduce it if ever used to check `stdlib/HeyC.hey`.

2. Exact classifier bug

`stdlib/HeySyntax.hey:29-89` (`hey_syntax_line_kind_value`) classifies a

TRIMMED line by pure string-prefix match against the RAW FILE TEXT, with NO

regard for whether that line is inside a string/heredoc literal. Opens are

lines whose trimmed text starts with one of: `program`, `spec `, `import `,

`module `, `fn `, `job `, `worker `, `actor `, `if `, `while `, `until `,

`for `. Closes are lines whose trimmed text is EXACTLY `end`.

`stdlib/HeyC.hey` contains three heredocs emitting literal C:

  • `hey_c_emit_if_value` (`stdlib/HeyC.hey:305-326`), heredoc at

`:315-318`: emitted line ` if (#{...}) {` trimmed starts with `"if "`.

  • `hey_c_emit_while_value` (`stdlib/HeyC.hey:328-338`), heredoc at

`:333-336`: emitted line ` while (#{...}) {` trimmed starts with

`"while "`.

  • `hey_c_emit_until_value` (`stdlib/HeyC.hey:340-350`), heredoc at

`:345-348`: emitted line ` while (!(#{...})) {` trimmed starts with

`"while "`.

Each of these heredoc lines is misclassified as a real Hey block opener.

Because the heredoc's own terminator (`C`) and the following `}`/text lines

never classify as `end`, the spurious open is unmatched *inside* the heredoc

region, so the checker's stack (verified by independent simulation, see

below) consumes the function's own legitimate closing `end` to close the

spurious open instead — leaving the enclosing `fn` open. This repeats for

all three functions, producing exactly 3 permanently-open frames and

`unclosed block depth 3` at end of file.

Independent verification (two methods, both agree with the real tool)

1. **Python re-implementation** of the exact classifier +

open/close-stack simulation

(`/private/tmp/.../scratchpad/wsmoketriage_replicate_checker.py`) run

against the real `stdlib/HeyC.hey`:

```

final depth=3 max_depth=13

remaining unclosed stack (top-level first), count=3:

line 305: kind='fn' text='fn hey_c_emit_if_value(stmt, env)'

line 328: kind='fn' text='fn hey_c_emit_while_value(stmt, env)'

line 340: kind='fn' text='fn hey_c_emit_until_value(stmt, env)'

```

This exactly matches the real checker's depth-3 verdict and identifies

the three unclosed frames as precisely the three heredoc-bearing

functions.

2. **Minimal isolated repro**, no `stdlib/HeyC.hey` involved

(`/Users/jthomas/dev/claude_01/.worktrees/wsmoketriage/wsmoketriage_repro.hey`,

left in place): a hand-built string containing a normal balanced

`fn ... if ... end ... end` PLUS one extra line that merely *looks like*

embedded C (` if (x) {`) with no matching `end`, fed straight to

`HeySyntax.check_text`. Result:

```

false

["sample: unclosed block depth 1"]

```

confirming the false-positive mechanism is general (any text line

starting with `if `/`while `/`for `/`until `/etc. with no paired `end`

trips it), not something exotic to `HeyC.hey`.

**Conclusion: this is a checker limitation (heredoc/string-blind naive line

scanner), not a real unclosed block in the Hey source.** The three flagged

functions are correctly written, properly balanced Hey code.

4. Cache-sensitivity verdict: NOT cache-sensitive

At `bde0089b`, ran the failing step (`./bin/heyc tools/hey_syntax_check.hey

--run`) three times:

1. Fresh build, first run → RED.

2. Immediate rerun, same (now-populated) cache → RED, byte-identical message.

3. `rm -rf "$HEY_CACHE_HOME"` (full nuke of parser/run/source-index/runtime-object

caches), rerun → RED, byte-identical message.

Also ran a full fresh build + fresh, uniquely-named cache

(`Hey-claude01-wsmoketriage-423a`) at `bb331f5e` and got the same RED,

byte-identical message. **No flip observed under any cache condition

tested.** This rules out the "load/cache-sensitive flake" hypothesis

outright — the failure is deterministic given the current

checker+HeyC.hey pairing, at every base tested.

5. On the "green at 423a" record

The wactordiet/`e2c65f48` commit message records `BASE (bb331f5e)` for its

actor-size measurements, and per the brief this base was separately recorded

as "self-hosting-smoke was green" during that battery. **Direct

reproduction at ALL FOUR tested bases (`bb331f5e`/423a, `fdf31642`/437a,

`e2c65f48`/438a, `bde0089b`/current), each with an independent rebuild and a

brand-new, never-before-used cache home, is RED**, with byte-identical error

text throughout. Given the file-identity findings above (the entire checker

call chain — `stdlib/HeyC.hey`, `stdlib/HeySyntax.hey`,

`tools/hey_syntax_check.hey`, `stdlib/Files.hey` — is byte-identical across

the whole `bb331f5e..bde0089b` range), there is no code-level way for any of

these four bases to have behaved differently from one another under the same

harness — and none did. The most likely explanations for the "green at

423a" record, in descending probability:

1. The "green" record from that other battery reflects a run against a

working tree that had **uncommitted local changes** at the time (e.g. a

WIP fix to `HeyC.hey`'s heredocs, or to the checker, that was later

discarded without being committed) — i.e., the actual on-disk bytes

differed from the `bb331f5e` git blob, even though the sha in the record

is `bb331f5e`.

2. The other battery ran a different target/invocation than the literal

`make self-hosting-smoke` recipe (e.g. a different `tools/*.hey` script,

or ran under `--run` against a stale prebuilt `heyc` from a different,

newer worktree on `$PATH` — an env-sourcing slip, which standing rule #1

explicitly warns is a live hazard: "unsourced = trunk toolchain silently").

3. Simple transcription/recollection error in the record.

**This is NOT an environment/cache flake class** (ruled out directly, see

§4) — it is either a genuinely pre-existing defect that was always present

at `bb331f5e` and simply never actually got exercised/verified then, or the

prior "green" data point itself is unreliable.

6. RESOLVED — fix landed in this commit

The triage below stands; the "not fixed" note in §6 applied to the triage-only

brief and is superseded. Both implementations of the checker are now

heredoc-aware, using the parser's own opener grammar:

  • `stdlib/HeySyntax.hey` — `hey_syntax_heredoc_open_value` /

`hey_syntax_heredoc_terminator?`, consumed by `hey_syntax_scan_lines_value`.

  • `runtime/hey_runtime.c` — `hey_llvm_tool_heredoc_open` /

`hey_llvm_tool_heredoc_terminator`, consumed by

`hey_llvm_hey_syntax_check_text_owned`.

Pinned by `specs/language/1231_syntax_checker_heredoc_awareness.hey` and held

in both-lane agreement by `test/regression_hey_syntax_heredoc_parity.sh`.

The throwaway `wsmoketriage_repro.hey` referenced in §2 was deleted rather than

committed: its shape is now case `heredoc_dedent_tag` in the parity fixture and

an assertion in spec 1231, and a stray `.hey` at the repo root would be swept

up by `tools/hey_source_hotspots.hey`'s `Files.hey_files('.')` glob.

6b. Not fixed (original triage-only scope)

No files were modified other than: this NOTES.md, the worktree-local env

script `bin/claude01-env-wsmoketriage.sh`, and the throwaway repro file

`wsmoketriage_repro.hey` (both untracked, left in place for inspection).

`stdlib/HeyC.hey`, `stdlib/HeySyntax.hey`, `tools/hey_syntax_check.hey`,

`runtime/hey_runtime.c` are untouched.
