A web server in Hey

You'll start with a three-line route, test it without opening a socket, then grow it into a small hey_web app with controllers, views, a SQLite database and background Jobs. Then you'll break a handler on purpose, build the server into one native binary, and choose between the two ways Hey can carry connections.

The short version

  • A route is a function. Web.get('/hello/:name', hello) pairs a path with an ordinary Hey function that takes a request and returns a response.
  • The same route table runs with or without a socket. Web.dispatch answers a request value in a test; Web.serve answers real HTTP.
  • The hey_web package adds the Rails-shaped parts: a config file, controllers, EHY views with layouts, Jobs helpers, a request log, auth helpers and a curl-like client.
  • A failing handler costs one request. That request gets a 500; the next one is served normally.
  • The default transport is a thread per connection. A second lane, the readiness poller, is opt-in: you import it and call one different function. Pick it when you hold many mostly idle connections.

1. Your first route Works today

A route is a pair: an HTTP method and path, and the function that answers it. A handler is that function. It gets one argument, the request, and returns a response. No classes, no decorators.

hello_web.hey

import 'stdlib:Web'

fn hello(request)
  return Web.text('Hello, ' + request.params.name + "\n")
end

fn health(request)
  return Web.json({ok: true})
end

program
  let routes = Web.routes([
    Web.get('/hello/:name', hello),
    Web.get('/health', health)
  ])
  says 'listening on http://127.0.0.1:8080'
  let served = Web.serve(routes, {host: '127.0.0.1', port: 8080, workers: 4})
end

:name in the path is a path parameter: whatever sits in that spot of the URL shows up as request.params.name. Start it with hey hello_web.hey (it compiles to native code and caches it, like go run), then from a second terminal:

$ curl -si localhost:8080/hello/Ada
HTTP/1.1 200 OK
content-type: text/plain
content-length: 11
connection: keep-alive

Hello, Ada
$ curl -s localhost:8080/health
{"ok":true}
$ curl -si localhost:8080/nope
HTTP/1.1 404 Not Found
content-type: application/json
content-length: 21
connection: keep-alive

{"error":"not_found"}

When it starts, the server also prints a line to stderr with the limits the runtime picked for this machine: how many worker threads, how many open connections it will hold at most (worked out from the machine's memory), and what happens past that limit (the extra connection gets a 503 and is closed).

The response helpers in stdlib:Web: Web.text, Web.html, Web.json, Web.created (201), Web.accepted (202), Web.bad_request, Web.unauthorized, Web.forbidden, Web.not_found, Web.method_not_allowed, Web.conflict, Web.payload_too_large, Web.unprocessable, Web.server_error, Web.redirect(location) and the general Web.response(status, headers, body). Routes: Web.get, Web.post, Web.put, Web.patch, Web.delete. Reading the request: Web.param, Web.query_param(request, name, fallback), Web.header, Web.body, Web.json_body. Static files: Web.file(root, path) and Web.file_from(request, root), which pick the content type from the extension.

2. Test routes without a socket Works today

The route table is a plain value, so you can hand it a request value and get a response value back. No port, no HTTP client, no waiting for a server to come up. Web.dispatch does the matching, and Web.serve uses the same function for real requests.

hello_dispatch.hey

spec 'routes answer without a socket'
  expect stdout "200\nHello, Ada\n\n404\n"
end

import 'stdlib:Web'

fn hello(request)
  return Web.text('Hello, ' + request.params.name + "\n")
end

program
  let routes = Web.routes([Web.get('/hello/:name', hello)])
  let found = Web.dispatch(routes, {method: 'GET', path: '/hello/Ada', headers: {}, body: ''})
  says found.status
  says found.body
  let missing = Web.dispatch(routes, {method: 'GET', path: '/nope', headers: {}, body: ''})
  says missing.status
end

The spec block at the top says what the program must print. heyc --test FILE runs the program and compares:

$ hey hello_dispatch.hey
200
Hello, Ada

404
$ heyc --test hello_dispatch.hey
PASS: routes answer without a socket

3. What happens to one request

Two things to take from the picture. First, everything except your handler is the runtime's C code: reading bytes, parsing the HTTP head, writing the reply. Second, the default lane gives each open connection its own thread for as long as the client keeps it open. (Browsers and HTTP clients keep a connection open after a request so the next one skips the TCP handshake; that's keep-alive.) That's simple and fast while connections are busy, and it's the reason a second lane exists (section 10).

4. Grow it into a hey_web app Works today

hey_web is a package that sits on top of stdlib:Web. It doesn't parse HTTP or open sockets itself. It adds the shape a Rails developer expects:

app/controllers/cards_controller.hey

import 'stdlib:Web'
import 'stdlib:Text'
import 'pkg:hey_web@0.3.9/views'
import 'pkg:hey_web@0.3.9/jobs'
import '../models/card_store.hey'
import '../jobs/welcome_job.hey'

# <%= %> prints text as it is. Escape anything a user typed before it reaches a view.
fn h(text)
  let out = Text.replace_all('' + text, '&', '&amp;')
  set out = Text.replace_all(out, '<', '&lt;')
  set out = Text.replace_all(out, '>', '&gt;')
  return Text.replace_all(out, '"', '&quot;')
end

module CardsController
  fn index(request)
    let shown = []
    for card in CardStore.all()
      set shown = [...shown, {front: h(card.front), back: h(card.back)}]
    end
    return HeyWebView.response('app/views/cards/index.ehy', {title: 'Cards', cards: shown}, 'app/views/layouts/application.ehy')
  end

  fn list(request)
    return Web.json({cards: CardStore.all()})
  end

  fn create(request)
    let body = Web.json_body(request)
    let added = CardStore.add(body.front, body.back)
    if added.ok == false
      return Web.bad_request({error: added.error})
    end
    return Web.created({front: body.front, back: body.back})
  end

  fn search(request)
    return Web.json({q: Web.query_param(request, 'q', '(none)')})
  end

  fn signup(request)
    let body = Web.json_body(request)
    return HeyWebJobs.accepted(WelcomeJob.pool(), {email: body.email})
  end

  fn boom(request)
    fail 'this handler always fails'
  end

  fn health(request)
    return Web.json({ok: true})
  end
end

app/models/card_store.hey: the database code, explained in section 6

import 'stdlib:Env'
import 'pkg:hey_sqlite3@0.5.2/adapter'

# One place that opens the database. A connection is not shared
# between threads, so each call opens its own and closes it.
module CardStore
  fn path()
    return Env.default('CARDS_DB', 'db/cards.sqlite3')
  end

  fn open()
    let connected = Sqlite3.connect(CardStore.path(), {library_path: Env.default('HEY_SQLITE3_LIBRARY', '')})
    if connected.ok == false
      fail connected.code + ': ' + connected.error
    end
    return connected.value
  end

  fn setup()
    let db = CardStore.open()
    let made = Sqlite3.execute(db, 'CREATE TABLE IF NOT EXISTS cards (id INTEGER PRIMARY KEY, front TEXT NOT NULL, back TEXT NOT NULL)')
    let closed = Sqlite3.close(db)
    return made.ok
  end

  fn add(front, back)
    let db = CardStore.open()
    let added = Sqlite3.execute_params(db, 'INSERT INTO cards (front, back) VALUES (?, ?)', [front, back])
    let closed = Sqlite3.close(db)
    return added
  end

  fn all()
    let db = CardStore.open()
    let found = Sqlite3.query(db, 'SELECT id, front, back FROM cards ORDER BY id')
    let closed = Sqlite3.close(db)
    return found.value.rows
  end
end

app/jobs/welcome_job.hey: background work, explained in section 7

import 'stdlib:Jobs'

# A worker is a plain function that runs on the Job's own threads.
worker SendWelcome(message)
  return 'welcome sent to ' + message.email
end

module WelcomeJob
  # Jobs.define names the pool. Defining the same name again hands back
  # the pool that already exists, so a handler can call this every time.
  fn pool()
    return Jobs.define('CardsWelcomes', SendWelcome, count: 2, capacity: 64, result_capacity: 64)
  end
end

server.hey

import 'stdlib:Cli'
import 'pkg:hey_web@0.3.9/main'
import 'pkg:hey_web@0.3.9/config'
import 'pkg:hey_web@0.3.9/server'
import 'config/routes.hey'
import 'app/models/card_store.hey'

program
  let ready = CardStore.setup()
  let config = HeyWebServer.options(Cli.args(), HeyWebConfig.load_or_default('config/hey_web.json'))
  let app = HeyWeb.application('cards', Routes.all(), config)
  says HeyWebServer.banner(app)
  let running = HeyWeb.serve(app)
end

HeyWebServer.options reads the JSON and then lets flags override it, so --port 3001, --workers 8, --host, --request-timeout-ms and --max-body-bytes all work. workers: 0 means one per CPU core.

Predict it. server.hey imports pkg:hey_web@0.3.9/main, and main.hey itself imports config.hey. So why does server.hey also import .../config?

Answer

Imports in Hey are lexical: a file may call a module only if that file imports it. Importing main doesn't pass HeyWebConfig through to you. Leave the import out and the compiler stops with HeyWebConfig.load_or_default requires a direct import in this source unit. That's on purpose: you can read any file and see every module it can touch. Modules, imports, exports has the rules.

5. Views: EHY templates and layouts Partly works

EHY is Hey's version of ERB. <%= expr %> prints a value, <% code %> runs a statement (loops, ifs), <%# ... %> is a comment, and -%> also eats the newline after the tag. The controller calls HeyWebView.response(view, bindings, layout): the view renders first, and its output becomes content in the layout. Pass '' as the layout for none.

Escaping is your job

<%= %> prints text exactly as it is. It does not turn < into &lt;, and the standard library has no public HTML-escape function. That's why the controller runs every user-typed field through its own small h() before handing it to the view. Without it, a card holding a <script> would run in your visitors' browsers.

Start the server from the app folder, with the SQLite library, and add two cards:

$ curl -s -X POST localhost:3000/cards -d '{"front":"hola","back":"hello"}'
{"front":"hola","back":"hello"}
$ curl -s -X POST localhost:3000/cards -d '{"front":"<b>x</b>","back":"tags & such"}'
{"front":"<b>x</b>","back":"tags & such"}
$ curl -si localhost:3000/
HTTP/1.1 500 Internal Server Error
content-type: application/json
content-length: 24
connection: keep-alive

{"error":"server_error"}

The page failed, and the server log says hey error: ehy: render failed for build/ehy_render_....hey. Rendering a template writes it out as a small Hey program in build/, then runs ./bin/heyc on it, and that program imports ../stdlib/Ehy.hey. Both paths are relative to the server's working folder, so they only exist inside the Hey source tree. Give the app those two paths and the page renders:

$ mkdir -p bin && ln -s $TOOLCHAIN/bin/heyc bin/heyc && ln -s $TOOLCHAIN/stdlib stdlib
$ curl -s localhost:3000/
<!doctype html>
<html><head><title>Cards</title></head>
<body>
<h1>Cards</h1>
<ul>

  <li>hola &rarr; hello</li>

  <li>&lt;b&gt;x&lt;/b&gt; &rarr; tags &amp; such</li>

</ul>

</body></html>

The escaped card shows up as text, as it should. But every request compiles and runs two small programs (view, then layout), so a page takes far longer than the same rows as JSON, and each render leaves a build/ehy_render_*.hey file behind.

What to use instead. hey_web's bin/pages-embed renders .html.ehy files once, at build time, into a generated Hey module, so serving a page is returning a string. Or read an HTML template with Files.read_text and fill {{TOKEN}} placeholders with Text.replace_all. Request-time EHY is fine for an admin page; keep it off a hot path.

6. A database Works today (as packages)

Hey has no database built in. Drivers are packages, published in the same registry as hey_web: hey_sqlite3 (SQLite: prepared statements, typed rows, rows as JSON built by SQLite itself), hey_postgres, hey_mysql, hey_duckdb (analytics queries), and hey_record (models on top of a driver, the Active Record role).

CardStore in app/models/card_store.hey opens the database, creates the table, adds and lists cards. Typed rows means each column comes back as the Hey value its SQLite type maps to: the INTEGER id arrives as a number ("id":1 below, no quotes), TEXT as a string, NULL as nil, a BLOB as bytes. The ? placeholders are filled by SQLite from the list you pass, so a value never becomes part of the SQL text:

$ curl -s localhost:3000/cards
{"cards":[{"id":1,"front":"hola","back":"hello"},{"id":2,"front":"<b>x</b>","back":"tags & such"}]}
$ curl -s 'localhost:3000/search?q=cats'
{"q":"cats"}

Rules for database calls in a server

  • One connection per thread. A connection is mutable state outside Hey; don't share one between workers. This sample opens one per call to stay short. A busier app keeps one per worker so SQLite's statement cache stays warm.
  • Database calls block. On the default lane that's acceptable: it ties up one worker for that request. On the poller lane (section 10) it stalls every connection on the loop, so move slow queries into a Job there.
  • Migrations are yours. Neither hey_web nor the drivers ship a migration tool. A simple pattern: db/schema.sql creates tables with CREATE TABLE IF NOT EXISTS, and a script checks each expected column with pragma_table_info and adds the missing ones.
  • JSON straight from SQLite. Sqlite3.query_rows_json(db, sql, params) returns the rows already encoded as JSON text, so a JSON endpoint doesn't build Hey values just to turn them back into text.

Decided, coming Each call into the C library goes through a general-purpose bridge that looks the function up by name at run time. The ruled replacement reads the package's hey.native.json at build time and emits a direct, typed call: Native code and C.

7. Background work with Jobs Works today

A Job is a named pool of worker threads with a bounded queue. You hand it a message, you get a receipt back right away, and a worker runs the function later. Retries, dead letters and how to choose between Jobs, workers and actors are in Workers, Jobs and streams; here's the web part.

WelcomeJob.pool() in app/jobs/welcome_job.hey calls Jobs.define with a fixed name; defining the same name again hands back the pool that already exists, so a handler can call it every time. The controller's signup calls HeyWebJobs.accepted(WelcomeJob.pool(), {email: body.email}). That enqueues the work and answers 202 Accepted with the receipt, so the client can ask about it later (HeyWebJobs.await(job, receipt, timeout_ms) waits for the result). If the queue is full the client gets a 500 with job_queue_full instead of the request hanging.

$ curl -si -X POST localhost:3000/signup -d '{"email":"ada@example.com"}'
HTTP/1.1 202 Accepted
content-type: application/json
content-length: 51
connection: keep-alive

{"accepted":true,"job":"CardsWelcomes","receipt":1}

Why not the shorter job Welcomes ... end form? That declaration only works in the file that holds program; put it in app/jobs/ and import it, and the compiler refuses: job declarations are application-entry declarations and cannot be imported. A handler also can't see values the program made at startup (handlers are looked up by name and capture nothing). So the pattern is a function that calls Jobs.define with a fixed name, as here.

8. When a handler fails Works today

Hey fails fast: there's no try/rescue. A runtime error or a fail stops the unit of work it happened in, and for a server that unit is one request. The /boom handler always fails. Here's the server answering it, then answering the next request as if nothing happened:

$ curl -si localhost:3000/boom
HTTP/1.1 500 Internal Server Error
content-type: application/json
content-length: 24
connection: keep-alive

{"error":"server_error"}
$ curl -s localhost:3000/health
{"ok":true}

The server log names the error and the route: hey error: this handler always fails, then hey: web handler on GET /boom stopped by a runtime error; answering 500. That holds on the native binary, on hey server.hey, and on both transport lanes.1 The runtime also releases the values the abandoned calls had registered, so a failing route doesn't pile up memory. What this does not cover: a handler stuck in an endless loop without an error is not stopped, and a call blocked inside C can't be interrupted. The full rules, with actors and Jobs, are in Actors and failure.

9. Build it: the binary you ship Works today

hey server.hey is for development: the first run compiles and caches, later runs reuse the cache. To ship, build one executable. It's called exactly what you pass to -o:

$ hey build server.hey -o build/cards
built .../build/cards
$ ls -lh build/cards
-rwxr-xr-x  1 ... 447K ... build/cards
$ otool -L build/cards

	/usr/lib/libSystem.B.dylib (...)

Under half a megabyte, linking only the system C library. Hey's runtime, the standard library parts you use and the hey_web modules are all inside it. The SQLite library isn't linked in: the app loads it at run time from the path in HEY_SQLITE3_LIBRARY.

Run it from the app folder (it reads config/hey_web.json and db/ from there), on any port you like:

Point a client at it:

$ curl -si http://localhost:3001/health

{"ok":true}
$ curl -s http://localhost:3001/cards

10. Going fast: the two transport lanes

Same routes, same handlers, same request values. Only the part that moves bytes between sockets and your handler changes.

Default: Web.serve Works today

What HeyWeb.serve(app) calls. A thread per open connection. Fastest when you have a modest number of connections that are actually sending requests: API servers behind a load balancer with a small pool, internal services, benchmarks.

Opt-in: HeyWebPoller Works today

One readiness loop (also called an event loop): a single thread asks the OS "which of these thousands of sockets have data?" (kqueue on macOS, epoll on Linux), then serves just those, in a batch. Choose it when you hold many connections that are mostly idle: browsers, mobile clients, long-lived API clients.

The trade, as measured on a Mac. With a few dozen busy connections the default lane does more requests per second, because it spreads over several cores and one loop uses one. With thousands of connections the two are close in throughput, but the default lane reaches its connection limit (section 1) and starts answering 503 while holding a thread per connection; one poller loop refuses nothing and stays at one thread and a few megabytes. The like-for-like web numbers are in Performance.

How to turn the poller lane on

Three steps. hey_web already depends on hey_poller, so hey package ensure installed it. Then: (1) import pkg:hey_web@0.3.9/poller, (2) call HeyWebPoller.serve_application(app) instead of HeyWeb.serve(app), (3) build the one native library your OS needs, once.

server_poller.hey: the only change is the import and the last line

import 'stdlib:Cli'
import 'pkg:hey_web@0.3.9/main'
import 'pkg:hey_web@0.3.9/config'
import 'pkg:hey_web@0.3.9/server'
import 'pkg:hey_web@0.3.9/poller'
import 'config/routes.hey'
import 'app/models/card_store.hey'

program
  let ready = CardStore.setup()
  let config = HeyWebServer.options(Cli.args(), HeyWebConfig.load_or_default('config/hey_web.json'))
  let app = HeyWeb.application('cards', Routes.all(), {...config, workers: 1})
  says 'cards on the readiness lane (one kqueue/epoll loop)'
  let served = HeyWebPoller.serve_application(app)
end
$ HEY_ROOT=$TOOLCHAIN .hey/packages/hey_poller/0.2.3/bin/build-native --project .
native_target=...
native_library=...
poller_backend=...
$ hey build server_poller.hey -o build/cards-poller
built .../build/cards-poller
$ curl -s localhost:3000/health
{"ok":true}
  • Run the poller binary from the project root so it finds the kqueue or epoll library, or set HEY_KQUEUE_LIBRARY (macOS) / HEY_EPOLL_LIBRARY (Linux) to the library's path.
  • workers here means number of loops. They share the port with SO_REUSEPORT (a socket option that lets several listeners bind one port); Linux spreads connections across them, macOS doesn't, so use one loop on a Mac.
  • Handlers run on the loop's thread. A slow query or an outbound HTTP call stalls every connection on that loop. Keep handlers quick and push slow work into Jobs.
  • Not supported on this lane: chunked request bodies (answered 411) and request heads over 64 KiB (431). Bodies over max_body_bytes get 413.
  • On Linux you can ask for io_uring (Linux's newer interface that queues I/O requests in memory shared with the kernel) instead of epoll with HEY_POLLER_BACKEND=io_uring; if the kernel or Docker's default security profile blocks it, it falls back to epoll and says why on stderr.
