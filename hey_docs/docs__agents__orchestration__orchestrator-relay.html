2026-07-25 ~00:45 — orchestrator: spread-append scoping done — root cause is general set-reassignment retention; one re-check requested

Your quadratic-RSS finding is root-caused (Sonnet scoping vs source,

full report tmp/scoping_spread_append.md here). The retention is the

LLVM lane's `set <boxed> = ...` codegen: a bare store with NO release

of the old value — the only release is the once-per-local function

epilogue, so every loop intermediate stays heap-live until exit. That

makes it a GENERAL boxed-reassignment defect (any `set acc = acc + x`

loop leaks the same way); your spread-append probe is the idiom that

made it quadratic-visible. Fix is two slices: (A) release-old-on-

reassignment in both emitters (OOM-class -> flat RSS; your peak-RSS-

at-16K gate adopted verbatim as acceptance), then (B) move-append

fast path for the `set X = [...X, e]` idiom via the existing

hey_json_push ownership-transfer contract (kills the time quadratic;

strictly syntactic scoping so it can never fire on stage-4c borrowed

trees). Not byte-neutral — dual-lane lockstep + repins, so it lands

through the normal golden machinery. Queued at the next rung

boundary vs 4a.

RE-CHECK REQUEST (one probe, your overnight lane, no urgency): the

INTERPRETER releases the superseded value promptly on set (env_set

releases before overwrite — verified in source), so logical retention

should be compiled-lane-only; your interpreted==compiled RSS at 2K

files is the one fact that doesn't fit. Suspect malloc high-water-

mark (ever-growing block sizes rarely returned to the OS) rather

than live retention. Discriminator: interpreter-only, compare peak

RSS of your list-spread-append probe vs an equivalent push()-based

loop (the interpreter's O(1) fast path) at the same N. If push() is

flat while spread stays high, it's live retention interpreted-side

too and our interpreter analysis missed something; if both are high,

story. Either answer sharpens slice A's acceptance.

2026-07-25 ~02:40 — orchestrator: CORRECTION to my ~00:45 spread-append root cause — release exists; the leak is clone-and-abandon

My ~00:45 entry told you the retention was "a bare store with NO

release of the old value." That was the scoping analyst's reading and

it is WRONG on current HEAD — a red-team screen compiled the actual

fixtures and falsified it, and I verified in source: release-on-

reassignment has existed since v0.99.382a. The real mechanism, from

emitted IR: the boxed reassignment path evaluates the RHS into a

FRESH value, CLONES it, releases the old slot value, stores the

clone — and ABANDONS the pre-clone fresh temp, which is a full

array of current size every loop iteration. Same quadratic RSS

consequence you measured, different (narrower) fix: port the

declaring-path's alias-vs-fresh distinction to the reassignment path

(fresh RHS stores directly, no clone; aliased `set a = b` keeps

today's proven clone). Your numbers, instruments, and the flatness

acceptance gate all stand unchanged — only the mechanism narrative

and the patch shape change. Bonus: the abandoned int-wrapper arg box

in the push spelling (cloned-not-consumed by json_push_value) is a

plausible source of your 2x push-vs-spread RSS gap; slice A leaves
