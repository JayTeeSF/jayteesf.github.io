One Worker Was Never One Core

A report reached us that our web server had collapsed — from 130,000 requests per second on a single core down to under 30,000. It was alarming, it was specific, and it was wrong. Nothing regressed. The number had always been measured on four cores, and comparing it against a per-core figure invented a fourfold collapse out of arithmetic. Two real defects were standing behind the fake one.

TL;DR

  • There is no regression, and no one should go looking for one. Our headline figure was measured with one worker configured, and one worker occupies 4.21 cores. Per core, the server has been steady at ~30,000 requests per second across five releases and two operating systems. The “drop to under 30,000” was that same steady number, correctly measured, compared against a four-core one.
  • The real defect is CPU cost per request: Hey spends 32.68 µs (microseconds) of processor time per request against Go's 7.65 µs — 4.3x. Hey needs roughly four cores to serve what Go serves on one.
  • The second real defect: the worker setting does nothing. Turning it from 1 to 8 moves processor usage from 4.21 to 4.24 cores on one operating system, and not at all on the other. It is not a parallelism knob today; it is decoration.
  • Disclosed weakness: one platform is five times worse and we cannot yet say why. The same build takes 4.2 cores on macOS and 0.79 on Linux. Every mechanism we would blame — the socket option that spreads incoming connections, the per-connection threads — is present and demonstrably working on both. Unexplained, and ours to fix.
  • Reproduce it in one line: while your benchmark runs, read the CPU seconds your server process has actually consumed and divide by the wall time. If that number is not printed beside your requests-per-second, your throughput figure has no denominator.

The number that started it

Somebody remembered 130,000 requests per second on one core. Today the same server measured a little under 30,000 per core. That is a 4.3x collapse, and it deserved the alarm it got.

Both numbers were correct. They were measuring different things. The original was recorded with the worker setting at 1 — and we had all read “one worker” as “one core.” It is not. A single worker spawns a thread per connection, and under load that one worker was occupying 4.21 cores. Dividing its throughput by the cores it actually used gives 31,437 per core. Our Linux measurement, taken independently on entirely different hardware, gives 27,491 to 30,257 per core.

Those agree. Two machines, two operating systems, two people who had not compared notes, and five releases spanning several weeks: the server has been serving about 30,000 requests per second per core the whole time. Nothing fell. The collapse was the distance between a four-core number and a one-core number, and we had put an equals sign between them.

Per core

Throughput divided by the processor cores the server actually consumed — not by the cores the machine has, and not by the workers you configured. It is the only throughput unit that survives being moved to another machine, which is exactly why two boxes could confirm each other here.

What was actually broken

Losing a fake regression is a good day only if it hands you a real one. It handed us two.

The first is cost. Serving one request costs Hey 32.68 µs of processor time. It costs Go 7.65. That 4.3x is the whole story of the per-core gap, and it is not mysterious: a separate profile of a tight numeric loop, taken the same day, found that about three quarters of all processor cycles went to copying values, adjusting reference counts, and calling the memory allocator — while arithmetic, the thing the program was ostensibly doing, accounted for four per cent. A web request that allocates and copies its way through a handler pays the same tax. Same root cause, two very different-looking workloads.

The second is that the worker setting is inert. Turn it from 1 to 8 and processor usage goes from 4.21 to 4.24 cores. On Linux it does not move at all. Go, measured on the same machines in the same sessions, climbs from 0.84 cores to 3.96. That is what a knob that works looks like, and it is what ours does not do.

The part we cannot explain

The same build takes 4.2 cores on macOS and 0.79 on Linux. We went looking for the obvious culprit and did not find it. The socket option that lets several listeners share a port and lets the kernel spread connections between them is present — and with four workers configured, the server really does open four separate queues. Threads really are created as load arrives: eight concurrent connections produced eleven threads, sixty-four produced sixty-seven. Every structure we would point at is there and working.

So sixty-seven threads exist, are handed work, and then wait. Whatever they are waiting on binds on one operating system and not the other, and it sits somewhere after the connection has been accepted. That is a much smaller place to look than “the server is slow,” and it is where we are looking.

A note on the tool we could not use

The profiler that cracked the cost problem in ten minutes is useless for this one. Sampling profilers record what is running, and a thread waiting on a lock is not running — it consumes nothing and casts no shadow in the profile. Sixty-seven idle threads look exactly like sixty-seven threads that do not exist. Blocking needs a different instrument entirely: one that reads what each thread is parked on rather than what it is doing.

What to take from this

If you publish a throughput number, publish its denominator in the same breath. Ours said “one worker,” every reader including its authors heard “one core,” and the gap between those two readings was large enough to manufacture a crisis and send several people hunting a regression that had never happened. The fix costs one line in the harness: read the server's own consumed processor time, divide by wall time, print it next to the requests per second. A throughput figure without it is a numerator looking for a story.

The second lesson is cheaper to state and harder to practise. Every finding in this piece that survived was checked against a reference running on the same machine at the same moment — which is also how an earlier version of this very measurement was caught producing four confident, entirely fictitious numbers. The reference costs a few minutes. Publishing the fiction costs considerably more.
