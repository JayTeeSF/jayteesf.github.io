RESEARCH COMMISSION — what is actually IRREDUCIBLE in Hey?

**Commissioned by:** the maintainer, 2026-07-29

**Orchestrated by:** the `bench` seat, with a worker team

**Deliverable:** markdown research in `docs/research/` → an article by

bench's writing team → **the maintainer evaluates and identifies

opportunities from the article.** Decision deferred until he reads it.

**No implementation is authorised by this commission.**

---

THE MAINTAINER'S ASK

> "our language is VERY simple: it has functions, actors,

> json-compliant objects, strings, numbers, conditionals, and loops.

> I'm not sure what else is fundamental to the language other than

> maybe the 'jobs' abstraction, but even that ?could? (theoretically)

> be written using some syntactic-sugar over our actor / function

> syntax.

>

> Ask 'bench' to setup workers to review the core concepts (primitives,

> etc) in our language and see how simple we are ...or can become. I'd

> like to have the essence simple (and completely lowered into LLVM)

> such that the language is fast and stable because there's not a lot

> of oddities."

**His claimed core, verbatim:** functions · actors · JSON-compliant

objects · strings · numbers · conditionals · loops. Plus, provisionally,

**Jobs** — which he suspects is already sugar over actors and functions.

**AMENDED by him minutes later:** *"I forgot to say, 'Booleans' (and I

don't recall if we have Bytes too)."*

paths does arithmetic have, and do the two emitters agree on promotion

and truncation at every one?** That is a higher-risk area than its

one-word summary suggests.

**ALSO NOTED:** `[true,false].to_json` works **with no import**, on an

array. Under rule 30 that is a default dot-method and should not exist.

Evidence that the ten-name shadow list is not the whole exemption

surface — **enumerate the real one.**

PRECEDENT — WE HAVE DELETED A CORE STRUCTURE BEFORE, RECENTLY

`byte_buffer` was **REMOVED by maintainer ruling 2026-07-27**: *"the

accidental mutable structure is gone."* This census is not

hypothetical — there is a live, recent precedent for removing something

from the core on his ruling, and it held. **Read that commit and its

fallout; it is the closest thing we have to a dry run of whatever this

census recommends.**

---

WHY THIS MATTERS MORE THAN IT LOOKS — the argument from our own ledger

**Simplicity here is not aesthetic. It is the mechanism that kills

two-lane divergence.**

We run two emitters: the native `runtime/heyc.c` island and the

shipping HeyLlvm mirror (`stdlib/HeyLlvm.hey`). **Every construct with

its own lowering path is a place those two can disagree** — and this

week's defect ledger is almost entirely made of exactly that:

defectthe divergence
467aa bool stored as the **text** `"true"` in one lane
470a`get` and `put` dispatching by **different rules for ten versions**
470athe mirror **refused** shape C while native accepted it — caught only by the corpus survey
open`has`/`has?` still carrying the same type-guessing disease

**Every one lived in a construct that had more than one lowering.**

Fewer primitives is fewer places a wrong answer can hide — **and a

shorter mirror to finish before native-C can be deleted (R3, R7.3).**

This commission therefore feeds the retirement ladder directly, not

just the language design.

---

THE DELIVERABLE — an inventory, with every construct classified

Enumerate **every** construct in the language. Not a sample: a census.

(Same discipline as the stdlib name census and S3's seven-route

enumeration — enumerate the family, do not sample it.) For each:

classmeaning
**IRREDUCIBLE**must exist as a primitive; nothing else can express it without losing semantics **or** performance
**SUGAR TODAY**already lowers to something simpler — **prove it with the IR/MIR, not by assertion**
**SUGAR POSSIBLE**could be lowered away; state what it would cost
**ODDITY**exists for no defensible reason; a deletion candidate

**And for each, the divergence-risk metric:** *does this construct have

its own lowering path in BOTH emitters?* That count — constructs ×

independent lowering paths — is the surface where two-lane divergence

can hide, and it is the number this whole commission is really about.

**Report it as a single figure at the top of the research.**

Constructs known to exist — a starting list, NOT a complete one

`program`/`end`, `fn`, `let`, `set`, `return`, `says`, `warn`,

conditionals, loops, arrays, objects, strings, numbers (**integer vs

float?**), **booleans**, **nil**, **Bytes**, ranges, `import` (and the proposed `expose`), modules, actors,

mailboxes, Jobs, `get`/`put`/`has`/`has?`, indexed access `a[i]`,

dot access `o.k`, the `?` predicate suffix, `to_json`/`to_s`

conversions, and whatever else the census turns up. **Finding

constructs not on this list is a deliverable.**

Specific candidates worth naming

  • **Jobs over actors** — the maintainer's own hypothesis. Test it.
  • **`says` and `warn` as STATEMENTS rather than functions.** Why are

they syntax? A function needs no special lowering. If there is a

reason, it should be written down; if there is not, they are sugar.

  • **The `?` predicate suffix** — naming convention, or something the

compiler knows about?

  • **`#<stop>`** — an internal sentinel that reaches user data (todo

item 9). What *is* it, and is it a primitive nobody documented?

  • **Dot access** — after rule 30, is it one lowering or several?

---

THE TWO TRAPS — the report is not honest without these

**1. COMPLEXITY RELOCATED IS NOT COMPLEXITY REMOVED.** The classic

failure of a small-core language is pushing complexity into the stdlib

or into the user's code and calling the language simple. **For every

proposed reduction, state where the complexity goes.** If removing a

primitive makes user code worse, that is a cost, and it may exceed the

benefit.

**2. SUGAR CAN BE SLOWER, AND WE HAVE MEASURED THIS.** The maintainer

wants the essence "completely lowered into LLVM... fast and stable."

But a naive lowering through more layers can lose real speed —

**we measured actors-as-mutable-cells at 2,600× slower than a plain

array write.** So if Jobs became sugar over actors, and actors carry

that cost, the reduction would be a performance disaster.

**EVERY PROPOSED REDUCTION MUST BE MEASURED, NOT ASSUMED.** A

reduction that costs speed is a finding, not a recommendation.

---

RULES

1. **Read the source, do not guess.** Claims about what lowers to what

must cite `heyc ir` / `heyc symbols` / MIR output or the emitter

line. **A claim from memory or from docs is not evidence** — the

docs may describe an intent the code does not implement (we found

`Web.log_requests` declared and wired to nothing).

2. **Check BOTH emitters for every construct.** A construct handled in

`heyc.c` but not in `HeyLlvm.hey` (or vice versa) is a finding in

its own right, independent of the simplicity question.

3. Capture stderr to a log on every command (rule 24).

4. Markdown in `docs/research/`, one file per theme.

5. **Recommendation required, dissent recorded.** Do not synthesise a

consensus.

6. **No implementation.** Inventory, evidence, and opportunities only.

---

HOW THIS BACKS RULE 30

The maintainer's point, and the reason this commission exists: **if the

essence is that small, everything else is sugar by definition.** Rule 30

then stops being a policy about collisions and becomes a *consequence*

of what the language is — sugar is opt-in because sugar is not the

language, and a dot-method shadowing a user's data is sugar overruling

substance.

**The census either supports that or it does not.** If it turns out we

have thirty irreducible primitives rather than seven, say so — that is

a more important finding than a tidy confirmation, and rule 30's

justification would need to fall back to the collision argument.
