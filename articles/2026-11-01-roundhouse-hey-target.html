Rails Apps as Fast Hey Binaries

You have a Rails app. It works, and you like writing it. Now you want it to serve ten times the traffic on the same box, and to deploy it as one file. This page describes how roundhouse --target hey would get you there, and what happens to your models, controllers, views and channels on the way.

After reading this you can

  • picture the two commands you'd run, and the files you'd get back;
  • point at any part of your app and say what it becomes in Hey;
  • predict which parts of your app the first version will refuse;
  • name the pieces Hey is adding to its own standard library for this;
  • weigh in on the open decisions.

Short version

  • Two commands: roundhouse --target hey -o out/hey ./my_rails_app writes a Hey project; hey build turns it into a native binary.
  • One binary per platform: for your own machine first; --target linux-arm64 and friends once Hey's cross-compiler lands (release v608).
  • What's new: one more output language for Sam Ruby's roundhouse, modelled on its Elixir target, plus a small hand-written Hey runtime for HTTP, SQLite, Action Cable, sessions and CSRF.
  • Speed target: at least 10x stock Rails on roundhouse's blog benchmark in version 1. That's a goal; nothing has been built or measured.
  • Cost: about 16–28 engineer-weeks to the blog app, about 25–46 to Campfire, plus 4–9 in Hey (all estimates).

This page expands the "Got a Rails app?" section of Fast Ruby Binaries for Any Platform. That page is the road for plain Ruby. This one is the shorter road for Rails.

What you'll type

$ roundhouse --target hey -o out/hey ./my_rails_app
$ cd out/hey
$ hey build                          # ./my_rails_app, for this machine
$ ./my_rails_app                     # opens the DB, applies the schema, serves

$ hey build --target linux-x64       # after Hey v608
$ scp my_rails_app server:           # one file to deploy

Your Rails app stays the source. You keep writing Ruby and running Rails in development. The Hey project is build output, like public/assets: regenerate it, don't edit it.

The pipeline

  • roundhouse does the hard part already. Rails' metaprogramming (has_many, before_action, ERB) is worked out at build time into plain classes and functions.
  • Even the framework is translated. roundhouse carries a Ruby version of the Rails pieces it needs (about 43,000 lines) and pushes it through the same emitter as your app. Its docs put it simply: "If your emitter can transpile runtime/ruby/, it can transpile a real Rails app."
  • Every generated file says so on line 1: # Code generated by roundhouse-hey ... DO NOT EDIT.

Why copy the Elixir target?

Rails code changes objects all the time: @article.title = ..., buf << html. Hey values don't change. So who fixes that?

roundhouse already does, for Elixir, which has the same rule. Its "functionalize" passes rewrite "change this object" into "return the changed object and rebind the name". Elixir passes roundhouse's blog check that way with no mutable box at all.

The Hey target reuses those passes. Hey rebinds a name in place when nothing else holds the old value, so the rewrite stays cheap.

Your model and controller, and what they become

You write (app/models/article.rb)

class Article < ApplicationRecord
  has_many :comments
  validates :title, presence: true
end

roundhouse writes (sketch)

# Code generated by roundhouse-hey 0.1.0 from
# app/models/article.rb. DO NOT EDIT. sha256:...
module Article
  fn new(attrs)
    return {cls: 'Article', id: nil,
            title: attrs['title'], errors: []}
  end

  fn validate(article)
    if blank?(article.title)
      return {...article, errors: ["Title can't be blank"]}
    end
    return {...article, errors: []}
  end

  # save hands back the record and whether it saved
  fn save(article)
    let checked = validate(article)
    if checked.errors.size() > 0
      return {record: checked, ok: false}
    end
    let id = Db.insert('articles', checked)
    return {record: {...checked, id: id}, ok: true}
  end
end

You write (app/controllers/articles_controller.rb)

class ArticlesController < ApplicationController
  def show
    @article = Article.find(params[:id])
  end

  def create
    @article = Article.new(article_params)
    if @article.save
      redirect_to @article, notice: "Created."
    else
      render :new, status: :unprocessable_entity
    end
  end
end

roundhouse writes (sketch)

module ArticlesController
  fn show(req)
    let article = Article.find(req.params['id'])
    if article == nil
      return Response.not_found()        # was RecordNotFound
    end
    return Response.html(200, ArticlesShow.render(article))
  end

  fn create(req)
    let saved = Article.save(Article.new(article_params(req)))
    if saved.ok
      return Response.redirect(article_path(saved.record),
                               {notice: 'Created.'})
    end
    return Response.html(422,                # :unprocessable_entity
                         ArticlesNew.render(saved.record))
  end
end
  • An object is a record. {cls: 'Article', id: ..., title: ...}, and its methods are functions that take it first. Generated code can still write article.save().
  • @article = ... is a local. The action returns a response value; the dispatcher sends it.
  • Symbols are strings. Hey has no symbols. :unprocessable_entity becomes 422 when the code is written.
  • Your relations are already SQL. roundhouse folds where(...).order(...) into a query at build time.
  • No type annotations. Generated Hey is untyped, like generated Elixir. Hey infers the rest.

The Hey above is a sketch of the design, not emitter output. Names such as Response and Db stand in for the runtime's real ones.

Follow one request

Views

Each template and partial becomes one Hey function that takes its data and returns a String. The ERB is built as a list of parts and joined once at the end. HTML escaping lives in the runtime, as in Rails.

Action Cable: one actor per connection

Hey runs long-lived work as actors: small workers that share nothing and talk by messages. That's a close fit for WebSockets. Elixir's target does the same with processes.

The protocol is Action Cable's own (actioncable-v1-json: welcome, ping, subscribe, confirm, message), so your existing JavaScript and Turbo Streams keep working.

Will my app compile?

Works

Whatever roundhouse already handles

Models, associations, validations, controllers, before_action, params, flash, cookies, CSRF, routes, ERB, jobs, Action Cable, Turbo Streams.

Works

The two common rescues

RecordNotFound becomes find returning nil and a 404. RecordInvalid becomes "not saved" and a 422. Go's target draws the same line.

Refused, with a message

Any other rescue

Generated code never catches. Other rescues are an "Unsupported" diagnostic in version 1. roundhouse check tells you where.

Later

Image variants and web push

Deferred, as in roundhouse's earliest Spinel lane for Campfire: the push job fails and logs.

What Hey adds, for everyone

Writing this spec turned up five gaps in Hey. Hey needs them anyway, roundhouse or not, so each is now a task on Hey's own list. Every Hey program gets them, not only translated Rails apps.

Hey task

HTTP upgrade and WebSocket

A handler can accept Upgrade: websocket and own the raw connection; a WebSocket module with framing, ping/pong and close codes; one connection per actor. About 1–2 weeks for the takeover (estimate).

Hey task

SHA-1, HMAC and bcrypt

Added to the existing Crypto module, not a new one. SHA-1 for the WebSocket handshake, HMAC for signed cookies, bcrypt for has_secure_password. About 1.5–2.5 weeks (estimate).

Hey task

Static linking of native libraries

A package's C library (SQLite, say) is built once per target at Hey's release time and linked into your binary. No .so to install on the server. About 2–4 weeks (estimate).

Hey task

SQLite through hey_sqlite3

The spec planned a new SQLite package. One already exists, hey_sqlite3, so the task is to fill its gaps (prepared statements, transactions, typed rows, migrations, an actor for concurrency) instead.

Hey task

A date and time facade

Calendar dates, ISO 8601 and strftime-style formatting, time zones and month arithmetic, as a thin layer over the existing Time and Duration modules. About 1–2 weeks (estimate).

The same pieces serve the plain-Ruby road too. So does stdlib:Cell (3–5 weeks, estimate), which both roads share.

What about shared mutable state?

  1. Values first. Request-scoped models, controllers and view buffers are plain records.
  2. Across requests, state lives in an actor: connection registries, subscriptions, rate limits, caches.
  3. A Cell only as a last resort, for an object shared and changed within one request that the rewrite can't thread, such as both ends of an association cache. CI counts them. The target for the blog is zero.

Deploying it

  • Before Hey v608: you build on the machine you deploy to.
  • After v608: hey build --target <os-arch> from your laptop.
  • Version 1 loads the system's SQLite at run time. macOS ships it; on Linux it's a package you install, and the generated README says so.
  • With static linking (the Hey task above), SQLite is inside the binary. One file, nothing to install. Static Linux builds follow.
  • TLS stays out of the app: a proxy such as Thruster terminates it, as in roundhouse's benchmarks.

Open decisions

Recommended: yes

Quiet the Cell warning in generated files

Hey warns on every Cell to teach hand-written code. Generated files carry a hash-checked marker, so the warning can stay off there, as it already does for the plain-Ruby tool.

Recommended: refuse in v1

Other rescues

Same boundary as the Go target. Revisit app by app from roundhouse check.

Recommended: load at run time in v1

SQLite: now, or wait for static linking?

Ship with the system SQLite first; the single-file binary comes in v2.

Recommended: separate packages

Where the runtime pieces live

SQLite, WebSocket and cookies as Hey packages that both roads use, published with Hey.

Recommended: after A2

Upstream

Work in a fork, then offer the target to roundhouse as a pull request once Hey is public, arriving with a green compare lane.

Recommended: Lobsters, then Campfire

Which app after the blog

The order roundhouse itself proved.

What lands in the fork, and how big the diff is

New code goes in its own files: src/emit/hey.rs and src/emit/hey/ (entry, expressions, modules, package, schema SQL, tests, paths, mirroring Elixir's 5,687 lines), runtime/hey/, a test file and a CI lane. Shared files get one-line touches: a Hey build target, a module line, and the target-name lists, about 25 of them. Rebasing onto upstream is estimated at half a day to a day a week. roundhouse is MIT or Apache-2.0; the fork uses it under MIT and keeps both license files.

What the hand-written runtime has to cover

Only the "target primitives": the database and HTTP. Hey already has a web server with middleware (stdlib:Web), HTTP parsing (stdlib:Http), sockets (stdlib:Net), JSON, Jobs, static files, AES-GCM, PBKDF2 and random bytes. The new Hey-side code is cookie parsing and flash, the CSRF token, WebSocket framing and the Action Cable protocol, each about half a week to two weeks (estimates). One thing to verify first: that a failing handler answers 500 and leaves the server running.
