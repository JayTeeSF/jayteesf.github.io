R6 design brief — ORC JIT for the persistent REPL session (R6.1–R6.4)

Research agent, 2026-07-26. Evidence class tags: [DOCS] official docs, [PAPER],

[BLOG], [FOLKLORE] community/unverified, **[MEASURED]** run on this machine

(macOS arm64, Apple M-series, Darwin 25.5.0, Homebrew LLVM 22.1.8, worktree

`~/dev/claude_01` @ claude_01 branch). Probe source:

`docs/agents/orchestration/research_r6_lljit_probe.c (committed beside this brief)`

(compiled and run twice; C11, `llvm-c` headers only, no C++).

0. Corrections to the task framing (load-bearing)

1. **The current session does NOT dlopen shared objects.** The `dlopen/dlsym`

in `runtime/hey_runtime.c:1684-1712` is the *native-extension* loader, not

the REPL. The actual session (`tools/hey_repl_session.hey`, driven by

`bin/hey-repl-session`) replays all committed source into one candidate

program, runs full `heyc build`, and executes the resulting binary as a

fresh process each turn; state is a JSON source ledger

(`session_state_path`, merged only after a successful compile+run).

`docs/humans/27-llvm-first-toolchain-and-repl.md` §7.3's

"temporary dylib → dlopen" stage was planned but has not been built. R6.1

can therefore **skip the dlopen rung entirely** and go straight from

"build+spawn per turn" to LLJIT — the transactional/replay semantics carry

over unchanged.

2. **The <100 ms budget is frontend-dominated, not JIT-dominated.**

[MEASURED] warm `./bin/heyc build` of a 3-line program: 191 ms wall

(`--emit-ll` alone: 50 ms → clang link+codesign ≈ 140 ms). The JIT replaces

only the link+spawn slice. Steady-state LLJIT cost for a fragment is

**~0.4 ms** (below), so post-R6.1 warm latency ≈ frontend + IR

parse/codegen ≈ 55–95 ms for small sessions — inside budget, but the

frontend share grows with session size under the replay model (see §d).

a. Recommended architecture and staged migration

**R6.1 — persistent JIT host, replay semantics unchanged (land first).**

New C11 binary `bin/hey-jit-session` (source e.g. `runtime/hey_jit_session.c`),

linked against the hey runtime objects **and** `libLLVM` (`-lLLVM

-Wl,-rpath,$(llvm-config --libdir)` — only this tool links libLLVM; product

binaries are untouched). Loop: read one `.ll` path (or bytes) per turn on

stdin; parse textual IR (`LLVMParseIRInContext`); create a **fresh JITDylib

per generation** (`gen_N`); attach a

`LLVMOrcCreateDynamicLibrarySearchGeneratorForProcess` so the module's ~571

`declare`d `hey_*` runtime symbols resolve against the host process; add the

module;

> **AMENDED 2026-07-28 (linux seat) — THIS MECHANISM WAS NEVER EXECUTED, AND

> ON ELF IT FAILS.** `research_r6_lljit_probe.c` attaches the process

> generator (:66-70) and then never resolves a host-executable symbol: its

> `hey_fib` is DEFINED in jitted IR (:75), so every resolution it demonstrates

> is JIT-to-JIT (:98-99, :140). The generator is attached and unexercised, on

> both platforms.

> **[MEASURED, Linux/Arch/LLVM 22.1.8, and on Darwin by the bench seat]** the

> resolution path is `dlsym` end to end (`Orc.h:1010-1029` -> `ExecutionUtils.h:310`

> -> `DynamicLibrary.inc:24-44`), so it reads `.dynsym` and never the

> executable's `.symtab`. On ELF a host symbol is therefore INVISIBLE unless

> the host is linked `-rdynamic`/`--export-dynamic`; on Mach-O it is exported

> by default. Verified both directions: adding the flag on ELF makes it

> resolve, and removing visibility on Mach-O

> (`-Wl,-unexported_symbol,_sym`) reproduces the exact ELF error string.

> only in which direction the default points.**

> Probes: `research_r6_lljit_hostsym_probe.c` (the cell this file's original

> probe omits, two link lanes) and `research_r6_lljit_rdynamic_control.c`

> (LLVM-free, three lanes, rules out the toolchain exporting by default).

> already installs an EPC generator over the same `dlsym`, so DELETING the

exit-status/stdout-delimiters; the Hey-side session tool keeps owning the JSON

state ledger and the commit/rollback decision.

  • Fresh-JITDylib-per-generation is required anyway because every candidate

module defines `@main` ([MEASURED] `frag.ll` line 584); it also sidesteps

cross-turn duplicate-symbol errors under replay, and gives a free

`ResourceTracker`-style discard path for failed turns (never commit the

dylib).

  • `tools/hey_repl_session.hey` changes from

`heyc build && ./candidate` to `heyc build --emit-ll && send-to-host`

(the `--emit-ll` mode already exists, [MEASURED]).

  • **Flag/fallback:** gate behind `HEY_REPL_JIT=1` (env) or

`--jit` on `bin/hey-repl-session`; the fallback is the existing

build+spawn lane, which stays the default until the latency gate

(`tools/benchmark_llvm_fragment.hey` lineage, budget dropped 500→100 ms)

and the parity battery pass on both macOS and Linux. Fallback also fires at

runtime if the host binary is missing or libLLVM can't load.

  • **Top technical risk (not the JIT):** today every turn is a *fresh

process*; under the JIT host, generation N's `main` runs in the same

process as N−1's, so `hey_runtime_init()` is re-entered every turn

([MEASURED] `frag.ll:12`), and actor/worker/atexit/journal state persists

across turns. The runtime must tolerate repeated program-entry, or the

emitter must give fragments an init-once entry. Probe this before

committing to the design (§g, P1).

**R6.2 — Eval onto the session path.** `Eval.expression` already routes

through `heyc build` (todo item 4, spec 1121). `Eval.callable` /

`Eval.into_session` become: compile fragment → add module to the *caller's*

session JITDylib chain → return the looked-up entry as a callable value via

the doc-27 §7.2 narrow ABI (`hey_repl_define_function` /

`hey_repl_find_function`). This is exactly clang-repl's PTU model (§d) and is

the piece that finally deletes the C evaluator's last consumer.

**R6.3 —** shell/raw-mode/history move into the Hey-side tool (no JIT

content; unchanged from ladder text). **R6.4 —** delete `runtime/hey_repl.c`

(5,721 lines [MEASURED]), drop the `#include` in heyc.c.

**Not recommended:** (i) building the doc-27 §7.3 dylib+dlopen intermediate —

it duplicates R6.1's host-integration work for zero semantic gain and adds

140 ms of clang link per turn; (ii) C++ ORC wrappers — the C API suffices

(§b) and the codebase rule is C11.

b. C-API feasibility verdict: **YES on LLVM 22, verified locally**

The entire R6.1 surface was exercised from pure C11 against Homebrew LLVM

22.1.8 [MEASURED, probe ran clean twice]:

LLJIT creation (`LLVMOrcCreateLLJIT`), textual-IR ingestion

(`LLVMParseIRInContext` + `LLVMOrcCreateNewThreadSafeContextFromLLVMContext`),

module add (`LLVMOrcLLJITAddLLVMIRModule[WithRT]`), process-symbol resolution

(`LLVMOrcCreateDynamicLibrarySearchGeneratorForProcess`), lookup+call,

resolved correctly.

Conclusions: (1) IR parse is **not** material (<10 ms) — emitting bitcode

instead of .ll buys nothing at these sizes; keep the textual-IR contract from

`stdlib/HeyLlvm.hey`. (2) JIT codegen at -O0 is 1–45 ms depending on how much

*code* (not declares) is in the module — which is why per-turn cost under

whole-candidate replay grows with session size, and why R6.1's success metric

must be measured on a *loaded* session (e.g. 50 committed functions), not an

empty one. (3) Object caching: ORC's C++ `ObjectCache` isn't reachable from

C, but the equivalent is: capture objects via

`LLVMOrcObjectTransformLayerSetTransform`+`LLVMOrcCreateDumpObjects`, key by

IR hash, and on hit skip parse+codegen with `LLVMOrcLLJITAddObjectFile` —

this is what a cross-session warm-start cache would look like. Defer it: at

0.4 ms/fragment it is not needed for the 100 ms gate; the existing

`HEY_RUN_CACHE_DIR` compiler-side caches matter more.

d. Redefinition / session design

Prior art: clang-repl models the session as a sequence of **partial

translation units**, each lowered to its own module and tracked so it can be

unloaded ("code undo") — redefinition = new PTU whose symbols shadow, undo =

ResourceTracker removal ([DOCS]

ClangRepl docs, [DOCS]

D104918, [BLOG]

compiler-research GSoC22,

DOCS] [2022 LLVM lightning talk PDF).

For Hey, R6.1 needs **none of that machinery** because the replay model

recompiles every committed definition into each generation's module; a

JITDylib-per-generation gives correct shadowing for free (later `Eval`

lookups target the newest generation's dylib). The doc-27 §7.6 scheme

(`greet$generation_N` versioned machine symbols, stable semantic identity)

becomes necessary only at **R6.2**, when long-lived callables from earlier

generations coexist with redefinitions. Two rules to specify then:

1. New calls resolve through the session table

(`hey_repl_find_function`), never through raw JIT lookup — so

redefinition is a table write, not a symbol-resolution trick.

2. Old callables keep their old code (doc-27 already says this); therefore

**never** `ResourceTrackerRemove` a generation that a live callable value

references — removal invalidates the pointer (ORC does not track native

pointers you handed out; caveat verified in [DOCS] ORCv2 doc's silence

plus general ORC list discussion — treat as a hard rule). Garbage-collect

dylibs only when the session proves no callable survives (or never; a

REPL leaks tolerably).

e. Crash-isolation stance

  • The C API does **not** expose ORC's out-of-process execution (EPC /

`llvm-jitlink-executor`), which is how clang-repl got crash isolation in

GSoC 2024 ([BLOG]

llvm blog).

In-process LLJIT means a segfaulting fragment kills the JIT host — same

blast radius as every mainstream in-process REPL (python, irb, julia).

  • Hey has a structural advantage those REPLs lack: the **durable state is a

source ledger, not live heap**. Recommended stance: two processes.

`bin/hey-repl-session` (Hey-side shell, owns ledger + terminal) supervises

`bin/hey-jit-session` (C host). A crashed host is respawned and the

committed ledger replayed through it (~0.4 ms × N fragments + one frontend

pass); the user loses at most the uncommitted turn. This is strictly

better isolation than the status quo *for the shell* and equal for state.

  • Do not attempt fork-per-fragment (state divergence) or C++ EPC (violates

C11 rule). Revisit out-of-process only if the C API grows EPC bindings.

f. macOS arm64 JIT-permissions checklist

  • [MEASURED] The probe — an ad-hoc-signed, un-entitled binary — JIT'd and

ran code successfully on this exact machine, launched from the same

harness shell lineage where AMFI killed `heyc link-ll` outputs

(`docs/agents/in-progress.md:545`). JIT'd code is never a signed artifact

on disk, so the link-ll/AMFI failure class does not apply to R6.1's

*generated code*; it applies only to the `hey-jit-session` host binary

itself, which should be produced by the normal `heyc build`/Makefile+clang

pipeline (the lineage that "RUNS FINE every time" per the triage note).

  • libLLVM's JITLink handles `MAP_JIT` + `pthread_jit_write_protect_np` +

`sys_icache_invalidate` internally; no calls needed in our C code.

  • Checklist for the host binary:

1. Plain dev builds (ad-hoc signature, no hardened runtime): nothing to do

— [MEASURED] works.

2. If ever distributed with **hardened runtime** (notarization):

entitlement `com.apple.security.cs.allow-jit` (enables `MAP_JIT` and

the pthread JIT APIs) ([DOCS]

pthread_jit_write_protect_np man page;

BLOG] [outflank macOS JIT memory).

Do NOT reach for `allow-unsigned-executable-memory`.

3. Watch item: reported behavior drift of `allow-jit`/`mprotect` on

macOS 26 for sandboxed arm64 processes ([FOLKLORE]

Apple dev forums thread 821584) —

not relevant to an unsandboxed CLI, but pin a gate test.

4. `-Wl,-rpath` to the LLVM libdir, or the host dies at dyld time on

machines without Homebrew LLVM on the default path — this is the

fallback trigger (§a).

  • Linux: no JIT permission regime (no W^X mandate for plain processes,

no signature enforcement); expectation of "none expected" **confirmed**

for standard distros — only exotic setups (SELinux `execmem` denials,

PaX/grsecurity) interfere [FOLKLORE, low risk; covered by the Linux gate

battery]. JITLink ELF/aarch64+x86-64 are mature ([DOCS] ORCv2/JITLink docs).

**AMENDED 2026-07-28 (linux seat) — this paragraph was the whole Linux

treatment and it was [FOLKLORE]. Measured on Arch/x86-64/LLVM 22.1.8:**

  • **Host-symbol resolution FAILS without `-rdynamic`.** See the §a

amendment. This is the one that would have stopped R6.1 at integration.

  • **TLS is a real blocker and it is a C-API gap.** A jitted module reading

a host `_Thread_local` dies with

`Symbols not found: [ __emutls_v.<name> ]` — the JIT emits the

EMULATED-TLS ABI while the host, compiled AOT by the same clang, uses

NATIVE TLS (`readelf`: symbol type `TLS` in `.tbss`; no `__emutls_v` in

the host). It fails LOUDLY, not silently — but neither `-rdynamic` nor

the absolute-symbol table can repair it, because there is no

`__emutls_v` symbol in the host to point at.

**DESIGN CONSEQUENCE: never expose a `_Thread_local` to jitted IR.

Per-thread actor state must be reached through an ordinary host function.**

AOT runtime code is unaffected. Probe:

`research_r6_lljit_tls_probe.c`.

**O1 ANSWERED 2026-07-28 — and the answer WIDENS this finding rather than

narrowing it.** Two of the three candidate causes are eliminated by

measurement. Running the identical IR through `llc` from the SAME LLVM

22.1.8 install:

```

llc (default) -> hey_tls_slot@GOTTPOFF(%rip) + %fs: NATIVE (initial-exec)

llc -relocation-model=pic -> callq __tls_get_addr@PLT NATIVE (general-dynamic)

llc -emulated-tls -> __emutls_v.hey_tls_slot + __emutls_get_address

```

So **Arch's build does not default to emulated TLS** (the AOT compiler

from the same install emits native TLS), and **`Reloc::PIC_` does not

cause it either** (PIC yields `__tls_get_addr`, still native). Emulated

TLS requires the option to be set explicitly. By elimination the

remaining cause is **the JIT path itself enabling `EmulatedTLS`**, which

means this is a property of LLVM's ORC/LLJIT configuration and NOT of one

distro's packaging — so the design consequence above should be expected

on any platform using this JIT path, not just here.

NOTE for whoever reads the earlier relocation-wall research: with emutls

OFF, PIC would emit `R_X86_64_TLSGD`, which is the one TLS relocation

JITLink's ELF/x86-64 backend DOES implement — so the two accounts are

not in conflict; emutls simply pre-empts that path.

STILL SCOPED: one box, one LLVM build; the elimination above is measured

here and has not been repeated elsewhere.

**O2 ANSWERED 2026-07-28 — JIT-DEFINED TLS IS GENUINELY PER-THREAD.**

`research_r6_lljit_tls_threads_probe.c`: a jitted module defines its own

`thread_local`, four pthreads each write their id and read it back, and

the main thread's slot is checked afterwards.

```

control main-thread rw(99) = 99

per-thread readback: t0=0 t1=1 t2=2 t3=3

main slot after threads = 99 (undisturbed -> separate storage)

VERDICT: PER-THREAD STORAGE CORRECT

```

The dangerous outcome would have been silent sharing, so the probe asserts

VALUES ACROSS THREADS rather than merely that it runs. **So the TLS

constraint is narrower than first stated: a fragment MAY define and use its

own `thread_local` safely; what it may NOT do is reach a HOST

`_Thread_local` (the emulated-vs-native ABI mismatch above).** That keeps

per-fragment scratch state available to R6.1 and confines the design rule

to the host boundary.

  • **JITLink is NOT a portability delta.** `LLJIT.cpp` ~633-677

(`case Triple::x86_64: UseJITLink = !TT.isOSBinFormatCOFF()`) makes it the

x86-64 ELF default since LLVM 17 — the same `ObjectLinkingLayer` class

macOS arm64 uses. That path forces `CodeModel::Small` and `Reloc::PIC_`.

  • **EH-frame registration needs no C-API call.** `setUpGenericLLVMIRPlatform`

installs `EHFrameRegistrationPlugin` unconditionally on ELF (the

`UseEHFrames=false` branch is Darwin-only); Arch's libLLVM exports

`llvm_orc_{de,}registerEHFrameSectionAllocAction` bound to libgcc's

`__register_frame`. GAP: not verified by unwinding through a JITted frame.

  • **PACKAGING HAZARD: Arch has NO static libLLVM lane.**

`llvm-config --link-static --libs orcjit` **errors out** (`missing:

/usr/lib/libLLVMCore.a`). Any build rule inheriting a Homebrew static

assumption fails immediately. Symbols are versioned `@@LLVM_22.1` on a

rolling distro, so an LLVM 23 bump breaks a built JIT host **at startup**,

not softly — budget rebuild-on-bump. `-lLLVM-22` also pulls a transitive

libstdc++ dependency into a C11 binary.

  • **glibc >= 2.34: no JIT-relevant delta.** `--system-libs` is empty, so

there is no `-ldl`/`-lpthread` to get wrong; the `-rdynamic` requirement

is not version-sensitive. The `libpthread_nonshared.a` class that bit this

seat before is a static-linking artifact and cannot recur here.

g. Not established, and the local experiments that settle each

1. **P1 — runtime re-entry (the real R6.1 gate).** Unknown: does

`hey_runtime_init()` + a full program epilogue tolerate being run N times

in one process (actors, workers, journals, atexit, GC/refcount pools)?

Probe: `runtime/`-linked C program that `LLVMOrcLLJITAddLLVMIRModule`s two

different `heyc build --emit-ll` outputs into two JITDylibs and calls both

`main`s sequentially; assert clean output twice. Extend to an

actor-spawning fragment. (Half-day; reuse `lljit_probe.c` scaffolding.)

2. **P2 — loaded-session latency.** Unknown: warm turn time with a realistic

ledger (50 functions / ~200 KB candidate .ll). Probe: script that feeds 50

committed fragments through `hey-repl-session`, then times turn 51 with

`HEY_REPL_WARM_BUDGET_MS=100` in a JIT-lane variant of

`tools/benchmark_llvm_fragment.hey`. Decides whether R6.1 ships with

whole-candidate replay or needs per-fragment module emission earlier.

3. **P3 — frontend floor.** Unknown: how much of the 50 ms `--emit-ll` is

fixed startup vs per-line work (it bounds the best possible warm turn).

Probe: `--emit-ll` timings at 3 / 300 / 3000-line inputs.

4. **P4 — dangling-callable behavior.** Unverified: what actually happens on

calling a pointer whose ResourceTracker was removed (expected: UB/crash).

Probe: extend `lljit_probe.c` — hold `greet` v1's address across

`LLVMOrcResourceTrackerRemove`, call it, observe. Outcome writes the §d

rule into a spec.

5. **Not found in literature:** hard per-statement latency numbers for

clang-repl/Cling/Julia at fragment scale (published material discusses

architecture, not ms); PG numbers include -O2/inlining tiers so they

overestimate our -O0 path. The probe numbers supersede the literature for

this decision.

6. **Unverified:** exact LLVM version that removed

`LLVMOrcThreadSafeContextGetContext` (hit empirically on 22; floor rule in

§b makes the exact version moot).

h. Effort estimate — R6.1, C11, this codebase

**5–8 engineer-days** to flag-gated landing; +2–3 to flip the default.

  • D1: `runtime/hey_jit_session.c` host (probe already proves every API call;

~400–600 lines with protocol + error surfaces), Makefile/`llvm-config`

wiring, rpath+fallback detection. (The 150-line probe took under an hour —

the host is mostly protocol and error discipline, not JIT novelty.)

  • D2: P1 runtime re-entry probe; if re-entry fails, scope the init-guard work

(this is the swing factor: +0 to +3 days in the runtime, e.g. idempotent

`hey_runtime_init` or a `hey_runtime_reset_for_repl()`).

  • D3: `tools/hey_repl_session.hey` integration (`--emit-ll` + host protocol,

per-generation entry symbol), transactional rollback = drop dylib.

  • D4: latency gate at 100 ms (P2/P3), macOS + Linux batteries, AMFI

regression check (host built via normal pipeline), crash-respawn

supervisor loop in the Hey-side shell.

  • D5: specs + defect-ledger rows + docs receipts per release conventions;

buffer for JITDylib lifecycle leaks under long sessions.

R6.2 is a separate, larger slice (session ABI of doc-27 §7.2 + callable

lifetime rules from §d) — not estimated here beyond noting it is

runtime-design-bound, not JIT-bound.
