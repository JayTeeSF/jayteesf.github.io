Hey: stable, ergonomic, extremely fast

Hey is a programming language that reads like Ruby, has no type annotations, gives you actors, workers and Jobs as words of the language, and compiles to native code through LLVM. This page is the map: what Hey promises, where it stands today, and which page to read next.

1. Hey in one picture

You write a file. hey app.hey compiles it to a native program and runs it; the second run skips the compiler and starts in a few milliseconds. hey build writes the same program to a file you can ship: 134 KB for hello world on a Mac, needing only the operating system's C library. Inside it, each actor (a small worker that owns its own state and talks only by messages) runs on a pool of threads across your CPU cores.

In the picture: HIR is the compiler's layer for what the program means, MIR the layer that fixes order and memory, LLVM the back end that makes machine code. The compiler page explains each.

2. The promise, and where it stands

Every page in this set is written against one claim: Hey is stable, ergonomic, and extremely fast, at Rust speeds. Each card says what proves it today and what's decided next. Nothing on these pages claims a speed that wasn't measured.

Stable

Today: one main compiler road from source to native code1 (the leftover old routes are being removed); a failure stops only the request, actor or Job that caused it2 (actors and failure); values never change after they're made; packages are locked by hash (Guide 2, which also lists the package gaps found while writing it).

Decided, coming the consolidation release deletes the leftover old compiler routes so only one road remains (ledger L-ARC-54; roadmap).

Ergonomic

Today: Ruby-shaped source (elsif, case/when, says, "#{interpolation}"); no type annotations, the compiler infers types; a counting actor in about twenty lines; tests in the same file; hey app.hey runs like go run.

Decided, coming the _ discard, _ = save(record) (ledger L-LAN-40), and type inference plus specialisation (one compiled copy of a function per kind of argument it's called with; L-TYP-11).

The ledger marks L-LAN-40 "built", but on the 0.99.606a candidate _ = f() fails with undefined name: _ (heyc --check) and unexpected token after expression: = (hey). This page reports what ran; the disagreement is left for the ledger's owner.

Extremely fast

Today: native code through LLVM (the optimizer and code generator Rust and Swift also use); memory freed right after a value's last use, planned by the compiler's MIR stage (its middle layer, where evaluation order and memory are decided); two benchmarks at exactly C's instruction count; a built hello world starts in 1 ms (macOS).

Not there yet: counting machine instructions, most benchmarks take 1.3 to 2.6 times C's, and the 1BRC data-processing benchmark about 56 times. Decided, coming in-place updates of values nobody else holds, a compact 16-byte String ("Phase S"), and direct calls from Hey into C libraries ("native ABI v2"). See section 6.

6. Where Hey is today, against C

Guess first: Hey ties C on a plain integer loop. On the One Billion Row Challenge (read lines of station;temperature, print min, mean and max per station), how many times C's work do you think it does today?

The bar, set by the Maintainer (ledger L-PRF-27): as fast as C or faster on every benchmark, and on the programs people actually build (web servers, phone and TV apps). Here's the honest distance. Numbers are machine instructions retired, Hey divided by C for the same program and input; 1.00 means a tie.

WorkloadHey ÷ CWorkloadHey ÷ C
W1 sum1.00W7 string1.35
W2 transform1.80W8 mixed1.33
W3 search1.00W9 dictionary1.56
W4 append1.65W10 word frequency1.38
W5 histogram1.90W11 binary trees2.63
W6 fannkuch2.55W12 n-queens1.62
1BRC (one billion row challenge), 10M rows56.53

Release 0.99.605a, Linux (Intel i7-1165G7), median of five runs; copied from the performance page's scoreboard, which has the method, memory figures and the 0.99.606a status (not yet measured there).

Measured by wall-clock time instead (an earlier 605a run on the same Linux machine), Hey puts the workloads at 1.0 to 2.9 times C and 1BRC at 63.3 times.

So: integer loops tie C, most real-shaped work is 1.3 to 2.6 times C, and string-heavy data processing is far behind. The decided work aimed at that gap (MIR facts that let a value nobody else holds be updated in place, a new map design, 16-byte Strings) and its schedule are on the performance page and the roadmap.
