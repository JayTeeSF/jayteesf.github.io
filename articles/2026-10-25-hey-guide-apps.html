Apps from one Hey file: Apple TV, iPhone and iPad, Android

You write the app's brain in ordinary Hey: a couple of functions that say what the screen shows and what a button press does. A small native host, supplied by Hey or a Hey package, draws real tvOS, UIKit or Android views and calls your functions. This guide builds one of each, times every step on a real Mac, and says exactly how far each one has been proven: a plan on disk, a simulator, a device, or a store.

The short version

  • Apple TV is the quickest. Three commands (test, lock, launch) took a one-file Hey app to running on the Apple TV simulator in 7.2 seconds on a cold build (3.5 s once the Hey runtime is cached), plus 14 s to boot the simulator. The optional plan step adds 0.55 s.
  • iPhone and iPad come from one command in Hey itself: hey mobile ios native-app. But on the 606a release candidate it fails before it builds anything: the compiler now hands the button number over as a pointer to a Hey value (boxed) instead of a plain 64-bit integer, and the command refuses it. That is an open P0 task.
  • Android has two roads today, and that's a gap. Hey's own hey mobile android app generates a Gradle project; the hey_android package builds an APK with no Gradle at all. The no-Gradle road ran end to end here: a Hey program and a Hey actor ran on the API 36 emulator, and their output matched the Mac byte for byte. Hey's own command fails with the same boxed-value problem as iOS.
  • Your code is ordinary Hey. No annotations, no Swift, no Kotlin. It goes through the same compiler road as any program and comes out as a native object file (compiled machine code, not yet linked into an app) for the device's chip. On the way it passes through HIR and MIR, the compiler's two internal forms for "what your code means" and "in what order, and who owns each value", and then LLVM, the code generator Rust and Swift also use.
  • Desktop means a native command-line or server binary today. There is no desktop window or GUI package, and nothing has been decided about one.
  • No store receipts yet. Nothing on this page has been through App Store or Google Play review. The tools can sign for TestFlight (tvOS) and build a Play upload bundle (hey_android's served-screen renderer), but those paths were not run for this guide.

One Hey program, four kinds of screen

Every target uses the same deal. Your Hey file exports a few named functions. The host calls them:

The contract each host expects
TargetFunctions your file exportsWhat they return
Apple TV (scene contract v2)tv_scene_init(), tv_scene_step(scene, event)a JSON "scene document": background plus widgets (text, image, QR code, cards)
iPhone / iPadios_app_manifest(), ios_action_code(action_id)a JSON manifest of list and form screens; an integer per button press
Android (Hey's Gradle road)android_app_manifest(), android_action_code(action_id)the same shape as iOS
Android (hey_android, no Gradle)a normal program blockyour program owns an event loop and draws rows through pkg:hey_android/android_ui
Android TVandroid_tv_app_manifest(), android_tv_action_code(id)a manifest with "profile":"public-display"

Two words used below. Mach-O is Apple's format for compiled code; ELF is Linux's and Android's. A served-screen app (also called api_screens) is one whose screens are described in JSON by your server and drawn by a renderer on the device; more below.

A host here means the few hundred lines of native code (Objective-C on Apple, Java or C on Android) that own the window, read the JSON and draw real platform views. It knows nothing about your product. Hosts live in Hey packages (for TV and the served-screen renderers) or in Hey itself (the iOS and Gradle Android commands).

Apple TV works today: a running app in three commands

Works today on the simulator, through the hey_ios_tv package (version 0.4.26, the newest in the package registry). It pulls in hey_tv 0.2.3 (screen descriptions that don't care which TV) and hey_ios 0.4.14 (Apple capability contracts).

The whole app

A lamp: press Select on the Siri Remote and it switches on (yellow screen) or off (dark screen). The state lives in the scene document itself, as a "lamp" field the app reads back by name with find: no hidden variables. (Why find and not Json.decode? Inside a TV app today, Json doesn't work; see gap 5.)

# A lamp for Apple TV: press Select on the remote to switch it on and off.
spec 'select switches the lamp; other buttons leave it alone'
  expect stdout "off\non\non\noff\n"
end

fn scene(lamp)
  let color = '#101820'
  let words = 'The lamp is off'
  if lamp == 'on'
    set color = '#F2C14E'
    set words = 'The lamp is on'
  end
  return '{"schema":"hey-tv-scene-v2","lamp":"' + lamp + '","background_color":"' + color + '","widgets":[{"kind":"image","id":"bulb","symbol":"lightbulb.fill"},{"kind":"text","id":"state","text":"' + words + '","style":"title","align":"center"},{"kind":"text","id":"hint","text":"Press Select","style":"caption","slot":"bottom","align":"center"}]}'
end

fn lamp_of(scene_json)
  if find(scene_json, '"lamp":"on"') >= 0
    return 'on'
  end
  return 'off'
end

fn tv_scene_init()
  return scene('off')
end

fn tv_scene_step(scene_json, event_json)
  if find(event_json, '"button":"select"') < 0
    return scene_json
  end
  if lamp_of(scene_json) == 'on'
    return scene('off')
  end
  return scene('on')
end

program
  let a = tv_scene_init()
  let b = tv_scene_step(a, '{"kind":"remote","button":"select"}')
  let c = tv_scene_step(b, '{"kind":"remote","button":"up"}')
  let d = tv_scene_step(c, '{"kind":"remote","button":"select"}')
  says lamp_of(a)
  says lamp_of(b)
  says lamp_of(c)
  says lamp_of(d)
end

The answer to the puzzle: three commands are required (heyc --test, hey package ensure, hey ios-tv-app --launch), 7.2 seconds cold, 3.5 seconds warm, plus 14 seconds the first time you boot the simulator. The plan step is optional. Pressing Select was not driven from a script (there's no command-line remote), but the spec checks what a press does and the app was still running 8 seconds after launch.

On a real Apple TV the same tool takes --device [ID]: it builds for arm64-apple-tvos, signs with your Apple Development identity and a tvOS provisioning profile, and installs with devicectl. Add --distribution (needs a paid Apple Developer Program account) and it emits an .ipa for TestFlight instead; --icon DIR adds the icon and top shelf image the App Store requires. Neither was run for this guide: no Apple TV is paired to this Mac and no distribution certificate is installed.

hey ios-tv-app --out build/tvos-device --source app/tv.hey --hey-root "$HEY_ROOT" --device
hey ios-tv-app --out build/tvos-store  --source app/tv.hey --hey-root "$HEY_ROOT" --device \
  --distribution --icon icon/ --export-compliance exempt
What the TV renderer can draw (scene contract v2)
  • Backgrounds: a flat colour, a felt-table gradient, or a top-level background_color.
  • Text in four styles (title, headline, body, caption), wrapped at the screen margin, with **bold**, *italic* and `code`.
  • Images (SF Symbols), QR codes with captions, rounded rectangles, and a playing-card family: card, stack, hand.
  • Remote presses arrive as {"kind":"remote","button":"select|up|down|left|right|playpause"}. Menu arrives as back only when the scene says "handles_back": true.
  • Unknown widget kinds draw a visible placeholder instead of crashing.

Source: hey_ios_tv/docs/GETTING_STARTED.md, docs/SCENE_CONTRACT.md. Bigger examples: hey_ios_tv/examples/native_tvos_scene_app.hey (blackjack) and the hey_demo_tv_app repository (Nim against the TV).

iPhone and iPad: one command, broken on the 606a candidate

Partly works (fails on the 606a candidate) This command lives in Hey itself, not a package. It has run on simulators and devices with earlier toolchains, but on the 606a candidate it fails at the first step. The commands below are exactly what you'd run; the outputs are what actually happened.

The example ships with Hey: examples/mobile/native_ios_app.hey. It exports ios_app_manifest() (two screens: a list and a form with a secure password field) and ios_action_code(action_id).

Android: two roads, and the package road works

There are two Android roads, and you should know which one you're on.

Road A: Hey's own command Partly works (fails on the 606a candidate)

hey mobile android app compiles your Hey into ELF objects for arm64-v8a, x86_64 and armeabi-v7a and generates an Android Studio / Gradle project with a JNI library and a Java Activity. Minimum API 21, target API 35. --build needs Gradle.

Road B: the hey_android package Works today

hey_android 0.4.7 builds an API 36 APK with no Gradle: NDK r28 clang, aapt2, zipalign, apksigner. Your Hey program plus the Hey runtime go into one shared library under NativeActivity.1 It also has a Java renderer for served screens that can produce a signed Play upload bundle (AAB).

Road B: doctor, then a Hey program on the emulator

Three Android words: NativeActivity is Android's built-in screen that hands control straight to compiled code, so the app needs no Java; an AVD (Android Virtual Device) is a saved emulator; logcat is Android's system log, where the app's output lands. The program is the one hey_android ships as examples/hello_runtime.hey:

# hello_runtime: a Hey program that uses the Hey runtime, built for Android.
#
# Maps, arrays, a string join, JSON parse and print, and SHA-256 of a string.
# specs/android_emulator_spec.sh builds it into an APK, runs it on an API 36
# emulator and requires its logcat output to equal the Mac run byte for byte.

program
  let queue = {title: 'Up next', rows: []}
  let names = ['Ada', 'Grace']
  set names = [...names, 'Linus']
  let i = 0
  while i < names.length
    let row = {id: i + 1, label: 'Row ' + names[i]}
    set queue = {...queue, rows: [...queue.rows, row]}
    set i = i + 1
  end
  let joined = Text.join(names, ', ')
  let parsed = Json.decode('{"kind":"list","items":[1,2,3],"ok":true}')
  let doc = Json.encode({queue: queue, joined: joined, parsed: parsed, count: parsed.items.length})
  says doc
  says doc.length
  says joined
  says Crypto.sha256_text(joined)
  says Crypto.sha256_text(doc)
end

What hey_android 0.4.7 can't do yet (from its README)
  • The Hey lane draws only text rows and taps: no buttons, text entry, scrolling or back handling from Hey yet.
  • One CPU target: arm64-v8a, minimum API 35, target API 36.
  • No TLS from the Hey runtime on Android;2 the served-screen renderer uses the platform's HTTP.
  • A runtime error ends the app; there is no per-call error boundary.
  • Some stdlib calls are refused at build time because they would need a Hey toolchain on the phone (use Files.write_atomic, not Files.write_text).
  • The README lists LLVM-lane miscompiles and unsupported shapes from earlier compilers; they were not re-checked against this toolchain for this guide.

One description, many screens: hey_mobile

Works today (packages). The served-screen idea: describe the whole app in Hey (every screen, the JSON route that feeds it, what every button sends), serve that description from your Hey web server, and let a native renderer on each device draw it. The renderer holds no product knowledge, so one description serves iPhone and Android.

# hey-package.json asks for "hey_mobile": "0.3.6"
import 'pkg:hey_mobile@0.3.6/api_screens'

program
  let row = {title: 'title'}
  let library = HeyMobileApiScreens.list_screen('library', 'Library', HeyMobileApiScreens.tab('Library', 'books.vertical'),
    [HeyMobileApiScreens.section('Recent', HeyMobileApiScreens.route('GET', '/v1/items', nil), 'items', row, nil, 'Nothing saved yet')])
  let signin = HeyMobileApiScreens.form_screen('signin', 'Sign in', nil, [HeyMobileApiScreens.field('username', 'Name', 'text', true)],
    {title: 'Sign in', request: HeyMobileApiScreens.route('POST', '/v1/session', {username: '$username'})})
  let session = {sign_in_screen: 'signin', check: HeyMobileApiScreens.route('GET', '/v1/session', nil), sign_out: HeyMobileApiScreens.route('POST', '/v1/session/revoke', {})}
  let app = {schema: HeyMobileApiScreens.schema_version(), tabs: ['library'], session: session, screens: [library, signin]}
  says HeyMobileApiScreens.problems(app)
  says HeyMobileApiScreens.routes(app)
end

Actors inside an app

Works today on Android through hey_android, run here. An actor is a small independent worker with its own mailbox and its own private state; you send it messages and it handles them one at a time (Actors and failure has the details). This one keeps a running total, and it ran on the Android emulator unchanged:

# An actor on Android: it keeps a running total and reports each step.
spec 'the counter actor adds what it is sent'
  expect stdout "total=5\ntotal=12\ntotal=12 done\n"
end

actor Counter(label)
  state total = 0
  receive amount
  if amount == 0
    says label + '=' + total + ' done'
    exit
  end
  set total = total + amount
  says label + '=' + total
end

program
  let c = spawn Counter('total')
  send c, 5
  send c, 7
  send c, 0
  join c
end

PASS: the counter actor adds what it is sent

What "desktop" means today

Works today for command-line tools and servers: hey build app.hey -o build/app makes a native executable for macOS (arm64) or Linux (x64). Guide 3 builds a tool; Guide 4 builds a web server, which is how most "desktop" Hey apps are used today: a local server and your browser.

Nothing planned Desktop windows (a macOS, Windows or Linux GUI app with native windows and menus) have no package and no ruling. A sweep of every repository under the Maintainer's dev folder found none. If you need one now, the nearest thing is a served-screen description from hey_mobile plus a browser.

Gaps and contradictions found while writing this

  1. iOS and Android app commands fail on the 606a candidate. hey mobile ios native-app, hey mobile android app and hey_android_tv all stop with "must export fn …_action_code(action_id) returning an integer", because the compiler now passes untyped scalar parameters boxed (ptr) where the native host expects i64. Hey's own maintained examples hit it. Task: ios-native-scalar-export-abi-regression (P0, no progress events). The inventory still lists the mobile app commands and the iOS native app as built.
  2. The plan's description of Android was wrong. It said hey mobile android app runs "via hey_android 0.4.7, no Gradle". In fact the core command generates a Gradle project (min API 21, target 35), and the no-Gradle build is hey_android's own tools/hey-android-app.sh (API 36). Two Android roads exist; nothing says which is the future one.
  3. hey_android's repository says 0.4.7; the registry's newest is 0.4.3. This guide ran 0.4.3, the version a user can actually lock. Versions 0.4.4 to 0.4.7 aren't published.
  4. hey_android_tv 0.1.3 can't run as a package command. Its version() still returns '0.1.0', so hey android-tv-app looks in the wrong folder. It also pins hey_tv 0.1.0 exactly while hey_ios_tv needs ^0.2.0, so no project can lock both TV adapters, and it pins the retired hey_android 0.1.4 Gradle line.
  5. The tvOS build road accepts less than hey does. Three things that run fine with hey app.hey failed inside the TV app: (a) 'Pressed ' + count with an integer count is refused by heyc build --emit-llvm-ir ("llvm backend supported subset cannot lower: string expression `0`"); (b) Json.encode fails to link ("Undefined symbols … _hey_fn_Json__encode"); (c) Json.decode returned nil inside the running app, which crashed with "get string-key fast path [borrowed] expects a JSON object; got nil for key kind". So today a TV app builds its JSON by hand and reads it with find, as the package's own blackjack example does. No task found; the Android README lists similar limits.
  6. A spec passed that the program doesn't do. An actor that changes its own parameter with set total = total + amount (instead of a state line) passes heyc --test with the expected "total=12", but hey prints "total=7" and "total=0 done": the test runner and the native run disagree on the same file. Either the program should be refused or both should agree. No task found. The page uses state, which works on both.
  7. The actor examples don't route button presses through the actor. In native_ios_actor_app.hey and native_android_actor_app.hey the actor runs in the program block, and the exported action function is a plain function.
  8. hey_party says retired and "unlisted from the registry", but the registry still lists 0.1.3.
  9. hey_ui_contract 0.1.0 is not published. It passes its own check but no app can lock it.
  10. Every tvOS app is named HeyPartyTV.app on disk, whatever --display-name says (the name on screen does change).
  11. Gradle isn't installed on this Mac, so the Gradle road's --build couldn't run even without the regression. No physical iPhone, iPad, Apple TV or Android device is paired, and no distribution certificate is installed, so no device or store step was run.
  12. Desktop GUI: nothing exists and nothing is decided.

Notes

  1. Runtime thread-local storage uses the initial-exec model only in executables, so a shared-library build such as Android's works: 1bea7c.
  2. A TLS server is a platform capability, not a dependency of every program, and an unsupported capability must not exist as a fake linked implementation: 36e862, e3eabe.
