Hey language · guided tour · 28 August 2026

Start with a function. End with a native distributed program.

Hey is trying to feel like a small, readable Ruby-style language while compiling like a serious native system: simple functions, immutable values, modules, actors and jobs at the surface; resolved identities, ownership and LLVM underneath. This page walks the ladder in that order.

The idea: you should be able to learn Hey from the outside in. Write ordinary values and functions first. Add modules when a program grows. Add actors when state needs an owner. Add remote actors when work crosses a machine. The compiler should get faster underneath without making the source language uglier.

1. Values and functions: the small center

fn greeting(name)
  return 'Hello, ' + name
end

program
  says greeting('Ada')
end

Why this is the center

Hey is deliberately function-first. Most features should lower to ordinary values and calls instead of requiring a separate object model. Strings, numbers, booleans, arrays, maps/JSON-shaped records, bytes and nil are the everyday building blocks.

Source values are immutable. The compiler may reuse storage when it can prove that reuse is invisible to the program.

2. Modules: make names explicit

module Accounts
  fn deposit(account, amount)
    return {...account,
      balance: account.balance + amount}
  end
end

import './accounts.hey'

program
  let next = Accounts.deposit(user, 10)
end

What a module means

An import identifies another source unit; the module declaration gives the semantic module its name. The compiler should remember the resolved unit/module/function identity, not merely the characters Accounts.deposit.

This matters because two units may legally contain the same source spelling while denoting different functions.

3. Collections: immutable at the surface, reusable underneath

Programmernext = put(stats,key,value)
CompilerRecognize one map-update operation.
OwnershipIf the old storage has one owner, reuse it.
RuntimeO(1)-style update instead of copying the map.
The important open gap: the builtin spelling already reaches a flat path in controlled measurements, while method-form stats.put(...) can still behave like O(map). The language experience says those are one operation; the compiler still needs to make that true semantically and in performance.

4. Actors: state gets an owner

Actors are the concurrency model for long-lived mutable state. An actor owns its state, receives messages and decides how that state changes. Other actors do not reach in and mutate it directly.

FunctionPure-ish transformation of values.
ActorOwns changing state over time.
MessageMoves intent/data between owners.
Supervisor / jobsOrganizes failure, retry and background work.

5. Distribution: actors cross the node boundary

Distributed Hey adds transport under the actor model instead of inventing a second distributed programming style. Remote process identity, request/reply and transport exist; TLS paths fail closed rather than silently becoming plaintext. Cluster discovery, membership and placement are the next layer and should remain separate from the transport itself.

6. Packages, web and native targets

Packages

Manifests, content/archive digests, lockfile v2 and verification provide the path from a source tree to reproducible dependencies.

Web

The native web runtime has already demonstrated strong per-core throughput when hot request paths avoid delegated sidecar calls. That is evidence the architecture can be fast; it is not permission to ignore remaining compiler cliffs.

Apple targets

Unsupported security capabilities are compiled out or fail closed instead of being represented by fake OpenSSL symbols. The tvOS build/sign/install/launch path has been proven.

7. What the compiler underneath is trying to do

Parse structureWhat are the expressions and occurrences?
Resolve meaningWhich module/function/value does each occurrence denote?
HIRCarry that meaning forward.
MIRMake ownership/effects/execution explicit.
LLVMLower mechanically to machine code.
A useful progress marker: the production compiler now keeps two same-spelling helper functions distinct and executes the expected 101 / 201 result. That closes a real wrong-code case. The next problem is breadth: every expression form has to carry nested call identity, not only the forms that already happen to be supported.

8. What is still open—and why you should care

Open workPlain-English consequence
Nested-call emitter coverageThe resolver may know the exact target, but some production LLVM expression arms cannot yet consume a target marker embedded in a larger expression. Turning complete occurrence emission on exposed 18 new build failures, including 1BRC.
Module-member producer factsSome qualified calls do not get resolver target rows yet, so later stages have nothing authoritative to carry.
Name-recovery deletionUntil all call families are covered, lexical recovery can still hide missing semantic facts.
Ownership/MIR recordsSome ownership decisions still inspect printed MIR. Equivalent spellings can therefore take very different performance paths.
MAP_PUTMethod-form map update remains a major known blocker to a C-class 1BRC result.

9. The promise

Hey is not trying to win by making programmers write LLVM-shaped code. The intended product is the opposite: Ruby-like ergonomics over simple functions and actors, with native compilation and aggressive reuse hidden underneath. The project earns that claim only when the real product paths compile through the Hey-owned compiler, fallbacks are zero, and the performance curves are flat where the semantics say they should be.
