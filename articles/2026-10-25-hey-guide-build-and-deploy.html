Build and deploy Hey programs

hey build app.hey -o build/app gives you one native file. On a Mac it's 134 KB for hello world and needs nothing but the operating system's C library to start. This guide opens that file up, measures it, and follows it into a container and onto a server.

Badges: Works today Partly works Decided, coming Proposed Being removed (meanings in the index).

Two toolchains, said plainly. macOS numbers come from the 0.99.606a candidate on an Apple M3 Pro. Linux numbers come from the released 0.99.605a toolchain image (hey-toolchain:0.99.605a-amd64, Alpine, run under emulation on the same Mac), because 606a for Linux is built on its own machine and wasn't available to this page. The two versions link differently (section 2), so don't compare a Mac row with a Linux row as if only the operating system changed. Nobody had recorded these facts before; every number here was measured.

1. What comes out of hey build

Works today

$ hey build hello.hey -o build/hello
built /Users/you/g6/build/hello
$ ls -l build/hello
-rwxr-xr-x  1 you  wheel  134328 build/hello
$ otool -L build/hello
build/hello:
	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1356.0.0)

The hey build line also printed 30 selfhost_ diagnostic lines on 606a (trimmed; see Guide 1).

Name and place: exactly what you pass to -o. Leave the folder out and it lands next to where you ran the command. heyc build app.hey -o build/app does the same thing.

Three layers are copied into the file when it's built. Only what your program can reach is kept: the linker drops unused code and unused libraries (-dead_strip and -dead_strip_dylibs on macOS). The proof is in the symbol table (the list of named functions inside the file, which nm prints): hello world's file defines 20 functions; a small web server's defines 87 Hey runtime functions, including the actor scheduler.

Predict: on Linux 605a, hello world is 18 KB, but the three-line actor program from Guide 1 is 1.6 MB. What did the actor program pull in that hello didn't? (Answer in the table: look at the linkage column.)

2. Measured: size, linkage, startup

Four programs: hello.hey; tour_03_actors.hey (Guide 1's counter actor); tour_08_web.hey (routes dispatched in memory, no sockets); and health.hey, a real HTTP server with one /health route (section 5 shows its source). "Stripped" is after strip, which removes debugging symbols.

Unstripped Linux sizes move by a few bytes with the folder you build in, because the debug information records the path (an editor's rebuild of tour_03_actors came out 16 bytes smaller); the stripped sizes don't. The plan asked for the Guide 3 tool here; Guide 3 measures its own tool (270 KB, 2.1 ms start), so this table uses two web programs instead. Startup per program was measured on macOS only (next section); timing Linux under emulation would mean nothing. Linkage from otool -L (macOS) and ldd (Linux). Linux file type: ELF 64-bit LSB pie executable, x86-64, dynamically linked, interpreter /lib/ld-musl-x86_64.so.1, with debug_info, not stripped.

Answer to the puzzle: OpenSSL. On 605a for Linux, any program that pulls in the runtime's I/O layer links libssl and libcrypto and carries the TLS code, even if it never opens a secure connection. On 606a for macOS, OpenSSL isn't linked at all: the runtime opens it the first time a program actually uses TLS (section 7 covers what that means for deploys). So the Mac files stay small. Whether 606a for Linux shrinks the same way wasn't measured here, but its source suggests it does: Linux links with -Wl,--as-needed (drop unused libraries; runtime/heyc.c:26680-26684) and the runtime loads OpenSSL with dlopen on Linux too (runtime/hey_runtime.c:235-252).

Static or dynamic? Both, by layer. Your code, the standard library pieces and the Hey runtime are static: inside the file, nothing to install. The C library is dynamic on both systems, as it is for almost every program on them. OpenSSL is dynamic on Linux 605a and loaded on demand on macOS 606a.

Startup

Works today

Hey ships a benchmark that times the three ways to start a program, from one empty cache. During the warm runs it replaces the compiler with a file that fails if started, so a passing run proves warm starts never touch the compiler.

$ ./bin/perf script-startup --iterations 25 --out /tmp/startup
script startup benchmark ok iterations=25 compiler_started_on_warm=false backend=llvm cold_ms=11772 warm_mean_ms=7 direct_mean_ms=1 receipt=/tmp/startup/summary.tsv
How you start itTime (macOS, 606a)
First hey app.hey (cold: compile, then run)11,772 ms
Later hey app.hey (warm: cache check, then run)7 ms average
./build/app directly1 ms average

So the cache check costs about 6 ms per start. For a server that's nothing; for a tool run in a tight shell loop, build it. The benchmark's own program printed script-startup-ok; the cold time includes compiling it from an empty cache.

./bin/perf script-startup --source FILE.hey, which Hey's docs suggest with examples/hello.hey, fails with cold script output mismatch: the benchmark insists the program print exactly script-startup-ok. It also has to be run from inside the Hey checkout (from elsewhere it stops with heyc: file not found: stdlib/Cli.hey).

3. The run cache

Works today

hey app.hey keeps its compiled program in your user cache, keyed by the content of your file, every file it imports, and the compiler itself. hey cache path shows where:

$ hey cache path
cache_home=/Users/you/Library/Caches/Hey
parser_cache=/Users/you/Library/Caches/Hey/parser
run_cache=/Users/you/Library/Caches/Hey/run
source_index_cache=/Users/you/Library/Caches/Hey/source-index
runtime_object_cache=/Users/you/Library/Caches/Hey/runtime-objects
compiler_build_dir=/path/to/hey/build
compiler_ir_cache=/path/to/hey/build/compiler-sidecars

Run with HEY_CACHE_HOME pointed at a scratch folder; shown here with the default location (macOS ~/Library/Caches/Hey, Linux $XDG_CACHE_HOME/hey or ~/.cache/hey) substituted. HEY_CACHE_HOME moves all of it.

Each cached program is a folder with three files: program (the executable), backend.txt and compiler-authority.json (what compiler made it). Entries are never overwritten; a change makes a new one. To diagnose a slow start, HEY_RUN_TRACE=1 prints the decision (index=hit, cache=hit backend=llvm, or the reason for a miss such as index_reason=dependencies). Guide 1 walks through a miss and a hit.

$ hey cache gc --dry-run
cache_gc_removed=0 all=false days=30 dry_run=true skipped_in_use=0 reclaimed_orphan=0

hey cache gc removes entries unused for 30 days (--days N to change, --all for everything) and never touches one that's in use.

4. Targets and platforms

Works today macOS arm64, Linux x64. Partly works Windows x64.

A Hey build makes a program for the machine you're on. To make Hey itself installable without a C compiler, the release command packs the whole toolchain into one archive per system (target archive v3): compiler, linker, standard library, a precompiled runtime and native libraries, with a SHA256SUMS file and an install.sh. Partly works: the commands work, a Linux archive passed a full native receipt (installed into an unrelated folder and used to compile and run a program with PATH=/nonexistent) in release 0.99.282a, and every archive still says publication_ready=false because signing, a license inventory and an SBOM (software bill of materials: a list of every third-party component and version) aren't done. No archive is published for download.

$ hey target matrix
target matrix version=0.99.606a host=darwin-arm64 verify=false
target=linux-x64 product_release=true native_receipt=native-host-required publication_ready=false
  ...
  next_action=./bin/hey target release prepare --target linux-x64
target=darwin-arm64 product_release=true native_receipt=native-host-required publication_ready=false
  ...
  next_action=./bin/hey target release prepare --target darwin-arm64
target=windows-x64 product_release=false native_receipt=runtime-policy-receipt-required publication_ready=false
  ...
  next_action=./bin/hey windows runtime-test-bundle --out FILE.zip
target_matrix_ok=true
$ hey target doctor --target darwin-arm64
target doctor target=darwin-arm64 host=darwin-arm64
clang=ready path=/opt/homebrew/opt/llvm/bin/clang
ld64_lld=ready path=/opt/homebrew/opt/lld/bin/ld64.lld
macos_sdk=ready path=/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX26.5.sdk

Matrix trimmed: each target also lists its gates, all status=not-run in this run (--verify runs them).

The release itself is hey target release --target linux-x64 --out hey-VERSION-linux-x64.tar.gz on a matching machine (it refuses a mismatch); hey target pack and hey target verify are the separate steps. A full release compiles the toolchain, so it wasn't run for this page. A user installs an archive with ./install.sh --user (into ~/.local/hey/VERSION) or sudo ./install.sh --system (into /opt/hey/VERSION).

Windows: there's no Windows compiler. hey windows runtime-test-bundle --out FILE.zip builds a ZIP that exercises the native Windows runtime pieces (I/O completion ports, HTTP, processes) on a Windows machine, and temporarily needs Microsoft's Build Tools to do it. It's evidence for future work, not a product (task windows-ordinary-toolchain-target, deliberately last). Phones and TVs are in Guide 5.

5. Containers

Works today

The toolchain image is Hey's compiler in an Alpine Linux image, tagged with the exact version and CPU (hey-toolchain:0.99.605a-amd64). It's built by bin/toolchain-image in the elders_prayer_app repository; because it's cached by its version tag, every Hey release bumps the version so an app never compiles against a stale compiler. It's big (3.33 GB for 605a on this Mac) and it never ships: you compile in it, then copy the result out.

Here's the whole thing for a server. health.hey:

import 'stdlib:Web'

fn health(request)
  return Web.json({ok: true})
end

program
  let routes = Web.routes([Web.get('/health', health)])
  Web.serve(routes, {host: '0.0.0.0', port: 8080})
end

A two-stage Dockerfile: compile in the toolchain image, ship only the binary.

# Stage 1: compile with the Hey toolchain image
FROM hey-toolchain:0.99.605a-amd64 AS build
WORKDIR /app
COPY health.hey .
RUN heyc build health.hey -o /out/health

# Stage 2: ship only the binary and the libraries it links
FROM alpine:3.21
RUN apk add --no-cache libssl3 libcrypto3
COPY --from=build /out/health /app/health
EXPOSE 8080
ENTRYPOINT ["/app/health"]
$ docker build --platform linux/amd64 -t hey-docs-health:605a .     # 22 s
$ docker image inspect hey-docs-health:605a --format '{{.Size}}'
9417519
$ docker run -d --rm --platform linux/amd64 -p 18080:8080 hey-docs-health:605a
$ curl -s -i localhost:18080/health
HTTP/1.1 200 OK
content-type: application/json
content-length: 11
connection: keep-alive

{"ok":true}

9.4 MB in all, of which Alpine itself is 7.8 MB and the server binary 1.6 MB. (Alpine 3.21 already includes libssl3 and libcrypto3; the apk add line just makes the dependency explicit.)

The repository's docker/README.md still describes images for version 0.49.0 and a heyc build --native flag that no longer exists. Use the pattern above, or hey_container, a package that generates release Dockerfiles for hey_web apps.

6. Deploy with Kamal

Works today in a real app

Kamal deploys a container image to your own servers over SSH and swaps traffic only when the new container answers its health check. The elders_prayer_app, a Hey web app with a SQLite database, deploys this way to a Hetzner server.

The parts that matter, quoted from its config/deploy.yml (not run for this page; this guide didn't deploy anything):

service: elders-prayer-app
image: jayteesf/elders-prayer-app
registry:
  server: ghcr.io
proxy:
  ssl: true
  app_port: 3072
  healthcheck:
    path: /health
    interval: 3
    timeout: 3
builder:
  arch: amd64
  dockerfile: Dockerfile
  driver: docker
volumes:
  - "elders_prayer_data:/var/lib/elders_prayer"
boot:
  limit: 1
  wait: 5
drain_timeout: 30

Lessons the app's comments record:

  • Match the server's CPU (arch: amd64) or the deploy ships a binary the server can't run.
  • Use driver: docker so Kamal can see the locally built toolchain image.
  • Put the database on a volume; the image is replaced on every deploy.
  • Restore packages with hey package ensure --project . --locked in the build stage, never --update-lock, so a new package version can't sneak into a release (Guide 2).
  • A health check proves a status code, not a page. Its bin/deploy fetches real pages after Kamal finishes, and fails on an empty body.
  • The runtime stage preloads mimalloc because musl's allocator takes one lock per allocation; the app's note records stock Web.serve going from 15K to 99K requests per second on one CPU (measured on hey_fast_web).

The app builds with heyc stage0-build, not hey build. stage0-build is Hey's older bootstrap compiler, which goes through C instead of the normal compiler road; heyc --help lists it as "private bootstrap/recovery only". The Dockerfile's comment (written at 601a) says the normal build, for this app's code, fell back to a binary that called heyc at run time. That didn't reproduce for this page's four sample programs, which all ran with an empty environment (env -i) from a different folder, but the app itself wasn't rebuilt with hey build, so its reason isn't disproved. A reason that's certainly still current is the pkg: import gap in Guide 2. Until that's fixed, an app that imports packages with modules in a subfolder can't use hey build.

hey_kamal_cli is a shared deploy command for Hey apps built around one rule: build and test the image first, publish it, and deploy only that exact image digest (kamal deploy --skip-push), so the server never receives source or a compiler.

7. Install layout and hidden host dependencies

Decided, coming

The rule: an installed Hey, and the programs it builds, depend on nothing on the machine that isn't declared. Toolchains live in one versioned folder (/opt/hey/VERSION or ~/.local/hey/VERSION), caches in the user cache folder, and built apps find their native libraries relative to themselves (@loader_path/../lib/hey/native on macOS, $ORIGIN/../lib/hey/native on Linux).

What the measurements show:

$ cp build/hello build/tour_03_actors build/fetch elsewhere/ && cd elsewhere
$ env -i ./hello
Hello, world
$ env -i ./tour_03_actors
visits=1
visits=2
$ env -i ./fetch          # Http.get_text of an https:// URL
true

Copied away from the build and run with an empty environment, the programs work. But the HTTPS one has a dependency you can't see with otool -L:

$ otool -l build/fetch | grep -A2 LC_RPATH | grep path
         path /opt/homebrew/opt/openssl@3/lib (offset 12)
$ DYLD_PRINT_LIBRARIES=1 ./build/fetch 2>&1 | grep openssl
dyld[88925]: <B5FB28DB-...> /opt/homebrew/Cellar/openssl@3/3.6.4/lib/libcrypto.3.dylib
dyld[88925]: <1B8AB7A7-...> /opt/homebrew/Cellar/openssl@3/3.6.4/lib/libssl.3.dylib

Partly works On macOS 606a the runtime opens OpenSSL with dlopen1 (which loads a library while the program is already running) the first time a program uses TLS, searching a library path written into the binary that points at Homebrew's openssl@3. On a Mac without it, a TLS call fails with a named error (could not load OpenSSL ...; that failure wasn't triggered for this page). Programs that never use TLS don't care. On Linux 605a, OpenSSL is an ordinary declared dependency that ldd shows, and the container above provides it. Until the no-hidden-host-dependencies work is finished, ship TLS-using macOS binaries only where openssl@3 is installed, or inside a target archive that carries it.

Notes

  1. The runtime loads OpenSSL on first TLS or crypto use, not at program start: e18214.
