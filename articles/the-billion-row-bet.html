The Billion-Row Bet

Last July, this project ran all one billion rows of the One Billion Row Challenge in 43.242 seconds on this machine. Then it deleted the code that did it — because the fast part wasn't Hey. The hot loop was a hidden native C routine, and “written in Hey” has to be true or it means nothing. The bet: earn that number back honestly, with immutable, zero-copy Hey and no hidden C anywhere. That bet is still open. Two smaller ones, running alongside it, are not.

Status: speed bet open, two adjacent bets resolved

Honest, immutable Hey does not beat 43.242 seconds yet — today it projects about 20.4 hours for the same billion rows (§1, §4). What changed since the bet was opened: the program's output is now proven correct against the challenge's own official results, and the language's one mutable value type has been deleted — on a measured receipt, not a promise (§5). Dated, newest-first record in §6.

1. The bet

TL;DR

  • Verdict: the speed bet is not won yet, but the ground around it just got a lot firmer. Honest, immutable Hey does not beat 43.242 seconds today — it projects about 20.4 hours for the same billion rows, on the file the target itself is measured on. What changed while that number sat there: the program is now proven correct, and the language's one mutable value type has been deleted, because the honest version turned out not to need it.
  • The gap, in one number: 20.4 hours is roughly 1,700× slower than the 43.242-second mark it's measured against — the honest cost of an algorithm that hasn't yet stopped copying memory it doesn't need to copy (§3, §4).
  • Two adjacent bets got settled while the main one stayed open. Running the official billion-row file, Hey's output now matches the challenge's own expected results exactly: all 413 stations, every minimum, mean and maximum. And the language's only mutable value type — an accidental output builder left over from an earlier attempt at this same benchmark — is gone, deleted on a receipt showing it cost nothing to remove (§5).
  • Why we still think we can make it: the actual per-row scanning work already runs at world-class pace. It's buried under roughly a thousand times its own cost in memory bookkeeping — overhead we now know how to stop paying, not speed we have to invent (§3).
  • Falsifiable, on purpose: every number on this page traces to a dated, timestamped entry in the project log (§6). Rebuild the tagged version and rerun the same probe to reproduce any of it.

Here's the wager, plainly. In July this project processed all one billion rows on this machine — the hard file, 41,344 stations — in 43.242 seconds. That isn't a target; it already happened. But it happened with a cheat we didn't fully own at the time: the entire hot loop was a single native C call per chunk that scanned, split, parsed and tallied a whole range of bytes at once, into a native table. Hey handed it chunk boundaries. C did the billion rows.

So the project killed it. A rule here says a Hey program has to be Hey; hidden native shortcuts make that claim false, so the call was banned, the code deleted, and the speed went with it — knowingly, at enormous cost. The bet is whether we can earn 43.242 seconds back the honest way: immutable, zero-copy Hey, no hidden C, same machine, same file, beaten by any margin. There was a smaller stake riding along, too — the language's one mutable type, an accidental output builder that survived from an earlier attempt at this same benchmark. That one is no longer riding along. It's gone (§5).

The world's numbers stay on the chart, but only as scenery. The fastest publicly known C we could measure on our own harder file needs 18.8 seconds; a fast Python needs about 143. The official world record is 1.5 seconds — easier dataset, different hardware, not a fair comparator here. None of those are the bet. The bet is Hey against Hey — and, as of today, Hey is still losing to itself by about 1,700×.

2. What is 1BRC?

Term: the One Billion Row Challenge

The One Billion Row Challenge (1BRC, Gunnar Morling, January 2024) asks for exactly one thing: read one billion station;temperature text rows and print the minimum, mean, and maximum temperature per station, as fast as possible. The winning entries all leaned on the same handful of tricks — reading the file straight into memory instead of calling read(), scanning several bytes at a time instead of one, and skipping text allocation until the very last step.

3. Why we think we can make it

The scanning work itself is already world-class; it's drowning in bookkeeping it doesn't need. A controlled measurement, pinned to a fixed number of stations so the comparison is clean, put actual scan-and-compare logic at about 7 nanoseconds (ns, billionths of a second) per row — genuinely fast, on par with the world's best. That 7 ns sits underneath roughly a thousand times its own cost in memory allocation, cloning, and release — the tax of copying values that never needed copying. We don't need to invent speed; we need to stop paying for overhead the algorithm never asked for.

That single measurement is what makes this bet winnable rather than romantic, and it took a second machine's worth of archaeology to see the full shape of it. The banned July routine's trick was fusing the whole scan into one native pass — but fusion is not what today's code is missing. Its scanning already runs at world-class pace; it is drowning in memory bookkeeping around every row instead. So the honest rebuild never has to re-cross the line the project drew when it deleted that native call. It has to stop allocating, not start cheating.

Most of the machine we need already exists. A fast 1BRC pipeline needs a handful of pieces: mapping the file without copying it, scanning it without copying it, parsing numbers without allocating, and fanning work across workers sharing one view of the data. Five of those six already exist in Hey, as immutable, zero-copy code. Two real gaps remain, both scheduled rather than speculative: replacing the one-time output sort that gets dramatically more expensive as the station count grows, and accumulating each row's result in place instead of copying the whole running tally on every single row.

We've done exactly this before, twice. The web server went from ~500 to over 120,000 requests per second the same way — measure, name, delete — in "From 500 to 100,000 Requests per Second." An idiomatic Hey port of a Ruby command-line tool now matches the hand-tuned version it retired (18.1 ms against 18.2 ms) while using none of its tricks, and a separate Ruby port's own memory story — a 481× reduction, printed in public along with the four wrong theories that came before the right one — is the same discipline on a harder problem. And there's a quieter piece of evidence, happening in real time: this team publishes bets before results and corrections in public. This article is doing that right now — the headline finding below (§4) is that three separate ways of checking our own work were themselves wrong before the program was, and we're printing that at full volume rather than editing it out.

4. What we already know that we didn't

Chasing the speed number surfaced five findings that have nothing to do with speed and everything to do with knowing what we're measuring. This is the most interesting part of the campaign so far.

4.1 Correctness is settled

The question most readers would ask first isn't "how fast" — it's "is it even right." Running the official billion-row file, Hey's output matches the challenge's own published expected results exactly: all 413 stations, every minimum, mean and maximum, zero disagreements. An independent full-scale check, run separately on a different machine using the challenge's own official expected-output file, confirmed it more strongly than our own smaller test ever could. So this is not a story about trading correctness for speed. The program is right and slow; the bet is about making it fast while it stays right.

4.2 Three checking mechanisms were wrong before the program was

Getting to that verdict meant testing something we had been asserting for a while but had never actually checked field-by-field. Along the way, three different tools used to verify the answer turned out to have their own bugs — none of them in Hey:

  • The widely used C reference implementation initializes a new station's minimum from zeroed memory instead of the first real reading, so on any station where every temperature is positive, its reported minimum silently stays 0. Invisible at a billion rows, because with enough data every station eventually sees a below-zero reading that overwrites the bug — but glaring on smaller samples, where it can go unnoticed for a long time.
  • A Python cross-check used ordinary rounding, but the challenge's own spec rounds the mean toward positive infinity. On exact halfway ties, the two disagreed by a tenth of a degree — not because either program mis-measured the data, but because they were answering two different questions about the same number.
  • A comparison script split each line on commas, and one official station name contains a comma ("Washington, D.C."), so the script reported a station missing that was never missing at all.

All three were bugs in the checking tools, not in Hey's output, and the program under test was right each time. The lesson we're taking forward is a plain one: "cross-validated" has to name which fields were compared, against which oracle, or it isn't a claim — it's a hope.

4.3 Two files, and the difference depends on the program

This project runs two datasets on purpose. The standard file is the one every published 1BRC number describes: 413 weather stations, about 13 GB. Our own file is harder — 41,344 stations, about a hundred times more distinct names, roughly 15.9 GB. How much harder depends entirely on which program you ask. On a controlled, same-size comparison that fits comfortably in memory, a world-class C reference ran 4.6× slower on our file than on the standard one. But at the full billion-row scale, that same comparison shrank to just 1.3× for C (2.3× for a slower Python reference, whose extra compute-per-row leaves more room for station count to still matter). The mechanism: once a program is memory-bound — spending its time waiting on data rather than computing on it — extra distinct station names mostly stop costing anything extra. Same underlying difficulty, two very different measured effects, because the two runs are dominated by different things.

That same effect is why this chart's "Hey, honest" bar only carries a number for the standard file. Our own file punishes one specific piece of unfinished work — the output-stage sort that gets dramatically more expensive as station count grows (§3) — so hard that the one number we have for it (a since-corrected 59.7-day estimate, §4.5) isn't trustworthy enough to print here. We'd rather leave that row pending than repeat a number we already know is wrong.

4.4 The memory wall, and why it decides the fastest rungs

This machine holds roughly 4–7 GB of file cache against 13 GB of standard-file data, so the file cannot all sit in memory at once. We measured what that costs, cleanly and reversibly: on the same file and program, timed three times back to back — once with the data warm in memory, once forced cold, once warm again — the runs took 1.38 s → 3.33 s → 1.28 s. A 2.4× swing, and it returns to baseline every time. We can turn this effect on and off on demand, which is what makes it trustworthy.

For a while we could describe that effect precisely and not explain it — and we published it that way rather than dress a guess as a finding. The explanation arrived a few hours later, by counting rather than reasoning. During the slow run, the machine pulled 94% of the file back off disk one page at a time; during the fast run, 1%. The extra time works out to about ten microseconds per page, or roughly 1.7 GB/s — against the 5–6 GB/s this same disk delivers when reading the file straight through. So the mechanism is not exotic: fetching memory on demand, a page at a time, is about three times less efficient than streaming it, and the arithmetic closes almost exactly.

We then wrote that this reconciled the two machines — the second one, with six times the memory, showing only a 17% effect because it evicts less of the file. Same curve, different point on it. That was tidy, and it was wrong. Measured on that machine directly, the penalty involves no disk reads at all: no waiting on storage, no faults of the kind our machine was drowning in. Most of its cost is the operating system's own bookkeeping as it fills its cache. So the two machines are not two points on one curve — they are two different mechanisms that happen to produce a similar-shaped symptom, and we only know that because someone measured the second one instead of accepting our explanation of it.

What survives is the consequence, which is the part that touches the bet: on our machine, simply fetching data that doesn't fit costs around nine seconds no matter how good the code gets. That is hardware, not software, and no cleverness in our program moves it. On a machine with enough memory the tax is far smaller and paid in a different currency. The fastest rungs need the second kind of machine — and we would not have known that from either machine alone.

What's certain either way: whatever it is, it costs something comparable to or larger than the entire per-row time budget of a 2-second run on this machine, against a per-row pace that today runs about 73,000 ns — so it's invisible now and will become the whole story as the honest code gets faster. The fastest rungs on the chart above need a machine the data fits on. Here, it's the wall that stops them, not the code, and the height of that wall turns out to be one of the biggest differences we've found between two machines running the identical program.

4.5 Our own predictions failed twice, publicly

Two projections we published this campaign turned out to be wrong, and both failures taught a rule we now use every time.

The first: an early run projected roughly sixty days to finish a billion rows. Corrected within the hour — 98% of that run's time turned out to be a one-time sort that costs more as station count grows, not a per-row cost at all. Measuring at 1,000 rows and projecting linearly had mistaken a fixed cost, paid once, for a rate that would repeat a billion times.

The second: the 4.6× cardinality difference in §4.3 above was first published as a general finding about how much harder our file is. It was corrected within about ninety minutes, once a full-scale run showed the ratio was really 1.3–2.3× there — the earlier number was real, but only in the cached, memory-resident regime it was measured in, not as a universal multiplier.

Two rules came out of those corrections, and they're now how this team works: measure across a full factor of ten before projecting anything — a single small measurement can hide a one-time cost as a per-row rate — and state the regime with every ratio, because "4.6× harder" and "1.3× harder" were both honestly measured, on the same two files, by the same team, in the same week.

5. The sub-stake, resolved

Riding alongside the speed bet was a smaller one: Hey had exactly one mutable value type, a byte-buffer that entered the language by accident during an earlier attempt at this same benchmark, and had survived ever since as an output-formatting convenience. If the honest, immutable rebuild turned out not to need it, it would go too.

It's gone. Before removing it, the team measured what deleting it would cost — a receipt taken as a condition of the deletion, not a promise made in its place:

Small, and not trending in either direction — noise, not a cost. Correctness after the removal: the same 413/413-station, zero-disagreement result as before. That's a cleaner outcome than the bet's original framing anticipated: the type wasn't deleted because the speed bet was won. It was deleted because the immutable version, once it existed, turned out never to have needed it in the first place.

And today's much-slower honest lane isn't evidence the bet is lost; it's a measured, dated starting point for the next fix to move.

Glossary

1BRC
The One Billion Row Challenge: read a billion station;temperature text rows and print the min/mean/max per station, as fast as possible.
byte_buffer
Hey's former one mutable value type — an append-many-times output builder that entered the language by accident and was later deleted once measurement showed the immutable version of this program didn't need it (§5).
zero-copy
Reading or sharing data by pointing at it, instead of duplicating it first.
cardinality
The number of distinct station names in a 1BRC dataset. The standard file has 413; this project's own file has 41,344 — and how much that difference costs depends on whether the program is compute-bound or memory-bound (§4.3).
memory wall
The slowdown a program hits once its working data no longer fits in available memory. Measured here as a reversible, on-demand effect (§4.4); the exact mechanism behind it is not yet confirmed.
The planned reference-counting upgrade
Values share until written, copy only when needed, instead of always copying. See the shared glossary. The in-place-aggregation gap in §3 is a small, scoped preview of this larger program.
