Windows for Hey: the web-view window opened on Windows 11 today; native Hey is planned for 607a

Hey reaches a Windows user two ways. A small window around a web app is built, and today it opened on a real Windows 11 for the first time. Hey itself on Windows barely runs at all. This page shows what ships when, what each needs, and five things you must decide.

Added after acceptance The Maintainer has answered the five decisions: aim for best practice, the integration level C# and C++ have wherever a non-Microsoft language has shown it is possible, and otherwise the next best thing, explained. The answers below each decision come from the research behind Making Windows apps and CLIs with Hey, which is also the practical guide to shipping Windows apps and CLIs built with Hey.

Words used on this page (each is also explained where it first appears)
Win32
The programming interface Windows itself offers: windows, files, threads, sockets. "Native Windows" means calling it directly.
WSL
Windows Subsystem for Linux: a Linux system running inside Windows. Hey in WSL is Linux Hey, which you ruled out as Windows support. The WSL scripts stay only as a stopgap for trying Hey today.
WebView2
The engine of Microsoft's Edge browser, packaged so a program can show a web page inside its own window.
DLL
A Windows system file full of functions that programs call, such as kernel32.dll.
Linker, import library, import table
A compiler writes object files. A linker joins them into a runnable .exe. lld-link is the free LLVM linker for Windows programs; it runs on any operating system. The exe carries an import table: a list of the DLL functions it needs. An import library is a helper file that tells the linker what to put in that table. A .def file is a plain list of function names an import library can be generated from.
C runtime
The library behind C functions such as malloc and printf. Microsoft's version has licence rules about shipping it.
PDB and unwind tables
A PDB is the file Windows debuggers read to map a running program back to source lines. Unwind tables let debuggers and crash reports trace which function called which.
IOCP
I/O completion ports: the Windows way to wait on many sockets and files at once.
COM, WinRT, WinUI 3
COM is the binary object interface much of Windows is built on. WinRT is the newer layer over it, used by WinUI 3, Microsoft's recommended native UI kit.
JIT, Native AOT
C# normally compiles while the program runs (JIT). Native AOT is its option to compile ahead of time into a plain exe, as Hey does.
winget
The install command built into Windows.
SmartScreen, Smart App Control
SmartScreen warns before running a downloaded program Windows has no reputation for. Smart App Control, on Windows 11, blocks such a program outright if it's unsigned.
Wine
A program that runs Windows executables on Linux. Good for a quick check, not the real thing.
mingw-w64
A free C compiler kit that builds Windows programs from Linux or a Mac.
VM
Virtual machine: here, a complete Windows 11 running inside the Linux test computer.
Receipt
This project's word for a saved output that proves something ran.
The coordinator, the linux agent
GippiPiTy, the agent coordinating Hey; and the agent working on the Linux test computer.
Fastest and issue-loaded dates
The forecast gives two dates per item: the date if nothing goes wrong, and the date if the usual number of problems turn up.

Track A: nine steps to native Windows Hey, in order

What exists, precisely: a C compiler builds five small runtime files for Windows, and one tiny test ran on a Windows PC around version 0.99.286a. That PC's security software blocked a larger test before it started, so nothing larger has run. No Hey program has ever been compiled for Windows. Step 1 will be the first.

  1. Build a Windows exe from a Mac or Linux machine. Join the pieces with lld-link, a free linker Hey already carries, using lists of Windows functions that Hey's tooling generates. Nothing from Microsoft. Zig does this.
  2. Fix Hey's Int. The runtime stores it in a C long, only 32 bits on Windows, so whole numbers above about two billion would come out wrong.
  3. Port the runtime. The actor scheduler (the part that picks which actor runs next) goes on IOCP, the Windows way to wait on many connections at once.
  4. Debug files. A PDB, the file Windows debuggers read, plus unwind tables, which let them trace which function called which.
  5. hey.exe, built on a Mac first, then by itself on Windows.
  6. Cross-compile from Windows. A PC with only Hey builds Linux and Mac programs. C#'s native compiler can't.
  7. The integration items, if you confirm the bar in the next section.
  8. Installer, the winget entry, signing.
  9. The gate: Hey builds itself on Windows, with a test report identical to Mac and Linux.

Step 1's link errors become step 3's to-do list, so the coordinator has asked the linux agent to start it now.

Optional: each step in full (who did it, what Hey has, what's missing, the proof)
1

Build a Windows exe from a Mac or Linux machine

The user gets
App authors ship .exe files without owning a PC.
Who did it
Zig generates its import libraries from plain .def lists. Go and Rust go further and write the import table straight from declarations in source.
Hey has
lld-link in its Windows kit; six small C files that clang compiles for Windows; a Hey tool that writes one fixed 1,024-byte exe that does nothing.
Missing
Compiling a Hey program for Windows at all (never done). Import libraries generated from .def lists for kernel32, ntdll and ws2_32. Hey's own start-up code. Default app settings in every exe (UTF-8, long paths, screen scaling) plus icon and version details, which today would need lld-link and a resource step. Added after acceptance lld-link merges manifests only when LLVM was built with libxml2, and otherwise calls Microsoft's mt.exe, which a Mac or Linux host lacks; the dependable route is the manifest as resource type 24 in the .rc file, compiled with llvm-rc, linked with /manifest:no. And longPathAware also needs a machine registry value, so the runtime should use \\?\ paths itself.
Later option
Hey writes the exe and its import table itself, as Go does, with no import libraries at all. That needs a real linker written in Hey. No estimate yet.
Proof
A hello world built on Linux runs under Wine, then on the VM. This is the linux agent's assigned receipt.
2

Fix Hey's Int

The problem
The runtime carries a Hey Int as a C long. Hey's Int is 64-bit; on Windows a long is 32 bits.
Status
Already ruled: "The runtime must use int64_t for Int everywhere; this is a 607 correctness item", assigned to the runtime String and ABI owner. It blocks every runtime step.
3

Port the runtime and put the actor scheduler on IOCP

The user gets
Real programs: files, threads, actors, sockets, HTTPS, long and non-English paths.
Who did it
Go's runtime calls kernel32.dll directly. Go, Nim, Crystal and Node's libuv use IOCP directly; Rust's Tokio and Zig use a lower, undocumented route.
Hey has
Five boundary files (platform, process, IOCP, HTTP, lifecycle) that cross-compile, and a written plan.
Missing
The main runtime file (about 38,000 lines of C) has never been built for Windows. Loading native libraries doesn't work.
Traps the supplement names
Decide early between the documented completion style (Go) and the undocumented readiness style (Tokio, Zig). Take completions in batches. Tell Windows not to queue a completion when a call finishes at once. Send file I/O through the same port. Tie high-resolution timers to the port: Go's Windows timers were 15.6 ms coarse until Go 1.23. Park idle workers with WaitOnAddress. Handle PCs with more than 64 processors. Don't build on fibers, user-mode scheduling, the Windows thread pool or I/O rings in 607a.
Proof
The runtime test bundle, a file read and an actor ping-pong (two actors passing a message back and forth) pass on the VM.
4

Debug files: PDB plus unwind tables

The user gets
Pausing on Hey lines, with variables, in Visual Studio, VS Code and WinDbg (Microsoft's low-level debugger). Readable crash reports.
Who did it
Rust, Swift, Odin, Zig. Go didn't write PDBs, and a proposal on Go's issue tracker says that makes Go "feel like an intruder in the Windows ecosystem".
Hey has
The foundation only: LLVM can describe debug data the Windows way and lld-link writes the PDB.
Missing
The editor searched the 606a tree twice: Hey's LLVM emitter writes no debug data for Hey code on any platform (only the C runtime gets it, from the C compiler). So this is new compiler work, plus unwind tables in every function and a small file telling debuggers how to show Hey's core types.
Proof
All three debuggers stop on a Hey line and show locals.
5

hey.exe: built on a Mac first, then by itself on Windows

The user gets
Hey in PowerShell and the command prompt. No WSL.
Who did it
V builds its Windows starter by cross-compiling. Rust, Go, Zig and Swift ship Windows compilers.
Missing
All of it; it needs steps 1 to 3.
Proof
hey.exe on the VM rebuilds itself.
6

Cross-compile from Windows, with no C compiler

The user gets
On a PC with only Hey installed, hey build --target linux-x64 makes a Linux program.
Who did it
Go and Zig, to both Linux and Mac. C# Native AOT "does not support cross-OS compilation". Dart reaches Linux only.
Hey has
A plan from your November 5 ruling, pencilled in for v608 and estimated at 5 to 9 engineer-weeks.
Missing
Linkers for Linux and Mac programs inside the Hey install. No need for the target's C library files at link time. For the Mac, a stand-in for Apple's system library and a code signature Hey computes itself. Prebuilt runtime files per target. Today Hey calls clang, a C compiler.
Proof
Proposed by the writer: a clean VM builds a Linux binary, and it runs on Linux.

Microsoft ran these "in our benchmarking lab" and doesn't state the operating system or hardware. A more recent Microsoft figure, for its Aspire dashboard (October 6, 2026): startup 1,429 ms down to 491 ms; total size about 183 MB down to 110 MB.

We measured none of these, and none is stated to be on Windows. Hey has no Windows number and no C# entry in its benchmarks. Its last full run (August 31, version 554a, Linux): 2 to 20 times slower than C on ten of twelve small compute tests; second of nine languages on web throughput, ahead of C, Go and Java; about 2,300 times slower than C on one large text-parsing test (1BRC).

C# leaves openings: Native AOT needs Visual Studio's C++ tools, can't build for another operating system, and has no built-in COM. The first honest test: the same small web service in both, on one Windows machine.

Five decisions for you

1. Does 607a also take the cross-compile work pencilled for v608?

Settled at 12:16 PM: you ruled "607a = native Windows plus performance; REPL after". Cost: the compiled REPL (the interactive prompt, rebuilt on the compiler) waits a release. Until then the last second implementation of the language stays, and people who install the packaged Hey have no interactive prompt at all.

Still open. You also asked for "the next release where cross-compilation will need to work (natively) on Windows". The coordinator reads that as pulling forward the work pencilled for v608: 5 to 9 engineer-weeks, plus 3 to 6 for Windows itself (estimates). Is that what you meant?

Added after acceptance Answer: yes. Best practice is to build for every target from every host, as Go ("you are always cross-compiling") and Zig ("builds for all supported targets independently of the host") do; C# Native AOT cannot, which is Hey's opening. Next best, if 607a runs long: Windows to Linux first, Windows to Mac after (the Mac also needs a code signature Hey computes). Brief B61, B62; S32.

2. How much C library Hey's Windows programs use

Provisional pick: borrow Windows' own C library for 607a; none as the end state. Hey's runtime is C, and removing its C calls is the 9 to 18 engineer-month rewrite. Windows 10 and later carry a copy, so Hey ships nothing. Cost: a C dependency stays, against your "no C" goal, until then.

Dissent: the main research recommends none from the start, as Go and Zig do. The linux agent's count of C calls will re-check this. Microsoft's own kit is out: its licence couldn't be read.

Added after acceptance Answer: the provisional pick stands. Best practice is no C library (Go, Zig). Next best while the runtime is C is the Universal C Runtime: Microsoft says it "is a Microsoft Windows operating system component" on Windows 10 and later, and an app-local copy is ignored; mingw-w64 has defaulted to it since v12, and Rust's gnullvm targets and Zig use it. Never vcruntime or msvcrt.dll. Unsourced: no Microsoft page says ucrtbase's exports are a stable contract for other toolchains. Correction to "Microsoft's own kit": the win32metadata repository is MIT, but the NuGet package that ships the .winmd files is under the Windows SDK licence, which says nothing about generating bindings; generating at build time looks like its intended use, and shipping the file itself needs a check. Brief B1, B9, B11, B13, A1, A3.

3. Encrypted connections

Recommended: Windows' built-in encryption and certificate store. Hey stays one file, and outgoing HTTPS already exists this way. Cost: behaviour may differ from OpenSSL, the library Hey uses elsewhere (the writer's inference).

The alternatives: Hey's own encryption with Windows checking certificates, as Go does (one behaviour everywhere; Hey owns encryption code), or a bundled library (same code everywhere; a bigger exe to keep patched). Serving HTTPS on Windows is unbuilt under all three.

Changed after acceptance Answer: Hey's own encryption with Windows checking the certificates is the end state; Windows' built-in encryption (Schannel) is the first step. Reasons: Schannel has no TLS 1.3 on Windows 10 at all; its settings are machine-wide; Microsoft's .NET pages list its pitfalls. Go (CertGetCertificateChain with the SSL policy) and rustls-platform-verifier show the end state, which fits the "no C" goal, gives TLS 1.3 everywhere, and still honours roots that IT installs. A bundled root list or OpenSSL is ruled out as the default: Microsoft's own page says Git and Python break behind company TLS inspection for that reason. Brief B16, B25, B26, B27, B31, B32.

4. Signing

Not signing costs nothing and is what 0.1.0 does. But Windows 11's Smart App Control blocks unsigned programs it has no reputation for, and an earlier test PC's security software stopped a Hey test before it started.

Recommended: sign hey.exe and the installer with Artifact Signing, Microsoft's signing service, from $9.99 a month. The writer adds MyQueue.exe. Cost: an identity check, and warnings until reputation builds.

Added after acceptance Answer: sign every exe and installer from the first public release, with one identity. Facts the recommendation lacked: Artifact Signing needs a paid Azure subscription; individuals must be in the US or Canada, organisations in one of twelve listed places; certificates last three days, so every signature must be timestamped; signing does not stop SmartScreen warnings at once ("several weeks and hundreds of clean installs"), but it gets past Smart App Control. From a Mac or Linux: Jsign (third party, not on Microsoft's list), or Microsoft's GitHub Action on a Windows runner. Otherwise an OV certificate on a hardware key, or MSIX through the Microsoft Store, which Microsoft re-signs and whose individual registration is free. My Queue publishes as a US company, JayTeeSF LLC: eligible by country; the certificate name must be the LLC's validated legal name; Microsoft lists no minimum company age, but a failed validation is final, so an OV certificate (no age minimum under the CA/Browser Forum rules) is the fallback. Brief C1, C2, C3, C6, C8, C9, C10, C26, C32, and the LLC addendum.

5. Is the C++ and C# bar a requirement?

The coordinator read your "perhaps" remark that way. Please confirm. If yes, the ten items join what 607a must pass. Cost: those sixteen pieces of work, on top of the weeks in decision 1.

Added after acceptance Answer: yes, confirmed. No non-Microsoft language fully matches C# and C++; Rust's windows-rs, maintained in Microsoft's organisation, comes closest (Win32, COM and WinRT from metadata, writing COM and WinRT objects, WinUI 3 from code). Blocked for everyone outside Microsoft: the XAML compiler (MSBuild only, "not yet fully shared"), one WinUI DLL that "will not be OSS", WinUI without XAML ("an unsupported scenario"), and Microsoft's support list (C# and C++). So the bar is Rust's: the ten items in 607a, then COM, WinRT and WinUI 3 written in code. Brief A6, A9, A14, A17, A18, A19.
