How to operate a Cagents project.

The short version: record the human intent once, decompose it into goals and tasks, let refs carry current state, and use the CLI for every state-changing operation.

This is the companion to the architecture article. It intentionally lives at the repository root until reviewed.

1. Start from one participant file

Agents should not recursively ingest the repository. Each persistent participant gets one START.md that gives exact bootstrap commands and tells it where current truth comes from.

cd "$HOME/dev/generic_cagents"
git pull --rebase

cd "$HOME/dev/cagents"
git pull --rebase

export CAGENTS_ACTOR=orchestrator
export CAGENTS_SESSION="orchestrator-$(date -u +%Y%m%dT%H%M%SZ)"

bin/cagents doctor
bin/cagents use hey
bin/cagents presence start
bin/cagents update
bin/cagents graph audit
What the agent should not search for: no NOW.md, no task STATE.md, no participant STATE.md, no giant handoff journal. cagents update and cagents now derive current work from canonical objects and refs.

2. Record the overriding prompt

The project prompt is the durable answer to “what does the Maintainer ultimately want?” It is not a daily todo list.

bin/cagents project-prompt init \
  --project cagents \
  --id prompt_cagents_self_supervising_control_plane \
  --title "Build Cagents into a self-supervising control plane" <<'EOF'
Build Cagents so the Maintainer can supervise many persistent agents
without depending on agents remembering handoff documents.
EOF

If the intent evolves, append an amendment rather than silently rewriting history:

bin/cagents project-prompt amend --project cagents <<'EOF'
Presence must distinguish an intentional budget pause from a blocked task.
EOF

3. Decompose intent into goals

Goals are outcomes, not implementation steps. They can survive several failed approaches.

bin/cagents goal new \
  --project cagents \
  --id goal_supervision_watchdog \
  --title "Algorithmic supervision without permanent agent overhead" \
  --parent prompt_cagents_self_supervising_control_plane <<'EOF'
Current work, actor presence and unattended execution must be detectable
algorithmically before an agentic reconciler is involved.
EOF

Good goal

“Hosted control plane works from web and native clients.”

Observable outcome. Multiple tasks can advance it.

Weak goal

“Edit server.hey and add three routes.”

That is an implementation task, not the outcome.

4. Create tasks as stable objects

A task gets a stable directory. Its workflow state and owner are refs. This makes transitions narrow and explicit.

printf '%s\n' 'Implement deterministic heartbeat supervision.' | \
bin/cagents task new \
  --project cagents \
  --id heartbeat-supervision \
  --title "Heartbeat supervision" \
  --owner cagents-orchestrator \
  --status ready

Conceptually, creation produces:

tasks/heartbeat-supervision/TASK.md
refs/workflow/ready/heartbeat-supervision
refs/owner/cagents-orchestrator/heartbeat-supervision

Starting it moves one ref:

bin/cagents task status \
  --project cagents \
  --id heartbeat-supervision \
  --status in_progress

That should be published in the same Git transaction as other related ownership/lease mutations whenever the operation spans several refs.

Current state is a query

bin/cagents now --project cagents
bin/cagents task list --project cagents --status ready
bin/cagents refs heartbeat-supervision --project cagents
bin/cagents graph audit --project cagents
Invariant: every live task has exactly one workflow ref and exactly one owner ref unless the system explicitly models an unowned state.

5. Model waiting separately from ownership

Ownership answers “who is accountable?” Waiting answers “what must happen before progress can continue?” They should not be collapsed into one field.

task_X
  owner       → orchestrator
  waiting-on  → decision_Y
  goal        → goal_compiler
  workflow    → waiting

A single task can therefore remain accountable to one agent while it waits on the Maintainer, another agent, a decision, an external service, or a compiler fix.

6. Delegate execution without surrendering accountability

The task owner can fan work out to sub-agents. The sub-agents execute attempts; they do not automatically become the task owner.

bin/cagents dispatch \
  --project cagents \
  --task heartbeat-supervision \
  --label review-watchdog-edge-cases
PolicyMeaning
allEvery child run must succeed.
first-successAccept the first successful run; cancel/supersede the rest.
quorum:NRequire N agreeing/successful results.
best-ofCollect several results and evaluate them.
manualMaintainer or owner chooses.

7. Keep presence outside Git

Heartbeat is frequent operational state. It should not create a Git commit every few minutes.

# agent/session comes online
bin/cagents presence start

# refreshed periodically
bin/cagents presence heartbeat

# intentional cost-saving pause
bin/cagents presence pause --reason budget_pause --expected-return 'tomorrow'

# normal shutdown
bin/cagents presence stop --reason normal_shutdown

The local CLI keeps that state outside the coordination repo. The hosted service keeps the equivalent state in its operational database.

What the watchdog checks

1
Read only facts.
Workflow ref, owner, heartbeat age, lease, child runs, accepted result, latest durable activity.
2
Respect declared silence.
If the agent said a build or delegated run will take 45 minutes, do not nag it at minute 10.
3
Nudge the owner.
Ask the accountable agent to checkpoint or finish its own task through the CLI.
4
Escalate only ambiguity.
A reconciler examines evidence only when deterministic facts conflict or the owner cannot respond.

8. Do not auto-label silence as blocked

Observed factDerived operational health
Live heartbeat + recent activityhealthy
Owner intentionally pausedpaused-owner
Running presence but heartbeat expiredunattended
Two workflow refs for one taskinconsistent
Task waits on explicit decisionworkflow may be waiting; not a heartbeat problem
Keep dimensions separate. Workflow says what is happening to the work. Operational health says whether the coordination graph and live execution look healthy.

9. Use doctor, audit, reconcile and GC for different jobs

doctor
  Is the repository structurally valid?

audit
  Do deterministic facts look inconsistent?

reconcile
  What semantic repair is justified by evidence?

gc
  What cold history can be compacted without forgetting it?

The first two should be algorithmic. The third may need an agent. The fourth should follow explicit retention and strong-reference rules.

10. Keep high-cardinality metadata compact

Do not create one filesystem inode for every tag or backlink. Use physical refs for high-value operational edges; use compact metadata and derived indexes for descriptive relationships.

physical refs
  workflow
  owner
  waiting-on
  lease / active-run

compact metadata + derived reverse index
  tags
  taxonomy
  mentions
  historical backlinks

11. Treat Git commits as coordination transactions

Claiming a task may need to change several relationships:

remove  refs/workflow/ready/task_X
add     refs/workflow/in_progress/task_X
add     refs/owner/orchestrator/task_X
create  execution lease

Publish those changes as one valid graph transition, not four externally visible half-states.

12. The normal operating loop

bin/cagents update
bin/cagents task list --status ready
bin/cagents task status --id task_X --status in_progress
# do the work; dispatch bounded runs if useful
bin/cagents task event --id task_X --kind evidence < receipt.txt
bin/cagents task status --id task_X --status done
bin/cagents graph audit

13. What the Maintainer should see

The CLI and hosted UI should render the same underlying graph:

CAGENTS_NOW project=cagents
prompt=prompt_cagents_self_supervising_control_plane

ready=7
in_progress=2
blocked=1
waiting=2

ACTIVE / ATTENTION
in_progress  cagents-orchestrator  server-web-control-plane
waiting      orchestrator          compiler-native-coverage
ready        cagents-orchestrator  managed-repository-provisioning

No agent authored that status page. It is a view.
