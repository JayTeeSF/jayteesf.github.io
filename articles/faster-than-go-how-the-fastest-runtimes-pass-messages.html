Faster Than Go: How the Fastest Runtimes Pass Messages

Hey 0.99.597a shipped a new actor scheduler that already matches Go on most message benchmarks. Matching is not the goal. This article shows, in pictures, what one message actually costs, how Erlang, Go, Pony, Tokio, CAF, Akka and Seastar each keep that cost down, the one benchmark where Hey is still four times slower than Go, the deadlock we found and fixed on the way, and the plan for making parallel code the obvious way to write Hey.

Short version

  • 597a shipped the scheduler. One run queue per CPU core, a "run next" slot, work stealing, a lock-free mailbox, and per-thread caches of message nodes. Against the previous release it is 10 to 300 times faster on actor benchmarks.
  • It ties Go on most rows. Ring of 100,000 actors: 226 vs 227 ns per hop. Pairs: 17.2 vs 17.0 million messages per second. Spawning and joining a million actors: Hey is faster (0.82 s vs 1.43 s).
  • One row loses badly. When 8 senders all send to 1 receiver, Hey does 5 million messages a second and Go does 19 million. The cause is 8 cores fighting over one memory location.
  • What the fastest runtimes do differently: they batch (Pony, Akka), they keep data on one core (Seastar), they avoid copying (Pony's isolated references), and they schedule an actor only when its mailbox goes from empty to non-empty (Pony, and now Hey).
  • Hey's advantage is ownership. Hey's compiler already decides who owns each value. A message the sender will never touch again can be moved, not copied: Erlang must copy, Go shares and hopes. That is the next big step.

3. Why eight senders are slow

A Hey mailbox is a lock-free list: a sender adds its message with one atomic exchange on the mailbox's tail. One sender doing that is fast. Eight senders on eight cores all doing it to the same tail means the cache line holding the tail is bounced from core to core millions of times a second. Each bounce costs about as much as everything else in the send put together.

5. The deadlock we found on the way

The "run next" slot is a trick from Go and Tokio: when an actor sends a reply, the receiver goes into a one-actor slot on the same core, so it runs next while the message is still in that core's cache. It is the reason ping-pong got 15 times faster. It also caused the one real bug we found while testing 597a, reported by the RecallCoach app's test suite.

6. Hey's unfair advantage: knowing who owns the message

Erlang copies every message so processes can never share memory; that is safe and costs time proportional to the message's size. Go shares memory and trusts the programmer not to race. Pony and Rust move values whose single owner is proven by the type system. Hey already has the information Pony and Rust use: its compiler's middle layer (MIR) decides who owns every value, and the code generator obeys. When MIR proves that the sender never uses a message again, the send can hand over the pointer instead of copying.

7. The plan

  1. Batch the shared step in progress
    Fix 8-senders-to-1: link messages locally and splice them into the mailbox with one exchange; never wake a receiver that is already scheduled. Target: beat Go's 19.4 M/s.
  2. Timers per core next
    Sleeping actors go on a per-core timer wheel instead of borrowing a thread each, so 2,000 sleepers wake together at 100 ms.
  3. Move, don't copy next
    When MIR proves a message has one owner, send the pointer. This is where Hey can pass Go (no races) and Erlang (no copies) at the same time.
  4. A memory region per actor queued
    Free an actor's whole memory at once when it dies, as Erlang frees a process heap.
  5. Measure against the best in progress
    The Linux benchmark machine is adding Erlang, Pony and Rust Tokio versions of every actor benchmark (and CAF or Akka if feasible), so every row shows who is fastest. The scorecard will carry them.

Why this matters

If sending a message costs about as much as a function call, splitting work across actors stops being an optimisation you reach for late and becomes the normal way to write a program. Every Hey web server, job queue and data pipeline gets faster without the programmer doing anything different. That is the bar: parallel code should be the obvious choice because it is the fast choice.
