We Counted Our Own Primitives. The Answer Was Not Seven.

Hey’s maintainer can name the language’s core from memory: functions, actors, JSON-shaped objects, strings, numbers, booleans, conditionals, loops. A small core is not a vanity metric for us — it is the mechanism that stops our two compilers disagreeing with each other. So we counted. The count did not support the premise, and that is the useful result.

Status: research. Nothing here is implemented.

No construct has been removed; no reduction is recommended on these numbers alone. Every figure is conditioned on 470a and re-verified unchanged at 471a. Nothing was timed except one relayed measurement, labelled where it appears.

TL;DR

  • Verdict: the “we are very simple” premise does not survive its own census. We went looking for a confirmation and could not produce one, so the design decisions leaning on a small core need a different argument.
  • Thirteen runtime type tags where the list named five (hey_runtime.h:29-43), and thirteen independent lowering surfaces where the two-lane picture has two — ten of those confirmed by name at their cited lines for this piece. About six times as many places two compilers can disagree.
  • The census classified 103 constructs — 34 irreducible, 26 already sugar, 29 reducible, 14 with no defence we could find. Those four figures are the census’s own and are not independently re-verified here; the counts that are, are marked as such. Thirty-four is not seven, and neither is thirteen.
  • The one reduction we were asked to test does not pay. Jobs already collapses to a single call — but that call is a compiler intrinsic, not an actor. Rebuilding it over actors relocates retries, backoff, a dead-letter ring and a journal into Hey source, on a substrate measured at about 2,600x a plain array write.
  • Disclosed weakness: we killed our own headline. The census’s “single most serious finding” was labelled PROVED off four links of source reading; two commands refuted it. Auditing seven of our scans found two with a 100% false-positive rate and one that missed a whole population.
  • Check it yourself: every number carries a source line or a transcript, and the sharpest example is five lines of Hey you can run in both lanes.

Lowering

Turning a line of your program into the machine’s version of it. Hey has two programs that do this — one in C, one in Hey — because we are migrating from the first to the second. Every construct with its own lowering path is a place they can produce different answers for the same file, so counting paths is really counting risk.

What that costs, in five lines

Take the “numbers” row, on the default compiled lane at 470a and unchanged at 471a: 

let a = 1.5
says a * 2      # the script you run: 3.0    the binary you build: 2
says a - 2      # the script you run: -0.5   the binary you build: -1
says 1.5 * 2    # the script you run: 3.0    the binary you build: 3.0

The literal is right and the variable is wrong, three lines apart, silently, at exit 0. The rule deciding whether to do float arithmetic fires on seeing a float literal in the expression text, not on the operand’s type: the predicate answering it takes a single string and nothing else (runtime/heyc.c:8446), so it cannot consult the symbol table. It cannot be right, because it cannot ask.

A rule keyed to syntax stops applying the moment a value moves into a variable. Worth asking of any core, including yours: does each rule key on syntax, on static type, or on the runtime value? Listing it will not tell you; reading what it looks at will.

Jobs is already sugar. Just not over actors.

Could Jobs — the background-work feature — be syntax over actors, and leave the core? Half of that is already true: a jobs block collapses to one line before the compiler proper sees it (runtime/hey_repl.c:5243-5245), a single Jobs.define(...) call.

That call is not an actor. It is a compiler intrinsic, handed sixteen tuning parameters beyond the worker itself — autoscaling range, queue capacity and latency target, retries, backoff and maximum backoff, a dead-letter ring, an idempotency window, a journal with a compaction threshold, a partitioning function (runtime/heyc.c:2608-2631, plus a separate arm for the second compiler at runtime/heyc.c:8891-8914). Rewriting Jobs over actors deletes none of that. It moves it into Hey source, for users to maintain and get wrong.

Complexity relocated is not complexity removed

The classic small-core failure: push the hard parts into the standard library or the user’s code, then advertise the language as simple. A reduction is real only if you can say where the complexity went and show the destination is cheaper.

The destination is not cheaper. Our Linux seat measured an actor used as a mutable cell at about 2.6 µs (microseconds) per write, roughly 2,600x a plain array write (their measurement, their machine, 2026-07-29; not re-run here). So the proposal fails both tests we set before starting: the complexity does not disappear, and the substitute is slower. Every other candidate reduction in the census is marked UNMEASURED, because it is.

The one place we really are small

Not everything came back bigger. Hey has no closures — a structural commitment, not a missing feature. The rule sits at the ownership boundary in the runtime (runtime/hey_runtime.c:1333-1340): a value’s fields may only refer to values fully built before it, so no arbitrary capture, no laziness, no recursive values. The reference graph therefore cannot contain a cycle, which is what lets the runtime reclaim memory by reference counting with no cycle collector at all — the property Perceus (Reinking, Xie, de Moura and Leijen, PLDI 2021) identifies in naming mutable references the sole source of cycles in an immutable world. That is what a real simplification looks like: an entire subsystem does not exist because one construct does not. It is also the only number here that came in smaller than we expected.

The finding we retracted, at the same volume we made it

The census named one result “the single most serious finding” and labelled it PROVED. The compiler types any function whose name ends in ? as returning a boolean — by name, overriding the analysis it already did of the body (runtime/heyc.c:5344). Four links of source were read, each correctly, and the conclusion drawn: such a function returning a number prints true where the interpreter prints 21. We ran it. Two commands. 

fn lucky?(n)
  return n * 7
end
program
  says lucky?(3)
end

the script you run    -> 21
the binary you build  -> 21     (on the exact lane the census named)

No wrong answer. Three links held and the fourth did not. The rule is real and does fire, and the emitted intermediate code genuinely contradicts itself — one line declares an integer return, the next calls the function as a boolean — but the consumer of that code does not act on the contradiction. The defect is latent, not live: queued as cleanup, still worth deleting, because a rule that reads the identifier and overrules the compiler’s own analysis is waiting for a consumer that trusts it. Our Linux seat reproduced the refutation on their platform.

A verified chain is not a verified conclusion. Every link can be correct and the composition still wrong: a link’s correctness is a fact about the code, the composition’s is a fact about the runtime. Reading source shows a rule exists and fires; only running shows it changes the answer.

What our own scans got wrong

A census is made of scans, so we audited seven. Two had a 100% false-positive rate — one searched the emitted code for float instructions and returned four hits, all four an identifier that merely contained the letters; one searched for a keyword and returned six hits, all six English prose in comments. A third failed the other way and missed a population. A scan’s output looks identical whether or not it is right, and an audit that under-counts a defect class is worse than no audit: it gets quoted to justify deferring the rest. Publish a scan’s false-positive rate beside its output, and sample the list before publishing a rate.

The honest answer

This census either supports “we are very simple” or it does not. It does not: 34 irreducible constructs where the working number was about seven, thirteen runtime types where the list named five, thirteen lowering surfaces where the mental model had two. The tidy confirmation would have been the worse outcome, because the reason a small core matters here is that every extra lowering path is a place two compilers can quietly disagree — and this week’s defect ledger is made entirely of constructs that had more than one.

One consequence lands immediately. A design rule of ours — the one letting a handful of standard-library names be reached with a dot — was justified partly by the essence being small enough that the exceptions could not collide with much. That justification is not available on these numbers, so the rule has to stand on the collision argument instead: a separate measurement, and a separate article.
