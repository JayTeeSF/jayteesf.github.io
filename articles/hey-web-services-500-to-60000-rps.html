From 500 to 60,000 Requests per Second

How three real Hey web services — a prayer-journal app, a blind-ciphertext sync server, and a church scheduling tool — went from three-digit to five-digit requests per second in nine days, through measurement, application fixes, and sixteen verified toolchain releases. The last doubling arrived in a single night.

TL;DR

  • We built a load-test harness in Hey itself, cross-checked with oha, and profiled with macOS sample and disassembly.
  • Four mechanisms explained the entire gap to Go: a ~7 ms interpreter-delegation tax on stdlib calls, inverse worker scaling, no HTTP keep-alive, and per-request deep-copying in the dispatch path.
  • Application fixes bought 3–10×. The toolchain ladder (v0.99.394a–409a) bought the rest — including a memory-leak fix that cut worst-case RAM 481× (2,741 MB → 5.7 MB) and a dispatch fix that turned the old 8-worker penalty into the new optimum.
  • The per-request memory leak took five attempts to measure, and the fourth attempt was a retraction we had to retract. It is real: ~13,200 bytes per request, dead flat. It looked like it "came back" because macOS resident_size — the number almost every tool reports — excludes compressed pages. Measured on phys_footprint, which includes them, the growth never stops and the same server reads 11,991 MB committed while resident says 709 MB. Chart and the full sequence below.
  • Result: the 60,000 req/s target is crossed. war-room serves 83,300 req/s at 8 workers (p50 88 µs); the scheduling app serves 65,000–68,200 req/s (p50 60 µs) — both measured as lower bounds on a busy machine. Hey now beats a tuned 4-worker puma cluster on throughput and latency.

Addendum — 2026-07-26 (v0.99.423a–426a)

The numbers below this box are the story as of v0.99.418a. One day later, three compiler/runtime landings moved them substantially — all measured on a quiet box with the same protocol, evidence in the bench repo's dated log:

  • The construction quadratic is gone. JSON object literals now build through a compiler-managed transient: per-request clone work on a 46-key document fell 18.4× (2,280 → 124 clones/request), and the served route's throughput rose 3.8× (16,075 → 60,687 req/s, p50 61 µs). The acceptance gate for this fix was written, and watched failing, before the fix landed — it flipped green on the day.
  • The worker ladder moved again: 1 worker now serves 22,544 req/s at p50 42 µs (was 16,617 at 59 µs when this article was written); 8 workers reach 96,718 req/s — above this article's 83,300 headline.
  • Per-request retention improved ~53× on the same kill-pressure protocol (76,420 → 1,445 bytes/request), and on the object-building routes the per-request clone balance is now net-negative — the leak family's restart guidance below is historical for those paths.

What has not moved: effective concurrency is still pinned at min(connections, workers) — the accept model remains the binding constraint and the next target, with per-access boxing behind it.

Where we started

On hey v0.99.390a, our fastest service answered a 364-byte JSON health check at about 2,251 req/s with a median latency of 7 ms (16 connections, oha). Page routes in the scheduling app sat near 110 ms per render. A Go net/http baseline on the same machine served the identical payload at 61,972 req/s. The gap was not mysterious after measurement — it decomposed into four named mechanisms, each with a probe watching it.

Finding 1: the delegation tax

Compiled Hey code calling a pure-Hey stdlib: or pkg: function paid ~7 ms per call — each call wrote a temp file and spawned an interpreter subprocess. A handler making one such call caps at ~117 req/s. Killed in two stages: a runtime facade table (397a, ~1,100× for tabled calls) and a persistent interpreter sidecar (402a) that took the un-tabled canary from 4,479 µs to 56 µs.

Finding 2: inverse worker scaling

More workers made every server slower: 1 worker = 5,977 req/s; 8 workers = 1,589. Two real causes, fixed in sequence: macOS SO_REUSEPORT does not load-balance (396a made accept platform-aware), and the dispatch path deep-cloned route data per request per worker — including a hidden atomic reference-count fight on one shared cache line, proven by disassembly and fixed in 407a by borrowing instead of copying.

Finding 3: no keep-alive

The runtime hardcoded connection: close; every request paid a fresh TCP connection, and response bytes cost ~0.2 ms/KB in a copy-heavy write path. Fixed in 396a.

Finding 4: memory, and four wrong answers about it

One form of this finding is solid and easy to state exactly, because peak memory is straightforward to measure: a clone-and-abandon compiler bug made list building quadratic in memory, so 16,000 appends cost 2,741 MB before v0.99.406a and 5.7 MB after — a 481× reduction. That number has survived every re-check.

The other form — how much memory each served request retains — took five attempts, and one of those attempts was a retraction that itself had to be retracted. It is the most instructive part of this article, so the correction below is written at length rather than as a footnote.

Correction, five attempts deep (2026-07-25) — including one retraction we had to retract

This section has been wrong four times. Keeping the sequence visible is more useful than the final number, so here it is in order: (1) the fix leaves a flat working set; (2) no — about 500 bytes per request, still linear; (3) no — 13,340 bytes per request, on a continuous saturation run, identical across four consecutive releases; (4) no — there is no leak at all, that figure is the slope of a warm-up ramp that the runtime's own 6 GB self-termination ceiling was cutting short; and now (5) the leak is real after all, at ~13,200 bytes per request, and step 4 was wrong for a reason worth more than the number.

macOS resident_size excludes compressed pages. That is the whole mechanism. When the compressor starts evicting cold garbage, resident memory falls while the process's real commitment keeps climbing — the objects never move, the pages do. The kernel's own ledger, phys_footprint, includes compressed pages, and measured on that quantity the growth simply does not stop:

Over a single 30-second run, sampled every 250 ms, the footprint slope held at 13,202 bytes per request (range 12,938–13,414 across fourteen intervals, never once negative) while the resident slope went negative in half of them. At the end: 11,991 MB actually committed, 709 MB reported resident — a 16.9× under-report, with the runtime's 8,192 MB safety ceiling armed and completely blind to it. The two instruments agree to four significant figures for the first fourteen seconds, and then one of them starts lying.

So the "ramp that turns over" in the chart below is exactly what a real leak looks like through an instrument that cannot see compressed memory. The chart is kept, and relabelled, because the shape it shows is the trap itself.

What each wrong answer teaches, since this article is partly about method. The "~500 bytes" figure survived review because two independent measurements agreed on it — ours from a served server, the compiler team's from a synthetic fixture, within 15% of each other. Both were low, in the same direction, for unrelated reasons: agreement between two instruments blind in the same way is not corroboration, and it is more dangerous than a number nobody has checked. The fourth answer — the retraction — came from a genuinely good control: re-running the identical build and getting the opposite result, which does prove the difference was not between versions. It was still wrong, because both outcomes were being read through the blind instrument. And the argument I was proudest of was the worst one: "13,335 bytes × 3 million requests is 37.6 GB on an 18 GB machine that never swapped, therefore impossible." The multiplication was fine. The machine had 5.8 GB of swap in use before the run started, and I never looked. An arithmetic proof is only ever as good as the premise you didn't measure.

What we will state, and nothing beyond it: per-request retention is ~13.2 KB and holds linear to at least 939,000 requests (~12.4 GB); accumulation must bound somewhere at or above that point, and neither the location nor the mechanism of that bound has been measured.

We are deliberately publishing neither "unbounded" nor "bounded". Something clearly stopped a 67 GB trajectory — runs here reached five million requests at flat throughput, and every run's memory curve sits within 6% of every other when matched against request count, so they were all one regime. But we have measured a floor on where the bound is and nothing else about it. A bound whose mechanism nobody can name is not reassuring; it is suspicious. It might be a property of the program, or of how much RAM the machine happened to have free that night. We went looking for a recycler that would explain it and the one candidate in the runtime does not fit. This section has already published four confident numbers that turned out to be guesses wearing a number's clothes, and we are not adding a fifth. What none of it changes: ~13,200 bytes retained per request and roughly 85% of allocations never freed, over every request we have measured.

Application-side fixes (what you can do in your own code)

  • De-delegate hot paths. Handlers must not call pure-Hey stdlib per request. Local response helpers from builtins took the scheduling app's health check 408 → 3,933 req/s (9.6×) before any toolchain help arrived. (Post-sidecar, this matters ~100× less — but hot paths keep the discipline until the archive work retires the last ~80 µs tier.)
  • Right-size workers by measurement, and re-measure every release. The optimum flipped three times in nine days: 1 worker → 4 workers → 8 workers (now the fastest, at 10,400 req/s per worker). Guessing would have been wrong in every era.
  • Ship fewer bytes. esbuild-minifying a 35.5 KB client bundle to 25 KB bought +46% throughput on that route.
  • Use native packages, not subprocess fallbacks. Swapping per-query sqlite3 CLI forks for the native hey_sqlite3 package took pages from 103 ms to single-digit milliseconds.

Where Hey sits between Ruby and Go

Two days ago we published this ladder with Hey at 23.1K — ahead of WEBrick, behind a tuned puma cluster, 4.5× behind Go. One night of toolchain work later:

The honest read: Hey now beats the tuned puma cluster on both axes in absolute terms — 1.4× its throughput at a third of its median latency — and on this payload its median latency reads below Go's while Go keeps a 1.24× throughput lead. Nine days ago Hey lost to WEBrick. But absolute totals hide a fairness problem, so here is the per-worker view we intend to be judged on: puma extracts 14.5K req/s per worker from 4 workers, while Hey's 83K takes 8 workers — 10.4K per worker. Per unit of parallelism, the tuned Ruby cluster is still ahead, and most production boxes run 4 cores or fewer, where that efficiency is what you actually get. The 100K follow-up to this article will therefore compare apples to apples: throughput per worker at equal worker counts, all-cores versus all-cores against Go, and a 4-core-constrained lane matching real deployment hardware. We are aware that "83K on a busy box" and "beats Go on p50" are the kinds of numbers that deserve suspicion; that is why every cell asserts output bytes and success rate, why the fleet's full behavior gates ran green on the same binaries the same hour, and why the remaining gap items are named in public rather than hand-waved.

What it cost: nothing was free, everything was measured

Three habits made the difference between this and a lucky benchmark run:

  • Pre-registered predictions. Before each fix landed we wrote down what the probes should read afterward. The 8-worker prediction ("crater dies, per-worker efficiency flattens") was confirmed 16.3/9.4/6.7/1.5 → 17.5/14.8/14.3/10.4 K req/s per worker. When a theory failed its pre-registered test (the worker "wake-storm" story), it died in public and the real mechanism was found by disassembly.
  • Output assertions on every cell. The night's most instructive failure: a "fast baseline" binary that measured 2.3 ms turned out to be silently dead — it compiled, exited 0, and did nothing. Chasing that corpse produced the deterministic reproducer for a silent-miscompile class, which is now structurally impossible to ship thanks to the new compile guards. The performance work paid for correctness fixes it had no right to expect.
  • Two independent measurement lanes. Every headline number in this article was reproduced by a second session with its own instruments before being written here.

How the collaboration worked

Two AI seats shared one machine: a benchmark seat owning harnesses, probes, profiles, and the published numbers; and a compiler-orchestrator seat landing verified toolchain slices (peaking at nine concurrent implementer/red-team/audit agents). They exchanged findings through append-only relay files — measured claims with reproduction commands, not vibes. Profiles named upstream fixes; landing notes predicted probe readings that were confirmed to the microsecond; wrong theories were killed by pre-registered falsification runs; and when one seat's baseline turned out to be a dead binary, the correction shipped with the same prominence as the original claim. Every number in this article is reproducible from the repos' committed probes and dated evidence logs.

What's next

Go's throughput lead is down to 1.24× on this payload, and the remaining items are named: big-list construction is still slower than it should be (the memory fix landed; the speed fix is queued), sustained multi-minute saturation surfaced a stability class that is being hardened before we publish soak-duration numbers, and the last ~80 µs delegation tier falls to the precompiled stdlib archive. Nine days ago the plan said "60,000 req/s is not speculative." Today it is a measurement. The plan now says Go parity — and given the week it has had, we are not inclined to argue with it either.
