Build a real command-line tool in Hey

You'll write wordfreq, a small tool that finds the most common words in a folder of text files. Along the way you'll read flags, walk files, count with a map, run another program, report errors with the right exit code, test it, and turn it into one native binary you can copy anywhere.

The short version

  • hey wordfreq.hey runs your tool like a script. The first run compiles it to native code and caches it; later runs start the cached program in a few milliseconds.
  • hey build wordfreq.hey -o build/wordfreq makes one small executable that needs only the system C library.
  • stdlib:Cli gives you flags, typed values and a help screen; Files, Process and Text do the rest.
  • Two gaps, both shown below: Hey has no statement that sets an exit status yet, and flag values need --top=5, not --top 5.

You are here Guide 1 installed Hey and ran hello. Guide 2 added packages. This guide builds a tool. Guide 4 builds a web server, guide 5 builds apps, guide 6 ships them.

Every command here is run by Hey's documentation test, and its output must match what you see. A line with ... stands for text left out.

1. The tool, in one picture

Every command-line tool is the same shape: arguments come in, some files get read, something gets computed, text comes out. wordfreq is that shape with nothing extra.

Hey in five words. let makes a name, set gives it a new value, says prints a line, program ... end is where the run starts, and [...out, x] is a new list with x added on the end. Values never change in place; you make a new one and set the name to it.

Make a folder with two short text files to count:

The quick brown fox jumps over the lazy dog.
The dog is asleep.
A fox is a dog? No, a fox is not the dog.

The project is two Hey files. Open each one and save it; the sections below explain them piece by piece.

lib/count.hey: the pure part, text in and counts out 
# The pure part of wordfreq: text in, counts out. No files, no flags.
import 'stdlib:Text'
import 'stdlib:Collections'

module WordCount
  # Lower-case a word and peel punctuation off both ends.
  fn clean(word)
    let w = Text.lower(word)
    let marks = ".,;:!?\"'()[]{}<>*_-#`"
    while len(w) > 0 and Text.contains?(marks, slice(w, 0, 1))
      set w = slice(w, 1, len(w) - 1)
    end
    while len(w) > 0 and Text.contains?(marks, slice(w, len(w) - 1, 1))
      set w = slice(w, 0, len(w) - 1)
    end
    return w
  end

  # Add every word in `text` to the `counts` map and return the new map.
  fn add(counts, text)
    let out = counts
    for raw in Text.words(text)
      let w = WordCount.clean(raw)
      if len(w) > 0
        if has?(out, w)
          set out = put(out, w, out[w] + 1)
        else
          set out = put(out, w, 1)
        end
      end
    end
    return out
  end

  fn by_count_then_word(left, right)
    return Collections.compare_chain([
      Collections.compare_desc(left[1], right[1]),
      Collections.compare(left[0], right[0])
    ])
  end

  # The `n` most common words as [word, count] pairs, ties broken A to Z.
  fn top(counts, n)
    let pairs = Collections.sort(entries(counts), WordCount.by_count_then_word)
    return Collections.take(pairs, n)
  end
end
wordfreq.hey: the program, with flags, files and output 
#!/usr/bin/env hey
# wordfreq: the most common words in the text files under a folder.
import 'stdlib:Cli'
import 'stdlib:Files'
import 'stdlib:Process'
import 'stdlib:Text'
import 'stdlib:Collections' exposing: [first] forms: [:dotted]
import './lib/count.hey'

fn schema()
  return Cli.schema('wordfreq [FOLDER]', 'Count the most common words in text files.', [
    Cli.option('top', 'int', 10, 'how many words to show'),
    Cli.option('ext', 'string', '.txt', 'which file ending to read'),
    Cli.option('git', 'bool', false, 'only read files git tracks'),
    Cli.option('help', 'bool', false, 'show this help')
  ])
end

# Hey has no statement that sets an exit status yet, so hand the text
# to /bin/sh, which prints it and exits with the status we choose.
fn finish(text, status)
  Process.exec_env_argv({}, ['/bin/sh', '-c', 'printf "%s" "$1"; exit "$2"', 'wordfreq', text, status.to_s])
end

fn files_from_git(folder, ext)
  let run = Process.run_argv(['git', '-C', folder, 'ls-files', '*' + ext])
  if !run.ok
    return []
  end
  let out = []
  for name in Text.lines(run.stdout)
    if name != ''
      set out = [...out, Files.join(folder, name)]
    end
  end
  return out
end

program
  let parsed = Cli.current()
  let checked = Cli.validate(parsed, schema())
  if !checked.ok
    finish(checked.error + "\n" + Cli.help(schema()) + "\n", Cli.exit_status(checked))
  end
  if Cli.typed_flag(checked, 'help', false)
    finish(Cli.help(schema()) + "\n", 0)
  end

  let folder = Cli.parsed_positionals(parsed).first('.')
  if !Files.directory?(folder)
    finish('wordfreq: no such folder: ' + folder + "\n", 1)
  end

  let ext = Cli.typed_flag(checked, 'ext', '.txt')
  let paths = []
  if Cli.typed_flag(checked, 'git', false)
    set paths = files_from_git(folder, ext)
  else
    set paths = Files.files(folder, ext)
  end

  let counts = {}
  for path in paths
    set counts = WordCount.add(counts, Files.read_text(path))
  end

  says "#{paths.length} files, #{entries(counts).length} different words"
  for pair in WordCount.top(counts, Cli.typed_flag(checked, 'top', 10))
    says "#{Text.pad_left(pair[1].to_s, 6, ' ')}  #{pair[0]}"
  end
end

Run it:

$ hey wordfreq.hey --top=5 sample
2 files, 13 different words
     4  dog
     4  the
     3  a
     3  fox
     3  is

2. Read flags with Cli Works today

You describe your options once, as data. Cli turns that description into a help screen and into checked, typed values. Nothing to subclass, no annotations.

fn schema()
  return Cli.schema('wordfreq [FOLDER]', 'Count the most common words in text files.', [
    Cli.option('top', 'int', 10, 'how many words to show'),
    Cli.option('ext', 'string', '.txt', 'which file ending to read'),
    Cli.option('git', 'bool', false, 'only read files git tracks'),
    Cli.option('help', 'bool', false, 'show this help')
  ])
end

Then the top of program reads the real arguments and checks them:

  let parsed = Cli.current()                    # reads argv and splits flags from the rest
  let checked = Cli.validate(parsed, schema())  # a Result: ok, or which flag was wrong
  ...
  let folder = Cli.parsed_positionals(parsed).first('.')   # first item, or '.' if there is none
  ...
  Cli.typed_flag(checked, 'top', 10)            # already an Int, not text

.first('.') works because the file has import 'stdlib:Collections' exposing: [first] forms: [:dotted]: that import lets you call first(list, fallback) as list.first(fallback). (Imports are covered in Modules, imports and exports.)

The help screen comes for free:

$ hey wordfreq.hey --help
Usage: wordfreq [FOLDER] [options]
Count the most common words in text files.
Options:
  --top <int>  how many words to show default=10
  --ext <string>  which file ending to read default=.txt
  --git  only read files git tracks default=false
  --help  show this help default=false

A bool option is switched on by its name alone (--git) or given =true/false/yes/no/on/off/1/0; --no-git switches it off. Anything that doesn't start with a dash is a positional argument (here, the folder).

Write values with =: --top=5, not --top 5. Partly works Cli.parse reads flags before it sees your schema, so it can't tell that --top takes a value. It treats --top as a switch and 5 as the folder, and then validation says the flag isn't an Int:

$ hey wordfreq.hey --top 5 sample; echo "exit status: $?"
--top expects int
Usage: wordfreq [FOLDER] [options]
...
exit status: 64

The older list helpers (Cli.flag(args, 'top', 10)) do accept --top 5, so the two halves of Cli disagree.

The full Cli, Files, Process and Env function lists live in the standard library reference.

3. Walk files and count with a map Works today

Files.files(folder, '.txt') returns every file under the folder that ends in .txt, sorted, searching subfolders too. Files.read_text(path) reads one file into a String.

The counting lives in its own module, lib/count.hey, so the tests can call it without touching the disk. This is its heart:

  # Add every word in `text` to the `counts` map and return the new map.
  fn add(counts, text)
    let out = counts
    for raw in Text.words(text)
      let w = WordCount.clean(raw)
      if len(w) > 0
        if has?(out, w)
          set out = put(out, w, out[w] + 1)
        else
          set out = put(out, w, 1)
        end
      end
    end
    return out
  end

What would you predict? Hey values never change. put(out, w, 1) returns a new map with one more entry. So does counting a 10,000-word file copy the map 10,000 times?

Answer

No. The compiler's middle stage (MIR, the step that decides when values are created and freed) tracks who still holds each value. In set out = put(out, ...) the old out is never used again and nobody else holds that map, so put changes it in place.1 You write code that reads as if nothing changes; the machine does the cheap thing. The full story is in Values, memory and Strings.

Back in wordfreq.hey, the main loop is four lines:

  let counts = {}
  for path in paths
    set counts = WordCount.add(counts, Files.read_text(path))
  end

4. Run another program Works today

With --git, wordfreq asks git which files it tracks instead of walking the folder. Process.run_argv takes the command as a list of words. There's no shell in between, so spaces and quotes in file names arrive exactly as written.

fn files_from_git(folder, ext)
  let run = Process.run_argv(['git', '-C', folder, 'ls-files', '*' + ext])
  if !run.ok
    return []
  end
  let out = []
  for name in Text.lines(run.stdout)
    if name != ''
      set out = [...out, Files.join(folder, name)]
    end
  end
  return out
end

The answer is a record: ok, stdout, stderr and the child's status. Make the sample folder a git repository that tracks only a.txt, and try it:

$ git -C sample init -q && git -C sample add a.txt
$ hey wordfreq.hey --git --top=3 sample
1 files, 10 different words
     3  the
     2  dog
     1  asleep

If a child might hang, use Process.run_argv_timeout(args, 30_000): it kills the whole process group after 30 seconds. For a long-running child you talk to, Process.spawn gives you its stdin and stdout handles.

5. Errors and exit codes

Hey separates two kinds of failure, and the difference matters for a tool.

Expected failures are values. A missing folder or a bad flag is something a user will do. Return a Result (Result.ok(v) or Result.error_with(code, message)), check .ok, and print something helpful. Cli.validate already does this for flags.

Bugs stop the program. fail 'message', or any runtime error, stops the unit of work at once: in a server that's one request, in a tool it's the whole process. It prints the message and exits with status 70. There's no try/catch; that's a ruled design choice (fail fast, Erlang style).

program
  says 'checking...'
  fail 'the config file is missing'
end
$ hey fail_demo.hey; echo "exit status: $?"
checking...
hey error: the config file is missing
exit status: 70

The gap: choosing your own exit code Partly works

Shell scripts and CI care about exit codes: 0 for success, 1 for "found a problem", 64 for "you typed it wrong". Hey has no statement that sets the process exit status yet. A program that ends normally exits 0; fail exits 70.

Cli can already work out the right number for you: Cli.exit_status(checked) gives 0 for success and 64 (the usual "bad usage" code) for a missing or malformed flag. Nothing applies that number to the process, though. The working pattern is to build the whole output as one String and hand it to /bin/sh, which prints it and exits with the code you pick. Process.exec_env_argv replaces the Hey process, so nothing printed earlier can be lost:

fn finish(text, status)
  Process.exec_env_argv({}, ['/bin/sh', '-c', 'printf "%s" "$1"; exit "$2"', 'wordfreq', text, status.to_s])
end

wordfreq passes Cli.exit_status(checked) to finish for a bad flag, and 1 for a missing folder:

$ hey wordfreq.hey --top=many sample; echo "exit status: $?"
--top expects int
Usage: wordfreq [FOLDER] [options]
...
exit status: 64
$ hey wordfreq.hey no-such-folder; echo "exit status: $?"
wordfreq: no such folder: no-such-folder
exit status: 1

It works, but it costs a /bin/sh start and needs a POSIX shell on the host. Treat it as a stopgap.

6. Test it

Hey has two kinds of test, and a tool usually wants both.

KindWhat it checksHow you run it
spec blockThe whole program's stdout, stderr or exit status (a golden test)heyc --test file.hey
stdlib:MinispecIndividual values: to_equal, to_include, to_be_error, and morecall it from a program; pair it with a spec block

A spec block runs the program with no arguments, so put the tests next to the pure module, not next to the tool. Save this as count_spec.hey:

spec 'WordCount cleans, counts and ranks words'
  expect stdout "WordCount: 5 passed, 0 failed\n"
end

import 'stdlib:Minispec'
import './lib/count.hey'

program
  let s = Minispec.suite('WordCount')
  set s = Minispec.to_equal(s, 'strips punctuation', WordCount.clean('"Hello!"'), 'hello')
  set s = Minispec.to_equal(s, 'keeps inner apostrophes', WordCount.clean("don't"), "don't")
  let counts = WordCount.add({}, 'the cat and the hat. The end')
  set s = Minispec.to_equal(s, 'counts case-blind', counts['the'], 3)
  set s = Minispec.to_equal(s, 'top word first', WordCount.top(counts, 1), [['the', 3]])
  set s = Minispec.to_equal(s, 'ties go A to Z', WordCount.top(counts, 3), [['the', 3], ['and', 1], ['cat', 1]])
  Minispec.report(s)
end

Run the file as an ordinary program to see the report, then as a test:

$ hey count_spec.hey
WordCount: 5 passed, 0 failed
$ heyc --test count_spec.hey
PASS: WordCount cleans, counts and ranks words

A Minispec suite is a plain value: each assertion returns a new suite with one more result in it. Minispec.report prints the totals, and the spec block checks that line. For a CI job without the golden harness, Minispec.finish(s) prints the report and exits 70 if anything failed.

7. Script or binary?

You've been running hey wordfreq.hey. That's the script path: Hey compiles the program to native code the first time and keeps the result in a cache keyed by the source and everything it imports. Change any imported file and the next run recompiles. Nothing goes stale.

The first line of wordfreq.hey is #!/usr/bin/env hey, so you can also make the file itself executable:

$ chmod +x wordfreq.hey
$ ./wordfreq.hey --top=3 sample
2 files, 13 different words
     4  dog
     4  the
     3  a

Or build one binary to copy to another machine, a container, or a bin/ folder:

$ hey build wordfreq.hey -o build/wordfreq
built .../build/wordfreq
$ ./build/wordfreq --top=3 sample
2 files, 13 different words
     4  dog
     4  the
     3  a

The binary links nothing but the system C library. A warm script start costs a few milliseconds more than starting the binary directly: that's the check that no source changed. Guide 6 shows what's inside the binary and how to build for Linux.

UseWhen
hey tool.hey or ./tool.heyYour own scripts, tools you edit often, anything where "always runs the latest source" matters more than a few milliseconds.
hey build tool.hey -o build/toolAnything you copy elsewhere, put in a container, sign, run from a supervisor, or benchmark. The build fails before deploy, never at first run.

8. Ship it as a package command Works today

A package can declare commands in its hey-package.json. Anyone who depends on the package gets the command, checked against the lock file's hashes every time it runs:

  "commands": {
    "wordfreq": "bin/wordfreq.hey"
  }

Guide 2 installs a package with a command and runs it; its last section starts your own package.
