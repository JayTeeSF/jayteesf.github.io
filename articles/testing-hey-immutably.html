Hey language · design note · 22 August 2026

Testing Hey, immutably

Hey has no mutable instance state and no closures — the two things almost every test framework leans on for fixtures. So we chose the framework: minitest's assertion vocabulary sitting on an immutable engine modeled on Elixir's ExUnit, where a fixture is just data you pass as an argument, and a spec costs a production build exactly nothing.

Design decided, not yet built. Everything in this note is the ruled design — the maintainer's decision, not shipped code. Implementation is deferred behind compiler completion and coupled to the module system for the separate-file convention; nothing here is built yet. (R4 status; spec-architecture: "Nothing here is built")

TL;DR

  • One decision, adopted. Hey's spec framework is minitest's assertion base + the immutable ExUnit model — the maintainer's ruling after the survey found Elixir solves the fixture and actor gaps immutably, with QuickCheck-style value generators closing the third. (R4)
  • Fixtures without mutation or closures. A fixture is a builder fn that returns a fresh immutable value, or a context map a setup block returns and the runner threads into each case — ExUnit's model, no @ivars, no capture. (R4, survey §1.4)
  • Actors get expect_receive … within N ms — you wait for the message, never sleep; assert. (R4, spec-architecture B5)
  • Properties use value generators, not closures — property "…" for x in integers(), generators as combinator values from the QuickCheck/Hypothesis lineage. (R4, survey §1.3)
  • A spec lives in any file. A dedicated foo_spec.hey that imports foo is a supported convention, not a requirement; inline specs stay first-class, and specs reach privates only via a co-located internal-test hatch. (R2 + amendment, R6/D44-a)
  • Production pays nothing. Every lane must parse a spec block, but only the test runner executes it — spec code is conditionally compiled, like Rust's #[cfg(test)]. (R5)
  • No mutable-class module needed. R3's "try immutable first" holds: the design makes specs fully immutable, so the opt-in mutable sublanguage is never required to test Hey code. (R3, R4)

How to read the citations: R# = a maintainer ruling; A# / B# = the spec-architecture proposal (parts A and B); §# = a section of the framework survey; O# = an open question in the proposal (Part C).

Every test framework you have ever used makes the same quiet assumption: that setup can stash something in a mutable slot — an @ivar, a this.x, a variable captured by a beforeEach closure — and each test can read it back. That assumption is impossible in Hey. There is no mutable instance state and there are no closures to capture the fixture. (survey §1.4, spec-architecture A3)

The tempting fix would be to bend the language: bolt on a mutable, class-based sublanguage just so specs can behave like xUnit. The maintainer's ruling was the opposite — Hey's core stays immutable; a mutable class flavor is at most an opt-in module and a last resort, and specs must try to test the real code immutably first. (R3) This note is the story of how that "try first" is answered on paper — the design is decided, not yet built — and it has a single through-line:

The design gives Hey a full-featured test framework — minitest's assertions over ExUnit's immutable engine — without one line of mutable state or one closure, and without slowing production down at all.

The base: minitest's assertions, kept; its fixtures, dropped

The survey treated minitest as the leading candidate and asked the blunt question: is it sufficient? The verdict was "almost." minitest is the right base and covers roughly 80% as-is, but it is not sufficient alone — it leaves exactly three gaps, and the load-bearing fix is to keep minitest's assertion face while replacing its fixture face. (spec-architecture B0)

minitest itself makes this clean, because it already ships two faces over one engine: the classic Minitest::Test subclass, and a spec face (describe/it/_(x).must_equal). Adopting minitest therefore does not force a DSL choice — and its stated philosophy, "minitest is ruby … it avoids magic," is exactly the ethos Hey wants. (survey §1.1/§1.2) What Hey keeps is the assertion vocabulary; what it refuses is the one piece built on mutation.

Which minitest pieces Hey adopts, adapts, or drops — condensed from the sufficiency verdict. (spec-architecture B0)

The mapped assertion set is small and shaped by Hey's own history. expect X to_equal Y is the workhorse: value equality — not type equality — is the semantics, because in Hey casts convey type, so equality compares the values themselves, and over immutable values that is total and well-defined. expect X to_be true/false covers truthiness. expect X to_be_close Y within D — mapping minitest's assert_in_delta — is a float-tolerance matcher that B2 calls essential (citing the survey), given Hey's scale(2.5, 2)-class float defects. And expect X to_raise "…" / to_fail covers the error path, subsuming today's expect error. (spec-architecture B2, O4)

Fixtures as data, not state

Here is the load-bearing change, and it is smaller than it sounds. Three surveyed languages already do fixtures with neither mutable state nor closures, and Hey borrows from all three: Go/Rust (a fixture is just a helper function you call at the top of a test), ExUnit (setup returns an immutable context map that the runner threads into each test as an argument), and pytest (fixtures injected by parameter name). (survey §1.4, A4) ExUnit is the closest living relative — an immutable, actor language that already proved this works. (A5)

The default is the plainest form: a builder fn that returns a fresh value. Because values are immutable, "fresh per test" is automatic — there is nothing to reset.

# the builder fixture — no framework feature at all
fn fresh_account() -> deposit(open_account(), 100) end

spec "BankAccount"
  it "withdraws"
    let a = fresh_account()
    expect balance(withdraw(a, 30)) to_equal 70
  end
end

When several cases share setup, the context map takes over — ExUnit's exact model. A setup block returns an immutable map; the runner hands it to each it as a named value. No @ivar is written, no closure captures anything — the fixture is data passed as an argument. Because the value is immutable, one map is safe to hand to every case; there is nothing to copy.

spec "BankAccount"
  setup
    { account: fresh_account(), rate: 0.05 }   # returns an immutable map
  end
  it "reads the seeded balance" using ctx
    expect balance(ctx.account) to_equal 100
  end
end

The diagram below is the whole idea. In a mutable framework the arrow between tests goes through a shared slot, which is why tests leak into each other and need resetting. In Hey the arrow is a value, passed to each case; there is no shared slot to leak — and no copy either, because a shared immutable value is safe to hand around.

A third form falls out for free: table tests. A table is an immutable list of value-tuples, and running one case per row needs no closures — just iteration. This is the most Hey-native shape, and it matches the spirit of the existing corpus.

spec "Math.scale"
  each [ (2, 2.5, 5.0), (4, 0.5, 2.0), (3, 3, 9) ] as (x, f, want)
    it "scales #{x} by #{f}"
      expect scale(x, f) to_equal want
    end
  end
end

And there is no teardown. pytest's yield-teardown exists to release side-effecting resources; immutable Hey values have nothing to release. If a spec touches an actor or Jobs resource, teardown is the runtime reclaiming it, not a user callback. (spec-architecture B3, A8)

The two remaining gaps

After fixtures, two of the three gaps are left: minitest has no message-passing story and no property layer. Both are closed with patterns from ExUnit and QuickCheck — again, neither needs a closure or a mutable cell.

Actors: wait for the message, never sleep

The naive actor test — sleep(100); assert mailbox empty — is the trap. The disciplined replacement is ExUnit's assert_receive, adopted here as expect_receive pattern within N ms: the spec spawns the actor, sends it a message with the test as the reply target, and blocks until a matching reply arrives or the timeout fails it. It is deterministic because it waits for the event, not the clock. (spec-architecture B5; survey §1.7) The eight Erlang/OTP shapes back this up — assert the next message's identity, assert an invariant after synchronized chaos, probe liveness by draining the mailbox — and Hey needs no mocking subsystem: you substitute a collaborator by passing a value and verify interactions by asserting on what lands in a test-controlled mailbox. (survey §1.8, A6)

Properties: generators are values, not closures

The highest-value oracle-free add for a compiler is property-based and metamorphic testing, and it fits Hey because QuickCheck-style generators are combinator values (integers(), lists(...), corpus_programs()) returning immutable data — no capture. Shrinking operates on the generated data, not on a closure. This is the gap minitest leaves entirely; Hey closes it from the QuickCheck/Hypothesis lineage. (spec-architecture B0 gap 3, B4/B7; survey §1.3, A7)

spec "scale properties"
  property "scaling by 1 is identity" for x in integers()
    expect scale(x, 1) to_equal x
  end
  property "comments don't change output" for p in corpus_programs()
    expect compile(strip_comments(p)) to_equal compile(p)   # metamorphic
  end
end

That second block is a metamorphic relation — "adding a comment must not change compiled output" — the single highest-value class of check for Hey's own compiler. It is phased after the fixture work, but the surface is already closure-free. (spec-architecture B4; survey §1.3)

Where specs live, what happens to the ones we have, and what they cost

Three rulings settle placement, the existing corpus, and cost — and they matter as much as the engine.

A spec lives in any file (R2). The target architecture is a dedicated file that imports the code under test — foo.hey alongside a foo_spec.hey that does import './foo.hey' exposing: [names] — which reuses the ordinary module system, no new import mechanism. But the same-day amendment is emphatic: the separate file is a supported convention, not a restriction. A spec block may live inline with the code it tests, and inline specs stay first-class. The design must neither prohibit nor force separate spec files. As for reaching a module's privates, that question is settled too: a spec sees only the exposes surface an ordinary importer sees, and reaches privates only via a co-located internal-test hatch — Rust's #[cfg(test)] / Go's same-package idiom, and it works for inline specs as well. (R2 + amendment; R6/D44-a; spec-architecture B1)

The tests we already have are reframed, not rewritten (B6). Hey already carries a 786-file specs/language/*.hey golden corpus. Today those files use the declarative golden harness — the form that accepts only expect stdout/stderr/error/exit — and the new to_equal assertion vocabulary is the destination, not today's reality. The ruling is that this corpus becomes one kind of expectation among several — the declarative golden form living alongside the new value-assertion, actor, and property forms — rather than being thrown out and re-authored. The runner's exact form is still an open question. (spec-architecture A2, A9/B6; survey §0)

A spec costs production nothing (R5). This corrects an earlier framing. The interpreter skipping spec blocks is not a defect — it is by design. Spec blocks are conditionally compiled and executed only in test mode, the way Rust uses #[cfg(test)] and Go uses build tags. A production build emits no spec code and pays nothing. The one real requirement is that every lane must still parse a spec block correctly — find it and its end — so it never breaks the surrounding code. The only genuine defect would be a lane mis-parsing the block, never a lane declining to run it in production. (R5)

The payoff: no mutability required

Put the pieces together and R3's cautious "try immutable first, use the mutable module only as a last resort" turns out to have a clean answer in the design: it was never needed. Fixtures are builder functions and immutable context maps; actor checks wait for messages; generators are values; isolation is nearly free because there is no shared mutable state to reset. Every dimension of the framework is closed with a closure-free, immutable-safe mechanism drawn from a language that already ships it — ExUnit above all, then Go/Rust and pytest, with QuickCheck-style generators for properties. (spec-architecture B7, R4)

So the mutable-class sublanguage that R3 held in reserve is not needed for testing Hey. That is the whole win, stated by the ruling that adopted the design: specs are fully immutable, and Hey's core stays immutable with them. (R4)
