Workers, Jobs and streams: parallel work without the plumbing

Index Reference 1: Language Reference 3: Actors and failure Reference 4: Workers, Jobs, streams Reference 5: Distributed Reference 7: Native code Reference 9: Performance

Resize a thousand images. Import a CSV file one row at a time. Send a welcome email that must not go out twice. None of these needs a long-lived owner of state, so an actor is the wrong shape. Hey gives you three tools for this: a worker pool for raw parallel work, a Job when you want receipts, retries and results, and a stream when your work is a chain of map and filter.

2. Worker pools

A worker handles one immutable message, keeps nothing between messages, and runs as a lightweight turn on the same thread pool actors use. No import is needed. Works today

workers_quickstart.hey

worker Double(message)
  send message.reply_to, message.value * 2
end

actor Collector(expected)
  state seen = 0
  state total = 0
  receive value
  set seen = seen + 1
  set total = total + value
  if seen == expected
    says total
    exit
  end
end

program
  let collector = spawn Collector(4)
  let pool = workers(Double, count: 2, capacity: 8)

  for value in [1, 2, 3, 4]
    if !pool.enqueue({reply_to: collector, value: value})
      fail 'worker queue is full'
    end
  end

  join collector
  says pool.status().completed
  let stopped = pool.stop()
end

Run it (exact command and output)

$ hey workers_quickstart.hey
20
4
$ echo $?
0
  • A worker takes exactly one message; it may use let, call functions, do I/O, return a value or send messages. It cannot declare state or use receive.
  • workers(Worker, count: 8, capacity: 1024): count is how many may run at once, capacity is how many may wait. count: 8 does not create eight threads.
  • A bare pool throws return values away. To get an answer back, send it to an actor (as above) or use a Job.
  • pool.stop() refuses new messages, drops queued ones that never started, lets running ones finish.

Backpressure: a full queue says no

Backpressure means the system pushes back on a producer that is going faster than the work can be done, instead of storing an ever-growing pile. pool.enqueue(msg) returns true only when the bounded queue accepted the message. It never grows a hidden queue. Workers.await_idle(pool, timeout_ms) from stdlib:Workers waits until nothing is queued or running. Works today

Predict it. One worker, a waiting room of 2, six messages sent as fast as possible. How many are accepted?

backpressure.hey

import 'stdlib:Workers'

worker Nap(ms)
  sleep ms
end

program
  let pool = workers(Nap, count: 1, capacity: 2)
  let accepted = 0
  let refused = 0
  for ms in [30, 30, 30, 30, 30, 30]
    if pool.enqueue(ms)
      set accepted = accepted + 1
    else
      set refused = refused + 1
    end
  end
  says 'accepted=' + accepted + ' refused=' + refused
  let status = Workers.await_idle(pool, 2000)
  says 'queued=' + status.queued + ' active=' + status.active + ' completed=' + status.completed + ' rejected=' + status.rejected
  let stopped = pool.stop()
end

3. Jobs: work with a receipt

A Job wraps a worker pool and adds what operations people ask for: a receipt per message (a small record that names this piece of work so you can ask about it later), kept results, retries, cancellation, dead letters, metrics. Jobs.define(name, Worker, options…) builds one; Job.enqueue returns a receipt; Jobs.result(job, receipt, timeout_ms) waits for its outcome.2 Works today

tour_05_jobs.hey

worker Thumbnail(image)
  return {path: 'thumbs/' + image.id + '.jpg'}
end

program
  let Thumbnails = Jobs.define('TourThumbnails', Thumbnail, count: 2, capacity: 8)
  let receipt = Thumbnails.enqueue({id: 'cover'})
  if !receipt.accepted
    fail 'tour job queue is full'
  end

  let result = Jobs.result(Thumbnails, receipt, 5000)
  if !result.ok
    fail result.error
  end

  says result.value.path
  says 'completed=' + Thumbnails.status().completed
  let stopped = Thumbnails.stop()
end

Run it (exact command and output)

$ hey tour_05_jobs.hey
thumbs/cover.jpg
completed=1
$ echo $?
0

A timeout on Jobs.result only bounds your wait; it never kills a handler that is already running.

The job declaration

When a Job's name and settings are fixed, declare it at the top level. It is only syntax: it becomes the same Jobs.define call. Jobs.await_all(job, receipts, timeout_ms) collects results in order and fails on the first one that did not succeed (Jobs.require does the same for one receipt). Partly works: the declaration is in the language, but this example does not compile on the 606a toolchain (below).

jobs_declaration.hey

import 'stdlib:Jobs'

worker Double(message)
  return message * 2
end

# `job Name ... end` is syntax only. It lowers to the same Jobs.define call.
job Doubles
  worker Double
  count: 2
  capacity: 8
  result_capacity: 8
end

program
  let receipts = []
  for value in [3, 4, 5]
    set receipts = [...receipts, Doubles.enqueue(value)]
  end
  says join(Jobs.await_all(Doubles, receipts, 1000), ',')
  let stopped = Doubles.stop()
end

4. Retries, backoff, idempotency keys, dead letters

A dead letter is a message the Job gave up on after its last retry, kept (with its attempts and last error) so you can inspect it. A worker that returns Result.error(…) has failed this attempt. With retries: 2 the Job tries again, up to three attempts in all, then records a dead letter. Works today

jobs_reliability.hey

import 'std:Result'

worker ImportRecord(message)
  if !message.valid
    return Result.error('invalid record')
  end
  return message.value * 2
end

program
  let Imports = Jobs.define(
    'Imports',
    ImportRecord,
    count: 2,
    capacity: 16,
    retries: 2,
    result_capacity: 32,
    dead_letter_capacity: 8
  )

  let good = Imports.enqueue({valid: true, value: 21})
  let bad = Imports.enqueue({valid: false, value: 0})

  let good_result = Jobs.result(Imports, good, 1000)
  let bad_result = Jobs.result(Imports, bad, 1000)

  says good_result.status
  says good_result.value
  says bad_result.status
  says 'attempts=' + bad_result.attempts
  says 'dead_letters=' + Jobs.dead_letters(Imports).length

  let stopped = Imports.stop()
end

backoff_ms and max_backoff_ms space the retries out (doubling, capped). Idempotent means "doing it twice has the same effect as doing it once". An idempotency_key in the message makes a repeat enqueue return the first receipt instead of doing the work twice; idempotency_capacity bounds how many keys are remembered.

Predict it. The second Imports.enqueue carries the same key but value: 999. Which value comes back, 42 or 1998?

jobs_backoff_idempotency.hey

import 'stdlib:Result'

worker ImportRecord(message)
  if !message.valid
    return Result.error('invalid record')
  end
  return message.value * 2
end

program
  let FailingImports = Jobs.define(
    'FailingImports',
    ImportRecord,
    count: 1,
    capacity: 8,
    retries: 2,
    backoff_ms: 20,
    max_backoff_ms: 40
  )

  let failed_receipt = FailingImports.enqueue({valid: false, value: 0})
  let failed = Jobs.result(FailingImports, failed_receipt, 1000)
  let failed_status = FailingImports.status()

  says failed.status
  says failed.attempts
  says failed_status.retry_delay_total_ms
  let stopped_failed = FailingImports.stop()

  let Imports = Jobs.define(
    'Imports',
    ImportRecord,
    count: 2,
    capacity: 8,
    idempotency_capacity: 32
  )

  let first = Imports.enqueue({
    idempotency_key: 'record-42',
    valid: true,
    value: 21
  })
  let duplicate = Imports.enqueue({
    idempotency_key: 'record-42',
    valid: true,
    value: 999
  })
  let completed = Jobs.result(Imports, duplicate, 1000)
  let status = Imports.status()

  says duplicate.duplicate
  says completed.value
  says status.enqueued
  says status.idempotent_reuses
  let stopped = Imports.stop()
end

5. Cancellation, partitions and adaptive scaling

Cancel a queued Job

job_cancel.hey

import 'stdlib:Jobs'

worker Slow(n)
  sleep 50
  return n
end

program
  let Work = Jobs.define('SlowWork', Slow, count: 1, capacity: 8)
  let first = Work.enqueue(1)
  let second = Work.enqueue(2)
  let cancelled = Jobs.cancel(Work, second)
  says cancelled
  says Jobs.result(Work, second, 1000).status
  says Jobs.result(Work, first, 1000).value
  let stopped = Work.stop()
end

The first line is the cancel record printed whole: cancelled: true because message 2 was still waiting behind message 1, and status: cancel_requested because cancellation is a request. Its result then reads cancelled. Cancellation succeeds for work that has not started, and cannot undo an effect that already happened.

Partitions: never two at once for the same key

partition_by: SomeFn computes a key from each message; messages with the same key never run at the same time, while other keys run in parallel. It guarantees non-overlap per key, not a global order. Partly works: the runtime supports it, but passing partition_by: a function does not compile on the 606a toolchain (below).

jobs_partitioned.hey

fn ByCustomer(message)
  return message.customer
end

worker SendCustomerEvent(message)
  sleep message.delay_ms
  return message.customer + ':' + message.sequence
end

program
  let Events = Jobs.define(
    'CustomerEvents',
    SendCustomerEvent,
    count: 4,
    capacity: 32,
    result_capacity: 32,
    partition_by: ByCustomer,
    partitions: 4
  )

  let first = Events.enqueue({customer: 'alpha', sequence: 1, delay_ms: 20})
  let second = Events.enqueue({customer: 'alpha', sequence: 2, delay_ms: 20})
  let third = Events.enqueue({customer: 'beta', sequence: 1, delay_ms: 20})

  let values = [
    Jobs.result(Events, first, 1000).value,
    Jobs.result(Events, second, 1000).value,
    Jobs.result(Events, third, 1000).value
  ]
  says join(values, ',')
  says first.partition == second.partition
  says Events.status().partition_count
  let stopped = Events.stop()
end

Adaptive scaling

With min_workers, max_workers and target_queue_latency_ms, the oldest waiting message drives scale-up, and sustained idleness retires workers back to the minimum. The sample uses a test clock so the result does not depend on your machine's speed. Partly works: the scaling is in the runtime, but the sample's test clock (Jobs.test_clock_set) does not resolve on the 606a toolchain (below).

jobs_adaptive_scaling.hey

# Adaptive Jobs use the same lightweight pooled workers as fixed Jobs.
# Oldest queued work drives bounded scale-up; sustained idleness drives scale-down.
worker RenderPreview(page)
  sleep 25
  return page * 2
end

program
  let clock = Jobs.test_clock_set(0)
  let Previews = Jobs.define(
    'Previews',
    RenderPreview,
    min_workers: 1,
    max_workers: 4,
    target_queue_latency_ms: 1,
    capacity: 16
  )

  let one = Previews.enqueue(1)
  let two = Previews.enqueue(2)
  let three = Previews.enqueue(3)
  let four = Previews.enqueue(4)

  let first_tick = Jobs.test_clock_advance(5)
  let first_scale = Previews.status()
  let second_tick = Jobs.test_clock_advance(5)
  let scaled = Previews.status().pool
  says 'workers=' + scaled.current_workers + ' peak=' + scaled.peak_workers

  let first = Jobs.result(Previews, one, 1000).value
  let second = Jobs.result(Previews, two, 1000).value
  let third = Jobs.result(Previews, three, 1000).value
  let fourth = Jobs.result(Previews, four, 1000).value
  says 'results=' + first + ',' + second + ',' + third + ',' + fourth

  let idle_tick = Jobs.test_clock_advance(200)
  let first_retirement = Previews.status()
  let final_tick = Jobs.test_clock_advance(200)
  let idle = Previews.status().pool
  says 'workers=' + idle.current_workers + ' retired=' + idle.workers_retired
  let stopped = Previews.stop()
end

6. Streams: map and filter, in parallel, in order

Import the stream words with forms: [:dotted] and a list (or Files.lines(path)) gains .map, .filter, .each, .through(job), .unordered(), .resequence() and .collect(). Each stage with workers: N runs N at once. .through(SomeJob) sends every item through an existing Job. Works today

parallel_streams.hey

import 'stdlib:Streams' exposing: [map, filter, each, through, collect, unordered, resequence] forms: [:dotted]

fn double(value)
  return value * 2
end

fn over_twenty(value)
  return value > 20
end

fn observe(value)
  return value
end

worker AddTen(value)
  return value + 10
end

program
  let Additions = Jobs.define('ExampleStreamAdditions', AddTen, count: 2, capacity: 4)
  let values = [5, 10, 20, 30]
    .map(double, workers: 2)
    .filter(over_twenty, workers: 2)
    .through(Additions)
    .collect()
  says join(values, ',')
  says values.each(observe, workers: 2)
  let stopped = Additions.stop()
end

stream_resequencing.hey

import 'stdlib:Streams' exposing: [map, filter, each, through, collect, unordered, resequence] forms: [:dotted]

fn SlowFirst(value)
  sleep (5 - value) * 20
  return value
end

program
  let completion_order = [1, 2, 3, 4]
    .unordered()
    .map(SlowFirst, workers: 4)

7. When a Job attempt fails at run time

Returning Result.error is the polite way to fail an attempt. A real runtime error or a fail inside the worker is the other way. Hey's fail-fast rule (see Actors and failure) says it should end that attempt: the Job's retries run, then a dead letter of kind runtime_error. Partly works task actor-and-job-failure-containment.

job_failure.hey

import 'stdlib:Jobs'

worker Divide(n)
  if n == 0
    fail 'cannot divide by zero'
  end
  return 100 / n
end

program
  let Divisions = Jobs.define('Divisions', Divide, count: 1, capacity: 8, retries: 1)
  let good = Divisions.enqueue(4)
  let bad = Divisions.enqueue(0)
  let a = Jobs.result(Divisions, good, 1000)
  let b = Jobs.result(Divisions, bad, 1000)
  says a.status + ' ' + a.value
  says b.status + ' attempts=' + b.attempts
  says b.error
  says Jobs.dead_letters(Divisions).length
  let stopped = Divisions.stop()
end

Run it (exact command and output)

$ hey job_failure.hey

What happened. The attempt with 0 failed twice (the first try plus retries: 1); each time the runtime printed "worker task stopped by a runtime error; failing this attempt" on standard error, then the Job recorded failed with the error and one dead letter. The other message completed, and the program exited 0. On 0.99.604a the same program ended the whole process with status 70.

8. Durability: local replay today, a provider contract next

Give a Job a journal_path and it writes accepted work to a JSON-lines journal (compacted after journal_compact_after events). After a restart, a Job defined with the same journal replays what was accepted and not finished (its status counts it under replayed). The sample below shows the journal being written (durable, journal_events); it does not restart, so it does not show a replay. Partly works: this survives a process restart on one machine, not the loss of the disk or the host.

jobs_durable_replay.hey

import 'stdlib:Files'

worker DoubleRecord(message)
  return message.value * 2
end

program
  let root = 'build/jobs-durable-example'
  let journal = root + '/doubles.jsonl'
  let cleaned = Files.remove_tree(root)
  let created = Files.ensure_dir(root)

  let DurableDoubles = Jobs.define(
    'DurableDoublesExample',
    DoubleRecord,
    count: 2,
    capacity: 32,
    result_capacity: 128,
    idempotency_capacity: 128,
    journal_path: journal,
    journal_compact_after: 4096
  )

  let receipt = DurableDoubles.enqueue({
    idempotency_key: 'double-21',
    value: 21
  })

  let outcome = Jobs.result(DurableDoubles, receipt, 1000)
  let status = DurableDoubles.status()

  says outcome.value
  says status.durable
  says status.journal_events
  says DurableDoubles.stop()
end

Where durability goes next. The design (526, see the decision ledger) keeps storage engines out of the standard library: a durability provider package plugs into Jobs through a narrow contract (append, replay, who has authority, fencing, retention). hey_durable_log is the first provider; it already replicates to a quorum of machines and fences old leaders. The modes, from cheapest to strongest: ephemeral messaging, recoverable local Jobs, quorum-backed Jobs, and "effectively once" business effects (which also need an idempotent or transactional sink in your application; no scheduler option can promise exactly once).
