Delete the Code and See If the Test Still Fails

We were told to stop asking anyone to take our word for things and go find out how other people solve this. Three answers came back. One argues against the thing we were about to do, and it is here at full strength. Then we counted our own bugs, and they overruled all three.

Status: research, nothing built yet

Everything below is either published work by other people or a count from our own commit history. None of the techniques described here is running in our build today. This is a recommendation about what to do first, not a report on something shipped.

TL;DR

  • Verdict: change the order, not the plan. Build the cheap checks that need only one compiler, run them alongside the second code generator until they are demonstrably catching things, and retire it last. Of 58 defects in our own history, only 4 needed the two generators compared — and 3 of those 4 gave the user the same answer either way.
  • The ritual of deleting the implementation to check the test notices has a name: extreme mutation testing. Published rates for the failure it detects: 11.4% of functions under close-in tests, 35.5% under end-to-end tests. Adopt the ritual; do not adopt the score as a target.
  • The best argument for a second implementation is not bug counts. Researchers searched three years of the busiest Java virtual machine mailing lists and found zero discussions of implementations disagreeing. The whole class of defect was invisible until two ran side by side.
  • Disclosed weakness: our 58-bug count cannot see half our own history. 596 of 1,211 commits predate the era when we started recording how a defect was found. Four-of-58 is a floor with a blind spot behind it, not a proof.
  • Reproduce the core of this today: take your last bug fix, delete the body of the function you fixed, and run your entire test suite. If it stays green, the test you just wrote is not watching that code.

The ritual has a name, and it is 48 years old

The instruction we were given was roughly this: when you miss something, write the test you should have written, check it fails for the right reason, fix it, watch it go green — then remove the implementation again to make sure the test was not green all along.

That last step is a published technique with 48 years of literature behind it. It is called mutation testing: damage the program on purpose and check that some test complains. The version described above — delete a whole function body rather than tweak one operator — is extreme mutation testing. And a function whose body you can delete with the suite still passing has a name too: it is pseudo-tested.

Pseudo-tested

Covered but unwatched. Coverage says the tests reach this function; delete its body and every test still passes. Coverage measures whether a line was executed, never whether anything checked the result.

Here is the ritual, written out. The third command is the one almost nobody runs. 

# 1. Write the test you should have written. Run it BEFORE the fix.
$ hey-spec specs/1234_precedence.hey
FAIL  expected 5, got 230      <- red, and red about the VALUE

# 2. Apply the fix. Run it again.
$ hey-spec specs/1234_precedence.hey
ok

# 3. Now delete the body of the function you just fixed, and rerun.
$ hey-spec specs/1234_precedence.hey
FAIL  expected 5, got 0        <- red again: the test really is watching that code

How common is the failure it detects? Common enough to be the default. One study of 14 open-source Java projects measured 11.4% of methods pseudo-tested under close-in unit tests and 35.5% under end-to-end tests (Niedermayr, Juergens & Wagner, 2016); a replication across 28,000-plus methods found them in every project it looked at. Most of our own tests are the end-to-end kind, which is the worse column.

The sharpest illustration applied this to a proof rather than a test. A team verified a sorting routine, then damaged it 81 ways to see how many the verification would catch. It caught 6. Seventy-one of eighty-one survived, because the proof had run on arrays of length one (Groce, Ahmed, Jensen & McKenney, 2015). It was green for the wrong reason, and only damaging the code could reveal it.

The “fails for the right reason” half has a name too — the RIPR model — and it is useful because it is a checklist. Four things must all happen for a test to catch a fault: it must reach the broken code; running it must produce a wrong value; that value must travel to the output; and the test must be looking at the part of the output that changed. A test that goes red because the build crashed has satisfied the first two and neither of the rest (Ammann & Offutt, Introduction to Software Testing, 2nd ed., 2017).

One caution, well evidenced. The technique comes with a standard number — the percentage of damaged versions your tests catch — and it is a bad target. A large study found every correlation between that score and real fault detection weak once you control for how many tests you have, while deliberately writing tests to kill survivors does improve detection. The number is a poor gauge; the individual survivor is an excellent bug report. Use it one fix at a time, never as a threshold in the build.

The tooling exists and does not need building: pitest for Java, and cargo-mutants for Rust, whose default operator is exactly this.

The argument for a second implementation is stronger than we expected

We keep two code generators and compare their output, and we have been leaning toward dropping one. The strongest finding in this review argues against that.

Running the same input through two systems that should agree, and treating disagreement as a bug, is called differential testing. A team applied it to five Java virtual machines and found real defects, one of which forced a change to the Java specification itself. The striking part was elsewhere in the paper. They searched three years of the busiest Java virtual machine mailing lists for any discussion of implementations disagreeing with one another, and found none (Chen, Su, Sun, Su & Zhao, 2016).

Not “rarely discussed” — absent. The defect class did not exist as a topic until two implementations ran side by side. Every other technique in this article tests a rule somebody wrote down in advance. A second implementation is the only one whose coverage you did not have to predict. It finds bugs in your understanding of what your own language means — the one category you cannot write a test for, because writing the test requires already having the understanding.

A head-to-head study on GCC and LLVM points the same way for a narrower reason. Comparing two different compilers was the only one of three methods that found any bugs unrelated to the optimizer: five, against zero and zero (Chen et al., 2016).

And the field is walking away from it anyway

The counterweight is not a rebuttal of the paragraph above so much as a report on what people are actually doing. The methods that need only one implementation are finding more bugs than the cross-implementation work they replaced. Three recent efforts against database engines and compilers found 159, 175 and 147 previously unknown bugs, each using a single implementation as its own reference (NoREC, TLP, EMI).

The clearest story is from machine learning. A 2019 paper built its entire method on a library that ran on several interchangeable back ends, comparing them against each other. Roughly 14 months later, that library dropped multi-back-end support. Three of the paper's four authors then published the single-implementation replacement, writing that the old approach required two libraries doing the same thing, “which is often unavailable,” and had become “prohibitively expensive and thus no longer maintained” (EAGLE, 2022).

What these share is the thing you build instead: manufacture a second opinion out of the implementation you are keeping. Two laws in our own shape, both assertable across our whole test corpus without writing a new compiler: 

# run the program directly, and run the compiled program. They must agree.
run(interpret(program))            ==  run(compile(program))

# compile the same program with the optimizer on and off. They must agree.
run(compile(program, optimized))   ==  run(compile(program, plain))

Then we counted our own fifty-eight bugs

All of the above is other people's evidence. So we classified 58 defects from our own commit history by how each was actually found. The chart above is that count; four rows of it decide the question. It is a partial view, and the limit is worth naming: 596 of our 1,211 commits predate the habit of writing down how a defect surfaced, so the earliest era — including the whole bring-up of the compiled path — cannot speak here at all.

One case makes the shape vivid. The compiled path once evaluated 25 - 2 * 10 as (25 - 2) * 10. It printed 230, exited successfully, and said nothing; running the same source directly printed 5. Our 100-program comparison between the two generators was green on all 100 the whole time, because both shared the mistake.

That is the honest summary: we are paying for a second implementation that is not independent. Both generators are fed by the same earlier stages, so they inherit the same misunderstandings. Independence is what makes cross-checking work — the Java virtual machine result came from genuinely separate projects — and we do not have it.

Two things we got wrong writing this

First, we had it backwards about the interpreter. An early draft called checking the compiler against our plain interpreter a weaker stand-in for comparing the two generators. It is stronger. The compiler is defined to preserve the interpreter's meaning, so any disagreement is unambiguously a bug — a legitimate difference cannot exist. Two code generators can differ perfectly legally: they may pick different instructions for the same meaning, so every disagreement needs a human to rule on it. On soundness, the cheaper check wins.

Second, the first draft overstated the case for keeping the second generator. It was written from the literature alone, where the arguments for a second implementation are the strongest results available, and rewritten once the 58-defect count came back — our two generators are not the kind of pair those studies measured. Both versions of that judgement are left visible rather than presenting the second as though it had been obvious.

What we are actually going to do: change the order, not the plan

The recommendation is about sequencing, not “the second generator is worthless.” Everything cheaper should exist and be demonstrably catching things before anything is switched off. In order:

  • Make interpreter-versus-compiled a hard gate across every test we have. Both halves already exist; this is wiring, not construction. It is our soundest oracle, and it already found the right answer in 15 of our 19 wrong-answer defects.
  • Compile every test with the optimizer on and off and require identical output. Days of work, no new compiler.
  • Adopt the deletion ritual per change, so we can tell when our tests have gone blind instead of finding out by accident.
  • Only then decide about the second generator, with a record of what it has actually been catching.

One cost should be said plainly rather than argued away. If the second generator goes, we lose the property nothing on that list replaces: an oracle whose coverage nobody had to anticipate. Every replacement above checks a rule we wrote down. The man who named differential testing put the same point as a matter of order rather than principle — retiring an old compiler in favour of a new one is exactly when comparing the two is worth most (McKeeman, 1998). It certifies the survivor. So it goes last.
