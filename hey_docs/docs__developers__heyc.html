Using heyc#

heyc validates specs, inspects compiler data, and builds native applications.

Default product build#

./bin/heyc build app.hey -o build/app
build/app

An unqualified build always means:

LLVM-hosted Hey frontend -> semantic HIR -> ABI MIR -> direct LLVM

--backend llvm is retained as an alias for the same default. It does not select the retired direct-source LLVM path.

Run and test source#

./bin/hey app.hey
./bin/heyc app.hey --test

hey content-addresses the source and compiler inputs, creates or reuses HIR/MIR sidecars, compiles the application through LLVM, and executes the cached native application. Cached applications replace the launcher process and inherit stdio. Application source execution has no native-C compatibility fallback; a compiler error fails closed. Stage-0 native-C remains an internal bootstrap mechanism only. heyc --test remains the fast embedded-spec harness and is not a separate product backend. heyc SOURCE --run is an embedded interpreter/developer path, not a native performance benchmark.

Source programs may be launched from directories unrelated to the SDK checkout. Compiler-side stdlib: and std: imports first preserve checkout-relative resolution when available, then use HEY_STDLIB_PATH, and finally $HEY_ROOT/stdlib.

Build from validated MIR#

The self-hosted compiler persists semantic HIR and ABI-explicit MIR. The product consumer can build validated MIR without reopening source:

./bin/heyc build-mir --backend llvm program.mir -o build/program
./bin/heyc llvm-ir-from-mir program.mir -o build/program.ll

HIR/MIR production and validation are Hey-owned. The LLVM consumer must not reparse .hey source or infer missing semantics.

Inspect compiler-facing symbols#

./bin/heyc symbols app.hey

Module-qualified source names retain their readable source form while the compiler also emits a backend-safe canonical symbol name.

Read API documentation#

./bin/heyc --describe Web.serve
./bin/hey doc Web.serve

Use the REPL#

./bin/hey-repl

The REPL is an interactive development surface. Production application builds continue to use the north-star HIR/MIR/LLVM pipeline.

Toolchain and distributions#

./bin/heyc toolchain

The direct LLVM consumer links through the target LLVM/Clang toolchain. Released distributions expose compiled Hey commands; application builds use the fixed-point self-hosted compiler path. Object generation and linking remain target-toolchain operations rather than language-semantic stages.

Release verification#

Maintainers run Release-C, Release-A, Release-B, and the separate promotion report. The default-route contract is part of Release-C and source-archive verification.

Runtime object cache identity#

Native applications link a cached runtime object, but cache reuse is never based only on modification time. The object name contains a digest derived from:

  • runtime/hey_runtime.c;
  • runtime/hey_runtime.h and runtime/hey_native_abi.h;
  • compiler executable path/size/high-resolution timestamp;
  • host platform and pointer width;
  • Hey version and fixed runtime compile flags;
  • platform TLS include configuration.

This makes a cache hit an identity claim. Even when a source file is replaced while retaining exactly the same timestamp, the compiler builds a different object before linking. Parallel builders publish the same identity atomically.
