Building Hey's Compiler from C

Hey's compiler is written in Hey, so a fresh machine needs a Hey compiler before it can build one. That first compiler will come from C printed from the same records the normal compiler already uses. This page shows how that works, how the result is checked, and what it does and doesn't cost.

Short version

  • Decided: a C back end is the permanent bootstrap. It prints C from the same records the LLVM back end reads, and decides nothing itself.
  • Recommended first: a c-portable ABI family in MIR, so one seed builds on Mac, Linux arm64 and Linux x86-64.
  • Decided: a compressed seed (the compiler printed as C) is committed, estimated at 2–6 MB and written only by an automatic update job.
  • Your programs don't change. LLVM still builds every user program and the final compiler.
  • Status on November 10, 2026: in progress, not released. The published release, 0.99.605a, still bootstraps through heyc stage0-build. On the development line a seed is committed and passed the fixed-point check on a Mac on November 5 and 6; it measures 6.1 MB packed and about 199 MB as C. The stage-0 compiler has not been deleted yet.

Today the first compiler comes from a second compiler

A source build first runs heyc stage0-build, a separate compiler written in C in runtime/heyc.c. It ignores the ownership decisions the real compiler makes: when a String is copied, when a value is freed, when a map may be updated in place. So a bug can live in one compiler and not the other. The fix: print the first compiler from the real compiler's output.

One set of records, two printers

MIR is the compiler's middle layer, where ownership is decided. Its last step, physical MIR, spells every decision out as an explicit operation, such as "copy this String" or "release that one". It's a closed list of 40 record kinds. Anything else is refused, so a printer never guesses. stdlib/HeyLlvm.hey prints all of it as LLVM IR (the input of LLVM, the toolkit that makes machine code) in about 1,000 lines on the development line. (In 0.99.605a the same file is the older emitter, about 24,000 lines.) A C printer should be about the same size and share the code that walks the records.

Each MIR decision becomes a plain call or assignment in C

What MIR decidedThe C the printer writes

Runtime functions keep their hey_llvm_ names; the C seed calls the same runtime.

The seed builds the compiler, and the compiler must rebuild itself byte for byte

The seed is that printed C for the whole compiler. Turning it into a working compiler needs only a C compiler, so Linux never waits on a Mac.

Is the runtime C? Yes

Hey programs are compiled to LLVM, but the runtime they link against is C: the allocator, Strings, maps, actors and the scheduler. clang compiles it and links it into every Hey binary, and the compiled Hey code calls into it. On the development line runtime/ holds 22 C files, about 62,000 lines; the part every binary links is hey_runtime.c plus hey_str.c, about 39,000 lines (about 33,000 in 0.99.605a). Most of the rest is the stage-0 compiler (heyc.c) and the REPL.

The speedups made on the development line for the one billion row challenge (1BRC) were all in that runtime: a per-thread small-block allocator, fixed-layout Result and line records, read_line adopting its buffer, and split sharing its last field. They speed up every compiled Hey program. None of them touched the stage-0 compiler.

The portable String keeps its 16 bytes; it costs one MIR ABI family and some bootstrap speed

An ABI is the rule for how a value crosses a function call: in registers, or through memory. Today MIR spells, per target, how a String's 16 bytes travel in LLVM. The seed gets a fourth, c-portable form: pass the struct, and let the C compiler apply the platform's rule.

TargetToday, in MIR for LLVMC passes the struct; clang applies
Mac and Linux arm64two 8-byte integers ([2 x i64])two registers (AAPCS64)
Linux x86-64two i64 valuestwo registers (System V AMD64 ABI)
Windows x86-64a pointerby reference (Microsoft x64)

The call should look the same at the machine level; that's the standard C ABI rule (sources below). Only the seed uses it. No platform gets slower Strings. The costs:

  • One more ABI family in MIR to keep and verify.
  • The compiler built from the seed (P0) may run somewhat slower than an LLVM-built one, because C has no guaranteed tail calls and stricter aliasing and overflow rules. That slows only the bootstrap step.

The decisions

Decided

The C back end is the permanent bootstrap

Replaces the stage-0 path, the old seed bundle and stdlib/HeyC.hey.

Decided

A compressed seed is committed

Estimated at 2–6 MB with xz; the seed on the development line is 6.1 MB: one seed/<unit>.c.tar.xz per compiler unit (three units) plus manifest.json.

Dropped

Bootstrapping from the previous release

Go's way. Why not: a feature would wait a whole release before the compiler could use it; the seed waits only for its next refresh.

Dropped

An interim saved-build seed

Why not: a fresh clone can't fetch it, each platform needs its own binary, and nothing in the repository says what source it came from.

Recommended

Add the c-portable ABI family to MIR first

Without it the seed works on one target only, and its function declarations disagree with the runtime's C.

Physical MIR's 40 record kinds: 14 statement kinds, 14 value kinds, 3 operand kinds, 6 machine types and 3 parameter attributes.

Koka and Roc have no seed (their compilers are written in Haskell and in Rust or Zig), but both decide reference counting in an IR before printing code, as Hey does.

Where the 2–6 MB estimate comes from
  • An earlier stage-0 C build of the pipeline was 21.1 MB (279,000 lines; later builds 24.5–27.2 MB) and 0.88 MB with xz. It has no ownership code.
  • C from physical MIR has the .ll file's operation count, which keeps every temporary, reference-count call, shadow slot and guard. The product .ll is 80–91 MB in normal builds and was 346 MB in one release build.
  • Estimate: about 30–60 MB of raw C, up to about 120 MB if the 346 MB shape is normal; 2–6 MB with xz. Even the worst case is under a fifth of Lean's 654 MB seed.
  • Measured since, on the development line: 199 MB of raw C for the three compiler units (137, 59 and 4 MB), 6.1 MB with xz. The raw C is larger than estimated; the packed size is at the top of the estimate.
  • Physical MIR as JSON is bulky (191 KB for a 142-byte test program), so the printer must stream unit by unit and join once per function.

Recommended for the seed runtime: refuse a seed whose manifest names a different runtime ABI identifier than the tree. Freeze a runtime copy beside the seed, as Lean does, only if refreshes get too frequent.

The manifest records the compiler source digest, the language version, the c-portable family name and version, the runtime ABI identifier, a SHA-256 for each unit file, and the generator version.

The build order
  1. The critical path: physical MIR for every compiler unit with zero refusals, including the fix for the quadratic map clone in hey_mir_physical_fresh. The baseline is 50 minutes and 8.6 GB.
  2. Add the c-portable family; a test that expects one String fragment must fail first.
  3. Move the shared walker out of HeyLlvm, with LLVM output byte-identical.
  4. First slice: one small program that uses a borrowed String, String append, a map updated in place, a loop, a guard and the main bridge, matching the LLVM build's output, exit status and copy counters.
  5. Widen family by family, each through one differential gate that compares both printers.
  6. Library and archive units.
  7. The whole compiler seed and the fixed point on Mac and Linux, recording size, build time and peak memory.
  8. Switch the Makefile seed targets to the committed seed directory (seed/ on the development line) and add make update-seed.
  9. Delete the stage-0 path, the old seed bundle, stdlib/HeyC.hey and the stage-0-only gates.

Steps 1–4 need only small programs, so they can run alongside step 0.

The two-step rule: the seed may lag, because it only has to accept today's compiler source. A feature the compiler itself wants lands first, the seed is refreshed, and only then does the compiler use it.

Main risks
  • Without the c-portable family, the seed's function declarations disagree with the runtime's C definitions. That is undefined behavior, even where it happens to work.
  • Physical MIR must cover the whole compiler first. The C printer can't get ahead of it.
  • The first seed is generated by the slow route: 50+ minutes and 8.6 GB until the map-clone fix lands.
  • C rules: signed overflow (use unsigned arithmetic), strict aliasing (use memcpy), no guaranteed tail calls (the deep-recursion stack limit still applies), __builtin_unreachable needs a fallback on MSVC, and failure unwinding must behave the same at -O2.
  • Seed drift: covered by the fixed point, a single writer, and a gate that refuses compiler source needing a newer seed than the committed one.
  • The two runtime tests that force copy-on-write mistakes must still turn the gates red against the C seed.
