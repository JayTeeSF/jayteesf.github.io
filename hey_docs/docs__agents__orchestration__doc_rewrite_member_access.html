`wdocs-member-access` — rewrite the HUMAN-facing docs for the member/key model

**Maintainer instruction, 2026-07-29:**

> "update our docs (not just for agents but humans and developers) so

> we teach about the new imports and we avoid messaging about how the

> conflict used-to work and instead show the warning, etc."

**THIS SLICE FIRES ON HIS RULING, NOT BEFORE.** The design is still

deferred until he reads bench's article. **Until it ships, our

user-facing docs must describe what actually ships** — documenting a

model we have not built would be a lie in the one place users trust

most. What is allowed *now* is this audit, and not writing any NEW doc

that entrenches the old model.

Decision tracking + re-ask protocol:

`research_member_vs_key_collision.md`.

---

THE FINDING THAT RESHAPES THE PROPOSAL

**The maintainer's design already exists in Hey and ships today.**

`docs/developers/collection-method-sugar.md`:

import 'stdlib:Collections'
says names.uniq              # lowers to Collections.uniq(names)
says names.includes?('Lin')  # lowers to Collections.includes?(names,'Lin')

> "These are ordinary module functions, not mutation or prototype

> patching... **The import remains explicit so a module controls which

> extension vocabulary it uses.**"

That is exactly the proposed rule: **module functions become

dot-callable only via an explicit import; otherwise you write the

qualified form.** Built, documented, and already taught.

THEREFORE THE PROPOSAL IS NOT "ADD A MECHANISM" — IT IS "REMOVE AN EXCEPTION"

**Ten builtin names bypass the rule that already governs every

`Collections` method.** We ship two models side by side and teach only

one of them as a model; the other is taught as a *caveat*.

**The only genuinely new part is the `expose <name>` selector.** Today

an import is all-or-nothing per module (`import 'stdlib:Collections'`

brings the whole receiver vocabulary). The maintainer wants named

selection (`import SomeModule expose count`). That is a refinement of a

shipping mechanism, not a new one — **and it materially lowers the cost

estimate for the whole proposal.**

**Hand this to bench.** It changes their central question from "should

we adopt this design?" to "**we already have this design for

`Collections` — why do ten builtins get an exemption, and what does the

exemption buy?**" That is a much sharper question and it should be

answered before the article is written.

---

THE SENTENCE THE MAINTAINER WANTS GONE

`docs/developers/object-field-access.md`, line 3, shipping today:

> "Bracket access remains the general form for dynamic keys, numeric

> indexes, punctuation, and **names that collide with built-in value

> properties or methods.**"

**This teaches the collision as a feature.** It is the "how the

conflict used to work" messaging in its purest form: it tells the user

the collision is normal, hands them a workaround, and never tells them

they lost anything. Under the new model this becomes: *the key always

wins, and the compiler warns you when you shadowed a method you

exposed.*

---

THE RULE THE DOCS MUST TEACH — standing rule 30, verbatim

> **"dot-methods are a syntactic-sugar (nice-to-have) they only (ever)

> exists because of an explicit import and they lose to conflicting

> names. At which point the system will (generously) produce a warning

> message."**

**Teach it in this shape, in one sentence, on one page.** Everything

else links to that page. Consequences the docs must carry:

  • **`Module.fn(x)` is the real spelling** and is always correct. Show it

FIRST, not as a fallback. The dot form is the convenience.

  • **UNIFORM — no type exemption.** `[1,2,3].count` and `'hey'.length`

need the import too. **Every array and string example in

`docs/course/` and the tutorials now needs an import line**, which is

the largest single mechanical change in this slice.

  • **No implicit prelude.** Do not write "the core methods are always

available" anywhere; rule 30 forecloses it.

  • **The key always wins**, and the warning tells the author they lost

the `.method`.

**This makes the course chapter-ORDER problem certain rather than

possible:** imports must be taught before any dot-method appears. Check

the sequence first, before editing any chapter text.

---

REQUIREMENTS FOR THE REWRITE

1. **Teach the import/expose model as the single model.** One page owns

it; everything else links. Two explanations is how we got here.

2. **Delete the collision-as-caveat messaging.** Do not replace it with

"this used to work differently" — the maintainer's instruction is

explicit. New users should never learn the old model at all. The

*migration note* is the only place the old behaviour is described,

because that is the one audience that needs it.

3. **Show the warning.** Real compiler output, copied from a real run,

not hand-written prose about what it says. Including its

self-bounding last line.

4. **Show the qualified form as first-class**, not as a fallback.

`Enumerable.count(obj)` is the always-correct spelling.

5. **Ruby column / Ruby comparison** wherever member access is compared

— north star.

6. **Every code sample must run.** Standing discipline: no sample goes

in that has not been executed against the shipping binary, with

stderr captured to a log (rule 24).

7. **Check the course chapter ORDER**, not just chapter text.

---

MEASUREMENTS ALREADY TAKEN — do not re-derive

  • Shadow list is **ten names**: `count size length keys values empty

sort reverse type to_s`. Fifteen others already let the key win.

  • `h.other` → 7: **dot does reach user data**; it loses only on the

shadow list, silently.

  • `heyc --check` exists, silent on success. `warn` is a **runtime**

statement, not a diagnostic. **Zero compiler warning sites.**

  • `h.empty` / `h.sort` / `h.reverse` on a map with that key → `#<stop>`,

an internal sentinel reaching user data (**todo item 9**, independent

of this).

  • **UNTRUSTED:** 168 grep hits (`.length` 103) counts **uses, not

receivers**. The receiver split is still the highest-value unmeasured

number in the whole programme.
