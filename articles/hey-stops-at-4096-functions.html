The Wall Isn’t at 4,096 Functions. It’s at 1,145 — and It Isn’t the Cap.

Hey refuses to load a program that defines more than 4,096 functions. The number is real. It is also not what stands between anyone and a large program.

TL;DR

  • Verdict: better diagnostics and one crash fix come first; raising or removing the 4,096 cap can wait. Nothing in the tree is near the cap. The diagnostic itself is good — it names the exact definition it could not register and exits non-zero, which is more than Erlang does.
  • Strongest measurement: heyc build fails at roughly 1,145 top-level functions. 1,140 built once; 1,150 and 2,000 each failed twice. 3.6× tighter than the cap — and a stack overflow in a helper process running Hey's own parser, not the table at all.
  • The defect is the shape, not the number. static ReplFunctionDef repl_function_defs[4096] makes the limit and the allocation one object: 104 bytes an entry, 416 KiB reserved in every Hey binary whatever the program does. Erlang keeps the two apart, which is why its ceiling can be a flag.
  • The cap charges for every import, and drops nothing. import 'stdlib:Deque' declares 14 functions and costs 143 slots. All 111 standard-library modules take 3,336 of 4,096 — 81.4% full, 760 left; the self-hosted compiler driver uses 297 (7.2%).
  • Disclosed weakness, found while measuring: build/hey-repl prints the fatal “table is full” diagnostic and then exits 0, while the other three lanes exit non-zero. Disclosed here; not yet fixed.
  • Falsifiability: generate N trivial functions. The 4,096th registers and the 4,097th is refused by name; heyc build passes at 1,140 and fails at 1,150. Both should reproduce on trunk at b4ba73b1 (497a).

Two ceilings, and where real programs sit

The cap is on the right. Everything anyone has actually written is bunched at the left. The dashed line between them is the limit that stops people.

The cap does not count what you wrote

Hey keeps one array of function definitions per process, shared by the interpreter and the compiler — not two tables of the same size, the same array. Every function the program can see registers in it, including every function inside every module it imports. There is no tree-shaking: an import registers everything in its import closure whether the program calls it or not. That is how a module declaring fourteen functions comes to cost a hundred and forty-three.

The wall users actually hit is at 1,145

Then the compiled lane failed at a number nobody had written down. Fed the same fixture, heyc build — the command that produces an actual binary — stops working between 1,140 and 1,150 top-level functions, 28% of the way to the cap.

Two controls pin down what drives the threshold. Raw file size is not it: one function plus six thousand comment lines builds fine. Declaration count is, with size as a secondary push — the same 1,140-function file with a thousand comment lines prepended fails, so 1,140 sits right on the edge.

The table is not involved. This is a stack overflow in Hey's own parser running inside a helper process, and the two limits compose badly. The table limit has a precise, actionable message. The one users meet first says this:

hey error: hey-selfc: semantic HIR emission failed (exit 70): hey error: stdlib delegation failed:
HeyParser.parse_file (sidecar exited before answering (crash or stack overflow in the delegated stdlib call))

Nothing there names the reader's program, the reader's function, or anything the reader can change.

Found while measuring. All four lanes print the identical fatal “table is full” diagnostic on the same 4,097-function fixture. Three of them exit non-zero. One does not: 
heyc f.hey --run                  exit 70   function table is full ... `gen_fn_4096`
heyc f.hey --check                exit  1   function table is full ... `gen_fn_4096`
heyc build f.hey -o app           exit  1   function table is full ... `gen_fn_4096`
build/hey-repl --quiet < f.hey    exit  0   function table is full ... `gen_fn_4096`
Anything that pipes Hey source into build/hey-repl and trusts the exit status reads a dropped definition as a clean run. The project's regression gate for this exact failure only ever drove the interpreter, so the zero exit sat outside what that gate could see. Disclosed here; not yet fixed. It is user-facing and independent of any capacity decision.

There is no recorded reason for the limit — only for its value

There is no recorded engineering rationale for having a limit at all. The constant predates the project's current name: an inherited fixed-size array of the kind written when a read-eval-print loop is a few hundred lines long, never revisited on the merits.

The current value does have a documented reason, and it is policy. The comment beside the constant, added when it was raised from 2,048, rejects a big round number on purpose: the standard library is too large, and a ceiling far above it would hide that. The cap is a budget signal, not a defence of memory. The same comment names a dynamic table as the real fix.

The 4,096 coincidence is a coincidence. C names 4,095 external identifiers per translation unit and C++ suggests 4,096 members in one class. Both are floors an implementation must clear, not ceilings on your program, and C++17's Annex B says its numbers “are only guidelines and do not determine compliance.” What transfers from the C standard is not the number but footnote 18 to that same clause: “Implementations should avoid imposing fixed translation limits whenever possible.”

The limit and the allocation are one object

Hey's table is declared like this, and the declaration is the problem:

#define HEY_REPL_MAX_FUNCTIONS 4096
static ReplFunctionDef repl_function_defs[HEY_REPL_MAX_FUNCTIONS];

Raising the ceiling and reserving the memory are one edit, because they are one thing. Each entry is 104 bytes, so the table reserves 416 KiB in every Hey binary whatever the program does — and two more arrays of the same length sit beside it in the compiler.

Sixteen times today's ceiling costs 7.5 MiB. This is the two-hundred-kilobyte story, not the two-hundred-megabyte story; memory is not what is being defended. Erlang shows the alternative: its atom table grows a page at a time as entries arrive, and the maximum lives in a separate field checked on insertion. That separation is exactly why Erlang can offer a startup flag to move its ceiling — the number costs nothing until the entries exist. Hey cannot offer that flag, because in Hey the number is the memory.

Hey's failure manners are better than Erlang's

Hey's failure manners are good. When the table fills it names the limit and the exact definition it could not register, then exits non-zero. That was built deliberately, replacing a behaviour that printed a warning, dropped the definition, and carried on until the omission surfaced later as an unrelated error. On failure mode Hey ranks above Erlang, which aborts a live virtual machine and writes a crash dump. The complaint here is about shape, not manners.

The honest comparison is that everyone else fails by getting slower, and Hey fails by refusing — Hey's wall simply arrives about two orders of magnitude earlier.

One caveat before the table, because the Erlang row is easy to over-read. What Erlang documents is narrow: atoms are never reclaimed, so the table only ever fills. Reading that as “the cap exists to stop untrusted input exhausting it” is the standard community interpretation, not a published rationale; the evidence is that list_to_existing_atom/1 and a safe decode option exist. Either way it is a security argument, and Hey cannot borrow it unless untrusted input can define functions. The mechanism transfers completely; the justification does not.

Hey's options

Option A — raise the constant

One line, and Ruby already ran this experiment

Everything is sized by the macro rather than a repeated literal, so a larger number is consistent by construction. Ruby is the reason not to stop here. Its fixed-size method cache was gentler than Hey's table — overflowing it cost speed, not a refusal — and Ruby still shipped a tuning knob, then gave up on it. Feature #16614, which removed the table in Ruby 3.0, gives the reason in one sentence: “it is not easy to predict the optimal value.” The knob was not the fix.

Cost: 7.5 MiB reserved at 65,536 slots · and it does nothing for the ~1,145 wall, which is what users meet first.

Option B — grow the table on demand

The pattern is already in the codebase, and so is the hazard

This is the fix the source comments already name and the shape Erlang uses, and it is less speculative than it sounds: the compiler already keeps two side-tables that line up one-for-one with the function table, and both are already grown on demand. There is a working example to copy rather than a design to invent, and nothing durable records a slot number, so there is no migration.

The hazard is quiet. Two places work out which slot they are looking at by measuring how far into the array a pointer sits, which only works while the array never moves — and a growing table moves. Fourteen sites hold pointers into it. Today none survives a growth, only because of the order the compiler's stages run in, which nothing checks; defining a function mid-emission would corrupt memory rather than fail. Only grow during the pass that defines functions, and assert it.

Second cost: exhaustion becomes an out-of-memory failure, a far worse message than one naming the function it could not register. The existing gate already requires any dynamic replacement prove the new path equally loud.

Option C — leave it and diagnose better

Recommended, because the numbers point here

Fix the 1,145 crash first: 3.6× tighter than the cap, reproducible, its message useless to the person reading it. Fix the zero exit code. Then make occupancy visible — a line reading function table: 3,336/4,096 (81.4%) turns an invisible cliff into a gauge — and attribute the count to imports, because the user's own function is almost never the cause.

This is not a fix and should not be sold as one: the day a real program crosses 4,096, the diagnosis is better and the program still will not build. Recommended anyway, because 760 slots remain free even with the entire standard library loaded, the largest single module in the tree fits inside that closure rather than on top of it, and the limit that actually bites is a different one.

What would change this recommendation: a real program — not a generated fixture — importing most of the standard library and adding several hundred functions of its own. Or the 1,145 crash proving to be a one-line stack-size change, which removes the tighter wall and promotes Option B.

The number 4,096 is not Hey's problem. Reserving it unconditionally, hiding how full it is, and standing behind a tighter wall with a worse error message — those are.

What was not measured

The 416 KiB table is zero-filled and paged in on demand, so a small script almost certainly does not pay all of it in physical memory — a mechanism argument, not a measurement; resident memory was not attributed. The recursion site behind the 1,145 crash was not located either.

One correction, at the same volume as the claims above: “2,329 public functions” still appears as a live measurement in three places in the source a reader would treat as authoritative, including the comment on the constant itself. It was retracted in the project's own records and the retraction never reached the source. Today's measurement is 3,336.

Terms used here

Function table
The single per-process array in which Hey records every function definition a program can see. The interpreter and the compiler share one array, and it holds 4,096 entries.
Import closure
Every module reachable by following a program's imports, and the imports of those, all the way down. Hey charges the full closure against the table.
Tree-shaking
Dropping the parts of an imported module a program never calls. Hey does not do it, which is why a fourteen-function module can cost 143 slots.
Helper process
A separate short-lived process the toolchain launches to do one job on its behalf. The 1,145-function wall is a stack overflow inside one of these.
Reserved memory
Space a program claims at start-up because a fixed-size array was declared, whether or not anything is stored in it. The 416 KiB table is reserved this way in every Hey binary.
