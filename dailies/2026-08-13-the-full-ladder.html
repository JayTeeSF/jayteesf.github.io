An Example Program That Shipped With Hey Was Dead, And No Test Could See It

One of the example programs distributed with Hey did not work. Built the ordinary way, it stopped partway through with an error and gave up. It had been broken for some time, and the test whose entire job is comparing the two ways Hey builds programs could not tell — because that test never actually ran any of the fifty-one programs it compared. Repairing the test found the broken program within one run.

TL;DR

  • Seven commits landed on the 13th; one version bump, to 496a. All three check suites are clean at that version, with every count identical to before the change. They are landed — committed and through the battery. Nothing is deployed: this checkout has no configured remote and no toolchain image has been built, so no user feels any of it yet.
  • A shipped example program was broken in the path Hey actually uses. jobs_reliability stopped with an error and exit code 70 partway through printing its results. The two older routes — the previous compiler and the interpreter — both ran it correctly. So the newest and most-preferred route was the only one that got it wrong.
  • The test that should have caught it was comparing the wrong thing. It compared the two routes' generated code as text and stopped at the first difference. It never ran the resulting programs, so two routes could produce different answers and the test still reported success.
  • Now all fifty-one programs give identical answers on both routes, up from fifty of fifty-one. The text comparison is unchanged at forty-two of fifty-one, so nothing regressed.
  • Five corrections to my own work are below, at the same volume as the claims. The worst is not a wrong number: I threw away a fix that was already correct, because a crashing program discards what it has printed and I read the missing output as failure.
  • Earlier the same day, unpublished until now: an idle actor went from 258 to 113 bytes, and the check tier roughly halved in wall time. Those figures are as recorded when they landed; I did not re-measure them.

The program that was dead in the box

Hey ships example programs. One of them, jobs_reliability, demonstrates what happens to work items that fail repeatedly. Its last line asks a simple question: how many gave up entirely?

says 'dead_letters=' + Jobs.dead_letters(Imports).length

.length means "how many things are in this". The list of failed items is a list; its length is a number. The compiler translated that request into something else entirely: look inside this list for a labelled compartment named "length" and give me what is in it. Lists do not have labelled compartments. Asked to find one, the machinery underneath does not politely answer "nothing" — it stops the program.

What the user saw. The program printed its first few results, then stopped with get string-key fast path expects a JSON object; got array for key length and exit code 70. The final line never printed. Built with the previous compiler, or run by the interpreter, the identical program printed dead_letters=1 and finished normally.

Two independent routes agreed with each other and disagreed with the newest one, which is as clear as this kind of evidence gets. There was one case where the wrong translation could have been defended — a value that really does have a compartment labelled "length". So I checked it. Given {length: 'not-a-count', other: 1}, both older routes answer 2: the number of compartments. They read .length as a count even when a compartment of that name is sitting right there. The lookup reading was not a defensible alternative; it was simply wrong.

The repair covers all four spellings of the same idea — .length, .len, .size, .count. That was not the original plan. I fixed .length, watched the example program come back to life, and nearly stopped. The other three were still broken; xs.len was still killing programs while the interpreter answered 3. A family is not closed because its most common member is.

Why nothing caught it

Hey has a test whose whole purpose is to compare the two ways of building a program across fifty-one example programs. It had two independent flaws, and each one alone would have been enough to hide this.

FlawConsequence
It stopped at the first differenceEverything after the first mismatching program went unmeasured. This is why the project's records carried a count of thirteen differing programs that was taken before two families of them were fixed, with nothing able to re-derive it. The real number is nine.
It never ran any of the fifty-one programsIt compared the generated code as text. Two routes could produce programs that behave differently and the test would still report success. That is exactly what happened.

Both are fixed. The test now gathers every result instead of stopping, and it runs each program on both routes and compares what they print and the code they exit with. The moment it ran, it found the broken example.

The result of repairing the instrument. Programs whose two routes now give identical answers: 51 of 51, up from 50. Programs whose generated text is identical: 42 of 51, unchanged — so the repair fixed a real defect without disturbing anything else. The nine that still differ as text are individually named in the test now, so that set cannot grow or shrink without someone noticing.

Corrections to my own work

Five, with the mechanism of each. The first is the one worth reading: it is not a wrong number, it is a correct fix that I threw away.

1. I deleted a fix that was already working, because a crash ate its output

My test program printed two lines. The first exercised the case I had just fixed; the second exercised one I had not. I ran it, saw only an error message and no output at all, and concluded the fix had done nothing. I removed it.

The mechanism: a program's printed output is held in a buffer and written out in batches. When a program stops abnormally, that buffer is discarded. The first line — the correct answer, produced by the fix I was about to delete — had been computed and buffered, and then thrown away when the second line killed the program. Absent output was not evidence of a failed fix. I had already watched this exact truncation happen to the example program earlier the same night, and still misread it. It cost three rebuild cycles to arrive back where I had been.

2. I patched five places that never ran

The part of the compiler that translates a program is about seventeen thousand lines, and it does not have one place that handles "the length of something". It has roughly ninety-two separate handlers, one per position a phrase can occupy — the handler for a phrase in the middle of a sentence is a different piece of code from the handler for the same phrase at the end. I picked the responsible handler by reading, five times in a row, and rebuilt after each. Every one of the five was never executed for this program.

The mechanism: reading tells you what a piece of code would do if reached. It does not tell you what is reached. I eventually tagged all thirty-three candidate sites with their own line number so the tag appeared in the compiler's output, rebuilt once, and read the answer directly. There were three responsible sites, in three different handlers, for what had looked like a single defect. The rule I should have followed: after the second wrong guess, stop reading and measure.

3. I nearly recorded nine program names I had guessed

The repaired test pins the list of programs whose generated text differs, so the set cannot drift unnoticed. I wrote that list by inferring names from written descriptions of the differences.

The mechanism: the descriptions group programs by cause, and a cause cannot be reversed into a list of names. When I measured, only three of my nine guesses were in the real set. Two programs whose names make them sound exactly like one of the described groups turned out to be perfectly identical on both routes. The list is now produced by a mode of the test that derives it from an actual run, and the code says never to fill it in from a description again.

4. My first version of the fixed test excluded the very programs that would show the problem

Some example programs are supposed to fail — they exist to demonstrate error handling. My first draft treated any program that exited with a failure code as "could not be run here" and skipped it.

The mechanism: that excluded five programs, including the two whose entire purpose is demonstrating runtime errors — precisely where a difference in error behaviour between the two routes would appear — and including the broken example itself, which fails by exiting with a code. I was excluding the error cases from the error comparison. Only a program that hangs is now treated as unrunnable, and the exit code is compared alongside the printed output. That single change is what surfaced the defect: skipped programs went from five to zero, and differing programs from zero to one.

5. I reported the cause to the maintainer before I had verified it

I described the defect as "one hardcoded name in a list", having found a piece of code that handled this exact shape for one specific function and nothing else. It was a real oddity and it was not the cause.

The mechanism: I had read a plausible explanation and reported it as a finding. The actual defect was broader — the same failure happened for an ordinary list held in a variable, with no function call involved at all — and the fix built on my explanation changed nothing when it shipped. A green build is not evidence that a change did anything; only running the program is.

What these have in common. Four of the five are the same error in different clothing: I trusted reading over measuring. The compiler is large enough that plausible explanations are cheap and almost always available, which makes them dangerous. The one instrumented build that finally settled it took the same five minutes as each of the five guesses that preceded it.

Where this leaves things

The visible output is one repaired example program and a version bump. The useful output is that a test which had been reporting success for months started measuring the thing its name claims, and immediately found a defect that had shipped. Every count that could have moved and should not have — the ledger totals, the debt census, the language decisions — is identical before and after, which is the only reason the repair can be trusted at all.

The five corrections above cost more time than the fix. That is not a complaint about the process; it is the argument for it. Four of the five were caught by running something rather than reasoning about it, and the fifth was caught by a check that had existed for a day.

Glossary

Reference for the shorthand used above. Terms marked new were coined since the previous daily.

Lane, or route
One of the ways a Hey program can become a running program. Three matter here: the newer Hey-written code generator (the one users get), the older C one, and the interpreter, which runs a program directly without building it.
Fallback
What happens when the newer generator meets a shape it does not handle: the whole program is quietly handed to the older generator instead.
Gate
An automated check with a recorded expected result. A check can be registered as expected-green or expected-red; a known-failing check is not a surprise, it is a tracked defect.
Tier
A group of checks run together. The fast tier is 116 checks; the heavy tier is 8 slower ones.
Ledger
The file listing every check and its expected result, with the reasoning for each. Because the reasoning lives there, it can go stale — three entries were corrected today for exactly that.
Ratchet
A check that records a running count of known debt and fails if the count rises. It permits the number to fall, never to rise. Ours is currently failing, and was already failing before this work.
Rotted check new
A check that no longer tests what it claims, usually because it looks for text that has since changed. It does not report a failure — it quietly stops being a check. Two were found this week, one of which no suite even runs.
The length property new
Asking how many things are in a list or record, written .length, .len, .size or .count. All four mean the same thing, which is why fixing one and not the others left programs broken.
Position new
Where a phrase sits in a sentence of code — the answer a function returns, the thing a loop walks over, an argument inside another call. Hey's newer generator handles each position with separate code, so the same phrase can work in one place and fail three lines later. Most of what remains before the older generator can be deleted is this, not missing features.
Instrumenting new
Making a program label its own output so you can see which part of it produced what. Used here to find which of thirty-three candidate pieces of the compiler actually ran, after five attempts to work it out by reading failed.
Buffered output new
Printed text is held in memory and written out in batches rather than one character at a time. If the program stops abnormally, that held text is discarded — so a crash can erase results the program had already produced correctly. This is what caused me to delete a working fix.
Byte-identical
Two paths producing exactly the same output, byte for byte. This project uses it as a standard of proof in place of "it seemed to work" — though as of this week it is no longer the standard for correctness, which is now whether the two paths give the same answer.
Landed / Verified / Deployed
Verified: on a branch, with reproduced evidence. Landed: committed and through the check battery. Deployed: available to users through the released route — the only one users feel. Everything on this page is landed. Nothing on it is deployed, and this checkout has no configured remote, so nothing has been pushed anywhere either.
