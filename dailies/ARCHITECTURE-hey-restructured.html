The whole diagram

Every stage of the restructured language, source text to running program. Each box names the file it lives in and the function you enter it through. Boxes that do not exist yet name the file they will be. This is a reference page, not an essay — find your bug's stage, take the file, go.

Corrected 2 August — where - is decided

Any diagram or note below that puts unary-versus-binary - in the tokenizer is superseded. The tokenizer always emits a MINUS token; the parser decides arity from context. Precedence, name lookup, imported operator meaning and numeric result types are likewise not the tokenizer's.

This matters beyond tidiness: the current implementation decides it by checking whether the previous character is in a set, that set is missing ], and that is why arr[0] - 1 fails with “undefined name” today. Moving the decision into the parser makes the whole family unrepresentable. See the review.

How to use this page

1. Find the stage on the first diagram.
2. Take the file and the entry-point function from the navigation table. Bookmark that table; it is the whole point.
3. Read what that stage is forbidden to do. Most defects in this codebase are one stage doing another stage's job.

Decisions needed from you — none. All three are ruled.

This block asked for three decisions, two of which blocked drawing. All three have since been answered, and the page has been reconciled to them. It is kept rather than deleted because what a document was blocked on is worth being able to look up.

1. How tightly do not and ! bind? — RULED. Ruby's rules exactly: ! binds tightest, not loosest, && tighter than ||, and and/or equal and loosest. && and || are added to the language. The order-of-operations table was unblocked by this and is written.

2. When do the saved expected outputs stop pinning the old compiler? — RULED, and the answer is not a date. Each byte-identity test first states what it was really protecting, then is replaced by a test of that contract; exact-byte tests remain only where the bytes are themselves the public contract. Each replacement must be mutation-proven — deliberately break the implementation and show the new test fails — before the old fixture is marked superseded.

3. Is the operator table generated, or written by hand and checked? — GENERATED. One registry, one host-side generator, per-stage projections, and a drift gate that regenerates and diffs against what is committed. Diagram 4 is the settled shape. The two design documents that disagreed are reconciled in its favour; see where the sources disagree.

Decisions on the language itself live on the standing decisions page, which is the current one to read. Nothing there is waiting on a maintainer answer either.

Diagram 1 — the whole pipeline

Source text to executable. Every box is a stage. Every arrow is named after the thing that crosses it.

Terms, once. A tokenizer splits text into words and symbols. A syntax tree records which operation contains which, so nothing has to be re-read as text later. Name resolution decides which x each x refers to. HIR and MIR are two written-down forms of the program between source and machine code: HIR carries Hey's own meaning and types, MIR carries machine-shaped types and instructions. Lowering means rewriting the program one step closer to the machine. LLVM is an off-the-shelf toolkit that turns a low-level text format — its IR, or intermediate representation — into real machine code for whatever chip you are on; Hey writes that text and lets LLVM do the rest. Arity is how many operands a symbol takes: the - in a - b takes two, the - in -b takes one.

What today's pipeline actually is, for contrast

There is no tokens box and no tree box today. stdlib/HeyParser.hey returns a list of forms with source locations — that is statement classification, not a tree. Its classifier ends by sniffing for punctuation: if the text contains a +, call it an expression (stdlib/HeyParser.hey:152 (the grammar report puts the same rule at :158)). stdlib/HeyAst.hey is not a tree either; its own header calls it an “AST-ish manifest” and nothing on the compile path imports it. stdlib/HeyExpressions.hey is a catalogue of command-line easter eggs — the name is a false friend. A search of the compiler and standard library for the words token, lex or lexer turns up comments, plus a handful of unrelated uses of the word token in the input and pattern-matching libraries. Nothing on the compile path.

Diagram 3 — the interpreter, on the same pipeline

The requirement is one pathway serving both: typing a line at the interpreter's prompt and building a program should go through the same code. Today the interpreter is at zero percent on that pathway. runtime/hey_repl.c contains no references at all to the HIR, MIR or LLVM modules — a count returns zero. It is a third independent implementation with its own splitters, its own precedence and its own table of built-in functions.

There are two possible shapes. The brief recommends the first, and this page draws it.

Why the first option, and what the second actually costs

A correction worth making, because the number in circulation is the wrong one. The measurement is:

cold run cache + COLD pipeline cache ....... 203.18 s
cold run cache + WARM pipeline cache .......   0.68 s
warm run cache .............................   0.01-0.02 s

The 0.019-second figure is a cache hit on unchanged source. Every line you type at the prompt is by definition a cache miss. The number the second option would pay per line is the middle one: 0.68 seconds. That is not an interactive loop. It also needs either an in-process linker or a just-in-time compiler — that direction has been probed but not built — plus a story for how a session's accumulated definitions survive a process boundary.

Three arguments for the first option. It is what “one pathway” means: one tokenizer, one precedence ladder, one resolver, so divergences like the three different bindings of not become structurally impossible rather than merely fixed. It retroactively upgrades the spec corpus — today an interpreter-only spec exercises zero stages of the compile pathway; under this option it exercises four of the seven, for free. And it keeps a fast loop without compiling every line, which is the actual product requirement.

What it costs: the front half of a 5,976-line file is rewritten, and the HIR walker is genuinely new code — it is not a port of the existing evaluator, because it consumes a different input. Size it as new construction, not as clean-up.

One line worth keeping open: make the first option the default and expose the second as an explicit command, for a hot loop the user wants compiled. Once HIR is the shared join point, leaving that door open costs nothing.

Diagram 4 — Operator Registry: generated projections and stage ownership

This diagram is a companion to the pipeline diagram, not a duplicate of it, and the two do different jobs. The generator boundary enforces consistency — no stage can hold a private copy of a fact. This table documents semantic ownership, which is a different guarantee: it stops a stage consuming a column it has no business acting on.

The failure it exists to prevent: the LLVM emitter consumes an instruction column, and must not conclude from that that it may reinterpret arithmetic semantics. Consuming a column is not authority over what the column means. Every semantic decision belongs to the registry; every stage below it is executing a decision already made.

ParserWhich declared form applies at this site — prefix or infix — from grammar context, and the resulting tree shapeArity forms, precedence, associativity and non-associativityInvent a precedence, or let an import change one. ** is non-associative: chaining is an error, not a right-associative default

Read the last row as the general rule. Every stage below the registry is executing a decision already taken. When a stage disagrees with the registry, the stage is wrong — and the reason to write that down is that the opposite instinct is what produced the current state, where one fact is decided in forty-five places and no two of them are quite the same.

The existence proof that this shape works

There are four incompatible operator-to-instruction maps inside stdlib/HeyLlvm.hey alone. Three of them fail closed on a symbol they do not know: they return nothing, and the caller has to cope. One of them falls through instead, returning a different operator's entry rather than refusing. It is unreachable today only because its single caller sits behind a character guard.

The fourth map, hey_llvm_cmp_word:5363, is the model: it covers all six comparisons in 19 lines, uniformly, and it is the only operator family in the tree with no recorded defect. Every comparison divergence in the ledger is about operand handling, never about which comparison got chosen. When the table is complete, it works. That is the whole argument for building one.

The surface the table must cover, exhaustively

21 rows. Arithmetic + - * / % and a leading -; comparison == != < <= > >=; logical and or not !; the range ..<; subscript; member access; and the statement forms let, set, state and bare =.

The absences are exhaustive and they matter more than they look. There is no exponent operator, no compound assignment such as +=, no && or ||, no bitwise anything, no pipeline operator, no null-coalescing, no ternary, and no inclusive range — ..< is the only range spelling. The ruling on operator overrides says a module may only reuse an existing operator symbol. The moment overrides ship, this list becomes the language's public contract. Adding an exponent operator is cheap now and expensive later — and note that it groups right-to-left, which the current string-splitting architecture structurally cannot express. So it is a mechanism change, not a new row.

Three things about specs a diagram should not hide

1. The corpus gate's instrument is bent. Zero fallbacks over 106 examples is not evidence of coverage. One example (examples/slot_table_accumulator.hey:24-27) admits in a comment that a hash table was rewritten as a stride walk because the remainder operator does not lower. The corpus is selected on the outcome being measured. It is a statement about the examples folder, not about Hey.

2. The byte-identity contract points the wrong way and has no exit. test/regression_hey_llvm_emitter.sh makes the old emitter the reference for the component whose purpose is to let the old emitter be deleted. So every improvement to the new one must first reproduce the old one's bytes, including its mistakes. A new front end will change the emitted output. No moment is scheduled when the saved outputs stop being “whatever the old one emits” and become the pipeline's own. This blocks the restructure.

3. The count discrepancy is unresolved, and part of it is the denominator. The program directive says 42 of 760 spec files invoke a build; its 760 is specs/language alone. A live search at this commit returns 18 of 988, and its 988 is the whole specs/ tree. So the two fractions are not over the same population. What is still unreconciled: a live count of specs/language by itself returns 773, not 760, and whether the 42 counts invocations rather than files. Do not quote either fraction without saying which directory it is over.

The MIR question, answered directly

Does MIR survive as-is, become a real structure, or get absorbed? It survives as a stage — but as a rebuild, not a clean-up. MIR is partly new construction.

The evidence that today's MIR is a placeholder. Take the checked-in pair for one program, specs/hir/020_functions_and_loops.hir and specs/mir/020_functions_and_loops.mir. The entire difference between them is: type names substituted, one cosmetic block marker inserted, one extra terminator, two extra header lines, and a changed schema string. The operand text is unchanged. HIR says store acc:Int = acc + i; MIR says store acc:i64 = acc + i. The right-hand side is still raw Hey source. stdlib/HeyMir.hey:285-286 states it outright: MIR expressions are raw text.

Three findings confirm it. Search stdlib/HeyMir.hey for any arithmetic or comparison operator and you get zero hits — it lowers no operators. Its one operator-shaped act is re-detecting the range operator textually at :221 to choose a loop shape — it performs a parse in order to make a lowering decision, which is exactly the anti-pattern. And one validator function is duplicated verbatim from HeyHir.hey:2344 at HeyMir.hey:254.

Job 2 is the load-bearing one, and it is what turns the LLVM emitter from a compiler into a printer. A printer is testable, portable to a second back end, and able to obey the rule already written in its own header. Without job 2, MIR is a rename pass and you would be right to ask why it is a stage.

Text or structure?

MIR stays a text file on disk and becomes a real structure in memory. The on-disk text form is load-bearing and it works: it is what the saved outputs pin, what the checker validates, what the dump flag produces, and what the cache stores. Do not throw that away. The defect is not that MIR is text. The defect is that MIR text contains unlowered source expressions. The same argument applies to HIR: keep the text, make it structural.

The source-path header problem, and the fix

Today a unit carries one source line — written at HeyHir.hey:2039, read back at HeyMir.hey:1132, re-emitted at :1138, validated at :1368. A unit built from many imported files carries one path. Per-file provenance is destroyed at HIR, not at MIR; MIR merely inherits the loss.

The fix is small. Provenance belongs on the record, not the unit header. The header carries a file table: one line per contributing file, with an id, a path and a hash — which also fixes cache keying, since today it hashes a single source hash. Every HIR and MIR record then carries a span: a file id, a line and a column. The tokenizer is where spans are minted, so this is free once the front end exists and impossible before it. Cost: one small integer per record. Benefit: an error message from the emitter can name a line in the file it came from, which today it structurally cannot.

The pattern to notice: four of these rules are already written down, in the headers of the very files that break them. Writing more rules will not help. The front end and a real MIR are what make the existing rules obeyable.

The rule this table encodes: anything that crosses a cache boundary is a text file, because the cache and the saved-output specs depend on it. Everything inside one run of the program is a structure. Today that rule is inverted at both places it matters: the front-end artifacts that should be structures do not exist, and the mid-pipeline artifacts that are text carry un-lowered text inside them.

The three biggest deltas, in order

1  The front end does not exist, and it causes most of what is downstream

Three missing stages. Every scattered decision below them — 45-plus precedence sites across 5 inconsistent notions, 16 disagreeing operator lists in HIR, 8 named plus 5 inline scanners in the new emitter (a second census counted six — unreconciled), 11 leading-minus decisions, 5 copies of one two-character guard, 2 character sets differing by 8 characters — exists because there is no token stream and no tree. This is the new construction, and it is the only new construction.

2  MIR is a placeholder, not a stage — rebuild, not clean-up

It lowers zero operators. The entire step from HIR to MIR is a type-name substitution plus a header rewrite. Its one operator-shaped act is re-parsing the range operator out of a string to pick a loop shape. Until MIR carries lowered operator forms, the rule written in the emitter's own header — never reopen source files, never parse expressions — cannot be obeyed by anyone. You should see this on the diagram, not discover it in month two.

3  The interpreter is a third implementation at zero percent, and fixing it is worth more than it costs

The recommendation is that it joins the pipeline at HIR and becomes a walker over HIR. Its value model and its built-ins already live in the runtime and are already shared — only its parser dies. The payoff is not just removing duplication: it retroactively converts 91 percent of the spec corpus from exercising zero shared stages to exercising four, without rewriting a single spec. Compiling every entry instead would cost 0.68 seconds per new line today, not the 0.019-second warm-cache figure — that number is a cache hit on unchanged source, and a typed line is by definition a miss.

What could not be drawn, and why

Seven things. Each is a box that would be hand-waving.

1. How tightly not and ! bind. Three different answers across the paths today. A documentation page asserts that all maintained paths share the same precedence — that sentence is false. Needs a ruling before the parser is written. Whichever way it goes, three of five paths move.

2. What a syntax-tree node is physically made of — the largest unknown here. The front end is to be written in Hey itself. Hey has no algebraic data types, no pattern matching, no closures beyond one binding form, and no lambda syntax. So a tree node has to be a boxed map, which means every node access is a boxed map lookup — and collections are 45 of the 344 runtime symbols the new emitter cannot reach, the remainder operator does not lower, and the new emitter cannot compile itself today. The compiler's own core data structure needs language features the compiler cannot currently compile. Three ways out are visible — write the front end against the interpreter first, complete the collection surface first, or add a record type to the language — and none can be sized without a build. This is the schedule risk that is not on the phase list.

3. The byte-identity contract has no exit. See the decisions block at the top.

4. The interpreter's resolver is a different function from the batch resolver. A typed line resolves a delta against a scope that persists across entries, including redefining something bound three entries ago. The entry point is named; scope persistence is not designed — in particular, what happens when an entry redefines a function an earlier entry captured.

5. Actor lowering does not fit the diagram cleanly. The new emitter has a separate two-pass actor path covering 8 of 26 operations; one tail-call form has no branch at all; one operation is missing from all three paths. Whether actors get their own family of MIR operations or ride the ordinary call path is undecided. One MIR box is drawn; it may be two.

6. The emit-C path and its fast sub-path have no home in the target. The fast sub-path copies characters verbatim into C, so C's order of operations applies rather than Hey's. It is a fifth set of semantics. It is drawn as a deletion, but it is reachable today and nobody has ruled it out of scope in writing.

7. The spec count discrepancy. 42 of 760 (specs/language) versus 18 of 988 (all of specs/), with specs/language itself counted at both 760 and 773. Unreconciled.

Where the sources disagree

The operator table: generated, or written by hand and verified? — RESOLVED 2 August, and the two positions turn out to converge. Both documents were right about the thing they were each protecting.

The architecture-diagram brief drew a generator producing both derived copies from a normative file, with a drift gate over the result.

The single-source-of-truth design refused to generate, and its reason was sound: the C compiler needs the derived C file in order to build, and a Hey generator needs the C compiler in order to run. That is a hard cycle, and it is the same cycle the node-schema generator would have hit.

What dissolves it is the host-generator ruling, made for the node schema and applying identically here: the generator is written in a language already present in the build environment — Ruby, Python or C — and never in the Hey being built. Its output is checked in. The build does not run it; make verify regenerates and diffs against what is committed. There is no cycle because Hey is never on the generating side.

So the objection lands on a design nobody is now proposing. “Checking the generated file in makes it a cache that needs a drift guard anyway” is true — and the drift guard is the design, not a concession to it. “Another language's generator makes that language a prerequisite for building Hey” would be fatal if generation were a build step; it is not. Building Hey needs only the checked-in output. The host language is a prerequisite for changing the table, not for building the compiler, and that distinction is the whole of the disagreement.

The single-source-of-truth design's own name for its alternative — “emit once, verify always” — is an exact description of what is now ruled. The two documents were never far apart; they were arguing about whether the generator runs during make, and it does not.

Path: docs/language/operators.tsv, the single-source-of-truth design's choice, not the standard library's. The normative file is not consumed by any program at run time — only the derived copies are — so putting it in stdlib/ would imply a dependency that does not exist. This last one is the orchestrator's call rather than a maintainer ruling; say so if you want it elsewhere.

A second, smaller disagreement, already flagged above: the number of spec files that invoke a build. 42 of 760 in the program directive (over specs/language), 18 of 988 from a live search at this commit (over the whole specs/ tree), with specs/language itself counted at 773 here and 760 there. A third census, the one behind The Answer Key Cannot Be One of the Contestants, uses 760 for specs/language and 964 for specs/language plus specs/compiler. Nobody has reconciled the three.
