Hey architecture · canonical current reference · 28 August 2026

One language. One meaning. One fast path.

Hey’s design is not complicated to state: write small Ruby-like programs with functions and actors; let the compiler decide what every name and operation means once; then carry that meaning all the way to machine code without guessing again. Most of the architecture now exists. The work in front of us is to remove the remaining places where two paths still disagree, and to prove the fast path on real programs.

Where Hey stands now

  • 0.99.554a is a development checkpoint, not a certified release.
  • The self-hosted compiler path is real. The resolver, HIR, MIR and Hey-owned LLVM emitter are not a paper design.
  • The 91 pinned LLVM fixtures now agree between the native and Hey emitters. An older “90/91” diagnosis was proved to be stale-artifact measurement and is closed.
  • The wider examples corpus is not yet at parity. Four examples still show genuine native-vs-Hey LLVM divergence, and other examples fail closed before comparison.
  • The release verifier itself still needs hardening before it can certify anything safely. The checked-in runner still exposes the old resource-bound interface and does not mechanically enforce the immutable-HEAD/tree-boundary contract documented for certification.
  • Performance is still a product blocker. In particular, method-form map update can still take an O(map) path where equivalent builtin update is flat. That keeps real 1BRC far from the native target.

The architecture in one picture

Read this left to right. The key boundary is between deciding meaning and carrying meaning. Later stages are allowed to optimize; they are not allowed to rediscover which function, field or intrinsic operation the programmer meant.

1 · SourceReadable values, functions, modules, actors and jobs.
2 · ParseTurn characters into structure. No semantic guessing.
3 · ResolveDecide which binding, function, module and operation each occurrence means.
4 · HIRCarry those decisions in a compiler-friendly program representation.
5 · MIRMake execution, ownership and effects explicit enough to optimize safely.
6 · LLVMLower mechanically to native code. Do not recover meaning from spelling.
The rule underneath the whole compiler: names are for people; identities are for the compiler. Two functions may have the same spelling and still be different functions. Two source spellings such as put(m,k,v) and m.put(k,v) may be different text while denoting the same operation. The resolver should settle both questions before ownership or code generation begins.

What is already real

A real self-hosted pipeline

Hey has a structured path through parsing, resolution, HIR, MIR and LLVM. The goal is no longer to invent that pipeline; it is to make it the single trustworthy authority for the whole product.

Semantic call identity

The compiler can keep same-spelling functions distinct instead of accidentally linking both calls to one body. Missing target/link facts can fail closed rather than silently guessing from a name.

Fixture-level emitter parity

The native and Hey emitters agree on the 91 pinned LLVM fixtures. This is useful evidence, but it is deliberately not described as whole-corpus parity.

The stage-0 runaway has a real fix

The return-cleanup leak that drove resolver processes into multi-gigabyte growth was repaired at the lifetime boundary. Bounded validation collapsed the resolver to a low, stable footprint instead of merely raising a limit.

The immediate path: make the verifier trustworthy, then make the compiler fast

The next five closures

1 · Safe verifierHarden resource bounds and certification invariants.
2 · Explain the REDsCollapse the release failures into causal families; separate pre-existing baseline from new regressions.
3 · Corpus parityFix four genuine emitter divergences and classify refusals.
4 · Ownership truthReplace textual ownership inference with structured facts.
5 · FASTClose MAP_PUT, then prove 1BRC, fannkuch and web under fixed identities.

These are completion gates, not a promise that every subtask must happen serially. Static investigation should run in parallel; only heavyweight local compiler executions are serialized.

How the team should work

The orchestrator should be an integrator: it owns the queue, decides what evidence is sufficient, keeps the product trunk moving, and merges bounded verified slices. It should not spend the day doing every grep and compiler experiment itself.

Parallel by default

Static source tracing, log attribution, fixture design, generated-artifact provenance, MIR-scan census, documentation, Linux inspection, and one-divergence-per-agent analysis can all proceed at the same time.

Serialized on purpose

Self-host builds, resolver runs, full release gates, large corpus sweeps, profilers and benchmark timings share one local heavyweight token. That protects the machine and keeps benchmark evidence uncontaminated.

A component is not complete because a narrow gate printed green. It is complete when there is one semantic authority, the real product path uses it, fallback is zero or explicitly fenced to bootstrap, the negative controls still bite, and the measured cost curve matches the claim.

What “fast like a systems language” should mean

Hey should not publish a giant speed multiplier as a substitute for proof. The useful ambition behind the Mojo comparison is architectural: high-level syntax should not force high-level overhead when the compiler can prove a lower-cost representation. For Hey, that means measuring three independent things:

Compile speed

Cold and warm compiler timings on named workloads, with parser/resolver/lowering attribution and no overlapping builders.

Generated-code speed

Real programs such as 1BRC and fannkuch should approach the relevant native implementations for the same work, rather than only winning microbenchmarks.

Server speed

Web throughput and latency should be measured per core, under a fixed concurrency model, with sidecars/fallbacks identified so the number belongs to the path we think it does.

The product promise

Ruby-like ergonomics over simple functions and actors; native performance underneath. The programmer should not have to choose a “fast syntax.” The compiler’s job is to preserve the simple language while proving when values can stay native, storage can be reused, and calls can lower directly. The roadmap is finished only when that statement is true in the real product, not merely in the architecture diagram.
