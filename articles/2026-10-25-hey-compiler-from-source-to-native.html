How the Hey compiler turns source into native code

Partly works General correction: proposed

You write let x = 2, then return x * 3. You can already work out the answer. The compiler should keep those same facts as it builds native code. This page follows that small function through the design, so you can tell which pass owns a wrong result.

fn answer()
  let x = 2
  return x * 3
end

The required result is 6. The proposed path connects the read of x to its initializer, proves the multiply fits, and emits native arithmetic. An earlier baseline lost the local's Int fact; the newer captured Hey graph preserves it through range analysis. Compilable LLVM alone doesn't tell you that the analysis worked.

Earlier executable snapshots and their limits

In the earlier recorded build3 run, five closed, zero-parameter fixtures passed through source admission, high-level intermediate representation (HIR), mid-level intermediate representation (MIR), LLVM and native test hosts. These checks stop at the AST: they don't execute those programs or prove the later compiler passes.

Recorded results below refer to named executable snapshots, not whatever binary happens to be in the working tree. The evidence note gives their hashes and exact limits. The release history and older audit sections remain optional background; they don't certify the replacement compiler.

The same value, with more facts at each step

  • Parse the expression's structure. Keep precedence, source spans and resolved declaration identities through structural sugar lowering.
  • Connect definitions to uses. Infer from those edges and revisit only the operations affected when a fact changes.
  • Make execution paths explicit. Each MIR value has one definition; branches and loops supply values at their joins.
  • Choose storage and calls together. An Int needs a range or overflow strategy before it can use a machine integer. Callers and callees must agree.
  • Insert ownership from actual uses. Preserve borrows, regions and String16/SDS; let LLVM encode the completed plan.

What has to work before you can trust a native program?

Decided and coming Each step must preserve the program's behavior and pass its own checks. A compiler that builds from the C seed hasn't yet proved that it can compile itself.

  1. Verify the direct Hey HIR cutover. Use one fresh binary from source admission through typed HIR, semantic mid-level intermediate representation (MIR), analysis and physical planning. Fix observed defects. Keep the canonical syntax tree, source diagnostics, resolved identities and scopes; keep machine calling conventions in MIR.
  2. Make every borrowed read name its owner. Carry owner dependencies as value operands, including through branch joins. Keep transitive owners alive: a view into a nested value also depends on the storage behind that value. Distinguish a borrowed view from a read that returns an owned value. Promote escaping views before return, owning storage, publication or consuming calls. Long String16 interior views need a copy on promotion unless a proved owner link supports sharing; retaining a non-owning range is insufficient. Range element reads must return scalar SSA values, replacing the singleton thread-local scratch slot.
  3. Choose safe lifetimes from proven facts. Worklists propagate escape, freshness and uniqueness facts. Use per-statement, per-iteration and per-call memory regions where proved safe. Preserve reference counting and live-object region holds; end loans before release or reuse, and close each region exactly once after normal or failure cleanup. These regions and allocation-free eligible borrowed reads are required in this correction.
  4. Select and independently verify every physical operation. Check representations, conversions, call signatures, branch arguments, owner edges and cleanup. Deliberately corrupt plans to test rejection. Unsupported operations must remain explicit failures.
  5. Write the terminal LLVM encoder in Hey. Translate decisions already present in verified MIR. Check LLVM validity, native results, exact overflow behavior and runtime linkage. The emitter must never reconstruct source expressions or decide missing lifetimes.
  6. Complete the language and prove self-hosting. Carry imports and exports, full grammar, aggregates, callable values, failure/recovery and actors through the same path. Compile the full compiler from stage A to B, then B to C; compare the required artifacts and execute both results. A small arithmetic suite can't establish this.

Try a view that survives a branch and then leaves its owner's scope. The required outcome is an independently owned value before escape, or a valid longer-lived owner established by the plan. A disappearing owner must never leave a dangling view.

Can we learn from MLIR and write the machinery in Hey?

Yes. No MLIR dependency has been added or is planned. Multi-Level Intermediate Representation (MLIR) is a reference for compiler structures and transformations. Its language reference describes typed values, operations, blocks and block arguments. Hey needs a small graph core with use lists and operations to create an operation, replace uses, split a block and update an edge.

  • Read the referenceUnderstand graph invariants and conversion contracts.
  • Implement the needed operations in HeyBuild deterministic analysis and structural lowering over Hey values and blocks.
  • Compare behavior and inspect outputCheck overflow, calls, branches, borrowed lifetimes and failure cleanup.

That is a limited internal application programming interface (API), not a full MLIR clone. MLIR's conversion framework is useful for understanding how types, operations and block arguments change together. Its structural regions contain blocks; Hey's memory regions govern allocation lifetimes. They solve different problems.

You can inspect LLVM output to learn how a lowering works. Several instruction sequences can implement the same behavior, so matching emitted text isn't the correctness test. The implementation applies explicit rules; this is neither machine learning nor guessing code from examples. MLIR's LLVM target documentation separates substantial conversion from final translation. Hey's plan similarly puts the decisions in MIR before the terminal encoder.

If an MLIR route existed: replace one pass at a time with Hey, give both routes the same inputs, and compare behavior plus required graph invariants. Delete the replaced route after the checks pass. That's a hypothetical migration method; today's work implements the needed passes directly in Hey.

Carry the initializer all the way to the return

The abstract syntax tree (AST) records which expressions contain which other expressions. Resolution attaches the selected declaration to each name. HIR adds language facts. MIR makes execution paths, storage and lifetime explicit. LLVM, the machine-code toolkit, receives the decided operations.

If you change the initializer to 4, the read, multiply and result facts must change with it. A name alone tells the compiler none of that. It needs the numeric connection between this read and the definition that reaches it.

What the directly defined Hey records must expose

Operations declare their value operands, results, nested bodies, successor blocks, effects and source origins. Direct fields and graph operations let passes build definition/use and call indexes once. Semantic rules still need implementations: a node tag or constructor doesn't infer a type or prove a lifetime.

The source chain uses HeySyntaxTree, HeyProgramResolution, native Hey HIR and the HeyIr graph. A new terminal LLVM encoder remains to be implemented; the retired emitter is not a fallback. Saving their records as JSON is transport. Later stages read declared fields and identities; they don't recover expressions from text.

Parse the whole arm before lowering case

Try this grouping: case false with when false or true. The arm's expression is false or true, so the comparison is false == (false or true). Inserting equality tokens before parsing can instead produce (false == false) or true. Those expressions have different answers.

Sugar is shorthand with the same behavior as its expanded structure. Its lowering must keep evaluation order and synthetic-node origins, and evaluate an effectful subject only once. Resolution decides which declaration a receiver call selects. Later HIR transformations work on these structural facts.

2 · Why one chain: the audit found six side roads

In plain EnglishBefore the overhaul, the main chain existed, but six side roads still let a fact into the program a second way. Whenever two parts of the compiler read the same program separately, they can disagree. That's why the same kinds of bug keep coming back.

One example: three readers, no referee

When two readers disagree, what you see depends on the program: a name resolves in one place but not the other, or a branch means something slightly different. Each symptom tends to get a local patch, and the cause survives (that's our reading of the history, not a measured count). Ownership written as text and operations matched by spelling repeat the same pattern further down the chain. With one reader per fact, there's no second reader to disagree with.

3 · Builtins are typed declarations in the built-in library

Internal only. The extern declaration form described in this section is for Hey's own built-in library and for people working on the compiler. The parser and resolver refuse it outside the built-in binding module:3 user code, packages, the REPL and hey run all get an error. It is never shown to users and never taught in the user documentation (Maintainer ruling). Users write ordinary functions such as fn shout(name), with no types and no arrows.

In plain EnglishA builtin is a function the runtime implements in C, such as trimming a string. Today the compiler mostly works out a builtin's type by matching its name against lists. After this release, each builtin is declared in the built-in library with its types, and the compiler treats a call to it exactly like a call to your own function.

Mature compilers split builtins into two layers. A small, closed set of true primitives lives inside the compiler, because the language can't express them. Everything a user calls is declared in the language's own source:

  • Rust declares intrinsics in library/core/src/intrinsics/mod.rs, for example pub const fn ctpop<T: Copy>(x: T) -> u32;. The compiler keeps its own expected signature only to refuse a declaration that disagrees (check_intrinsic_type).
  • Swift writes its standard library in Swift. Bool is an ordinary struct over a compiler-provided Builtin.Int1.
  • Koka writes pub extern (++)(x : string, y : string) : string with a C symbol for each backend. A ^ on a parameter marks it borrowed, the same fact Hey keeps today in a separate table.
  • OCaml writes external name : type = "c_function". The manual says the arity "is automatically determined from its OCaml type".
  • Go and Zig keep a compiler-internal set of builtins, but only for operations generic over types the language couldn't express (Go's len works on five unrelated kinds). Ordinary runtime functions are plain source.

Why the generated signature table and the name lists are cruft. They're a second vocabulary next to Hey source, and it drifts: the HIR lists say they were "transcribed" from the C emitter. A type that lives in a list never reaches the resolver, the docs or an editor. And the lists break the design rule against classifying operations by name. The physical calling details (C symbol, register or boxed slot, borrowed or owned) are legitimate compiler data. They stay, generated from the declarations or checked against them, as Rust checks its intrinsics. The numeric runtime target identity is resolver output and stays too.

How a declaration is kept honest. Each declaration has four fields: the name (trim), the parameter types with a borrow mark on each borrowed parameter (as in Koka), the result type, and the runtime provider, which names the registered runtime function. The exact internal spelling is not shown here and is not part of the language. The extern states semantic types only (String, Int, Bool ...), never str or i64, because representation stays MIR's choice. A verifier, the Hey version of Rust's check_intrinsic_type, refuses the build unless every extern names a registered runtime function, its arity matches that function's LLVM ABI row (the table entry saying how arguments and results pass in machine terms; ABI means application binary interface), its borrow marks match what the C code really does, and no runtime function lacks an extern.

What stays in the compiler universe: a few builtins whose result depends on their argument, such as len (String, Bytes, arrays or maps), slice (String or Bytes), get, and the compiler-written Ranges.until. With generalisation (section 4) some become externs with a type variable;4 the rest keep a small typing rule keyed by the extern's resolved identity, never by spelling. That list can shrink to a handful but not to zero, which the design rules allow. User code never writes it; your code reaches C through native packages.

When a fact changes, follow its users

Proposed Inference works out facts you didn't annotate. For the local example, the path is initializer → binding definition → read → multiply → return. Build those dependency edges once. A worklist is a queue of operations whose inputs changed; processing one operation can enqueue its users.

  1. Seed the facts. The literal is Int, exactly 2. Its read depends on that definition.
  2. Apply the operation's rule. With 2 and 3, multiplication yields Int and the range [6, 6]. Type and range remain separate facts.
  3. Wake only affected users. A changed result queues its consumers. Already queued operations don't need another queue entry.
  4. Stop when facts stop changing. Joins must be monotone: repeated updates can't oscillate between incompatible guesses. Growing range or context domains need a documented widening rule that safely merges distinctions.

Which of these two “unknowns” can become Int merely because one incoming path is Int?

Not analyzed yet: bottom

Bottom means the solver has no contribution yet. Joining it with an Int fact yields Int. This is analysis state, not a legal runtime value.

Genuinely unrestricted: dynamic

This input may have other kinds. Joining it with Int doesn't prove it is Int. Required dynamic behavior must survive.

The answer is bottom. Using one “unknown” code for both cases can either lose a fact forever or incorrectly narrow an unrestricted value. MLIR's dataflow tutorial makes this distinction explicit; the proposed Hey solver uses it without changing Hey's source-language rules.

A call summary describes a relationship

fn identity(value)
  return value
end

The useful summary is “the result follows the argument.” One visible Int caller doesn't make every possible call Int-only. Hey stays annotation-free, with its existing warning, strict-mode and runtime-failure behavior. A failed narrowing proof isn't automatically a static type error.

Build the call dependency graph once. Mutually recursive functions form a strongly connected component: analyze their changed summaries together, then notify dependent calls. Use finite abstract call contexts and canonical keys; merge growing contexts so recursion can't request a new specialization for every concrete argument. Decide any physical specialization with the call-boundary plan below.

At a branch, keep the value from the path that ran

Proposed Static single assignment (SSA) means each intermediate value has one definition. A source assignment creates a new value; it doesn't change earlier reads. At a control-flow join, a block parameter receives the value supplied by the incoming path.

then: v1 = 2; jump join(v1)
else: v2 = 4; jump join(v2)

join(x): return x * 3

This is illustrative MIR, not Hey source or emitted serialization. The result is 6 on the first path and 12 on the second. A branch supplying a String would require the applicable Hey behavior; the first predecessor alone can't establish Int.

The selected algorithm is Braun and colleagues' sealed-block construction. Finish a predecessor's definitions before adding successors. Install the placeholder before following loop predecessors; seal only when the predecessor set is complete. Removing a trivial join rewrites its uses and corresponding incoming arguments together.

Hey's adaptation represents joins as MIR block parameters and edge arguments. Verify that each use is dominated by its definition, every edge supplies the right arguments, and reachable reads have a definition. Addressable storage still uses slots when semantics require them. The simple construction needn't produce minimal SSA for arbitrary irreducible control flow; valid nonminimal SSA is a different issue from wrong code.

A native result needs a caller that agrees

Proposed A value's representation is how it occupies machine storage. Its application binary interface (ABI) says how it crosses a compiled call. Choose parameters, results, ordinary values, block arguments and necessary slots together; insert explicit conversions at boundaries that need a different representation.

Same native representation

two() returns i64
      ↓
answer() receives i64
      ↓
multiply i64 by 3

Illustrative physical plan. The call and return agree; no generic carrier is needed here.

The conversion is a MIR operation with ownership consequences. LLVM encodes it.

Would knowing “Int” make 9223372036854775807 + 1 safe as an unchecked machine add? No. Hey integers are arbitrary precision. Prove every relevant intermediate fits signed 64 bits, or preserve exact arithmetic through a checked operation and promotion path. A final result that fits doesn't excuse an overflowing intermediate. Analyze canonical literal data before narrowing it to a machine integer.

Keep Float bits and exceptional behavior; don't assume fast-math rules. Keep String semantics separate from its German String16 carrier and SDS backing storage. A generic carrier remains legitimate where Hey requires dynamic behavior. The mistake is assigning it universally before analysis.

MLIR's conversion framework illustrates coordinated value, operand and signature conversion. Hey's correction applies that principle in its own numeric records. The emitter receives verified operations; it doesn't repair a mismatched call by rediscovering types.

Keep an owner until its last required use

Proposed Once execution paths and representations are explicit, work backward from uses. Liveness asks whether a value will be needed again. Each call contract says whether an argument is borrowed or consumed. Those facts decide where to retain, transfer or drop an ownership credit.

Predict the required behavior: if an update is followed by a read of the old value, can it overwrite storage that both values share? No. Preserve the old value. If the old value is dead, reuse still needs a uniqueness check and compatible storage. “Last use” alone doesn't prove exclusive access.

Perceus supplies the reference-counting and reuse model. An extra consuming use needs an ownership credit; a final consuming use can transfer one. Reconcile branches, loop edges, early returns and failures. Plain scalars need no heap owner. The paper's garbage-free result is for cycle-free programs, not a general cycle-collection promise.

Hey also needs its own region and borrow checks. A borrowed range must not outlive its backing storage or escape a reset region. An owned return from a borrowed input needs the declared ownership conversion; a borrowed range isn't automatically an owned allocation that can be retained. Preserve inline short Strings, long String16/SDS ownership and existing language behavior.

LLVM prints the selected operations and cleanup paths. It neither discovers the last use nor infers ownership from source spelling. Type inference, SSA construction, representation planning and ownership insertion remain distinct passes with explicit contracts between them.

To prove nothing still uses the old code, its entry points are rigged to crash, and the compiler must still build itself, the test corpus and real applications.

A negative control is a test that must fail when the thing it guards is broken. Each trap above is one. 7 · Optimizations that follow, on the one chain

In plain EnglishOnce the cruft is gone, the same release makes both the compiler and compiled programs faster. (The Maintainer had first put performance in a later release; he then added it to this one: "Make sure we include compilation optimizations as well as runtime optimizations once we have the new compiler design fully implemented and the cruft removed.") Every optimization is built on the one chain, uses typed MIR facts, and helps any program that does the same thing. None is shaped around a benchmark.

The numbers below come from Hey's fixed benchmark set: W1 to W12 are small workload programs with C versions for comparison, and 1BRC is the One Billion Row Challenge program (read weather readings, report each station's minimum, mean and maximum), run here at 5 million and 10 million rows.

Runtime

  • Uniqueness and last-use facts in MIR, for in-place updates even under COW0. W9 runs 1,309.5G instructions under COW0 and W10 680.9G, against under 2G with COW1, and every 1BRC COW0 case (5M and 10M rows) times out at 300 seconds. These are whole-value copies MIR can prove unnecessary: at a value's last use, consume it instead of copying it.
  • A map and hash redesign. W6 and W11 run at about 2.6 times C's instructions, and W11 roughly doubled over three releases (6.40G to 12.75G). An earlier index design clustered keys in the table, so the map moves to SwissTable-style probing.
  • Allocator follow-ups, such as the page overhead tiny programs pay: an idle one-second program uses 4.8 MB against C's 1.7 MB.

Compile time

Inference and specialisation (section 4) feed both halves. Inferred parameter types let MIR keep Ints in registers, and the instance cache, which reuses a copy within one program's compile, keeps the extra copies from undoing the compile-time gains. Reuse between modules is planned, not built, and no compiled work is shared between programs. Every optimization is measured red-then-green on instructions and peak memory against 604a, 606a and C.

9 · Where the compiler is going

In plain EnglishAn audit of the compiler documents against current research turned up six upgrades worth making while the code in question is still being written. None of them is built; each is planned, and each changes how the compiler works inside, not the language you write.

Widening to Value, on a proper footing Planned

Section 4 says that when a variable is an Int on one path and a String on another, Hey doesn't reject the program; it widens the type to Value. Today that's done by a join over a small lattice of types, without a clean way to generalise. Algebraic subtyping is the theory for exactly this: it infers the most general type a function can have even when types may fit inside other types, by tracking lower and upper bounds instead of forcing two types to be equal. Simple-sub is a short, practical version of it. Hey plans to use it as the formal model of "widen to Value" in the inference phase, while that code is still being written.11

A checked report of what runs in place Planned

Perceus (section 5) frees a value at its last use and reuses its memory when it can. Koka's later work, FP², goes further: it proves when a whole function runs with no allocation at all. Hey won't add a keyword for that, because the language has one surface. Instead, the planned MIR update report becomes a checked fact: a test can assert that a named function allocates nothing, and MIR verifies it. Reuse is limited to the current frame, so the guarantee stays local and easy to check.12

Rebuild only what a change really affects Planned

The Rust compiler records which facts each step read, with a fingerprint of each. When you edit a file, it recomputes the changed facts, and if a fingerprint comes out the same, everything that depended on it is skipped: that's early cutoff. Hey plans the same chain: a hash per file's syntax tree, then the resolution facts, then a hash per function's type summary, so a dependent recompiles only when a fingerprint it read has changed. It's the most likely route to the goal of a much faster self-compile.13

Compiler nodes as flat arrays with integer IDs Planned

Hey's compiler nodes are records backed by maps, so every node is its own allocation and every field read is a lookup. Carbon's toolchain stores its parse tree as one flat array, where a node is an integer index, and stores each identifier once in an intern table, so two names compare as two integers. Hey plans the same layout for its nodes, plus identifier interning. Fewer allocations and better cache use make the compiler faster, and comparing interned IDs fits the rule that facts come from identities, never from spellings.14

Actor messages: move when unique, share when immutable Planned

Erlang copies every message into the receiver's heap. That's simple and isolates failures, but copying costs time. Swift's region-based isolation lets the compiler hand a value to another task when it proves the sender keeps no reference to it, and Pony sends messages with no copy at all. Hey already shares immutable message values instead of deep-copying them; adding a MIR uniqueness fact at send means a value the sender holds alone is moved, with no count change. Hey keeps Erlang's failure isolation without Erlang's copying.15

Measure clang's share before choosing a debug backend Planned

Zig wrote its own x86 backend, and Rust has Cranelift as an alternative backend, both because LLVM dominates debug-build time. Hey keeps LLVM until it knows how much of its own build time clang really takes. The phase profile will report clang's share as a deliverable, and the backend question will be answered with that number, not by guessing.16

What a useful green check looks like

A verifier checks the invariants the next stage relies on. A negative control deliberately breaks a required fact and confirms the check notices. Golden snapshots record expected output; differential tests compare behaviour across implementations; round-trip tests check that decoding and re-encoding give the same thing. None replaces the others: two consumers can agree on a wrong producer fact, and a stable snapshot can preserve wrong behaviour.

Ordinary builds turn off per-pass checking for speed, but the LLVM input boundary still validates MIR. Under the consolidation plan, the ownership check can no longer be switched off. The C interpreter stays as an independent oracle so a differential test never compares native code with itself.

Inspect the syntax tree yourself

This uses the same lexer and parser that resolution uses:

import 'stdlib:HeyTokens'
import 'stdlib:HeySyntaxTree'

program
  let code = "program\n  let total = 2 + 3\n  says total\nend\n"
  let lexical = read_source_text_into_lexical_admission(code)
  let parsed = HeySyntaxTree.parse_unit_lexical_admission(lexical, 0)
  if !parsed.ok
    fail parsed.error
  end
  says json_canonical_text(parsed.value.tree)
end

It prints a syntax_tree containing an infix_expr for the addition, with sealed unit and node identities (the 0 is this unit's id). By contrast, the old HeyParser tree records the same binding as expr: "2 + 3", a string later stages had to re-scan; that's exactly what the overhaul removes.

Before you propose an optimization: three questions
  1. Which stage owns this decision? Grouping: syntax. Which declaration: resolution. Language types: HIR. Representation and lifetime: MIR.
  2. What fact permits it? For example a resolved identity, the last use of a named value, and a successful uniqueness check.
  3. What happens when the fact is missing? Missing required facts refuse; a missing optional fact keeps correct general code.
Glossary
AST (abstract syntax tree)
The tree the parser builds: structure, not characters.
(unit_id, node_id)
The identity of one node: which source unit (file) and which node in it. Facts are keyed by this, never by spelling or line.
Resolution
Deciding which declaration each name refers to.
IR, HIR, MIR
Intermediate representation: the compiler's description of the program between source and machine code. HIR is high-level (meaning, types); MIR is mid-level (steps, storage, ownership).
LLVM
The compiler toolkit that turns Hey's low-level instructions into optimized machine code.
ABI
Application binary interface: how compiled code passes arguments and results.
Builtin, extern
A function implemented by the runtime in C; an internal declaration (never user-written) gives it a typed signature.
Inference, bottom, dynamic
Working out facts from operations and dependencies; analysis has not contributed a fact yet; no narrower runtime fact is proved. Bottom and dynamic must remain distinct.
SCC (strongly connected component)
A group of functions that call each other in a cycle; solved together.
Specialisation (monomorphisation)
Making a separate machine-code copy of a function for specific concrete types.
Value
Hey's general boxed type, used where nothing narrower is known.
Perceus, dup, drop, borrow
Precise reference counting placed by the compiler: add a reference, remove one, or lend a value without either.
COW0, COW1
Runtime copy-on-write modes. COW1 (default) shares values and copies only on a shared write; COW0 (HEY_RC_COW=0) turns sharing off, so every copy is a full clone.
Negative control
A test that must fail when the thing it guards breaks.
stage0, seed, bootstrap, oracle
Stage 0 is the C compiler (heyc.c) that built the first Hey compiler up to 0.99.605a. In 0.99.606a the first compiler is built from the seed, C printed from the compiler's own MIR; stage 0 is outside make all and make test. The oracle is the C interpreter, kept as an independent reference for tests.
