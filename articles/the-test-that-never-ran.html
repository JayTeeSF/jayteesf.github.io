The Test That Never Ran

Hey's plan for a faster interactive session rests on one thing: code compiled on the fly must be able to call the runtime functions already loaded in the running program. A test said that worked. It never tested it. Verdict up front: the plan survives, the mechanism changes. Someone finally ran the missing test on Linux, where it fails outright — and the chase produced something better than what it replaced.

Status: measured research, unshipped plan

Everything below was measured — Arch Linux x86-64 and an Apple M-series Mac, both LLVM 22.1.8. The just-in-time interactive session is a design, not shipped software; unshipped means not-yet-built, not rejected.

TL;DR

  • Verdict: the design stands — stop relying on the loader. Hand the compiler the host's function addresses directly. No link flags, and it fails at compile time when a runtime function is renamed rather than at the first call in a live session.
  • The test that "verified" this never verified it. The probe defined its own function in generated code and resolved against that. The mechanism the design rests on — reaching a function in the host program — was switched on and never used.
  • Same mechanism, opposite defaults. On Linux you add a linker flag to make it work; on macOS you add one to make it fail. Not a platform quirk: one rule, seen from two sides.
  • We published the untested claim; this corrects it. Our earlier article listed host-function resolution among things a probe had measured. It had not. That article now carries a dated correction.
  • A sourced prediction was wrong. Per-thread variables do fail across the boundary — but not for the predicted reason, and they fail loudly rather than silently returning a wrong address.
  • Reproduce it: four small C programs, two link lanes each, pass/fail outcomes rather than timings — a busy machine cannot change the answer.

1. What the design needs

Hey's interactive session is slow because every turn builds a real executable and launches it. The plan is to skip that: compile each new line straight to machine code inside the running program and call it. For that to work, the fresh fragment must reach roughly 571 runtime functions already in the host program — string handling, memory, actors. It does not contain them. It only names them, and expects someone to fill in the addresses.

The mechanism in one line

The compiler was told to look up unknown names in the running program itself — the same lookup a plugin system uses to find a function by name.

2. The test was green — and it never ran

The probe backing the design attached that lookup and reported success. Read closely, it defined its test function in generated code, then had a second fragment call it: one piece of generated code calling another. The lookup into the host program was switched on and never once needed. Nothing in the output separates "the mechanism works" from "the mechanism was never asked to do anything."

3. What Linux says when you finally ask

Written properly — a function that exists only in the host program, named but not defined in the generated code — the Linux answer is immediate: 

LANE A  no flag      Symbols not found: [ hey_probe_host_answer ]   FAIL
LANE B  -rdynamic    returned 4242                                  PASS

This is the classic dynamic-symbol-table problem: a program's own functions land in a table the debugger reads, but name-based lookup at runtime searches a different, smaller table that a program does not publish itself into by default. The GNU linker documentation says exactly this about --export-dynamic. A control program containing no JIT at all showed the same split, ruling out the local compiler quietly adding the flag.

The macOS half is the mirror image, and it is what turns a platform anecdote into a rule. Mach-O publishes those symbols by default, so it works with no flag — but link the identical source with -Wl,-unexported_symbol and it fails with the same message Linux gives. One variable changed, both directions observed. The mechanism is publication of the symbol on both systems; only the default differs.

4. The better fix: hand over the addresses, skip the loader

The obvious fix is to add -rdynamic and move on. The better one is to stop asking the loader anything. LLVM's just-in-time library lets you register a name and an address directly — and the host already knows where its own functions live, for free, at compile time. Measured with the host built without any export flag: the generated code called it and got the expected value, while the loader still could not see the symbol at all.

That wins on four counts: nothing added to the published symbol table, no loader involvement, a whole class of name-mangling bugs gone, and — the one that matters most — the list of 571 functions becomes an explicit table that fails to build when a runtime function is renamed. The flag-based version compiles fine and fails later, in front of a user, at the first call.

5. The prediction that was wrong — and failed loudly, not silently

Commissioned research predicted that per-thread variables would break for a specific, well-sourced reason: the linker layer implements only one of the machine-level patterns they need. It was checked rather than assumed. It was wrong.

They do break — but the failure names a different missing piece. The generated code uses an emulated scheme for per-thread storage while the host, built by the same compiler, uses the processor's native one. They cannot meet. It fails loudly, as a missing name, rather than silently reading a wrong address — the outcome genuinely worth fearing. But neither the link flag nor the fix above repairs it: there is no address in the host to hand over.

So the design gains a rule rather than a patch: fragments never touch a per-thread variable directly; they call a host function that returns what they need. Why the emulated scheme is on at all is still unanswered, and nobody has invented an answer to fill the gap.

6. What changed: the plan stands, with two new rules

Both changes — register the host's addresses directly, keep per-thread variables behind a function call — are far cheaper now than after the session is built around them.

One correction belongs here at the same volume as the original claim. Our earlier article listed resolving the runtime's functions against the host program among the things a probe had measured. It had not; the claim was carried over from the probe's own framing without checking which lines did what. That article now carries a dated correction pointing here. Its latency numbers stand — the error was one entry in a capability list, not a timing.

The reusable lesson is not about linkers. A test that cannot fail reports exactly the same green as a test that passes, and the only way to tell them apart is to make one fail on purpose. The most valuable twenty minutes here were spent breaking something that worked.

Reproduce it

Four C programs of a few dozen lines each, built against llvm-config on LLVM 22.1.8: a JIT-free control, the host-function lookup in two link lanes, the direct-address version, and the per-thread-variable pair. Every outcome is a pass/fail or a symbol name rather than a timing, so a loaded machine cannot change the answer. One trap: LLVMOrcThreadSafeContextGetContext is gone in LLVM 22.

Glossary

Just-in-time compilation (JIT)
Turning code into machine instructions inside the running program and calling it immediately, with no file, linker, or new process in between.
Dynamic symbol table
The smaller list of names a program publishes for lookup while it runs. Distinct from the fuller table used by debuggers — and the reason a function can exist, be callable directly, and still be "not found" by name.
Per-thread variable
A variable with a separate copy for each thread. Reaching one requires machine-level cooperation that generated code and the host program must agree on.
Linker flag
An option controlling how a program is assembled and what it publishes — here, the single variable that decides whether the lookup succeeds.
