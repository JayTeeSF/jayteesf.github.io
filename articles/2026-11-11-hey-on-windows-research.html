2. Ruby on Windows

Hey has Ruby-like syntax, so Ruby users on Windows are a natural audience. What they live with today:

How Ruby gets onto a Windows machine

  • ruby-lang.org says "On Windows, RubyInstaller gives you everything you need to set up a full Ruby development environment", also names WSL as an option, and lists winget with a note that for projects you may want the RubyWithDevKit package [R7].
  • RubyInstaller describes itself as a "self-contained Windows-based installer that includes the Ruby language" that "combines the possibilities of native Windows programs with the rich UNIX toolset of MSYS2" and "the large repository of MINGW libraries". Its news lists a Microsoft Store install for Ruby 4.0 (January 2026) and "a brand-new package for Windows on ARM" in 3.4.1-2 [R4].
  • Ruby's own build document names two Windows builds: "mswin: Build using Microsoft Visual C++ compiler with vcruntimeXXX.dll" and "mingw-ucrt: Build using compiler for Mingw with Windows Universal CRT". The mswin build needs "Visual C++ 14.15 (Visual Studio 2017 version 15.8) or later" [R8]. RubyInstaller is the mingw-ucrt kind.

The C runtime switch and what it cost

RubyInstaller 3.1.0 (2021-12-31) changed runtime: "RubyInstaller-3.1.0-x64 has a changed C-runtime called UCRT replacing the old MSVCRT", so "the ruby and gem platform is now x64-mingw-ucrt instead of x64-mingw32", and "gems with C extensions are not compatible between ruby-3.0 and 3.1" [R5]. This matches the existing document's point that msvcrt and ucrt must not be mixed [S36]. A language that links no CRT at all never has this migration.

Native gems: the main pain point

  • Building a gem with a C extension needs the MSYS2 Devkit: "Run ridk install for MSYS2 installation subsequent to the installer", and "To enable MSYS2 and MINGW tools in cmd or powershell simply run" ridk enable [R6].
  • Prebuilt binary gems lag new Ruby versions: "Most of the binary gems are updated for Ruby-3.3, but not necessary for Ruby-3.4". The fallback is gem install <gem> --platform ruby to force a source build, or bundle config force_ruby_platform true, which "requires to manually install dependent pacman packages" [R6].
  • Paths are fragile: "Spaces in the path will cause issues when installing gems, so its better to avoid them", and per-user installs can break "if the username contains spaces or non-ASCII characters" [R6].

Performance on Windows

  • JIT: Ruby's YJIT document now says YJIT is supported "for Windows (mswin) on x64 and arm64 CPUs", and "On Windows (mswin), YJIT can be built only in release mode" with a Rust msvc target [R9]. That is the Visual C++ build, not RubyInstaller's mingw-ucrt build. The RubyInstaller FAQ still says "Neither RJIT not YJIT work on Windows, so far" and that MJIT "did not provide any performance advantage" [R6]. Unverified: whether a current RubyInstaller release ships YJIT; the FAQ may be stale.
  • Unverified: no current, reputable Windows-versus-Linux Ruby benchmark was found. A search returned only forum posts from roughly 2007 to 2011 that blame slow Windows file operations and process creation; those are not used as evidence here.

3. Erlang, Elixir and the BEAM on Windows

Hey has BEAM-like actors, so this is the runtime Hey's actor model will be compared with on Windows.

The installer is built with NSIS 3.05 or later. The instructions cover 32-bit and 64-bit x86; ARM64 is not mentioned [R11].

Installers

  • Erlang: the download page offers a 64-bit Windows installer (otp_win64_29.1.2.exe) and a 64-bit zip; no x86, ARM64, winget or Chocolatey entry is listed on that page [R16].
  • Elixir: "The only prerequisite for Elixir is Erlang, version 27.0 or later". Unverified: whether OTP 29 ships a native Windows ARM64 build; the pages fetched do not say [R11][R16]. No published Windows-versus-Linux BEAM benchmark was found.

What this means for Hey

  • The BEAM's default Windows poller is a thread-per-64-handles design [R12]. A Hey runtime on IOCP (section 7) starts with a structural advantage for many-connection actor servers on Windows, and that is a claim worth measuring against Erlang on the same Windows machine.
  • Elixir users install two things in a version-matched order [R17]. One hey.exe beats that.
  • The BEAM is built with Microsoft's compiler under WSL scripting [R11]. A Hey toolchain that builds itself natively on Windows (existing plan step d) is a cleaner story.

4. Java and the JVM in more depth

GraalVM Native Image on Windows

  • What it promises: a native executable "Starts in milliseconds", "Delivers peak performance immediately, with no warmup" and "Uses a fraction of the resources required by the Java Virtual Machine"; a sample HelloWorld run shows "Max RSS: 7620 KB". It is "Available for Linux, macOS, and Windows platforms" [R20].
  • Windows prerequisites: "To use Native Image on Windows, you need Microsoft Visual C++ (MSVC) compiler version 14.x or later"; Visual Studio 2022 17.6.0 or later with the "Desktop development with C++" workload and the Windows 11 SDK ("Use Visual Studio 2022 version 17.13.2 or later for best compatibility") [R19][R20].
  • Architecture: "GraalVM is available for Windows on the x64 architecture"; ARM64 is not listed [R19].
  • Cross-compiling: the reference page only says the builder creates "a binary for a specific operating system and architecture"; it does not offer cross-OS builds [R20].
  • Static linking: the static and mostly-static guide covers Linux only (musl); Windows is not mentioned [R21].

So the JVM's native-executable answer on Windows has the same weakness as .NET Native AOT: it needs Visual Studio's C++ tools and SDK, and it is x64 only.

jpackage and startup

  • jpackage produces exe or msi installers and bundles a runtime; each format "must be built on the platform it runs on" [S100]. That is a packaged JVM, not a native executable.
  • Startup work in the JDK itself (AOT class loading and linking, JEP 483) could not be read: openjdk.org returned HTTP 403 for JEP 483 and JEP 444. Unverified: any JDK startup figure.

Concurrency model

Virtual threads are the JVM's closest thing to cheap actors: "the Java runtime schedules when a virtual thread is run", mounting it on a platform thread called a carrier; it "can unmount from its carrier" when it "performs a blocking I/O operation". A virtual thread "is pinned when it runs a native method or a foreign function", which "might hinder its scalability" [R22]. The fetched page gives no Windows-specific behaviour. In Hey's own Linux web9 run, the JDK's built-in HTTP server reached 200,293 rps against Hey's 266,085 [R2].

6. Windows-first languages the existing document omits

F#

F# ships inside the .NET SDK and shares everything in the existing document's C# section. Microsoft calls it "a universal programming language for writing succinct, robust and performant code", with "Lightweight syntax", "Immutable by default", "Pattern matching" and "Async programming" [R25], "used by many thousands of developers" [R28]. Two points matter to Hey:

  • F# already has an in-process actor: MailboxProcessor is "A message-processing agent which executes an asynchronous computation" that "encapsulates a message queue that supports multiple-writers and a single reader agent" [R27]. A Windows developer who wants actors without leaving .NET has this today.
  • F# task { } expressions compile to .NET tasks through "Resumable State Machines", and continuations go to the .NET thread pool [R26]. So F# concurrency sits on the same thread pool described in section 7.

Visual Basic (.NET)

Microsoft's stated strategy: Visual Basic has "hundreds of thousands of developers ... concentrated around the traditional Windows-based client workloads"; it "will remain a straightforward and approachable language with a stable design", "will generally adopt a consumption-only approach and avoid new syntax", and "won't be extended to new workloads" [R28][R29]. That is a large group of Windows developers on a language Microsoft has frozen. What they have and value is the Visual Studio WinForms designer and readability ("natural language syntax enables programmers and non-programmers to read code") [R29]. Hey's readable Ruby-like syntax is relevant to them; a GUI designer is not something Hey can match in 607a.

PowerShell (what administrators script in)

  • PowerShell is "a command-line shell, a scripting language, and a configuration management framework"; "Unlike most shells that only accept and return text, PowerShell accepts and returns .NET objects" and is "built on the .NET Common Language Runtime" [R30].
  • Two versions coexist: "Windows PowerShell 5.1 is built on top of the .NET Framework v4.5"; PowerShell 6 and later are built on .NET Core, and the binary was renamed to pwsh.exe to "support side-by-side installations" [R31].
  • Script policy: the default on Windows is RemoteSigned, which "Requires a digital signature from a trusted publisher on scripts and configuration files that are downloaded from the internet"; if nothing is set, the effective policy is "Restricted for Windows clients" [R32]. A Hey install script written in PowerShell must therefore be signed or delivered through an installer.
  • Cmdlets "are instances of .NET classes; they aren't stand-alone executables" and pass objects, not text [R33].

What Hey must match: a compiled hey.exe is an ordinary native command to PowerShell, so it must behave well as one: correct exit codes, UTF-8 output that PowerShell reads correctly (section 10, console row), and machine-readable output (JSON) that an administrator can pipe into ConvertFrom-Json [R30]. Hey's advantage for administrators is a single signed exe that starts fast and needs no runtime, where a PowerShell script needs the right PowerShell version and an execution policy that allows it [R31][R32].

Delphi and Object Pascal

Partly unverified. Embarcadero's documentation wiki returned HTTP 403 for every page tried, and the Free Pascal wiki was offline. The statements below come from Embarcadero's product page and Wikipedia only.
  • Delphi compiles "native code for Microsoft Windows, macOS, iOS, Android and Linux (x64)", and "supports native cross-compilation to many platforms including Windows, Linux, iOS, and Android" [R37]. Embarcadero's headline is "One Codebase, Any Platform and Device!" [R36]. The Windows ARM64 target is not named on the product page [R36].
  • The compiler can produce a single executable that does not require DLLs, and also standard DLLs, ActiveX DLLs, COM automation servers and Windows services [R37].
  • UI: the "Visual Component Library (VCL) is the framework for developing pure Windows applications" [R37], with "Extensive Windows UI component libraries for fast visual UI design and data binding" and design-time styling [R36]; FireMonkey is the cross-platform GUI framework [R36][R37].
  • COM: Delphi has native COM support, including interfaces with reference-counted class implementations [R37].
  • The latest version listed is RAD Studio 13.2 Florence (2026-09-18), with a free Community edition limited to low-revenue users [R37].

Delphi matters as the long-standing proof that a non-Microsoft language can be a first-class Windows citizen: single native exe, no runtime to install, COM built into the language, a visual designer, and cross-compilation from a Windows host. That list is very close to the Maintainer's brief for Hey. Unverified: that Delphi and Free Pascal link with their own linkers and need no Visual Studio; this is widely known but no page stating it could be fetched.

C++/CLI and C++/WinRT

  • C++/CLI "is a technology designed during the early years of .NET (2003-2010) and remains supported for compatibility purposes"; "no new feature work is planned"; it is "only supported on Windows" and is "a bridge between native C++ code and managed code" [R34]. On modern .NET, "Compiling a C++/CLI project to an executable isn't supported. You must compile to a DLL" [R35]. Native AOT does not support it at all [S65]. Hey need not match C++/CLI; the lesson is that mixing native and managed code in one binary is a legacy path even for Microsoft.
  • C++/WinRT is covered in the existing document [S90] and in section 10 below.

  • TechEmpower: the benchmark toolset runs frameworks in Docker with Linux containers [R78], so its published rounds give no Windows figures for any language.

The conclusion is itself useful: almost nobody publishes Windows numbers. If Hey publishes honest Windows results for Hey, C#, Go, Rust/Tokio and Erlang on one machine, it will be nearly alone in doing so.

The recipe this implies for a fast Hey on Windows

  1. One IOCP per scheduler (or one shared), dequeued in batches with GetQueuedCompletionStatusEx, as Go does [S16][R51].
  2. Set FILE_SKIP_COMPLETION_PORT_ON_SUCCESS on sockets so synchronous completions cost no port round trip [R45][R52].
  3. Overlapped file I/O through the same port, so files do not need Tokio's blocking pool [R59][R52].
  4. High-resolution waitable timers tied into the IOCP wait, as Go does with NtAssociateWaitCompletionPacket [R42][R53][R54].
  5. WaitOnAddress for worker parking and locks [R46].
  6. Processor-group awareness for more than 64 logical processors on pre-Windows 11 systems [R44].
  7. No UMS, no fibers, no OS thread pool [R38][R39][R40].
  8. Decide completion-style (Go) or readiness-style through AFD (mio, Zig) early; completion is the documented, supported route [S62], AFD is undocumented but used by two major projects [R57][S23].

Getting import libraries legally

The cleanest answer is to need none. A DLL import is only a pair of names (DLL name, function name) written into the executable's import table; nothing from Microsoft has to be copied. Three working precedents:

  1. Go: the linker writes the import table from declarations in Go source [S16].
  2. Rust raw-dylib: the compiler synthesises the import library from the declaration [R65], and Microsoft's own crate uses it [R66].
  3. Zig: import libraries generated from mingw-w64's .def files, which are that project's own text files, not Microsoft binaries [S21][S23].

Hey already has a PE32+ writer (project fact in the existing document), so it can write import directory entries directly from Hey declarations, the Go way, and never ship or download a .lib. The function names themselves can be generated from Microsoft's win32metadata, published for exactly this purpose: "metadata for Win32 APIs such that idiomatic projections ... can be generated for all languages" [R95]. The existing document's unresolved question about the Windows SDK licence [S42] then does not arise.

Qualitative facts that shape the contest

  • Native AOT gives "Reduced startup time", "Minimized disk footprint" and "Reduced memory demand", but "Not all features in ASP.NET Core are currently compatible with Native AOT": Minimal APIs and SignalR work (some partially), MVC does not [R72].
  • Native AOT has no tiered recompilation: "tiering doesn't exist in the Native AOT world" [R75]. The JIT, in contrast, keeps getting profile-guided gains: .NET 10 adds stack allocation of small arrays, escape analysis for struct fields and delegates, array-interface devirtualization, and profile-driven inlining [R80]. So C# has two different opponents: Native AOT (fast start, small, fixed code quality) and JIT (slow start, large, very good steady-state code).
  • Native AOT chooses "a blended approach: generate fast code, but be mindful of the size"; OptimizationPreference can favour Size or Speed [R73].
  • Native AOT on Windows uses the Windows thread pool by default, which changes its concurrency behaviour from JIT .NET [R61][R63].
  • Native AOT needs Visual Studio's C++ workload and cannot cross-compile across operating systems [S65][S32].
