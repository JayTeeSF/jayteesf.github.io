Actors and failure: give state an owner, and let failures stay small

Index Reference 1: Language Reference 2: Modules Reference 3: Actors and failure Reference 4: Workers, Jobs, streams Reference 5: Distributed Reference 7: Native code Reference 8: Memory

Most programs have some state that has to live a long time: a counter, a cache, a connection, a game board. In Hey that state belongs to an actor, a small object with a private mailbox. Nobody else can touch its state; they can only send it messages. That one rule removes locks from your code, and it also decides what happens when something breaks: a failure ends the actor that had it, and nothing else.

On one screen Actors, sending, asking with a timeout, links, monitors and supervisors all Works today. A fail or runtime error inside an actor ends that actor only, and the actors that care are told1 (Partly works: web requests are fully contained; actor and Job containment is being finished). Thousands of actors run on a few threads. Next, decided for the 0.99.606a release: messages shared instead of copied, and short sends to idle actors run straight away on the sender's thread.

1. When state must live, give it an owner

This is a whole program. The actor counts how many times it was told 'increment'.

counter.hey

actor Counter(label)
  state count = 0
  receive message

  if message == 'increment'
    set count = count + 1
    says label + '=' + count
  elsif message == 'stop'
    exit
  end
end

program
  let counter = spawn Counter('visits')
  send counter, 'increment'
  send counter, 'increment'
  send counter, 'stop'
  join counter
end

Run it (exact command and output)

$ hey counter.hey
visits=1
visits=2
$ echo $?
0

Read it top to bottom. actor Counter(label) declares the kind of actor and its start argument. state count = 0 is a slot only this actor can see. receive message names the incoming message; everything after it is the handler, which runs once per message. set changes a state slot. In the program, spawn starts one actor and gives back a handle, send puts a message in its mailbox and returns at once, and join waits until the actor has exited.

Predict it. The program sends three messages and never waits between them. Can visits=2 ever print before visits=1? No: one sender's messages to one actor arrive in the order they were sent, and the actor runs one turn at a time. Two different senders have no order between them.
Why set count = count + 1 never loses an update. Reading count, adding one and writing it back looks like three steps that another thread could interleave with. It can't: only this actor can see count, and an actor handles one message at a time, on one thread. So the read-modify-write is atomic by construction, with no atomic instructions and no locks. That's also why Hey has no shared mutable variable between actors or jobs: a counter that many parties update lives in an actor, and each update is a message. The short form set count += 1 means the same thing and applies only to actor state. Decided, coming (the += spelling; the long form above works today)

3. Asking and answering, and why a timeout means "unknown"

send never waits for an answer. When ordinary code (not another actor) needs one, use Actor.call(target, body, timeout_ms) from stdlib:Actor. The actor receives {kind: 'actor_call', body: …, reply_id: …} in normal mailbox order and answers with Actor.reply(reply_id, value). Works today

ask.hey

import 'stdlib:Actor'

actor Bank
  state balance = 100
  receive msg

  if msg.kind == 'actor_call'
    set balance = balance - msg.body.amount
    let answered = Actor.reply(msg.reply_id, balance)
  end
end

program
  let bank = spawn Bank
  let answer = Actor.call(bank, {amount: 30}, 1000)
  says answer.ok
  says answer.value
  let again = Actor.call(bank, {amount: 5}, 1000)
  says again.value
  stop bank
end

Run it (exact command and output)

$ hey ask.hey
true
70
65
$ echo $?
0

Actor.call returns a Result (a record with ok, value, code and error). The rules that matter:

  • A timeout means the outcome is unknown. actor_call_timeout removes the waiter, not the request. The bank may already have taken the money, or may take it later. Hey never retries for you; use a request id your application can check.
  • Only ordinary callers may wait. A call made from inside an actor returns actor_call_from_actor immediately, so actor turns never block each other (actors talk to actors with send).
  • At most 1,024 calls can be waiting at once; the next gets actor_call_overloaded. An unknown or stopped target gives actor_unavailable; a timeout outside 1 to 3,600,000 ms gives invalid_timeout.
  • Only the first reply from the target counts. Late or duplicate replies return false.

4. Waiting for I/O inside an actor with await

A turn must not sit on a blocking read; it would hold one of the few scheduler threads. Instead, inside an actor, await handles, timeout_ms, tag registers the handles with the runtime's one I/O reactor (kqueue on macOS, epoll on Linux, poll as a fallback) and ends the turn. When a handle is ready, the actor gets an ordinary message with kind: 'io_completion' and your tag. Partly works: the runtime side (the reactor, the parked turn, the io_completion message) exists and is checked by spec 966, but on this toolchain the source form below does not compile. The compiler consolidation lists "await (with its ruling)" as an open item (see the decision ledger).

await_actor.hey

import 'stdlib:Files'
import 'stdlib:Io'
import 'stdlib:Pipes'

actor await_reader(reader, sink)
  receive msg
  if msg.kind == 'start'
    await [reader], 2000, 'pipe-ready'
  else
    if msg.kind == 'io_completion'
      send sink, {kind: 'done', tag: msg.tag, backend: Io.reactor_backend()}
      exit
    end
  end
end

actor await_sink
  receive msg
  says msg.kind == 'done'
  says msg.tag == 'pipe-ready'
  says msg.backend == 'epoll' or msg.backend == 'kqueue' or msg.backend == 'poll'
  exit
end

program
  let created = Pipes.create(4096)
  let reader = created.value.reader
  let writer = created.value.writer
  let sink = spawn await_sink
  let worker = spawn await_reader(reader, sink)
  says actor_info(worker).pooled
  send worker, {kind: 'start'}
  let wrote = writer.write_all('ping')
  join worker
  join sink
  let writer_closed = writer.close()
  let reader_closed = reader.close()
end

5. Links, monitors and supervisors

Three ways for one actor to care about another:

  • Link link(a, b): the two share a fate. When one exits, the runtime stops its partner too, with the exit reason linked_exit (Erlang's link rule). Use a link when two actors are useless without each other.
  • Monitor monitor(a) or monitor_to(watcher, a): one-way watching. When a exits, the monitor records (or delivers to watcher) the event and the reason. You can read it with monitor_info.
  • Supervisor supervise Child max N: a parent that restarts its child from the same start arguments when the child exits.

Works today

links_and_monitors.hey

# Demonstrates explicit link metadata and monitor exit observation.

actor worker(label)
  receive msg
  if msg == 'stop'
    exit
  else
    says label + ': ' + msg
  end
end

program
  let left = spawn worker('left')
  let right = spawn worker('right')
  says link(left, right)
  says actor_info(left).linked_pids.length

  let mon = monitor(left)
  says monitor_info(mon).event
  send left, 'stop'
  sleep 2
  let after = monitor_info(mon)
  says after.event
  says after.reason

  stop right
  join left
end

6. Fail fast, Erlang style

The Maintainer ruled: a runtime error stops the current unit of work at once and stays isolated; the system carries on or restarts around it. There is no catch or rescue in Hey. Errors you expect (a missing file, bad input) are values: functions return a Result (stdlib:Result) and you check ok. Anyone proposing a catch form must first write the full case for and against. Works today (ruling linked in the decision ledger).

Stack overflow is a runtime failure too

The rule does not change for deep recursion. Jobs and actors exit without taking down any other Job, actor or the process. Running out of stack is a runtime failure like any other, so it ends only its unit of work.3
Where the recursion runs out of stackWhat stopsWhat you seeStatus
Main programthe process (main is its own unit)hey: stack overflow (recursion too deep): the stack is exhausted, exit status 70Coming in 0.99.606a
Actor turnthat actor only; siblings keep answering, the process continuesexit reason error: stack overflow to its links, monitors and supervisorDecided, coming — until then it still crashes the whole process
Job attemptthat attempt only; retries, then a dead letterthe failure in the Job result, like any runtime_errorDecided, coming — until then it still crashes the whole process

How it works: each thread has a guard page below its stack and a small emergency stack for the signal handler. When the guard page is hit, the handler reports the overflow; on an actor or Job thread it returns to that unit's failure point instead of ending the program, then resets the guard so the thread can run more work. A later release also gives the main program a large stack that only uses memory as it grows, so deep recursion like the cfold benchmark fits.

See it: a failing actor and a steady one

Predict it. Fragile fails on its first message. Will Steady still print? Will main finished print, and what will the exit status be?

actor Fragile

actor Steady
  receive msg
  says 'Steady got ' + msg

How the runtime contains a failure (the mechanism)

Works today (the mechanism; actor and Job units are being wired to it). Each unit of work pushes a recovery point when it starts (hey_runtime_recovery_push plus a setjmp mark; setjmp is the C call that saves "where we are" so a later jump can return there, the same pattern PostgreSQL uses for its errors). A runtime error records its message in per-thread state and jumps back to that point; nothing after the error runs. So the jump leaks nothing, compiled frames register the values they own (hey_frame_cleanup_push) and the jump releases every abandoned frame's values (hey_frame_cleanup_unwind).4 A value held only in a register of an abandoned frame would still leak, which is why ownership facts belong in MIR, where every owner is registered. A fiber (an actor turn that parked on await) carries its own error state, so its recovery point stays valid after it resumes. The runtime never raises an error while holding one of its own locks, and the process-wide error count only counts errors no unit took, so a contained failure does not turn the exit status into 70.

8. What a message costs, and what changes next

Today, every send makes one copy of the message for the mailbox (the runtime counts these as send_clones). With reference counting on, a copy of an object or list is just a count increase, but a value handed to another thread is copied deeply, because the counts are not thread-safe. Two decisions change that for 0.99.606a:

ChangeWhat it buysStatus
Messages shared by reference, not copied. An immutable message is marked "shared between threads" once and then passed by pointer. Sharing never changes who fails.No deep copy per send, whatever the message size.Decided, coming (606a; not in the 607 source this page was checked against, where hey_actor_enqueue still clones)
Inline turns. A send to an idle actor may run its handler right away on the sender's thread. The inline turn is still its own unit of work, with its own recovery point: a failure ends the receiver, never the sender.No queue hop, no thread wake-up for the common request/response shape.Decided, coming (606a; the runtime still says "no actor runs inline on the sender's stack")
