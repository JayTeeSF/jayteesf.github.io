Daily: We Rebuilt Hey’s Compiler. It Still Needs the Old One.

We paused app work to replace the part of Hey that reads source code. Five ways of running Hey now agree on 12 test programs. That is progress, not victory: one line still sends an entire file back to the old compiler, and three known tests still get different answers depending on how the program is run.

What matters today

  • Product work stays paused. The replacement compiler must stop handing files to the old one, all run methods must agree, and each product must pass a saved test tied to one exact code version.
  • All five run methods matched on all 12 current test programs. That is not full language coverage.
  • The visible blocker is a function call used directly inside find(...). The shape is below.
  • Three quiet wrong-answer cases remain, and three dashboard checks shown as passing were actually failing.
  • Every number comes from a test record containing the code version, command, output, and result.

The line the new compiler still cannot handle

The old article called this “one unsupported source form.” In plain English, it means a line shaped like the amber line below. Names are shortened, but the important arrangement is unchanged: 

fn candidate_is_present(candidate_name)
  if candidate_name == nil or candidate_name == ""
    return false
  end

  return find(build_report(), "candidate=" + candidate_name) >= 0
end

Green: fixed today. Amber: the current visible gap.

The new compiler can build the report, join the text, and search when those pieces appear separately. It cannot yet combine them as a function call used directly as the text passed to find. The whole file moves to the old compiler. That older path gives the expected result for this example, so the handoff is visible only in a build log. Two similar fixes exposed two new blockers in the same function, so we do not yet know whether this is the last one.

The replacement has a simpler shape

The old compiler let several parts reread the source and repeat decisions. The replacement design reads it once, builds one agreed description of the whole program, and then either runs it immediately or builds a native executable.

All five produced the same output for the same 12 programs. The first report had marked three as failing when they had simply not been run; once run, they matched. Not tested is not failed, and 12 passing programs are not full coverage.

The scoreboard had bugs too

Three checks shown as passing were failing on a clean copy. One still expected an old halfway count. Another ran the wrong command. A malformed row also stopped the runner before later checks were attempted. The runner now prints how many checks it expected, ran, and classified.

This repeats the lesson from the 48-minute build: optional work must be off by default, time-limited, and recorded exactly.

What the old article meant by a “receipt”

It meant a saved test record:

Code version: 923ee16c
Test:         run 12 programs five ways
Observed:     all five outputs matched
Missing:      0
Result:       PASS

What must happen before product work resumes

  1. Fix the three known different-answer cases.
  2. Find every line that sends a file to the old compiler, then reduce that count to zero.
  3. Keep all five run methods agreeing while the test set grows far beyond 12 programs.
  4. Finish the copying cleanup and measure speed again. None of roughly 3,000 targeted copies has been removed in this phase; the last clean build took about six and a half minutes.
  5. Test the command line, web, iOS, Android, and Apple TV against one exact committed version. The current snapshot ran 18 of 36 checks; all 18 passed, but the other 18 were not run.

Then the main effort returns to applications. The long-term goals remain stable results, C-like speed, Ruby-like readability, and the cheap immutable actors described in Designing Hey’s Actors. This compiler campaign is the road back to that work, not the work itself.
