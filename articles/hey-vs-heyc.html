Hey · command guide · 25 September 2026

hey or heyc?

The shorter command doesn't select a different compiler. Hey has two separate choices: which command interface you use, and which operation that command performs.

2

There are two axes. The command name selects the user-facing interface: hey for convenient everyday tasks, heyc for explicit compiler work. The operation or flag selects ordinary native compilation, interpretation, testing, or private bootstrap work.

Two everyday commands reach the same compiler

hey app.hey is optimized for the edit-and-run loop. heyc build is optimized for publishing a named executable. Underneath, both use the ordinary application compiler.

  1. Hey source.hey files
  2. HIRresolved program facts
  3. MIRexplicit machine plan
  4. LLVM IRlow-level intermediate code
  5. Target toolchainobject generation + link
  6. Executablethe program you run

HIR is Hey's high-level account of the resolved program. MIR is the lower-level plan with execution and machine-level calling details. Hey emits LLVM intermediate representation (IR); the target LLVM/Clang toolchain generates object code and links the executable with its required runtime and library objects.

The commands differ in what they deliver

The first two cards are ordinary native compilation. The others are development or toolchain-maintenance paths.

Ordinary native

Run source conveniently

hey app.hey
./app.hey  # with #!/usr/bin/env hey

The first run compiles the complete source graph and stores a native executable under an identity derived from its inputs. A warm run validates the source, transitive imports, compiler inputs, and target identity, then replaces the launcher with that cached executable. A #!/usr/bin/env hey script uses the same path.

Choose this for: scripts, local tools, and edit-run work.

Ordinary native

Build a deployment artifact

heyc build app.hey -o build/app
./build/app

This compiles once and leaves an explicit native executable. hey build delegates to the same compiler operation.

Choose this for: services, releases, containers, signing, and benchmarks.

Developer path

Interpret a source file

heyc app.hey --run

This uses the embedded interpreter. It is useful for diagnosis and behavioral comparison, but it does not prove that the ordinary compiler can build the program.

Choose this for: focused development checks, not native performance measurements.

Developer path

Run embedded specs

heyc feature.hey --test

This runs Hey specs through the embedded test harness. It isn't a second application compiler.

Choose this for: quick language and library checks.

Interactive

Explore in the REPL

hey repl

The read-evaluate-print loop gives immediate feedback while learning or probing an expression. hey-repl is the direct form.

Choose this for: experiments and interactive exploration.

Schematic · maintainers

Build through Stage-0

heyc stage0-build TOOLCHAIN_SOURCE.hey -o BOOTSTRAP_TOOL

This schematic maintainer command selects the private native-C Stage-0 compiler. The placeholders are deliberate: Hey's repository build recipes supply required bootstrap setup. Stage-0 exists to seed, compare, and recover compiler tooling—not to build application deployments.

Choose this for: compiler bootstrapping and recovery work.

Choose from the result you need

I want to run this source

Use hey FILE.hey. You get ordinary native compilation plus a correctness-aware cache.

I need a deployable binary

Use heyc build FILE.hey -o APP, or the equivalent hey build.

I need a quick interpreter check

Use heyc FILE.hey --run, knowing that you are testing the interpreter rather than the ordinary compiler.

I want to explore

Use hey repl.

The ordinary compiler rejected my app

Report or fix that compiler failure. A Stage-0 result can help diagnose it, but Stage-0 isn't an application deployment path.

A Stage-0 success does not validate an application build

A successful Stage-0 build and a successful ordinary build are evidence about different compilers.

Ordinary application path

hey FILE.hey
heyc build FILE.hey

  • HIR → MIR → LLVM IR → target toolchain
  • Required for application acceptance
  • Produces the native code Hey intends to ship

Private Stage-0 path

heyc stage0-build TOOLCHAIN_SOURCE.hey

  • Native-C bootstrap compiler
  • Useful for compiler seeding, recovery, and diagnostic comparison
  • Not an application build or deployment route

Why the distinction matters for a real application

Example
MMeow needs an ordinary-built deployment binary.

If heyc build rejects MMeow while Stage-0 accepts the same source, that difference is diagnostic evidence for the compiler team. It does not produce an accepted MMeow deployment. Acceptance comes when the ordinary HIR → MIR → LLVM IR → target-toolchain path builds the application.

The other executable names are compiler machinery

You may see these names in build logs. Application projects shouldn't call them directly.

NameRole inside the toolchain
hey-selfcThe Hey-written self-hosted compiler driver.
hey-resolveThe compiled ProgramResolution component that assigns identities across the program.
hey-fullA compiled source-running/compiler application used behind the normal command surface.
hey-selfc-pipeline-stage0A Stage-0-built bootstrap pipeline artifact used to bring up the product compiler.

The short version

Run source with hey. Publish binaries with heyc build or hey build. Use --run, --test, and the REPL for development. Reserve stage0-build for the compiler team's bootstrap and recovery work.
