Hey · architecture guide · 15 September 2026

Decide meaning once. Carry it all the way down.

A compiler is a relay race. Parsing, resolution, intermediate representations, and code generation have different jobs. The baton is the program's meaning; a later runner cannot drop it and guess from the name printed on the track.

The verdict

  • Hey's architecture works when each stage owns one kind of decision. Resolution chooses identity; high-level IR carries meaning; mid-level IR plans execution and memory; LLVM translates the plan.
  • A registry is a reference table, not the architecture. Moving a special-case name into generated data does not make the operation generic.
  • The runtime standard-library interpreter service is deleted. Native boundaries must now be explicit rather than a hidden route for missing library lowering.
  • Disclosed weakness: textual carriers, spelling recovery, compiler-side tables, and incomplete ownership transport remain. The full ordinary archive is not green.
  • Falsifiability: withdraw a resolved identity, type fact, representation, or lifetime authorization; the owning stage should refuse instead of selecting a same-spelling fallback.

Source says what; the compiler decides how

A Hey programmer writes values, functions, modules, and actors. The language promises observable behavior. It does not promise that every number uses a general-purpose wrapper or every immutable update copies memory. Those are implementation choices, provided the answer stays the same.

This separation is what makes optimization possible. You can read the language tour without learning compiler internals, while the compiler can still prove lower-cost representations underneath.

private fn add_score(scores, score)
  return [...scores, score]
end

program
  let scores = []
  let next = add_score(scores, 7)
  says len(scores)
  says len(next)
end

Conceptually, parsing finds the update's structure; resolution identifies add_score; HIR tracks value meaning; MIR decides evaluation and whether reuse is safe; LLVM and the linker produce the executable. The observable result remains 0, then 1.

The parser turns characters into structure

The parser answers questions such as “which arguments belong to this call?” and “which operator groups first?” It records source spans so later facts can point to exact occurrences. It must not decide which same-named function a call means; that is the resolver's job.

The resolver gives each call a stable identity

Imagine two students named Alex. A class roster needs student IDs, not just the name “Alex.” Hey's resolver does the same for functions and operations. A stable target identity distinguishes same-spelling definitions and unifies different source spellings that mean the same operation.

Module authority also begins here: imports and declarations determine what a scope may name. That migration is still transitional. Compiler-side compatibility tables and incomplete named exposure remain, so this page does not claim that the planned Sys cutover is complete.

HIR carries meaning—and owns the latest focused repair

High-level intermediate representation (HIR) is the compiler's semantic account of the program. It carries types and resolved calls in a form later stages can use. It must reconcile the representation a caller supplies with the parameter a function receives.

The latest focused Transformer provider run exposes a refusal here: floating-point values reach parameters inferred as integers. The complete archive remains unaccepted. Focused backend tests reject the idea that a missing LLVM conversion is the root cause. The proposed HIR repair will propagate floating-point evidence by resolved call identity; it is not implemented yet.

MIR records execution and memory choices

Mid-level intermediate representation (MIR) is where the compiler records its plan for evaluation order, machine representation, effects, and lifetime. An effect says what a call may do to an argument. Lifetime says how long an allocated value must remain valid. If HIR says “this is a floating-point calculation,” MIR can carry floating-point loads and arithmetic. If ownership analysis proves one owner and no later observation of the old logical value—a proven last use—MIR may authorize reuse.

The September 12 decision draws a sharp line: ordinary immutable source should become “functional but in place” when uniqueness and last use are proven, and fall back safely when they are not. This direction is inspired by Perceus; it does not claim that Hey uses MLIR or has completed every ownership optimization.

A focused higher-order mechanism has landed. A known reducer identity can carry a consume-and-return contract through a callable value, while an ordinary indirect call remains borrowed. Its test checks results and MIR facts with copy-on-write disabled; it is not a timing result, and it does not yet prove that every ordinary immutable rebuild avoids copying.

A quadratic algorithm is one where each new item can revisit all earlier items, so doubling the input can approach four times the work. Ownership can remove repeated copies of a unique accumulator. It cannot remove repeated semantic lookups; those need indexes, summaries, or a different traversal. A separate owned-string loop-transfer candidate remains pending review.

LLVM consumes the plan; it does not invent one

Hey emits LLVM intermediate representation. LLVM then optimizes it and generates machine code; the linker joins that code with provider objects and runtime support. Hey's emitter should translate declared function agreements, representations, and lifetime authorizations mechanically. It must not infer ownership from emitted text or choose behavior because a callee happens to have a familiar name.

This is why “put it in a registry” is insufficient. A registry can map an ID to an application binary interface—an agreement about inputs and results. It cannot replace resolver identity, HIR typing, MIR evaluation order, or lifetime proof. A Web candidate was reviewed and held because its initial registry approach still carried a program-specific callback special case rather than a generic resolved callback and link plan.

Linking and runtime code finish explicit boundaries

The link plan joins calls and declarations to the provider objects that actually implement them. Runtime primitives serve explicit native boundaries such as operating-system work. They are not a hidden interpreter for ordinary library algorithms.

That distinction became enforceable when official commit 6bf118f1f removed the runtime standard-library interpreter service and its compiler route. Compiler cache artifacts may still use “sidecar” in their names; deletion of the runtime transport does not rename every artifact or complete every provider.

Safe fallback and honest refusal are different

When uniqueness is unknown, ordinary correct behavior continues through copy-on-write or cloning. That is a safe optimization fallback, not a compile error. The compiler refuses when a required semantic identity, function agreement, representation, or lifetime contract cannot be satisfied. A fallback that silently selects a different compiler backend makes a green result ambiguous.

Stage0 remains legitimate for creating a bootstrap seed. It is not accepted as the production application backend when ordinary lowering fails.
