Great Command-Line Scripting with Hey

The week of: 2026-10-10 · re-measured on 601a and Ruby 4.0.7

One job, two implementations, one rule: the outputs must match to the byte. Re-measured on Hey 601a, the Hey this site ships builds its package index in 115.6 ms compiled, against 310.7 ms for Ruby 4.0.7 — 2.7× faster, and 2.3× as a script. Hey is still behind on building long lists, on parallelism and on length.

TL;DR

  • Hey is 2.7× faster than Ruby on this job, compiled. Building the index for the site's 34 packages: Ruby 4.0.7 + YJIT 310.7 ms, the shipped Hey 115.6 ms as a binary, 137.2 ms as a script (2.3×), and 176.0 ms through the site's bin/hey-run (1.8×). Byte-identical output on every lane.
  • Until this week, Ruby won. The port had carried a hand-written sort, written when .uniq and .sort were broken in Hey; the bug got fixed but the workaround stayed, and against it Ruby was about 2.5× faster. Restoring paths.uniq.sort(cmp) reversed that.
  • The site's own runner costs about 60 ms a call. bin/hey-run decides on every call whether to rebuild, which takes the lead from 2.7× to 1.8× (176.0 against 115.6 ms for the same build run directly).
  • Hey is still behind on building long lists (an append copies the list: 16,000 appends take 1.17 s against Ruby's 2.7 ms), on parallelism (no parallel map on 601a; --workers does nothing), and on length: 592 lines against Ruby's 313.
  • Not a quiet box. A Hey compiler build ran throughout (load 2.4–3.4), and a virtual machine joined it in the last round. Lanes held within 5% across rounds. Every figure is as measured under that load.

How to read these numbers

Apple M3 Pro (6 performance + 6 efficiency cores, 18 GiB), macOS 26.6.2. Hey 601a from hey-lang-bootstrap-plan at 565e6ddad, set explicitly per lane with HEY_ROOT. Ruby 4.0.7 (the newest stable release) and 4.0.6, with YJIT (Ruby's built-in just-in-time compiler) on unless a lane says otherwise. Each Ruby is called as its real binary: rbenv, the Ruby version manager, normally runs ruby through a small wrapper script (a shim) that costs 53 ms per launch here and would have been charged to Ruby. Timings from hyperfine, which repeats a command and reports mean ± standard deviation: --warmup 3, 30 runs per Hey lane and 20 per Ruby lane, fixed PACKAGES_INDEX_GENERATED_AT. Every lane deletes its output, asserts it came back non-empty, and byte-compares it with Ruby's before any clock is trusted.

The box was loaded. A single-threaded Hey compiler build held about one core for the whole session, and the 1-minute load average (roughly, how many processes wanted a CPU at once) sat between 2.4 and 3.4, this benchmark included. Benchmarks ran at nice -n 10, lane order rotated each round, and the set ran three times. In the last round a virtual machine started using a core and load rose to 3.0–3.4; the lanes moved by up to about 5% (the Hey script lane most, 134.5 to 141.8 ms), which is within what the table's spreads show. The old version of this article said numbers off a loaded machine are lower bounds; these are offered as measured under that load. Every raw number, the harness and the controls are in the evidence file.

Where Hey is ahead, and where it's behind

Ahead of Ruby

  • This job, compiled. 2.7×; 2.3× as a script.
  • Start-up. A compiled Hey hello world runs in 1.2 ms. Ruby 4.0.7 needs 28.3 ms to run nothing, 30.6 ms once this script's three requires load. Running a script through the hey command (its first line is #!/usr/bin/env hey) costs 19.4 ms.
  • Per-item work. Subtract each side's separately measured start-up floor (1.2 ms and 30.6 ms) and the Hey binary does its work in about 114 ms against Ruby's 280. That's an estimate from separate measurements, not one.

Still behind Ruby

  • Building long lists. An append copies the list. 16,000 appends take 1.17 s on 601a; Ruby's << does it in 2.7 ms. Even the stdlib merge sort builds its output that way.
  • Parallelism. There's no parallel map on 601a. --workers is parsed and validated and does nothing; 1 and 4 workers time the same.
  • Length. 592 lines and 25 functions against Ruby's 313 lines and 22 methods: 1.89×. Without comments and blank lines, 435 against 265: 1.64×.
  • The site's runner. bin/hey-run adds about 60 ms a call: 1.77× Ruby through it, against 2.69× for the binary run directly.

Why this benchmark compares idiomatic to idiomatic

In July this article reported 5.46×. The Hey it measured had been hand-optimized for speed: builtins-only inner loops, work hoisted out of the comparator, a worker pool tuned against the clock. The Ruby it beat is plain idiomatic Ruby nobody has ever tuned. That isn't a fair fight. Anyone who can hand-optimize the Hey can hand-optimize the Ruby, so the canonical script became an idiomatic port, a rewrite that mirrors the original's structure instead of chasing the clock, and the headline came from that.

The Ruby isn't tuned either. Instrumenting it shows about half its 276 ms of work inside compare_paths, which converts each Pathname to a string and lower-cases it on every comparison. A sort_by with a precomputed key would cut that, and the Hey could do the same. Neither side gets it here.

Hey can read like Ruby

The names still line up almost one-for-one: digit_run, trim_leading_zeroes, compare_digit_runs, compare_paths, sorted_unique, relative_path, package_section, render_page, on down the file. Ruby's initialize is Hey's new, and the Hey has three functions the Ruby doesn't: worker_count, package_tasks and rendered_sections, left from the parallel path that no longer runs. Side by side, as committed:

Ruby (generate-packages-index.rb)

def sorted_unique(paths)
  paths.uniq.sort { |left, right| compare_paths(left.to_s, right.to_s) }
end

def linkable_files(files)
  sorted_unique(
    files.select { |path| LINKABLE_EXTENSIONS.include?(path.extname.downcase) }
  )
end

Hey (generate-packages-index.hey)

private fn sorted_unique(paths)
  return paths.uniq.sort(PackagesIndex.compare_paths)
end

private fn linkable_files(files)
  let linkable = []

  for path in files
    let lower_path = Text.lower(path)
    if Text.ends_with?(lower_path, '.md') or Text.ends_with?(lower_path, '.html')
      set linkable = [...linkable, path]
    end
  end

  return PackagesIndex.sorted_unique(linkable)
end

sorted_unique reads the same in both. linkable_files shows the gap that's left: Ruby filters with select and a block; the port filters with a loop that rebuilds the list with [...linkable, path]. A Ruby programmer reads it cold, but it's longer, and every one of those appends copies the list.

The ergonomics tax

Identical behaviour costs 1.89× the lines (592 against 313), against 1.67× in July. Comments account for part of it: without comments or blank lines the ratio is 1.64× (435 against 265). What's left is Hey's explicitness: let/set, return, and loops where Ruby has blocks. Price it in.

The parity gate

The thesis, and it outranks every number here: a benchmark without an output-parity gate is a wish. Two receipts from this program's history.

In July the first optimization pass rewrote the comparator to use byte_at(string, i). It compiled, and silently returned 0 for every string argument, being a Bytes-value operation. Every path compared equal to every other, the sort collapsed into a no-op, and the benchmark got faster and wrong. The byte-parity check caught it on the first run.

The second is worse, because the gate itself lied. The fastest result this project ever recorded was a 2.3 ms binary: exit 0, zero bytes of output, dead before the first line of user code. The parity check blessed it because it never deleted the output file first, and so compared the one left by the previous lane. My bug, and the reason the harness below deletes first.

The gate was itself made to fail before any number here was trusted. A lane that runs true exits 0 and the gate reports NO OUTPUT; the real binary run with a different timestamp exits 0 and the gate reports PARITY FAIL; the real binary with the right timestamp passes.

Running it

There are three ways to run one source file.

# the site's way: builds once into .hey-bin/ (gitignored), then execs the binary
bin/hey-run generate-packages-index ./packages

# the script lane: no build step, shebang is #!/usr/bin/env hey
./generate-packages-index.hey ./packages

# the binary you build yourself: a standalone native executable
export HEY_ROOT="$HOME/dev/hey-lang-bootstrap-plan"
HEY_STDLIB_PATH="$HEY_ROOT/stdlib" HEY_COMPILER_BUILD_DIR="$HEY_ROOT/build" \
  "$HEY_ROOT/bin/heyc" build --backend llvm \
  ./generate-packages-index.hey -o "$HOME/bin/generate-packages-index"

bin/hey-run pins 601a and rebuilds only when the script, a stdlib file it imports, or the compiler changes. The catch is that it works out whether to rebuild on every run, by walking the script's stdlib imports and hashing them together with the compiler (hashing the two compiler binaries alone took 23 ms here). It took 176.0 ms against 115.6 ms for the same build run directly: about 60 ms of overhead a call. That's more than the 19 ms the hey command adds to a script. For a page generator you run by hand it hardly matters; in a loop, call the binary.

The first stdlib call is no longer the expensive one

In July, at 410a, the first delegated stdlib call in a process (one the compiled program handed to an interpreter) cost about 6 ms and every later one about 54 µs. A 12-line argument check made the script 5 ms slower because its Text.int_token? was the first such call. Re-run on 601a, the same probe (cli-startup-call-cost.hey) reports Text.int_token?'s first call at 4–23 µs, and every call it checks at 0–1 µs once warm. The largest one-time cost left in that list is Time.utc_iso8601, 0.37–0.51 ms on first use. The whole program agrees: --workers 1, which pays for that validation, times the same as no flag.

The three rules, revised

Rule 1: watch how you build lists, not how often you call the stdlib

The July rule was “stdlib freely outside hot loops, builtins only inside them”, because a stdlib call from compiled code cost about 54 µs through the sidecar. On 601a, Collections.compare costs 0.11 µs a call and Text.lower 3.9 µs. Calls aren't what bites any more.

Lists are. On 601a [...xs, x] and xs.push(x) behave as if each returns a new list: they time the same, and appending n items one at a time is quadratic, which is what copying the whole list on every append produces:

AppendsHey 601a, [...xs, x] or pushRuby 4.0.7, xs = [*xs, s]Ruby 4.0.7, xs << s

Each doubling costs Hey four times as much. Ruby written the same copying way grows too, but Ruby's idiom is <<, which appends in place, and Hey has no equivalent. For a few hundred items per list, as here, it's fine. For tens of thousands, it's the cost that decides the run. This generator sorts with the stdlib's merge sort, which still builds its output one append at a time; the fix for the language is a list that can grow without copying, which Hey doesn't have on 601a.

Rule 2: measure output before you measure time

Delete the output, run, assert it came back, compare bytes, and only then start a clock. Every memorable failure in this article's history — the comparator that sorted nothing and the binary that did nothing — looked like success from its exit code.

Rule 3: parallelism has to exist before it can be measured

In July, at 410a, this article reported that .map(fn, workers: n) made the port faster: 24.2 ms at 4 workers against 31.4 at 1 (its Rule 3 said 24.7, its table 24.2), so the default became 4. That verdict doesn't carry over. On 601a .map(f, workers: 2) doesn't compile (“unresolved callable: map”), --workers is parsed and ignored, and 1 and 4 workers time the same. Ruby's version is serial too. Any fan-out verdict for Hey waits until there's a fan-out to measure.

A harness that cannot lie to you

The ordering is what matters — rm before the run, the assertion before the comparison — so a program producing nothing fails here instead of posting a record. This is the shape of the one used for every figure above (the full script is in the evidence file). 

set -eu
export PACKAGES_INDEX_GENERATED_AT=2026-10-10T00:00:00Z
R="$HOME/dev/hey-lang-bootstrap-plan"                       # 601a, pinned per lane
export HEY_ROOT=$R HEY_STDLIB_PATH=$R/stdlib HEY_COMPILER_BUILD_DIR=$R/build
export PATH="$R/bin:$PATH"                                  # the shebang's hey
RUBY="$HOME/.rbenv/versions/4.0.7/bin/ruby"                 # the real binary, not the shim

lane() {                      # $1 = label, $2.. = command
  rm -f packages/index.html
  "${@:2}" >/dev/null
  test -s packages/index.html || { echo "$1: NO OUTPUT"; exit 1; }
  cp packages/index.html "out.$1.html"
}

lane ruby   "$RUBY" --yjit ./generate-packages-index.rb ./packages
lane script ./generate-packages-index.hey ./packages
lane binary ./generate-packages-index ./packages

cmp out.ruby.html out.script.html
cmp out.ruby.html out.binary.html

uptime; ps -Ao pcpu,pid,comm -r | head -6                   # load travels with the number
hyperfine -N --warmup 3 --runs 30 \
  "$RUBY --yjit ./generate-packages-index.rb ./packages" \
  './generate-packages-index.hey ./packages' \
  './generate-packages-index ./packages'
uptime; ps -Ao pcpu,pid,comm -r | head -6

When a lane dies silently (exit 0, no output), suspect the caches before the compiler: in July a racy publish minted a corrupted entry that deterministically produced do-nothing programs, and a dead run wrote its own entry into the run cache. The cache layout has moved since then; the July advice's ~/.cache/hey/run doesn't exist any more. Ask Hey where its caches are, look before deleting, then delete: 

hey cache path          # run_cache=~/Library/Caches/Hey/run, compiler_sidecar_cache=$HEY_ROOT/build/compiler-sidecars, ...
hey cache clear --dry-run   # lists every entry it would remove
hey cache clear             # removes all Hey caches
rm -rf .hey-bin             # bin/hey-run's own build cache, in the site repo

Checked on 601a: hey cache path and hey cache clear --dry-run report the paths above. No poisoned entry was reproduced this time, so this is layout advice, not a re-test of the July failure.

Where Hey loses

On this job: nowhere, compiled, scripted or through bin/hey-run. Beyond it, long-list batch work is still Ruby's. The append table above is the re-measured reason, on 601a. The sibling source-zip port that first showed it was published here in July 2026 as Hey 66.5 ms against Ruby's 153.3 at 500 files, a tie at 2,000, and 2.16 s against 672 ms at 8,000, without the release it was measured on. (The project's findings log has a 402a run of the same port, 2026-07-24, with different figures and the same shape: Hey ahead at 500 files, behind from 2,000, Ruby 5× faster at 8,000.) It hasn't been re-run on 601a, so read those as July's numbers.

Glossary

hyperfine
A benchmark runner: repeats a command, reports mean ± standard deviation.
idiomatic port
A rewrite mirroring the original's structure rather than tuning for speed.
byte-parity
Comparing outputs byte for byte, not “looks right”.
sidecar
A long-lived helper process that serviced stdlib calls for compiled programs in the July-era toolchain.
delegation
A compiled program handing a call to the interpreter instead of running it.
builtin
A primitive the compiler lowers straight to machine code.
worker pool
A fixed set of workers taking items from a shared queue.
exit code
The integer a process returns on termination; 0 means success, and doesn't mean the output is right.
run cache
Where the toolchain stores compiled artifacts for scripts already run (hey cache path prints it).
quadratic
Cost growing with the square of the input: double the items, four times the work.
