Rich questions: images, equations, occlusion

A real 240 MB MCAT deck landed on my desk and it will not import — and the reasons run straight into product choices only you can make. Questions are text-only today. Nearly every card in that deck is an image. You have also asked for a math-equation editor and Anki-style image occlusion. All of it collides with one invariant we have never bent: while a question is open, nothing on any screen may reveal the answer — and the classroom TV makes that sharp. Here is what the file actually contains, what Anki and others already did, and the five things I need you to rule.

The decisions

Decision R1

Where does an image attach — without leaking the answer on the TV?

This is the one that governs the rest. Anki mixes image and text in a single field, and the image often sits on the answer side of the card. Our rule (product invariant 1b) is that while a question is open, no payload and no screen may mark the key — and the classroom television, which the whole room reads at once, must never show it. So we cannot render an imported card’s raw HTML: half of these decks would put the answer diagram on the wall the moment the question opened.

The fix is structure. A question grows two image slots — a prompt image shown while it is open, and an optional reveal image shown only when the teacher reveals — and the importer decides which is which, the same way it already splits a card into question and answer text.

Decision R2

The equation editor — how do we render the math?

You want questions and answers that carry real math: summation signs, fractions, the things a plain text box cannot show. This is a solved problem with a clear split of prior art. Anki itself renders LaTeX through MathJax. KaTeX is the lighter, faster engine most sites moved to; it renders synchronously to HTML and CSS and needs no network. The constraint on our side is that the app ships as a single binary and page scripts are inlined heredocs that must stay byte-identical to their twins and carry no apostrophe — so where the rendering happens matters as much as which engine.

Decision R3

Image occlusion — new question kind, import-only, or later?

You asked for occlusion: black bars laid over a diagram so the student names the hidden label — the anatomy-class staple. Anki ships this as its own Image Occlusion notetype, storing the picture plus a list of rectangles; the study screen hides one and asks for it. It is genuinely useful and it is genuinely the biggest thing on this page: a new question kind, a vector overlay editor in the browser, the regions stored per question, reveal semantics, and rendering on both phone and TV. It also leans hard on R1 — an occlusion is an image whose answer is a region, so the same secrecy machinery has to hide the right box until reveal.

Decision R4

A deck of 2,885 cards and 2,552 images. What are the limits?

The current numbers were set for small decks and a single-shot upload: 500 notes, 4 MB collection, 512 KB per image, and no ceiling at all on images-per-deck. This file breaks all of them — and on a 2 GB box with no swap, “just raise everything” is how the machine and the prayer site next door get killed. I need a shape for the limits, not infinite ones.

Decision R5

Does version one reach the Apple TV, or phones and browser first?

Everything above has to render somewhere. The phone play screen and the browser are this seat’s to build. The native Apple TV app is your device lane — a hey_ios_tv package release and a signed TestFlight build — and images, rendered math and occlusion each need real work in that renderer, which owns its own layout and font sizing. So the question is scope, not capability: does the first version light up the TV too, or ship on phone and browser while the TV keeps showing text aggregates?

Not on this page

Already moving, no ruling needed

Chunked upload is being built now, on your instruction — ~512 KB parts posted into an upload session and assembled server-side, which is the only way a file over 768,000 bytes reaches the server at all. It is the prerequisite under R4 and this whole page; the 240 MB deck cannot import until it lands.

Modern-Anki (zstd) support is a pure-Hey decoder, your call over binding the C library. It is an in-lane build with its own spec and fixture, and it fixes the newer-format refusal — though not this particular old-format file.

The dependency order, so the ruling is buildable

R1 is the foundation — the image slots and the reveal-secrecy machinery. R2 (equations) and R3 (occlusion) both build on it; R4 sets the caps that let a real deck through; R5 decides how far each reaches. A ruling that takes R3-a without R1-a, or R4-c with a 2,885-card deck, is internally inconsistent — I will flag it rather than build something that cannot hold.
