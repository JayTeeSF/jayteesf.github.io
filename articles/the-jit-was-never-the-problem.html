The JIT Was Never the Problem

Hey's interactive session spends 191 milliseconds on every turn, and the obvious suspect is compiling code on the fly. So we measured it. Just-in-time compiling a session fragment with LLVM's ORC costs 0.37 milliseconds. The real bill is a linker step whose entire output gets thrown away one process-exit later. A measured tour of where a REPL turn actually goes, how far a plain-C program can drive LLVM's JIT in 2026 — and the one risk that is still open. The verdict, up front: the JIT plan is ON. Adopting it is how the REPL gets fast — the JIT costs almost nothing, and it deletes the expensive step.

Status: measured research, unshipped plan

Every latency number in this article was measured on real hardware (Apple M-series, LLVM 22.1.8) with a probe you can compile and run yourself. The JIT-backed session itself is a design (R6.1), gated behind a flag, and not landed — today's shipping REPL still uses the build-and-spawn path described below. One named risk (runtime re-entry, §6) must be probed before the design is committed. This article does not claim a shipping JIT REPL; it claims the budget for one — and concludes that budget is easily met. Unshipped means not-yet-built, not rejected.

TL;DR

  • Verdict: the JIT-backed REPL is worth building, and the plan stands. The JIT itself is nearly free (0.37 ms per turn). What makes today's REPL slow is a 140 ms link-and-sign step whose output is thrown away every turn — exactly the step the JIT deletes. Projected warm turn after the switch: ~55–95 ms, inside the 100 ms budget. The only open gate is a runtime question (§6), not JIT cost.
  • A warm Hey REPL turn costs 191 ms today. Only ~50 ms of that is the compiler frontend. Roughly 140 ms is the clang link-and-sign tail plus spawning a fresh process — work whose product is deleted after one run.
  • The JIT costs 0.37 ms. Steady-state, parsing a fragment's textual IR, generating machine code at -O0, looking up the entry point, and calling it averages 0.37 ms (worst of 20 runs: 0.45 ms). One-time warm-up: ~30 ms for the first module, 8.3 ms cold JIT creation.
  • All of it drives from plain C11. No C++. LLVM 22's llvm-c bindings cover the whole needed surface — module ingestion, symbol resolution against the host process, cross-fragment calls, even redefinition — verified by a 168-line probe, not by documentation.
  • Redefining a function in a live JIT session costs 0.4–0.7 ms, using ORC's resource trackers to remove and re-add a module.
  • macOS lets an ordinary un-entitled binary JIT freely. The same machine that blocks improperly signed on-disk executables ran JIT-generated code without a single entitlement — because JIT'd code never exists as a signed artifact on disk.

1. What a REPL turn buys today

Hey's interactive session keeps its state as a source ledger: every definition you have committed, as text. Each new turn replays that ledger plus your new line into one candidate program, compiles it with the full heyc build pipeline, runs the resulting binary as a fresh process, and — only if it succeeds — commits your line to the ledger. It is a wonderfully honest design: the durable state is source code, so nothing can drift, and a failed turn simply never gets committed.

Term: REPL

A REPL (read–eval–print loop) is an interactive prompt: you type an expression, the system evaluates it, prints the result, and waits for the next one. Typing 2 + 2 and seeing 4 is a REPL turn. The whole experience lives or dies on how fast one turn feels.

The honesty has a price. Measured warm on this machine [MEASURED]: a full heyc build of a three-line program is 191 ms (191–243 ms across runs). The interesting part is the split. Asking the compiler to stop after emitting LLVM IR (--emit-ll) takes 50 ms — so the frontend is a quarter of the bill. The remaining ~140 ms is the clang link step, code signing, and process startup: turning perfectly good machine code into an on-disk executable that will be run once and thrown away.

2. The reveal: the expensive part produces garbage

Look at the red block. The linker resolves symbols, lays out an executable, and macOS signs it; then the OS loads it, runs it, and the file is deleted on the next turn. Nothing about the result of that work survives. The only thing a REPL turn actually needs is: get this fragment's machine code into memory and call it. That is precisely the job of a just-in-time compiler.

Term: JIT

A JIT (just-in-time) compiler generates machine code in the running process's own memory and jumps to it directly — no executable file, no linker, no new process. When your browser runs JavaScript fast, a JIT is doing this thousands of times per page. LLVM's production JIT library is called ORC; its batteries-included front door is LLJIT. — LLVM ORCv2 documentation

The suspicion that kept this off the table was cost: JITs have a reputation for heavy startup and unpredictable latency, and the docs for ORC's C bindings are nearly silent. So instead of trusting reputation in either direction, the research wrote a 168-line C11 probe against LLVM 22.1.8 and timed the actual operations on the actual machine. [MEASURED]

Three conclusions fall out. First, at these sizes textual IR is fine: parsing costs under 10 ms even for the largest real module, so emitting bitcode instead would buy nothing. Second, the steady-state number — 0.37 ms — is nearly four hundred times smaller than the link tail it replaces. Third, the honest caveat: under the replay model the candidate module grows with your session, and codegen grows with code mass (~45 ms for a 42 KB program), so the design's success gate is measured on a loaded session of 50 committed functions, not an empty one.

4. You can drive all of this from plain C

Hey's runtime and compiler tooling are C11 by rule; a C++ dependency would be a real cost. The probe exercised the complete needed surface through llvm-c headers only [MEASURED]: creating the JIT, ingesting textual IR, resolving the ~571 hey_* runtime symbols a fragment declares against the host process itself [retracted — see the correction below], calling across fragments (fragment 2 calling fragment 1's function worked on the first try), and redefinition via resource trackers — remove the old module, add the new one, observe the new answer (the probe checks 222 replaces 111).

Two traps worth recording. The C API has real gaps — no out-of-process execution, no object-cache hook — but none of them sit on this design's path. And the bindings churn: LLVMOrcThreadSafeContextGetContext, present in every old tutorial, is gone in LLVM 22 [MEASURED] (compile error; use LLVMOrcCreateNewThreadSafeContextFromLLVMContext). Code written from the community walkthroughs will not build unmodified. The probe file is the working reference: docs/agents/orchestration/research_r6_lljit_probe.c in the toolchain tree — C11, llvm-c only, compile it against llvm-config and every number above reproduces.

5. The macOS surprise

Term: Code signing (AMFI)

macOS verifies a cryptographic code signature on executables before running them; the kernel component enforcing this is called AMFI. Ship a binary with a broken or missing signature and macOS refuses to launch it — this project has the scars: a whole class of generated on-disk executables was once killed at launch by exactly this.

The pleasant twist: the JIT probe — an ordinary ad-hoc-signed binary with zero entitlements — generated and ran machine code freely on the same machine [MEASURED]. The reason is architectural: JIT'd code never exists as an on-disk artifact, so there is nothing for launch-time signature enforcement to check. LLVM's JITLink quietly handles the memory-permission choreography (MAP_JIT, write-protect toggling, cache invalidation) internally. Only a distributed, notarized host binary would ever need the com.apple.security.cs.allow-jit entitlement [DOCS]. Linux, for completeness, imposes no comparable regime for plain processes.

6. The plan — and the risk that is still open

The staged design (R6.1) keeps the session's transactional soul and swaps only the wasteful slice: the session tool compiles each turn to IR as before, but hands it to a persistent C11 host process that JITs and runs it in-process — one fresh, discardable JIT library per turn, so a failed candidate is simply never committed. It lands behind a flag (HEY_REPL_JIT=1) with the current build-and-spawn lane remaining the default until a 100 ms latency gate and the full parity batteries pass on both macOS and Linux. Crash isolation follows from the ledger design: if a fragment takes the JIT host down, the supervisor respawns it and replays committed source — at 0.4 ms per fragment, rebuilding a fifty-definition session costs a blink.

And the honest open question, stated plainly: today every turn runs in a fresh process, so Hey's runtime initialization has never needed to tolerate running twice. Under a persistent host, generation N's entry point runs in the same process as generation N−1's, and actors, workers, and exit-handlers persist across turns. Whether hey_runtime_init() survives re-entry is unknown and unprobed — it is the named first experiment (P1) and the single largest swing factor in the estimate. If it fails, the fix is runtime work, not JIT work. The JIT, for once, is the part that is already proven.

Correction — 2026-07-28

One capability listed above as measured had not been measured. §4 said the probe resolved the ~571 hey_* runtime symbols “against the host process itself.” It did not. The probe defined its test function in JIT'd IR and then resolved a second fragment against the first — JIT-to-JIT, never JIT-to-host. The process-symbol lookup the design depends on was attached and never exercised, so the probe could not have failed on it.

When the missing test was finally written, it failed on Linux: without -rdynamic the host's symbols are not published for runtime lookup and the JIT reports “Symbols not found.” macOS passes by default, which is why this went unnoticed here. The design survives with a better mechanism — registering the host's addresses directly, no link flag — and it gains one new constraint: JIT'd fragments must not touch a _Thread_local directly.

Full account, with both platforms' receipts: The Test That Never Ran. The latency measurements in this article are unaffected — the error was one entry in a capability list, not a timing. The open runtime re-entry question (§6) also stands.

Glossary

REPL
Interactive read–eval–print prompt; one typed expression per turn.
JIT
Compiler that emits machine code into the running process and calls it directly, skipping files, linkers, and process spawns.
ORC / LLJIT
LLVM's production JIT library, and its batteries-included entry point.
Textual IR
LLVM's human-readable intermediate representation (.ll files) — what Hey's compiler emits before machine code.
Resource tracker
ORC handle that lets you remove a previously added module — the primitive behind redefinition and undo.
AMFI
macOS kernel enforcement of code signatures on executables at launch.
Source ledger
Hey's REPL state: the committed source text of every definition, replayed each turn.
