The Ladder With No Bottom

A compiled Hey program needs a helper binary. It has a list of places to look. What should it do when every one of them comes up empty? Ours picked a path relative to whatever directory it happened to be started in. We put a stand-in there, and it ran.

Status: fixed before publication

Both paths described here are closed in 468a. This piece was written while they were open and held until a fixed version existed — the reason it can name the mechanism is that naming it no longer helps anyone.

TL;DR

  • Verdict: a lookup that invents an answer when it runs out of candidates is a security defect, not a convenience. Ours had no bottom, so it walked off the end into the current working directory.
  • Measured, not theorised: with no toolchain installed and a decoy in the working directory, our stand-in binary executed — twice, because the runtime respawns its helper on death. The program reported a delegation error and carried on.
  • One cause, three bug reports. The same ladder produced a ~150x slowdown, a wrong answer, and this. Three people filed three tickets over one week and nobody saw it was one defect until the third arrived.
  • Disclosed weakness: our first proposed fix would not have worked. We wrote "reject relative paths, require an absolute one" — and getcwd() returns an absolute path, so the dangerous case sails straight through that check.
  • Check your own: find the fallback at the end of any resolution chain in your code. If it returns a value rather than an error, ask what happens when an attacker controls the directory your program was started in.

What a program does when it runs out of ideas

Hey compiles to a native binary, and that binary sometimes needs a helper process for standard-library calls the compiler cannot yet emit directly. To start the helper it has to find it, so it works through a list: an environment variable, a path derived from another environment variable, a location beside the running executable, the current directory.

Every one of those is a defensible place to look. The defect was in the line after the list. When all four came up empty, the function did not stop — it returned a default: a path relative to wherever the process happened to be running. On a developer's machine one of the earlier candidates always matched, so nobody saw the last line. On a customer's machine, running a binary you shipped them with no toolchain installed, the search fell all the way through.

Fail-open

A component that carries on with a substitute when it cannot do its job, instead of stopping and saying so. The convenient choice, and always the more expensive one to debug: the symptom surfaces far from the cause, and everything in between looks healthy.

The measurement

We built a minimal program that makes one delegated standard-library call, cleared the toolchain environment — the state a customer's machine is in — put a harmless stand-in where the fallback pointed, and ran it.

The stand-in executed. Twice — because when the helper exits unexpectedly the runtime respawns it, so a hostile stand-in gets invoked once per attempt. The program printed a delegation error and continued running, which is the part worth sitting with: from the outside this looks like a minor bug in an unrelated feature, not like something else executing.

A second path was found in the same family: an environment variable holding a bare name, which was resolved through PATH. That one also ran.

How bad is it, honestly

It is not a remote hole and it does not cross a user boundary by itself. Someone who can already set your environment can usually do worse. What it does is upgrade a weak primitive into a strong one: "an attacker can create a file in the directory this service runs from" — normally a low-severity finding — becomes "an attacker runs code as this service." No user interaction, no toolchain on the target, and the application's own logs say only that a library call failed.

Working directories are not exotic. Services get started from data directories, containers mount volumes at the working directory, CI runners execute in workspaces that job configuration can write to.

The fix we proposed first, and why it was wrong

Our initial recommendation was: never fall back to a relative path, and validate that the target is absolute.

That check does not work, and the reason is worth more than the bug. getcwd() returns an absolute path. A fallback built from the current directory is absolute by construction, so "is this path absolute?" waves it straight through. We would have written a check that could not fail, in the fix for a security defect — caught by a second engineer on another machine within the hour.

The dangerous property is not the form of the path, it is its provenance: derived from the current working directory. So the shipped fix does not validate that rung. It removes it. One resolver replaces the two ladders; every candidate is now either an absolute environment value or an ancestor of the real path of the running executable; getcwd(), "." and "./bin/heyc" do not appear at all. When nothing resolves, the function returns a refusal and all three callers fail closed. The spawn also moved from the PATH-searching call to the one that does not search, which removes the second path by construction rather than by checking.

Three tickets, one defect

The part we would most like to have back is not the bug, it is the week. The same ladder had already produced two other failures:

Reported asActually
A server running ~150x slower than expectedthe invented answer sent it down a slow path instead of stopping to say the fast one was missing
A wrong answer in compiled codesame ladder, different consumer
A code-execution pathsame ladder, this article

Three reports, three categories, three owners, one cause — and it took the third to see the first two. That is not carelessness; it is that our categories are shaped like symptoms. A stopwatch, a wrong answer and a threat model are three instruments pointed at the same place, and none of them is built to say this is the other two.

What we would ask you to check

Find the end of any resolution chain in your own code — a plugin loader, a config search path, a helper binary lookup. Read the line after the last candidate. If it returns a value rather than an error, you have the same shape, and the question is only whether anyone can write to the directory your program starts in.
