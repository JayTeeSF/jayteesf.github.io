Great Command-Line Scripting with Hey

A practical guide to writing a real Hey command-line program on today's toolchain (v0.99.397a): Ruby-style ergonomics, honest benchmarks against an identical Ruby implementation, and the hot-loop rules that keep compiled Hey fast.

TL;DR

Build once, run the native executable:

export HEY_ROOT="$HOME/dev/hey-lang-bootstrap-plan"
"$HEY_ROOT/bin/heyc" build --backend llvm \
  ./generate-packages-index.hey \
  -o "$HOME/bin/generate-packages-index"

generate-packages-index --workers 1 ./packages

On an Apple M-series laptop this renders a 12-package documentation index in 22.8 ms — 5.8× faster than the equivalent Ruby (134 ms, Ruby 3.4 + YJIT) — while producing byte-for-byte identical HTML. Use --workers 1 for small trees: parallel rendering only pays past hundreds of items.

The running example

One script, two implementations: generate-packages-index.hey and generate-packages-index.rb. Both walk a package directory, natural-sort every versioned docs/ directory and every Markdown/HTML file, and render one static index page. Given the same timestamp (PACKAGES_INDEX_GENERATED_AT), their output is identical to the byte — which is what makes the benchmark honest: you cannot get faster by quietly doing less.

Hey can read like Ruby

Receiver chains, predicates with ?, string interpolation, heredocs:

private fn linkable?(path)
  let lower_path = Text.lower(path)
  return Text.ends_with?(lower_path, '.md') or Text.ends_with?(lower_path, '.html')
end

private fn linkable_files(package_files)
  return PackagesIndex.sorted_unique(
    package_files.filter(PackagesIndex.linkable?)
  )
end

private fn package_directories(packages_dir)
  return Files.entries(packages_dir)
    .filter(PackagesIndex.visible_directory?)
    .sort(PackagesIndex.compare_paths)
end

Also available: .uniq, .map(fn), .map(fn, workers: n).collect() for parallel fan-out, .empty?, value.length, %qq(...) interpolated strings with #{expr}, and <<~'TEXT' heredocs for usage banners. A Ruby programmer can read the whole 560-line script cold.

The three rules that keep compiled Hey fast

Rule 1: bare builtins in hot loops

Language builtins (len, slice, find, parse_int, to_json…) compile to native code. Stdlib facade calls are fast for ordinary use (~3 µs via v0.99.397a's 60-entry direct table), but a natural-sort comparator that runs thousands of times per sort should not pay even that. Switching our comparator's inner loop from per-character facade calls to bare slice plus direct != was a 20% end-to-end win.

Rule 2: verify output, not just speed

Our first optimization pass used byte_at(string, i) — which compiles and silently returns 0 (it is a Bytes-value operation, hey 0.99.397a). The comparator declared every path equal, the sort became a no-op, and the benchmark got faster and wrong. The byte-parity check against Ruby caught it instantly. Benchmarks without output verification are wishes.

Rule 3: parallelism has a floor

.map(fn, workers: 10) over 12 packages: 109 ms of wall clock for 783 ms of CPU — 4× slower than one worker. Worker fan-out pays for large workloads, not a dozen quick renders. Default to --workers 1 and measure before scaling.

Where the next speed comes from

Profiling the 22.8 ms shows no single hotspot — the time is spread across boxed-value allocation and copying plus real filesystem syscalls. That diffuse cost is precisely what the toolchain's in-flight work targets (copy elimination in ordinary compiled paths, and a precompiled stdlib archive). The same probes that measured this article's numbers are committed beside the source, so when those land, this table gets a new row rather than a rewrite.
