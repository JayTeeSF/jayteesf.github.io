Who Decides When a Value Is Freed

Step 2 of Hey's typed-MIR work, designed on October 23 and being built from October 24. MIR is the compiler stage that plans how values are stored and released. The LLVM emitter, the last stage, turns that plan into low-level code. Today both decide when a value is freed. Step 2 gives the job to MIR alone, with a separate checker.

Status, 24 October 2026: being built now, each pick reversible

As of about 05:00 PDT, the compiler team is implementing the recommended picks so the work isn't blocked waiting for rulings. Each pick goes in its own change, so any one can be reversed. The six decisions each show the options, what's being done, and what a "no" costs.

  • Branch: a dedicated ownership branch, made from the integration branch.
  • First step: a failing test for the quadratic put inside a branch, then the consume-exactly-once verifier.

Short version

  • A missed note makes a map loop quadratic: 80,000 updates take 88 s instead of 0.02 s when the update is stored inside a branch.
  • After step 2, MIR decides, a separate verifier checks, the emitter obeys.
  • Slice S4 moves the decision with identical output; S6 and S7 change it, measured.

1. A map update stored inside a branch is copied every time

Ordinary Hey: each put returns a new map, and the old one is never used again.

while i < n
  if direct
    set stats = stats.put("k#{i}", {sum: i, count: 1})
  else
    set stats = add_reading(stats, "k#{i}", i)    # the same put, inside a function
  end

A Hey map counts how many places hold it. If put sees a count of one, it writes in place; otherwise it copies the whole map.

in the branch, 20,000 keys
5.1 s
in the branch, 40,000 keys
20.0 s
in the branch, 80,000 keys
88.0 s
through a function, 80,000 keys
0.02 s

One run each, Apple M3 Pro, evening of October 23 (PDT). Doubling the keys quadruples the time: every update copies the map.

The difference is a text note MIR adds to the end of a line:

store stats:boxed = call @r1769118190 @o1 put(stats, ...)                        # branch: no note, copies
store stats:boxed = call @t0.0 add_reading(stats, ...) ; move b7                # function: handed over
store stats:boxed = call @r1769118190 @o1 put(stats, ...) ; own b2 ; reuse b2   # no branch: in place

Nothing flagged the missing note.

2. Today MIR and the emitter both decide, and the check reruns MIR's own code

  • MIR has eight kinds of note. Passes that scan MIR text write them; later code finds them by searching for substrings.
  • The emitter makes most release decisions itself. It reads back the LLVM it just wrote, and two hand-written lists of runtime function names fill in the rest.
  • The check reruns the passes that wrote the notes and compares text, so it can't catch a note they never write.

3. After: MIR writes every release as a statement, and a separate verifier checks it

This is the Perceus design (the Koka compiler, PLDI 2021), which builds on Lean 4’s reference counting (“Counting Immutable Beans”, 2019).

1Name every value

Every intermediate result becomes a temporary, $1, $2, so each has a last use.

2Write dup and drop

dup adds a reference, drop releases one, at last use. A dead value passed to a parameter that keeps it is handed over, not copied.

3Verify separately

A pass of its own counts +1 per owned definition, parameter or dup, −1 per drop or hand-over. Every path must end at zero, or it names the rule, line and binding.

4The emitter obeys

It turns the statements into instructions and stops reading its own output.

# the branch after step 2: a sketch in the design's form, not compiler output
# (@r1769118190 is put's runtime identity)
temp $1:boxed = call @r921413014 to_s(i)
temp $2:boxed = "k" + $1
drop $1
temp $3:boxed = {sum: i, count: 1}
store stats:boxed = call @r1769118190 @o1 put(stats, $2, $3)   # stats dead after: handed over

One rule covers every binding: stats isn't used again and put keeps its map, so put gets the only reference, branch or not. The author's reading: this loop gets fast once S5 marks put's map parameter as kept and S6 moves drops to last use; the bug's notes name S6.

A wasted copy isn't a wrong release, so a second test times put, push and append loops at n and 2n: time must double, not quadruple. The C runtime's one uniqueness test, hey_rc_count_is_unique, stays as the final guard for values MIR can't see into.

5. It needs every call's target first (step 1b)

MIR has to know which function each call reaches (its call identity), resolved, never guessed from a spelling. About 650 calls in the compiler's own MIR lack one; the fix is in progress. Until then they keep today's safe, slower default.

6. Decisions: retire heyc's MIR path, use $N, no leaks, accept a measured S6, specialize later, gate memory every slice

From the design's open questions. Picks are the author's, and the compiler team is building them now (see Status at the top). Each card shows every option, what's being done for the pick, and what a "no" costs. To answer, copy the reply line.

Reversal estimates are the author's judgment, not measurements.

The verifier fails on: use after hand-over, a count below zero (double drop), a count not zero at ret, fail or a self tail call (missing drop), branches or loop edges that disagree where they join, and a borrowed value dropped, handed over or outliving its owner. Each rule has a broken-MIR test that must fail, and must fail again if that rule is switched off. Source: design sections 3 and 5.

Borrow inference (from Lean): a parameter a function only reads is borrowed, so neither caller nor callee touches its count; one that's returned, stored, sent or passed on to a keeping parameter is owned. This is what S5 does.

Evidence: reuse, the test switches, and what Perceus and Lean measured
  • Reuse (Lean 4 reset/reuse): when a record dies just before a record of the same shape is built in the same function, the new one is written into the old memory if the old one was unique.
  • Two test switches live inside hey_rc_count_is_unique: HEY_VIOLATE_COW_UNIQUENESS=1 (always "unique") must turn the alias tests red; HEY_RC_COW_FORCE_SHARED=1 (always "shared") must zero the in-place counters with identical output.
  • From the Hey research brief of 2026-10-23, which quotes the papers; the papers weren't re-read for this page. Perceus (Reinking, Xie, de Moura, Leijen, PLDI 2021): red-black tree with 42 million insertions, purely functional Koka "within 10% of the performance of the in-place mutating algorithm in C++"; without the reference-count optimizations "more than 2x slower". Where data is heavily shared, the gain is smaller. Reuse can hold memory: cfold without the optimizations used 11% less. The paper argues the best results need static compiler facts and a runtime is-unique test together.
  • Lean 4, "Counting Immutable Beans" (Ullrich, de Moura, IFL 2019): reset/reuse and borrow inference.
  • Later work, not measured: the 1BRC program (the one-billion-row challenge, in ordinary Hey) reads a returned record field by field and drops it. Step 2 makes that last use visible; not building the record at all is later work with no estimate. 1BRC runs at about 12,000 instructions per row against C's 326 (lesson of 2026-10-23).
Words used here
MIR
Hey's mid-level intermediate representation: evaluation order, temporaries, how values are stored and who owns each one.
LLVM emitter
The last Hey stage. It turns MIR into LLVM, the low-level code that becomes machine code. By the rules it obeys MIR and decides nothing.
reference count
How many places hold a value. At one, the value can be changed in place safely.
dup / drop
Add one reference / release one. At zero the value is freed.
A-normal form
Every intermediate result has its own name, so each has a definite last use.
verifier
A pass that checks MIR's rules and fails with the rule, line and binding. It's separate code from the passes it checks.
call identity
The resolved target of a call (@t for Hey functions, @r for runtime functions), not its spelling.
self-compile
The Hey compiler compiling itself. Its peak memory and time are part of every landing's checks.
byte-identical
The compiled LLVM text is exactly the same as before the change.
