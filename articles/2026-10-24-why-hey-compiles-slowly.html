Why Hey Compiles Slowly

For weeks the release metric was how long one stage of Hey's self-compile took, most recently 63.4 seconds. A real self-compile, with every stage, takes about 16 minutes. And every Hey stage does more than twice the work when the program doubles.

Status, 24 October 2026, 05:55 PDT: the Maintainer has answered all three questions; six fix streams

  • Running now: four fix branches and one measurement gate; two more streams assigned by the Maintainer, emit-llvm memory and narrowing (below).
  • Decided: Q1 not yet (measure first), Q2 yes, Q3 yes. Work on Q2 and Q3 follows those answers.

A real compile takes 16 minutes, not 63 seconds

The 63.4 s metric timed one stage, HIR emission (HIR: the form that says what the program means), on a short route that skips name resolution. This morning every stage of the real route was timed. measured

A real self-compile

Even emit-hir alone does 5.6x more work on the real route: it reads the resolver's output. "G" means billions of machine instructions, the steady number; wall seconds were taken on a busy Mac and run high.

Words used on this page
Resolve
Work out which definition each name refers to.
HIR, MIR
Hey's two in-between program forms. HIR says what the program means; MIR adds evaluation order, how each value is stored, and when it's freed. emit-hir, lower-mir, annotate-mir and emit-llvm are the stages that build them and then the LLVM text.
Narrowing
HIR rounds that work out more precise types; they repeat until nothing changes.
Gate
An automatic test the release line runs. A "landing" is merging a change into the release line.
Per doubling
How much more work a stage does when its input is twice as long. 2x is linear; 4x is quadratic.
Interning
Storing each distinct name once and handing out its number, so equal names get equal numbers.
Hash index
The table that lets a map find a key without checking every entry.
Thread-local lookup
Finding the current thread's own data; on macOS today it's a function call per memory allocation.
Perceus
A published method (PLDI 2021): the compiler marks each value's last use, so an unshared value is updated in place instead of copied. Hey is adding it in steps; step 2 is ownership in MIR.
Backend
The part that turns the final form into machine code. Hey's is LLVM, run through clang. Cranelift, TinyCC and Zig's x86 backend are smaller, faster ones.
MLIR
LLVM's framework for building compilers out of in-memory IRs that also have an exact text form.

Map copies lose their index

A copied map has no hash index, so the next lookup rehashes every key: 49-70% of the narrowing functions measured (7,606-line test).

One import costs 48x

Hello world resolves in 0.037 G. Add import 'stdlib:Text' and one call: 1.772 G.

Ordinary Hey programs share some of this. Building a string with out = out + piece grows 3.5-3.9x per doubling when piece isn't typed; typed strings are already linear.

Fast compilers keep small numbers in memory, not text

Hey spends about 106 million instructions per line just to reach HIR. TinyCC, a C compiler, spent roughly 2,800 cycles per line to compile and link, on a 2002 Pentium 4. Fast compilers share four habits. sources

Three questions, decided by the Maintainer

The cards were written as questions; the Maintainer answered from the draft on 24 October. Each still shows every option and the original recommended pick, with the decision on top.

Q1Decided: not yet. Measure the print-and-parse cost at each stage boundary first

Maintainer's answer: not yet. First measure what printing and re-parsing costs at each stage boundary. Meanwhile fix repeated decoding inside stages now, under the existing rules. (The design had recommended yes.)

Why it's a question: design rule 1 says each IR has one parser and print(parse(x)) == x. Passing what parse returns, instead of its printout, adds no second reader and no side file of extra facts, but the gates would no longer run the text through every compile.

OptionCostsRisksEnables later
Pick One process; pass the parsed records; print text for gates, debug dumps and the parse cache Large: the stages become one process, and the gates add a print-then-parse check at each boundary. A record could hold something its text can't express; the boundary check catches that. Earlier stages' data may still be in memory at emit-llvm's 9.33 GB peak, and peak memory is part of the landing bar, so each stage's data must be freed when the next starts. Removes about 117 MB of print and re-parse per self-compile, and the places that cut text apart to read it back (HeyMir 79, HeyLlvm 111, HeyHir 48). Gain unmeasured; the research guesses over 20% of a full build.
One process, but pass the text in memory Medium: one process; no rule change. Saves file writes and process starts, but every stage still parses. A first step toward the pick.
Keep text files between every stage (today) None now. The print and re-parse cost stays in every stage. Each stage stays a separate process anyone can inspect.
A binary format between stages (like Go's export data) A second serialized form to keep in step. That's a second reader, which rule 1 forbids. Fast loading, decoding only what's used.

Why this pick: it's how MLIR works. The text round-trips exactly for testing, and passes never re-parse it. Hey already took MLIR's text and verifier ideas; this takes the in-memory half.

Q2Decided: yes, identity only. A lexer-interned name number counts as a resolved identity

Maintainer's answer: agree, identity only, with a rule against comparing a symbol to a fixed name.

Why it's a question: the rule says no facts from spellings; use resolved identities (@t, @r: the IDs MIR's reader decodes). An interned number stands for one exact spelling, so it could be misused as a spelling check in disguise.

OptionCostsRisksEnables later
Pick Yes: the number means "same bytes", nothing else; it's a type that can't be compared with a constant, and a gate scans compiler source for such comparisons Medium: the lexer, the naming module (HeyNames) and HIR change; plus the type and the gate. Someone writes if sym == PUSH. The type and the source gate are what refuse it; the MIR verifier can't see compiler source. Name comparisons and lookups become integer operations (part of the ~10% string building and ~6% field-name lookups in one emit-hir profile); makes 5-byte tokens possible.
No: names stay strings until the resolver gives them an identity None now. Byte-by-byte name comparison stays in the lexer, parser and resolver. Nothing new.
Only resolver-issued numbers, no lexer interning Small. Helps only after resolution; the resolver itself, the 3,534 G stage, gains little. A smaller step toward the pick.

Why this pick: every fast compiler in the research interns (Zig, Carbon, rustc, MLIR, TinyCC). Interning only says two names are spelled the same. The resolver still decides what a name means.

Q3Decided: LLVM only for now; measure the -O0 option separately

Maintainer's answer: agree with the pick (LLVM only until clang's share is measured), and measure the LLVM -O0 option on its own.

Why it's a question: Zig, Rust (Cranelift), V (TinyCC) and Roc all add a fast debug backend, and Zig measured 3-4x. But a second backend has to obey every MIR plan the LLVM one obeys.

OptionCostsRisksEnables later
Pick LLVM only for now; measure clang's share of hey run on real apps, and reopen if it's over a third One measurement. If clang is already a large share of hey run, debug builds stay slower than they could be until then. One backend to keep correct while ownership and typed MIR change.
A fast backend now (emit C for TinyCC, or Hey's own) High: a second emitter. Two emitters can disagree about MIR's plans. Faster edit-and-run.
LLVM with less optimisation and its fast instruction selector for hey run Low: flags (the author's guess). heyc's LLVM default is -O2 (set in the heyc driver); what hey run passes wasn't checked. Gain unmeasured. Some debug speed with no new backend.

Why this pick: in the self-compile clang is 65 s of 973 s, 7%; its share in hey run of ordinary apps hasn't been measured. The slow parts measured so far are Hey's own stages, and emit-llvm's 285 s is Hey code a new backend would have to replace too. The one-third threshold is the author's suggestion.

How the estimates were made
  • HIR reads the tree: on the real route, operator rescans (hey_hir_top_level_marks 10.4% and four helpers, 14.2% together), number-token normalisation and receiver sugar (16.8%) and the type-guard scan (8.7%) are 39.7% of emit-hir's 5,676 G, about 2,250 G. "Up to" because some of that work stays.
  • Resolver: array-copy steps 36.2% plus freeing the copies 11.2% of the resolver's samples. That profile was on tools/hey_resolve_program.hey, a smaller input; applied to the self-compile's 3,534 G it gives about 1,675 G.
  • Runtime: the thread-local lookup was 5.5% of one short-route emit-hir profile, about 800 G if that share holds across the compile. Index rebuilding shows up in narrowing and emit-llvm, but its share of the whole compile hasn't been measured.
  • Short-route shares, for comparison (the 61.3 s profiling run, bottleneck ledger rows 9-11): operator rescans ~19%, type-guard scan 14.9%, growing-string copies ~14%.
