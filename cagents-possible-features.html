The first paying customer probably won't buy “multi-agent.” They'll buy control.

Cagents can coordinate many agents already. The commercial question is harder: what problem is painful enough that an organization pays to put Cagents in the middle of its engineering work? Research across agent platforms, regulated industries and storage systems points to a specific answer.

The product is not another coding agent

Coder, Factory, GitLab, OpenHands, Cursor, Microsoft, AWS and the model vendors are investing heavily in agent execution. LangGraph, CrewAI, Microsoft Agent Framework and other frameworks already make it easy to construct multi-agent workflows. Trying to win by adding one more orchestration graph or one more secure VM is fighting markets with strong incumbents.

Cagents has a different set of primitives: persistent actors, project and channel membership, scoped communication, task ownership, delegation, durable decisions/evidence, provider-neutral sessions, and a human-and-agent coordination graph.

Recommended category: Cagents is the coordination, authority and governance plane for AI-native engineering organizations—or, more compactly, an organization control plane for humans and AI agents.

The buyer pays because Cagents can answer: Who is this agent? Who authorized it? What can it see, do, tell another agent, or send outside the company? Which model is it using? What happened? Can we revoke it now? Can we prove all of that later?

The first customer should already have an agent-governance problem

The ideal design partner is not a tiny team experimenting with one assistant, and it is probably not a federal agency with a two-year procurement path.

Examples include defense-tech/aerospace contractors, fintech/trading infrastructure, cybersecurity vendors, medical-device/biotech software organizations and energy/industrial software companies.

The pitch: “Use Claude Code, Codex, OpenHands, Coder, local models and future agents. Cagents gives every human and agent one durable identity, scopes what each may see/do/delegate, coordinates their work, and produces an explainable audit trail—inside your infrastructure.”

Compliance language matters. CMMC, HIPAA, FedRAMP and FDA Part 11 generally apply to scoped organizations, systems and uses—not to a software binary in isolation. Cagents should support controls and produce evidence without making unqualified “compliant” claims.

Why defense contractors first?

NIST SP 800-171 and the CMMC ecosystem make protection of Controlled Unclassified Information an economic requirement for many defense suppliers. An AI coding agent that can read source, invoke commands, reach networks, delegate work or send context to a remote model creates exactly the kind of access and audit questions those organizations already have to answer.

Direct federal/FedRAMP sales can come later. Building the technical deployment posture early is useful; paying the full procurement/authorization cost before product-market evidence is not.

What about using customer data to train a better model?

Private communications, source code and agent traces could eventually make powerful customer-specific training corpora. But making cross-customer training the hidden economic engine would sabotage the trust proposition needed to win regulated customers.

Default recommendation: no training on private customer content. Offer opt-in, customer-owned SLM/fine-tuning/corpus generation inside the customer's boundary. Cross-customer learning should require explicit contractual opt-in and provenance—not a broad terms-of-service permission.

What about building so GitLab buys it?

GitLab is both a serious competitor and a plausible strategic partner/acquirer because its Duo Agent Platform already links agents to project permissions and audit. But acquisition should be an outcome, not the product requirement. A Cagents that works equally well over GitLab, GitHub, Bitbucket, local source and arbitrary A2A/MCP agents is strategically more valuable to every potential acquirer.

Git should become the export, not the transaction

The current Git-centered design bought Cagents something important: a portable, human-readable, inspectable history. It also created a fatal real-time coupling: an agent can leave a coordination checkout dirty and prevent another agent sharing that checkout from synchronizing status.

Recommended first database: PostgreSQL. It already has mature MVCC, transactions, row/advisory locks, constraints, HA/backup tooling and an enormous operational ecosystem. Cagents already has a `hey_postgres` package repository, so this aligns with a Hey/Distributed Hey server without making the product a database research project.

Why not ordinary SQLite?

SQLite's own guidance says it allows one writer at an instant per database file and recommends client/server databases when many independent writers truly need concurrent writes. Cagents Cloud is becoming exactly that workload.

Why Turso is still worth watching

Turso Database now has an MVCC mode and BEGIN CONCURRENT for optimistic concurrent writers. That is extremely interesting for Cagents' embedded/self-contained future. But in 2026 its concurrent-write path is still described as beta/early preview in current Turso materials, so the first regulated enterprise customer should not be the durability test.

Do not throw away Git

Make the database authoritative and export the same durable Cagents graph deterministically to Git. The customer keeps readable history, diffs, escrow and portability without asking every agent to become a Git synchronization worker.

A2A and MCP make the “browser wars” strategy better, not worse

Trying to make every vendor adopt a Cagents-only agent protocol would be a losing fight. A2A now gives independent agents a shared interaction model, while MCP gives agent applications a shared way to discover and use tools/data.

MCP
agent/application ↔ tools, data, resources
A2A
agent/system ↔ independent agent/system
Cagents
organization ↔ identity, delegation, policy, authority, approvals, audit

The platform play is to become the enterprise policy and receipt boundary around standard communications. Cagents should know that an A2A call was authorized by delegation X and exposed source scope Y; it should know that an MCP tool call was allowed by policy version Z and approval A.

North star: don't own every wire. Own the answer to why this wire was allowed to carry this action/data for this actor/project.

Then talk to customers before adding fifty more things

The next validation step is 10–20 structured conversations with engineering/security leaders already managing multiple AI coding agents. The most valuable answers are not “would you use this?” but:

  • Which agent activity are you currently forbidding because you cannot govern it?
  • What event would force you to buy a control plane this quarter?
  • Which data can never leave your network?
  • Which approvals/access records do security or auditors already ask you to produce?
  • Which existing product almost solves this, and why doesn't it?
  • Would you deploy a customer-VPC/self-managed service? Who owns that decision?
The commercial thesis is testable: if organizations are willing to pay to safely permit agent autonomy that they currently prohibit, Cagents has a business. If they only want a nicer agent chat UI, incumbents have the advantage.

The recommendation

Keep the most unusual parts of Cagents—the persistent actor graph, channels, delegation, authority, task ownership, decisions/evidence and provider neutrality. Replace the live Git mutation mechanism with a proper concurrent service. Make A2A/MCP standards first-class. Build deterministic enterprise controls around source, tools, models, networks and agent-to-agent delegation.

Then sell the result as the system that lets a security-conscious engineering organization say “yes” to more agent autonomy because it can bound, revoke and explain that autonomy.
