The Tax C Never Pays

When an array read is a function call. Hey's raw arithmetic already runs within 6% of C — yet a benchmark that does nothing but shuffle a small array runs 161× slower. Those two numbers cannot both be about "a slow language." They are both about what one access costs: a bill of materials, measured by counting, with a fix that removed exactly half of it and a pre-registered plan for the rest.

TL;DR

  • Verdict: Hey's speed gap on array-heavy code is the price of the access, not the arithmetic — so the next fix inlines the access, and it ships only through pre-registered measurement gates. It is designed, priced, and not yet built. On a registers-only integer recurrence Hey runs at 1.056× of C; on fannkuch-redux, which is all array reads and writes, the quiet-box figure is 161× (n=10, linux i7-1165G7, 471a).
  • The honest ladder (fannkuch-redux n=10, same linux box, same session, lanes interleaved, medians of 5, answers oracle-checked, Hey at 473a): C -O2 185.5 ms (milliseconds), Go 191.3 ms, Ruby 4.0.6 2,492 ms, Hey 32,215 ms. This includes a correction that goes against us: the previously published "~3× behind Ruby" was measured against end-of-life Ruby 2.6; against current Ruby the honest number is 12.93×.
  • The bill of materials, measured by counting: every element store buys two heap allocations of a 32-byte value box. A fusion fix removed one of them exactly — allocations per store 2.000 → 1.000, −22.7% on the store path (linux, branch-ready 2026-07-30).
  • That fix scored its own prediction as a MISS, and the miss re-priced the story: removing one allocation pair bought ~9 ns (nanoseconds) of a ~38 ns per-store budget, not the predicted half. Allocation is about half the cost; the other ~20 ns is the call itself — dispatch, defensive checks, and bookkeeping C never executes, because C's a[j] is one load instruction.
  • Disclosed weaknesses: half of the 38 ns decomposition rests on an assumption (the second allocation site is assumed to cost the same ~9 ns as the first; it was never measured directly). And fresh counting on a second machine found that the compare shape if a[1] > a[2] leaks 64 bytes per iteration on that venue (Darwin, 474a) — and fannkuch's flip test is exactly that shape.
  • Falsifiability: the allocation counts reproduce with a three-shape counting probe under HEY_ALLOC_STATS=1 (evidence archived in the project's dated benchmark cells, 2026-07-30, run twice with identical counts), and the coming fix carries published predictions — including the result that would prove it wrong — written down before it is built.

How to read these numbers

Every timing in this article names its box, its version, and its instrument, because the numbers do not transfer without them. The linux figures come from a 4-core i7-1165G7; timings are medians of 5 with the competing lanes interleaved (run A, B, C, A, B, C… rather than all of A then all of B), and no timing counts unless the program's output first matches the reference answer. The Darwin (macOS) figures are allocation counts, not timings — counts don't care about load, which is why they could be taken on a busy machine. Cross-machine numbers are never merged: where the two venues disagree below, the disagreement is stated, not averaged. "Quiet box" means nothing else was running; "shared box" cells say so.

1. Two numbers that should not coexist: 1.056× and 161×

Hey is usually benchmarked against Go and Ruby on web serving and scripting, where it does well. This article is about the benchmark where it does worst. fannkuch-redux is a classic from the Computer Language Benchmarks Game: take a small array of integers, repeatedly reverse prefixes of it, count the flips. No I/O, no strings, no memory growth — just reads, writes, and compares against one tiny array, tens of millions of times. It is the purest measurement of one question a benchmark can ask: what does it cost this language to touch an element of a collection?

Here is the pair of measurements that frames everything else. On a registers-only integer recurrence — arithmetic that never touches an array — compiled Hey runs at 1.056× the speed of C: within 6%, close enough that nobody would bother optimizing it (linux box, value-representation research note, 2026-07-30). On fannkuch, the quiet-box figure is 161× of C (471a, same linux box).

The same compiler cannot be both "6% behind C" and "161× behind C" unless the two benchmarks are buying different things. They are. The recurrence spends its time on arithmetic, which Hey compiles to the same machine instructions C uses. fannkuch spends its time on array accesses — and in Hey today, every one of those is a function call into the runtime. The entire gap lives in that difference. The rest of this article is the receipts.

2. The honest ladder — including the correction that goes against us

First, the ladder itself, because an earlier version of it was wrong in Hey's favor and the correction is part of the record. The project had published that Hey ran "about 3× behind Ruby" on this benchmark. That cell was real, but it was measured against the macOS system Ruby — version 2.6, end-of-life, three major versions old — on a busy box. Re-measured on 2026-07-30 against current stable Ruby 4.0.6, same box, same session, lanes interleaved: the honest number is 12.93× behind Ruby. Nothing about Hey changed between the two cells. The bar we had published was artificially low, and modern Ruby is a much faster interpreter than the folklore says.

The corrected ladder (fannkuch-redux n=10, linux i7-1165G7, Hey at 473a, medians of 5, interleaved, oracle-checked; dated log 2026-07-30): C -O2 185.5 ms · Go 191.3 ms · Ruby 4.0.6 2,492 ms · Hey 32,215 ms — Hey/C 173.7× on this shared-box cell, 161× on the quiet-box 471a cell. Two side measurements from the same session sharpen the picture: Ruby's YJIT bought 1.0002× — nothing — on this shape, and its brand-new ZJIT made the workload 2.06× slower, so the Ruby column stays plain interpreter, its best mode here. This shape defeats JITs and interpreters alike for the same reason it exposes Hey: it is nothing but accesses.

One more disclosed cost riding on this ladder: a float-correctness landing (472a) made fannkuch +11.0% ± 1.4% slower (linux, interleaved A/B, C control flat) — correctness paid for with per-operation allocation, localized to the boxed-arithmetic change, corroborated by a matching rise in allocation counts. Every Hey cell in this article brackets its version for exactly this reason.

Why publish a correction that makes our own number four times worse? Because the whole argument that follows — the bill of materials, the fix, the miss, the plan — rests on measurement, and a measurement is only worth citing if it gets published whichever way it lands. Every future Ruby row prints its interpreter version.

3. What one array read buys: a function call and a 32-byte box

In C, a[j] compiles to one load instruction: base address plus offset, done. In compiled Hey today, the same expression compiles to a call into the runtime — a real C function, one per read, no exceptions. Neither of Hey's two code generators knows the memory layout of a runtime value; every collection access goes through the front door. Here is what that front door does on the hot path — an ordinary in-range integer read from an ordinary array (runtime source, trunk of the 474a era):

  • A range probe, first. Before the array case is even considered, a helper call checks whether the collection is a range like 1..10 — on every read, including the tens of millions where it never is.
  • Type dispatch and a two-sided bounds check. This part is legitimate and cheap; C skips it, but safe languages shouldn't.
  • A clone of the element. For an integer this is just a copy — but it unconditionally runs profiling-counter bookkeeping and a statistics hook on the way through.
  • A fresh 32-byte heap allocation. The element is returned inside a newly allocated transport box — a 32-byte tagged container (4-byte type tag plus a 24-byte value union, padded) whose only job is to carry the value back to the caller.
  • An unboxing call. The caller, which usually wanted a plain 64-bit integer all along, calls another helper to take the value back out of the box — and should then free the box.

Allocating a fresh box to read a number you are about to immediately unwrap is paying for gift-wrap on something you open in the same aisle. And the "should then free" is not rhetorical: one of the project's own pinned code-generator outputs shows 6 read calls but only 5 release calls — the free is not always emitted, which becomes measurable in section 5.

Writes are worse. The measured budget of record is ~38 ns per element store (linux, -O2-corrected cell, 2026-07-30), and counting — not profiling, counting — showed each store performs two of those 32-byte box allocations: one to carry the value in, one inside the store machinery itself. Two mallocs and two frees, per element, per store, in a benchmark that stores elements tens of millions of times. Meanwhile the fannkuch inner loop's arithmetic compiles inline: a census of the compiled loop body (linux, measured) counts 9 element-read calls, 5 unboxing calls, 8 boxing calls, and zero arithmetic helper calls. The math is already free. The touching is not.

4. The fix that worked — and the prediction it killed

The obvious first fix: fuse the swap. fannkuch's hottest write is set a = put(a, dst, a[src]) — read an element, store it elsewhere. A fused runtime helper does the read half and the store half in one call, so the transport box that only existed to carry the value between the two calls is never allocated at all. That fix is built and branch-ready (linux, 2026-07-30), and its receipt is exact: allocations per store went from 2.000 to 1.000 — not roughly, exactly, by count — and the store path got 22.7% faster.

Here is the part that makes this article worth writing. Before that fix ran, the team wrote down what the result would mean either way — pre-registration, borrowed from clinical trials. The registered prediction: if allocation is the whole story, removing one of two allocation pairs should roughly halve the per-store budget. The registered contingency: if it does not halve, allocation is not the whole cost — stop and re-decompose before building the next allocation fix.

It did not halve. The prediction was scored a MISS — removing the pair bought ~9 ns, not the ~19 the halving story required — and the miss re-priced the story. One malloc/free pair of this size costs ~9 ns on that box. Two pairs, if the second costs the same (an assumption, flagged below), account for ~18 ns of the ~38. The remaining ~20 ns is everything else in section 3's list: the call itself, the range probe, the dispatch, the clone bookkeeping. Allocation is about half the tax. The function call is the other half.

Why did the whole benchmark barely move when the fusion fix ran (about −0.7% on fannkuch, linux)? Because after earlier store work, fannkuch's time is dominated by exactly the accesses the fusion does not cover: the flip-count loop's compares, the probe reads, the reads feeding arithmetic — the census from section 3. The fusion fix is a real 22.7% on the path it covers. The story's center of gravity just isn't on that path. It's on the call.

5. Counting on a second machine: an exact 1.000 — and a leak

Before building the next fix, the project priced the problem on a second venue — a Darwin (macOS) box — using pure allocation counts, which don't care whether the machine is busy. Three one-line shapes, one million iterations each, a 64-element integer array, Hey 474a, script lane, counters on via HEY_ALLOC_STATS=1. The probe ran twice; the counts were identical to the digit.

Three findings travel with their conditions. First, the bare read's cost is exactly one 32-byte box — 1.000, not 1.02 — which gives the coming fix a beautifully falsifiable target: 0.000. Second, the compare shape leaks both of its boxes: two allocations, zero frees, 64 bytes gone per iteration, on this venue — the missing-release defect from section 3's pinned output, now measured. fannkuch's innermost test, "is this element bigger than that one," is exactly this shape. The linux box independently found a member of the same leak family on arithmetic shapes with a completely different instrument (a malloc-interposing library, compiled lane); different venue, different instrument, both stated here, deliberately not merged. Third, read-plus-add costs three boxes on this venue where linux's instrument reports one allocation and zero frees for the same spelling — a cross-venue divergence that is flagged, not reconciled. The honest sentence is "we measured different things on different machines and wrote both down."

Sidebar: the instrument that reads zero

The allocation counters that produced the table above are compiled in but gated: without HEY_ALLOC_STATS=1 in the environment, every counter reads zero. A counter that reports zero allocations is either very good news or a counter that isn't plugged in, and the two feel identical right up until you publish. The probe therefore carries a blindness arm: shapes that are known to allocate (string building, array append) run alongside as a positive control — if they ever read zero, the instrument is blind and the whole cell is discarded, the mirror image of a negative control. Both arms are archived with the cell. An instrument is trusted only after it has been seen reading both something and nothing, for known reasons.

6. The lever every fast language pulled: inline the access

None of this is a novel disease, and the cure has a long literature — surveyed at length in this site's companion piece, "Boxed Values and Fast Languages," so here is just the shape of it. Every dynamic language that got fast at array code did it by making the common-case element access stop being a call into a general-purpose runtime function. PyPy's storage strategies (Bolz, Diekmann, Tratt — OOPSLA 2013) keep a list of integers as a flat machine-integer array and specialize the access to a direct load. V8 tracks "elements kinds" per array so a JavaScript array of small integers reads with a raw indexed load, no boxing anywhere. Julia's isbits layout rules (Bezanson, Edelman, Karpinski, Shah — SIAM Review 2017) make an Array{Int64} literally a block of integers, accessed like C's.

The project's own value-representation research note (linux, 2026-07-30) ranks this lever first and calls the shim-call barrier "the term they never pay" — the one cost in Hey's access bill with no counterpart in any of the fast systems above, and the one C never pays either, because C's access is the load. It is also, unusually for a rank-one lever, low-risk in Hey's case: reads don't mutate anything, so the change is neutral to the language's immutability guarantees, and it needs no speculative guards and no deoptimization machinery of the kind JITs pay for — the type knowledge it relies on is already computed by the compiler for other purposes.

7. The punchline for Hey: two steps, and the gate the first one must pass

Status, stated plainly: what follows is designed and priced, not built. The measurements above are real; the fix is a plan with published predictions, and this article ends on the gate, not on results that don't exist yet.

Step one: a read helper that returns the bare integer. Today's read helper always returns a freshly allocated box. The designed change adds a sibling that returns the raw 64-bit integer directly — no box, no unboxing call, no clone bookkeeping — and the compiler emits it only where it can already prove the consumer wants an integer (a compare, arithmetic, an integer binding), using type knowledge both code generators already maintain. There is precedent in the tree: the string-keyed lookup already has exactly such an unboxed twin; the array-indexed lookup simply never got one. Per covered read this deletes the 32-byte allocation and free, the unboxing call, and the clone preamble — and where no box is ever allocated, section 5's compare-shape leak has nothing left to leak. What it keeps: one call, the range probe, the type dispatch.

Step two — maybe: the true inline. Emit the type guard, the bounds check, and the direct element load as machine code at the call site, with the general helper kept as the slow path. That is C's price, and it is what "the term they never pay" ultimately means. It is also a bigger bet: it requires teaching both code generators the memory layout of a runtime value, which today neither knows — there is no precedent for it in the tree. Whether step two is worth building is precisely what step one's measurement decides: step one removes the box while keeping the call, so the difference it measures is the price of the box, and what remains is the price of the call.

And that measurement is already committed to, in writing, before any code. The pricing protocol is pre-registered, and it runs a measurement-only prototype (a hand-patched probe, the same method that priced the fusion fix) before the compiler change is built:

  • Prediction 1: allocations per covered read go from exactly 1.000 to exactly 0.000, flat across array sizes.
  • Prediction 2: the timing delta between the stock and patched versions is the Darwin price of box-plus-unbox-plus-bookkeeping per read. No magnitude is predicted — this cell exists to produce that number, and the linux ~9 ns pair cost is not assumed to transfer across operating systems.
  • Prediction 3: both versions stay flat as the array grows (8, 64, 512 elements) — size-independence preserved.
  • Prediction 4: whole-benchmark movement on fannkuch is measured when the compiler change lands, never projected from the prototype — the same house rule that already caught one optimistic projection this week.
  • The registered contingency: if Prediction 1 holds but the timing delta is small, then dispatch and call overhead dominate even without the box — step one alone is not the fix, step two rises, and the budget gets re-decomposed before either is built. This is the same contingency structure that scored the fusion fix's MISS, doing its job a second time.
  • The falsification arm: deliberately patch the wrong call site (a string-keyed read) — the output-checking oracle must break; and turning the change off must restore the binary byte-for-byte. A gate is trusted only after it has been seen returning both verdicts.

That is where this story ends today: not with a benchmark bar shrinking, but with the predictions that will judge the attempt already published, misses scored at the same volume as hits, and the one number that decides everything — what the call itself costs once the box is gone — queued to be measured rather than guessed. The last fix's prediction died in public and left behind a better map. This one was written down first on purpose.

Glossary

boxed value / transport box
A value wrapped in a heap-allocated tagged container (in Hey, 32 bytes: type tag plus value union) so generic runtime code can handle any type through one shape. "Unboxing" is taking the raw value back out.
malloc / free
The C runtime's heap allocation and deallocation calls. "Two mallocs per store" means two heap allocations happen for every element written.
ms / ns
Milliseconds (thousandths of a second) and nanoseconds (billionths). A modern CPU core executes a few instructions per nanosecond, which is why a ~38 ns store is expensive: it is roughly a hundred instruction-times for what C does in one.
interleaved (runs)
Alternating the competing programs rep by rep (A, B, C, A, B, C…) instead of running each in a block, so slow drift in the machine's state hits all lanes equally.
median of 5
Run five times, report the middle value — robust against a single unlucky rep.
oracle-checked
The program's output is compared against a known-correct reference answer before its timing is allowed to count. Fast and wrong scores zero.
quiet box
A machine verified to be running nothing else during the measurement. Cells from a shared (busy) box say so explicitly.
lane
How the program was executed: the script lane runs via the toolchain driver; the compiled lane runs a standalone built binary. Numbers name their lane because the two differ.
positive control
A case that must produce a non-zero reading if the instrument works at all — run alongside the real measurement so "zero" can be distinguished from "blind."
pre-registration
Publishing a prediction, and the result that would prove it wrong, before running the experiment — so the outcome is judgeable either way. See the shared glossary.
residual (by subtraction)
The part of a measured total left over after the directly measured parts are subtracted. It inherits the uncertainty of every assumption in the subtraction — which is why this article flags the ~20 ns as such.
