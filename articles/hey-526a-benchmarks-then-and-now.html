Hey 526a: Every Benchmark, Then and Now

Every benchmark the project keeps, re-run on one Linux laptop against the shipped 526a compiler, and set beside the earliest number on record for the same test. One clear win, one steady class-result, and one honest regression — each with its conditions attached.

TL;DR

  • Web throughput is the headline win. On the documented Hey server (Web.text/Web.json helpers), plain-text throughput went from 23,823 rps at 475a to 323,931 rps at 526a on the same box — about 13.6×. Hey now leads Go (227k) and Ruby/Puma (77k) on this laptop, where in the earliest run only a hand-inlined workaround was fast.
  • The numeric array matrix holds C's class. Across eight shared workloads, Hey ties C on streaming (sum, search — 0.99–1.00×), lands 1.4–1.8× C on the array shapes, is 3.6× C on fannkuch, and runs 11–29× past Ruby on every numeric shape. The two string workloads that used to time out now finish (~2.24 s).
  • 1BRC regressed, and it is reported straight. The earliest record (240a) had Hey’s single-core One Billion Row program at 405 ms for five million rows, 1.60× C. At 526a that same program no longer compiles on the shipping LLVM path (object-key map access is outside the supported subset); the one route that still builds it is >1000× slower than C. The web and array wins do not paper over this.
  • Provenance: Intel Core i7-1165G7 (4 cores / 8 threads), Linux 7.1.4, x86-64. Best-of-3, output verified byte-for-byte against C before timing, GOMAXPROCS/HEY_WORKERS pinned in every cell. These are Linux/x86 numbers; they are not comparable to the project’s macOS/arm figures — each box’s ratios are its own claim.

How to read this, and the one rule that governs it

Three benchmark families live in the tree: a compute matrix of eight small workloads across seven languages, a web-throughput harness, and the One Billion Row Challenge. Each is re-run here on a single quiet Linux laptop against the released 526a build, then placed next to the earliest number the project ever recorded for it. Where the earliest record is from the same machine, the comparison is a real before/after; where it is from a different machine or OS, that is said out loud and the absolute times are not compared — only the shape.

Absolute times do not travel across machines or operating systems. A Linux/x86 second is not a macOS/arm second. The web and 1BRC baselines below are from this same laptop, so their ratios are real; the compute matrix’s only earlier record is a macOS build, so that row compares shape, not seconds.

1 · Web throughput — the win

The web harness serves three routes — plain text, a small JSON body, and a JSON echo of request fields — and asserts every response byte-for-byte before a cell is measured. All lanes pin four workers; the load generator is wrk -t4 -c64. The Hey server here uses the documented Web.text and Web.json helpers — what a Hey user actually writes.

That last point is the whole story. In the earliest recorded sweep (475a, this same laptop), the documented helper path served ~24k rps while a hand-inlined map literal on the identical routes served ~314k — a 13× tax for writing idiomatic code. By 526a that tax is gone: the documented path itself serves 324k.

At 526a the JSON and params routes track the plain route (Hey 303,657 and 288,811 rps; Go 223k and 219k; Ruby 73k and 70k), so the ordering holds across all three: Hey > Go > Ruby. One caveat kept honest: box load reached ~9 by the end of the Hey lane on this passively-cooled laptop, so the Go and Ruby lanes ran slightly warmer — read these as ±a few percent, not to the digit. The 13× helper-path result is far outside that band; the Go/Ruby deltas are inside it.

2 · Compute matrix — C’s class held

Eight workloads, the same deterministic algorithm in each language, one line of output checked byte-for-byte against C before any time counts. Sizes: 100 million elements for the streaming shapes, 50 million for the array shapes, 10 million strings, and fannkuch-redux at n = 11. Hey uses ordinary subscripts and put — no special fast-path API.

Then vs now. The only earlier record for these exact workloads is the pre-array-rewrite Hey build, measured on a macOS/arm machine, where transform and fannkuch ran past a 120-second timeout and the two string rows did not finish at all. Absolute seconds do not cross that OS boundary, but the shape change reproduces here: on Linux at 526a, every workload finishes, including the two spotlighted string rows that used to be DNF. They now complete in ~2.24 s with a linear memory profile — the O(n²) boxed-string-append wall named in the earlier write-up has moved. The constant factor is still there: Hey finishes the string shapes at ~4.3× C and a hair behind Ruby, a real loss, now on time rather than as a non-finish.

Everywhere the element is a flat machine number, Hey sits where the earlier story put it: tied with C on the two streaming shapes, within ~1.8× on the array shapes, an honest 3.6× on fannkuch (and behind Go there), and 11–29× ahead of Ruby throughout. Erlang (OTP 29) sits with the dynamic languages: 3.3 s on the streaming shapes, 12 s on histogram, 33.6 s on fannkuch — but it wins the two string shapes outright at 1.76 s and 1.88 s, ahead of every runtime here including Hey.

3 · 1BRC — the regression, reported straight

The One Billion Row Challenge parses station;temperature lines into a per-station min/mean/max table. The project’s earliest record (240a) put Hey’s single-core program at 405 ms best for five million rows against a C reference’s 253 ms — a 1.60× ratio, produced through the optimized LLVM pipeline. That is the number to beat.

At 526a, the maintained 1BRC program does not build on the shipping path. Three routes, three outcomes on this box:
  • Default LLVM backend (heyc build): fails. The emitter’s supported subset cannot lower object-key map access — current["count"], stats[station], get(current, "sum") — and the whole program falls back and then errors out (exit 70).
  • native-C self-host driver: fails to build the emitter itself — the generated C has an implicit-declaration / type-mismatch error (hey_fn_to_i), a compiler bug rather than a language-subset limit.
  • stage-0 bootstrap (heyc stage0-build): builds, but the binary is unusably slow — it does not finish even a one-million-row file in 60 seconds, where the C reference does the same file in 0.02 s. The bootstrap map path is not the optimized one.

So the fast route that produced 405 ms in 240a is exactly the route that no longer accepts this program, and the routes that remain either miscompile or run more than a thousand times slower than C. The C reference itself is healthy — 2.1 s best for a fifty-million-row prefix on this laptop — which is what makes the Hey side a clean regression rather than a measurement problem. This is the one benchmark where 526a is behind its own history, and it is named here as plainly as the wins.

What is not claimed

The compute matrix here runs seven languages — C, Rust, Go, Hey, Ruby, Python and Erlang (OTP 29). The web and 1BRC baselines are same-box before/afters and their ratios stand; the compute “then” is a different-OS build and only its shape is carried across. No number here is offered as a prediction for any other machine — they are measurements of these toolchains on this one laptop, on a passively-cooled part whose load and temperature are logged with every cell.

526a nets out ahead: a ~13.6× jump on the documented web server that puts Hey in front of Go and Ruby, and an array/numeric matrix that reaches C’s class and finishes every shape. The exception is 1BRC, which regressed to not-building on the shipping path — the next thing to fix, stated as loudly as the wins.
