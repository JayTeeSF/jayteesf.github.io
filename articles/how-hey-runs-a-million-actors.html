How Hey Runs a Million Actors

Is there one actor per thread? No. Hey parks millions of actors in memory and runs whichever ones have mail on one worker thread per CPU core. This article shows how that works in pictures, what happens when one actor fails while sharing a thread with thousands of others, and what Hey is taking from Erlang, Go, Pony, Swift and Tokio.

Short version

  • Many actors per thread. A compiled Hey actor is a small record (its state plus a mailbox) with no stack and no thread of its own. One worker thread per core runs whichever actors have mail. A million idle actors take about 137 MB and use no CPU.
  • The new scheduler measures with Go. Copying Go's design took ping-pong from 3.5–4.7 µs to 110 ns per message, and throughput now grows with cores instead of falling. It is measured on a branch and has not shipped yet.
  • Failure belongs to the actor, not the thread. Hey fails fast, like Erlang: an error stops that actor's turn, and the thread moves straight on to the next actor. Error state has to live with the actor, because thousands of actors share each thread.
  • Next: a memory region per actor. When an actor dies, its whole memory region should be freed at once, the way Erlang frees a process heap. Regions already cut about a third of the instructions from a record-heavy benchmark.

1. One thread per actor, or many actors per thread?

The obvious way to build actors is to give each one an operating-system thread. That works for a few hundred actors. It fails at a million, because every thread reserves a stack (typically 512 KB to 8 MB of address space) and the kernel has to schedule all of them.

Hey's compiled actors use the other model, usually called M:N: M actors share N threads, with N equal to the number of cores. An idle actor is just data. When a message arrives, a worker thread picks the actor up, runs its handler to completion, and puts it down again.

2. How the worker threads share the work

Many actors per thread only pays off if the threads don't fight over the work. Until this month they did: Hey's old scheduler had one global lock that every message went through. Adding cores made it slower, because the threads spent their time waiting for each other.

The new scheduler copies the design that Go has refined since 2012. Each core keeps its own queue, and there is no global lock on the path a message takes.

3. When an actor fails, who else gets hurt?

Hey follows Erlang's rule: fail fast, keep the failure isolated, restart. A run-time error, such as a failed JSON parse or an explicit fail, stops the current unit of work right there. There is no try/catch to thread errors through the program. The unit's supervisor, the server or the job runner, decides what happens next: answer 500, mark the job failed, or restart the actor.

Sharing threads adds a twist. If the record that says "an error happened" belonged to the thread, the failed actor's error would leak onto the next actor that thread runs. So the error has to belong to the actor's turn:

Stopping at once, without slowing the normal path

Today a Hey handler that hits an error keeps running, using nil for the failed value. The response is 500, but the handler's side effects still happen. The fix being built now makes the handler stop where the error happened. The Maintainer's condition was that this must not turn into a heavyweight exception system that slows every program down. The design meets it this way:

  • The compiler's middle stage (MIR, the step that already decides who owns each value) marks which calls can fail. Most can't: arithmetic on known integers, field reads on known records, and so on.
  • After a call that can fail, the compiled code makes one cheap, predictable check: "did that fail?" If yes, it jumps to the function's normal clean-up exit. Owned values are released exactly as on a normal return, so nothing leaks.
  • The caller does the same, all the way up to the unit's boundary. There, the request answers 500, or the actor stops and its supervisor is told.

A call that cannot fail pays nothing. A call that can fail pays one branch the CPU almost always predicts correctly. Status: in progress.

4. Problems that can reach many actors at once

A failing handler is the easy case. The hard cases are the ones where something goes wrong in a way the thread itself feels:

ProblemWhat happens in Hey todayBest known fixWho does it that way
A handler loops forever or computes for a long time Hurts others. It keeps its worker thread, and the actors queued behind it on that core wait (other workers can steal some of them). Preemption. The compiler adds a cheap "time's up?" check at the top of every loop. When a turn runs out of budget, the actor yields its place. Erlang counts "reductions" (units of work) and switches process after a budget; Go interrupts long-running goroutines with a timer signal
A handler sleeps Handled on the new scheduler: the sleeping actor's core passes to a spare thread (up to 512). Better: the actor parks, with no thread at all, until a timer wakes it. Erlang, Go, Tokio all park rather than block
A handler blocks on slow I/O Not yet covered: it holds a worker thread. Non-blocking I/O: the actor parks, and an event loop wakes it when the data arrives. Go's network poller, Tokio, Erlang's I/O ports
A hard crash (memory corruption, out of memory) Kills the whole process, and every actor with it. Make it impossible: memory safety proved by the compiler. Contain it: a memory limit per actor. Recover: an operating-system supervisor (such as systemd) restarts the process. Erlang has the same limit for native code; Pony and Rust prevent it at compile time
Two actors touch the same data Prevented. A message is copied on send, so actors never share anything they can change. Keep the safety, lose the copy: when the compiler proves the sender will not use a value again, move it instead of copying it. Pony (reference capabilities), Swift (Sendable checks), Rust (ownership)

6. Regions: an actor's memory, freed in one step

Erlang has a trick that makes failure cheap. Each process allocates from its own private heap, so when a process dies, nothing has to be walked or counted: the whole heap goes back at once.

Hey already has the building block. A region is a group of allocations that share one lifetime, allocated side by side and freed together. Since October 3, MIR has proved where a temporary graph of records, such as decoded JSON, is built, only read, and then dropped. That graph goes into a region, and the region is freed in one step instead of one object at a time.

What regions did already

−35%

instructions on a record-heavy benchmark (34.2 billion → 22.3 billion), same output, same peak memory, once MIR put temporary record graphs in regions.

Why it fits actors

An actor's state and the values built during one turn have obvious lifetimes: "until the turn ends" and "until the actor dies". Those are exactly what a region needs.

Bonus

Allocation is the single largest cost in Hey's own compiler right now (about a third of its CPU, measured October 9). Regions attack the same cost from the other side.

The background on regions, and why they work together with flat records rather than competing with them, is in Flat Records or Regions?.

7. The order of work

  1. Land the new scheduler. Message throughput about 30 times higher, and it grows with cores instead of shrinking. measured on a branch, not shipped queued after the Elders release
  2. Fail fast, per unit of work. An error stops the turn at once, and the error lives with the request, job or actor, never the thread. in progress
  3. Run supervise on the worker pool. Today every supervised actor gets an OS thread. On the pool, a million supervised actors need no more threads than one does. queued after the Elders release
  4. A region per actor and per turn. Values built during a turn are freed in one step when the turn ends; the actor's state is freed in one step when it dies. queued
  5. Move, don't copy, when the compiler proves it is safe. This closes the remaining gap with Go when many senders feed one actor (5 million messages per second versus Go's 20 million). proposed
  6. Preemption checks at the top of loops, so one busy actor cannot hold up the others on its core. proposed

Glossary

actor
An independently scheduled unit with private state that communicates only by sending messages.
M:N scheduling
Running M lightweight tasks (here, actors) on N operating-system threads, with N usually equal to the number of cores.
turn
One visit by a worker thread to an actor, during which the actor handles up to 64 messages from its mailbox.
run to completion
A handler finishes its current message before the worker moves on. Between turns, an actor needs no stack.
work stealing
An idle worker takes half of a busy worker's queue, so no core sits idle while another has a backlog.
parking
A worker (or an actor) going to sleep without using CPU until something wakes it.
preemption
Taking the core away from a task that has run too long, so others get a turn.
fail fast
Stopping the current unit of work at the first error, instead of carrying on with a placeholder value.
supervisor
An actor or runtime component that is told when another actor fails and decides whether to restart it.
MIR
Hey's mid-level compiler representation. It decides who owns each value, when it is released, and (now) which calls can fail.
region
A group of allocations with one shared lifetime, allocated together and freed together in a single step.
