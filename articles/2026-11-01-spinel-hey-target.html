Fast Ruby Binaries for Any Platform

You wrote a Ruby script. It works. Now you want it to be fast, and to hand someone a single file that runs on their Linux server, without asking them to install Ruby. This page describes a compiler that does exactly that, and what happens inside it.

After reading this you can

  • picture the one command you'd run, and what you'd get back;
  • predict whether your Ruby program will compile in the first version;
  • say how your threads and queues will run;
  • explain why the compiler leans on Matz's Spinel instead of reading Ruby's own syntax tree;
  • weigh in on the open decisions.

Short version

  • One command: hey-spinel app.rb writes ./app, a native program. No Ruby, no C compiler, nothing else to install. (hey-spinel is a working name.)
  • Your machine first, any platform next: --target linux-arm64 arrives when Hey's cross-compiler lands (release v608).
  • Inside: Spinel, Matz's Ruby compiler, works out every type. The program is translated to Hey, and Hey builds the binary. You never see the Hey.
  • Speed target: at least 5x faster than the Ruby interpreter in the first version. That's a target; nothing has been measured yet.
  • The promise: every program Spinel compiles, this compiles too, with the same output. That is the bar for version 1, checked on Spinel's own test and benchmark suites.
  • Cost: about 93–186 engineer-weeks for that first version, plus 9–18 in Hey (estimates). Most of it is Ruby's core library, about 1,450 methods, rewritten in Hey.

What you'll type

$ hey-spinel fib.rb
$ ./fib
5702887

$ hey-spinel fib.rb --target linux-arm64 -o fib-linux   # after Hey v608
$ scp fib-linux server:   # one file, runs there, no Ruby needed

That's the whole interface: -o, -E (compile and run), -I, --check (just tell me what won't compile), --release and --target.

What happens inside, in five steps

Spinel normally prints C and runs a C compiler. Here we only ask it what it learned. It already exports that as JSON (--emit-types): the type of every expression, which method each call reaches, and which blocks it can turn into plain loops. We use Spinel exactly as Matz publishes it, with no changes.

Your Ruby, and what it becomes

You write

class Counter
  def initialize
    @n = 0
  end

  def add(k)
    @n += k
    self
  end

  def n = @n
end

c = Counter.new
[1, 2, 3].each { |v| c.add(v) }
puts c.n

The tool writes (you never see it; sketch)

fn Counter__new()
  return {cls: CLS_Counter, n: 0}
end

fn Counter__add(self, k)
  return {...self, n: self.n + k}
end

fn Counter__n(self)
  return self.n
end

program
  let c = Counter__new()
  for v in [1, 2, 3]
    set c = Counter__add(c, v)
  end
  Rb.puts(Counter__n(c))
end
  • The method call is direct. Spinel proved c.add can only mean Counter#add.
  • The block is a plain loop. Spinel proved it can be inlined.
  • Integers never overflow wrongly. Hey grows an Int into a big integer, just like Ruby, and keeps the plain fast path where it can prove the value fits.
  • The object is a plain value. Only one name ever holds c, so "change it" can become "make the changed one and rebind the name", and Hey does that in place. The compiler proves this for each kind of object; about 80% of the classes in Spinel's benchmarks qualify (an estimate from a scan).
  • Only objects that are shared and changed, such as tree nodes with parent pointers, go into a Cell from Hey's standard library, the one mutable box Hey offers.

"Why not just read Ruby's own syntax tree?"

Ruby will hand you its syntax tree (Prism, RubyVM::AbstractSyntaxTree). And Hey infers types by itself. So why bring Spinel in?

Because Hey's inference knows about numbers, strings and arrays of integers. It doesn't know about Ruby objects. Translated without Spinel, every object looks the same to Hey. Then every method call needs a lookup at run time, every instance variable is a boxed value, and every block becomes a closure.

The estimate: you'd save 0–4 weeks of building, and object-heavy programs would run 3–10x slower. So the compiler uses Spinel, and keeps a "no Spinel" mode only for testing.

Will my program compile?

Works

Everyday Ruby

Classes, modules, mixins, super, Struct, blocks, procs, lambdas, Integer (any size), Float, String, Symbol, Array, Hash, Range, Regexp, File, ARGV, ENV.

Works

rescue, ensure, retry

Raise and rescue as usual. An uncaught exception prints Class: message; Ruby's exact message and exit status 1 come in version 2.

Works

Common thread patterns

Thread.new { }.join, .value, Queue, SizedQueue, Mutex#synchronize, Fiber and Enumerator as generators. See below.

Refused, with a message

What Spinel refuses

eval of a string, method_missing, send or define_method with a computed name, ObjectSpace, binding.

The one exception

Your own C code

Gems or packages that bring their own .c files need a C compiler, which this tool promises you won't need. Spinel's own bundled packages are ported, so they work.

Everything else Spinel compiles, this compiles. Not sure? hey-spinel --check app.rb lists every line it would refuse, and why.

How your threads run

Hey runs work as actors: small, isolated workers that share nothing and talk by messages, and that run in parallel across your cores. Each Ruby thread or fiber becomes one. Your objects never do: an object is a value, or a value in a Cell.

Threads that share nothing, or share only through a Queue or a Mutex, run in parallel. Threads that share a changed object (Ruby allows it; it's a data race) are put in one group that Hey runs one at a time, like Ruby's own global lock. Your program still works; that group just doesn't run in parallel.

How we'll know it's right

Every test program runs three ways: under Ruby, as Spinel's C binary, and through this compiler. The outputs must match exactly. The corpus starts with Spinel's own benchmarks and its thousands of feature tests, which already carry Ruby's expected output, plus hand-written thread tests, each run 20 times.

Open decisions

Decided

Values first, then a public Cell

Hey's compiler warns on every Cell: you're writing shared mutable code, here's the value-based rewrite, and you lose parallelism. The warning is off only in files this tool generates.

Recommended: yes

A small private Spinel patch

About 100–300 added lines that print what Spinel already worked out. That saves re-creating its 30,000-line desugarer.

Recommended: accept for v1

Cyclic object graphs leak

A cycle of objects is freed only at exit in v1. A collector that scans only the cells comes in v2.

Recommended: pick before going public

The name

hey-spinel is a working name. The public one shouldn't borrow "Spinel" alone, which is Matz's project.

Recommended: tarball now, gems later

How it's installed

One private repository, a download per platform; platform gems for gem install when it's public.

Why some objects need a Cell at all

Two shared, changing objects, such as a tree node and its parent, can't be plain values: a change made through one name has to show up through the other. Plain Hey can't express that cheaply. Building the box out of an actor would cost a message round trip per field read (about 50–200x slower), which is why the design rejects that. Passing one immutable heap through every function copies the whole heap the moment anything shares it, and never frees memory. So Hey's standard library gets one small, honest box, stdlib:Cell, with a warning that tells hand-written code how to avoid it.

How Spinel is shipped

We build Spinel's compiler from its release archive on each platform we support, at our release time, and put the binary in the download, with its MIT license. It runs on your machine; the target you choose doesn't change it. Its C output is never compiled.

Got a Rails app? There's a shorter road

Spinel compiles plain Ruby. A Rails app is mostly metaprogramming, so on its own Spinel refuses it. Sam Ruby's roundhouse solves that: it works out what your Rails app means at build time and writes the same app as a standalone project in Rust, Go, Crystal, Elixir and six more languages. It checks each one against live Rails, page by page. 37signals' Campfire already runs this way, compiled by Spinel.

  • The plan: add a Hey target to roundhouse, modelled on its Elixir target, which already turns Rails' changing objects into values passed along, the way Hey wants them.
  • The proof: roundhouse's own check, same URL against Rails, first on its blog app, then Lobsters, then Campfire.
  • The cost: about 16–28 engineer-weeks to the blog, about 25–46 to Campfire (estimates). That's far less than the plain-Ruby road, which is why it starts first.
  • The speed goal: at least as fast as roundhouse's Go output (about 5,200 requests a second on its blog page, 10x stock Rails) in version 1; then Spinel's, then Crystal's. These are targets.
