Flat Records or Regions

On the binary-trees benchmark, Hey is beaten by Erlang, Ruby and Python. Two different fixes are available, from two different traditions. This is an argument that they are not alternatives, and that picking only one leaves most of the gap on the table.

TL;DR

  • The measurement. w11 bintrees: Hey 2.331 s against Erlang 0.163, Ruby 0.487, Python 0.956, C 0.217. We are 10.7× C and lose to three garbage-collected languages.
  • Erlang does not use actors here. The benchmark is one sequential process. Its advantage is representation and allocation, not concurrency.
  • Roughly half the gap is not ours to close. The Erlang program's leaf allocates nothing; ours allocates a node. We build about twice as many objects before any implementation difference. The benchmark sources are fixed.
  • Option A, flat records, attacks the cost per object: a two-field record should be two slots, not a hash table with string keys.
  • Option B, regions, attacks the cost per object's lifetime: a tree built and discarded inside one loop iteration should be one allocation and one free, not 2d+1.
  • They multiply. A is the larger and more tractable win and should go first. B is what finally beats Erlang rather than merely catching it.
  • One measurement decides the order, and we do not have it yet: the Perceus reuse rate on w11. If it is zero, our FBIP story is aspirational and B is urgent.

On w11 we are beaten by Erlang by 14×, Ruby by 4.8× and Python by 2.4×. A compiled language losing to three interpreted, garbage-collected ones on an allocation benchmark is a statement about allocation, not about compilation.

2. What Erlang is actually doing

The first question was whether Erlang wins here by using its process model. It does not. The entire program is sequential:

make(0) -> nil;
make(D) -> {make(D-1), make(D-1)}.
check(nil) -> 1;
check({L, R}) -> 1 + check(L) + check(R).

No processes, no messages, no scheduler. Matching Erlang's concurrency model would buy exactly nothing on this benchmark. Three other things are doing the work.

2.1 Flat positional tuples

{L, R} is a header word followed by two words, contiguous. No keys are stored anywhere. check({L, R}) destructures by pattern match, which compiles to two loads at constant offsets.

Ours is a hashed map. A record literal builds a HeyJsonObject, and n.left is a hash lookup on the string "left".

2.2 An immediate leaf — which deflates Erlang, but not C or Ruby

Erlang's make(0) returns the atom nil, which allocates nothing. Hey's make_tree(0) returns {left: nil, right: nil}, a real node.

A tree of depth d therefore costs Erlang about 2d−1 cells and costs us about 2d+1−1. We allocate roughly twice as many objects before any representation difference at all.

Corrected after measurement

This section first claimed the factor halves the whole gap. It doesn't. C's make mallocs unconditionally — d == 0 only selects field values — and Ruby's [] is a fresh Array at every level. Both build the same 14,985,902 nodes Hey does, so Hey÷C = 10.86× and Hey÷Ruby carry no discount at all. Only the Erlang and Python columns are deflated.

Ruby allocates exactly our object count and is still 4.6× faster. That's the cleanest comparison in the table and the one worth being accountable to. The benchmark sources stay untouchable; what changed is that there's no free half to subtract before judging a fix against C or Ruby.

What the measurement actually found

Three things in this article's original reasoning turned out to be wrong, and the real defect was none of them.

  • The reuse rate on w11 is 0.00% — zero reuses across 14,985,902 allocations. Not a broken implementation: Perceus pairs a torn-down cell with a same-size constructor in the same branch, and here make_tree allocates without destructuring while check_tree destructures without allocating. Neither does both, so reuse is correctly inapplicable. Finishing Perceus buys this benchmark nothing.
  • Hashing and keys were never the cost. The index threshold is 16, so a two-field record linear-scans with one strcmp, and keys are already free — three strdup calls in the entire run.
  • The real defect is a leak. Peak RSS 2.58 GB against C's 5.7 MB. A box minted for n.left == nil is never released on any path and pins every subtree, so essentially nothing is ever freed. 8 mallocs and 336 bytes per node, against C's 1 and 16.

Beating Erlang is not reachable by representation work. Erlang's 0.163 s beats the C reference at 0.2086 s, and a perfect flat unboxed refcounted node measures 0.2664 s — already slower. The honest target is to match C, about 1.3×, which beats Ruby and Python. A sampling profile puts the allocator at 63.6% and the user's own algorithm at 2.4%, which is the case for regions.

2.3 Bump allocation and a generational collector

On BEAM, allocating is a pointer increment into a per-process heap, and objects that die young cost almost nothing to collect. We call malloc per node and pay reference-count traffic on the way in and out.

This is precisely the cost that Perceus reference counting and FBIP exist to remove, and binary trees is the benchmark the Perceus paper itself uses. Which raises the question this document cannot yet answer, and which is the most important open item on the project:

What is our measured reuse rate on w11 today? If it is zero, the FBIP story is aspirational rather than real, and that is a larger finding than the hash table.

3. Option A — flat records

A record whose key set is known at compile time becomes a fixed-slot object: construction is one allocation of a known size with no keys written, and n.left is a load at a constant offset.

This is the mainstream answer. Erlang's tuples, Rust's structs, Mojo's structs, and OCaml's records all work this way. It is also what our own research concluded independently:

Every system that keeps data flat does it by declaration, not by analysis. Escape analysis is a cautionary tale: HotSpot's C2 rejects roughly 80% of candidates, and does not even do stack allocation — it does scalar replacement.

For

Largest single win available, and it applies to every record in every program, not just to trees. Well-understood, with four mature implementations to learn from. Composes with everything else we are building.

Against

Needs the shape published in the signature so it survives a call, which is the same machinery three other lanes are already building. Records whose shape is genuinely dynamic must keep the hashed representation, so we will carry both and must decide between them soundly.

The same defect, three times

This is not a new problem. It is the third instance of one pattern, and noticing that changes how it should be built.

All three are a value whose shape is statically known, represented as a dynamic container, and all three need the same thing: the fact published in the signature rather than re-derived at each site. They should share one representation-agreement pass, not grow three that drift apart.

4. Option B — regions

A region is ownership of a whole subgraph rather than of one value. You allocate into it by bumping a pointer, and you release the entire thing in one operation without touching the objects inside it.

Look at what w11's inner loop actually does:

set sum = sum + check_tree(make_tree(d))

The tree is created by one call, consumed by another, never stored, and dead at the end of the statement. Every node in it shares one lifetime. Under reference counting we still pay per node on the way out; under a region we pay once.

4.1 Why Verona specifically

Project Verona is a research language for concurrent ownership, and it is MIT licensed, which matters for us: it can be read and used directly, unlike the Apache-2.0 sources we are holding at arm's length behind a clean-room process.

Its useful idea is subtyping between an owning region root and a mutable view of it. Passing the owner where a view is expected is a coercion that does not consume the owner, and a view parameter lowers to a widened calling convention — payload plus a region token — which is defaulted on and removed by dead-code elimination where it is not needed. That is a flat, unboxed parameter with an ownership story attached, which is exactly the shape of two problems we already have open.

For

Attacks the cost that flat records leave behind. Turns 2d+1 frees into one. Answers our open question about when writing through a borrowed parameter is sound, which our stated Perceus foundation does not answer at all. MIT, so usable directly.

Against

Needs an inferred region, because we allow no type annotations in user source — and inference is the thing the escape-analysis literature warns about. Verona is explicitly a research project. The payoff is concentrated in allocation-heavy code; it does nothing for w12-style scalar work.

Why our Perceus foundation cannot answer this on its own

Two findings from the research, both of which cut against the assumption we have been working under.

Perceus is not silent on calling conventions — it makes a loud choice. Its technical report states that ownership of references is passed down into each function; every parameter is owned. What it is silent on is separate compilation, module interfaces and ABI.

Perceus has no mutably-borrowed parameter mode at all. Borrowed means read-only by construction, and in-place reuse comes only from owned arguments via a run-time reference-count test. The later FP² work did not remove that test; it added a static guarantee about the function body and kept the boundary check deliberately. Our MIR records a parameter as borrowed and we want to write through it. That combination has no answer in the foundation we say we follow.

There is also a piece of our own ancestry to reclaim: the borrowed calling convention appears in Counting Immutable Beans, the paper Perceus was built on, as an inferred per-parameter owned/borrowed signature. Perceus dropped it and Koka later re-added it as an annotation. So this is not a research gap. It is a part of the lineage that was left out.

5. They are not alternatives

The framing of the question was "A or B". The measurement says the honest answer is "A, then B", because they attack different multiplicands and therefore compose.

Flat records shrink each node and make field access a load. Regions then make the set of nodes nearly free to discard. Doing only the first still leaves us calling malloc and free a few million times; doing only the second leaves us bump-allocating hash tables.

6. What this means for the order of work

Flat records first. It is the larger and more tractable win, it benefits every program rather than one benchmark, and — the decisive practical point — the pass it needs is already being written. A whole-program representation-agreement fixpoint, fail-closed over all call sites, is under construction for flat integer buffers right now. The question a record asks it is the same question with a different payload.

Regions second, and scoped narrowly at first. The general problem is inferring region structure, which is hard and is where escape analysis historically disappoints. But the specific case in front of us is not general: a value constructed within one expression, consumed within the same statement, never stored and dead at the statement's end. That is a statement-scoped region, and the escape facts we already compute are close to sufficient for it. Start there; do not start with the general case.

Measure the reuse rate before committing to either ordering. If Perceus reuse is already firing on w11 and the remaining cost is genuinely the hash table, A alone may close most of the practical gap. If reuse is at zero on the canonical FBIP benchmark, then the allocation cost is fully exposed, B matters more than this document assumes, and we have a correctness-of-story problem worth naming plainly.

7. What would count as success

Not 14×. Subtract the leaf-allocation factor from §2.2 first, and judge against what remains. Concretely, the checks worth setting before any work starts:

  • w11 output stays byte-identical at 14985902, and matches the interpreter.
  • w1 and w3 stay at exactly 1.00×. They have no functions and must not move.
  • The corpus zero-fallback count stays at 0. A speed-up that pushes any program back onto the legacy path is a loss, whatever the benchmark says.
  • Records whose shape is not statically known keep working, on the hashed representation, and there is a test that proves the compiler chooses correctly between the two rather than guessing.

Glossary

Perceus
Precise reference counting with reuse, from the Koka line of work. Ownership is passed into each function; reference counts are inserted precisely rather than conservatively.
FBIP — Functional But In-Place
Writing in a functional style and having the compiler turn it into in-place updates when a value is provably unique. Reuse analysis is the mechanism; a constructor torn down and one of the same shape built in the same scope with a reference count of one reuses the memory.
Reuse rate
The fraction of allocations that reuse memory just released instead of calling the allocator. The number we do not yet have for w11.
Region
Ownership of a subgraph of objects rather than of a single value. Allocation inside is a pointer bump; release frees everything at once without visiting the objects.
Isolated subgraph
A set of objects reachable through exactly one entry point, with no references in from outside. The property a region needs, and the thing that must be proven or declared.
Representation-agreement pass
A whole-program analysis that decides, for every call site, whether caller and callee agree on a value's physical representation, and falls back to the boxed form if any site cannot prove it.
