Hey language design · explored, not yet shipped

Dot Syntax Without Objects

The nice-looking call can stay. The class system does not have to come with it.

Status: design direction adopted; generic import and receiver resolution are not in the shipping compiler. Four edge choices remain open.

TL;DR
  • Build it: account.deposit(25) can be a compile-time rewrite to deposit(account, 25).
  • The receiver is always argument one; every other argument stays in order.
  • Imports are lexical and inspectable. Runtime does not search for methods.
  • Weakness disclosed: callable map fields and imported receiver functions can claim the same dotted spelling; that precedence is not ruled yet.
  • Reproduce the reasoning from the linked Kotlin, C#, Rust, Elixir, Haskell, and Python language documentation.

The tempting syntax is not the dangerous part

When you see account.deposit(25), it is easy to assume the language must attach methods to an account object. It does not. C# extension methods are static methods that can be called with instance-looking syntax; the receiver is represented by the first parameter. Kotlin says explicitly that extensions do not add members to the extended class and are resolved statically.

account.deposit(25, 50, 100)
# resolver produces
deposit(account, 25, 50, 100)

That is Hey's rule. It keeps immutable values and module functions while giving a Ruby reader the left-to-right call shape they expect.

The real feature is lexical scope

The compiler needs to know which deposit the file adopted. Elixir's imports and aliases are lexical and can be narrowed with inclusion or exclusion lists. Haskell separates module exports from import restrictions and hiding. Those are better guides than a runtime method table.

import './bank_account.hey' exposing: [deposit]
let updated = account.deposit(25)

Hey resolves the import, records one binding identity, and warns when a nearer or later declaration shadows another. Ignore the warning and the lexical winner still wins—but runtime never repeats the contest.

Lexical means the answer comes from where the code is written: inner scopes beat outer ones, and the compiler can point to both declarations.

Public, private, visible, concealed

A module ends with an explicit exposes surface. Private helpers remain available inside that module but are not callable outside it, matching the public/private boundary documented by Elixir. An importing file may adopt exposures, rename them, narrow their supported forms, or conceals selected defaults.

import 'stdlib:RubyMath' as RM \
  exposing: [{div: ruby_div}] \
  conceals: [mod]

The exact alias-selector spelling above is still a choice, not a shipped promise. The important invariant is already fixed: module metadata tells both the compiler and Reflection.module(...) which public names and forms exist.

One collision still deserves a real decision

Hey already allows functions in maps and promises handlers.on_save(document). What if an imported receiver function named on_save is also visible?

Kotlin and C# generally favor a real member over an extension. Rust avoids the same ambiguity syntactically: its reference says value.name(...) is parsed as a method call, while a callable field must be written (value.name)(...). Hey could preserve callable fields, apply its normal latest-lexical-binding rule with a warning, or reject the ambiguous spelling. The docket shows what each choice does to actual code.

Dynamic loading is not a dynamic import list

A runtime array cannot decide which lexical names exist after compilation. Python makes the distinction clear: ordinary imports are language syntax, while programmatic loading uses importlib.import_module. Hey can later add a separate module-value loader. Reusable exposing lists, if adopted, must be compile-time manifests or generated source.

Discovery matters as much as spelling

A receiver form is only friendly when a reader can discover where it came from. That is why the design includes exposure metadata rather than treating dotted syntax as compiler folklore. Reflection.module('stdlib:RubyMath') must be able to report the public function name, its supported forms, its operator symbol when it has one, and its source location. Editor tooling can use the same record to complete after a dot, explain an override warning, or show the qualified call that avoids a conflict.

This also keeps built-ins honest. Instead of a secret list scattered through the parser and emitters, built-ins become the default outer exposure of stdlib:BuiltIns. A file can conceal one, shadow one with a visible warning, or import the module explicitly to compare behavior. The feature becomes inspectable language data rather than a set of exceptions that only the compiler remembers.

The payoff

You get code that reads naturally, stays immutable, and compiles to direct calls. Library authors publish one inspectable surface. Importers choose what enters scope. Warnings make overrides loud. The runtime stays out of the naming business.

The syntax looks object-oriented. The architecture remains functions, values, modules, and one resolver with an authoritative answer.
