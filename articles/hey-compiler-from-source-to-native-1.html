How the Hey compiler turns source into native code

Stages 1–8 unified native pipeline: works today <=4-scalar record unbox: decided, coming

Hey is written without type annotations, lifetime markers, or borrow syntax, yet compiles through a single eight-stage pipeline written in Hey into native machine code. This page states what each stage owns, how its internal representations and passes work, and what CPU, instruction-cache, memory, and safety benefits each architectural choice gives Hey programs.

Hey · Unannotated polymorphism, strings, borrowed record & loop scratch
fn add(a, b) => a + b   # called as add(1, 2), add(0.5, 1.5), add(1, 0.5)

fn score_line(line, prefix, weights)
  if Text.starts_with?(line, prefix)
    return clamp(weights.base + Text.byte_length(line), 0, 1000)
  end
  return 0
end

fn score_batch(lines, raw_tag, weights)
  let total = 0
  for line in lines
    let prefix = Text.trim(raw_tag) + ':'
    set total = total + score_line(line, prefix, weights)
  end
  return total
end

One pipeline, zero text IR, three measurable goals

Source text ends at tokenization (HeyTokens.hey). Every arrow after that passes typed, structured Hey nodes or static single assignment (SSA) graphs—never serialized expression strings or name-matching heuristics—down to the terminal LLVM encoder. Every internal stage decision serves three targets simultaneously:

  • C/Rust-grade throughput (ops/sec): Unboxed 64-bit scalars, two-register 16-byte German Strings (HeyStr atop SDS), direct linkonce_odr register workers, and bounded pointer sharing keep hot loops in registers and the Level-1 instruction cache (L1-I) warm.
  • Minimum retired CPU instructions: Range intervals prove when arbitrary-precision Int operations fit signed 64-bit hardware adds and multiplies; owner-scoped borrows read strings and records with zero atomic reference-count (RC) traffic.
  • Lowest total and flat 1x peak RAM: Short strings (<= 12 bytes) allocate zero heap bytes, Perceus reset/reuse updates unique cells in place without 2x memory spikes, and lexical scope arenas reclaim per-iteration scratch in one pointer reset.

Write a plain loop, get register SSA: why MIR-SSA beats boxed C shims

You write a seven-line loop to sum every byte in a buffer. You don't write a single type annotation, lifetime parameter, or unsafe block:

Hey · Summing every byte in a buffer
import 'stdlib:Bytes'

fn sum_bytes(data)
  let sum = 0
  let i = 0
  let n = len(data)
  while i < n
    set sum = sum + Bytes.at(data, i)
    set i = i + 1
  end
  return sum
end

program
  says sum_bytes(Bytes.from_text('Hey!', 'utf-8'))
end

What happens inside the CPU on each byte? If Hey handed Bytes.at and + across an opaque C object file (runtime.o) using 32-byte heap-boxed HeyValue structs, each byte would cost 40 to 90 instructions of tag checks, reference-count traffic, and pointer reloads. Instead, Hey lowers both your loop and stdlib/Bytes.hey into Static Single Assignment (SSA) form—where no virtual register is ever mutated twice. Every step defines a fresh numbered value (%sum_0, %sum_1, %i_1), and the loop header becomes a parameterized block (a phi join) that receives incoming register values from the entry edge and the loop back-edge.

What would you predict? If you move a standard library function out of C and rewrite it in pure Hey, does a tight caller loop get slower or faster? Check the two paths side by side—because an opaque C shim hides memory aliasing from LLVM, moving stdlib code into MIR-SSA -> LLVM SSA lets LLVM inline it straight into caller registers.

  • 63-bit register InlineInt & native bitwise lowering: Unbounded integers stay in a single CPU register up to ±4.61 × 1018 before touching heap BigInt storage, and & | ^ << >>, Bits.*64, and Binary.read_u64_le compile directly to hardware instructions.
  • Single-probe flat Map, zero-copy Bytes, and richer --warn-boxed: Map.increment and Map.update hash and probe once on flat specialized slots, Bytes.each_line and Bytes.parse_fixed_slice scan mapped files without copying strings, and hey check --warn-boxed flags multi-probe map loops and array boxing at exact file:line:col spans (Performance §7).

1 · Overview of the eight-stage pipeline

Every Hey compilation unit travels through one linear sequence of eight responsibilities. Earlier stages settle syntax, names, and language types; middle stages prove control-flow, numeric range, borrow, and escape facts; physical stages choose machine registers, specialize worker signatures, insert exact memory lifetimes, verify every invariant, and hand a finished plan to LLVM:

2 · Stages 1 & 2: Parse once, desugar post-parse, resolve numeric IDs

Hey separates concrete syntax from core compiler semantics at an explicit boundary right after parsing. In Stage 1 (works today), HeyTokens.hey lexes UTF-8 source once and HeySyntaxTree.hey builds a lossless Surface AST. Grammar rules never desugar expressions on the fly and never re-scan source strings.

In Stage 2 (works today), HeyFinalSyntaxNodes.hey and HeySelectorNormalize.hey rewrite surface shorthand—elsif chains, case/when arms, for loops, trailing blocks, says, collection receiver sugar, and functional record update—into a compact 67-kind Koka-style Core AST, carrying synthetic-node origin pointers back to Stage 1's exact spans. HeyNames.hey and HeyProgramResolution.hey then resolve every identifier, module import, and static receiver call to a sealed numeric pair (unit_id, node_id).

  • Why desugar after parsing instead of inside the lexer or grammar: Consider case subj with an arm when false or true. Splicing == tokens before parsing misgroups the arm as (subj == false) or true and evaluates an effectful subj once per arm. Parsing the full arm subtree first produces Or(false, true), binds let $s = subj once, and lowers the arm to Equal($s, Or(false, true))—preserving both operator precedence and single evaluation.
  • Why shrink to 67 Core AST kinds with numeric identities: Every downstream pass (HIR, SSA-MIR, range analysis, specialization, ownership) handles one small set of canonical constructs and keys facts by integer (unit_id, node_id) rather than string names—eliminating duplicate lowering paths and driving Hey's 60% faster self-compile target.
Inspect the lossless syntax tree yourself

The compiler's front end exposes structured records directly to Hey tools; serializing to JSON is only for external inspection:

Hey · Inspecting HeySyntaxTree structured nodes
import 'stdlib:HeyTokens'
import 'stdlib:HeySyntaxTree'

program
  let code = "program\n  let total = 2 + 3\n  says total\nend\n"
  let lexical = read_source_text_into_lexical_admission(code)
  let parsed = HeySyntaxTree.parse_unit_lexical_admission(lexical, 0)
  if !parsed.ok
    fail parsed.error
  end
  says json_canonical_text(parsed.value.tree)
end

The output is a structured syntax_tree containing an infix_expr node with sealed unit and node IDs—never raw expression text for later passes to re-parse.

3 · Pure-Hey standard library & ThinLTO OS PAL declarations

User-written Hey has no type annotations and no extern keyword: you write plain functions like fn score_line(line, prefix, weights), and the parser and resolver refuse extern anywhere outside Hey's internal built-in binding module (Note 3). In 0.99.610a, application and library logic—including Text, Bytes, Bits, Binary, Map, Json, Codec, Compress, Archive, Packages, Files, Path, Http, Web, and Jobs—is written in pure stdlib/*.hey, while C is trimmed to a thin Operating System Platform Abstraction Layer (PAL) linked as cached Link-Time Optimization (ThinLTO, -flto=thin) bitcode.

1 · Pure-Hey stdlib/*.hey

Codecs, formats, HTTP/Web routing, and collection operations compile through the exact same parser, resolver, HIR, and MIR-SSA passes as your own code—inlining straight into caller registers.

2 · Typed OS PAL declarations

Each thin OS PAL entry point carries one internal declaration stating semantic types (String, Int, Bool, Bytes), per-parameter borrow marks, and LLVM purity/range metadata (memory(...), nocapture, !range, !tbaa).

3 · Tiny compiler universe

Only operations polymorphic across unrelated containers (len, slice, get, Ranges.until) use built-in typing rules keyed by resolved numeric identity, never by function spelling.

Architectural benefit: Because Text.starts_with?(line, prefix) and Text.byte_length(line) compile with verified semantic return types (Bool, Int) and borrowed parameter marks, Stage 3 knows their return types immediately, Stage 7 passes line and prefix in registers with zero reference-count increments or decrements, and LLVM ThinLTO inlines across the OS PAL boundary without an opaque runtime.o wall.

4 · Stage 3: Tree HIR, monotone worklists & Layer 1 call-instance typing

HeyHir.hey (works today) lowers the Resolved Core AST into structured Tree HIR records carrying explicit lexical scope_ids and def-use links. HeyHirInference.hey then infers unannotated types over that dependency graph:

  1. Seed definitions once: Literals, constructors, and verified builtin declarations seed known language types (Int, Float, Bool, String, shaped records) onto their SSA/HIR definitions.
  2. Separate bottom from dynamic: An unvisited edge starts at bottom ("no path has contributed yet"), so joining bottom with Int yields Int. An unrestricted runtime input carries dynamic (Value), so joining dynamic with Int widens safely to Value without miscompiling polymorphic programs.
  3. Wake only affected consumers: When an operation's output type changes, a monotone worklist queues only direct def-use readers—eliminating whole-function map cloning and solving mutually recursive strongly connected components (SCCs) to a fixed point.
  4. Layer 1 demand-driven call-instance typing (works today): When a call site supplies concrete argument types—such as add(1, 2), add(0.5, 1.5), or add(1, 0.5)—HeyHirInference.hey records a typed call instance @t<unit>.<fn>#<TypeTuple> (add#Int,Int, add#Float,Float, add#Int,Float) without cloning AST or HIR trees.

Architectural benefit: Layer 1 resolves overloaded operators (i64 + i64 vs double + double vs mixed Int + Float widening to double) and static record field offsets per observed call tuple while keeping Hey 100% annotation-free. Unused parameters are excluded from the instance tuple so calls differing only in an ignored argument share a single instance.

5 · Stage 4: Sealed-block SSA-MIR & interval/escape facts

Tree HIR preserves structured control flow; Stage 4 (works today) turns that tree into an explicit control-flow graph of basic blocks in HeyIr.hey so path-sensitive value, numeric, and lifetime facts can be proven:

  • Braun sealed-block SSA without dominance frontiers: HeyMirLowering.hey and HeyMirSsa.hey implement Braun et al.'s algorithm directly over basic-block parameters and edge arguments. Unsealed loop headers install an incomplete join parameter to break cycles immediately, then seal once every predecessor edge is wired, folding trivial single-value joins in place. Whenever critical-edge splitting inserts a synthetic block, HeyIr.hey propagates the enclosing block_scopes chain so Stage 7's scope arenas never lose a lexical boundary.
  • Arbitrary-precision Int semantics at 64-bit hardware speed (i64 + 63-bit InlineInt): Knowing a variable has language type Int doesn't by itself make 9223372036854775807 + 1 legal as an unchecked 64-bit add—Hey integers are exact at arbitrary precision. HeyMirFacts.hey and HeyIntRanges.hey propagate exact [lo..hi] bounds (including [0..255] on Bytes.at and multi-branch joins) with monotone cyclic widening. Every operation whose inputs and result fit signed 64 bits (fits_i64?, such as clamp(..., 0, 1000) in score_line or native bitwise & | ^ << >>) compiles to plain 1-cycle i64 registers. When static bounds aren't proven, Hey carries a 63-bit Least Significant Bit (LSB)-tagged InlineInt directly in a CPU register up to ±4.61 × 1018 with zero heap allocation, promoting to heap BigInt only when a hardware overflow flag fires (walkthrough receipt).
  • Unified borrow and escape facts (F1–F4, works today): On the same SSA-MIR graph, HeyMirFacts.hey computes fresh return results (F1), whether a value escapes its lexical scope via return, heap store, closure capture, or actor send (F2), the innermost non-escaping statement/iteration/call region (F3), and dead-after-use uniqueness for in-place reuse (F4).

6 · Stages 5 & 6: Two-layer worker specialization & physical carriers

In an unannotated language, function boundaries are where naive compilers burn most of their instructions and heap allocations. If every call boxed its arguments into 32-byte HeyValue* cells—or into a single 64-bit word that cannot hold a 16-byte German String—every non-inlined call to score_line(line, prefix, weights) would allocate heap wrappers, copy borrowed string slices, and bounce atomic reference counts. Conversely, cloning a full function body in HIR for every distinct language type misses SSA-MIR's fits_i64? and borrow/consume facts while duplicating identical machine bodies across dozens of heap-pointer record types and thrashing the CPU's Level-1 instruction cache (L1-I).

Hey solves both halves by splitting specialization across two coordinated layers: Layer 1 types call tuples in HeyHirInference.hey, and Layer 2 (Stage 5) deduplicates and emits define linkonce_odr machine workers right between HeyMirFacts.hey and HeyMirPhysical.hey:

LLVM IR · Emitted on-demand linkonce_odr workers (0 boxed HeyValue* copies when all callers are typed)
; Observed static calls instantiate linkonce_odr workers; unused HeyValue* entry is omitted:
define linkonce_odr i64    @"hey_fn_add#i64,i64"(i64 %a, i64 %b)         ; add(1, 2)
define linkonce_odr double @"hey_fn_add#f64,f64"(double %a, double %b)   ; add(0.5, 1.5)
define linkonce_odr double @"hey_fn_add#i64,f64"(i64 %a, double %b)      ; add(1, 0.5)
define linkonce_odr i64    @"hey_fn_score_line#str_b,str_b,i64"(
  { i64, i64 } %line, { i64, i64 } %prefix, i64 %weights_base)           ; 0B heap, 0 RC

Measurement & model basis: The 32-byte HeyValue cell, 16-byte HeyStr, 408-byte dynamic 4-field record allocation cost, and the 19x Perceus reuse prototype speedup (0.219 s vs 4.239 s) are measured in the repository; per-call instruction counts on non-inlined score_line follow the AArch64/x86-64 ABI instruction model across 10 million lines.

How the bounded worker key keeps L1-I hot and compile time linear

Between HeyMirFacts.hey and HeyMirPhysical.hey, Stage 5 maps each observed call instance onto a canonical physical worker key:

  • 1-to-1 register workers for scalars, strings, and small scalar structs: Proven i64 integers, f64 floats, i1 booleans, countable range_i64 triples, and two-register 16-byte HeyStr values (distinguishing zero-RC borrow from consume) pass straight in CPU registers (works today); unboxed register passing for flat user records of up to 4 scalar fields is decided, coming.
  • N-to-1 pointer sharing for heap aggregates (Go GC-shape principle): Every List, Map, large or nested record, BigInt, and callable travels as a pointer to a HeyValue cell. Stage 5 collapses all heap pointer shapes with the same ownership mode into one shared (borrow HeyValue*) or (own HeyValue*) worker—so 50 record types share one compiled machine body instead of bloating binary size and evicting L1-I cache lines.
  • Hard caps and zero-overhead static calls: Each function caps specialization at <= 8 workers and recursive specialization depth at <= 4 (recording a specialisation_fallback diagnostic counter if exceeded), deduplicates identical workers across compilation units with define linkonce_odr, and emits zero boxed HeyValue* entry wrappers whenever all callers are statically typed.

Stage 6: Physical carriers, 63-bit InlineInt, flat collections & 16-byte HeyStr atop SDS

HeyMirPhysical.hey (works today) assigns every SSA value, block parameter, and call operand to one of Hey's physical carriers—raw i64, 63-bit register InlineInt (managed_int), f64, i1, countable range_i64, two-register string16, flat homogeneous arrays (int64_t[], double[], or contiguous static-key record slots HEY_ARRAY_REPR_SHAPED) with hoisted {data_ptr, len} loop preheaders, flat value-specialized Maps, or dynamic HeyValue*—inserting explicit boundary conversions only where a value enters a dynamic HeyValue* slot. For strings, Hey pairs an Umbra-style 16-byte German String (HeyStr) in registers with a 32-byte-header reference-counted Simple Dynamic String (SDS) buffer for long owned text (Values, memory and Strings):

  • Short strings (0–12 UTF-8 bytes) stay 100% inline in two 64-bit registers: A 4-byte length plus 12 zero-padded bytes need 0 heap bytes, 0 pointer dereferences, and 0 atomic RC operations—so loop tags like "ERR:" never touch the allocator.
  • Long strings (> 12 bytes) cache a 4-byte prefix + tagged SDS word: Bytes 4..7 copy the first 4 bytes of text; bytes 8..15 pack the storage class (OWNED, STATIC, BORROWED) into bits 54..55—leaving bits 56..63 untouched for ARM memory tagging—pointing to an SDS block whose geometric slack capacity supports in-place unique append (works today). Comparing len + pfx[4] rejects unequal strings or checks a 4-byte prefix in one 64-bit register compare with zero RAM reads.

7 · Stage 7: The lifetime trio—borrows, Perceus reuse & scope arenas

With physical carriers fixed, Stage 7 (HeyMirLiveness.hey and HeyMirOwnership.hey, works today) computes exact linear backward liveness across every branch, loop edge, early return, and failure exit to eliminate unnecessary reference-count and allocator work:

  1. Zero-RC owner-scoped borrows (view <= owner): Every borrowed view or read-only parameter names its transitive backing owner as an explicit SSA dependency, propagated linearly across branch joins by HeyMirLiveness.hey. As long as the owner stays live across the read—as with line, prefix, and weights in score_line—the call executes 0 retain ops, 0 drop ops, and 0 bytes of cloning. If a view escapes into a return value, owning collection, or actor message, Stage 7 inserts an explicit to_owned promotion before the owner can end.
  2. Perceus last-use move, in-place reuse & dynamic receiver COW fusion: Following Reinking et al. (PLDI 2021), an owned value's final consuming use transfers its ownership credit directly (a move). Dead unique records paired with same-size constructors reuse the cell in place (~2 field stores instead of ~45 allocator instructions, holding peak RAM flat at 1x). For dynamic HeyValue* map and array accumulators (set m = put(m, k, v) or set a = push(a, v)), own_fuse_cow_take_receivers fuses last-use receiver ownership into hey_llvm_json_put_value_take_receiver and hey_llvm_json_push_value_take_receiver so box_refs == 0 && backing->refs == 1 holds and updates run in O(1) instead of cloning on every step (Note 5).
  3. Dynamic scope arenas on block_scopes: Fresh values proven by F1–F3 not to escape a statement, loop iteration, or call bump-allocate inside a dynamic region (hey_region_push / hey_region_pop) and reclaim in one pointer reset once the scope exits and live holds hit zero—capping score_batch's scratch memory to a single loop turn on both normal and failure unwinds.

8 · Stage 8: Independent MIR verifier & terminal LLVM backend

Before a single line of LLVM IR is emitted, HeyMirVerify.hey (works today) audits the completed physical plan as a mandatory entry gate to HeyMirLlvm.emit_module that cannot be switched off:

  • SSA & carrier agreement: Every operand is dominated by its definition, every branch edge supplies block arguments matching the target block's physical carriers, and every caller/callee signature pair agrees on registers and conversion ops.
  • Borrow, Perceus credit & arena balance: Eight independent invariant checks verify that no borrowed view outlives its transitive owner or escapes a closing region, every owned value is consumed or dropped exactly once on every normal and failure path, and every hey_region_push has a balanced hey_region_pop after loans end. Eight negative-control mutation tests deliberately corrupt plans to confirm HeyMirVerify.hey rejects every class.
  • Mechanical HeyMirLlvm.hey translation: The terminal encoder translates verified operations one-for-one into SSA LLVM IR—emitting define linkonce_odr workers, musttail self-recursive integer loops (Performance §6), and exact checked-overflow promotion paths—without ever guessing source types, re-scanning names, or inventing cleanup actions.

9 · Composable seam & self-hosting proof

works today Because every stage feeds structured Hey records into the next, the compiler assembles its passes in dependency order with zero throwaway code and verifies its own fixed point (Figure 4, left):

  1. 1 · Unified Core AST admission & module surfaces: Every surface construct and multi-file import/exposes boundary (all 13 positive and refusal module cases) routes through HeySyntaxTree.hey -> HeyFinalSyntaxNodes.hey -> HeyProgramResolution.hey -> HeyHir.hey.
  2. 2 · Two-register HeyStr & owner-scoped borrows in Physical MIR: HeyMirPhysical.hey and HeyMirOwnership.hey pass 16-byte strings in [2 x i64] registers, keep borrowed reads at zero RC via transitive owner operands, and promote escaping interior views explicitly.
  3. 3 · F1–F4 escape arenas, Perceus reuse & receiver COW fusion: HeyMirFacts.hey escape/uniqueness sets drive hey_region_push/pop on block_scopes, in-place unique cell reuse, and _take_receiver accumulator updates.
  4. 4 · Mandatory HeyMirVerify.hey gate & HeyMirLlvm.hey: Negative-control plan verification guards terminal LLVM emission on both the permanent HeyValue* dynamic fallback entry and specialized register workers.
  5. 5 · Layer 1 + Layer 2 worker specialization & stage2 == stage3 fixed point: @t<unit>.<fn>#<TypeTuple> instance typing plus SSA-MIR carrier/borrow workers compile tools/hey_selfc_pipeline.hey from stage 1 to stage 2 and stage 2 to stage 3 with byte-identical stage-2 and stage-3 outputs (Note 5).

10 · Learning from MLIR without an MLIR dependency

Hey has zero MLIR C++ dependency and none is planned. Multi-Level Intermediate Representation (MLIR) serves purely as design literature for three clean compiler engineering boundaries implemented directly in small native Hey modules (HeyIr.hey):

  • Block arguments instead of fragile phi nodes: Like MLIR regions, HeyIr.hey passes join values as explicit arguments on branch edges into typed block parameters, keeping def-use chains uniform. (Note terminology: MLIR's structural "regions" nest basic blocks; Hey's runtime "regions" are dynamic memory arenas.)
  • Monotone lattice dataflow (MLIR DataFlow): Keeping unanalyzed bottom distinct from unrestricted dynamic prevents premature widening in loops and branches.
  • Coordinated dialect-style conversion (Dialect Conversion & LLVM Target): Converting value carriers, block parameters, and call signatures together in MIR—and verifying the result before terminal LLVM translation—keeps code generation mechanical.

11 · Architectural rulings, glossary & primary evidence

Every design choice on this page is backed by an explicit Maintainer ruling in the decision ledger: lossless single-parse HeySyntaxTree, post-parse Core AST desugaring of elsif and case/when, internal-only typed extern declarations for runtime builtins, two-layer HIR + SSA-MIR worker specialization, 16-byte HeyStr atop SDS, typed Perceus + scope-arena lifetimes in MIR, and a single native Hey LLVM backend.

Glossary of compiler terms
Surface AST & Core AST
HeySyntaxTree.hey builds the lossless Surface AST with exact source spans; Stage 2 normalizes surface sugar into the 67-kind Core AST before HIR.
(unit_id, node_id)
The numeric declaration identity assigned by resolution; every later pass keys facts by this pair, never by identifier spelling.
Tree HIR & SSA-MIR
HIR is Hey's high-level tree representation for lexical scopes and type inference; SSA-MIR is Hey's basic-block graph where every intermediate value has one definition and explicit control-flow, range, carrier, and lifetime facts.
Layer 1 & Layer 2 specialization
Layer 1 (HeyHirInference.hey) types static call tuples (#Int,Float) to resolve operators and fields; Layer 2 (HeyMirPhysical.hey) deduplicates linkonce_odr machine workers by physical carrier, fits_i64?, and borrow/consume mode while sharing 1 pointer worker across heap aggregates.
HeyStr & SDS
Hey's 16-byte German String carrier (0–12 bytes inline in two 64-bit registers; > 12 bytes storing a 4-byte length, 4-byte prefix, and tagged pointer to a 32-byte-header reference-counted Simple Dynamic String buffer with slack capacity).
Perceus, borrow & scope arena
Precise compiler-placed memory management: zero-RC owner-scoped reads (borrow), last-use ownership transfer (move) plus unique-cell in-place reuse and _take_receiver accumulator fusion, and bulk pointer-bump scratch regions (hey_region_push/pop) tied to lexical block_scopes.
bottom vs dynamic (Value)
bottom means dataflow hasn't visited an edge yet; dynamic means the runtime value is unrestricted and travels in a 32-byte HeyValue cell.
InlineInt
Hey's 63-bit Least Significant Bit (LSB)-tagged register integer carrier ((word & 1) == 0), holding integers in ±4.61 × 1018 with zero heap allocation and promoting to a heap BigInt only when hardware overflow fires.
ThinLTO OS PAL
The thin C Operating System Platform Abstraction Layer (syscalls, mmap/pread, sockets/reactors, OpenSSL 3, M:N actor scheduler, 27-class allocator, HeyStr SDS, dlopen) compiled as cached Link-Time Optimization (-flto=thin) bitcode so LLVM optimizes across the OS boundary.
Negative control
A verification test that deliberately injects a broken invariant (such as an escaping borrow or mismatched carrier) and asserts that HeyMirVerify.hey refuses the plan.
