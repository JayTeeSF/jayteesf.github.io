Hey language · design note · 22 August 2026

Imports that change the flavor of the language

In Hey an import is designed to do more than pull in names — one file can opt into another module's sugar, so the same language reads differently from file to file, and the only cost you're warned about is the one that's real: name collisions — conflicts, shadowing, and overrides — never speed. It's a settled design, still deferred behind compiler completion, not something that ships in today's build.

TL;DR
  • The import model is settled by design — but not yet built. It's a banked, reconstructed design deferred behind compiler completion; in the current build (v0.99.475a) the flat 4,096-slot function table described below is what actually exists.
  • The design runs on four words with four jobs — exposes, exposing, as, forms — plus conceals to subtract and private to never export.
  • Flavor is per-file. A bare import gives you qualified access only; exposing * adopts a module's whole surface into this file — including Ruby-flavored arithmetic — without touching any other file.
  • The warned cost of adopting sugar is a conflict / shadowing / overrides warning, not a performance warning: sugar lowers at ~zero runtime cost, and where a real cost exists it's engineered away, not surfaced (ruling R1, 2026-08-22).
  • Dotted calls are method-like without objects: the receiver is argument one. account.deposit(25) lowers to deposit(account, 25).
  • Resolution is lexical and static: the resolver picks the binding once and writes it into the HIR — the high-level IR the resolver produces; the runtime never re-resolves.
  • Four edge-decisions — 35, 39, 40, 41 — remain open as of 3 August 2026; no daily through 22 August revises the design.

Four words, four jobs

Most module systems make you choose between two extremes: import a name and it's global everywhere, or qualify every single call. Hey's surface is built from four keywords, and each answers exactly one question about how much of a module you want and how it may be called.

A module names its public surface explicitly at the bottom — there's no __all__ convention to remember, and nothing leaks unless the module says so:

module BankAccount
  fn deposit(account, amount) ... end
  private fn valid_amount?(amount) ... end
  exposes deposit forms: [:qualified, :unqualified, :dotted]
end

private fn is never exported; valid_amount? stays callable inside the module but is invisible outside it. Everything a caller may reach passes through that one exposes line — and the forms: on it declares which call-forms the exposure enables (a settled design; more on that below).

The importing file then chooses how much to take. Same module, five different postures:

import "stdlib:RubyMath"                    # qualified only: RubyMath.div(-7,2)
import "stdlib:RubyMath" exposing *         # adopt the whole surface into THIS file
import "stdlib:RubyMath" as RM              # rename the namespace, adopt nothing
import './Actions.hey' exposing: [on_save]  # selective (bracket list)
import 'stdlib:RubyMath' as RM \
  exposing: [div] \
  conceals: [mod]                           # multi-clause with \ continuation

A bare import is the default, restrained posture — "how you see the difference without adopting it." You get RubyMath.div(-7, 2) and nothing has changed about how the rest of your file reads. Everything else is a deliberate step toward pulling a module's flavor into your namespace.

A drift worth flagging: exposing * (no colon, an adopt-all token) sits on the same page as exposing:, conceals: and forms: (colon, an argument list). The maintainer's reference marks this as likely intentional but never reconciled.

Flavor is a per-file decision

This is the part that makes Hey read differently from a language where an import is just a name lookup. Math, another stdlib module, exposes an operator — exposes pow infix: '**' — so when a file writes import "stdlib:Math" exposing *, it isn't only borrowing functions. It's adopting that module's forms, including the ** operator. Arithmetic in that one file can take on Ruby's flavor. The file next door, importing nothing, still sees plain Hey. Nothing about the adoption reaches beyond the file that asked for it.

Two rules keep this from turning into chaos. First, precedence is owned by the symbol, never the module — "an import supplies meaning, never shape." A module may claim any existing symbol except the six state-mutation operators (set … =, +=, and their kin). Second, when adopted names collide, there's a clear order: inner scope beats outer; at the same scope, the later declaration or import wins — and the compiler warns, naming both locations. A rename, a narrower exposing:, or a conceals: silences it.

Even the built-ins play by these rules. stdlib:BuiltIns is an ordinary module whose surface is adopted at the outermost scope by default — and it's concealable like any other exposure. There's no privileged core you can't move out of the way.

The warning is about conflicts — never performance

It would be easy to assume that pulling a module's whole flavor into a file costs something at runtime, and that Hey ought to warn you about it. As of a maintainer ruling on 22 August 2026 (R1), it does not — and the reasoning is deliberate.

Ruling R1 — verbatim "yes, let's avoid warning about things that do NOT have a cost. Let's try to get rid of costs where possible. (Let's continue to strive for the Fast language that is ergonomic like Ruby, etc)"

Most sugar — pipes, pattern-matching, with-chains, keyword and block sugar, transient builders, batch-update, and flavor-via-imports under the module system — lowers at roughly zero runtime cost. A warning for a cost that doesn't exist is noise, and it erodes trust in the warnings that do matter. So the warning you get when you expose or adopt sugar is reserved for genuine correctness hazards: name conflicts, shadowing, and overrides. Those change meaning, not speed.

And where a real cost does exist — the one identified case is a naive string-interpolation lowering that re-triggers a quadratic append — the doctrine is to engineer it away, not paper over it with a warning. That's the same runway as the rest of the compiler: remove costs (COW-by-default, byte tokenizer, buffer reuse), don't surface them. The north star is restated plainly: fast and ergonomic, sugar and speed, never either/or.

One guard rail on the doctrine: a warning is never a substitute for an error where the answer would be wrong. Warnings flag hazards; they don't bless something silently incorrect. Conflicts are the only hazard warned at import/expose time — not the only hazard the language guards against.

Dotted calls: the receiver is argument one

Hey has method-like syntax without objects. When you write account.deposit(25), there is no method dispatch and no object with a deposit slot — the resolver rewrites it into an ordinary function call where the receiver becomes the first argument:

account.deposit(25)        # what you write
deposit(account, 25)       # what it lowers to

That receiver rule is why forms: matters. A module's exposes can declare which call-forms are legal — :qualified (M.f(x)), :unqualified (f(x)), and :dotted (x.f()) — and adopting the exposure auto-enables the forms it declares. The forms: import-clause that would narrow those is shipped reserved-but-unbuilt on purpose: adding a keyword later is safe, taking one back is not.

Decided once, at resolve time

All of this — the receiver rewrite, the chosen binding when names collide, the operator a symbol resolves to — happens in the resolver, statically. The resolver rewrites account.deposit(25) into deposit(account, 25) and stores the selected binding in the HIR, the high-level IR it writes. From then on the meaning is fixed: "HIR already contains the selected binding," and the runtime never re-resolves. The same authoritative exposure record — names, forms, operator symbols, source locations — is what Reflection.module(...) reports and what drives the conflict warnings.

The payoff of doing it this way is concrete. Today's stopgap — the thing that actually runs in the current build — is a single flat, per-process function table shared by interpreter and compiler: every import registers its entire closure by name, with no tree-shaking and no visibility boundary. In that world "a module declaring fourteen functions comes to cost a hundred and forty-three," and 111 stdlib modules consume 3,336 of 4,096 slots — 81.4%. Meaning gets re-decided across 45-plus precedence sites and 28 name sites. The new resolver gives imports one owner and one place where a name's meaning is settled.

One boundary is drawn on purpose: no dynamic binding from data. Runtime arrays and maps cannot create lexical bindings. A hypothetical future Modules.load(...) module-value API would be a separate thing — the lexical layer stays lexical.

Still open: four edge-decisions

The core is settled — "the import model is settled," and the list of things not to vote on again is long: receiver = arg one; the inner-scope / later-at-same-scope conflict rule with its naming warning; as renaming; the explicit exposes surface; private helpers callable inside the module; adopted exposures auto-enabling declared forms; forms: narrowing and conceals removing; stdlib:BuiltIns implicit-outermost and concealable; independent chain-segment resolution; the runtime executing the direct chosen call. All of it is settled design — the language work itself is deferred behind compiler completion, so none of this yet exists in the build. Four narrow choices remain open as of 3 August 2026, and no daily through 22 August revises them.

Why it's shaped this way

The through-line is a single idea: an import supplies meaning, never shape. You can pull another module's flavor into one file and read arithmetic the way Ruby reads it — and Hey will tell you the truth about the only thing it warns you about, which is a name colliding with another name. It won't invent a performance tax to warn you about, because the design's whole posture is to remove costs rather than announce them. Decided once, at resolve time; fast at runtime; ergonomic where you write it. That's the language changing flavor without changing its promises — a design that's settled on paper, waiting on the compiler to make it real.
