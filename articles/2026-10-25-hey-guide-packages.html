Using third-party packages

A Hey package is a folder of Hey source with a version and a hash for every file. You list the ones you want, Hey picks versions, downloads them, checks every byte, and writes a lock file. Commit that lock, and every other machine gets exactly the same bytes, or nothing at all.

1. Why packages are locked and hashed

Think of a package download as a chain of signed receipts. Each link carries the SHA-256 fingerprint (a 64-character hash that changes completely if one byte changes) of the next link. Your lock file keeps a copy of every fingerprint.

So there are no "it worked on my machine" upgrades. A version that's in the lock can't silently change: a new download that reuses a locked name and version with different bytes is refused.1

2. Add a package to a new project

Works today

We'll use hey_cache, a read-through cache from the registry. Make a folder with one file, hey-package.json:

{
  "name": "pages_app",
  "version": "0.1.0",
  "registry": "https://www.jayteesf.com/packages/registry-v1.json",
  "dependencies": {
    "hey_cache": "~0.1.0"
  }
}

Now ask Hey to resolve, download, check and lock:

$ hey package ensure --project . --update-lock
ensured hey_cache@0.1.1 from project
updated ./hey.lock.json packages=1 edges=0
$ ls -a
.  ..  .hey  app.hey  hey-package.json  hey.lock.json

Two new things appeared:

FileWhat it isCommit it?
hey.lock.jsonThe exact version of every package (including the ones your packages need), and the hash of the registry entry, release file, archive, manifest, combined content and each file.Yes.
.hey/The downloaded, checked packages. Rebuilt from the lock any time.No. Add .hey/ and **/.hey/ to .gitignore.

When a package needs other packages, ensure fetches those too. Asking for hey_config pulled in its dependency:

$ hey package ensure --project . --update-lock     # with "hey_config": "^0.1.0"
ensured hey_packager@0.1.13 from hey_config
ensured hey_config@0.1.1 from project
updated ./hey.lock.json packages=2 edges=1

Here's one lock entry, shortened (the real one lists all 18 files of hey_config with a hash each):

3. Version ranges

A requirement says which versions you'll accept. Hey picks the highest version that fits every requirement in the whole graph, and backs up when a later choice makes an earlier one impossible.

Each form below was tried with hey_cache, whose only versions are 0.1.0 and 0.1.1:

RequirementMeansResult on 606a
0.1.1exactly this onepicked 0.1.1
0.1.0exactly the older onePartly works refused: the registry's 0.1.0 archive is malformed (archive_duplicate_entry: hey-package.json), so only 0.1.1 can be installed
~0.1.00.1.0 or later patch releases, below 0.2.0picked 0.1.1
^0.1.0compatible with 0.1.0 (caret)picked 0.1.1 (tried on hey_config)
0.1.*any 0.1 release (wildcard)picked 0.1.1
>=0.1.0 <0.2.0both comparisons must holdpicked 0.1.1
0.1.0 || 0.1.1either onepicked 0.1.1
~0.1, ^0.1the short, two-number formsPartly works refused (full output below)
$ hey package ensure --project . --update-lock     # with "hey_cache": "~0.1"
hey error: package_ensure_failed: package_resolution_failed: no hey_cache version satisfies ~0.1
  at /path/to/hey/tools/hey_package.hey:1:1 in repl     # exit 70

Write all three numbers. Hey's own package guide shows "example_mobile": "~2.4" as an example, but two-number tilde and caret ranges are refused on 606a. Use ~2.4.0. If no version fits, ensure fails and your old lock stays as it was: it never writes half a graph.

4. Import it

A package's manifest gives each public file a short name (a module alias). hey_cache publishes main and cache. You import them by package, exact version and alias:

import 'pkg:hey_cache@0.1.1/cache'
import 'pkg:hey_cache@0.1.1/main'

fn render(key)
  says 'rendering ' + key
  return 'page:' + key
end

program
  let cache = HeyCache.open({
    namespace: 'pages',
    layers: [HeyCache.memory_layer('mem', {})],
    default_ttl_ms: 60000,
    clock: HeyCache.fixed_clock(1000),
  })
  let first = HeyCache.fetch(cache, 'home', render, {})
  let second = HeyCache.fetch(first.cache, 'home', render, {})
  says first.value
  says second.value
  says 'hey_cache ' + HeyCacheInfo.version()
end

Predict: fetch is called twice for 'home'. How many times does rendering home print?

$ hey app.hey
rendering home
page:home
page:home
hey_cache 0.1.1

Once. The second fetch found the page in the memory layer. (Note it's first.cache, not cache: values don't change in Hey, so fetch hands back an updated cache along with the value.)

Each source file imports what it uses directly. Leave out the /cache import above and compilation stops; the key line of the (longer) error is missing direct module import: .../app.hey:11:14: HeyCache.memory_layer requires a direct import in this source unit.

Partly works Native builds can't import modules that live in a subfolder of the package. hey_cache's files sit at the package root, so it works. hey_config keeps its main module at src/main.hey, and on 606a (and 605a) the native compiler can't find it:

$ hey app.hey          # app.hey imports 'pkg:hey_config@0.1.1/main'
hey error: could not open read file
$ hey build app.hey -o build/app
hey error: hey-selfc: ProgramResolution production failed (one authoritative resolution; no downstream re-resolution) (exit 70): hey error: hey_resolve_program: import not found: .../app.hey: pkg:hey_config@0.1.1/main
$ heyc app.hey --run     # the interpreter reads the alias correctly
env:DATABASE_URL
hey_config 0.1.1

The compiler guesses main.hey at the package root instead of reading the alias from the verified manifest. This is the known P0 task selfhost-package-module-alias-resolution. Of the 26 pure-Hey packages in the registry, 9 keep at least one module under src/. Until it's fixed, a real app such as the elders_prayer_app builds with the private stage-0 compiler instead (see Guide 6).

5. Restore exactly on another machine; verify; audit

Works today

This section continues with the project from section 2 after adding hey_config, so its manifest lists "hey_cache": "~0.1.0" and "hey_config": "^0.1.0", and the lock holds three packages (hey_config brings hey_packager). On a second machine (here, a fresh folder with only the manifest, the lock and the program), restore from the lock. --locked doesn't consult the registry's version list and can't change the lock:

$ shasum -a 256 hey.lock.json
d9736cd576b86bde0c27106efd1645216b348149589f50e0f0e71954ecce9fe2  hey.lock.json
$ hey package ensure --project . --locked
restored hey_cache@0.1.1 to ./.hey/.package-locked.5cs3Dc/packages/hey_cache/0.1.1
restored hey_config@0.1.1 to ./.hey/.package-locked.5cs3Dc/packages/hey_config/0.1.1
restored hey_packager@0.1.13 to ./.hey/.package-locked.5cs3Dc/packages/hey_packager/0.1.13
restored locked project packages=3
$ shasum -a 256 hey.lock.json          # unchanged
d9736cd576b86bde0c27106efd1645216b348149589f50e0f0e71954ecce9fe2  hey.lock.json

(The .package-locked.5cs3Dc folder is a temporary staging name; the finished tree is moved into .hey/packages in one step, so a half-restored tree is never visible.)

Two checks, for two different questions:

$ hey package verify --project .     # offline: do the installed bytes match the lock?
verified hey_cache@0.1.1
verified hey_config@0.1.1
verified hey_packager@0.1.13
verified project packages=3
$ hey package audit --project .      # online: does the registry still serve the same releases?
verified hey_packager@0.1.13
audited hey_cache@0.1.1 release/archive/content immutable
audited hey_config@0.1.1 release/archive/content immutable
audited hey_packager@0.1.13 release/archive/content immutable
audited project packages=3

audit first re-verifies every installed package (only the last verified line is shown above).

Now tamper with an installed file and watch:

$ sed -i '' "s/return '0.1.1'/return '6.6.6'/" .hey/packages/hey_cache/0.1.1/cache.hey
$ hey package verify --project .
hey error: package_project_verify_failed: installed_content_tampered: ./.hey/packages/hey_cache/0.1.1
  at /path/to/hey/tools/hey_package.hey:1:1 in repl    # exit 70
$ hey build app.hey -o build/app
heyc: package module checksum mismatch: .hey/packages/hey_cache/0.1.1/cache.hey
heyc: file not found: pkg:hey_cache@0.1.1/cache    # exit 1
$ heyc app.hey --run
heyc: package module checksum mismatch: .hey/packages/hey_cache/0.1.1/cache.hey
heyc: file not found: pkg:hey_cache@0.1.1/cache    # exit 1
$ hey app.hey
rendering home
page:home
page:home
hey_cache 6.6.6

Partly works verify, hey build and heyc --run catch the change. hey app.hey runs the tampered code and printed hey_cache 6.6.6. Hey's own publishing guide (docs/developers/package-publishing.md:74) says compilers verify every imported module against the install record and the lock; on 606a the hey file.hey path doesn't. Until that's fixed, run hey package verify in CI and build anything you ship with hey build. hey package ensure --project . --locked puts the original bytes back.

There's also an explicit escape hatch, HEY_PACKAGE_VERIFY=off, documented as development-only. Whether to keep it is an open question in the decision ledger (entry L-IMP-36, recommended: remove).

6. Commands that come with a package

Works today

A package can ship commands written in Hey. Add "hey_secret_lint": "0.1.2", run ensure, and a new hey subcommand appears for this project:

$ hey package commands --project .
secret-lint hey_secret_lint@0.1.2 bin/secret-lint.hey
$ hey package command-path secret-lint --project .
./.hey/packages/hey_secret_lint/0.1.2/bin/secret-lint.hey
$ cat lintdemo/login.hey
fn admin?(supplied, expected)
  return supplied == ('Basic ' + expected)
end

program
  says admin?('Basic abc', 'abc')
end
$ hey secret-lint lintdemo
lintdemo/login.hey:2: == on '('Basic ' + expected)' looks like a secret; use Crypto.constant_time_equal?(bytes(a), bytes(b))
secret-lint: 1 finding in 1 file (1 .hey file scanned)      # exit 1

Built-in commands can't be shadowed, two packages can't claim the same name, and Hey verifies the installed tree before each dispatch. Other packages with commands in the registry today: hey_ios_tv (ios-tv-app), hey_android_tv (android-tv-app), hey_party (party), hey_mysql (mysql-dev); Guide 5 uses the TV ones.

7. Packages with C inside

Works today with a build step you run yourself.

Some packages wrap a C library: hey_sqlite3, hey_postgres, hey_mysql, hey_zstd and 13 others in the registry carry a hey.native.json file. Installing one proves its source bytes, not that its C half was compiled for your machine. You build that half once per target with the package's own bin/build-native, into your app's build folder, and point the app at the result. The elders_prayer_app's Dockerfile does exactly this for hey_sqlite3:

".hey/packages/hey_sqlite3/$version/bin/build-native" --out "$out"
# then, in the runtime image:
ENV HEY_SQLITE3_LIBRARY=/app/lib/libhey_sqlite3.so

Quoted from elders_prayer_app/Dockerfile; not run for this page. Guide 4 builds and uses hey_sqlite3.

  • Decided, coming Direct typed calls into C, read from hey.native.json at build time and lowered in MIR to a plain LLVM call (about 40-90 instructions per call instead of about 5,400), ruled (decision ledger L-IMP-30); the import spelling native: was picked (L-IMP-31). Where it goes: the native ABI v2 release (estimate provisional, later if loaded). Details: native code and C, schedule: roadmap.
  • Proposed One declarative native build receipt per package, so a build records targets, toolchains, flags, libraries and artifact hashes the same way for every native package.

8. Write and publish your own

Works today hey package init; Partly works the publish step.

$ hey package init demo_pkg --path $PWD/demo_pkg --description "A tiny demo package"
Created Hey package demo_pkg@0.1.0
path=/.../demo_pkg
packager=hey_packager@0.1.0
next: cd /.../demo_pkg && bin/check
$ cat demo_pkg/src/main.hey
# A tiny demo package

module DemoPkg
  fn version()
    return '0.1.0'
  end

  fn hello()
    return 'hello from demo_pkg'
  end
end
$ cd demo_pkg && HEY_ROOT=/path/to/hey bin/check
PASS: demo_pkg basic contract
verified demo_pkg@0.1.0
manifest sha256 57d19658604f98771280e1021f0527b78f168032ded6121331e9741791c7569c
content sha256 bb7945697e1152b6ee13ab7bbcf6929588d42c8081d0d4ac924cdb0986a20d81
demo_pkg v0.1.0 checks passed

You get source, a spec, VERSION, hey-package.json, docs, an example, and bin/check, bin/release, bin/publish, bin/package-zip, bin/source-zip. Every file you ship must be listed under "files" in the manifest, and every importable file under "modules". Released versions never change: new bytes need a new version.

Release and publishing live in a separate package, hey_packager (0.1.13), so website policy stays out of Hey itself. Its commands: bin/bump (move the version everywhere it's written), bin/check, bin/release (build the ZIP, the release JSON and checksums under dist/), bin/publish (copy into a registry folder and commit there; it never pushes), bin/source-zip, and bin/registry-prune.

$ HEY_ROOT=/path/to/hey HEY_PACKAGER_ROOT=/path/to/hey_packager bin/release --registry-root /path/to/scratch-registry
...
hey-packager release ok package=demo_pkg version=0.1.0 checked=true
archive=.../demo_pkg/dist/demo_pkg-0.1.0.zip
release=.../demo_pkg/dist/demo_pkg-0.1.0.release.json
checksums=.../demo_pkg/dist/SHA256SUMS.txt
publication=.../demo_pkg/dist/registry-publication/packages/demo_pkg/0.1.0
publication_zip=.../demo_pkg/dist/demo_pkg-registry-publication-0.1.0.zip
heyc: file not found: stdlib/Cli.hey
hey-packager: Hey metadata compiler failed

Three rough edges a new package author will hit on 606a:

  • The release files are built correctly, but the last step fails with heyc: file not found: stdlib/Cli.hey when run outside the Hey checkout. It's the same folder-dependent lookup that breaks heyc --describe (Guide 1).
  • The generated scripts default to developer paths ($HOME/dev/hey-lang-bootstrap-plan, $HOME/dev/hey_packager). On a machine without them, set HEY_ROOT and HEY_PACKAGER_ROOT as above; on a machine that has them, the scripts silently use those copies.
  • init records hey_packager@0.1.0 although 0.1.13 is current.

And remember section 4: init puts your module at src/main.hey, which today's native compiler can't import through pkg:.
