Language conformance#

Hey conformance is an outside-in behavioral contract. An implementation conforms when it accepts/rejects the specified source and produces the specified observable behavior. Portable conformance does not require a particular host language, IR, object layout, or backend.

Portable manifest#

specs/conformance/manifest.json
specs/conformance/schema.json
specs/conformance/README.md

Each fixture may describe:

  • source and arguments;
  • standard input;
  • compile acceptance or rejection;
  • standard output, standard error, and exit status;
  • documented files, sockets, messages, and other effects;
  • ordering and timeout guarantees;
  • semantic tags.

It must not require a specific HIR/MIR/LLVM shape or compiler implementation.

Internal compiler contracts#

The repository separately tests structural facts:

  • tokenizer spans and token kinds;
  • final-syntax node shape and recovery;
  • resolved binding/module/operator identity;
  • HIR and MIR schemas;
  • ownership and borrow lifetimes;
  • LLVM/runtime ABI lowering;
  • cross-lane identity.

Those belong under compiler/IR/backend specs, not the portable language manifest.

Adapter protocol#

ADAPTER build SOURCE OUTPUT

The conformance runner invokes the produced executable with the fixture's declared inputs and compares only observable results.

./bin/test --conformance
./bin/subcmds/hey-conformance --adapter ./path/to/adapter

An independent C, Rust, Go, JVM, JavaScript, WebAssembly, interpreter, or other implementation can therefore participate without adopting Hey's internal compiler pipeline.

Reference implementation#

Hey's reference compiler uses the shared source contract:

source -> tokens -> final syntax -> resolved names -> HIR -> MIR -> LLVM

That architecture is tested internally, but portable conformance remains backend-opaque.
