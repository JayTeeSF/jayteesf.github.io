What Is on the Other Side of the Pipe?

Hey's runtime starts a helper process to run standard-library calls the compiler cannot yet emit natively. That helper inherited every open file descriptor from its parent, live network connections included. The fix was routine; the question it raised was not. Are helper processes inherently unsafe, and should we replace ours before a user gets hurt?

TL;DR

  • Verdict: we are keeping the helper process and changing what it may do. Splitting a program into processes is one of the standard ways to build security — it is what OpenSSH and Chromium do on purpose. The pattern is not the defect.
  • The bug we shipped: our helper inherited every open descriptor, live client connections included — so one standard-library call from a request handler pinned those connections open, with no close signal to the client. Fixed in 466a.
  • The question we were not asking: what privilege does the helper have? Ours has exactly its parent's. We pay for a subprocess and collect none of the containment.
  • Disclosed weaknesses, both open: one helper behind one lock with a 30-second timeout taken inside it, so one hung call stalls every other caller; and a helper outliving its parent can sit on a socket it opened, which inheritance fixes cannot reach.
  • Check it yourself: with a Hey server running, list the open files of its helper child (pgrep -P <server-pid>, then lsof -p). On 466a you should see its two pipes and no client sockets.

The bug we shipped

When a Hey program calls a standard-library function the compiler has not yet lowered to native code, the runtime hands that call to a child process and waits: one child per application, spoken to over anonymous pipes. That child inherited every descriptor the parent had open at the moment it started — not only the pipes it needed, but everything, live connections included.

File descriptor

The integer a program uses to refer to something it has open. Handing one to a child hands over the thing itself, not a copy. Full entry →

For a web server the consequence is quiet and unpleasant. A request handler makes one delegated call; the helper starts, and now holds a copy of that request's socket. The handler finishes, the server closes its end — and nothing happens, because the kernel tears a connection down only when the last holder lets go. The client waits out its own timeout. Descriptors leak.

The good news is that this bug has a name

We did not discover a new failure mode; we rediscovered a well-mapped one. Descriptor inheritance has been a known hazard long enough that whole ecosystems swept it out by policy — Python changed the default for the entire language in PEP 446, and Mozilla ran a systematic sweep across Firefox for exactly this class.

That is the useful part. A bug with a name and a precedent is one you can go looking for on purpose. An unnamed bug is found by a user; a named one is found by an audit. Ours began as three named sites; auditing for the class rather than the three known spellings found fifteen socket-creation sites to harden — twelve of them defense in depth, which is to say twelve no bug report was ever going to name.

So we asked whether we should have a helper at all — the literature says keep it

We went looking for a warning and found the reverse: process separation is one of the standard ways security gets built.

The canonical result is OpenSSH privilege separation (Provos, Friedl & Honeyman, USENIX Security 2003): split the daemon into a privileged monitor and an unprivileged child, so that “programming errors occurring in the unprivileged parts can no longer be abused to gain unauthorized privileges.” It killed vulnerabilities nobody had discovered yet. Chromium's process model (Reis & Gribble, EuroSys 2009) does the same at browser scale, running page renderers in a sandbox with no direct access to disk, network, or devices. Capsicum (Watson et al., USENIX Security 2010) and seccomp-bpf make “less privileged” real rather than aspirational, and RLBox (Narayan et al., USENIX Security 2020) shows the boundary need not be a process at all.

Read that list for what it does not say. None of those systems gains anything from the subprocess as such. They gain because one side can do less. A helper with the same privileges as its parent buys no containment. It is not insecure by nature; it simply is not security. In the literature a helper is a boundary; ours is a convenience — it exists because some standard-library names are not lowered natively yet, not because anyone wanted a wall there.

If you have read that sidecars are dangerous, you read about something else

Two unrelated things are called a sidecar. The one in the security headlines is an infrastructure proxy injected beside every application in a cluster. Its sharpest failure is the Sidecar Siphon: compromise the proxy and you walk off with the certificate and the workload identity, because both sit in the pod beside the application — which is why Istio's ambient mode moves the proxy out of the pod entirely.

Hey's helper shares the name and nothing else: one child per application, holding no credentials, terminating no encryption, unreachable over a network. There is no socket file, no named pipe, and no port, so the classic attacks on a local channel have nowhere to land — by construction rather than by vigilance. The channel is the part we got right, which is a statement about the channel and not a clean bill of health: a separate issue in this area is being fixed, and will be described once a released version carries the fix.

Two more things you should know about ours

It serialises everything, and it can stall you. There is one helper, one lock, and a 30-second default read timeout — taken inside the lock. One hung delegated call therefore blocks every other concurrent one for up to 30 seconds: a single slow path becomes a whole-server stall, reachable by whatever input selects it. That is a documented trade-off rather than a vulnerability, but it belongs in your threat model. The escape valve the source names — a small bounded pool — is not built and would not be free: a pool is the most likely reason to move this channel off anonymous pipes, which is exactly the change that would make the local-channel literature apply to us.

Helpers can outlive the application that started them. On one development machine we found a helper still running after its parent had died — adopted by the init process, still holding the listening socket its application had used, until we killed it by hand. That was on 466a, and it is not a gap in the inheritance fix: the socket was never inherited, because the helper opened it itself. A fix for what crosses a process boundary cannot reach what was created on the far side.

The durable fix is to need the helper less

The tempting response to a bug in a helper process is a better guard on the helper. We are doing some of that, and it is the right first move — but the durable one is to need the helper less: every standard-library name the compiler lowers to native code can never reach the delegation path at all. That deletes the surface instead of guarding it, and takes the stall with it. The work was already on the roadmap for speed; it now has a second, independent argument behind it.

Only once that has narrowed what the helper must be allowed to do is the literature's design worth building — drop privileges in the child, and turn a convenience into a boundary. The order matters. Sandboxing a helper that still has to do everything is how you get a sandbox with every door propped open.

What is shipped, and what is not

Shipped: the descriptor-inheritance fix, in 466a. Not shipped, and described here as open work: the bounded helper pool, dropping privileges in the helper, and reaping helpers that outlive their parent.
