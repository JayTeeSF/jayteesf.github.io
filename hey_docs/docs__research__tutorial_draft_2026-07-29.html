The Hey Tutorial

Welcome. Hey is a small language with a fast native compiler. Its essence fits in one sentence: functions, actors, JSON-shaped objects, strings, numbers, conditionals, and loops — everything else is sugar or standard library. If you know Ruby, you already know most of Hey; this tutorial is designed so that a Ruby developer feels at home in under an hour.

Every example below was executed against Hey v0.99.471a, and the output shown is the real output. Run any of them yourself: save the code to a file and run `hey yourfile.hey` (or `heyc yourfile.hey --run`).

---

Part One — Values

1. Hello, Hey

A Hey file's executable entry point is the `program` block. `says` prints a value followed by a newline (like Ruby's `puts`). Save this as `hello.hey` and run `hey hello.hey`.

program
  says 'Hello, Hey'
end

Hello, Hey

**Try this:** change the greeting, run it again, and notice the second run starts faster — `hey` caches a compiled native executable behind the scenes.

2. Comments

A `#` starts a comment that runs to the end of the line, exactly as in Ruby. Comments can take a whole line or follow code.

# This whole line is a comment.
program
  says 'comments are for humans'  # so is everything after the hash
end

comments are for humans

**Try this:** comment out the `says` line and confirm the program prints nothing.

3. Numbers

Hey has exactly two runtime number types: integers and floats. Mixing them promotes to float (`1 + 2.5` is `3.5`), and dividing two integers truncates (`7 / 2` is `3`, like Ruby) — write `7.0 / 2.0` when you want `3.5`. There are no type annotations in Hey source; when a value's kind matters, convert explicitly with Ruby-style `.to_i` and `.to_s`.

program
  says 40 + 2
  says 7 / 2
  says 7 % 2
  says 7.0 / 2.0
  says 1 + 2.5
  says '42'.to_i + 1
  says 7.to_s + '!'
end

42
3
1
3.5
3.5
43
7!

**Try this:** predict `9 / 4` and `9 % 4` before running them, then check yourself with `9.0 / 4.0`.

4. Strings and interpolation

Double-quoted strings interpolate with `#{...}` and honor escapes like `\n` — the same syntax as Ruby. Single-quoted strings are raw: `#{}` and backslashes stay literal, and only `\'` and `\\` are escapes. Prefer single quotes for plain text and double quotes when you interpolate. `+` concatenates and `*` repeats.

program
  let name = 'Ada'
  says "hello #{name}"
  says 'raw #{name} stays literal'
  says 'ab' * 3
  says 'it\'s easy to quote "both" kinds'
end

hello Ada
raw #{name} stays literal
ababab
it's easy to quote "both" kinds

**Try this:** interpolate an expression, not just a name: `says "sum is #{40 + 2}"` prints `sum is 42`.

5. Booleans and nil

Hey has `true`, `false`, and `nil`, with Ruby's truthiness rule: `false` and `nil` are falsey, everything else is truthy. `!` negates (`not` is a readable alias), and `and` / `or` short-circuit.

program
  let signed_in = true
  says signed_in
  says !signed_in
  says 3 > 2 and 2 > 1
  says nil
  if nil
    says 'never printed'
  else
    says 'nil is falsey'
  end
end

true
false
true
nil
nil is falsey

**Try this:** check that `0` and `''` are truthy in Hey (as in Ruby, unlike JavaScript): `if 0 ... says 'truthy' ... end`.

6. Bindings

`let` binds a new name; `set` re-binds an existing one. Here is THE rule about Hey data, and it is worth reading twice: **assignment copies the value — two names never share.** Every value is immutable; "updating" means building a new value (usually with spread `...`) and re-binding, so no distant alias can ever change data out from under you.

program
  let visits = 1
  set visits = visits + 1
  says visits

  let original = [1, 2]
  let copy = original
  set copy = [...copy, 3]
  says original.to_json
  says copy.to_json
end

2
[1,2]
[1,2,3]

**Try this:** do the same with an object — `let a = {n: 1}`, `let b = a`, `set b = {...b, n: 2}` — and confirm `a` still holds `{"n":1}`.

7. Arrays

Arrays are ordered, immutable values written with `[...]`, indexed from zero with brackets. Spread syntax builds a new array from an old one; the original is untouched. `.length` (also `.size`, `.count`) reports the element count, and `.to_json` renders any value as JSON text.

program
  let names = ['Ada', 'Grace']
  says names[0]
  says names.length
  let expanded = [...names, 'Katherine']
  says expanded.to_json
  says names.to_json
end

Ada
2
["Ada","Grace","Katherine"]
["Ada","Grace"]

**Try this:** arrays are heterogeneous — build `[1, 2.5, true, nil, 'A']` and print its `.to_json`.

8. Objects and records

Where Ruby reaches for a hash or a small class, Hey uses one thing: the JSON-compliant object, written `{key: value}`. Read ordinary fixed fields with dot access (`user.name`), and use bracket access — `user['visits']` — for dynamic keys, punctuated keys, and any key whose name matches a built-in property or method (`count`, `type`, `keys`, `length`, ...). For data access, brackets always mean *your data*; that is the form to reach for when in doubt (`get(user, 'count')` is an equivalent functional spelling). Updates are spreads that produce a new value.

program
  let user = {name: 'Ada', visits: 2, tags: ['admin']}
  says user.name
  says user['visits']
  says user.tags[0]

  let next = {...user, visits: user.visits + 1}
  says user['visits']
  says next['visits']
  says next.to_json

  let record = {name: 'Ada', count: 9}
  says record['count']
end

Ada
2
admin
2
3
{"name":"Ada","visits":3,"tags":["admin"]}
9

Why the bracket rule matters: `record.count` would answer the *built-in* count (how many keys the object has), not your `count` field. Brackets say what you mean.

**Try this:** store a key that is not an identifier — `let doc = {'display-name': 'Ada'}` — and read it back with `doc['display-name']`.

9. Bytes

`Bytes` values hold binary data as immutable byte sequences; a `b'...'` literal builds one, and `stdlib:Bytes` decodes, slices, and searches them. Keep data as bytes at I/O boundaries and decode to text exactly once, at the edge. (There is deliberately no mutable byte buffer in Hey — build output by collecting immutable pieces and joining.)

import 'stdlib:Bytes'

program
  let raw = b'hey'
  says raw.length
  says Bytes.decode(raw, 'utf-8')
end

3
hey

**Try this:** slice before decoding — `Bytes.slice(raw, 0, 2)` decodes to `he`.

Part Two — Logic and structure

10. Conditionals

`if ... else ... end` reads like Ruby. Conditions use ordinary comparison operators, plus `and` / `or` / `!`. Chain decisions by nesting an `if` inside the `else` branch.

program
  let visits = 3
  if visits == 0
    says 'welcome!'
  else
    if visits < 5
      says 'welcome back'
    else
      says 'regular'
    end
  end
end

welcome back

**Try this:** set `visits` to `0` and to `7` and confirm each branch fires.

11. Loops and control flow

Hey has four loop forms: `for name in collection`, `while condition`, `until condition`, and `forever` (for actor-style servers). `print` writes without a newline, which is handy inside loops.

program
  for name in ['Ada', 'Grace', 'Katherine']
    says 'hi ' + name
  end

  let countdown = 3
  while countdown > 0
    print countdown.to_s + ' '
    set countdown = countdown - 1
  end
  says 'liftoff'

  let fuel = 0
  until fuel == 2
    set fuel = fuel + 1
  end
  says fuel
end

hi Ada
hi Grace
hi Katherine
3 2 1 liftoff
2

**Try this:** rewrite the countdown as an `until countdown == 0` loop and confirm the output is identical.

12. Functions

`fn name(params) ... end` defines a function; `return` returns a value. By convention a predicate's name ends in `?` (and an effectful operation's in `!`) — the suffix is part of the name, exactly like Ruby's convention, with no hidden behavior. A function name written *without* parentheses is a first-class callable value: store it in arrays or objects, pass it to other functions, and call it through any binding.

fn greet(name)
  return 'Hello, ' + name
end

fn admin?(user)
  return user.role == 'admin'
end

fn apply(value, callable)
  return callable(value)
end

fn double(value)
  return value * 2
end

program
  says greet('Ruby friend')
  says admin?({name: 'Ada', role: 'admin'})
  let pipeline = [double]
  says apply(21, pipeline[0])
end

Hello, Ruby friend
true
42

One caution: do not name your own functions after builtins like `find`, `join`, `split`, `sort`, `get`, or `put` — pick a more specific name.

**Try this:** write `triple` and swap it into the pipeline array; `apply(21, pipeline[0])` should print `63`.

13. Error handling

Hey splits errors in two, Erlang-style. *Expected* failures are ordinary Result-shaped values: `stdlib:Result` gives every module the same `{ok, value, error, code}` shape, so you branch on `Result.ok?` instead of rescuing exceptions. *Unexpected* runtime errors fail closed — the program stops with a nonzero exit rather than limping on with wrong data; `fail message` raises one deliberately.

import 'stdlib:Result'

fn safe_divide(top, bottom)
  if bottom == 0
    return Result.error_with('divide_by_zero', 'cannot divide by zero')
  end
  return Result.ok(top / bottom)
end

program
  let good = safe_divide(10, 2)
  if Result.ok?(good)
    says Result.value(good)
  end

  let bad = safe_divide(10, 0)
  says Result.error?(bad)
  says Result.code(bad)
  says Result.message(bad)
end

5
true
divide_by_zero
cannot divide by zero

And failing closed with `fail`:

program
  says 'before the failure'
  fail 'config file missing'
  says 'never reached'
end

before the failure
hey error: config file missing

(The error goes to stderr with a source location line, and the process exits with status 70. `'never reached'` never prints.)

**Try this:** wrap the `fail` example in a spec with `expect error 'config file missing'` and `expect exit 70` — see chapter 25 for the spec form.

14. Modules, imports, and qualified calls

Modules group related functions (and actors) — they are Hey's unit of organization, playing the role Ruby modules and classes share. Call module functions with their qualified name: `Greeter.hello(user)`. `import './file.hey'` loads an app-local module; `import 'stdlib:Name'` loads a bundled standard-library module. Functions are public by default; mark internals `private fn` and callers outside the module cannot reach them.

`greeter_lib.hey`:

module Greeter
  private fn title_for(user)
    if user.admin
      return 'Chief '
    end
    return ''
  end

  fn hello(user)
    return 'Hello, ' + Greeter.title_for(user) + user.name
  end
end

`main.hey`:

import './greeter_lib.hey'

program
  says Greeter.hello({name: 'Ada', admin: true})
  says Greeter.hello({name: 'Lin', admin: false})
end

Hello, Chief Ada
Hello, Lin

**Try this:** call `Greeter.title_for({admin: true})` from `main.hey` and read the visibility error you get back.

15. Syntactic sugar: dot-method notation

Here is a rule that will feel different from Ruby, and better once it clicks: **sugar is a choice you make per file, not a property of the value.** Dot-method calls like `names.uniq` are not methods living on the array — they are sugar for module functions, and they exist in a file only because that file imported the module. `names.uniq` lowers to `Collections.uniq(names)`; nothing is ambient, nothing is monkey-patched, and your own conflicting names always win over sugar.

Verified today — importing a module enables its receiver vocabulary:

import 'stdlib:Collections'

program
  let names = ['Ada', 'Ada', 'Lin']
  says Collections.uniq(names).to_json
  says names.uniq.to_json
  says names.includes?('Lin')
  says names.empty?
  says names.uniq.take(1).to_json
end

["Ada","Lin"]
["Ada","Lin"]
true
false
["Ada"]

Both spellings above call the exact same function. Delete the import and the dot spelling stops existing; the qualified call `Collections.uniq(names)` is always available and is never re-interpreted as sugar.

Selective exposure — coming: today an import enables a module's whole receiver vocabulary. The `expose` aspect of the import statement narrows that to exactly the names you choose:

import 'stdlib:Collections' expose uniq

program
  let names = ['Ada', 'Ada', 'Lin']
  says names.uniq.to_json      # sugar for Collections.uniq(names)
  # names.includes?('Lin')     # NOT exposed — use Collections.includes?(names, 'Lin')
end

`expose` makes the sugar contract visible at the top of the file: a reader sees precisely which dot-names are in play. Un-exposed functions remain one qualified call away.

The ergonomic default — `Sys`: the default-on sugar set (`.length`, `.to_json`, `.to_i`, ...) will be backed by an ordinary module named `Sys` that itself imports other modules with `expose *`. One explicit line — `import Sys` — gives a program the ergonomic defaults, and it is the recommended way to open a program once `Sys` ships. Because `Sys` is an ordinary module, a developer can adjust or fork it like any other; there is no implicit prelude and no magic.

16. Names: whose word wins?

Hey's name resolution has one loyalty: *your names always win.* The default calling convention is the qualified module call — `Module.fn(x)` — which can never be shadowed and never surprises. Dot-method sugar exists only where an `import ... expose` brings it in, and if you define a function with the same name as an exposed or built-in one, your definition wins in your file. Overriding a builtin makes the compiler warn generously — you can do it, but never by accident — unless you explicitly opt out of the warning.

import 'stdlib:Collections' expose uniq

fn uniq(values)
  says 'my uniq runs'
  return values
end

program
  let names = ['Ada', 'Ada']
  says uniq(names).to_json          # yours — local names beat sugar
  says Collections.uniq(names).to_json  # the stdlib one, always reachable, qualified
end

The rules in one breath:

1. `Module.fn(obj)` is the default and always works.

2. `import ... expose` is the only way dot-sugar enters a file.

3. Your names always win over sugar and builtins.

4. Overriding a builtin warns, loudly, unless you opt out on purpose.

And the everyday defaults obey the same four rules: the default-on sugar set (`.length`, `.to_json`, `.to_i`, ...) will be backed by an ordinary module named `Sys` that imports other modules with `expose *`, so `import Sys` — one explicit line, the recommended program opening once it ships — is how the ergonomic defaults enter a file. `Sys` is a module like any other: adjust it or fork it, no implicit prelude, no magic — and your names still win over anything it exposes.

17. A brief stdlib tour

The standard library ships as ordinary modules under `stdlib:` — you import what you use and call it qualified. A taste of `Text` and `Collections`:

import 'stdlib:Text'
import 'stdlib:Collections'

program
  let parts = ['keep', 'values', 'immutable']
  says Text.join(parts, ' ')
  says Text.trim('  spaced out  ')
  says Collections.range(1, 4).to_json
end

keep values immutable
spaced out
[1,2,3]

Pointers, not a catalog: `stdlib:Collections` (transforms, grouping, sorting), `stdlib:Text`, `stdlib:Bytes`, `stdlib:Json` / `stdlib:Jsonl` (codec boundaries), `stdlib:Result`, `stdlib:Files` and `stdlib:Io` (opaque handles, Result-shaped lifecycle), `stdlib:Streams` (chapter 22), `stdlib:Web` (routes as ordinary callables), `stdlib:Time`, `stdlib:Duration`, `stdlib:Crypto`, `stdlib:Http`. Each has a reference page under `docs/developers/stdlib/`.

**Try this:** `Text.join(Collections.range(1, 5), '-')` — modules compose like anything else.

18. Packages

Packages are versioned module trees installed under your project; import them with the `pkg:` scheme — `import 'pkg:cards@1.2.3/main'` — and call them qualified like any module. The `hey package` command owns the project graph: `ensure` resolves and installs (with a lock file), `verify` checks the whole installation offline, `audit` re-checks against the registry. `stdlib:Packages` exposes the package data contracts themselves:

import 'stdlib:Packages'

program
  let manifest = Packages.manifest('hello_package', '0.1.0', ['main'])
  says manifest.name
  says manifest.version
end

hello_package
0.1.0

**Try this:** in a project, run `hey package ensure --project . --update-lock`, then `hey package verify --project .`.

Part Three — Concurrency

19. Actors

An actor owns private state that only it can change, one received message at a time — this is Hey's answer to both objects-with-state and threads-with-locks. `spawn` starts one and returns a handle; `send` delivers a message (values are copied into the mailbox — the no-sharing rule from chapter 6 extends to concurrency); `exit` ends the actor from inside, and `join` waits for it.

actor Counter(label)
  state count = 0
  receive msg

  if msg == 'inc'
    set count = count + 1
    says label + '=' + count
  else
    if msg == 'stop'
      exit
    end
  end
end

program
  let clicks = spawn Counter('clicks')
  send clicks, 'inc'
  send clicks, 'inc'
  send clicks, 'stop'
  join clicks
end

clicks=1
clicks=2

**Try this:** spawn two counters with different labels and interleave sends — each keeps its own count.

20. Workers

A worker is the stateless sibling of an actor: one message parameter, no `state`, no identity. Because workers are interchangeable, `workers(Name, count: N, capacity: M)` replicates one definition into a bounded pool draining a single queue in parallel. Here a pool of squarers reports to a collecting actor.

worker Square(message)
  send message.reply_to, message.value * message.value
end

actor Total(expected)
  state seen = 0
  state total = 0
  receive value

  set seen = seen + 1
  set total = total + value
  if seen == expected
    says total
    exit
  end
end

program
  let collector = spawn Total(4)
  let pool = workers(Square, count: 2, capacity: 8)

  for value in [1, 2, 3, 4]
    pool.enqueue({reply_to: collector, value: value})
  end

  join collector
  says 'completed=' + pool.status().completed
  let stopped = pool.stop()
end

30
completed=4

**Try this:** raise `count:` to 4 and confirm the total is still 30 — order of arrival may vary, the sum cannot.

21. Jobs

Jobs are the managed layer over workers — the thing you reach for when work needs receipts, results, and operational visibility (think Sidekiq, minus the Redis). `Jobs.define` wraps a worker in a named pool; `enqueue` returns a receipt telling you whether the bounded queue accepted the work; `Jobs.result` awaits the outcome with a timeout.

worker Thumbnail(image)
  return {path: 'thumbs/' + image.id + '.jpg'}
end

program
  let Thumbnails = Jobs.define('Thumbnails', Thumbnail, count: 2, capacity: 8)
  let receipt = Thumbnails.enqueue({id: 'cover'})
  if !receipt.accepted
    fail 'job queue is full'
  end

  let result = Jobs.result(Thumbnails, receipt, 5000)
  if !result.ok
    fail result.error
  end

  says result.value.path
  says 'completed=' + Thumbnails.status().completed
  let stopped = Thumbnails.stop()
end

thumbs/cover.jpg
completed=1

**Try this:** enqueue three images and await each receipt; `status().completed` should report 3.

22. Streams

Streams keep the collection chains you love from Ruby — `map`, `filter`, `collect` — while running the work on bounded worker pools underneath. Add `workers: N` to a stage and it fans out; `collect()` gathers results back in order. Bare `.map`/`.filter` (chapter 15) stay synchronous — parallelism is always visible in the source.

import 'stdlib:Streams'

fn double(value)
  return value * 2
end

fn big?(value)
  return value > 4
end

program
  let values = [1, 2, 3, 4]
    .map(double, workers: 2)
    .filter(big?, workers: 2)
    .collect()

  says values.to_json
end

[6,8]

**Try this:** add a second `.map(double, workers: 2)` stage before `.collect()` and predict the output (`[12,16]`).

23. Monitors and links

Monitors and links are how Hey processes watch each other, straight from the Erlang playbook. `monitor(handle)` gives you a one-way observation point — `monitor_info` reports the actor's lifecycle event and exit reason. `link(a, b)` declares a two-way fate-sharing relationship you can inspect with `actor_info`.

actor Courier(label)
  receive msg
  if msg == 'stop'
    exit
  else
    says label + ' delivered ' + msg
  end
end

program
  let courier = spawn Courier('bike')
  let watch = monitor(courier)
  says monitor_info(watch).event

  send courier, 'package'
  send courier, 'stop'
  join courier

  let after = monitor_info(watch)
  says after.event
  says after.reason
end

monitoring
bike delivered package
exit
exit

**Try this:** link two actors — `link(a, b)` returns `true`, and `actor_info(a).linked_pids.length` reports `1`.

24. Supervisors

A supervisor exists so that a crash is an event, not an outage: it watches a child and restarts it, up to a budget. Conceptually a supervisor *is* monitor-plus-link with a restart policy — the Erlang recipe — so everything from chapter 23 applies; `supervise child max N` is the packaged form. Here the child exits after every message, and the supervisor brings it back for the next one.

actor FragileGreeter
  receive msg
  says 'handled ' + msg
  exit
end

program
  let sup = supervise FragileGreeter max 3
  send sup, 'one'
  sleep 20
  send sup, 'two'
  sleep 20
  stop sup
end

handled one
handled two

**Try this:** send a third and fourth message — the restart budget (`max 3`) decides how many revivals the child gets.

Part Four — Ship it

25. Three ways to run, and testing

Hey programs run three ways. **Script:** `hey app.hey` compiles on first run, caches a content-addressed native executable, and re-runs are instant native starts — edit/run ergonomics with compiled speed. **REPL:** `hey repl` gives an interactive prompt with multi-line continuation for exploration. **Compiled binary:** `hey build app.hey -o build/app` (or `heyc build ...`) produces one deployable native executable for services, containers, and benchmarks. (`heyc app.hey --run` is a fourth, developer-facing lane: the embedded interpreter — it is the oracle this tutorial was verified against.)

Testing is built into the file format: a `spec` block declares expected output, and `heyc app.hey --test` (or `hey app.hey --test`) checks it.

spec 'greet formats a friendly hello'
  expect stdout "Hello, Ada\n"
end

fn greet(name)
  return 'Hello, ' + name
end

program
  says greet('Ada')
end

Run with `--test`:

PASS: greet formats a friendly hello

Run normally:

Hello, Ada

Specs can also assert failures: `expect error 'boom'` and `expect exit 70` make chapter 13's fail-closed behavior testable.

**Try this:** change the expected stdout to something wrong and run `--test` to see a failure report; then fix it.

Appendix: DEFECTS-ENCOUNTERED

Defects hit while verifying this tutorial against v0.99.471a (`heyc <file> --run`), and the routes taken around them:

1. **Interpreter stack overflow is a segfault, not a diagnostic.** Self-recursive `sum_down` crashes with `Segmentation fault: 11` under `heyc --run` at depths between 400 and 600 frames (400 passes, 600 crashes; 1,000,000 was the intended showcase). The native lane's self-tail-call elimination is documented and not in question, but the interpreter has neither elimination nor a clean stack-guard error. The recursion chapter's example was re-scoped to depth 400 and the compiled-lane guarantee is described in prose. Suggest: a clean "recursion too deep in the interpreter lane" error before publishing a bigger number. The recursion chapter is deferred pending the recursion program (research commissioned; the chapter returns when full tail-call depth is guaranteed in both lanes).

2. **`fail` location line says `in repl` for file runs.** `heyc file.hey --run` reports `at <path>:2:1 in repl` — the frame label is wrong for a file execution (cosmetic). Chapter 14 shows the two content lines verbatim and describes the location line in prose.

3. **`stdlib:` imports resolve relative to the deployed tree, not the invoking directory.** Running `heyc /elsewhere/file.hey --run` from an arbitrary cwd failed with `file not found: stdlib/Bytes.hey`; running the same command from the deployment root succeeded. All verification runs were made from the deployment root. Worth confirming this is intended installer behavior for end users of `hey`.

4. **Un-imported receiver sugar evaluates to silent nil.** With no `import 'stdlib:Collections'`, `names.uniq` does not error — it evaluates to `nil` (`says names.uniq.to_json` prints `null`, exit 0). This contradicts the "sugar exists only via import" contract's expected failure mode and is a silent-wrong-answer shape. Found while verifying a planned exercise for chapter 15; the exercise was replaced. Presumably in scope for the wfnwins/wwarnchannel work — a missing-import diagnostic at the call site is the fix the tutorial wants to teach against.

Known live defects routed around per instruction (not showcased, not re-triggered): float-through-variable arithmetic (all float examples use literal expressions or single-step conversions); bare-dot data access on reserved names (`record.count` etc. — the tutorial teaches brackets for data access); user functions named after builtins (chapter 12 warns against it).
