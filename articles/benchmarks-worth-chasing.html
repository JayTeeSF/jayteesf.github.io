Benchmarks Worth Chasing

A sourced tour of the benchmark suites that actually tell you something — what each one isolates, where each one rots, and the single open goalpost that no immutable-first language has claimed yet. It ends in an eight-rung goal ladder for Hey, with a falsifiable target on every rung.

TL;DR

  • TechEmpower Framework Benchmarks was archived March 24, 2026, after its top tier hit a ~30M requests/second cap imposed by the load-testing client itself, not by any framework — a benchmark that outlived its own measuring instrument.
  • No immutable-first language has a competitive One Billion Row Challenge entry. Java's winner does the job in ~1.5 seconds; the only Erlang entry, naive and single-threaded, takes 130 seconds. That gap is an open goalpost, not a settled score.
  • Skynet spawns one million actors in a tree and sums their replies: Erlang does it in 700–1,100 ms, Go in 200–224 ms, on comparable hardware.
  • Hey's CLI startup time (~23 ms) sits in the Python/Ruby tier today — an order of magnitude slower than Lua and Bash, which start in 0.6–0.9 ms.
  • Put together, these five suites resolve into eight goal-ladder rungs for Hey, from single-core plaintext throughput to memory held per idle actor — each with a target that can be proven wrong.

How to read this article

Every number below comes from a cited primary source — official benchmark results, project documentation, or a maintainer's own published numbers — linked inline where it's used, plus a full source list at the end. Technical terms get a definition with an example the first time they show up, boxed like this one. There's a glossary at the bottom if you lose track.

What you measure is what you become

A benchmark suite is a fixed, repeatable set of tasks measured the same way across languages or frameworks, so results are comparable instead of anecdotal — the point is that anyone can rerun it and get the same answer. What a project chooses to benchmark is what it ends up optimizing, because a number that is visible and embarrassing gets fixed, and a number nobody measures does not. That makes the choice of suite a roadmap decision, not just a reporting one.

But a suite is only a roadmap for as long as it keeps measuring something real, and not every suite manages that for its whole lifetime. Three of the ones surveyed here stopped, in three different ways, before this piece gets to the one genuinely open target left standing and the ladder it points to.

Term: benchmark suite

Benchmark suite: a fixed, repeatable set of programs or tasks, run the same way against every contender, so the results are comparable rather than anecdotal. Example: TechEmpower ran the identical JSON-serialization test against 330+ web frameworks on the same hardware.

The benchmark graveyard

A benchmark can die the way TechEmpower did: get outrun by the very instrument built to measure it. It can die the way thread-ring and chameneos-redux did: get quietly dropped from the scoreboard that used to run them. Or it can never really have been alive in the first place, the way WhatsApp's "2 million connections" number wasn't: repeated everywhere, verified nowhere. All three still get cited today as if they were live numbers. Chasing any of them means optimizing Hey toward a mirage instead of a competitor.

TechEmpower Framework Benchmarks — outrunning its own instrument

TechEmpower Framework Benchmarks (TFB) exists to answer one question with disclosed, physical hardware instead of vendor marketing: how many rps can a web framework actually serve? Rps (requests per second) is the standard throughput unit for this kind of test — how many requests a server finishes each second under sustained load. .NET 9 hit roughly 27.5M rps on the plaintext test in Round 23; Actix Web reached ~7.1M rps on a 28-core box. Its Plaintext test isolates keep-alive handling, request routing, and header generation with no serialization and no allocation beyond a static buffer — this is the test that isolates exactly Hey's accept-loop weakness. Its JSON serialization test adds object instantiation and JSON encoding on top of that same pipeline, isolating JSON-construction cost from accept-loop cost — directly relevant to how Hey's immutable data gets built per request. Further tests (single/multi/cache query, Fortunes, Updates) stress database drivers and templating, weighted by TFB into a composite score that favored the "most realistic" Fortunes test over raw Plaintext.

Term: rps & keep-alive

rps (requests per second): how many requests a server completes each second under load — the standard throughput unit for web benchmarks. Keep-alive: reusing one network connection for many requests instead of opening a fresh one each time. Example: the TFB Plaintext test isolates keep-alive handling with nothing else in the way — no database, no serialization, just the accept loop.

TFB ran on physical, not cloud, hardware — an app server, a load-generator running wrk (the HTTP load-generating tool TFB standardized on), and a database server on switched 10GbE, most recently a Dell R440 (Xeon Gold 5120, 14/28 cores, 32GB RAM) — verified with a "preview" pass against unmodified forks before each round counted. That rigor is exactly why its ending is a cautionary tale rather than a footnote: TFB was archived on March 24, 2026, after Round 23 (February 2025, 330+ frameworks), because the project had gone stale — "virtually no changes... in recent years" — and its own numbers were being called "highly misleading." Two separate rot mechanisms did the damage: top-tier plaintext throughput was effectively capped near 30M rps by the wrk load-generator itself, not by any framework under test, and the rules permitted enough low-level overfitting that placement stopped reflecting real-world framework quality. TechEmpower didn't get slower; its stopwatch did. A successor, HttpArena, is emerging (16 test profiles, HTTP/2 and WebSockets, PR-triggered CI runs, an explicit "keep implementations realistic" mandate) but has no comparable history yet. The lesson for anyone building a benchmark ladder: a good instrument can still expire, either because the world outgrows what it measures or because the incentive to game it outlives the incentive to keep it honest. Treat TFB's own numbers as historical reference, not a live target — the project it measured had already outrun its own load-testing client before anyone pulled the plug — and note that Elixir/Phoenix's mid-pack-or-below TFB placement is not a clean immutable-language reference either, since Phoenix ran with a smaller database pool and heavier logging than some peers in certain rounds; raw Cowboy (Erlang, no Phoenix layer) would have been the fairer comparator but was never isolated in this pass.

Retired and unverifiable: thread-ring and the WhatsApp number

The CLBG thread-ring and chameneos-redux tests have been explicitly retired from the Computer Language Benchmarks Game's own summary comparisons; numbers still circulating for them (e.g., Go 9.4s vs. Erlang 8.5s at M=100/N=100,000) are third-party blog reproductions — the lowest-credibility figures in this entire survey, useful only as informal context, which is why they sit at rung 8 of the ladder below: lowest priority, context and never an external claim.

WhatsApp's famous 2012 claim of 2 million connections per server sits at the opposite end of the same problem: it isn't retired, because it was never verified to begin with. No disclosed, reproducible methodology backs it, so it gets cited here only as folklore, never as a target — flagged precisely because it keeps circulating as fact everywhere else, not because it deserves to be treated as one.

What's still worth measuring

Not everything in this survey has rotted. Some suites are exactly what they claim to be — self-reported, narrow, or unglamorous, but honest about those limits instead of quietly outliving them. These are the ones the goal ladder below actually draws its rungs from.

Skynet and Savina — what stresses an actor runtime

An actor is a lightweight, independent unit of computation that only communicates by passing messages, never by sharing memory — the concurrency model Erlang, Go's goroutines, and Hey all lean on to different degrees. Skynet is the sharpest single actor stress test in this survey: a root actor spawns 10 children, six levels deep, for exactly 1,000,000 leaf actors, each returning its ordinal number, all summed to a known expected total of 499,999,500,000. It measures actor-creation cost, garbage collection, and scheduler fan-in — deliberately not message throughput. On an i7-4771 under Ubuntu, Erlang finishes in 700–1,100 ms without its HIPE native compiler (HIPE actually makes it slower here, 2,100–3,500 ms) while Go finishes in 200–224 ms. On a 2015 MacBook 12″ (Core M) the same test takes Erlang 4,414 ms and Go 979 ms. There is no official Skynet leaderboard: every number circulating is self-reported on the author's own hardware, which makes it fine for tracking your own regressions but weak as an external claim without rerunning the comparators yourself.

Term: actor

Actor: an independent unit of computation that communicates only by passing messages, never by sharing memory. Example: Skynet spawns a tree of one million of them and sums the replies that come back up the tree.

Savina (Imam & Sarkar, AGERE! 2014; github.com/shamsimam/savina) is the more rigorous complement: 28 benchmarks in three groups (7 micro, 8 concurrency, 13 parallelism), of which the 7 micro-benchmarks — Ping Pong, Counting Actor, Fork Join Throughput, Fork Join Creation, Thread Ring, Chameneos, and Big — are the subset later actor-runtime papers keep re-citing. Their input parameters are fixed and published in the paper's appendix, so a Savina port is well-defined and its results are independently checkable, unlike Skynet's self-reported numbers. Between them, Big (many-to-many mailbox contention) and Chameneos (many-to-one contention) cover a stress pattern Skynet's tree never touches at all. (Thread-ring and chameneos-redux — Savina's CLBG-era cousins — are covered in the benchmark graveyard above.)

CLI startup and memory-per-connection: the unglamorous suites

Startup time is the wall-clock time from launching a program to it being ready to run — for scripting languages this is dominated by interpreter and runtime initialization, not by whatever the program actually does. There is no single dominant recognized suite here; the closest is bdrung/startup-time, a hyperfine-driven, disclosed-hardware comparison. On an i5-2400S: Lua starts in 0.63 ms, Bash in 0.71 ms, Perl in 0.94 ms, Python 2 in 9.43 ms, Python 3 in 25.84 ms, and Ruby in 32.43 ms. On a Raspberry Pi 3 the same ordering holds at roughly an order of magnitude (7.6×–13× depending on interpreter; Bash 7.31 ms, Ruby 421.53 ms). Sub-millisecond interpreter differences can still vanish under OS overhead: LuaJIT's first run (85 µs (microseconds)) beats plain Lua 5.1.4 (155 µs), but Linux process and loader overhead alone adds at least 250 µs regardless of interpreter, so that delta barely matters in practice. Modern CPython's own baseline (python -c) runs 54 ms, and just adding import requests pushes it to 150 ms — import-graph cost, not interpreter startup, dominates real-world Python init. Hey's own measured CLI startup, ~23 ms, sits in the Python 3/Ruby slow tier today, an order of magnitude above Bash and Lua.

Term: startup time

Startup time: the wall-clock time from launching a program to it being ready to run, usually dominated by interpreter or runtime initialization rather than the program's own logic. Example: Bash is ready in 0.71 ms; Ruby takes 32.43 ms to do nothing at all.

Memory-per-connection has no standardized suite at all — only one-off engineering write-ups, which is itself a finding. An idle connection is a connection (or actor) sitting open but not actively sending or receiving data, whose memory footprint still counts against total server capacity. Phoenix's "Road to 2 Million Websocket Connections" post reported 2.3M connections on a 64GB/20-core box, but per-connection memory was reported inconsistently within that same post: ~1.5KB counting only the process, versus 5–10KB/idle socket counting the process plus transport buffers — a methodology gap that has to be resolved before adopting either number. The one rerunnable artifact in this whole category is github.com/dsander/phoenix-connection-benchmark, and it is the best candidate to model Hey's own memory ladder on. On the other side, Go's gorilla/websocket with 8KB buffers runs about 32KB/socket in userland, and goperf.dev cites 200–500K idle connections on a 4-core/8GB box.

Term: idle connection & percentile

Idle connection: a connection or actor sitting open but not actively sending or receiving data, whose memory footprint still counts against total capacity. Example: a chat server holding two million idle WebSocket connections, each costing some number of kilobytes just to exist, whether or not a message is currently in flight.

p50 / percentile, since latency numbers appear throughout this piece even where this survey doesn't quote them directly: p50 (the median) is the latency below which half of all requests finish; p99 is the latency below which 99% finish, capturing the slow tail an average can hide. A p50 of 5 ms means half of requests returned in 5 ms or less, however slow the unlucky few were.

Which leaves one benchmark this survey hasn't touched yet — not because it rotted, and not because it's unglamorous, but because it's the one still waiting on an answer.

The one goalpost nobody holds

1BRC, the One Billion Row Challenge (Gunnar Morling, January 2024; github.com/gunnarmorling/1brc), asks for exactly one thing: parse one billion station;temperature text rows, emit the min/mean/max temperature per station, and verify the answer against a reference output, on a fixed 8-core eval instance. It exists because text parsing and aggregation at real scale exposes I/O strategy, string handling, and memory-allocation discipline all at once, in a way a synthetic microbenchmark cannot. The results form a real leaderboard: Java's fastest entry (Wuerthinger/Mai/Peterssen) does the whole job in about 1.5 seconds, using memory-mapped I/O (letting the OS page the file into memory instead of read() calls), SIMD scanning (processing many bytes per CPU instruction), and one thread per core. Ben Hoyt's Go series went from 1 minute 45 seconds down to 3.4 seconds across nine successive optimizations on his own laptop. Community Rust entries land around 1.2–2.5 seconds.

Now the gap. The only Erlang entry on record (jesperes/erlang_1brc) is single-threaded and unoptimized: 130 seconds on an i7-10610U, with the author noting it spends "almost all the time inside binary:split/3." That is a naive floor, not a competitive entry. Elixir has an open discussion thread with no strong confirmed result, and Haskell has a long-running optimization thread with no confirmed headline number either. No immutable-first language has a competitive, parallel 1BRC entry — which makes 1BRC a live, uncontested goalpost for that entire category of language, rather than a settled score to catch up to. It matters specifically for Hey because 1BRC stresses exactly the immutable-string and accumulation path where Hey's own known quadratic list-append would bite hardest: building up per-station aggregates from a billion lines is precisely the workload that punishes an append implementation that copies more than it needs to. Beating Erlang's naive 130-second floor would be a low bar cleared; landing in Go's or Rust's neighborhood would be a genuine, uncontested first-mover claim for an immutable-first language on this benchmark.

Term: 1BRC

1BRC (One Billion Row Challenge): parse one billion station;temperature text rows and emit min/mean/max per station, checked against a reference answer. Example: the fastest Java entry does the whole job in about 1.5 seconds; a naive single-threaded Erlang entry takes 130 seconds on the same class of task.

The eight-rung goal ladder for Hey

Folding all five suites together, weighted by verification quality and by what each rung would actually expose about Hey's implementation, gives eight ordered targets:

RungSuiteTargetWhat it exposes
1 TFB-rules plaintext, single core, pinned Hey at 19.5K rps today vs. Go's ~96K matched / ~133K static — target: within 3% of Go per-core The accept-model defect in isolation, zero JSON confound — highest information value of any rung
2 TFB-rules JSON serialization Hey's JSON/plaintext ratio within 10% of Go's own ratio (relative, falsifiable) JSON-construction cost, separated cleanly from accept-loop cost
3 Skynet, 1M-actor spawn-and-reduce, ported verbatim Erlang's non-HIPE band (~700–1,100 ms) as immutable parity; stretch: within 2× of Go's ~200–224 ms Actor creation and GC overhead at the millions-of-actors scale
4 Savina's 7 cited micro-benchmarks, paper-fixed parameters Publish the full 7-number table Mailbox contention (many-to-many and many-to-one) that Skynet's tree never touches
5 1BRC, single-threaded lane first Beat Erlang's naive 130s; stretch: same order of magnitude as Go's parallel 3.4s Whether the append/allocation family is dead in a realistic workload; an uncontested first-mover claim for an immutable-first language
6 CLI startup, hyperfine hello-world Hey's ~23 ms today → sub-5 ms on comparable hardware Falsifies against a rerunnable public suite; matters because Hey markets itself on ergonomic scripting
7 Memory-per-idle-actor at N=100K and N=1M Bracket the 1.5–10KB/idle band, reporting both checkpoints, modeled on dsander/phoenix-connection-benchmark Real memory cost per held actor/connection, not the disputed 1.5KB folklore number
8 Thread-ring / chameneos, informal parity check Lowest priority — retired from the CLBG scoreboard; third-party numbers only Context, never an external claim

The numbers again, in one place

TechEmpower archived March 24, 2026, after hitting a ~30M rps client-side cap. No immutable-first language has beaten Erlang's naive 130-second 1BRC floor against Java's ~1.5-second winner. Skynet's one million actors take Erlang 700–1,100 ms and Go 200–224 ms. Hey's CLI starts in ~23 ms today, against a <5 ms goal, an order of magnitude above Lua and Bash's 0.6–0.9 ms. Eight rungs, eight falsifiable targets, above.

Glossary

benchmark suite
A fixed, repeatable set of tasks measured the same way across contenders, so results are comparable rather than anecdotal.
rps
Requests per second: how many requests a server completes each second under load.
p50 / percentile
The latency below which a given percentage of requests finish; p50 is the median, p99 captures the slow tail.
keep-alive
Reusing one network connection for many requests instead of opening a fresh one each time.
actor
An independent unit of computation with private state that communicates only by passing messages, never by sharing memory.
1BRC
One Billion Row Challenge: parse a billion text rows and emit aggregates per key, checked against a reference answer.
startup time
Wall-clock time from launching a program to it being ready to run, usually dominated by interpreter/runtime initialization.
idle connection
A connection or actor held open but not actively exchanging data, whose memory still counts against capacity.
